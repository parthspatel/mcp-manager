IPC channels for CLI/TUI/GUI ↔ Core

Neutral inventory of the local-machine transport channels the MCP Manager core could expose to its clients. Covers Unix domain sockets, Windows named pipes, abstract sockets (Linux), TCP loopback, and the cross-platform Rust abstractions over them. Permission model, discoverability path, and platform caveats are recorded per option.

Channel inventory

Channel Platforms Identity / address Permission model Notes
Unix domain socket (UDS) Linux, macOS, BSDs, Windows 10+ (limited) Filesystem path, e.g. $XDG_RUNTIME_DIR/mcp-manager.sock POSIX file mode + owner/group; SO_PEERCRED reveals client uid/gid/pid Standard library + tokio provide native support. Linux additionally supports abstract sockets (leading \0) outside the filesystem.
Windows named pipe Windows only \\.\pipe\mcp-manager SDDL security descriptor passed to CreateNamedPipeW; default DACL grants Everyone read GetNamedPipeClientProcessId and ImpersonateNamedPipeClient let the server identify / impersonate the caller.
Abstract UDS namespace Linux only Path with leading NUL byte; not bound to filesystem No filesystem permissions — anyone in the same network namespace can connect Survives without a runtime dir, but loses filesystem-mode gating. Not portable to macOS / Windows.
TCP on 127.0.0.1 All 127.0.0.1:<port> (or ::1) Any local process can connect(); auth must be application-layer (token, mTLS) Loopback packets are not normally observable by other hosts but are observable to any local user via netstat + port scan. Works in browsers / WebViews where UDS doesn't.
Stdio of child All (parent ↔ child only) Inherited file descriptors Tied to process tree — child inherits parent's privileges Pattern MCP itself uses for stdio-transport servers; Tauri "sidecar" is the same idea. Not viable when N decoupled clients exist.
Tauri-internal IPC All (GUI-only) WebView ↔ host process pipe Bounded by OS process isolation + Tauri capability manifest Not reachable from CLI/TUI. Useful only if core ships inside the GUI binary.

Rust cross-platform crates

interprocess — full local-IPC toolkit

Provides a local_socket abstraction implemented as UDS on Unix and named pipes on Windows. Tokio-async feature available; supports both filesystem-path and (Linux) namespaced creation modes. Documents the platform-specific caveat that Windows has no filesystem-path pipe path — only the \\.\pipe\ namespace.

parity-tokio-ipc — Tokio transport over UDS + named pipes

Endpoint API that hides the UDS / named-pipe split behind tokio::net::UnixStream (Unix) and tokio::net::windows::named_pipe (Windows). Used by several Substrate-derived projects.

Standard library + tokio directly

std::os::unix::net and tokio::net::UnixListener/UnixStream on Unix; on Windows, tokio::net::windows::named_pipe. Axum has an official UDS example wiring its router to a UnixListener.

Discoverability — where the socket lives

Linux

XDG_RUNTIME_DIR (typically /run/user/<uid>) is the per-user runtime directory; the spec mandates mode 0700, owner-only. A socket at $XDG_RUNTIME_DIR/mcp-manager.sock inherits owner-only access without an explicit chmod on the socket file, because the parent directory walls it off.

macOS

No XDG_RUNTIME_DIR by default. Common patterns: $TMPDIR/mcp-manager.sock (per-user temp), ~/Library/Application Support/mcp-manager/run/sock, or $HOME/.mcp-manager/sock. Whatever the choice, the socket file's POSIX mode must be tightened to 0600 on creation — $TMPDIR is owner-only on stock macOS but /tmp is not.

Windows

Pipes live in the \\.\pipe\ kernel namespace; default DACL grants Everyone read access. The recommended pattern is to pass an explicit SDDL string to CreateNamedPipeW at creation time. A pipe name like \\.\pipe\mcp-manager.<username> reduces collision risk in multi-user sessions; "WD" in SDDL is the well-known SID for Everyone.

Comparable products

Docker's daemon socket is conventionally /var/run/docker.sock with mode 0660 owned root:docker. Group membership gates access. MCP Manager is a per-user tool, so a per-user runtime directory is the closer analogue.

Browser / WebView reachability

Browsers cannot connect() to a Unix domain socket; if any client (GUI WebView, future remote console) is a browser, that client needs HTTP loopback or a Tauri-internal bridge. Most Chromium-based WebViews can talk to 127.0.0.1 but localhost permissions still trip mixed-content and CORS checks. tonic-web bridges browsers into a tonic gRPC backend at the cost of a tower-layer in front of the gRPC service.

Concurrency & connection model

  • Unix sockets: connection-oriented (SOCK_STREAM) like TCP; one accept per client; multiple concurrent client connections fine.
  • Windows named pipes: each CreateNamedPipe call instantiates one instance; max-instances is configurable. Async overlapped IO is the modern path; tokio::net::windows::named_pipe wraps this.
  • HTTP loopback: any number of TCP connections; HTTP/2 multiplexes streams over one connection — the same property that makes gRPC efficient.
