Auth — who can talk to the daemon

The client API is local-machine by design, so the threat model is "any other user on this machine should not be able to drive my daemon" — equivalent to Docker's longstanding socket-permissions model. This page inventories the four mechanisms in play (filesystem permissions, peer-credential inspection, bearer tokens, capability passing) and notes which one is necessary for which client (CLI, TUI, GUI WebView, future remote console).

Per-client posture

CLI

Same user as daemon → owns the UDS by construction. No further auth required if the socket lives in $XDG_RUNTIME_DIR (mode 0700 directory) or in a per-user temp dir with the socket file set to 0600.

filesystem mode is sufficient

TUI

Identical posture to CLI — same process model, same user. No additional layer.

filesystem mode is sufficient

GUI (native windowing toolkit)

Same user → same posture. If GUI launches the daemon as a child via tauri::shell().sidecar(), FD passing or inherited UDS is an option.

filesystem mode is sufficient

GUI (Tauri WebView)

The WebView itself cannot connect() to a UDS. Two routes: (1) keep all IPC inside Tauri commands/channels and let the host process talk UDS to core; (2) expose an HTTP loopback endpoint and require a bearer token bound to the GUI session.

needs token if HTTP loopback

Future remote / multi-machine

Not in v1.0 scope, but a token + TLS layer over the same wire protocol is the standard extension path. Equivalent to Docker's tcp:// mode with --tlsverify.

explicit token + mTLS

Per-platform local-only socket recipe

Linux — owner-only socket in XDG_RUNTIME_DIR
  1. Resolve $XDG_RUNTIME_DIR; the directory is guaranteed mode 0700 by pam_systemd.
  2. Fall back to $HOME/.cache/mcp-manager/run with explicit chmod 0700 if XDG is unset (e.g. unusual containers).
  3. Create the socket inside; set socket file mode to 0600 (fchmod after bind).
  4. Optionally call getsockopt(SOL_SOCKET, SO_PEERCRED) per accepted connection to assert client uid == server uid.
macOS — owner-only socket in TMPDIR
  1. Resolve $TMPDIR (per-user on stock macOS); fall back to $HOME/Library/Application Support/mcp-manager/run/.
  2. chmod 0700 the directory if newly created.
  3. chmod 0600 the socket file after bind.
  4. Optional getsockopt(SOL_LOCAL, LOCAL_PEERCRED) check.
Windows — named pipe with restrictive SDDL
  1. Construct an SDDL string granting only the current user SID and SYSTEM read/write on the pipe.
  2. Pass it as lpSecurityAttributes to CreateNamedPipeW; the default DACL grants Everyone read, which is too permissive.
  3. On accept, optionally call GetNamedPipeClientProcessId for logging.

Token strategy when HTTP loopback is needed

If the GUI WebView (or any browser-based client) must reach the daemon over 127.0.0.1:<port>, filesystem permissions don't apply — the daemon is reachable to any local process. The mitigation is a session-scoped bearer token:

  • Daemon generates a random token at startup, writes it to a 0600 file in the runtime dir.
  • Token is required in Authorization: Bearer <token> on every request.
  • Token is short-lived in practice: it rotates each daemon restart, and the GUI/CLI re-reads from the same 0600 file.
  • Browser clients receive the token via an out-of-band channel (e.g. URL fragment that the host process injects into the loaded HTML, never a query string that would land in access logs).

This is the model Jupyter and many local IDE servers use; equivalent threat model is "any malicious process running as my user can read the token file and impersonate me" — at which point the attacker already has all the access of the daemon anyway.

Authorization (not just authentication)

Authentication answers "who is this caller". Authorization answers "is this caller allowed to do this thing". For v1.0 the answer is the same as Docker's: any authenticated caller has full control. Future room for differentiation:

  • Read-only token (e.g. for a status widget that should never start/stop servers).
  • Per-server scoped token (give a workspace tool access to one server's logs).
  • Privileged operations (system.shutdown) gated to the parent process token only.

Capability-style auth — handing out per-resource handles to the client — is implementable on Unix via SCM_RIGHTS FD passing, but with no portable Windows equivalent it is unlikely to be the v1.0 model.
