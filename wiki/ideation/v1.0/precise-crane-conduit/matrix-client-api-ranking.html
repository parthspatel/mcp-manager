How to read the criteria

Perf
Throughput and latency under typical loads (a few hundred RPC/s + a couple of log streams). Higher score = lower CPU + lower latency on the same hardware.
Debuggability
Can a developer poke this with off-the-shelf tools (socat, curl, nc, grpcurl) without writing custom code first?
Low codegen burden
Inverse of "how much build-time machinery / multi-language toolchain is required". Higher is better for contributors.
Cross-platform
Works on Linux, macOS, Windows out of the box, including in non-typical environments (WSL2, Docker dev containers, locked-down enterprise machines).
Web-reachability
Can a browser / Tauri WebView talk to this directly? Matters if any GUI client is HTML-based.
Streaming support
Native streaming semantics with at least TCP-level backpressure; bonus for protocol-level windowing or cursor-resume.
Schema versioning
Strength of backward/forward compat guarantees and the tooling around them.
Security boundary
Default posture — does kernel/filesystem enforce "only me", or must the application bolt on a token?
Rust ecosystem maturity
How well-maintained are the relevant crates? Are they used in production by other Rust projects?

Sensitivity probes

Some weight movements expose where the ranking is fragile:

  • Crank web-reachability to dominate → REST+SSE and Tauri-native overtake everything else. (Implication: if Stream 5 picks Tauri, that biases the answer here.)
  • Crank streaming support + perf → gRPC pulls ahead but only marginally; the gap narrows once debuggability is weighted back in.
  • Crank debuggability + low codegen burden → JSON-RPC and NDJSON climb above gRPC and Cap'n Proto.
  • Crank schema versioning → protobuf-backed stacks (gRPC, MessagePack with versioned envelopes — to a lesser degree) and Cap'n Proto are the only acceptable answers.
  • Zero out web-reachability (assume native-GUI) → the UDS-based stacks dominate.

What the matrix doesn't capture

The score is a simplified blend; some real considerations are categorical not numeric:

  • MCP affinity: MCP itself uses JSON-RPC 2.0 over stdio / Streamable HTTP. Picking JSON-RPC for the client API means the same parser/codegen work serves both. Not a numeric criterion, but a real architectural lever.
  • "One-binary" deployment: if Stream 3 lands on library-not-daemon, the wire format is between in-process Rust and a host-process Rust — both ends are guaranteed to be the same version, which collapses several of these criteria.
  • Contributor pool: JSON-RPC is the lowest-barrier for occasional contributors; gRPC and Cap'n Proto require more onboarding.
