Schema evolution & versioning

The MCP Manager core and its three clients are versioned independently: a user might upgrade the GUI without realizing the daemon is older, or vice versa, or have a long-running CLI script pinned to an old format. Each wire-format candidate has its own story for adding fields, removing fields, evolving enums, and negotiating compat between mismatched versions. This page collects those stories neutrally.

Wire-format options & their evolution model

JSON (+ JSON Schema) Yes — keys carry meaning Safe; old client ignores it Safe if old client tolerates absence By convention; additionalProperties can be loose or strict
Protobuf (proto3) Partially — field numbers only Safe iff new field gets new number; lower numbers cheaper to encode (1–15 take 1 byte) Don't change numbers, don't reuse; reserved keyword prevents accidental reuse Adding fields is the safest operation; never reuse field numbers
Cap'n Proto No — schema-driven offsets Safe; new @N ordinals appended Don't reorder ordinals; values keep deserializing Built-in SchemaLoader compatibility check
MessagePack Yes for maps; no for arrays Safe if map-encoded; arrays are positional Safe if map-encoded By convention; depends entirely on encoder choices

Protobuf — the rule-of-five

  1. Never change a field number — equivalent to deleting + re-adding.
  2. Never reuse a number — old binaries decoding under the old type get silent corruption.
  3. Reserve removed numbers with the reserved keyword to prevent accident.
  4. Use numbers 1–15 for hot fields — they take one wire byte.
  5. Don't change required-ness or types — only safe to widen int32 → int64 in a single direction.

In Rust, prost assigns tags sequentially starting at 1 by default; explicit #[prost(tag = "...")] attributes are needed to skip reserved numbers.

Cap'n Proto — schema as forward-compat machinery

Cap'n Proto's design philosophy explicitly pushes validation to application layer and frames evolution as a first-class concern. Compatibility rules:

  • Add new fields/methods/enumerants only at the end (higher ordinals).
  • New method parameters must be added at the end and have defaults.
  • SchemaLoader auto-detects compatible vs incompatible schema pairs at runtime.
  • No "required" — every field has a zero value and silently fills in if absent.

Tradeoff: this is the strongest static evolution story, paid for with a code-generation step and a tooling ecosystem that is smaller than protobuf's.

JSON Schema / OpenAPI — schema-first for JSON wire

OpenAPI 3.1 is 100% compatible with JSON Schema draft 2020-12; in 3.1 the legacy nullable attribute is gone in favor of plain type: [..., "null"] arrays. The Schema Object can declare its $schema dialect explicitly. For a JSON-based API this provides: editor tooling, codegen, mock servers, request validation, contract testing.

Versioning policy with a schema-first JSON API typically uses URL versioning (/v1) or media-type versioning (Accept: application/vnd.mcp-manager.v1+json). Within a major version, additive changes are non-breaking by convention; removals require a new major.

Semver of the API surface

A separate version from the daemon binary version:

  • Major: bumped on any removal or shape change — old client refuses to talk.
  • Minor: bumped on additive change (new method, new optional field, new event topic). Old clients keep working.
  • Patch: docs / clarifications only.

The system.version method returns both the daemon's build version (semver of the binary) and the API version (semver of the wire surface). Clients should compare API major before making any other call and refuse if they don't match.

Negotiation patterns

Header / parameter (REST + JSON-RPC)

Client sends X-MCP-API-Version: 1 (or JSON-RPC param "api_version": 1). Server rejects with a defined error code if the major doesn't match. This is the lowest-effort approach.

Reflection + capability discovery (gRPC)

gRPC reflection lets clients fetch the server's proto descriptors at runtime, used by tooling like grpcurl. For runtime compat checks, a typed SystemService.GetCapabilities returning a feature-flag set is the more common pattern.

Schema attached to every message (Cap'n Proto SchemaLoader)

Cap'n Proto can compare the schema embedded in a binary against the one the consumer knows. This is heavier than a version number but catches semantic skew (e.g. enum widening) automatically.

Versioned envelopes (MessagePack / NDJSON)

With no native schema mechanism, the only durable approach is to wrap every payload: 

{ "v": 1, "type": "runtime.state_changed", "payload": { ... } }

Consumers branch on v. Pragmatic but easy to drift without discipline.

Compatibility matrix the daemon must support

ScenarioExpected behavior
Newer client, older daemon Daemon rejects unknown methods with a stable error code; client falls back to documented compatibility plan or refuses to start.
Older client, newer daemon Daemon must keep old methods working until next major. New fields in responses are tolerated — old client ignores them.
Same major, drifted minor Always allowed. Client may not see new event topics introduced after its release; that's fine.
Different major Daemon rejects v0 if it now speaks v2. Surface a clear error: "update your client".
