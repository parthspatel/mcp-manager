Research — Rust TUI tooling for the MCP Manager TUI

A TUI like lazydocker or k9s is the natural "between" surface — running in a terminal, but interactive and continuously redrawn. The Rust ecosystem effectively has two viable framework choices (ratatui and cursive), one component-model add-on (tui-realm), and three terminal backends (crossterm, termion, termwiz).

Framework choices

ratatui is the active fork of tui-rs after the original was archived, and is described on its homepage as a "lightweight Rust crate for building complex terminal user interfaces with widgets, utilities, and immediate rendering capabilities" . It is the default choice for new Rust TUIs and powers the largest production apps in the space .

cursive is the higher-level alternative: a declarative, retained-mode TUI library where you compose views and the framework manages the event loop, focus, and dialog stacking . It supports multiple backends (ncurses, termion, crossterm).

tui-realm is not a competitor to ratatui but an add-on on top of it that introduces a React/Elm-style component model: components own state, receive events, and communicate via messages through a global update routine .

// ratatui — immediate-mode draw loop with intermediate buffers.
use crossterm::event::{self, Event, KeyCode};
use ratatui::{prelude::*, widgets::*};

fn main() -> std::io::Result<()> {
    let mut terminal = ratatui::init();
    let mut counter = 0u32;
    loop {
        terminal.draw(|f| {
            let block = Block::default().title("MCP servers").borders(Borders::ALL);
            let p = Paragraph::new(format!("counter: {counter}")).block(block);
            f.render_widget(p, f.size());
        })?;
        if let Event::Key(k) = event::read()? {
            match k.code { KeyCode::Char('q') => break,
                           KeyCode::Char('+') => counter += 1, _ => {} }
        }
    }
    ratatui::restore();
    Ok(())
}

You rebuild the widget tree every frame; ratatui diffs into an intermediate Buffer and only writes deltas to the terminal . No state is retained between draws — state lives in your App struct.

// tui-realm — components + messages.
// Components own props/state, emit Cmd, the View routes events.
use tuirealm::{Component, MockComponent, NoUserEvent, Event, Update};

#[derive(MockComponent)]
struct ServerList { component: SomeListWidget }

impl Component<Msg, NoUserEvent> for ServerList {
    fn on(&mut self, ev: Event<NoUserEvent>) -> Option<Msg> {
        match ev { /* ... */ Event::Keyboard(_) => Some(Msg::SelectionChanged) }
    }
}

tui-realm trades flexibility for structure — its component lifecycle, focus stack, and message routing are opinionated, and it adds dependencies on top of ratatui . Good fit when the TUI has many independent panes that need their own state machines.

// cursive — declarative retained-mode views.
use cursive::views::{Dialog, TextView};

fn main() {
    let mut siv = cursive::default();
    siv.add_layer(Dialog::around(TextView::new("Hello MCP")).button("Quit", |s| s.quit()));
    siv.run();
}

Cursive owns the event loop; you mostly describe the view hierarchy and attach callbacks. Easier for simple UIs and dialogs; less ergonomic for custom rendering and continuous data refresh than ratatui's per-frame draw model .

Terminal backends

Ratatui defines a Backend trait implemented for three crates, and the documentation explicitly recommends Crossterm for most tasks :

BackendPlatformsMouseAsyncWhen to pick
crossterm Windows + macOS + Linux + WSL Yes Yes — EventStream with the event-stream feature Default. Pure Rust, widely supported, active maintenance .
termion Unix only (no Windows) Yes No native async Only if you're locked into a Unix-only environment and want minimal deps .
termwiz Win+macOS+Linux (extracted from Wezterm) Rich (kitty-protocol, ImageProtocol, etc.) Yes If you specifically need Wezterm-native features (sixel, kitty graphics, full undercurl) .

Underline colors and some advanced styling are only supported by Crossterm and Termwiz, not Termion . The MCP Manager TUI needs to run on developer machines across all three desktop OSes, which immediately rules out termion.

Data-flow patterns

Three patterns dominate Rust TUI app architecture, all on top of ratatui:

1. Bare immediate-mode loop

One App struct + a draw(frame, app) function + a handle_event(app, evt) dispatcher. The pattern used by bottom, simple admin tools, and the official ratatui templates .

2. Component pattern

Each pane (server list, log tail, detail panel) is a struct implementing Component { fn draw(...); fn handle_event(...); fn update(...); }. The official "ratatui components template" formalizes this .

3. Elm/Redux pattern (tui-realm)

Msg enum + central update(state, msg) + side-effects via commands. tui-realm is the framework-shaped version; many ratatui apps adopt the same pattern by hand .

State management

Ratatui itself is stateless across frames; widgets are constructed fresh each draw . Long-lived state lives in the app: server list, selection indices, scroll positions, in-flight async tasks. The interesting question is how state changes from background tasks reach the UI thread.

The two patterns the ecosystem has converged on:

  • Channel-based: background tasks (polling the MCP Manager daemon, tailing logs) push into a tokio::sync::mpsc; the main loop multiplexes crossterm::event::EventStream + the channel using tokio::select! .
  • Shared state: an Arc<Mutex<AppState>> or Arc<RwLock<...>> written by background tasks and read on each draw. Simpler but couples the data model to the UI redraw cadence.

The ratatui FAQ explicitly discusses async patterns and points at tokio as the standard runtime for TUI apps that need concurrent I/O .

Mouse & advanced input

All three ratatui backends expose mouse events when enabled; crossterm and termwiz also support bracketed paste, focus events, and the Kitty Keyboard Protocol for distinguishing modifier-only releases . The ratatui components template includes a canonical pattern for routing mouse hover/click events to focused components .

// crossterm: opt-in mouse capture.
use crossterm::execute;
use crossterm::event::{EnableMouseCapture, DisableMouseCapture};

execute!(std::io::stdout(), EnableMouseCapture)?;
// ... event loop with Event::Mouse(MouseEvent { kind, column, row, ... }) ...
execute!(std::io::stdout(), DisableMouseCapture)?;

Although lazydocker (Go) and k9s (Go) sit in the same niche and inform the UX the MCP Manager wants, they don't constrain the Rust framework choice — they only show that the niche has shipped successful TUIs before.

The two production apps that are most directly architecturally informative — bottom and gitui — both run on ratatui + crossterm, which is the default stack the documentation also recommends .
