Analysis — Where each framework hits a wall

This page enumerates failure modes, not winners. Each framework has a regime where its design choices stop paying off; understanding that regime is what makes the recommendation page defensible.

CLI parsers — where they wall

clap (derive) default

  • Compile time: full clap_derive build is multi-second; clap (full) adds ~570 KiB of binary .
  • Runtime introspection: the derive API does not expose value_source or argument ordering — if you need to know which source set a value, you fall back to builder .
  • Dynamic subcommands: registering subcommands at runtime (e.g. plugin-style) is awkward; builder is the escape hatch .

clap (builder)

  • Verbosity: imperative builder code is significantly longer; reuse across subcommands requires explicit functions or augment_args .
  • Sync-with-types: nothing auto-syncs the parser to a Rust struct; easy to drift.

bpaf

  • Familiarity: applicative-style parser combinators are unusual in Rust; team onboarding cost is real .
  • Ecosystem gravity: most Rust CLI tooling (helpers, docs, snippets) targets clap first; bpaf integration with adjacent crates is rarer.

argh

  • Convention mismatch: argh follows Fuchsia conventions rather than POSIX/GNU — long-only options, no --flag=value equals syntax for some flags .
  • Shell completion: not built-in .
  • Niche: best when you're already inside the Fuchsia/Google ecosystem.

gumdrop

  • Feature gap: less popular than clap; no shell completion; doesn't deserialize directly to domain types .
  • Velocity: low recent activity; not a serious candidate for a new flagship CLI.

pico-args

  • No help generation: you write all --help text by hand .
  • No subcommand support: you write the dispatch loop by hand.
  • Use case: tiny single-purpose utilities. Not a fit for a docker-style CLI.

TUI frameworks — where they wall

ratatui + crossterm default

  • Immediate-mode learning curve: state must live outside the widget tree; new contributors typically write retained-mode-flavored bugs the first week .
  • No batteries: no built-in router, no focus stack, no theming system. Apps end up rolling their own — see the components template .
  • Async: works via crossterm::event::EventStream + tokio::select!, but the wiring is hand-written each time .

ratatui + termion

  • Windows: unsupported . Disqualifying for the MCP Manager's expected user base.
  • Async: no native async event stream.

ratatui + termwiz

  • Community: small relative to crossterm; most ratatui templates and examples assume crossterm .
  • Niche: pays off if you specifically need wezterm-class features (kitty graphics, sixel images).

tui-realm

  • Lock-in: opinionated about lifecycle and routing; you cannot mix it freely with bare ratatui patterns .
  • Extra dependency: adds another crate on top of ratatui; bug surface includes upstream changes in either.
  • Pay-off: dominantly worth it when you have many independent panes with their own state machines.

cursive

  • Custom rendering: declarative view model is harder when you need pixel-precise widgets or non-trivial layouts .
  • Async: not as natural as a select-loop driven app.
  • Mind-share: ratatui has the gravity; cursive is increasingly the road less travelled in 2025.

GUI frameworks — where they wall

Tauri 2 — WebView hybrid
  • Three rendering engines: WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux. CSS that works on Windows can break on Linux because WebKitGTK is behind on prefixes or renders fonts differently .
  • IPC boundary: every action that needs Rust state crosses a typed-but-async boundary; the v2 Channel API helps, but it is still serialization-bound for non-primitive payloads .
  • Linux dependency: requires webkit2gtk-4.1 on the user's system; older distros may need backports.
  • Two-team build: a Tauri app has a Rust side and a frontend side; CI complexity doubles vs a pure-Rust binary.
Dioxus desktop — WebView hybrid
  • Stability: 0.6 was a major rewrite of the CLI and ecosystem; pre-1.0 churn risk remains .
  • Frontend choice: you are choosing both your frontend framework and your shell at once; if you ever want to migrate to native, you migrate the whole UI.
  • Same WebView caveats as Tauri: three engines, GTK dependency on Linux .
egui — immediate-mode native
  • Native look: egui explicitly does not look native; controls are its own design language. Fine for "tool" apps (Rerun-style), worse for "consumer" apps .
  • Stability: the README warns that "if you want a GUI that…doesn't break when you upgrade it, egui isn't for you (yet)" .
  • IME: incomplete CJK input method support .
  • Layout: immediate-mode flex/grid is workable but verbose for complex form-heavy screens.
iced — Elm-style native
  • Accessibility: open accessibility issue has been unresolved for years; no Windows Narrator support .
  • Pre-1.0: 0.14 is the "final experimental release before 1.0", so breaking changes are still expected .
  • Subscription model: Elm-style async via Subscription is elegant but unfamiliar; team needs to internalize the pattern.
Slint — DSL-based native
  • License: GPLv3 for open-source apps; commercial use requires a paid royalty-free license . This is the single most likely deal-breaker for a project that wants to stay permissively licensed.
  • DSL learning curve: the .slint language is good but it is another language to learn and review .
  • Two-source UI: UI in .slint, logic in Rust; refactors cross both worlds.
GPUI — Zed's framework
  • Windows: not fully supported as of 2025 — the docs require macOS or Linux .
  • Stability: pre-1.0; "There will often be breaking changes between versions" .
  • General-purpose maturity: per the boringcactus survey, GPUI "lacks basic text input widget" and is "overly complex to use" for non-editor apps .
  • Community: most third-party docs and examples are written for Zed-flavored code, not general apps.
Freya / Xilem / Makepad — earlier-stage
  • Freya: usable but jank; smaller community than Slint or egui .
  • Xilem: alpha, no numbered release in a year as of survey time .
  • Makepad: 1.0 reached but appears built primarily for its own team; sparse docs .
  • All three are watch-list rather than pick for v1.0.

Is Tauri a hedge against pure-native limits?

The boringcactus survey makes a striking observation: of the 43 libraries tested, only four pass a minimal accessibility + IME baseline — Slint, egui, Dioxus, and WinSafe (Windows-only) . Two of those four are WebView-based. Phrased differently, choosing a WebView-hybrid GUI in 2025 means inheriting decades of browser engineering investment in screen readers, IME, text-shaping, and i18n — for free.

The cost: a separate frontend codebase, a typed-but-async IPC boundary, three WebView engines to test against, and a heavier toolchain. For a tool like the MCP Manager whose v1 GUI is mostly lists + forms + log streams (i.e. exactly what HTML does well), this trade looks favorable. Tauri's 2024–2025 work specifically addressed the worst parts of the boundary: ACL-based permissions, custom-protocol IPC, and the typed Channel API for streaming events .

Where Tauri stops being a hedge:

  • Pixel-perfect, framerate-sensitive UI (e.g. a Zed-class editor) — pick GPUI or Makepad if you can absorb their pre-1.0 risk .
  • Embedded / low-RAM targets — Slint is the only credible choice .
  • Pure-Rust shop hard requirement — pick Dioxus desktop, egui, or iced.

None of those special cases apply to a Docker-Desktop-like MCP Manager GUI, which is why Tauri sits at the top of the GUI recommendation and pure-native options sit just below it as "flippable" alternatives.
