Runtime sandboxing — Linux, macOS, Windows

A devenv profile gives a reproducible build. It does not restrict the running process. This page surveys the OS-level primitives the MCP Manager can layer on top to scope filesystem access, network egress, and IPC — and notes where each one is missing or weak.

Linux: namespaces & seccomp ecosystem

bubblewrap

bubblewrap is the unprivileged sandbox originally built for Flatpak. It leans on Linux user namespaces to construct a fresh PID, mount, network, IPC, and UTS namespace without needing root. The host filesystem is replaced with an empty tmpfs root, and the caller explicitly bind-mounts what the sandboxed process is allowed to see (typically --ro-bind /nix/store /nix/store for a Nix-built binary). 

# launch an MCP server with read-only /nix/store, isolated network,
# read-write access only to one project directory
bwrap \
  --ro-bind /nix/store /nix/store \
  --ro-bind /etc /etc \
  --proc /proc --dev /dev \
  --tmpfs /tmp \
  --bind /home/me/projects/foo /work \
  --unshare-all --share-net=no \
  --die-with-parent \
  --new-session \
  -- /nix/store/<hash>-mcp-server/bin/mcp-server-foo

bubblewrap accepts seccomp BPF filters via --seccomp <fd>, letting callers further restrict syscalls, and uses PR_SET_NO_NEW_PRIVS to neutralize setuid binaries inside the sandbox.

firejail

firejail is a SUID helper that ships pre-built profiles for >1,000 desktop applications. It composes namespaces with seccomp-bpf via a higher-level profile language. Because it is SUID-root, it has historically had more CVE surface than bubblewrap; for a daemon-launched MCP server it is overkill compared to direct bubblewrap invocation.

nsjail

nsjail (Google) combines namespaces, cgroups, rlimits, and seccomp-bpf via the Kafel policy language. It supports a TCP-listener mode (spawn one jail per connection) and is the go-to in production fuzzing and CTF infrastructure. Compared to bubblewrap, nsjail is heavier and aimed at server-side untrusted code execution; bubblewrap's filesystem story is finer-grained per the community.

Linux user namespaces directly

Both bubblewrap and nsjail are thin layers over the kernel's namespace API (clone(2) + CLONE_NEW*). A Rust daemon can call these directly through crates like nix or caps — useful when the manager wants no external runtime dependency, but a non-trivial amount of code to get right. Most projects prefer to shell out to bubblewrap.

macOS: sandbox-exec / Seatbelt

macOS's sandbox is configured through Sandbox Profile Language (SBPL), a Scheme dialect. The sandbox-exec binary applies a profile and then execs the child. The profile language is deny-by-default (deny default) plus explicit allow rules over filesystem, network, Mach IPC, and POSIX IPC categories. 

; mcp-server.sb
(version 1)
(deny default)
(allow process-exec)
(allow process-fork)
(allow file-read*
  (subpath "/nix/store")
  (subpath "/usr/lib")
  (subpath "/System")
  (literal "/etc/resolv.conf"))
(allow file-read* file-write*
  (subpath (param "PROJECT_ROOT")))
(allow network* (remote tcp "*:443"))
(allow mach-lookup (global-name "com.apple.system.notification_center"))

# invoke
sandbox-exec \
  -f /etc/mcp-manager/profiles/mcp-server.sb \
  -D PROJECT_ROOT=/Users/me/projects/foo \
  /nix/store/<hash>-mcp-server/bin/mcp-server-foo

Caveats: Apple has marked sandbox-exec deprecated since approximately 2016, but it remains functional on every shipping macOS, including current versions, and is still used internally by the system. A deprecation warning is printed to stderr on each invocation. No documented replacement exists for headless / non-App-Store sandboxing. SBPL is undocumented; profile authors typically iterate by running the target and reading ~/Library/Logs/DiagnosticReports/sandboxd.

Windows: AppContainer

Windows's documented isolation model for arbitrary Win32 processes is the AppContainer. Microsoft summarises six isolation domains:

  • Credential isolation — application identity blends user + app, preventing impersonation.
  • Device isolation — camera, microphone, GPS blocked by default; granted via capability.
  • File & registry isolation — explicit read/write paths only.
  • Network isolation — separate caps for Internet, intranet, and server-mode.
  • Process isolation — kernel-object sandboxing prevents cross-process effects.
  • Window isolation — UI isolation; less relevant to a headless MCP server.

Win32 App Isolation (public preview since 2023) layers low-integrity launch onto AppContainer for a baseline secured environment, configured by manifest. Capability sets are authored ahead of time and the OS enforces them.

For a Rust daemon spawning child processes, the relevant APIs are CreateProcess with a STARTUPINFOEX that carries security attributes plus CreateAppContainerProfile and DeriveAppContainerSidFromAppContainerName. Job Objects can layer resource limits (CPU, memory, process count) on top — analogous to cgroups on Linux.

Practical observations

  • The strongest parity story is Docker / Podman, covered separately in the escape hatch page; native sandbox primitives diverge substantially per OS.
  • SBPL's lack of public documentation means a small "profile library" for common MCP server shapes (filesystem, network-only, mixed) is a non-trivial recurring authoring cost.
  • On Linux, the cheapest path is bubblewrap + a small Rust wrapper that builds the argv from a declarative policy stored next to the devenv profile.
