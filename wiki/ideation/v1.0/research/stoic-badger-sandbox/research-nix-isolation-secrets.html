Secrets — survey of options

MCP servers routinely need API keys, OAuth tokens, and service credentials. This page catalogues the relevant secret stores in the Nix-adjacent world (sops-nix, agenix, SecretSpec), the platform-native keychains, the long-standing Unix tool pass, and HashiCorp Vault — and draws the boundary between what an MCP Manager should implement vs. what it should delegate.

Nix-native secret stores

sops-nix

sops-nix provisions secrets declaratively into a NixOS or home-manager system. Files remain encrypted in version control; decryption happens during the activation phase, not at build time (so secrets never enter the store unencrypted). Atomic-replace semantics mean the old secret stays present until the new one is in place, and rollback restores the old set.

Encryption backends include age, GPG, and cloud KMS (AWS, GCP, Azure, Vault). Yubikey works via the GPG or SSH-key path.

agenix

agenix is the simpler cousin: it encrypts secrets with the age tool using SSH public keys (your existing ~/.ssh/id_ed25519.pub plus your GitHub-published keys, if you choose). Decrypted secrets land at runtime under /run/agenix/<name>, owned by a configured user/group, ready to be read by a service. 

# secrets.nix — who can decrypt what
let
  alice = "ssh-ed25519 AAAA…alice";
  bob   = "ssh-ed25519 AAAA…bob";
in {
  "openai-api-key.age".publicKeys = [ alice bob ];
}

SecretSpec (devenv-adjacent)

SecretSpec separates the declaration of secrets ("this app needs DATABASE_URL and OPENAI_API_KEY") from where the value lives. The declaration is a checked-in secretspec.toml; the storage is one of many backends:

  • System keyring (macOS Keychain, gnome-keyring, KWallet — via libsecret)
  • dotenv files (legacy / quickstart)
  • Environment variables (CI)
  • Unix pass
  • 1Password, LastPass, Bitwarden Secrets Manager, Proton Pass
  • AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault / OpenBao
# secretspec.toml — declaration only, never a value
[project]
name = "my-mcp-server"

[profiles.default]
OPENAI_API_KEY = { description = "OpenAI", required = true }
GITHUB_TOKEN   = { description = "GitHub", required = false }

# run, sourcing from the user's macOS Keychain
secretspec run --provider keyring -- mcp-server-foo

devenv's own guidance is to load secrets at runtime, not into the shell: keep the dev shell free of secret env vars and exec the server through secretspec run.

OS-native keychains

macOS Keychain

Available via the security CLI and the Security framework. The Rust keyring crate maps onto it transparently and is what most cross-platform tools use.

Linux: gnome-keyring + libsecret

The Secret Service D-Bus API is implemented by gnome-keyring (and by KDE's ksecretservice). Clients link against libsecret — the modern, thread-safe, async-capable successor to libgnome-keyring. The CLI front-end secret-tool can store and retrieve from shell scripts. The Rust keyring crate uses libsecret on Linux.

Windows: Credential Manager + DPAPI

The Data Protection API (DPAPI) provides per-user (and per-machine) encryption tied to the user's login secret. windows-dpapi is a safe Rust wrapper. The higher-level "Credential Manager" stores named blobs and is what the Rust keyring crate uses on Windows. Scope::User data is only decryptable by the same user on the same machine; Scope::Machine by any user on the same machine.

Unix-native: pass

The standard Unix password manager stores each secret as a GPG-encrypted file under ~/.password-store. Hierarchies map to folders, optional Git history is automatic, and the GPG agent caches the unlock for as long as the user configures. It is the lowest-tech option that still gives at-rest encryption and is what many engineers already use day-to-day on Linux/macOS. 

# typical usage
pass insert mcp/openai-api-key
OPENAI_API_KEY=$(pass mcp/openai-api-key) mcp-server-foo

HashiCorp Vault

Vault is the enterprise choice when secrets must be centrally administered, audited, and rotated. Vault Agent is the client-side daemon that handles auto-auth, token renewal, and template rendering of secrets into files or environment variables for the consuming process — it's the natural integration point for a desktop MCP Manager that pulls credentials from Vault rather than from a local keychain. 

# Vault Agent template fragment
template {
  source      = "/etc/mcp/openai.tpl"
  destination = "/var/run/mcp/openai.env"
}

Boundary: what the MCP Manager itself should ship

Three layers are useful to distinguish:

LayerSuitable ownerExamples
1. Secret declaration — what does this server need? MCP Manager (or SecretSpec re-used) secretspec.toml; manager's own schema
2. Secret storage — where does the value live? Delegate to OS keychain or external store libsecret, Keychain, DPAPI, pass, Vault, sops-nix
3. Secret delivery — how does the running MCP server get the value? MCP Manager (the spawner) Env vars set on execve, /run/agenix/*, ephemeral named pipes

Implications for design

  • The manager should never persist plaintext secrets itself. Treat the keychain / Vault as the source of truth.
  • SecretSpec already does layers 1 and 2 well; wrapping it (rather than reinventing) gives users a wide provider menu for free.
  • For Nix-using teams, sops-nix or agenix provides a check-in-friendly path for server-shaped secrets (admin credentials, deployment tokens). For per-user secrets (a developer's GitHub PAT), keychain integration is the better fit.
  • The non-Nix escape hatch must still hit the same keychain APIs through the Rust keyring crate so single-laptop UX doesn't degrade.

What the MCP spec says (and doesn't say)

The MCP specification recognises tools as “arbitrary code execution” and calls out user consent and tool-safety principles, but explicitly disclaims runtime enforcement: “MCP itself cannot enforce these security principles at the protocol level.” Secret storage is therefore entirely out of scope for the protocol; the host application owns the boundary.
