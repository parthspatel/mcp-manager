Tradeoff analysis

A neutral synthesis of the research pages. The questions: how strong is each option's isolation, what does it cost the user in install friction and ergonomics, and where does cross-platform parity break? The goal here is to make the design space legible — no recommendations, those live on the recommendation page.

Three axes of cost

  1. Isolation strength — how contained is a misbehaving or compromised MCP server?
  2. User-facing friction — what does the developer have to install and learn before the first server starts?
  3. Reproducibility — does “working last week” mean “working today” across machines?

Cross-platform parity, honestly

The single biggest divergence between options is how cleanly they cross OS lines:

  • Containers are the most uniform: the same OCI image runs on all three OSes via Docker Desktop, Podman, or Podman Machine. The cost is consistent: ~1s cold-start and a VM on macOS / Windows.
  • devenv works on Linux and macOS; Windows is via WSL, which is a usability cliff for non-power-users.
  • OS sandbox primitives diverge: bubblewrap (Linux only), sandbox-exec (macOS only, deprecated), AppContainer (Windows only). Any first-class “layered sandbox” story has to author three policy languages.

The Nix learning curve, quantified honestly

Community surveys consistently flag three independent learning burdens: the Nix expression language, the conventions of nixpkgs (overrides, callPackage, lib customisation helpers), and reasoning about whatever upstream tool is now living inside Nix. Several long-form retrospectives describe a multi-month productive-ramp.

devenv compresses this meaningfully by hiding raw Nix behind a TOML-flavoured attribute set with toggles, but it doesn't eliminate the learning cost — when something fails, error messages still reference store paths and Nix internals.

What does the threat model actually require?

MCP servers are explicitly “arbitrary code execution” per the spec; they inherit the host user's filesystem and network unless something intervenes. Documented in-the-wild attacks include the mcp-remote RCE (CVE-2025-6514, CVSS 9.6) and npm supply-chain compromises affecting MCP server packages. The threat model needs at least:

  • Per-server filesystem scoping (servers should not see ~/.ssh or ~/.aws unless explicitly granted).
  • Network egress controls (servers should default to no internet unless declared).
  • Pinned, ideally signed binaries (no implicit “latest” on launch).
  • Audit trail of secret access (the manager knows when which server obtained which key).

Three of those four are achievable by either the Nix-plus-sandbox path or the container path. Only “pinned, signed binaries” is meaningfully easier on the container side today, because of the Docker MCP Catalog's signing pipeline.

The two-tier model

The shape of the design space pushes naturally toward a two-tier offering:

  • Best-effort isolation by default — a Rust daemon that, for any MCP server, applies whatever isolation it can without user opt-in: pinned versions, OS sandbox if available, no network unless granted, no host FS outside an explicit project directory.
  • Strong isolation when Nix or containers are available — opt into devenv profiles + OS sandbox for reproducibility, or into Docker / Podman for catalog-driven isolation.

This is closely analogous to how Flatpak markets bubblewrap: the user picks an “app,” the runtime enforces a sandbox automatically; advanced users can author tighter policies. The lesson transfers.

Open tensions

Tension 1 — “Just runs” vs reproducible

Asking the user to install Nix to get a server running is a much higher bar than asking them to install Docker, which is much higher than “already has Node”. Each step up costs adoption and buys reproducibility / isolation.

Tension 2 — Cold-start vs sandbox strength

Containers cold-start in ~1s; native exec with a sandbox wrapper is <100ms. Some MCP host apps spawn-on-demand many short-lived servers. The manager may need to choose: a single supervised long-lived process per server (lower latency, more state), or per-call ephemeral containers (higher latency, no state).

Tension 3 — Windows parity

Nix on Windows means WSL, which is a partial fit. AppContainer is the right primitive for Windows-native isolation but capability-set authoring is its own learning curve. Containers via Docker Desktop work but require Hyper-V or WSL2.

Tension 4 — Secret store proliferation

The manager could integrate against 8+ secret backends directly, or it could delegate to SecretSpec and inherit a curated provider list. The latter is simpler but adds a transitive dependency and a second authority over secret schema.
