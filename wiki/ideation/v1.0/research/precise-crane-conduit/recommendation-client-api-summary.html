v1.0 / precise-crane-conduit / Recommendation

Stream recommendation — JSON-RPC 2.0 over UDS, with optional HTTP/SSE bridge

Recommended stack

  • Wire protocol: JSON-RPC 2.0 implemented with jsonrpsee; subscriptions for streams.
  • Primary transport: Unix domain socket on Linux/macOS, named pipe on Windows, via parity-tokio-ipc or interprocess; well-known path $XDG_RUNTIME_DIR/mcp-manager/api.sock (Linux), $TMPDIR/mcp-manager/api.sock (macOS), \\.\pipe\mcp-manager.<user> (Windows).
  • Optional secondary transport: HTTP/1.1 loopback with SSE for streams, gated by a bearer token, mounted only when a browser-based client (Tauri WebView, future web console) requires it.
  • Frame discipline: NDJSON over the raw socket — same framing MCP itself uses for stdio — so the daemon's stdio-MCP code path and its client-API code path share helpers.
  • Streaming: JSON-RPC subscription pattern (server-to-client notifications keyed to a subscription id). Every notification carries a monotonic cursor for resume-after-disconnect — Kubernetes-style.
  • Auth: filesystem-mode 0600 on UDS / restrictive SDDL on named pipe; bearer token additionally on the HTTP bridge if mounted.
  • Schema: JSON Schema (draft 2020-12, OpenAPI 3.1-compatible) co-located with the daemon, exposed via system.schema. Semver of the API independent of binary version.

Why this stack — linked rationale

The matrix at default weights ranks JSON-RPC-over-UDS in the top cluster on debuggability, codegen burden, cross-platform, and Rust ecosystem maturity, while losing only modestly on perf and schema versioning (see ranking). The decisive factors:

  1. MCP affinity. The Model Context Protocol itself uses JSON-RPC 2.0 over stdio and Streamable HTTP. The daemon already needs a JSON-RPC parser/encoder + NDJSON framer to talk to MCP servers. Reusing that code path for the client API halves the protocol-handling surface.
  2. Debuggability under field conditions. Users hitting bugs can describe what they see with socat and the daemon log. gRPC and Cap'n Proto would require us to ship and document a binary tool just to read the wire (analysis).
  3. Single-user, single-machine threat model. UDS in $XDG_RUNTIME_DIR (mode 0700 directory) needs no application-layer token. This matches Docker's well-understood model without inheriting its multi-user-via-group complexity.
  4. Tauri compatibility without dictating Stream 5. Tauri's GUI can either embed the daemon and use Tauri channels, or talk to a separate daemon over the optional HTTP/SSE bridge. The core can support both without redesign.
  5. Contribution barrier. Adding a method is "write a function + register". Adding a method to a gRPC service is "edit .proto + regenerate + write a function + register". That extra step compounds over the lifetime of the project.

What we accept by choosing this:

  • No protocol-level backpressure. Backpressure on log/event streams is TCP-buffer level. For the projected load (a few MCP servers, a few hundred log lines/s each) this is fine. If load grows past that we will need to add per-stream credit accounting in the daemon — not infrastructure, but extra code.
  • Hand-written schema discipline. JSON has no built-in evolution machinery. The daemon will ship JSON Schemas and version the API per versioning policy — discipline, not compile-time enforcement.
  • ~20–30% larger wire size than binary formats. Acceptable on a local socket; not a customer-visible cost.

Recommended schema sketch

Connection bootstrap

// Client opens UDS / named pipe; sends first frame:
{ "jsonrpc": "2.0", "id": 1, "method": "system.hello",
  "params": { "client_api_version": 1, "client": { "name": "mcp", "version": "0.1.0", "kind": "cli" } } }

// Server replies with negotiated version + daemon info:
{ "jsonrpc": "2.0", "id": 1,
  "result": { "server_api_version": 1, "min_api_version": 1, "daemon_version": "0.3.7",
              "capabilities": ["server.search", "runtime.attach"] } }

Representative unary call — runtime.start

// Request
{ "jsonrpc": "2.0", "id": 17, "method": "runtime.start",
  "params": { "server_id": "github-mcp", "idempotency_key": "01HEX..." } }

// Response
{ "jsonrpc": "2.0", "id": 17,
  "result": { "instance_id": "inst_01HEX...", "state": "starting",
              "operation_id": "op_01HEX..." } }

// On error
{ "jsonrpc": "2.0", "id": 17,
  "error": { "code": -32000, "message": "INSTALL_REQUIRED",
             "data": { "kind": "precondition", "retryable": false,
                       "details": { "server_id": "github-mcp" } } } }

Representative subscription — log.tail

// Subscribe
{ "jsonrpc": "2.0", "id": 42, "method": "log.tail.subscribe",
  "params": { "instance_id": "inst_01HEX...", "follow": true,
              "since_cursor": "cur_AAABl9xWqz" } }

// Response — subscription handle
{ "jsonrpc": "2.0", "id": 42,
  "result": { "subscription": "sub_01HEX..." } }

// Server-initiated notifications (one per line, NDJSON):
{ "jsonrpc": "2.0", "method": "log.tail.update",
  "params": { "subscription": "sub_01HEX...",
              "frame": { "cursor": "cur_AAABl9xWr0", "ts": "2026-05-24T14:25:01.412Z",
                         "stream": "stderr", "level": "info",
                         "message": "tool=create_issue duration_ms=143" } } }

// Unsubscribe
{ "jsonrpc": "2.0", "id": 43, "method": "log.tail.unsubscribe",
  "params": { "subscription": "sub_01HEX..." } }

Representative broadcast — event.subscribe

{ "jsonrpc": "2.0", "id": 1001, "method": "event.subscribe",
  "params": { "topics": ["runtime.state_changed", "install.*"],
              "since_cursor": "evt_01HEX..." } }

// Notifications carry their own cursor field
{ "jsonrpc": "2.0", "method": "event.update",
  "params": { "subscription": "sub_01HEX...",
              "event": { "cursor": "evt_01HEX...", "topic": "runtime.state_changed",
                         "instance_id": "inst_01HEX...",
                         "from": "starting", "to": "running",
                         "ts": "2026-05-24T14:22:00.412Z" } } }

Optional HTTP/SSE bridge — same calls, REST-shaped

POST /v1/rpc                                  // body = JSON-RPC envelope
Authorization: Bearer <session_token>

GET  /v1/streams/log?instance_id=inst_...      // text/event-stream (SSE)
GET  /v1/streams/events?topic=runtime.*        // text/event-stream (SSE)

# SSE frames mirror the JSON-RPC notification "params.frame" body 1:1,
# and SSE 'id:' lines carry the same cursor so EventSource auto-reconnect
# transparently resumes via Last-Event-ID.

Compat boundary with the daemon (Stream 3 handoff)

This stream commits to:

  • The on-wire format (JSON-RPC 2.0).
  • The transport (UDS / named pipe; optional HTTP/SSE).
  • The set of methods and their request/response shapes (see surface).
  • The versioning policy (semver of the API; system.hello negotiation).

This stream does not commit:

  • Whether the daemon is a separate process or a library linked into the GUI — Stream 3.
  • Which Rust crate hosts the JSON-RPC server module organization — Stream 3, though jsonrpsee is suggested.
  • Which framework each client uses to consume the API — Stream 5.

The contract Stream 3 receives: "implement these methods speaking JSON-RPC 2.0 over a tokio-async UDS / named-pipe listener, with NDJSON framing, exposing subscriptions for log/event streams". The contract Stream 5 receives: "your CLI/TUI/GUI may assume JSON-RPC over the path the daemon advertises, with the schemas in this stream's research pages".

Open questions for the orchestrator

  • Does the GUI ship Tauri (browser engine present) or a native toolkit? If native, the optional HTTP/SSE bridge can be skipped in v1.0. This blocks on Stream 5's framework decision.
  • Is multi-user (shared daemon for all users on a workstation) ever in scope? If yes, the recommendation shifts toward Docker-style group-permissioned socket plus bearer tokens.
  • Is the daemon expected to run as a system service (root-owned, system-level) or strictly per-user? This stream assumed per-user.
