Live updates — log tail, event subscriptions, metrics

Three operations are inherently streaming: log.tail, event.subscribe, and (optionally) live metrics. Streaming has its own design dimensions independent of the unary RPC choice: framing, backpressure, reconnect / replay semantics, and how the chosen IPC channel encodes "this connection is dedicated to a long-lived stream of N frames". This page enumerates the available transport-level patterns without choosing.

Backpressure mechanics in detail

HTTP/2 window-based (gRPC)

Default per-stream send budget is 64 KiB; as the consumer reads, WINDOW_UPDATE frames credit more bytes back to the producer. This is automatic and applies separately per stream, which means a slow log subscriber does not starve a parallel install-progress stream. gRPC layers a message-based view on top so producers see "message ready / not ready" rather than raw bytes.

TCP-only (everything else over a raw socket)

With NDJSON / MessagePack / SSE / WebSocket over a single connection, backpressure is just the OS socket buffer plus the producer's write returning EAGAIN / pending. In Tokio that surfaces as the async write future not progressing. If the protocol is multiplexed onto a single connection (e.g. JSON-RPC subscriptions sharing the socket with unary calls), a single slow reader stalls unrelated calls — the same head-of-line blocking problem HTTP/1.1 has and HTTP/2 solves.

SSE: simple but server-buffered

SSE has no application-layer flow control; the spec doesn't define one. Servers must implement their own buffering / drop policies. The benefit is in the client: EventSource auto-reconnects with exponential backoff and re-sends the Last-Event-ID header — if the server actually implements replay-from-id this is "free".

Reconnect & replay

A cursor (opaque monotonic token attached to each frame) is the lowest common denominator that works across every transport. Kubernetes uses resourceVersion for exactly this purpose: a watcher disconnected mid-stream reconnects with resourceVersion=<last_seen> and the server resumes from after that point — until the watch cache evicts the cursor, after which the client must do a fresh list. The MCP Manager event/log API can adopt the same envelope: 

// every frame:
{ "cursor": "evt_01HEX...", "kind": "runtime.state_changed",
  "instance_id": "inst_01HEX...", "from": "starting", "to": "running",
  "ts": "2026-05-24T14:22:00.412Z" }

// reconnect:
event.subscribe(filter={...}, since_cursor="evt_01HEX...")

Server side, the daemon needs a bounded ring buffer per topic; clients receiving a 410 Gone-equivalent error must do a fresh snapshot. Kubernetes' streaming-list feature in 1.32 packages this as a single response.

Mapping streams onto IPC choices

JSON-RPC over UDS

JSON-RPC 2.0 itself defines only request/response/notification, but its widely-used "subscription" pattern (used by Ethereum nodes, jsonrpsee, LSP) is: a subscribe method returns an opaque subscription id; subsequent server-to-client notifications tagged with that id are the stream. The jsonrpsee Rust crate ships first-class subscription support. Framing on UDS is typically NDJSON (one JSON value per line) — the same approach MCP itself uses for stdio.

gRPC over UDS (tonic)

gRPC's server-streaming and bidi-streaming map directly. Tonic's bidi pattern composes naturally with a tokio mpsc channel on each side; an example connecting tonic over a Unix socket exists in the tonic repo. Backpressure is HTTP/2-window automatic.

HTTP loopback + SSE (axum / hyper)

Axum has a UDS example; SSE works the same over UDS or 127.0.0.1. Critical caveat: EventSource only exists in browsers. CLI/TUI clients written in Rust still need to read the chunked text body manually (it is just text/event-stream framed by blank lines).

Tauri channels (GUI-only special case)

If the GUI ships core in-process, tauri::ipc::Channel<T> is the idiomatic streaming primitive — guaranteed ordering by index, fast post-v2 raw-bytes path. But this only solves GUI; CLI and TUI still need a separate channel.

Practical edge cases

  • Slow client: producer needs a policy — block, drop oldest, or sever the subscription with RESOURCE_EXHAUSTED. gRPC's flow control makes "block" the default; over raw sockets the daemon must implement this explicitly.
  • Daemon restart while client is subscribed: client gets EOF; cursor-based replay is the only way to recover without losing events.
  • Log bursts: a chatty MCP server can emit thousands of log lines per second. JSON encoding cost dominates if every frame is parsed; consider per-frame batching ({cursor, frames: [...]}) for high-volume streams.
  • Binary payloads: if any frame carries raw bytes (e.g. a downloaded blob from an install op), base64-in-JSON costs ~33%. MessagePack / protobuf / Cap'n Proto carry bytes natively.
