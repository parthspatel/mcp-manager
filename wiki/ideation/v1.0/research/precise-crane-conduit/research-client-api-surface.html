API surface — required operations by resource

Neutral enumeration of the operations the client API must expose so that CLI, TUI, and GUI can do everything users expect a "Docker for MCP servers" to do — manage installations, control runtimes, read/write config and secrets, and observe logs and events. Operations are grouped into six resources. Request and response shapes are illustrative, not yet bound to a wire format (that is decided in the recommendation page).

Operations by resource

server — managed MCP server definitions
  • server.list — return all known server definitions.
  • server.get(id) — fetch one definition with its current installation + runtime state.
  • server.create(spec) — register a new server (from manifest, URL, or template).
  • server.update(id, patch) — partial update of metadata or pinned version.
  • server.delete(id, opts) — remove definition; opts.purge also drops install + secrets.
  • server.search(query) — query a registry (server registry is Stream 1 territory; the API only needs to forward the result).

installation — version installation lifecycle
  • installation.install(server_id, version_constraint) — produces a long-running operation; emits progress events.
  • installation.uninstall(server_id, opts)
  • installation.upgrade(server_id, version_constraint)
  • installation.list_versions(server_id) — query candidate versions from registry / Nix derivations.
  • installation.verify(server_id) — hash/signature check.
  • installation.operation_status(op_id) — for async installs.

Representative request — start an install

// Request
{ "server_id": "github-mcp", "version": "^0.4.0", "force": false }

// Initial response (op handle)
{ "operation_id": "op_01HEX...", "kind": "install", "status": "running" }

// Progress events delivered on the events stream:
{ "kind": "install.progress", "op_id": "op_01HEX...",
  "stage": "fetch", "percent": 42, "message": "downloading github-mcp@0.4.2" }
{ "kind": "install.complete", "op_id": "op_01HEX...",
  "version": "0.4.2", "duration_ms": 12345 }
runtime — process control (start, stop, restart of MCP server processes)
  • runtime.start(server_id, opts) — returns instance_id on success.
  • runtime.stop(instance_id, grace_period_s)
  • runtime.restart(instance_id)
  • runtime.signal(instance_id, signal)
  • runtime.inspect(instance_id) — pid, started_at, resource usage if collected, last health probe.
  • runtime.list(filter) — running instances (analogous to a container listing).
  • runtime.attach(instance_id, request) — only meaningful for some sandboxes (Stream 2); may be unsupported.

config — read/write structured configuration
  • config.get(server_id, scope?) — merged view by default, or raw scope.
  • config.set(server_id, scope, patch) — JSON-merge patch.
  • config.unset(server_id, scope, key_path)
  • config.schema(server_id) — return JSON Schema for a server's config (lets GUI generate forms).
  • config.validate(server_id, candidate) — server-side validation before commit.
  • config.diff(server_id, candidate) — show effect of a candidate vs current.
secret — opaque credential storage (separate so the value never round-trips in logs)
  • secret.list(server_id) — returns key + metadata only, never values.
  • secret.put(server_id, key, value, opts) — value is write-only.
  • secret.delete(server_id, key)
  • secret.exists(server_id, key)
  • Note: no secret.get — secrets are injected into the server's environment by core, not handed back to clients. The keyring binding is Stream 3's concern.
log — server stdout / stderr / structured records
  • log.tail(instance_id, opts) — open a streaming log feed. opts.follow, opts.since, opts.until, opts.cursor (replay from a cursor — Kubernetes-watch-style).
  • log.page(instance_id, before_cursor?, limit) — non-streaming historical lookup.
  • log.export(instance_id, range, format) — bulk export for support bundles.

Representative streaming frame

{
  "cursor": "cur_AAABl9xWqz",
  "instance_id": "inst_01HEX...",
  "stream": "stderr",
  "ts": "2026-05-24T14:25:01.412Z",
  "level": "info",
  "message": "tool=create_issue duration_ms=143"
}
event — broadcast stream of state changes
  • event.subscribe(filter, since_cursor?) — long-lived stream.
  • Topics: runtime.state_changed, install.progress, install.complete, install.failed, health.transition, config.changed, secret.changed, system.error.
  • Each event carries a monotonic cursor so clients can replay from where they left off — same pattern Kubernetes watch uses with resourceVersion.
system — meta operations
  • system.version — daemon build + API version.
  • system.health — daemon's own self-check.
  • system.shutdown — graceful daemon shutdown (probably privileged).
  • system.events_replay(from_cursor) — bootstrap snapshot for late-attaching clients.

Cross-cutting requirements

  • Idempotency: mutating operations should accept a client-supplied idempotency key so retries don't double-install.
  • Long-running operations: install / upgrade / verify must return an op handle immediately; clients poll operation_status or subscribe to event.
  • Cursor-based replay: every stream (logs + events) emits monotonic cursors so a reconnecting client can resume without losing or double-delivering records.
  • Pagination: list operations on potentially large collections (logs, events history) must support cursor pagination.
  • Strong typing: every payload should be schema-described — see versioning.

Error envelope

A single envelope shape across all operations simplifies client code. JSON-RPC 2.0 defines a {code, message, data} error object; gRPC has canonical status codes; HTTP has status + body. A wire-protocol-neutral sketch: 

{
  "error": {
    "code": "INSTALL_FAILED",
    "message": "Nix derivation failed to build",
    "kind": "subprocess",
    "retryable": false,
    "details": {
      "exit_code": 1,
      "stderr_tail": "...",
      "operation_id": "op_01HEX..."
    },
    "trace_id": "trace_..."
  }
}
