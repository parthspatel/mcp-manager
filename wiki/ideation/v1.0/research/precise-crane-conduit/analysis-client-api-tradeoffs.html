Wire-format + transport tradeoffs

The four research pages enumerate facts in isolation. This analysis page treats them as a combined choice: an IPC channel, a serialization format, a streaming model, and a versioning style together form a wire-protocol stack. Eight stacks dominate the design space. The matrix in the next page scores them; this page argues neutrally about the axes on which they differ.

The eight stacks

Stack Channel Wire Streaming Schema source
1. JSON-RPC over UDS UDS / named pipe JSON, NDJSON-framed Subscription pattern JSON Schema (hand-written or generated)
2. gRPC over UDS UDS / named pipe protobuf, HTTP/2-framed Server-stream + bidi .proto files
3. REST + SSE over loopback HTTP 127.0.0.1 JSON request/response, SSE for streams SSE (server → client only) OpenAPI 3.1
4. REST + WebSocket HTTP loopback JSON over HTTP for unary, JSON over WS for streams WebSocket frames OpenAPI 3.1 + AsyncAPI
5. Cap'n Proto RPC over UDS UDS / named pipe Cap'n Proto Capability-style + futures .capnp files
6. MessagePack-RPC over UDS UDS / named pipe MessagePack Notification stream JSON Schema (msgpack mirrors JSON model)
7. NDJSON over UDS UDS / named pipe NDJSON Native — every line is a frame JSON Schema
8. Tauri-native (GUI only) Tauri IPC JSON (legacy) or raw bytes (v2) Channel<T> App-defined

Axis-by-axis analysis

Debuggability — "can I poke this with off-the-shelf tools?"

JSON-on-the-wire (stacks 1, 3, 4, 7) wins outright. socat - UNIX-CONNECT:$XDG_RUNTIME_DIR/mcp-manager.sock followed by a hand-typed JSON-RPC frame works on every Linux/macOS machine; on Windows the equivalent is nc or PowerShell against a named pipe. SSE responses are plain-text and curl streams them by default. WebSocket needs websocat but is still printable.

gRPC needs grpcurl + reflection turned on + the right proto if reflection is off. Cap'n Proto has no analogue to grpcurl; debugging requires generated tools or custom code. MessagePack is binary but trivially decoded with msgpack-cli or a one-line Python.

Codegen tax

JSON-RPC and NDJSON have none — write a Rust struct, derive serde, done. jsonrpsee ships proc macros for declaring methods/subscriptions but no separate compile step. OpenAPI doesn't require generation but rewards it.

gRPC requires a build.rs running prost-build/tonic-build on every change to .proto files; clients in other languages need their own toolchains. Cap'n Proto requires capnpc + capnpc-rust. Both are mature but add CI friction.

Cross-platform

UDS+named-pipe bridges (interprocess, parity-tokio-ipc) handle Windows transparently. HTTP loopback is the most portable — even WSL2 and constrained containers usually allow it. gRPC over Unix sockets needs the slightly fussy connect_with_connector shim on tonic.

Web-reachability

Critical iff the GUI ships as Tauri or any browser-based client appears. Browsers cannot dial UDS. Native HTTP/SSE/WebSocket work out of the box. gRPC requires the tonic-web tower layer and can only do unary + server-streaming. Cap'n Proto / MessagePack-RPC / JSON-RPC over UDS are not browser-reachable without a proxy.

An out: if the GUI ships as Tauri and core is in-process, the WebView never touches a network/UDS at all — it talks to the host process via Tauri commands and the host process talks to core via in-memory calls. This is fast but couples core's release cadence to the GUI's.

Streaming support

gRPC is the only stack with protocol-level backpressure (HTTP/2 windowing). Every other stack puts backpressure at the OS-buffer level — which is usually fine for the modest message rates the MCP Manager generates, but requires explicit thought for log-tail of a chatty server.

SSE has unparalleled client-side ergonomics in browsers (auto-reconnect, Last-Event-ID); for Rust clients it's just plain HTTP chunks. NDJSON over a raw socket is the simplest possible streaming model and the same model MCP itself uses for its stdio transport — there's something to be said for matching the surrounding ecosystem.

Schema versioning

gRPC/protobuf and Cap'n Proto have the strongest static guarantees. OpenAPI + JSON Schema rely on documented convention but tooling support is huge. Plain JSON-RPC has no schema mechanism unless one bolts on JSON Schema. Versioned-envelope MessagePack works but is the least disciplined option.

Security boundary

UDS in $XDG_RUNTIME_DIR is the simplest "any local user other than me cannot connect" story — kernel-enforced via filesystem mode. HTTP loopback is reachable to all local users by default and needs an application-layer token. Tauri's WebView is isolated by the OS process boundary plus Tauri's capability manifest.

Rust ecosystem maturity

jsonrpsee, tonic+prost, axum+hyper are all top-tier maintained, used in production at scale. capnp is mature but smaller; rmp-serde is mature; interprocess / parity-tokio-ipc are smaller-scale but battle-tested by Substrate-derived projects.

Friction examples — what does "developing against this" feel like?

JSON-RPC over UDS — flat learning curve
  • Test in shell with socat + handcrafted JSON one-liners.
  • Add a method: write a Rust function, register on the module, done.
  • Cross-language client (Python, TS): just JSON over a stream-socket — no toolchain.
  • Cost: no compile-time wire schema check; rely on tests + JSON Schema if discipline matters.
gRPC over UDS — typed but heavier
  • Define method in .proto; cargo build regenerates Rust types.
  • Test with grpcurl -unix /path/to/sock list, then grpcurl -d '{}' ... ServiceName/Method.
  • Bidi streaming is the strongest streaming primitive available.
  • Cost: every .proto change rebuilds. Cross-language clients need protoc + a grpc library.
REST + SSE — best browser story
  • Test with curl / HTTPie on the unary side, curl -N for SSE.
  • Auto-reconnect for browser clients comes for free.
  • OpenAPI 3.1 yields client SDKs and mock servers via off-the-shelf generators.
  • Cost: TCP loopback is open to other local processes; bearer token mandatory. Backpressure is TCP-level only.
Cap'n Proto over UDS — fastest, most fragile to debug
  • Zero-copy in-memory traversal.
  • Schema evolution rules are the cleanest of the bunch.
  • Cost: debugging requires generated tooling; ecosystem narrower than protobuf's.

Hybrid stacks are realistic

Nothing forces a single answer. Two practical hybrids:

  • "Core speaks JSON-RPC over UDS; an optional gateway exposes HTTP/SSE for browser clients." The gateway is the same binary or a sidecar that translates and adds a bearer token. Clients running locally as the same user use the fast path; Tauri WebViews or curl-debuggers use the slower path.
  • "JSON-RPC for unary, separate UDS endpoint for log/event streams using NDJSON." Eliminates head-of-line blocking and lets the streaming endpoint be tuned independently (larger buffers, drop policies) without affecting the request/response path.
