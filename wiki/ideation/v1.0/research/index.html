Rust MCP Manager — v1.0 Ideation

Six independent, evidence-grounded design explorations for a Rust-based MCP Manager comprising a core library/daemon plus CLI, TUI, and GUI clients — conceptually "Docker for MCP servers". Each stream produces neutral research, tradeoff analysis, an interactive ranking matrix, and a recommendation with linked rationale. Streams run in parallel with no shared memory; convergences below emerged independently.

Naming note (post-research rename): the research below consistently uses the original names — daemon mcpd and library crates mcp-core, mcp-protocol, etc. The v1.0 lockdown renamed these to binary mcpmanagerd (from crate mcpm-daemon), CLI binary mcpm (from crate mcpm-cli), and library crates mcpm-*. The audience-facing docs (overview, product, technical, UX) reflect the new names; this research is preserved as authored.

Addendum 2026-05-24 — Stream 6 added by user request

After the initial 5 streams completed, the user flagged a gap: the design covered how to read MCP server configs from existing hosts (Stream 1) but not how to project the canonical MCP Manager state back out to the many tools that consume MCP servers. Stream 6 (clever-fox-bridge) closed that gap: it catalogues 12 MCP-consuming tools, settles on managed-block as the default sync mode (Ansible-style fenced regions), picks TOML as the custom-toolchain spec format, and surfaces 6 scoping questions for the orchestrator.

Headline finding: schema drift means even bundled Tier-1 tool support has to be expressed as data-driven manifests, not hardcoded Rust — every Tier-1 tool ships schema changes every few months.

v1.0 lockdown — 2026-05-24 (latest)

The product owner reviewed all 6 streams + the GUI shootout + the gap analysis, and committed the following for v1.0. These supersede contradicting language in the original stream pages (kept as authored snapshots).

  1. Platforms: macOS + Linux only — permanently. Windows is dropped, never to return. Removes named-pipes / SDDL / AppContainer complexity from S4 and S2.
  2. Auto-spawn the daemon. mcpm exec auto-spawns mcpd on first call (~200ms one-time). On first launch, if the OS has a service manager (systemd-user on Linux, launchd on macOS), prompt the user once: "register mcpd as a background service?" — opt-in, not default. Obsoletes the proposed "mcpd-lite" from S6 entirely.
  3. Toolchain scope is user-configurable per registered project. Both per-user and per-project canonical scopes supported; the user picks when registering a project. Lockfile location follows the scope (per-user → ~/.config/mcp-manager/projection.lock; per-project → .mcp-manager.lock).
  4. JetBrains XML projection ships in v1.0. IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand all Tier-1.
  5. Daemon supervision: full process supervisor. Restart-on-crash with jittered backoff + max-attempts; cgroupv2-based OOM handling on Linux + jetsam-inferred on macOS; append-only JSONL audit log; ring-buffered tail API for 3 log streams (mcpd / each MCP server / audit). See the "Daemon supervision surface" card below.
  6. Distribution: curl-installer + Nix flake. Two paths for installing mcpd itself: a curl-piped install script (familiar UX) and a Nix flake (reproducible, the source-of-truth path). No Homebrew formula or App Store distribution in v1.0.
  7. GUI deferred to a future version. v1.0 surfaces are CLI + TUI + config files only. The GUI shootout is preserved as research for whenever the GUI ships (recommendation stands: Actix + Askama inside mcpd). Falls out: no Actix-Web in v1.0, no HTTP server in mcpd, no HTTP/SSE bridge — the wire is just JSON-RPC over UDS. See future features.
  8. Server discovery + install: multi-source federation. v1.0 ships with 3 default registries baked in (official = LF-stewarded MCP Registry, github = GitHub MCP Registry, docker = Docker MCP Catalog when Docker is present). Minisign on the index, cosign-when-present on packages. Users add private/corp sources via apt-style --signed-by. See closing-gaps/server-registry.
  9. Onboarding: mcpm init as a thin scaffolder (NOT a doctor). Interactive default + full non-interactive via --defaults -y. Idempotent (re-runs are no-ops). Direnv-style trust gate for project configs cloned from elsewhere. Service-manager prompt defaults to no because the daemon auto-spawns from mcpm exec anyway. See closing-gaps/onboarding.
  10. Secrets v1.0: one SecretStore Rust trait, two backends (OsKeyringStore via macOS Keychain / Linux libsecret + EnvVarPassthroughStore read-only escape hatch), composed via LayeredSecretStore. Values never on argv (rpassword-prompted). #[non_exhaustive] + opt-in subtraits leave room for v1.1 vault providers / rotation / leasing with zero re-architecture. See closing-gaps/secrets-lifecycle.
  11. Version management: range-in-manifest + exact-in-lockfile (Cargo/npm model). Three-phase MCP-spec-version negotiation (install-time allow-list check, initialize-time advertisement, wire-time re-check). Renovate vocabulary for mcpm update classification (PATCH / MINOR / MAJOR / DIGEST / PIN / MAINT + SPEC). Auto-runs mcpm test after every classified change. See closing-gaps/version-management.
  12. Health check. v1.0 ships mcpm test <server> — spawns the server, runs initialize + tools/list, reports status. CI-friendly.
  13. Documentation: mcpm help + mdbook in repo. CLI help text rich enough to be self-sufficient for power users; mdbook (docs/) for the docs site, built and deployed alongside the project.
  14. Curated community toolchain registry deferred to v1.1. v1.0's TOML escape hatch covers the immediate need. See future features (v1.1).
  15. No telemetry, ever. No phone-home, no anonymous metrics, no opt-in pings. This is a permanent project commitment, not a v1.0 deferral.
  16. License: Apache 2.0.
  17. Scale target: 10s of MCPs per user, not thousands. v1.0 optimizes for a few dozen managed servers; the daemon's memory/process budget reflects that.

Convergent v1.0 design

Decisions where two or more streams arrived at compatible conclusions independently, or where one stream had decisive evidence. These should be treated as the working baseline for v1.0.

Daemon model

Long-lived background process is required. Recommended pattern: podman/conmon-style per-server supervisor rather than a single central daemon (dockerd).

Converged from S1 (lifecycle gap), S3 (library-only unfit), S4 (assumed long-lived).

Async runtime

Locked to tokio. The official rmcp Rust MCP SDK is tokio-native; using anything else would mean re-implementing the SDK or running dual incompatible runtimes.

Source: S3 · Constraint type: upstream dependency.

Client surfaces: TUI + CLI + config files

v1.0 ships three interactive surfaces — no GUI:

  • CLI — clap with derive macros. Primary surface for scripting, automation, and power users.
  • TUI — ratatui + crossterm. Single-screen lazygit/k9s style with three left panes (Servers / Toolchains / Secrets) + contextual right pane. Mouse + keyboard.
  • Config files — TOML (mcpd's canonical state). Hand-editable. e in the TUI dispatches to $EDITOR; mcpd reloads atomically on save.

Detailed design — keymap, log multiplexing, source-URI shape, per-project layering, project detection + trust gate — captured at UX design — TUI + config files.

GUI is deferred. The GUI shootout remains as pre-decided research (Actix+Askama inside mcpd) for whenever a GUI is added; see future features.

Source: S5 + 2026-05-24 UX exercise + 2026-05-24 lockdown (GUI deferred).

Client ↔ daemon wire

JSON-RPC 2.0 over Unix domain socket. JSON-RPC affinity is decisive — MCP itself uses JSON-RPC, so the daemon shares its parser/encoder between client-facing and MCP-server-facing code.

The previously-mandatory HTTP/SSE bridge is no longer in v1.0 — it was required only to feed the Tauri GUI's WebView, and the GUI is now deferred. v1.0 is UDS-only; streaming (e.g. log tails) is JSON-RPC streaming over UDS.

Source: S4 · Simplified by 2026-05-24 GUI deferral.

Auth model

Filesystem-mode + peer-credentials check on UDS (SO_PEERCRED / LOCAL_PEERCRED) and restrictive SDDL on named pipes — kernel-enforced single-user auth, zero application-layer token logic for the local IPC path. Bearer token only for the HTTP/SSE bridge.

Source: S4.

Isolation

Two-tier: devenv (Nix) + OS sandbox primary (bubblewrap / sandbox-exec / AppContainer); Docker MCP Toolkit / Podman / pinned uvx-npx as escape hatch for non-Nix users.

Source: S2 · Forced by CVE-2025-6514 + supply-chain evidence.

Toolchain sync mode

Managed-block by default — Ansible-style fenced regions with begin/end markers. Pure-JSON tools degrade to sentinel-key fencing (Cursor) or sibling-file projection. Only strategy that simultaneously preserves hand-edits, stays idempotent, surfaces conflicts honestly, and works across TOML/YAML/JSONC/XML.

Behavioral asymmetry: additive-with-consent, subtractive-automatic. Adding a server prompts in N places; removing happens silently across N places. This rules out watch+reconcile as a default.

Source: S6.

Custom-toolchain spec

Declarative TOML (toolchain.toml) — the escape hatch for tools MCP Manager doesn't ship native support for. Comments are first-class, the Rust ecosystem already uses TOML (Cargo, mise, proto), and mcpd's own config is TOML — single-parser strategy minimises format surface.

Bundled tools also ship as TOML manifests, not hardcoded — schema drift in editors makes data-driven manifests the only sustainable option.

Source: S6.

Tool support tiers

Tier 1 (auto-detect + native projection): Claude Code CLI, Codex CLI, VS Code, Cursor, Zed, JetBrains family (IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand). JetBrains XML projection ships in v1.0 (user lockdown, 2026-05-24).

Tier 2 (opt-in projection): Windsurf, Continue, Cline, Goose, LibreChat, Claude Desktop.

Source: S6 + v1.0 lockdown.

Daemon UX: auto-spawn

The CLI mcpm exec wrapper auto-spawns mcpd if it isn't running (~200ms one-time, then a UDS connection). Subsequent clients (Zed, Claude Code, Cursor, …) get the already-running daemon for free. The proposed "mcpd-lite" alternative is obsolete.

On first launch (the first time mcpm runs at all), the CLI detects the OS's service manager (systemd-user on Linux, launchd on macOS) and prompts the user once: "register mcpd as a background service?". Opt-in, not default. The full first-launch UX is owned by closing-gap agent B (onboarding).

Source: S3 + v1.0 lockdown.

Toolchain scope: user-configurable per project

When the user registers a project with mcpm, they pick whether the canonical scope is per-user (one MCP toolset for all projects) or per-project (this project has its own toolset). Both are first-class. Default is per-user; opt-in to per-project at mcpm project init time.

Lockfile follows scope: per-user → ~/.config/mcp-manager/projection.lock; per-project → .mcp-manager.lock at the project root.

Source: S6 + v1.0 lockdown.

Platforms: macOS + Linux only

v1.0 ships macOS + Linux. Windows support is not in v1.0. Removes named-pipes / SDDL / AppContainer / Docker-Desktop-on-Windows complexity from the design space. UDS is the only IPC primitive; sandbox runtime is the macOS Sandbox + bubblewrap on Linux; service-manager integration is launchd + systemd-user.

Source: v1.0 lockdown (2026-05-24).

Distribution: curl + Nix flake

v1.0 ships two install paths: a curl -sSf https://… | sh installer (familiar UX, downloads a signed prebuilt binary), and a Nix flake (nix run github:user/mcp-manager; reproducible, the source-of-truth path). No Homebrew formula, no App Store, no AppImage in v1.0.

Source: 2026-05-24 lockdown.

Health check: mcpm test <server>

First-class CI-friendly command. Spawns the server in isolation, runs MCP initialize + tools/list, verifies a valid JSON-RPC handshake, reports tools/resources/prompts the server advertises, and exits with appropriate exit code. The TUI surfaces the same check as a per-server "verify" action.

Source: 2026-05-24 lockdown.

Documentation: mcpm help + mdbook

CLI help text rich enough to be self-sufficient (every subcommand has full examples, not just flag descriptions). Docs site is an mdbook under docs/ in the repo, built and deployed alongside the project. No separate docs-site repo.

Source: 2026-05-24 lockdown.

Project commitments (permanent, not v1.0-only)

  • License: Apache 2.0.
  • Platforms: macOS + Linux. Windows is never supported. Not a v1.0 deferral — a permanent project decision.
  • Telemetry: none, ever. No phone-home, no anonymous metrics, no opt-in pings. Permanent project commitment.
  • Scale target: 10s of MCPs per user, not thousands. Architecture optimizes for "a few dozen managed servers" — not a global package index.

Source: 2026-05-24 lockdown (permanent).

Server discovery + install

Multi-source federation. 3 default registries baked into the binary: official (LF-stewarded MCP Registry), github (GitHub MCP Registry), docker (Docker MCP Catalog, asked-once at mcpm init if Docker is present; CLI flag --docker-enable=true|false skips the prompt). Users add private/corp registries with mcpm registry add <name> <url> --signed-by <pubkey>.

Trust split: minisign Ed25519 on the index (required for defaults); Sigstore/PEP 740 verify-when-present on the underlying npm/PyPI package; cosign required for OCI images from the docker source.

Pubkey rotation: TUF-lite. A baked-in root key signs a runtime-fetched trust.toml manifest enumerating current registry pubkeys + valid_until dates. mcpd fetches with 7-day TTL. Per-registry rotation = update + re-sign + publish (zero user action). Root rotation = hotfix mcpd release (rare). See closing-gaps open questions §1 for the full manifest schema.

Search is local (BM25 over cached indexes); queries never leave the machine on default sources.

Source: closing-gaps/server-registry (Agent A, 38 citations) + 2026-05-24 sub-decisions.

Onboarding: mcpm init + mcpm uninstall

Thin scaffolder, not a doctor. Models on aws configure + terraform init + npm init -y. All choices have bracketed defaults; -y skips confirmations; --defaults accepts every default. Per-prompt flags also accepted for non-interactive scripting (e.g. --docker-enable=true).

Five canonical transcripts documented: lucky-day interactive (~30s), full non-interactive (Nix/CI), project-scope with import-from stub, freshly-cloned-repo with direnv-style trust gate, and the service-manager prompt (declines by default since daemon auto-spawns from mcpm exec).

Idempotent by construction; re-running is a no-op + summary.

mcpm uninstall performs symmetric cleanup: (1) unregisters from launchd/systemd-user if registered, (2) stops mcpd cleanly, (3) terminates managed MCP server children (SIGTERM → 5s → SIGKILL), (4) removes config directory (preserve with --keep-config), (5) keeps keychain entries by default (purge with --purge-secrets), (6) keeps the audit log + prints its path.

Source: closing-gaps/onboarding (Agent B, 37 citations) + 2026-05-24 sub-decisions.

Secrets lifecycle (v1.0 + extension surface)

One trait, two backends. SecretStore trait with OsKeyringStore (macOS Keychain + Linux libsecret via the keyring crate) and EnvVarPassthroughStore (read-only env-var escape hatch), composed via LayeredSecretStore. Service-string namespace: dev.mcp-manager.mcpd (reverse-DNS; the mcpd suffix leaves room for future sibling binaries without collision).

v1.0 CLI: mcpm secret set/list/unset. Values never on argv (rpassword TTY-only). Audit-logged as secret.{read,write,unset,list}; values never appear in events.

Code-signing: v1.0 ships macOS code-signed binaries (Apple Developer Program enrollment + notarization). TouchID-gated keychain reads (Secure Enclave) is a best-effort v1.0 stretch goal: ships if implementation is light (~20 lines of Rust + an `LAContext` bridge), defers to v1.1 otherwise. Linux biometric deferred regardless.

#[non_exhaustive] SecretRef + opt-in subtraits RotatableSecretStore / LeasedSecretStore mean v1.1+ vault providers (1Password, Bitwarden, Vault, Doppler, Infisical, AWS/GCP/Azure SM) plug in without re-architecture.

Source: closing-gaps/secrets-lifecycle (Agent C, 32 citations) + 2026-05-24 sub-decisions.

Version management + MCP spec negotiation

Range-in-manifest, exact-in-lockfile (Cargo/npm model). Lockfile (TOML) co-located with the projection lockfile per scope.

3-phase MCP-spec-version negotiation: (1) install-time check against mcpd's spec allow-list (baked into binary); (2) initialize-time advertise-and-pick per the MCP lifecycle contract; (3) wire-time re-emission as MCP-Protocol-Version header on every Streamable HTTP request. Per-server spec override: [server.<name>].spec = "2025-06-18" ships in v1.0 as an escape hatch for servers that lie about their advertised version (skips the install-time allow-list check; documented as "use only when you trust the server author").

mcpm update classifies changes with Renovate's vocabulary: [PATCH] auto-apply, [MINOR] confirm-once, [MAJOR] refused without --accept-breaking, [DIGEST] refused as supply-chain anomaly, plus a new [SPEC] class for spec-version bumps. Health check (mcpm test) auto-runs after each change with atomic rollback on failure; --no-test flag (or per-server test_on_update = false in config) disables for offline/air-gapped/CI environments.

Source: closing-gaps/version-management (Agent D, 45 citations) + 2026-05-24 sub-decisions.

Daemon supervision surface (full v1.0 scope)

mcpd is a real process supervisor for the MCP servers under its management, not a thin launcher. Locked v1.0 capabilities:

  1. Start / stop — primitive. Triggered by client requests over JSON-RPC.
  2. Restart on crash, with jittered exponential backoff and max-attempts:
    • Backoff schedule: delay = min(base × 2^attempt × (1 + rand(0, 0.3)), cap). Tentative: base=1s, cap=60s. The 30% jitter prevents thundering-herd when many servers all crash together (post-sleep, post-network-flap).
    • Max-attempts within a sliding window: e.g. 5 restarts in 600s. Exceeding the budget marks the server failed and stops retrying — prevents infinite restart loops for a server that crashes immediately on every boot. User must explicitly mcpm restart <server> to clear failed state.
    • Modeled on systemd's Restart=on-failure + StartLimitBurst + StartLimitIntervalSec semantics.
  3. OOM handling:
    • Linux: per-server memory limits via cgroupv2 (memory.max); OOM kills observed deterministically via memory.events. Optional memory.high for soft throttling. Treated as a crash for restart purposes; audit-logged with the OOM cause.
    • macOS: weaker observability — no native OOM events API. v1.0 will infer OOM from SIGKILL with no signal info + recent memory pressure (read via host_processor_info). Per-server limits via posix_rlimit RLIMIT_AS if requested; otherwise jetsam decides. Audit log marks the cause "OOM (inferred)".
  4. Audit log — append-only JSONL of every state change: {ts, actor, event, server, details}. Events: server.spawn, server.stop, server.crash, server.oom, server.failed, config.change, secret.read, secret.write, projection.write. Default rotation: daily files, 90 days retained, located at $XDG_STATE_HOME/mcpd/audit/ (Linux) or ~/Library/Logs/mcpd/audit/ (macOS).
  5. Tail-API access to three log streams:
    • mcpd itself — structured Rust logs via tracing + a ring buffer (e.g. 10MB in memory + on-disk rotation).
    • Each MCP server — stdout + stderr captured by the supervisor through pipes; per-server ring buffer (e.g. 4MB in memory).
    • Audit log — same JSONL file, tailable live as new entries land.
    All three exposed via:
    • CLI: mcpm logs --follow [<server> | --daemon | --audit], with --since, --lines, --grep filters.
    • GUI (Actix): three SSE endpoints — /logs/daemon/stream, /logs/server/<id>/stream, /logs/audit/stream. The browser tab can show all three side-by-side in real time (this is the SSE+HTMX strength that won the GUI shootout).
    • Wire: JSON-RPC logs.tail method over UDS, returns a streaming response.

Source: user directive #3 (2026-05-24). Implementation owner: steady-bear-foundation.

Open questions for v1.0 scoping

Most originally-open questions were resolved by the v1.0 lockdown decisions above. What remains:

✓ User directive #3: daemon supervision scope resolved 2026-05-24

Resolved by the user: mcpd is a real process supervisor — restart-on-crash with jittered backoff + max-attempts (prevents both thundering-herd and infinite-loop), OOM handling (cgroupv2 on Linux, jetsam-inferred on macOS), audit log of every state change, and tail API for three log streams (mcpd itself, each MCP server, audit). See the "Daemon supervision surface" convergent-decisions card above for the full enumeration. This also closes the previously-open "daemon ambition: how much supervision in v1.0?" question.

GUI stack — resolved to Actix + Askama resolved 2026-05-24

3 parallel agents evaluated Tauri+Leptos, Tauri+Dioxus (which pivoted to recommending Dioxus-desktop standalone), and Actix-Web+Tera/Askama. Weighted ranking matrix gave Actix 8.57 / Dioxus 8.13 / Leptos 6.71. Detailed comparison + sensitivity analysis at ui-shootout/.

Sub-decisions captured at shootout open questions: (a) tray icon ships in v1.0, (b) LAN binding opt-in (default localhost-only), (c) Tauri-shell-over-Actix as a v1.1 upgrade path if "browser tab" UX becomes a complaint.

✓ Daemon ambition / supervision surface area resolved 2026-05-24

Closed by directive #3 above. v1.0 commits to: start/stop + restart-with-backoff + OOM handling + audit log + tail API for three log streams. See the "Daemon supervision surface" convergent card for the full spec.

Linux sandbox-root enumeration depth — tentatively "medium"

For each Tier-1 tool, hardcode its Snap package name and Flatpak app ID, check those well-known paths in addition to the native ~/.config/<tool>/ location. ~5–10 stats per tool, no filesystem walk. The list of Snap/Flatpak IDs is part of each tool's TOML manifest (per S6's data-driven-manifests decision). User confirmed this is the right tier of aggressiveness; remaining open detail is the per-tool manifest population.

How to read each stream

Every stream follows the same four-stage flow. You can sample at any depth.

  1. research-*.html — raw factual landscape, every claim cited.
  2. analysis-*-tradeoffs.html — interpretation and tradeoffs, still neutral.
  3. matrix-*-ranking.html — interactive ranking matrix; drag weight sliders to re-rank live, click [n] evidence pills to jump to citations.
  4. recommendation-*-summary.html — the stream's recommendation with rationale linked to evidence pages and citations. The only place opinions appear.

Citations are footnotes at the bottom of each page; hover or focus any [n] to preview the source. Theme toggle in the top-right cycles light/dark/auto.
