Closing v1.0 gaps

The 2026-05-24 gap review identified five Tier-1 blocking gaps. Distribution was resolved directly (curl + Nix flake), and the GUI was deferred. The remaining four gaps — server discovery+install, onboarding flow, secrets lifecycle, version management — were each given to a focused-design agent. All four reported back; this hub summarises and links to their work.

Cross-agent convergence

Four independent agents (each unaware of the others) all converged on the same architectural principles. That's a robust signal.

Trait-based extension points

Each agent designed a v1.0 surface that v1.1 can extend without re-architecting:

  • Secrets: SecretStore trait, #[non_exhaustive] ref enum
  • Registry: RegistrySource trait (named + signed + cached) — multi-source federation built in
  • Versioning: per-server spec override, opt-in --accept-breaking, lockfile schema versioned
  • Onboarding: --import-from stubbed but already accepted as a flag

Argv hygiene

Three agents independently rejected putting sensitive data on argv (secrets via --value, install via --token, etc.). Universal pattern: TTY prompt (rpassword) or env-var passthrough. The fourth agent (versioning) doesn't surface sensitive values, but applied the same hygiene to its lockfile (no plaintext checksums or hashes leaking past safe boundaries).

Audit-log integration

Every agent emits audit events: secret.read/write/unset (C), config.change on lockfile updates (D), registry.refresh + registry.verify (A), project.trust + project.register (B). The common audit-log shape decided by directive #3 lands as the single sink. Schemas are non-conflicting; the orchestrator confirms the unified schema below.

Default trust = baked into binary

The "default registries" (A's 3 sources) and the "default mcpd spec allow-list" (D's 2 dates) both ship inside the mcpd binary. Updating either is a hotfix release, not a runtime manifest. Same model as OS-package-manager trusted-keys. Pubkey rotation cadence is the open question both agents flagged.

Idempotency by construction

Onboarding (mcpm init re-runs as no-op), registry refresh (re-syncs in place), version pinning (lockfile written atomically + rolled back on health-check failure), secret set (overwrites existing keychain entry with no error). v1.0's CLI surface is replay-safe end-to-end.

Cross-stream coupling on per-project scope

All four agents respected the v1.0 lockdown decision: canonical scope is user-configurable per registered project, lockfile location follows. Verified:

  • A: mcpm install --scope user|project consistent
  • B: mcpm project init distinct from mcpm init
  • C: per-project secret stores called out as a cross-stream open question for v1.1
  • D: lockfile placed alongside projection lockfile per scope

Aggregated open questions all 7 resolved 2026-05-24

All seven product-owner questions resolved. Details below.

✓ Pubkey rotation policy: TUF-lite signed trust manifest resolved

Decision: Adopt a TUF-lite two-level trust hierarchy. A long-lived root key (mcp-manager-root, 5-year validity) is baked into the mcpd binary. The root key signs a runtime-fetched trust.toml manifest that enumerates the current registry pubkeys (one entry per default registry: official, github, docker) with per-key valid_until dates.

mcpd fetches trust.toml at install time and refreshes with a 7-day TTL. Rotating a registry pubkey = update trust.toml + re-sign with root + publish (zero user action). Rotating the root itself = hotfix mcpd release (rare, every 3–5 years). Offline failure mode: cache the last-valid manifest locally; if refresh fails, keep cache and warn.

Sample trust.toml:

signed_by = "mcp-manager-root"
signature = "RWQ..."
version   = 1
valid_until = "2026-12-01T00:00:00Z"

[registry."official"]
pubkey_minisign = "RWQabc..."
valid_until     = "2027-12-31"

[registry."github"]
pubkey_minisign = "RWRdef..."
valid_until     = "2027-06-30"

[registry."docker"]
pubkey_cosign = "..."
valid_until   = "2028-01-15"

Prior art: Sigstore Fulcio root, Let's Encrypt ISRG Root X1, Apple code-signing chain.

✓ Docker source UX: ask once at init, CLI flag to skip resolved

Decision: mcpm init detects Docker; if present, asks once: "Enable Docker MCP Catalog as a registry source? [Y/n]". User can skip the question entirely with mcpm init --docker-enable=true or --docker-enable=false (and similar flag-shape for the rest of the prompts via the --defaults / -y mechanism Agent B already defined).

Per the onboarding contract, this decision is reversible via mcpm registry add docker or mcpm registry remove docker at any time.

✓ Service-string namespace: dev.mcp-manager.mcpd resolved

Decision: The OS keychain entry uses service string dev.mcp-manager.mcpd. Reverse-DNS prevents collision with any other tool that might pick a generic label (e.g. mcp-manager). The mcpd suffix is the daemon binary name, leaving namespace for future siblings (dev.mcp-manager.mcpm for CLI-side credentials if ever needed, dev.mcp-manager.mcp-tray for a future tray helper) without renaming existing entries.

We do not need to actually own mcp-manager.dev — the service field is a label, never resolved over the network. This is a free convention to adopt.

Linux libsecret xdg:schema attribute uses the same string.

✓ Code-signing in v1.0; biometric is best-effort resolved

Decision: Code-signing macOS binaries is a v1.0 mandatory commitment (Apple Developer Program enrollment + notarization). TouchID-gated keychain reads (Secure Enclave) are v1.0 best-effort:

  • If macOS biometric integration lands cheaply (kSecUseAuthenticationUI + kSecUseAuthenticationContext on keychain queries; ~20 lines of Rust + a `LAContext` bridge), include in v1.0.
  • If the integration hits friction (entitlement weirdness, code-signing toolchain not ready, etc.), defer to v1.1.
  • Linux biometric is deferred regardless (no native equivalent; PolKit is complex; v1.1+ if real demand).

Code-signing on Linux ships as GPG-signed packages (apt/dnf repos when those land in v1.1; for v1.0's curl installer + Nix flake, the curl script verifies a minisign signature on the tarball).

✓ Per-server spec override ships in v1.0 resolved

Decision: [server.<name>].spec = "2025-06-18" ships in v1.0 as an escape hatch for servers that advertise an unsupported MCP spec version or lie about their support. When set, mcpd skips the install-time allow-list check and uses the user-specified spec for the initialize-time advertisement.

Documented in the docs as: "use only when you trust the server author and have verified manually that the server actually behaves at the spec version you're claiming."

✓ Auto-run mcpm test after updates with --no-test flag resolved

Decision: mcpm update auto-runs mcpm test after each classified change. On test failure, the lockfile entry rolls back atomically. The --no-test flag skips the auto-test (for users in offline / air-gapped / CI-without-network environments). The flag is also accepted on a per-server basis as [server.<name>].test_on_update = false in canonical config.

✓ mcpm uninstall unregisters from service manager first resolved

Decision: mcpm uninstall performs cleanup in order:

  1. If mcpd is registered with the service manager: unregister it (launchd: launchctl bootout gui/501/dev.mcp-manager.mcpd; systemd-user: systemctl --user disable --now mcpd.service). Audit-logged as service.unregister.
  2. If mcpd is running (not via the service manager): stop it cleanly via the same UDS RPC that mcpm daemon stop uses. Audit-logged as daemon.stop.
  3. Stop and clean up any managed MCP server child processes (graceful SIGTERM with 5s timeout, then SIGKILL).
  4. Remove the canonical config directory by default (~/.config/mcp-manager/ on Linux, ~/Library/Application Support/mcp-manager/ on macOS). User can preserve with mcpm uninstall --keep-config.
  5. Do NOT remove keychain entries by default (secrets persist). User can wipe with mcpm uninstall --purge-secrets, which removes every dev.mcp-manager.mcpd/* keychain entry.
  6. Print the path of the audit log (kept around regardless) so users can find historical activity after uninstall.
