Registry strategies — trade-offs

Given the landscape (research page), six broad strategies for how mcpd talks to the world of MCP registries. This page lays each out, scores them on the criteria that matter for v1.0, and pulls out the failure modes that ruled three of them out.

The six strategies

1. Single official registry only

mcpd reads only registry.modelcontextprotocol.io. No third-party sources. Pinned to a known schema, single trust root.

Sibling parallel: npm against the npm registry pre-2010 — one source, one truth.

2. Multi-source federation (user-configurable)

Seeded with two trusted sources; user can mcpm registry add any compliant source. Search fans out, results union-merged with attribution. Each source is independently trustable.

Sibling parallel: brew taps, cargo [registries], apt sources.list.d/.

3. Registry-of-registries (meta-index)

mcpd reads a single "index of indexes" maintained somewhere central; that index points at the actual registries. User adds sources by editing the index entry.

Sibling parallel: Nix flake registry layer 1, mise's first-party registry.

4. GitHub-topic search only

No registry at all. Use the GitHub Search API for topic:mcp-server + query string; parse server.json from the repo if present, else best-effort.

Sibling parallel: Go module proxy reads VCS directly — the package is the repo.

5. Curated allowlist + corp opt-in

Hard-coded allowlist of ~50 high-quality servers ships with mcpd. Anything else is a manual import. Corp users can ship an allowlist via config.

Sibling parallel: Docker MCP Catalog, GitHub MCP Registry's curation tier.

6. Local-vendored mirror snapshot

Bake a snapshot of the registry into mcpd at release. Periodic mcpm refresh pulls a new snapshot. Air-gap-friendly.

Sibling parallel: cargo source replacement, apt offline mirrors.

Critical dimensions in detail

Coverage breadth

"How many servers can the user actually find?" Official registry today is ~2k and growing. Glama is ~24k. GitHub topic is ~16k. Coverage matters less for our "10s of MCPs per user" target than freshness and trust — we just need to surface the right one, not every one.

Trust / provenance

Given 40+ CVEs in early 2026 and the STDIO RCE class, "trust" is the single most weighted criterion. Three sub-questions:

  1. Did the named publisher actually publish this? Official registry's GitHub-auth + namespace pinning answers this. mcp.so does not.
  2. Was the underlying package signed at build time? npm Sigstore provenance answers this for npm packages. Docker images via cosign.
  3. Has the registry itself attested to the manifest? Minisign-signed registry index answers this. Plain HTTPS does not.

Freshness

Registry-of-registries adds a lag layer (the meta-index has to update). Local-vendored is the worst — ships fresh at release, stale within a week. Multi-source federation fans out to live endpoints and is always fresh.

Search quality

"Semantic search" (Smithery) is great UX but requires sending the query to a third party — conflicts with our no-telemetry constraint. Local BM25 over name+description+tags is good enough at 10k-record scale and keeps queries local. We can augment with semantic if the user opts a source in.

Search latency

Local search over a cached index is ~ms. Fanned-out HTTP search is hundreds of ms per source, in parallel. The user-perceived ceiling is the slowest source — we apply a hard timeout (default 2s) and surface partial results.

Escape-hatch friendliness (corp / private)

A user at a company will need to add their internal registry. Strategies #2 and #6 make this trivial; #1 makes it impossible without a fork; #3 forces them to wait for the meta-index to add them. This single criterion eliminates strategy #1 outright.

Maintenance burden

Each adapter is code we own. Strategy #2 with two seeded sources = two adapters at v1.0. Strategy #3 needs a meta-index and all the adapters. Strategy #5 needs only manual curation but the curation itself is unending work.

License risk

Some registries re-publish per-server metadata under their own terms. We do not redistribute metadata — we cache it locally on the user's machine — so the risk is small, but we still want to flag per-source license in the registry manifest so a corp user can audit.

Failure modes that ruled options out

StrategyKiller failure mode
#1 Single official registry only Cannot support private corporate registries without forking mcpd. With 40+ CVEs and 9 of 11 marketplaces affected, security-conscious orgs must have an internal allowlist. This strategy makes them ineligible users.
#3 Registry-of-registries Adds a centralization point we don't own. Meta-index becomes a single point of failure for trust. Doubles the "who broke the world" surface. Nix has gotten away with this only because the meta-index is a flat JSON file in a famous git repo — not a service. We'd have to host such a service or ride on someone else's.
#4 GitHub-topic search only No manifest = we'd have to guess the install command, transport, env-var contract for every server. That's exactly the threat surface STDIO-spawn RCE exploits. Cannot be a primary strategy; useful only as a "no results found, do you want to search GitHub?" fallback.
#6 Local-vendored mirror snapshot PyPI's pip search died precisely because "ship the whole index to every client" doesn't scale. Even at MCP-registry scale (~2k entries) we'd be shipping ~100MB of manifests and re-shipping on every mcpd release. Air-gap users still want it — we make it a per-registry option (--cache=full), not the default mode.

Conclusion & handoff to recommendation

Strategy #2 (multi-source federation) dominates on the weights we expect a v1.0 user to apply, and it's the only one that closes both the "private corp registry" gap and the "ship today" gap. Strategy #5 (curation) is folded in as a property of a source rather than a strategy — "this source is curated" becomes a pill on results, not a separate code path. Strategy #6 (local-vendored) is folded in as a per-registry caching option for air-gapped users.
