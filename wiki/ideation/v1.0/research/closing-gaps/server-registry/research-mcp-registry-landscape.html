The MCP registry landscape, May 2026

Survey of where MCP servers live in May 2026 — what each registry covers, how it gates entries, what programmatic surface (if any) it exposes, and how friendly it is to a self-hosted client like mcpd. We then briefly cover sibling-ecosystem patterns we want to borrow (cargo, brew taps, mise, apt, pipx, Nix flake registry) and the signing/provenance options on the table.

Timeline — how we got here

  • Nov 2024 — Anthropic announces MCP. Discovery is exclusively GitHub README lists.
  • Q1–Q2 2025 — Smithery, mcp.so, Glama, PulseMCP all bootstrap as third-party directories. Each picks its own metadata schema.
  • Sep 2025 — Official MCP Registry preview launches at registry.modelcontextprotocol.io. Ships an OpenAPI 3.1 spec other registries can adopt ("Generic Registry API").
  • Dec 2025 — Anthropic donates MCP to the Linux Foundation's Agentic AI Foundation. Registry governance becomes vendor-neutral.
  • Jan–Apr 2026 — 40+ CVEs disclosed against MCP SDKs and 9 of 11 marketplaces; major STDIO-spawn RCE class makes "only install from verified sources" a baseline ask.
  • Mar 2026 — Enterprise-readiness roadmap published; signing and provenance are explicit goals.
  • May 2026 (today) — 12,000–24,000 servers cataloged depending on whose counting; ~16k GitHub repos with the mcp-server topic.

First-party / vendor-neutral registries

Official MCP Registry — registry.modelcontextprotocol.io
URLhttps://registry.modelcontextprotocol.io
GovernanceLinux Foundation / Agentic AI Foundation as of Dec 2025; vendor-neutral.
API surfaceREST, OpenAPI 3.1.0; JSON-Schema draft 2020-12.
GET /v0.1/servers — paginated list
GET /v0.1/servers/{serverName}/versions
GET /v0.1/servers/{serverName}/versions/{version} (latest alias)
POST /v0.1/publish, DELETE for removal
Manifest schemaserver.json with name, description, version, repository, packages[] (with registryType = npm/pypi/oci/…), remotes[], transport, env. Schema hosted at static.modelcontextprotocol.io/schemas/2025-10-17/server.schema.json.
Auth for publishGitHub OAuth; io.github.<user>/* namespaces are pinned to that user. npm packages must declare mcpName; PyPI packages must embed the name in README. Cross-checks the package against the publisher's claim.
MutabilityDELETE endpoint exists; versions are append-only by convention. No yanked-version tombstones documented yet.
TelemetryNone observed; reads are anonymous.
Coverage (May 2026)"~2,000 entries within months of launch" per the preview blog; growing.
mcpd fitExcellent — this is the canonical schema we adopt for our local "normalized" representation. The Generic Registry API means private corp registries can serve the same shape.
GitHub MCP Registry — github.com/mcp
URLhttps://github.com/mcp + GitHub Blog announcement.
GovernanceCurated by GitHub; each entry backed by a GitHub repo. Aligned with the official registry as an upstream consumer (publishes against the same schema where applicable).
API surfaceBrowseable web UI + (per blog) programmatic access integrated into GitHub Copilot's server picker. Programmatic surface for non-Copilot clients is currently limited — we treat this as a curated allowlist source.
Trust modelStrong: every entry has a known GitHub identity, repo URL, and (for org-owned servers) GitHub org verification.
mcpd fitTreat as a high-trust seeded source for v1.0. Adapter can be a thin wrapper over a public JSON manifest at a stable URL.
Docker MCP Catalog — docs.docker.com/ai/mcp-catalog-and-toolkit
URLhttps://docs.docker.com/ai/mcp-catalog-and-toolkit/catalog/ + source at github.com/docker/mcp-registry.
DistributionEach server is a signed Docker image on Docker Hub. Custom catalogs distribute as OCI artifacts.
Coverage (May 2026)300+ verified servers.
Trust modelStrong: Docker-built servers are digitally signed by Docker; reproducible image hashes. Onboarding via PR with 24h SLA.
mcpd fitExcellent for the "user already has Docker / wants containerized servers" path. Maps cleanly to the Docker escape-hatch in stoic-badger-sandbox. Adapter reads github.com/docker/mcp-registry directly — no telemetry surface.

Community directories & marketplaces

Smithery — smithery.ai
URLhttps://smithery.ai
Coverage (May 2026)~7,000 servers.
API surfaceREST registry API with semantic search ("query is a prompt"); requires API key from smithery.ai/account/api-keys.
CLI parallelsmithery mcp search [term], smithery mcp add <url>. npm-distributed (@smithery/cli).

Raw discovery surfaces

GitHub topic mcp-server

~16,300 repositories tagged as of May 2026; Python ~5,700, TypeScript ~5,100, JavaScript ~1,700. GitHub Search API can power mcpm search as a fallback, but ranking is by stars+freshness and there is no manifest. Treat as last-resort discovery, not as a registry.

npm mcp-* packages

npm Search API is alive and unrestricted (unlike PyPI). Useful for "find packages whose name starts with @modelcontextprotocol/server- or mcp-" queries. Provenance via npm + Sigstore attestations is GA — mcpd can verify package provenance at install time without trusting any registry adapter.

PyPI mcp-* packages

PyPI's XML-RPC search was permanently disabled in March 2021; pip search no longer works. The only viable PyPI discovery is the JSON metadata endpoint per known package name. This is a cautionary tale for any "search a global package index" strategy that scales linearly with the index.

Sibling-ecosystem prior art

cargo — [registries] + source replacement

Cargo lets a user define multiple named registries in .cargo/config.toml, then pass --registry <name> on install. A separate "source replacement" knob lets a corp mirror the whole crates.io index without changing crate URLs in Cargo.toml. Lesson: two distinct concepts — additive sources (more packages) and replacement sources (same packages, different endpoint) — both matter. We need additive in v1.0; replacement is v1.1.

brew taps

brew tap user/repo adds a git repo to the search universe; tap order matters for collisions. Lesson: the UX of "give me a URL, I clone it locally and re-scan periodically" is friendly and well-understood. We adopt the verb tap's ergonomics under the name mcpm registry add.

mise plugins

mise rejects new asdf-style plugins because they execute arbitrary shell at install time — instead, it favors declarative aqua/github backends. Lesson: we follow the same posture — never let a registry tell us "run this shell snippet to install". We only accept declarative manifests (the official server.json schema). Tool-poisoning attacks make this non-negotiable.

apt sources.list.d + signed-by

Each third-party apt source pins to a specific signing key via signed-by=/etc/apt/keyrings/<name>.gpg. Lesson: per-source signing key is the right abstraction. mcpm registry add should accept an optional --signed-by <key> argument and refuse manifests not signed by that key.

pipx with custom --index-url

pipx supports per-install --index-url but not --extra-index-url. Lesson: single-source-per-invocation is too constraining for our case; we need fan-out across multiple registries in one search, with per-result attribution.

Nix flake registry

Three layers: global registry (channels.nixos.org/flake-registry.json), per-user overrides via nix registry add, and per-flake nixConfig.flake-registry. Lesson: three-layer precedence is overkill for v1.0 but the per-user override is the natural mcpd model. Per-project pinning is a v1.1 idea.

Trust & provenance options for v1.0

OptionWhat it gives usv1.0 verdict
Maintainer trust only (the apt PPA model before signed-by became mandatory)"You added this registry, you trust it." Zero crypto.Acceptable floor — what we do for unsigned user-added sources.
Minisign / signify per-registry manifestSingle Ed25519 pubkey signs the entire registry's manifest list. Tiny, embeddable, no infra.Default for v1.0 official + GitHub registries — lowest implementation cost, strongest practical guarantee for our threat model.
Sigstore (Fulcio + Rekor) per-packageKeyless OIDC-bound signing, transparency log, per-version attestation. Already GA on npm.Verify-only in v1.0 — if a package has npm/PyPI provenance, mcpd checks it before install. We don't require it.
Cosign for OCI imagesFor the Docker MCP Catalog path, image signatures live alongside images in the registry.Verify-only in v1.0 — rely on Docker's existing signature check; mcpd invokes cosign verify when the package is OCI.
Full PKI (Notary v2 / TUF)Defense in depth against registry compromise.Out of scope for v1.0 — complexity not justified at 10s-of-MCPs scale.
