Closing gap · First-run / onboarding flow

The six original v1.0 streams catalogued what MCP Manager must do but did not specify the moment a user crosses the threshold from "I just installed this" to "mcpm exec works the way I expect." This page closes that gap. The onboarding flow ties together four things that have to land in one ceremony: (1) a service-manager opt-in (launchd or systemd-user), (2) which editors to project into (tier-1 toolchains), (3) which upstream registries to subscribe to, and (4) an optional first secret. 37 citations 3 pages 5 worked transcripts

Sibling closing-gap streams

server-registry

How a user finds and installs an MCP server (mcpm search / mcpm install). Our mcpm init can invite the user to install a starter server from a curated registry but defers the actual install UX to this stream.

secrets-lifecycle

Keychain-backed secrets via mcpm secret set. Our flow can prompt the user to set one secret on first run to demonstrate the round-trip, but never owns the entry UX.

version-management

How mcpd itself is upgraded post-install. The handshake on first run records the installed version and the auto-update policy; this stream owns the policy semantics.

Headline recommendation in one paragraph

mcpm init is a thin scaffolder, not a doctor — modelled directly on aws configure for default-handling, terraform init for project-scoped staged output, and npm init -y for the non-interactive escape hatch. It writes exactly three things on a default run: a per-user TOML config under $XDG_CONFIG_HOME/mcp-manager/config.toml (or the macOS equivalent), an empty servers.lock, and an audit-log entry recording what was created and by which mcpm version. Every prompt has a visible default in [brackets], every prompt is accepted with ENTER, and every prompt maps to a long-form CLI flag so mcpm init --defaults -y produces an identical end state with zero stdin reads. The service-manager opt-in (launchd / systemd-user) is a separate prompt with its own non-interactive flag (--register-service / --no-register-service) and always defaults to no, because the daemon auto-spawns from mcpm exec anyway. Project-scope init (mcpm project init or mcpm init --scope project) writes a .mcp-manager/ directory in the current repo following the same layout but never touches the user-scope config. The flow is fully idempotent: re-running prints a diff of what would change and exits zero if nothing would.

v1.0 locked constraints this design honours

  • No browser pop-ups. Pure CLI/TUI; the device-flow pattern surveyed in Stripe is rejected for v1.0 because every comparable host (Claude Code, Cursor, Codex) already handles its own auth — mcpm has no central server to auth against.
  • macOS + Linux only. Service-manager prompt branches on which manager exists; falls through quietly if neither does (rare; running inside a container).
  • No telemetry, ever. The init flow does not phone home; the "registered servers" prompt only lists registries the user explicitly opts into.
  • Daemon auto-spawns. The service-manager opt-in is genuinely opt-in — declining it does not break mcpm exec, which spawns its own daemon on demand.
  • TUI is ratatui-based . The interactive walk uses a small ratatui wizard for multi-select (toolchains, registries) but falls back to line-based prompts (à la aws configure) when stdout isn't a TTY.
