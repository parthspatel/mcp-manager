Recommendation — mcpm init flow design

The opinionated half of the stream. Five worked transcripts cover the cases the design has to handle: an interactive lucky-day run, a fully non-interactive run, an importing-from-cursor stub, a project-scope run inside a repo, and the service-manager opt-in mid-flow. Every prompt has a flag; every flag has a documented default; every default is overridable; every run is idempotent.

TL;DR

  • One command surface: mcpm init (user-scope by default). mcpm project init is a shorthand for mcpm init --scope project.
  • Three universal flags: --defaults (accept the documented default for every choice), -y / --yes (skip all confirmations), --force (re-init over existing config with a backup).
  • Files written on a default user-scope run: $XDG_CONFIG_HOME/mcp-manager/config.toml, $XDG_STATE_HOME/mcp-manager/servers.lock (empty), and one audit-log line in $XDG_STATE_HOME/mcp-manager/audit.log. On macOS, the same paths via ~/Library/Application Support/mcp-manager/ with a symlink shim at ~/.config/mcp-manager for cross-OS muscle memory.
  • Service-manager prompt: separate, opt-in, defaults to no. The daemon auto-spawns from mcpm exec regardless.
  • Idempotent: re-running prints a no-change summary and exits zero. --force backs up old config to config.toml.bak.<timestamp> before overwriting.
  • Trust gate for project-scope: a project-scope config in a freshly cloned repo is inactive until the user runs mcpm project allow (or passes --allow at init), modelled on direnv allow.

Transcript 2 — mcpm init --defaults -y (full non-interactive)

Zero stdin reads. Suitable for Ansible / Nix / homebrew post-install hooks / CI. Produces an identical end state to Transcript 1 when run on the same machine, modulo timestamps.

$ mcpm init --defaults -y
mcpm v1.0.0 first-run (non-interactive)
Detected toolchains: claude-code, vscode
Projecting into: claude-code, vscode
Registries: community
Secrets: 0 captured (deferred to `mcpm secret set`)
Service registration: skipped (auto-spawn enabled)
Wrote:
  ~/.config/mcp-manager/config.toml
  ~/Library/Application Support/mcp-manager/servers.lock
  ~/Library/Application Support/mcp-manager/audit.log
Done.

$ echo $?
0

# Re-running is a no-op (idempotent).
$ mcpm init --defaults -y
mcpm v1.0.0 already initialized (config.toml exists, sha256 matches defaults)
No changes.
$ echo $?
0

# To re-init over existing config:
$ mcpm init --defaults -y --force
mcpm v1.0.0 re-init (--force)
Backing up existing config to ~/.config/mcp-manager/config.toml.bak.2026-05-24T19-22-03Z
Wrote:
  ~/.config/mcp-manager/config.toml
Done.

This is the contract mcpm commits to: mcpm init --defaults -y produces a working setup on any supported machine with no input — the same guarantee npm init -y ships.

Transcript 4 — mcpm project init (project-scope shorthand)

Equivalent to mcpm init --scope project. Provided because a verb-first form ("project init") matches user mental model in muscle-memory tools like git init / terraform init / cargo init.

$ cd ~/projects/freshly-cloned
$ mcpm project init

mcpm v1.0.0 project-scope init
Target: /Users/me/projects/freshly-cloned/.mcp-manager/

Existing config detected at .mcp-manager/project.toml (committed by upstream).

The project declares 3 MCP servers and 2 toolchains. Before any of them
are activated for this directory, you need to grant trust.

Server declarations in .mcp-manager/project.toml:
  - github-search   (github.com/mcp-manager/registry-community)
  - postgres        (github.com/mcp-manager/registry-community)
  - filesystem      (local path: ./tools/fs-mcp)   <-- LOCAL EXECUTABLE

The filesystem server runs a local executable from this repo. Review
./tools/fs-mcp before allowing.

[1/1] Trust this project's MCP config and run `mcpm sync` to project it?
      [y/N]: y

Recording trust … wrote ~/.config/mcp-manager/trusted-projects.toml
Running mcpm sync … projecting servers into cursor and claude-code … done.

Next:
  mcpm project status         Verify the projected state matches project.toml
  mcpm project sync --dry-run Preview future projections without writing
Trust modelModelled on direnv allow: a fresh clone is inactive until the user explicitly trusts it. Servers that run local executables are called out by name — the user has to look at ./tools/fs-mcp before allowing.
Audit trailEvery trust grant is appended to ~/.config/mcp-manager/trusted-projects.toml with a sha256 of the project.toml at trust time. If the file changes upstream, the trust is invalidated and the user is re-prompted.
Non-interactive variantmcpm project init --allow -y performs the same trust-grant non-interactively; intended for CI in your own repos, not for arbitrary clones.

Non-interactive acceptmcpm init --register-service -y (no further prompts; identical end-state to the accept branch).
Non-interactive declineDefault. mcpm init -y or --defaults -y skips the prompt entirely.
Why default no?The locked v1.0 design has the daemon auto-spawning from mcpm exec. Registering as a service is a performance optimisation (skip the ~200ms cold-start) and a logout-survival feature — both nice but not required for "it works". Off-by-default matches the principle of least intrusion: a fresh install never leaves a background process running on the user's machine without an explicit yes.
Why prompt at all on first run, then?Because asking later is awkward — nobody discovers mcpm service register on their own. One prompt with a clear default is better than a config option that 95% of users never touch.

What gets written on disk

User-scope (Linux, XDG-compliant)

User-scope (macOS)

macOS apps that follow XDG conventions resolve $XDG_CONFIG_HOME to ~/.config, but Apple's HIG points at ~/Library/Application Support/. mcpm splits the difference: human-edited config under ~/.config/mcp-manager/, runtime state and logs under ~/Library/Application Support/mcp-manager/ and ~/Library/Logs/mcp-manager/. Both locations are symlinked from each other for muscle memory.

Project-scope (any OS)

./.mcp-manager/.gitignoreAuto-generated; ignores local-only state (cache, logs).Yes (the .gitignore itself).
./.mcp-manager/local/Per-user local state for this project (cache, log).No — ignored by the auto-generated .gitignore.

Idempotency & re-run semantics

Following clig.dev's idempotency principle, every mcpm init invocation falls into one of three deterministic states:

  1. No existing config → fresh write, summary, exit 0.
  2. Existing config, no flags would change it → print "no changes," exit 0. (Matching terraform init's "already initialized" path.)
  3. Existing config, flags would change it, no --force → print a diff of what would change, exit 1. The user sees exactly what we would have done.
  4. Existing config, flags would change it, --force passed → back up the old config to *.bak.<ISO-timestamp>, write the new, append an audit entry citing the previous sha256, exit 0.
# State 3 example: diff and bail
$ mcpm init --toolchains claude-code,vscode,cursor
mcpm v1.0.0 already initialized at ~/.config/mcp-manager/config.toml.
Re-init would change:
  toolchains:
    - claude-code, vscode
    + claude-code, vscode, cursor

Pass --force to apply (previous config will be backed up).
$ echo $?
1

This shape is borrowed directly from terraform plan's diff-then-bail behaviour, ported to init. The diff format follows unified-diff conventions so users can pipe it into review tools.

Open questions for the orchestrator

  1. Should mcpm init auto-detect Codex / Cursor / Zed / JetBrains the same way it detects Claude Code and VS Code? Toolchain auto-detection is owned by clever-fox-bridge; the init flow consumes the result but has no opinion on the detection mechanism. The expected behaviour from this design: for any tier-1 toolchain the detector reports "installed," the init prompt shows a ✓ default; for tier-2, the prompt shows a ● "opt in?" default. The orchestrator should confirm this matches what clever-fox-bridge produced.
  2. What is the canonical name of the "community registry"? Transcript 1 names it github.com/mcp-manager/registry-community. The server-registry stream defines this; whatever it lands on should be the documented default for --registry.
  3. Does the audit log live under $XDG_STATE_HOME or somewhere the user is more likely to find it? Spec-compliant placement is $XDG_STATE_HOME; that path is buried under ~/.local/state/ by default. mcpm logs --audit tails it without the user needing to know the path. The orchestrator may want to surface this in the mcpm status command alongside whatever else steady-bear-foundation shows.
  4. The trust-grant model for project-scope (Transcript 4) is borrowed from direnv. Sister stream secrets-lifecycle might have its own opinion about trust scoping that the orchestrator needs to reconcile.
  5. Should --import-from ship as a stub at all in v1.0? The argument for: users can write the flag into their setup scripts now and the v1.1 upgrade transparently activates it. The argument against: a flag that doesn't work is a footgun; better to not advertise it. This page chose to ship the stub; the orchestrator may overrule.
  6. What happens to the service registration on mcpm uninstall? Not addressed here because uninstall semantics are outside this stream's scope. Some product owners will want the service auto-unregistered on uninstall; others will want it left alone so a re-install picks up where it left off. Worth a decision before v1.0 ships.
