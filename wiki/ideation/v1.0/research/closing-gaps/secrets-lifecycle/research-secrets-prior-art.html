Survey of secrets prior art

What does everyone else do? This page maps the secrets ecosystem in three concentric rings: (1) the OS-level keyring backends our v1.0 store will sit on top of, (2) the Rust crates that implement or wrap them, and (3) the vault-provider CLIs whose surface area defines what our v1.1+ SecretStore trait must be able to express. The goal is not to pick one — v1.0's choice is already locked (OS keychain) — but to make sure the trait we ship in v1.0 can model every shape we'll need later without breaking changes.

OS-level backends

macOS — Keychain Services (SecItemAdd / SecItemCopyMatching)
Identity modelEach item is a CFDictionary keyed by kSecClass (we use kSecClassGenericPassword), kSecAttrService, and kSecAttrAccount. The (service, account) pair is the lookup key.
Access policykSecAttrAccessible attribute. kSecAttrAccessibleWhenUnlocked (default) is the right choice for mcpd — the daemon won't try to read secrets when the user is logged out.
ACL / promptingItems can be ACL-bound to specific processes; if mcpd isn't on the ACL, macOS prompts the user. For v1.0 we ship without ACL restrictions (every user-session process can read) to avoid prompt fatigue; v1.1 can introduce Touch ID / code-signed entitlements.
Code-signing gotchaMany keychain entitlements (Secure Enclave keys, biometric gates) require the calling binary to be code-signed and bear specific entitlements. Unsigned binaries hit ErrSecMissingEntitlement. We need a clear release-engineering plan for signed builds before TouchID-gated secrets are viable.
Sync behavioriCloud Keychain sync is opt-in per-item via kSecAttrSynchronizable; mcpd defaults to not syncing — an Anthropic key on an iPad makes no sense.
Linux/BSD — freedesktop Secret Service (libsecret / gnome-keyring / KWallet)
ProtocolD-Bus interface org.freedesktop.Secret.Service. Clients OpenSession(), then operate on Collection and Item objects identified by lookup-attribute maps.
Implementationsgnome-keyring-daemon (most common), KWallet (KDE), KeePassXC (with its Secret Service plugin enabled). All speak the same D-Bus protocol.
Default collectionEach user has a default collection (usually login, unlocked at session start). We write there; reads return the first matching item.
Schema attributeItems carry an xdg:schema attribute (we propose dev.mcpmanager.Secret) plus arbitrary application attributes — we use {server: "github", name: "GITHUB_TOKEN"} as the lookup key.
Headless-server gotchaA server with no graphical session and no D-Bus user bus has nowhere to talk to. mcpd in this configuration must fail with a clear error pointing to the env-var escape hatch, NOT silently fall back to a plaintext file (locked policy — "no file-based fallback in v1.0").
WSL / remote SSHOut of scope — macOS + Linux only, and Linux means "Linux with a session keyring available." Document this clearly.
Other OS keychains (informational)
Windows Credential ManagerNot supported (no Windows). The keyring crate has a Windows backend; we will not exercise it.
VS Code SecretStoragePer-extension store backed by the OS keychain via Electron's safeStorage; useful as an existence-proof that editor-tier tools use the OS keychain too. We do not read/write VS Code's slot — that's a different namespace and would surprise users.

Rust crate ecosystem

keyring — cross-platform OS-keyring wrapper
StatusMature; v3.x recently refactored into keyring-core (API trait) + per-platform store crates. Maintained by the open-source-cooperative org.
ModelEntry::new(service, user) identifies a credential; set_password / get_password / delete_credential.
Featuresapple-native enables Keychain Services on macOS/iOS; linux-native-sync-persistent enables Secret Service via libsecret. We pick exactly those two features.
Async-nessSynchronous API. mcpd is tokio-based, so calls happen inside tokio::task::spawn_blocking. Fine for low-frequency operations (set/get on server spawn).
LicenseApache-2.0 / MIT — compatible.
Why pick thisAlready-debugged abstraction over both OS backends we need. Avoids two FFI dependency trees in our build.
keychain-services — lower-level macOS-only binding
StatusExperimental, maintained by iqlusion. Exposes Secure Enclave / TouchID-gated keys that keyring hides.
When we might pull this inv1.2+, when we want optional biometric-gated reads. Not needed for v1.0.
RiskExperimental + macOS-only + requires code-signing — introduces a build-side complexity that v1.0 doesn't justify.
secrecy + zeroize — in-process secret wrappers
PurposeSecretString/SecretBox implement Debug as [REDACTED] and zero the buffer on drop. Prevents accidental logging.
Backbonezeroize uses core::ptr::write_volatile + atomic fences. Pure Rust; no FFI.
Use in mcpdEvery plaintext that comes out of a SecretStore is wrapped in SecretString until the moment we hand it to the OS via std::process::Command::env. The String lives microseconds; the rest of mcpd never sees plaintext.
rpassword — terminal prompt with echo disabled
PurposeCross-platform getpass(). Reads from /dev/tty rather than stdin, so it works correctly when the user has redirected stdin.
LicenseApache-2.0 — compatible.
BacksThe interactive prompt for mcpm secret set GITHUB_TOKEN.
secretspec — declarative multi-backend secrets manifest
IdeaApp ships a secretspec.toml declaring which secrets it needs; backend (1Password, .env, env-only, GCP Secret Manager, system keyring, LastPass, pass) is a deploy-time choice. Same code works against all of them.
Why it mattersClosest existing crate to the shape of our trait. We do not depend on it, but we steal the abstraction: declare-vs-store separation, provider as a config-time choice, identical Rust call sites for every backend.
Why we don't depend on itOur model is centred on a daemon, not a per-app library. Their providers list is informative but their API surface doesn't quite match our needs (e.g. they don't have a notion of audit-logging through a host-defined channel).
SOPS, agenix — file-encrypted prior art

Both encrypt secrets at rest in version control: SOPS uses YAML/JSON files encrypted with KMS or age ; agenix encrypts with age and decrypts at NixOS activation into /run/agenix/. Neither is a runtime secret-fetching API; they're at-rest formats. Out of scope for v1.0, but a future SopsFileStore impl is plausible (and free to design now, ship later).

Vault-provider CLI surfaces

The pattern we want from every one of these is: given a secret reference, return the plaintext to stdout, exit 0 on success. That's what our shell-out provider stubs will rely on.

1Password — op
Reference syntaxop://<vault>/<item>/[section/]<field>
Read oneop read "op://Dev/GitHub/credential" → plaintext on stdout.
Inject manyop run -- <cmd> resolves all op:// URLs in the environment of the subprocess. We don't use this form — mcpd resolves per-secret — but it's a natural fit for users who want to bypass mcpd entirely.
AuthDesktop-app biometric session, OR service-account token in OP_SERVICE_ACCOUNT_TOKEN.
Failure modeExits non-zero with a human-readable error to stderr. We surface stderr verbatim through mcpd's audit log on read failure.
Bitwarden — bw
Reference syntaxItem name or UUID. bw get password <name> for a password; bw get item <id> returns JSON.
Authbw unlock issues BW_SESSION; every subsequent call needs it. Session expiry is the main complication for a daemon.
WrinkleSession management is the user's job, not ours. The BitwardenStore impl assumes BW_SESSION is present in mcpd's environment; if absent, fail with a "run bw unlock first" error.
HashiCorp Vault — vault
Reference syntaxFor KV v2: vault kv get -mount=<mount> -field=<field> <path>
VersionsKV v2 is versioned (-version=N), supports soft delete, metadata, and check-and-set. This is the model we'd reach for if we ever want native rotation tracking.
AuthVAULT_TOKEN, AppRole, OIDC, AWS, k8s — many. The VaultStore impl reads only what's in the environment and trusts the user's vault CLI to be authenticated.
Leases / TTLDynamic-secret leases give us the model for our future "leased" SecretStore variant: every read returns (value, lease); mcpd renews or revokes.
Doppler — doppler
Reference syntaxNo per-secret URL — configuration via project + environment + config name; secret names are bare strings within that scope.
Inject manydoppler run -- <cmd> injects the entire config's secrets.
Read onedoppler secrets get <NAME> --plain
MCP-specific blogDoppler's own engineering blog argues for runtime-only injection into MCP server processes.
Infisical — infisical
Reference syntaxProject + environment + path; secret name within. infisical run --env=prod --path=/mcp -- <cmd>
Multi-path--path=/common --path=/app1 merges from multiple paths — useful for shared API keys across many MCP servers.
AWS Secrets Manager — aws secretsmanager
Reference syntaxARN or name. aws secretsmanager get-secret-value --secret-id <arn> --query SecretString --output text
AuthWhatever aws CLI is configured for in mcpd's env (AWS_PROFILE, IRSA, instance profile, SSO).
JSON-vs-stringSome secrets store JSON; --query 'SecretString' returns the raw string, the caller does its own JSON parse. The AwsSecretsManagerStore impl will expose a "JSON field selector" string in the secret reference to pluck a field.
GCP Secret Manager — gcloud secrets
Reference syntaxgcloud secrets versions access latest --secret=<name> prints the secret payload to stdout.
AuthApplication Default Credentials (gcloud login or workload identity).
Azure Key Vault — az keyvault secret
Reference syntaxaz keyvault secret show --vault-name <vault> --name <name> --query value -o tsv
AuthAzure AD identity (signed-in user or managed identity).

Common abstractions across all vault CLIs

Every one of the eight CLIs above maps cleanly onto the same three-operation shape:

OperationConceptual inputsConceptual outputAudit semantics
readprovider-specific reference (URL, ARN, name)plaintext bytesone secret.read event per call
writereference + plaintext(ok)one secret.write event; value never logged
listoptional namespace/pathset of references (names only)one secret.list event; names only, no values

This is exactly the shape of our v1.0 trait. The provider-specific reference type is the place where each backend gets to be itself: OS keychain uses (service, account) string pairs; 1Password uses op:// URLs; AWS uses ARNs. We model this by parameterizing the trait with an associated Ref type and a parse_ref(&str) constructor — same surface, store-specific decoder.

The other shared assumption: every provider returns plaintext over stdout (or HTTP body). Our shell-out stubs wrap that uniformly: spawn the child, capture stdout into a SecretString, drop on completion. No backend forces us to think about a different shape.

CLI patterns for secret entry

What ways are safe to put a secret into our store from a terminal? The cheat sheets are consistent: any pattern that lets the secret reach argv is wrong because (a) it shows up in ps, (b) it lands in ~/.bash_history or ~/.zsh_history, and (c) CI runners capture argv into logs.

PatternVerdictNotes
mcpm secret set NAME --value $TOKENbannedArgv leak. We refuse to implement --value.
mcpm secret set NAME (interactive prompt)defaultrpassword reads from /dev/tty, echo off.
mcpm secret set NAME --from-file ./token.txtsafeFile contents read, whitespace trimmed.
cat token.txt | mcpm secret set NAME --stdinsafePipe is in-memory; argv carries no secret.
mcpm secret set NAME --from-env GITHUB_TOKENsafeReads another env var (not argv); useful in scripts.
mcpm secret set NAME --generatev1.0 skipGenerate-random-on-write is useful for some flows (basic-auth passwords); not a v1.0 priority.

Docker's --password-stdin flag is the canonical precedent for the --stdin pattern; their own documentation explicitly warns against passing passwords via argv.

Auditability prior art

Where does a "secret was read" event get logged? Two common designs:

  1. Store-level audit — Vault's own audit devices, AWS CloudTrail, GCP Cloud Audit Logs. The vault knows who called it. Outside our control, but a useful complement.
  2. Consumer-level audit — the program that uses the secret records the read. This is the only level we can guarantee, because we control mcpd. Even if the user's vault has audit turned off, mcpd's own log records every read.

Kubernetes' audit-policy machinery is the closest existing precedent — it logs every Secret access at the API-server level with structured JSON events containing actor, verb, resource, and outcome, but explicitly never values. We adopt the same shape, narrower to our needs.

The Goose AI agent ships the closest existing pattern in the MCP-host space: it stores LLM provider keys in the OS keyring by default, with a GOOSE_DISABLE_KEYRING escape hatch back to plain env vars. That validates both halves of our v1.0 design — OS keychain as the default, env-var override as the escape hatch.
