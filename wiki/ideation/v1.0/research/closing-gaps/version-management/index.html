Closing-gap · Version management

Two version axes intersect inside MCP Manager and they are not the same problem. Axis A — server pins: when a user types mcpm install github-mcp, do they get the latest github-mcp-server build, or the one a teammate had last Tuesday? Axis B — spec compatibility: the MCP wire protocol itself versions on a date string (currently 2025-11-25 stable, 2026-07-28 on a release-candidate track) and every server advertises one. Our daemon must negotiate, refuse incompatible matches honestly, and tell the user why a server failed to start. Stream summary in one paragraph

MCP Manager v1.0 adopts the range-in-manifest + exact-in-lockfile model proven by Cargo and npm: users declare github-mcp = "^0.4" in mcp-manager.toml, the daemon resolves and writes the chosen version + checksum into mcp-manager.lock, and the lock becomes the source of truth on subsequent installs. mcpm update classifies changes using Renovate's vocabulary — major / minor / patch / digest / pin / lockFileMaintenance — and surfaces them as a colored CLI/TUI diff before any write happens. For the spec-version axis, mcpd advertises a set of supported protocol dates (the current stable 2025-11-25 plus a configurable allow-list of older versions), and on every initialize picks the newest common version with the server — mirroring the MCP lifecycle requirement rather than enforcing strict equality. The lockfile lives co-located with the toolchain projection lockfile (decided by clever-fox-bridge): per-user → ~/.config/mcp-manager/mcp-manager.lock; per-project → ./mcp-manager.lock. Every version change writes an audit.config.change record so a teammate can ask "who bumped the GitHub server to 0.5?" and get a real answer. After each successful update, the daemon optionally runs mcpm test <server> (the health check) and rolls back the lockfile entry if initialize fails — making version churn safe by default.
