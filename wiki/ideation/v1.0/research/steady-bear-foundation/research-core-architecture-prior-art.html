Research — Prior art for process-management cores

Survey of how analogous systems are architected, ordered by "structural distance" from MCP Manager: container engines (dockerd, containerd, podman), OS service managers (systemd, launchd), package/build daemons (nix-daemon), local-VM orchestrators (lima, colima), MCP-native tools (mcp-inspector), and per-invocation tool runners (uvx, pipx). Each section extracts the load-bearing design choice and notes which patterns transfer to managing MCP servers.

Docker / dockerd

Docker is the canonical "client-server with a persistent daemon" design. The Docker CLI converts user commands into REST API requests sent to the dockerd daemon over a Unix socket (/var/run/docker.sock) or TCP; the daemon does the heavy lifting of building, running, and distributing containers. dockerd itself doesn't directly run containers — it passes the image and run-configuration to containerd, which uses runc to create the container process.

Two consequences worth lifting: (1) the daemon centralizes state and supervision (auto-restart, log aggregation, port mapping) but becomes a single point of failure for everything it manages, and (2) remote management "for free" — any client that can reach the API socket can drive the daemon, including from another machine.

containerd + containerd-shim

Underneath dockerd, containerd manages the container lifecycle and spawns one containerd-shim per container. The shim is a subreaper that adopts the container's PID-1 children and any orphaned descendants, keeps the container's stdio file descriptors open, and reports the exit status back to containerd — all while allowing runc (the actual OCI runtime) to exit cleanly right after execve.

The shim pattern decouples "runtime that knows how to execve a container" from "monitor that owns the running container forever". For MCP servers, the analogous question is: should we have one supervisor process per MCP server (shim-style, robust against the manager crashing) or one supervisor for all of them (less code, but if the supervisor dies all children's stdio is orphaned)?

podman + conmon

Podman is a "fully featured container engine that is a simple daemonless tool", explicitly positioned as a drop-in CLI replacement for Docker (alias docker=podman). Without a long-running daemon, Podman invokes the OCI runtime directly and relies on the host's init system (systemd) — or per-container conmon monitors — to keep containers alive across CLI invocations.

conmon is the per-container monitor used by both Podman and CRI-O. After it spawns the OCI runtime as a child, conmon daemonizes itself so the managing program can die while the container keeps running; while the container is alive, it (a) exposes a socket for attach, (b) holds the container's standard streams open and forwards them, (c) writes container logs to a file or the systemd journal, and (d) records exit time and status for the next CLI invocation to pick up. It is described as "the smallest daemon a container can have".

This hybrid model — no persistent central daemon, but a tiny per-managed-thing monitor — is the most directly transferable pattern to MCP servers, since MCP servers are themselves typically lightweight long-running processes.

systemd

On Linux, systemd is PID 1 and acts as a unified service supervisor: it tracks services via cgroups rather than PIDs (so daemons cannot "escape" by double-forking), restarts crashed services per declarative policy, and routes service stdout/stderr into systemd-journald as structured binary logs with PID/UID/cgroup metadata. The documented mechanism for delegating subtrees of cgroups (and thus resource limits and tracking) to a service manager nested inside systemd is described in the cgroup-delegation guide.

The transferable idea is the declarative-unit-file model: a server is described by an immutable file (command, env, resource limits, restart policy) and the supervisor reconciles toward it. MCP server descriptions in the registry can follow the same shape.

launchd

On macOS, launchd is PID 1 and uses property-list (.plist) files in ~/Library/LaunchAgents (per-user) and /Library/LaunchDaemons (system-wide) to describe services. A key launchd feature is on-demand activation: launchd can listen on a socket on the service's behalf and start the service only when the first connection arrives, then shut it down when idle.

On-demand activation maps cleanly to MCP: hosts often connect to local MCP servers only when the user invokes a tool — a manager that can lazily start, then idle-stop, MCP servers can save large amounts of memory.

nix-daemon

In multi-user Nix installations, the /nix/store and the SQLite database that indexes it are owned by a privileged user (usually root). Unprivileged users do not poke at the store directly; instead they set NIX_REMOTE=daemon and their Nix CLI forwards operations over a Unix socket to a nix-daemon process running as the store owner, which performs the builds inside unprivileged nixbld* users. Concurrency is capped by the number of build users.

The "privileged daemon owns a state directory, unprivileged clients use a socket" pattern is the closest prior art for MCP Manager's case where multiple host apps on the same machine need consistent installs of the same server. The sandbox in nix-daemon, however, is explicitly described as a reproducibility tool — not a security boundary between users.

lima / colima

Lima is "Linux Machines" — a host agent that boots a small VM (qemu or vz) and provisions container runtimes inside it; Colima ("Containers on Lima") wraps Lima with a Docker-CLI-compatible UX. Lima's architecture is documented as four layers: CLI (user interface), YAML config (declarative VM templates, validated, persisted), host agent (manages VM lifecycle, drivers, host↔guest channels), and guest environment (in-VM agent + container runtime).

The pattern of separating a stable config / template layer from a stateful orchestrator layer is directly relevant: MCP Manager's registry of "what to install" should be replayable and reproducible without depending on the supervisor's in-memory state.

mcp-inspector

The official modelcontextprotocol/inspector tool is the most direct prior art. It has two components: an MCPI React-based web UI for testing/debugging, and an MCPP Node.js proxy that acts as a protocol bridge between the browser and a configured MCP server. The proxy supports all three transports — stdio (it spawns a child), SSE (deprecated), and Streamable HTTP — and acts as both an MCP client (to the server) and an HTTP server (to the UI).

Inspector demonstrates two things directly relevant to MCP Manager: (1) a proxy-style component is sufficient to bridge transports when a UI cannot itself spawn child processes, and (2) treating the manager as an MCP client allows reusing the official SDK for handshake, capability negotiation, and lifecycle management.

uvx / pipx

Both tools install or run Python CLI tools in isolated environments. pipx creates one durable virtualenv per installed tool under $PIPX_HOME/venvs/<name>, with executables exposed on $PATH. uvx (built into uv) instead resolves the requested package, creates a short-lived environment, executes the entry point, and discards the env afterward — though cached envs are reused until pruned, pinned, or refreshed. uvx is written in Rust and reportedly 10-100x faster than pipx.

For MCP Manager specifically: most MCP servers ship as npx or uvx-invokable scripts. We can either (a) shell out to uvx/npx (cheap, fragile) or (b) provide our own equivalent ephemeral-env layer. uvx's model — resolve, cache by package+version, execute, retain cache — is the lighter-weight option and is implementable on top of rustup-managed environments or Nix profiles depending on Stream 2's outcome.
