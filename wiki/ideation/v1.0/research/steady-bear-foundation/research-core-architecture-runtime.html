Research — Async runtime, supervision, and health checks

The core spends almost all of its life waiting on I/O — pipes from child MCP servers, IPC sockets from clients, network connections to remote servers. This page lays out the Rust primitives that make that practical: async runtime, child-process spawning, signal handling, Windows job objects, health-check strategies, and stdio backpressure.

Async runtime choice

The Rust async ecosystem has consolidated around tokio; the State-of-Async-Rust 2025 piece notes that async-std was officially discontinued in early 2025, with the team pointing users at smol. Tokio is documented as more than a runtime — it bundles fs, net, process, and signal modules and is what the major networking crates (Hyper, Axum, Tonic, Reqwest) are written against.

Critically for MCP Manager: the official MCP Rust SDK (rmcp) is built on tokio. Using a non-tokio runtime would require either re-implementing the SDK or running two runtimes in one process — a known source of deadlocks because tokio uses its own AsyncRead/AsyncWrite traits incompatible with the smol/futures ecosystem.

Tokio's task model is also cheap by design: tasks are "green threads" that need only one allocation and ~64 bytes of memory. Tasks have two constraints — 'static lifetime and Send — which mostly only matter when sharing state across tasks.

Spawning child MCP servers

tokio::process::Command is the async mirror of std::process::Command: builder-style configuration (arg(), env(), stdin()/stdout()/stderr(), current_dir()) plus async spawn() returning a Child, and status()/output() that await completion.

The default behavior is the trap most people hit first: when the Child handle is dropped without an explicit wait() or kill(), the child is not killed — the runtime attempts background reaping but offers no guarantees. The fix is one of two:

  • kill_on_drop(true) — the simplest hammer; child dies with the handle.
  • Always co-own a JoinHandle for a supervisor task that awaits child.wait(); the supervisor task is then the structural owner of the child's lifetime.

Sketch — supervisor task per child

// each MCP server becomes one supervisor task
let mut child = tokio::process::Command::new(cfg.command)
    .args(&cfg.args)
    .envs(&cfg.env)
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .kill_on_drop(true)        // safety net; real exit via wait()
    .spawn()?;

let pid  = child.id();
let stdin  = child.stdin.take().unwrap();
let stdout = child.stdout.take().unwrap();
let stderr = child.stderr.take().unwrap();

tokio::spawn(async move {
    // ... pump stdio, watch ping, write to event journal ...
    let status = child.wait().await?;
    journal.record(Exit { pid, status, at: Instant::now() }).await;
});

Unix reaping & SIGCHLD

On Unix, the kernel sends SIGCHLD to the parent when any child changes state; waitpid() with WNOHANG is the standard way to non-blockingly collect status. A subtlety: SIGCHLD is not queued per-event — multiple deaths can collapse into one signal, so handlers should loop waitpid(WNOHANG) until it returns no more children.

For MCP Manager, the typical pattern is:

  1. Tokio internally installs a SIGCHLD handler and exposes async child.wait().await — so most code does not need to touch nix directly.
  2. The nix crate is still needed for: setting up new session/process group via setsid()/setpgid() so the child detaches from the manager's terminal; mounting Linux namespaces if Stream 2 chooses that sandbox; sending SIGTERM to a process group (killpg(pgid, SIGTERM)) so children of the MCP server die together.

nix::sys::wait::WaitStatus has variants Exited, Signaled, Stopped, StillAlive covering every state transition the manager needs to record.

Windows Job Objects

Windows has no concept of process groups; the canonical "kill the whole subtree when the parent dies" mechanism is a Job Object with the JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE flag set. The win32job crate provides a Rust wrapper exposing a Job type with set_extended_limit_info() for the kill-on-close flag. The same crate underpins higher-level supervisors like process-wrap.

Cargo upstream uses this exact pattern: a PR added job objects on Windows specifically so that Ctrl-C during a build cleans up all spawned rustc processes rather than leaking them.

Higher-level wrappers

Three crates sit above tokio::process and bake in the patterns above:

  • process-wrap — adds Unix process-group + Windows job-object wrappers around tokio::process::Command. Used by file-watcher / runner ecosystems (e.g. watchexec).
  • tokio-process-tools — streams stdio with configurable backpressure: DropLatestIncomingIfBufferFull (favors not blocking the child) or BlockUntilBufferHasSpace (favors reliability).
  • kill_tree — best-effort cross-platform recursive kill of a process tree, useful for the "user clicked stop" path when servers themselves spawn helpers.

Health checks: passive vs active

A managed MCP server is "healthy" along two axes the supervisor can observe:

Passive — process aliveWhether the OS reports the child PID still running.Zero (just child.wait()).Crashes, OOM kills, SIGKILL.
Passive — pipe openEOF on stdout/stderr indicates child closed its end.Zero (already reading the pipe).Premature exit, deadlocked event loop that closes stdio.

Active — capability re-listCall tools/list and compare to last snapshot.Higher; only useful for drift detection.Server reloaded its tools but didn't notify.

Per the MCP spec, ping is bidirectional: either party can initiate, the receiver MUST respond promptly with an empty result, and the sender MAY treat timeout as stale. The spec leaves the timeout duration and frequency up to the implementation; community guidance is 2-5 second timeouts. Implementations SHOULD log ping failures for diagnostics.

stdio framing & backpressure

Per the MCP spec, stdio framing is "JSON-RPC messages delimited by newlines, MUST NOT contain embedded newlines". tokio::io::BufReader::read_line with a length cap is the obvious primitive on the read side, and tokio::io::AsyncWriteExt::write_all on the write side.

Backpressure has two flavors:

  1. From the MCP server to the manager — if the manager doesn't drain stdout, the server's write() will block on a full pipe. The manager must always drain stdout in a dedicated task; tokio-process-tools formalizes this with a bounded channel between the reader task and the consumer, with a policy switch between drop-latest and block-on-full.
  2. From the client(s) to the MCP server — if a host fires 200 tool calls at once, the manager should fan them out via a bounded mpsc::channel (Tokio's canonical backpressure primitive) rather than queueing them in memory. The community convention is "mpsc for queues, watch for state, broadcast for events".

Tracing & observability

The tracing crate provides spans, events, and a layered Subscriber model designed for async-heavy code; the #[instrument] attribute auto-wraps functions with spans that record arguments as structured fields. For export to standard observability backends, tracing-opentelemetry is a tracing Layer that converts spans into OpenTelemetry spans and emits them via OTLP.

For an MCP Manager this gives the manager a single instrumentation surface that simultaneously:

  • Drives the internal event journal the clients read (see research · state) by adding a custom tracing Layer that funnels events into the journal store.
  • Bridges to log-using crates via tracing-log so e.g. hyper's logs are captured uniformly.
  • Exports to Datadog/Honeycomb/SigNoz/etc. for users who want it, without forcing OTLP on those who don't.
Caveat from the docs: holding a span guard across an await point can produce incorrect traces; use #[instrument] or instrument() rather than manual enter()/exit() in async code.
