Research — Daemon-only, library-only, or hybrid

This page lays out four real-world archetypes for "tool that manages other long-running processes" — Docker (daemon-required), Podman (daemonless, optional service), Cargo (library + ephemeral CLI), Nix (privileged daemon + unprivileged clients) — and projects them onto MCP Manager. It also covers the practical OS-integration angle: how each archetype interacts with launchd, systemd, and Windows services.

Docker — daemon required

Docker is the canonical "always-on daemon" design: the docker CLI is thin and converts commands into REST API requests sent to dockerd over a Unix socket (default /var/run/docker.sock) or TCP; the daemon does all the work of building, running, and supervising containers and exposing them over the network.

Architectural consequences:

  • Startup latency near-zero per command — the daemon is already warm; first call to the runtime is fast.
  • Centralized supervision — auto-restart, log capture, network setup all happen daemon-side, automatically. If a container dies, the daemon notices.
  • Remote management for free — same REST API works locally over Unix socket or remotely over TCP.
  • Single point of failure — if the daemon crashes, every container loses its supervisor (mitigated in modern Docker by containerd-shim staying alive per container).
  • Privilege model — by default dockerd runs as root, so containers it spawns inherit a path to root; rootless mode exists but is opt-in.
  • OS service required — needs systemd / launchd / Windows Service to start on boot.

Podman — daemonless + optional

Podman explicitly inverts Docker's design: "a simple daemonless tool". The CLI invokes the OCI runtime directly. Persistent supervision is delegated to two layers:

  1. Per-container conmon — daemonizes itself, holds stdio, captures exit status, writes logs to a file or systemd-journal. There is one conmon per running container, "the smallest daemon a container can have".
  2. Optional systemd integration — generated unit files (e.g. podman generate systemd) let users opt into proper service supervision.

Podman also offers an opt-in podman-system-service daemon that exposes a Docker-API-compatible REST endpoint for compatibility with tools that want a daemon — making podman effectively "daemonless by default, daemon if you ask".

Performance characteristics reported in independent benchmarks: Podman scales linearly with 100+ concurrent containers (vs slight Docker degradation), uses ~65% lower memory and ~70% lower idle CPU because there's no persistent daemon paying overhead — Docker funnels every container start through the daemon's event loop, while Podman forks independent processes concurrently.

Cargo — library + ephemeral CLI

Cargo is the "no daemon at all" archetype. State lives on the filesystem (Cargo.toml, Cargo.lock, target/, ~/.cargo/) and each invocation is a fresh process that reads and writes those files. The advisory Rust workspace pattern is documented in the Cargo book and matklad's "Large Rust Workspaces".

Consequences:

  • Startup latency is the cost of process spawn + reading state files — adequate for a build tool, marginal for a tool the user invokes many times a minute.
  • No background work possible — Cargo doesn't ping anything between invocations.
  • No supervision — Cargo would not know if a server it started died after Cargo itself exited.
  • Zero installation overhead — no service to install on boot; works on machines where the user can't enable LaunchAgents/systemd units.

uvx takes a similar shape — short-lived environment, execute, exit; cached environments live on disk to make subsequent invocations cheap. pipx similarly stores each tool's venv in $PIPX_HOME/venvs/<name> and shells out per invocation.

Nix-daemon — privileged + clients

In multi-user Nix the nix-daemon owns the store (database + filesystem) at root privilege. Unprivileged users set NIX_REMOTE=daemon and their CLI connects to the daemon over a Unix socket; the daemon performs all operations on behalf of the user, including running builds inside unprivileged nixbld* users. Build concurrency is capped by the number of build users.

Notable design points the spec / manual call out:

  • The sandbox is for reproducibility, not as a strong security boundary between users.
  • The daemon is launched by the host's service manager — systemd on Linux, launchd on macOS.
  • Single-user mode skips the daemon entirely; the CLI itself becomes the privilege owner.

This is the most relevant template for MCP Manager's "shared install across users" question, even though MCP server installs probably don't require root.

Implications for MCP Manager

Background work the manager actually needs

  • Lifecycle of long-running stdio MCP servers — must persist across host-app restarts so a server doesn't die just because Claude Desktop quit.
  • Periodic ping — needs someone awake between client invocations.
  • Log/journal capture from stderr — needs to consume the pipe continuously even when no CLI/TUI/GUI is watching.
  • OAuth refresh / scheduled re-auth — many MCP servers will eventually mint tokens with finite lifetimes.

These are background tasks; a library-only design (pure cargo-style) cannot do them.

Some prior-art notes on lazy / on-demand activation: launchd lets a service register listening sockets, and launchd itself accepts connections, starting the service only when the first connection arrives — useful for an "idle until first IPC connect" daemon model.

Startup latency budget

A grounded budget for CLI invocations:

  • Cold Rust binary start: ~5-30ms depending on target / static-linkage.
  • Reading SQLite + deserializing registry: 1-10ms for typical (1-50 servers) cases.
  • IPC connect (Unix socket): <1ms locally.
  • Round-trip to daemon over IPC: <1ms (kernel-only).

So a daemon-required CLI is dominated by Rust binary start (~5-30ms) and the daemon hop is essentially free. A library-only CLI pays the same Rust binary start plus the SQLite read (~6-40ms total). The difference is rarely perceptible. The library model gets perceptibly slow only when CLI commands trigger work that the daemon would have already done in the background (e.g. listing tools across 20 stdio servers requires connecting to all of them).
