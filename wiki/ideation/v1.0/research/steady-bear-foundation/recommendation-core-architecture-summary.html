Recommendation — Workspace layout and daemon decision

This is the only page in the stream where opinions appear. The recommendation is one concrete Rust workspace and one daemon-vs-library call, with every load-bearing claim cited back to evidence on the research pages.

TL;DR

  1. Architecture archetype: single binary w/ embedded daemon — one mcp executable that runs as daemon when invoked as mcp daemon (or auto-launched by a CLI command that needs one) and as a thin client otherwise. This is the podman-style "daemonless with optional daemon" pattern, refined to ship a single binary instead of two.
  2. Async runtime: tokio (multi-thread scheduler), because the official MCP Rust SDK (rmcp) is tokio-native.
  3. State store: SQLite via rusqlite with bundled libsqlite3-sys, accessed from async code through spawn_blocking; durable journal in the same DB.
  4. Secrets: keyring crate with OS-native backends; references stored in registry, never resolved into the DB.
  5. Supervisor: per-server async task, transport via rmcp wrappers, Unix process groups via nix, Windows Job Objects via win32job/process-wrap.
  6. Manager-to-server relationship: supervisor by default, opt-in proxy — covers the common case cheaply, while keeping the proxy door open for audit/transport-bridging.

Bottom line: ship the smallest thing that survives MCP's lifecycle requirements, lean on the official SDK for protocol correctness, and keep an exit ramp to a heavier daemon model if usage demands it.

Why single-binary-with-embedded-daemon

From the daemon-vs-library research, the background-work requirement (long-lived stdio servers must outlive the CLI invocation, periodic ping must keep running) eliminates the pure cargo/library archetype. From the podman/conmon prior art, the daemonless-with-optional-daemon design is the most directly applicable pattern.

Three reasons we go further and consolidate into a single binary:

  1. Install ergonomics. One binary, one $PATH entry, one Cargo install command. No "did you install both mcp and mcpd?" failure mode.
  2. Code reuse. The daemon process and the CLI process both link the same mcp-core; the only difference between modes is which subcommand was invoked. No serialized inter-mode upgrade story.
  3. Tmux/Nvim precedent. tmux and nvim --listen both ship a single binary that becomes daemon-like when needed. Users grok this model.

When the user runs mcp ls:

  1. Probe $XDG_RUNTIME_DIR/mcp-manager/daemon.sock (or platform equivalent).
  2. If a daemon is reachable, send a query over IPC and print the result.
  3. If no daemon, open the SQLite store directly in this process (library mode) and print from the registry. No supervised servers are started/touched.

When the user runs mcp start <server> with no daemon:

  1. Auto-spawn mcp daemon as a detached child (with OS-appropriate signal isolation).
  2. Wait for it to be ready; send the start command.
  3. The newly-spawned daemon survives this CLI invocation and keeps supervising.

For users who want the daemon on at boot, ship templates: mcp daemon --install-launchd writes ~/Library/LaunchAgents/io.mcp-manager.daemon.plist, mcp daemon --install-systemd-user writes ~/.config/systemd/user/mcp-manager.service, and the Windows variant registers a per-user Scheduled Task.

Why supervisor by default, opt-in proxy

Per the transports research, full proxy mode couples the manager tightly to MCP version evolution and adds an extra hop on every tool call. Supervisor mode keeps the manager out of the hot path entirely; the manager only needs MCP knowledge to perform passive ping and the initial initialize handshake required by the spec.

We keep proxy mode as an opt-in toggle because it solves real bridging problems — a host that wants Streamable HTTP can talk to a stdio-only server through the proxy — and because it's the only path to per-tool audit logs. Both modes share the same mcp-supervisor code; proxy just adds an extra rmcp client on top.

Why tokio + rusqlite + keyring

  • tokio: Mandatory because rmcp is tokio-native and the broader ecosystem (hyper/axum/reqwest/tonic) is tokio-first.
  • rusqlite vs sqlx: rusqlite is synchronous-only, but our SQL workload (registry reads, journal inserts) is tiny enough that spawn_blocking is fine. rusqlite has decades of stability, can bundle SQLite (no system dep), and exposes hooks/blobs we'll want eventually. sqlx is the alternative if we ever need a multi-backend story (Postgres for shared installs).
  • keyring: The mainstream cross-platform secrets choice; covers macOS Keychain, Windows Credential Manager, Linux Secret Service / keyutils, Android prefs, plus a SQLite-encrypted fallback for headless environments.

Migration story

Schema evolution is planned in:

  • Numbered SQL migration files (0001-init.sql, …) applied at mcp-store startup; version pinned in PRAGMA user_version.
  • Tagged-enum serde versioning for structured columns (transport descriptors, host-config payloads) using a serde-evolve-style pattern.
  • A --read-only mode for the store so a too-new daemon doesn't auto-migrate the DB out from under a still-running older daemon.

Open questions for the orchestrator

  1. Auto-spawn vs require-explicit. Should mcp start silently background-spawn a daemon if none is running, or should it fail with a friendly error pointing to mcp daemon --install-…? The first is friendlier; the second is more transparent about what's happening to the user's machine. (Leaning toward auto-spawn with a one-time interactive prompt on first use.)
  2. Multi-user shared installs. For machines where multiple OS users want to share an MCP server install (the nix-daemon use case), do we ship a "system mode" where a privileged daemon owns the registry? Likely defer to v2.0; v1.0 stays per-user.
  3. Wire protocol scope (defer to Stream 4). The CoreApi trait has both request/response and streaming methods (subscribe_events, subscribe_state). Stream 4 needs to pick a wire format that supports server-streaming — gRPC, JSON-RPC over Unix socket with bidi notifications, or custom. We're flagging that this trait cannot be cleanly served by request/response-only protocols.
