Dialing mcpd — UDS via Tauri command vs. HTTP/SSE from WASM

There are two viable patterns. They are not mutually exclusive; a real implementation will probably use both depending on the call site.

Pattern A — Tauri command proxies UDS

The Leptos WASM cannot itself open a Unix-domain socket (the WebView's network APIs don't expose UDS). The clean path is to have Rust-side Tauri commands hold the tokio::net::UnixStream connection to mcpd, and expose typed commands (list_servers, start_server, get_secret, ...) that the Leptos frontend invokes via wasm-bindgen[?]. Community precedent for resident-daemon IPC in Tauri specifically discusses UDS-vs-pipe trade-offs and lands on UDS for multi-window apps[?]. 

// src-tauri/src/lib.rs — Rust holds the UDS connection.
use tokio::net::UnixStream;
use tauri::State;

struct McpdConn(tokio::sync::Mutex<UnixStream>);

#[tauri::command]
async fn list_servers(state: State<'_, McpdConn>) -> Result<Vec<Server>, String> {
    let mut s = state.0.lock().await;
    jsonrpc_call(&mut *s, "servers.list", json!({})).await
        .map_err(|e| e.to_string())
}

Streaming responses (log tails, server status events) use Tauri's tauri::ipc::Channel API, which is the recommended mechanism for ordered, low-overhead streaming from Rust to the WebView[?].

Pattern B — Leptos hits mcpd's HTTP/SSE bridge directly

Since the orchestrator notes mcpd already exposes an HTTP/SSE bridge for browser-based clients, the Leptos WASM can use the WebView's native fetch and EventSource APIs to talk to http://127.0.0.1:<port> directly — exactly as a browser would. This skips the Tauri-command marshaling entirely, but loses the ability to enforce Tauri's ACL/capabilities security model on a per-call basis. 

// Leptos resource against mcpd's HTTP/SSE bridge — no Tauri command in the loop.
use leptos::prelude::*;
use gloo_net::http::Request;

fn servers_resource() -> Resource<Vec<Server>> {
    Resource::new(|| (), |_| async move {
        Request::get("http://127.0.0.1:7777/v1/servers")
            .send().await.unwrap()
            .json::<Vec<Server>>().await.unwrap()
    })
}

The "mcpd not yet running" boot case

The orchestrator's constraint: mcpd auto-spawns on first GUI launch; the GUI must handle "mcpd not yet running" with a brief startup spinner, not an error. Tauri has clean primitives for this.

  1. Sidecar mcpd or detached spawn. Tauri's sidecar feature lets you embed mcpd as an external binary and run it via app.shell().sidecar("mcpd").spawn()[?][?]. This makes the bundle ~5–10 MB heavier but guarantees a known-good mcpd binary ships with the GUI. Alternatively, the GUI can probe for a running mcpd (UDS file exists + socket accepts), and only spawn one if absent.
  2. Probe + retry loop. In the Tauri setup hook (Rust), open a UDS connection with exponential backoff (50ms → 100ms → 200ms ... up to 5s). Emit a tauri::Event to the frontend on each retry so Leptos can show "Starting mcpd…" instead of an error.
  3. Leptos UI shows the spinner. A top-level <Suspense> wraps the app's root; until the boot_status signal flips to Ready, it shows the spinner. On Ready, the rest of the app mounts.
// src-tauri/src/lib.rs — sidecar spawn + ready probe.
tauri::Builder::default()
  .setup(|app| {
    let handle = app.handle().clone();
    tauri::async_runtime::spawn(async move {
        let _child = handle.shell().sidecar("mcpd")?.spawn()?;
        wait_for_uds("/run/user/1000/mcpd.sock", Duration::from_secs(5)).await?;
        handle.emit("mcpd-ready", ()).ok();
        Ok::<_, anyhow::Error>(())
    });
    Ok(())
  })
  .run(tauri::generate_context!())?;

Live updates — server list, log tails, projection status

Three streams matter for the v1.0 GUI:

  1. Server list (rare updates, low fan-out) — best via polling-on-event: Leptos invalidates its Resource whenever mcpd emits a servers.changed event. Both Pattern A (Tauri event) and Pattern B (SSE) work; A is leaner.
  2. Log tails (high-frequency, append-only) — best via Tauri Channel API streaming UDS bytes. The Channel API is explicitly designed for ordered streamed data and is what Tauri itself uses internally for download progress and child-process output[?]. Leptos appends each LogLine to a RwSignal<VecDeque<LogLine>> with a max length to cap memory.
  3. Projection status (periodic, structured) — same as server list. Mostly tens of events per minute; both patterns are fine.

The SSE feature request for Tauri's plugin workspace (#1002)[?] is open, which means there is no first-party Tauri SSE plugin yet. The WebView's built-in EventSource works on WKWebView; on WebKitGTK it has historically been more fragile (and the version differs between distros). For MCP Manager, that argues for Pattern A (Channel API) for log streams and reserving SSE for cases where the same code must also run in a plain browser.

Secrets editor flow

Secrets are the most sensitive surface. The constraints:

  • Plaintext must never persist client-side; the canonical store is mcpd.
  • Editing should round-trip via mcpd's existing API; the GUI is a thin editor.
  • Pasting from the clipboard should not be blocked, but the secret should not be logged.

Recommended flow in Tauri+Leptos:

  1. User clicks "Edit secret FOO". Leptos invokes Tauri command get_secret_redacted("FOO") which returns a placeholder (e.g. "●●●●●●") — never the plaintext.
  2. User types the new value into a Leptos <input type="password">. The signal is held only in-memory in the WASM heap.
  3. On save, Leptos invokes set_secret("FOO", value). The Tauri command writes through UDS to mcpd, which encrypts and persists.
  4. The Rust command immediately drops the value; Leptos resets the input signal to a fresh placeholder.

Tauri's ACL/capabilities layer lets you restrict which windows can invoke the secrets commands[?] — useful if a future version of the app embeds a tools-panel that should not have secret read access.

Type sharing with the Rust core

This is the single biggest win of the stack. mcpd's wire types — request/response structs, error enums, JSON-RPC envelopes — live in a workspace crate (e.g. mcpd-protocol). Both mcpd, the CLI/TUI, and the Leptos WASM crate depend on mcpd-protocol with default features. The same struct Server { name: String, status: ServerStatus, ... } is used in three places:

  • mcpd serializes Server when answering servers.list.
  • The Tauri Rust process deserializes it from UDS, validates Tauri ACL, re-serializes it across the IPC boundary as JSON.
  • The Leptos WASM deserializes it on the other side via serde-wasm-bindgen and binds it into its reactive signal graph.

When the protocol changes — a new field, a renamed variant — the compiler tells you everywhere it broke. No TypeScript types file to keep in sync, no codegen step. This is a guarantee no JS/TS frontend on Tauri can match, and it is the headline reason to consider Tauri+Leptos over Tauri+React for an app that lives this close to its daemon.

For typed IPC commands themselves, TauRPC[?] provides a trait-based abstraction over Tauri commands so you write the contract once and both sides type-check. With Leptos you skip its TS codegen and use the Rust bindings directly.
