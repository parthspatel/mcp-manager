Stack research — Tauri 2 + Dioxus in 2026

Dioxus 0.7 (released September 8, 2025; latest patch 0.7.9, May 8, 2026) reframed the project around four targets that share one component tree: web, desktop, mobile, and the new Native renderer powered by Blitz[1]. The release also shipped Subsecond — incremental linking that lets you hot-patch Rust code at runtime — and a fully reworked Axum-based fullstack story with SSE, WebSockets, and typed forms[1][2]. This page covers each renderer in turn, the build/dev loop, and what production looks like.

Dioxus's four renderers

One of the most-misunderstood facts about Dioxus is that it isn't a single rendering engine — it's a VirtualDOM (dioxus-core) plus pluggable renderers. As of 0.7 there are four production-or-experimental targets[3].

Desktop — Wry/Tao WebView

dioxus-desktop embeds the OS WebView via wry (rendering) and tao (windowing) — exactly the same engine layer Tauri uses[4]. On macOS that means WKWebView; on Linux, WebKitGTK. The crucial property: the UI code runs as native Rust in the host process, not as WASM inside the WebView. The WebView only renders the HTML/CSS that Dioxus produces. There is no JS<->Rust IPC boundary like Tauri has by default.

Concretely this means a Dioxus event handler is a normal Rust FnMut closure, can capture tokio handles, and can synchronously call any crate (reqwest, tokio::net::UnixStream, rusqlite) without crossing a serialization boundary. 

// dioxus-desktop — components live in Rust, event handlers are just closures
use dioxus::prelude::*;

fn main() { dioxus::LaunchBuilder::desktop().launch(App); }

fn App() -> Element {
    let mut count = use_signal(|| 0u32);
    rsx! {
        h1 { "MCP servers" }
        button { onclick: move |_| count += 1, "Refresh ({count})" }
    }
}

Web — WASM via web-sys

The same RSX component tree compiles to WebAssembly and renders into the browser DOM through web-sys. This is what enables Dioxus's marketing claim of one codebase across web and desktop[1]. For MCP Manager the relevance is: if you ever want to expose the GUI as a web app pointed at a remote mcpd, the same components ship there with no rewrite.

Web is also the only target where the WASM<->JS boundary actually applies — desktop is plain Rust.

Native — Blitz (experimental, pre-alpha)

dioxus-native renders Dioxus apps entirely on the GPU using Blitz, a new HTML/CSS engine built on Firefox's Stylo (CSS), Taffy (layout), and Vello (paint), running on WGPU[5][6]. The promise is huge: no system WebView, no IME-via-WebKit quirks, fully self-contained binary, full GPU compositing.

The reality in May 2026 is sober. Blitz's own README describes itself as "still in a pre-alpha state. It already has a very capable renderer, but there are also still many bugs and missing features. Performance has not been a focus."[5] Missing event types include mouseover and form events; missing widgets include several <input> variants and <iframe>[5]. The team publishes a live CSS support matrix at blitz.is/status/css[7].

Verdict for MCP Manager v1: not yet. Worth re-evaluating in 6–12 months — by which time accessibility (AccessKit integration is the natural fit) and missing widgets may have landed.

LiveView — being deprioritized

Dioxus LiveView renders on the server and streams DOM patches to a browser over WebSocket, Phoenix-style. The maintainers have explicitly stated they are deprioritizing LiveView and recommend the new Fullstack story (server functions + hydration over Axum) instead[8]. LiveView may be removed in a future release.

Not relevant to MCP Manager — the GUI is a single-user desktop client, not a server-rendered shared app.

Tauri-wrapped vs. standalone Dioxus

The orchestrator's framing — "Tauri 2 + Dioxus" — is genuinely a choice between three architectures. They are not interchangeable.

ArchitectureWhat runs whereIPC boundaryRecommended for MCP Manager?
Plain dioxus-desktop Rust process embedding WKWebView via Wry; components are native Rust closures; WebView only paints HTML/CSS None — all UI logic is in-process Rust Yes — best fit, least ceremony
Tauri-2 shell + Dioxus-WASM frontend Tauri's main process in Rust; Dioxus runs as WASM inside the WebView; UI talks to host via tauri::invoke / Channel WASM <-> JS bridge <-> Rust Tauri commands (two hops) No — more code, more ceremony, no real upside on macOS+Linux
dioxus-native (Blitz) Rust + WGPU; no system WebView at all None No — pre-alpha; missing widgets, layout bugs, no a11y story yet

The Tauri maintainers themselves take the position that Dioxus has its own desktop framework and that mixing the two is community-supported only — there is no first-party create-tauri-app template for Dioxus[9]. The only notable template is the community Desdaemon/tauri-dioxus repo[10].

So what would Tauri-wrapping a Dioxus frontend buy you? Mainly: Tauri's capabilities/permissions ACL, its mature sidecar bundler for shipping binaries, its broader plugin ecosystem (keyring, store, updater, autostart). For mcpd as a sidecar binary specifically, Tauri's app.shell().sidecar() API is well-trodden[11]. But these are bundling/distribution wins, not runtime wins — and they come at the cost of routing all UI events through an extra serialization boundary.

Build pipeline and dev loop

Dioxus 0.7's dx CLI is the headline dev-experience win[12]:

$ dx new mcp-manager-gui    # scaffold
$ dx serve                  # dev server with RSX hot reload
$ dx serve --hotpatch       # add experimental Rust hot-patching (Subsecond)
$ dx bundle --package-types macos,dmg,deb,appimage   # ship

Two layers of hot reload[13]:

  • RSX hot reload — stable since 0.6. Edits to RSX literals, formatted strings, and properties update instantly without a rebuild. App state preserved.
  • Subsecond Rust hot-patching — experimental in 0.7. Edits to actual Rust function bodies are incrementally linked into the running binary, also preserving state. Works on macOS, Linux, Windows, and even mobile[2]. This is the first Rust framework to ship runtime hot-patching of Rust code — by a comfortable margin.

For MCP Manager, where iteration on log-tail UI, secret-editor forms, and server-row layouts dominates the dev loop, this is materially better than Tauri's frontend-HMR-but-restart-the-backend cycle.

Bundling: dx bundle produces .app + .dmg on macOS and .deb + .AppImage on Linux[14]. Code signing on macOS is the standard codesign + notarization flow — no Dioxus-specific tooling. Tauri's bundler (if you wrap) is marginally more mature for notarization automation but the gap is small.

Ecosystem and production users

Dioxus Labs is a YC-funded company[15]; the project has 36.1k GitHub stars and a small full-time core team backed by FutureWei, Satellite.im, and the GitHub Accelerator[3]. Named production users include Huawei (internal apps), an Airbus + ESA collision-avoidance UI, and Satellite.im (a P2P Discord alternative)[15]. Notably no major shipping app uses the Tauri+Dioxus combo specifically; teams that pick Dioxus use dioxus-desktop directly.

Tauri 2 (stable since October 2, 2024) is comparatively far more battle-tested — Spacedrive, dozens of indie apps, and a deep first-party plugin lineup (HTTP, WebSocket, Store, FS, Shell, Notification, Updater, OS info, Stronghold/Keyring)[16].

The boringcactus 2025 GUI survey — the most comprehensive recent comparison — identified Dioxus as one of only four Rust GUIs (alongside Slint, egui, and WinSafe) that pass a minimal accessibility + IME test, and noted that Dioxus inherits a11y trivially from the WebView[17].

License and governance

Dioxus and Tauri are both MIT/Apache-2.0 dual-licensed[3][18]. Wry, Tao, and Blitz inherit the same. Zero GPL/commercial exposure against MCP Manager's permissive-license requirement.

Governance: Dioxus is a single-vendor open-source project (Dioxus Labs, YC company) with community contributions. Tauri is governed by the Tauri Foundation, a Commons Conservancy member. Tauri has the more diversified governance; Dioxus has tighter product direction at the cost of being one rugpull away from disruption — though YC funding and named institutional users mitigate that risk substantially as of 2026.
