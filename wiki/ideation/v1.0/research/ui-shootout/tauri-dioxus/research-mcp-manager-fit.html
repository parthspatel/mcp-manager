Fit research — Dioxus for the MCP Manager GUI

This page walks through MCP Manager's actual requirements — GUI ↔ mcpd dialing, secrets editing, daemon-not-yet-running boot, live updates, type sharing with the Rust core — and shows the concrete Dioxus shape for each. Throughout, "Dioxus" means dioxus-desktop standalone unless noted. The Tauri-wrapped variant and the Blitz/Native variant are flagged where they materially differ.

Dialing mcpd: UDS or HTTP/SSE bridge

mcpd exposes JSON-RPC over a Unix domain socket and an HTTP+SSE bridge over loopback. The GUI's question: which transport does it dial, and from which side of the WebView boundary?

Dioxus-desktop has a unique advantage here: there is no WebView IPC boundary. Event handlers and effects run as native Rust in the host process, so the UI code can construct a hyper client over a tokio::net::UnixStream or a reqwest::Client against loopback and drive it directly from a signal-tracked async task[1]. There is no Tauri command to declare, no #[tauri::command] marshalling.

// Dioxus-desktop: dial mcpd's UDS directly from a use_resource
use dioxus::prelude::*;
use mcp_core::{ServerList, McpClient};  // shared crate

fn ServerListView() -> Element {
    // Background-resolved async query, re-runs when deps change.
    let servers = use_resource(|| async move {
        let client = McpClient::connect_uds("/var/run/mcpd.sock").await?;
        client.list_servers().await
    });

    match &*servers.read_unchecked() {
        Some(Ok(list))  => rsx! { ServerTable { servers: list.clone() } },
        Some(Err(e))    => rsx! { ErrorBanner { message: "{e}" } },
        None            => rsx! { Spinner {} },
    }
}

By contrast, the Tauri-wrapped variant must declare each call as a #[tauri::command] on the Rust side, register it in .invoke_handler(...), and the WASM frontend invokes it via tauri::invoke("list_servers", &()). That's an extra layer of serialization (always JSON-encoded by Tauri's IPC[2]) for no benefit — the data was already going to be serde-encoded JSON-RPC on the wire to mcpd.

UDS vs HTTP/SSE bridge: pick UDS where possible. Local UDS skips TCP overhead, can use Unix file permissions for auth, and avoids port-conflict edge cases. hyperlocal or hyper's bundled UDS connector both work fine inside dioxus-desktop's Rust process[3]. Use the HTTP/SSE bridge for remote/headless mcpd setups in the future.

Cold start: mcpd not yet ready

Per the orchestrator's constraints: mcpd auto-spawns on first GUI launch; the GUI must show a brief startup spinner, not an error. The clean shape in Dioxus:

// Boot sequence: ensure mcpd is up, then mount the app
fn App() -> Element {
    let mcpd_ready = use_resource(|| async {
        ensure_mcpd_running().await?;          // spawn if needed
        wait_for_health(/* deadline = 10s */).await
    });

    match &*mcpd_ready.read_unchecked() {
        None              => rsx! { BootSplash { message: "Starting mcpd..." } },
        Some(Err(e))      => rsx! { BootError { message: "{e}", retry: || mcpd_ready.restart() } },
        Some(Ok(())) => rsx! { MainShell {} },
    }
}

ensure_mcpd_running either spawns a sidecar binary or connects to an already-running instance. With dioxus-desktop, this is plain tokio::process::Command::new("mcpd").spawn() — no Tauri plumbing required. If wrapping in Tauri, use app.shell().sidecar("mcpd").spawn()[4], which is more polished for bundling but functionally equivalent.

The use_resource hook integrates cleanly with Suspense-style rendering — the spinner shows automatically while the future is pending, and the UI swaps in once Ok(()) arrives.

Live updates from mcpd: log tails, status, toolchain projection

This is where Dioxus's signal model and Dioxus Fullstack's streaming primitives shine. mcpd publishes events as SSE — log lines, server state transitions, toolchain projection status changes. The GUI subscribes and renders them live.

From dioxus-desktop's Rust process, the idiomatic shape is a background tokio task that owns the SSE connection and pushes events into signals[5]:

// Subscribe to mcpd's SSE event stream; route each event into a signal.
fn use_mcpd_events() -> Signal<Vec<LogLine>> {
    let mut log = use_signal(Vec::<LogLine>::new);

    use_future(move || async move {
        let mut events = McpClient::connect_uds("/var/run/mcpd.sock")
            .await?
            .subscribe_events()
            .await?;          // returns futures::Stream<Item = McpEvent>

        while let Some(ev) = events.next().await {
            match ev {
                McpEvent::Log(line) => log.write().push(line),
                McpEvent::StateChange { .. } => { /* update other signals */ }
                _ => {}
            }
        }
    });

    log
}

Component code consumes the signal — no callback wiring, no useEffect dependency arrays. Dioxus's signals only re-render the subscribed components, so a log-tail panel scrolling thousands of lines doesn't trigger renders elsewhere.

Alternative — EventSource from the WebView side: the WebView has native EventSource for HTTP-based SSE, which works fine if mcpd's loopback HTTP bridge is preferred. But routing through the Rust process and signals keeps everything typed and avoids polyfills[6].

Dioxus 0.7's fullstack story added first-class SSE and WebSocket helpers on the Axum side[7]. For MCP Manager (where mcpd is the server, not Dioxus's Axum) we mostly use these as client-side consumers — but the same primitives apply if we ever serve the GUI as a web app.

Secrets editor

The secret editor is the most security-sensitive surface. mcpd holds the canonical store; the GUI is just a form. Two transport considerations:

  1. Plaintext in flight: UDS with appropriate Unix permissions is sufficient for v1; if HTTP/SSE bridge is used, bind to loopback only.
  2. Storage at rest: mcpd's job, not the GUI's. The GUI should never persist secrets to disk.

If the GUI needs to remember a local convenience credential (e.g., a passphrase for unlocking the mcpd vault), use the OS keychain via the Rust keyring crate directly — no need for a Tauri plugin since dioxus-desktop is native Rust. (If wrapping in Tauri, the community tauri-plugin-keyring wraps the same crate[8]; Tauri's old Stronghold plugin is being deprecated in v3 in favor of OS-keychain approaches[9].)

// Secret edit form — values are sent to mcpd, never persisted locally
fn SecretEditor(server_id: ReadOnlySignal<ServerId>) -> Element {
    let mut value = use_signal(String::new);
    let mut status = use_signal(|| SaveStatus::Idle);

    let on_save = move |_| async move {
        status.set(SaveStatus::Saving);
        match mcpd().set_secret(server_id(), value.read().clone()).await {
            Ok(_)  => { value.set(String::new()); status.set(SaveStatus::Saved); }
            Err(e) => status.set(SaveStatus::Failed(e.to_string())),
        }
    };

    rsx! {
        input { r#type: "password", value: "{value}", oninput: move |e| value.set(e.value()) }
        button { onclick: on_save, "Save" }
        StatusPill { status }
    }
}

Type sharing with the Rust core

The single biggest argument for any Rust-frontend stack over Tauri+TypeScript: one set of types. With dioxus-desktop the wins compound — no marshalling boundary at all.

StackWhere types liveWhat crosses a boundary
Tauri + React/TS Rust structs in mcp-core → manually mirrored TS types (or via ts-rs, specta) JSON over tauri::invoke → runtime type-checked by serde
Tauri + Dioxus-WASM One Rust crate shared between Tauri host and WASM frontend JSON over tauri::invoke → serde both sides, same types
dioxus-desktop One Rust crate shared between UI components and core logic Nothing — UI and core are the same process. Boundary is only mcpd's JSON-RPC wire format.

The practical shape: a mcp-core workspace member that defines ServerSpec, ToolDescriptor, McpEvent, etc., with #[derive(Serialize, Deserialize)]. Both mcpd and mcp-gui depend on it. The GUI passes ServerSpec values as Dioxus prop values directly — no FFI, no JSON-RPC stringification, no ts-rs codegen step[10].

Putting it together — workspace shape

mcp-manager/
├─ crates/
│  ├─ mcp-core/           # shared types (ServerSpec, McpEvent, JSON-RPC client)
│  ├─ mcpd/               # the daemon — bin
│  ├─ mcp-cli/            # CLI client — bin
│  └─ mcp-gui/            # Dioxus desktop app — bin
│     ├─ Cargo.toml       # depends on dioxus, mcp-core, tokio
│     ├─ Dioxus.toml      # dx config (bundle metadata, assets)
│     ├─ src/
│     │  ├─ main.rs       # LaunchBuilder::desktop().launch(App)
│     │  ├─ boot.rs       # ensure_mcpd_running / health check
│     │  ├─ ipc.rs        # thin wrapper around mcp-core's client
│     │  └─ views/        # ServerList, LogTail, SecretEditor, ...
│     └─ assets/          # CSS, icons, fonts
└─ Cargo.toml             # workspace

To run during development: dx serve --hotpatch from crates/mcp-gui/. To ship a release: dx bundle --release --package-types app,dmg on macOS, dx bundle --release --package-types deb,appimage on Linux[11].

That's the entire delta from a CLI-only mcp-manager workspace: one new crate. No node_modules, no separate src-tauri/ directory, no two-toolchain build.
