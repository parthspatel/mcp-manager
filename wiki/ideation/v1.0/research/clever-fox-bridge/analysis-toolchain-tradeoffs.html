Tradeoffs analysis

The research pages catalogue tools, mechanics, and prior-art sync strategies neutrally. This page is where the trade-offs surface — where each strategy hurts, what the security model demands, and how schema-version drift complicates everything. Opinions remain in the recommendation; this page is analytical.

Overwrite vs merge

The deepest design choice is whether MCP Manager owns each target file or collaborates with the user on it. Overwrite is dramatically simpler — render canonical state, write the file, done — but it forces users into "all servers go through MCP Manager or none" without nuance. Merge models (managed-block, three-way, overlay) let the user mix MCP-Manager-owned servers with hand-edited servers in the same target file, at the cost of significantly more code and a real conflict-resolution story.

The empirical reality, observed from how users actually treat their MCP configs (Stream 1's pain-points page documents this), is that they hand-edit. They paste snippets from GitHub READMEs, they tweak args arrays, they try things. A tool that refuses to coexist with that behaviour will be uninstalled within a week. Therefore: overwrite is not viable as the default.

Push vs watch

A push model writes the target file when the canonical state changes (server added, removed, edited via the CLI/TUI/GUI). A watch model adds the reverse: when the user edits the target file, the daemon notices and either (a) propagates the change back into canonical state, or (b) refuses, opening a conflict dialog.

Watch sounds elegant but creates a positive feedback loop with editors that auto-format on save: the editor reformats the JSON, the watcher sees a change, projects again with our preferred formatting, the editor reformats again. Beyond formatting, watch also means that an attacker who can write to any one target file can poison the canonical state by triggering the import path — an inversion of the trust model.

Conclusion of the tradeoff: push by default, no watch in v1.0. The user can re-run mcpm sync manually or it can be invoked by a save hook in their editor of choice.

Full-file ownership vs managed-block

Managed-block has one structural weakness: it does not work on pure JSON. Claude Code, Cursor, Cline, Windsurf, and Claude Desktop all use JSON without comments. Five Tier-1 or Tier-2 tools cannot host a comment-fenced managed region.

Three workarounds exist:

  1. Sentinel-key fence — reserve a top-level key like "_mcpManagerManaged" whose value is the managed object; the user retains any other top-level keys. The fence is structural rather than lexical. Cost: target tool must tolerate unknown top-level keys (most do).
  2. Sibling-file projection — for tools that natively support multiple config files, project to a sibling that the tool already reads. Claude Code's .mcp.json beside settings.json works exactly this way.
  3. Full-file ownership — for tools that have no other config in the file, take it over. The user understands ".cursor/mcp.json is MCP Manager's file; if you want a hand server, add it in the canonical state."

Different tools land in different buckets; no single answer covers all cases. The recommendation specifies a per-tool policy table.

Schema-version drift

Every Tier-1 tool ships a new MCP-related schema version every few months: VS Code added inputs for prompt-on-load secrets in mid-2025; Continue moved mcpServers from object to array; Claude Code added headersHelper. If the projector hardcodes schema knowledge, every drift requires a new MCP Manager release.

This is the strongest argument for declaring per-toolchain projection in data rather than code. Even Tier-1 tools should be expressed as a toolchain manifest (just one that ships in the binary's assets/ directory). Community manifests can be loaded from $XDG_CONFIG_HOME/mcp-manager/toolchains/*.toml at runtime — the same model Renovate uses with customManagers and Homebrew with taps.

Conflict-resolution UX

When the projector finds the existing target file differs from the last-projected baseline (i.e. the user hand-edited the managed region), three policies are possible:

  1. Preserve & report. Don't write. Surface the conflict in the CLI/TUI/GUI with a diff. User decides.
  2. Refuse & prompt. Block all projection across all targets until the user resolves. Hard fail.
  3. Backup & overwrite. Move the existing file to file.bak.<timestamp> and proceed. User can recover.

Each has real arguments. (1) is the kindest but creates the "why didn't my server appear?" failure mode. (2) is safest but blocks unrelated tools from getting updates. (3) is reversible but feels destructive. The recommendation picks (1) with the user-affordance that mcpm sync --force degrades to (3).

Security implications

The projector is the highest-leverage security surface in the whole product. A poisoned canonical entry projected into N editors on M projects equals N×M places where a malicious server appears as already-approved. Stream 2's threat model (stoic-badger-sandbox) treats canonical-state writes as privileged operations behind their isolation boundary; our projector inherits that requirement and adds three of its own:

  • No projection on un-trusted canonical state. Servers imported via untrusted channels (e.g. one-click install links from the web) must be marked "quarantined" until the user confirms, before they are projected anywhere.
  • Diff-before-write. The CLI/TUI/GUI must show the user the projection delta before the projector writes, on first-time projection into each target.
  • Secret materialization is per-tool. Never write a secret value to a target file. If the only way to give a target the secret is to materialize it (e.g. envFile-style references), write the file with 0600 permissions to ~/.local/state/mcp-manager/secrets/<target>/, never under the target tool's directory.

The asymmetric blast radius is the key insight: deleting a server from canonical state is "remove from N places", adding a server is "authorize on N places." The default should be additive-with-consent and subtractive-automatic.

Cross-platform edge cases

  • MSIX virtualization on Windows. Claude Desktop's MSIX install on Windows reads its config from a virtualized path under %LOCALAPPDATA%\Packages\<package>\LocalCache\Roaming\Claude\, not %APPDATA%\Claude\. Our projector must detect MSIX and project to the right path.
  • Flatpak/Snap sandbox on Linux. Cursor and VS Code installed via Flatpak read from ~/.var/app/<flatpak-id>/config/ not ~/.config/. Same for Snap with ~/snap/<snap-name>/current/.config/.
  • JetBrains per-major-version directories. A user with IntelliJ 2024.3 and IntelliJ 2025.2 installed has two separate config trees. Projection must enumerate all, prompt before projecting into the older one.
  • Symlink ownership semantics on macOS Sequoia. macOS 15 added tighter protection on user-config files for sandboxed apps; symlink-based projection breaks for App Store-installed editors.
  • WSL2 cross-filesystem. A VS Code instance running on Windows pointed at a WSL2 distro reads workspace config from the Linux file system but user config from the Windows side. Our projector running in either environment must understand the split.
