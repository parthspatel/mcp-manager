Sync modes — prior-art survey

This page surveys the families of sync semantics used by other declarative-config / dotfile / config-management tools, with citations to their reference implementations. The point is to anchor our recommendation in concrete prior art rather than inventing terminology.

Push (overwrite)

The simplest model: take the canonical state, render the entire target file, write it. Everything in the target file that wasn't generated by the projector is lost.

Prior art: chezmoi's basic apply mode without templates is essentially this for files marked as "managed". Most CI-generated config (GitHub Actions writing .github/workflows/*) operates this way.

Strengths: Trivial to implement, perfectly idempotent, easy to debug (the file is exactly what the canonical state says).
Weaknesses: Destroys hand-edits silently. Hostile UX when the user has added a server outside MCP Manager. Forces a binary "MCP Manager owns this file" choice the user may not want.

Managed-block (fenced region)

A region inside the target file is delimited by marker lines (# BEGIN MCP-MANAGER MANAGED BLOCK ... # END MCP-MANAGER MANAGED BLOCK). The projector reads the file, replaces only the region between markers, and writes the file back. Content outside the markers is preserved byte-for-byte.

Prior art: Ansible's blockinfile module is the canonical reference for this pattern. Starship's shell-integration installer uses the same fence approach to inject hooks into .bashrc / .zshrc without losing the rest of the rcfile. Many language-version managers (rbenv, pyenv) follow this pattern.

Strengths: Preserves hand-edits outside the fence. Self-documenting (the markers tell future humans what's going on). Universal across line-oriented config formats (YAML, TOML, JSONC, XML, INI).
Weaknesses: Does not work on pure JSON (no comments). Requires careful parsing of the existing file to find the markers. If the user moves the markers or edits inside them, behavior is undefined — conflict-resolution UX matters.

Pull-only (one-time import)

MCP Manager never writes to the target file directly. Instead, it provides a CLI subcommand (mcpm export --target vscode > .vscode/mcp.json) that prints the projection to stdout. The user redirects to the file. Subsequent canonical changes are not automatically propagated.

Prior art: The way fnm env outputs shell-init code for the user to eval. The way Kubernetes kustomize build produces YAML the user redirects into kubectl apply -f -. asdf-style language version managers emit shims rather than mutating shell rcfiles.

Strengths: Zero blast radius. The user is always in control. The projection is a pure function with no I/O side-effects on the user's machine.
Weaknesses: Trades safety for inconvenience. The user must remember to re-run the export every time canonical state changes. Doesn't compose with daemon-driven workflows.

Three-way merge (diff3)

Maintain three versions of the file: the last-written-by-mcpm version (the "base"), the user's current version (the "ours"), and the newly-projected version (the "theirs"). Use diff3 to merge them, emitting conflict markers if the user's edits collide with the projection.

Prior art: FreeBSD's etcupdate applies this pattern to /etc updates across base-system upgrades. Git's merge driver uses diff3 as one of its three styles.

Strengths: Preserves hand-edits everywhere, not just inside a fence. Surfaces conflicts explicitly. Familiar UX for any developer who has done a merge.
Weaknesses: Requires keeping the "base" version on disk (typically under ~/.local/state/mcp-manager/). Conflict resolution is now an interactive UX problem — the daemon can't resolve it on its own. Diff3 on structured formats (JSON/TOML/XML) often produces semantically nonsensical merges.

Overlay / kustomize-style

The user owns a "base" file that they edit freely. MCP Manager owns an "overlay" file (e.g. .vscode/mcp.json.mcp-manager-overlay) that the projector regenerates. At runtime, the target tool reads the merged file, computed via JSON Merge Patch or JSON Patch semantics.

Prior art: Kustomize's overlay/base model. Nix home-manager's lib.mkMerge at module level.

Strengths: Clean separation of ownership. The user knows exactly which file is theirs. The overlay is regenerable from canonical state without consultation.
Weaknesses: Requires the target tool to know how to read the merged result. Most MCP-consuming tools do not; they read one file. This pattern only works if MCP Manager owns the canonical file and the user-edits flow into the overlay — inverting the usual mental model. Confusing for novices.

Watch + reconcile loop

The daemon watches both its own state store and the target file. On either side changing, it reconciles. If the target file diverges from canonical, the daemon overwrites (or, more politely, opens a conflict prompt). This is operator-style continuous reconciliation.

Prior art: Kubernetes controllers' reconcile loop. Home-manager's switch with the systemd-user-units mode. chezmoi apply --watch patterns.

Strengths: Always converged. Most automated of the strategies. Surfaces drift in near-real-time.
Weaknesses: Worst blast radius — a bad canonical entry lands in every editor within seconds, on every machine, before the user can react. Surprising when the user wants to experiment in a single tool's config. Hard to disable selectively.

Symlink / bind mount

Replace the target file with a symlink (or, on Linux, a bind mount) to a file in ~/.local/share/mcp-manager/projections/. MCP Manager owns the destination; the target tool follows the link transparently.

Prior art: dotter, GNU Stow, and Nix home-manager all use symlink farms for dotfiles.

Strengths: No file rewriting needed. Atomic updates (replace the link target). Cleanly reversible (delete the link, restore the original).
Weaknesses: Symlinks are second-class citizens on Windows — they require admin rights or developer mode. Some applications (notably MSIX-virtualized Claude Desktop on Windows) resolve symlinks unexpectedly. Many editors detect "file replaced underneath me" as a security issue or reload-prompt trigger. Bind mounts require root on Linux. Doesn't work for tools whose config file is inside a versioned application directory that the OS recreates on upgrade.
