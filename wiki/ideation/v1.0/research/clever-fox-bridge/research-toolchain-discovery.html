Tool discovery

Before MCP Manager can project into a tool, it has to know the tool is installed. This page documents the cross-platform mechanisms for detecting each Tier-1/Tier-2 client, in order of preference: well-known paths first, executable on PATH second, OS metadata (Spotlight / registry / desktop entries) third. The goal is high precision with zero spawning of the target application during discovery.

Discovery strategy hierarchy

  1. Well-known config path exists. Most reliable signal. If ~/.cursor/mcp.json exists, Cursor is installed; if ~/.codex/config.toml exists, Codex CLI is installed.
  2. Well-known config directory exists. Lower-confidence than a file but precedes first-time MCP config. ~/.config/zed/ indicates Zed is installed even before the user touches MCP.
  3. Executable on PATH. which code, which cursor, which claude. Cross-platform via which crate.
  4. Application bundle / install metadata. macOS Launch Services, Windows App Paths registry, Linux .desktop files.
  5. Extension marketplace query. For VS-Code-hosted tools (Cline) we run code --list-extensions and look for the publisher ID.

Flatpak/Snap sandboxing is the trickiest Linux concern: a Flatpak-installed Cursor reads its config from ~/.var/app/com.cursor.cursor/config/Cursor/ rather than ~/.config/Cursor/. Discovery must enumerate Flatpak app IDs and rewrite paths accordingly.

Windows MSIX virtualization is the single most painful discovery scenario. The Claude Desktop file the user sees in %APPDATA%\Claude\ may not be the file the app reads — the real read path is under %LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\. Our discovery layer must detect MSIX install and project to the virtualized path. Stream 1's pain-points page documents this footgun in more detail.

Per-tool detection recipes

Claude Code CLI

Primary: which claude on PATH. Secondary: ~/.claude/ directory existence. The CLI also writes an install marker at ~/.claude/install.json on first run.

Codex CLI

Primary: which codex. Secondary: ~/.codex/ directory.

VS Code

Primary: code --version for executable detection and version. Per-OS app-bundle/registry checks for non-PATH installs.

Cursor

Primary: cursor --version. Secondary: ~/.cursor/ directory. App-bundle ID on macOS.

Zed

Primary: zed --version. Secondary: ~/.config/zed/ directory.

JetBrains family

Primary: enumerate ~/Library/Application Support/JetBrains/<Product><Year.x>/ directories on macOS, ~/.config/JetBrains/ on Linux, %APPDATA%\JetBrains\ on Windows. Secondary: JetBrains Toolbox keeps an installed-IDE inventory at ~/.local/share/JetBrains/Toolbox/state.json we can parse.

Cline

Cline is a VS Code extension. Detection: run code --list-extensions | grep saoudrizwan.claude-dev. If VS Code is not installed, Cline cannot be installed.

Windsurf

Primary: ~/.codeium/windsurf/ directory. Secondary: windsurf --version if on PATH.

Continue

Continue is a VS Code/JetBrains extension. Probe ~/.continue/ (created on first run); cross-check with VS Code extension list (Continue.continue) or JetBrains plugin directory.

Goose

Primary: which goose. Secondary: ~/.config/goose/.

Discovery cadence

Discovery is run once at mcpd startup and again on a file-system watcher signal targeting the parent directories of all known well-known paths. We don't poll. The watcher uses notify-rs on Linux/macOS and ReadDirectoryChangesW on Windows. New tools appearing on disk (e.g. the user installs Cursor mid-session) trigger an opt-in prompt in the CLI/TUI/GUI; we do not auto-project without consent.
