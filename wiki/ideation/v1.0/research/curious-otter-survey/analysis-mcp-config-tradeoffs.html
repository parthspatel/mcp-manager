Tradeoff analysis: which gaps belong to a manager?

Manager vs host — where does ownership live?

The host application owns three things that an external manager cannot trivially take from it:

  1. Tool invocation gating — only the host can show the user an approval dialog before a tool runs, because only the host is the AI conversation surface.
  2. Conversation-scoped state — tool outputs, MCP resource attachments, prompt-as-command discovery (e.g. Claude Code's /mcp__server__prompt) are all host concerns.
  3. OAuth callback handling — the host's process owns the browser launch and the localhost callback HTTP listener.

The manager, by contrast, is well-positioned to own:

  1. The canonical server definition — a single source of truth for "what servers do I have, what do they need".
  2. Process supervision — restart-on-crash, health checks, structured logs, parallel teardown — exactly the things bug reports show are missing (Issues #28211, #30267).
  3. Secrets resolution — at server-launch time, fetching from OS keychain / pass / Credential Manager and injecting into the spawned process, addressing the closed-as-not-planned feature gap.
  4. Transport bridging — running a Streamable HTTP server locally and exposing it as stdio to the host, or vice versa.
  5. Per-host config emission — generating claude_desktop_config.json, ~/.cursor/mcp.json, etc., from the canonical store.

"One config to rule them all" — three interpretations

Interpretation A: Centralized config + projection

One canonical TOML/YAML file the manager owns. The manager writes host-specific configs (mcpServers for Claude Desktop, servers for VS Code, context_servers for Zed, an array for Continue) on every change. Hosts are unaware of the manager. Pro: requires zero host cooperation; works with the messy reality documented on the landscape page. Con: changes made in the host's UI (Cursor's MCP settings dialog, Windsurf's Cascade panel) drift away from the canonical file unless the manager polls and reconciles.

Interpretation B: Manager as supervisor + uniform proxy

The manager runs every MCP server as its own child and exposes a single Streamable HTTP endpoint per server, with auth. Every host configures one URL pointing at the manager. Pro: one place for secrets, lifecycle, logs. Cons: requires every host to support Streamable HTTP (most do — see the transports page); adds local network surface; the manager becomes the trust boundary; some servers expect stdio working-directory semantics that get lost over HTTP.

Interpretation C: Hybrid — supervise stdio, proxy HTTP

Default Interpretation B but allow per-server stdio passthrough where the host insists on stdio. The manager still owns secret resolution and process lifecycle; the host still spawns the listed command but that command is a tiny proxy binary the manager provides. Adds a hop but preserves stdio semantics. Closest to the Inspector's architecture today.

Sync to host-specific files vs replace them

Why "sync" is the conservative default

Hosts ship UIs for adding servers, restarts, and approvals. A user who already has 12 working servers in Claude Desktop will not adopt a manager that forces them to rewire everything. The minimum-viable manager imports existing configs, becomes the single canonical store, and writes host-specific files on save. This is the pattern Smithery has validated at small scale.

Why "replace" can be a v2 promise

Once hosts uniformly support Streamable HTTP with OAuth and DCR, a single manager-hosted endpoint becomes a credible architecture: hosts authenticate, the manager owns the upstream. Today the gating constraint is Claude Desktop's limited remote support (only via curated connectors / DXT) and Goose's transport list omitting Streamable HTTP. Until parity, "replace" is a power-user opt-in.

Read–write hazards

The Windows MSIX bug (Issue #26073) shows a manager that writes to "the documented path" can still write to a file the host never reads. A manager must therefore detect which path the host is actually reading (e.g., probe both the MSIX virtualized path and the canonical APPDATA path), or refuse to write when the install kind is ambiguous.

Problems best left to hosts

Per-tool approval flow

The user-facing "Claude wants to call delete_branch — allow?" dialog is the host's territory. The manager can express policy (allowlist/denylist) but cannot replace the gate.

MCP elicitation dialogs

When a server requests structured input mid-task (Form / URL mode), the host owns the rendering. The manager can log these but cannot satisfy them out-of-band.

Tool discovery from prompts (/mcp__server__prompt)

Slash-command-style discovery is a host UI concern, tied to the conversation surface.

Context-window tool budgeting

Claude Code's tool-search budgeting (ENABLE_TOOL_SEARCH=auto:N) only makes sense inside the LLM client. The manager can declare alwaysLoad hints but the trade-off lives in the host.

Open questions

  • Schema canonicalization. Does the manager invent its own canonical schema (likely a superset of Claude Code's, since Claude Code already covers OAuth and headersHelper), or piggyback on Claude Code's .mcp.json and treat it as the de-facto standard?
  • Conflict resolution. If a user edits Cursor's MCP settings panel after the manager has written ~/.cursor/mcp.json, who wins on next reconcile? Three-way merge is hard for nested JSON.
  • OS keychain abstraction. macOS Keychain, Windows Credential Manager, and Linux Secret Service / pass each have different semantics. The keychain feature request itemized all three but never settled on a unified URI — does the manager?
  • Runtime bundling. DXT bundles a runtime; npx/uvx rely on the host having one. Does the manager ship Node and Python, or assume them present?
  • Telemetry boundary. If the manager proxies servers, it sees every tool call. That is operationally useful (audit, debug) and a privacy concern (especially for enterprise). Default should be off.
