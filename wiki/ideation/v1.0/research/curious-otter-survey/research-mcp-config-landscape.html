Claude Desktop

Config paths and schema

The desktop application reads a single JSON file at:

  • macOS: ~/Library/Application Support/Claude/claude_desktop_config.json
  • Windows: %APPDATA%\Claude\claude_desktop_config.json (but see the MSIX virtualization bug on the pain points page)
  • Linux: Claude Desktop is not officially shipped for Linux.

The schema is the canonical mcpServers object with command, args, and optional env:

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/Desktop"]
    }
  }
}

Transports

Local stdio only for user-configured servers; remote servers arrive via Anthropic's connectors and Desktop Extensions (.mcpb) packaging.

Lifecycle owner

The host. Servers are spawned at app start; only a full app restart picks up config changes.

Notable extensions

Adds developer_settings.json with allowDevTools for Chrome DevTools inspection.

Claude Code (CLI)

Claude Code stores configuration across three scopes — local, project, and user — and is unusual in that the canonical way to add servers is the CLI, not a hand-edited file:

ScopeLoads inSharedStored in
Local (default)Current project onlyNo~/.claude.json
ProjectCurrent project onlyYes (via VCS).mcp.json in project root
UserAll projectsNo~/.claude.json
CLI command examples 
# Stdio server
claude mcp add --transport stdio --env AIRTABLE_API_KEY=YOUR_KEY airtable \
  -- npx -y airtable-mcp-server

# Streamable HTTP server
claude mcp add --transport http notion https://mcp.notion.com/mcp

# Header auth (Bearer)
claude mcp add --transport http secure-api https://api.example.com/mcp \
  --header "Authorization: Bearer your-token"

Transports: stdio, http (the spec's streamable-http — both names are accepted by type), and the deprecated sse. The host owns lifecycle: stdio servers are not auto-reconnected, while HTTP/SSE servers reconnect with exponential backoff (up to five attempts). Environment variable expansion (${VAR}, ${VAR:-default}) is supported in command, args, env, url, and headers.

Cursor

Config paths
  • Global: ~/.cursor/mcp.json
  • Project: .cursor/mcp.json in the repo root (project-level wins on conflict)

Source: Cursor MCP docs.

Schema is mcpServers with an explicit type field (stdio or remote), url, headers, and auth (OAuth) for remote servers, plus envFile for stdio. Variable expansion supports ${env:NAME}, ${userHome}, ${workspaceFolder}, and others.

Transports: stdio, SSE, and Streamable HTTP. Lifecycle: managed by Cursor; full Cursor quit-and-relaunch is required to pick up new servers.

Cline (VS Code extension)

Config paths
  • macOS: ~/Library/Application Support/Code/User/globalStorage/saoudrizwan.claude-dev/settings/cline_mcp_settings.json
  • Linux: ~/.config/Code/User/globalStorage/saoudrizwan.claude-dev/settings/cline_mcp_settings.json
  • Windows: %APPDATA%\Code\User\globalStorage\saoudrizwan.claude-dev\settings\cline_mcp_settings.json

Source: Cline docs.

The schema mirrors Claude Desktop's mcpServers but adds two operationally important fields: disabled (toggle without removing) and autoApprove (list of tools that bypass the per-call approval prompt). Transports: stdio plus remote HTTP/SSE. Lifecycle managed by the extension; the MCP settings panel offers explicit restart and timeout controls.

Continue

Continue accepts both YAML and JSON. Local configuration lives at .continue/mcpServers/ in the workspace (one file per server) and the global config at ~/.continue/config.yaml on macOS/Linux or %USERPROFILE%\.continue\config.yaml on Windows. The published schema places mcpServers as an array (not an object) with a required name per entry — a portability hazard for users copying from Claude Desktop or Cursor.

Continue supports all three transports (stdio, sse, streamable-http) and offers first-class secret syntax ${{ secrets.KEY_NAME }} resolved either against the local environment or Continue's hosted Mission Control. MCP servers are only active in agent mode; this is the only host that gates MCP behind a mode switch.

Zed

Config paths
  • macOS / Linux: ~/.config/zed/settings.json
  • Windows: %APPDATA%\Zed\settings.json
  • Project-local: .zed/settings.json in the repo root

Zed is the outlier on the schema key: it uses context_servers, not mcpServers. Local servers use command/args/env; remote servers use url/headers and trigger Zed's built-in OAuth flow if no header is set. Zed also has a dedicated MCP Server Extensions marketplace that wraps server installations as installable Zed extensions, so the host can also be the package manager.

Windsurf (Cascade)

Single config path on all OSes: ~/.codeium/windsurf/mcp_config.json (must be created by the user; not generated on first launch). Schema is mcpServers with the usual command/args/env for stdio, and serverUrl or url + headers for remote. Variable interpolation supports both ${env:VAR_NAME} and ${file:/path/to/file} (file contents inlined).

Lifecycle owner: Windsurf itself, via the Cascade UI. Windsurf imposes a hard cap of 100 total tools across all configured servers — a hint at the scale of multi-server installations users are reaching.

VS Code (Copilot MCP)

VS Code reads mcp.json from two locations: workspace (.vscode/mcp.json) or the user profile (opened via the MCP: Open User Configuration command). The schema key is "servers" (not mcpServers) — another portability hazard. Fields include type (stdio/http), command, args, url, headers, sandboxEnabled, and inputs for prompting users for secret values at install time.

VS Code's inputs and sandboxEnabled features make it the most security-aware host in the survey; it explicitly warns against hardcoded secrets.

Goose

Goose, built by Block, configures MCP servers as extensions in a YAML file at ~/.config/goose/config.yaml on Linux/macOS. Each entry declares a type of stdio, sse, or builtin; the latter denotes Goose's bundled extensions, which require no external command.

Example Goose YAML 
extensions:
  developer:
    name: Developer
    type: builtin
    enabled: true
  fetch:
    name: Fetch
    type: stdio
    cmd: uvx
    args: ["mcp-server-fetch"]
    enabled: true
    timeout: 30
    envs: {}

mcp-inspector, mcp-cli, uvx/npx-launched

MCP Inspector

Not a host: a developer tool. Spawns a browser UI on port 6274 and a proxy on port 6277. Supports stdio, SSE, and Streamable HTTP; the proxy spawns local stdio processes and bridges to remote endpoints. Has both UI and CLI modes.

Smithery CLI

A registry installer and cross-host manager. Pattern: smithery mcp add <url> --client claude|cursor; it edits the right host config file for you. Closest existing analogue to an MCP Manager, but limited to registry-listed servers.

uvx- and npx-launched servers

Not configuration formats themselves — these are the de facto distribution mechanisms. Most MCP servers are published as PyPI packages run via uvx, or npm packages run via npx -y <pkg>, with the host filling in command/args. Implies the host must have a Node/Python runtime in PATH — a frequent source of failure (see pain points).
