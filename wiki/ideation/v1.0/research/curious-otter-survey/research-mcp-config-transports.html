Transports: stdio vs Streamable HTTP vs SSE

What the MCP spec actually defines, how the three transports compare in adoption, and the operational constraints each one places on a manager process.

What the spec defines

The current Model Context Protocol specification (revision 2025-06-18) defines exactly two standard transports — stdio and Streamable HTTP — and states that clients SHOULD support stdio whenever possible. The earlier HTTP+SSE form from protocol revision 2024-11-05 was deprecated in March 2025 (spec revision 2025-03-26) and is retained only for backwards compatibility.

Recommended stdio

Client launches the server as a subprocess. JSON-RPC messages over stdin/stdout, newline-delimited, logs on stderr.

Recommended Streamable HTTP

Single HTTP endpoint accepting POST and GET. The same endpoint can return plain JSON or open an SSE stream for long-lived operations. Optional Mcp-Session-Id header for stateful sessions.

Deprecated HTTP+SSE

Used dual endpoints (one POST for requests, one GET-SSE for responses). Hostile to load balancers, serverless, and modern HTTP/2/3. Removal targeted mid-2026 deadlines.

stdio in detail

The stdio transport requires very little from the host: spawn a subprocess, write JSON-RPC frames to its stdin, read newline-delimited responses from stdout. The server may write UTF-8 strings to stderr for logging and clients may capture, forward, or ignore these. Crucially, the server MUST NOT write anything to stdout that is not a valid MCP message.

Constraints stdio imposes

  • One process per server, per client. Two hosts running the same stdio server today each spawn an independent child process; there is no shared session.
  • No persistent state across sessions. Process exit drops any in-memory caches.
  • Working directory is undefined. The MCP spec maintainers explicitly warn that clients may launch a server with cwd at /; configurations must use absolute paths.
  • Env vars are not inherited fully. Only a platform-dependent subset (typically USER, HOME, PATH) is passed unless the host explicitly supplies env.
  • stderr is not captured for HTTP servers. For Streamable HTTP servers, clients cannot read stderr — debugging must use notifications/message log notifications or external aggregation.

Streamable HTTP in detail

Streamable HTTP is a single-endpoint transport. The client sends each JSON-RPC message as an HTTP POST with Accept: application/json, text/event-stream. The server then chooses to either return one JSON object or upgrade the response to an SSE stream for streaming notifications and a final response. The client may also open a separate GET-SSE stream to receive server-initiated messages without sending a request first.

Session management

A server MAY assign a session ID via the Mcp-Session-Id response header on the InitializeResult. Subsequent requests MUST then include that header. The server MAY terminate the session at any time, responding 404 to subsequent requests; the client SHOULD send an HTTP DELETE on shutdown.

Security requirements

The spec explicitly requires Streamable HTTP servers to validate the Origin header on every request (preventing DNS rebinding), to bind only to 127.0.0.1 for local use, and to implement authentication.

Resumability

Servers MAY attach SSE id values to events; clients SHOULD send Last-Event-ID on reconnect to allow replay of missed events from the same stream.

HTTP+SSE — the deprecated form

The original SSE transport had two endpoints — one POST endpoint for client requests, one GET endpoint for the SSE stream — which created coordination state that was error-prone, scaled poorly behind load balancers and serverless platforms, and could not recover from mid-stream disconnects. The deprecation deadlines were communicated for mid-2026, with Streamable HTTP support landing in the TypeScript SDK at v1.10.0 (April 2025).

Auth model per transport

stdio

Authentication is the server's responsibility, typically through environment variables for API keys. The transport itself is unauthenticated — anything that can spawn the process can connect to it. Isolation comes from the OS user account boundary.

Streamable HTTP — header-based

The simplest model: Authorization: Bearer ... or custom headers. Claude Code supports headersHelper to compute headers dynamically on each connection (Kerberos, short-lived tokens) — running an arbitrary shell command whose stdout JSON merges into request headers.

Streamable HTTP — OAuth 2.0

Discovery starts at /.well-known/oauth-protected-resource (RFC 9728), falling back to /.well-known/oauth-authorization-server (RFC 8414). Claude Code supports DCR (Dynamic Client Registration), CIMD, and pre-registered client IDs with --callback-port. Tokens are stored in the OS keychain (macOS) or a credentials file.

Scope pinning

Claude Code's oauth.scopes string lets administrators restrict tokens to a security-approved subset of advertised scopes. offline_access is appended automatically for refresh support.
