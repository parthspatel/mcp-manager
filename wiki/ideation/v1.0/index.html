Rust MCP Manager — v1.0 Ideation

Six independent, evidence-grounded design explorations for a Rust-based MCP Manager comprising a core library/daemon plus CLI, TUI, and GUI clients — conceptually "Docker for MCP servers". Each stream produces neutral research, tradeoff analysis, an interactive ranking matrix, and a recommendation with linked rationale. Streams run in parallel with no shared memory; convergences below emerged independently.

266 citations 52 HTML pages 9 ranking matrices All 6 streams complete

Addendum 2026-05-24 — Stream 6 added by user request

After the initial 5 streams completed, the user flagged a gap: the design covered how to read MCP server configs from existing hosts (Stream 1) but not how to project the canonical MCP Manager state back out to the many tools that consume MCP servers. Stream 6 (clever-fox-bridge) closed that gap: it catalogues 12 MCP-consuming tools, settles on managed-block as the default sync mode (Ansible-style fenced regions), picks TOML as the custom-toolchain spec format, and surfaces 6 scoping questions for the orchestrator.

Headline finding: schema drift means even bundled Tier-1 tool support has to be expressed as data-driven manifests, not hardcoded Rust — every Tier-1 tool ships schema changes every few months.

Convergent v1.0 design

Decisions where two or more streams arrived at compatible conclusions independently, or where one stream had decisive evidence. These should be treated as the working baseline for v1.0.

Daemon model

Long-lived background process is required. Recommended pattern: podman/conmon-style per-server supervisor rather than a single central daemon (dockerd).

Converged from S1 (lifecycle gap), S3 (library-only unfit), S4 (assumed long-lived).

Async runtime

Locked to tokio. The official rmcp Rust MCP SDK is tokio-native; using anything else would mean re-implementing the SDK or running dual incompatible runtimes.

Source: S3 · Constraint type: upstream dependency.

CLI

clap with derive macros. Consensus pick across the Rust ecosystem (Cargo, ripgrep, uv).

Source: S5.

TUI

ratatui + crossterm. Consensus pick (bottom, gitui, yazi, atuin, trippy).

Source: S5.

GUI

Tauri 2 with a Leptos (Rust-WASM) frontend. Pure-native Rust GUIs largely failed a basic accessibility + IME baseline; Tauri inherits system WebView a11y "for free".

Source: S5. Frontend choice still re-openable — see open question.

Client ↔ daemon wire

JSON-RPC 2.0 over Unix domain socket / Windows named pipe. JSON-RPC affinity is decisive — MCP itself uses JSON-RPC, so the daemon shares its parser/encoder between client-facing and MCP-server-facing code.

Auxiliary HTTP/SSE bridge is mandatory in v1.0 because the Tauri GUI's WebView cannot dial UDS.

Source: S4 · Constraint resolved by S5's Tauri choice.

Auth model

Filesystem-mode + peer-credentials check on UDS (SO_PEERCRED / LOCAL_PEERCRED) and restrictive SDDL on named pipes — kernel-enforced single-user auth, zero application-layer token logic for the local IPC path. Bearer token only for the HTTP/SSE bridge.

Source: S4.

Isolation

Two-tier: devenv (Nix) + OS sandbox primary (bubblewrap / sandbox-exec / AppContainer); Docker MCP Toolkit / Podman / pinned uvx-npx as escape hatch for non-Nix users.

Source: S2 · Forced by CVE-2025-6514 + supply-chain evidence.

Toolchain sync mode

Managed-block by default — Ansible-style fenced regions with begin/end markers. Pure-JSON tools degrade to sentinel-key fencing (Cursor) or sibling-file projection. Only strategy that simultaneously preserves hand-edits, stays idempotent, surfaces conflicts honestly, and works across TOML/YAML/JSONC/XML.

Behavioral asymmetry: additive-with-consent, subtractive-automatic. Adding a server prompts in N places; removing happens silently across N places. This rules out watch+reconcile as a default.

Source: S6.

Custom-toolchain spec

Declarative TOML (toolchain.toml) — the escape hatch for tools MCP Manager doesn't ship native support for. Comments are first-class, the Rust ecosystem already uses TOML (Cargo, mise, proto), and mcpd's own config is TOML — single-parser strategy minimises format surface.

Bundled tools also ship as TOML manifests, not hardcoded — schema drift in editors makes data-driven manifests the only sustainable option.

Source: S6.

Tool support tiers

Tier 1 (auto-detect + native projection): Claude Code CLI, Codex CLI, VS Code, Cursor, Zed, JetBrains family (IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand).

Tier 2 (opt-in projection): Windsurf, Continue, Cline, Goose, LibreChat, Claude Desktop.

Source: S6.

Open questions for v1.0 scoping

Four decisions remain genuinely open. Each is scoped, not blocking — but should be answered before lock-down.

Windows default isolation strategy

S2 tentatively recommends Docker MCP Toolkit on Windows for cross-OS uniformity, but it requires Docker Desktop (license + Hyper-V/WSL2). Alternatives: AppContainer-direct with pinned uvx/npx (native, but per-server capability authoring is heavy and not every MCP server has been tested), or WSL2-with-devenv (most reproducible, but adds a second OS into onboarding).

Decision blocks: the Windows installer flow.

Owner: stoic-badger-sandbox

Auto-spawn daemon vs hard-fail with install pointer

Should mcp start <server> silently auto-spawn a daemon when none exists (podman-like, friendliest UX), or hard-fail with a friendly pointer to mcp daemon --install-launchd|--install-systemd-user (more transparent about what's appearing on the user's machine)?

Decision blocks: first-run UX, OS-permission prompt experience, and CI/headless behavior.

Owner: steady-bear-foundation

Tauri frontend: Leptos (Rust-WASM) vs TypeScript

S5 recommends Leptos for a mono-lingual codebase and shared types from mcp-client, but a TS frontend remains viable if the project plans to hire TS/React engineers. Re-decidable at scaffold time, not at design time.

Decision blocks: GUI hiring profile, frontend build pipeline.

Owner: nimble-raven-toolkit

Daemon ambition: how much supervision in v1.0?

S1 raised this; S3 + S4 effectively answered "yes, real supervision." But the surface area of supervision in v1.0 is still open: just spawn/stop, or also restart-on-crash, OOM handling, resource limits, audit logs, telemetry export? Each level adds scope.

Decision blocks: v1.0 feature scope, beta cut date.

Owner: curious-otter-survey

Canonical scope: per-user vs per-project as the default new — S6

Editors split on this: VSCode and Cursor encourage per-project .vscode/mcp.json and .cursor/mcp.json respectively; Claude Code, Zed, and JetBrains lean per-user. MCP Manager has to pick one as the canonical default and translate to the other.

Decision blocks: the mcpm init flow, the team-onboarding story (committing canonical into a repo vs not), and whether .mcp-manager.lock ships per-project or per-user.

Owner: clever-fox-bridge

Linux sandbox-root enumeration depth (Flatpak / Snap) new — S6

Flatpak-installed VSCode lives at ~/.var/app/com.visualstudio.code/config/Code/User/settings.json; Snap puts it elsewhere again. Aggressive enumeration finds more tools but slows mcpm doctor and increases false positives. Conservative enumeration misses installs.

Decision blocks: discovery UX on Linux desktops (a sizeable fraction of the target user base).

Owner: clever-fox-bridge

Wrapper-command secrets fallback when mcpd isn't running new — S6

If a user launches their editor without mcpd running, projected configs that reference live secrets fail. S6 proposes mcpm exec --secrets-from as a wrapper-command shim so the editor spawns the server through a transient mcpd-lite. This trades a small "Where's that mcpm exec command from?" cognitive cost for not requiring users to always have mcpd running. Accept, reject, or alternate design?

Owner: clever-fox-bridge

Curated community toolchain registry (Homebrew-taps style) new — S6

The TOML escape hatch lets anyone teach mcpm about a new tool. Should we host a curated registry of community-contributed manifests (like Homebrew taps or mise plugins) so users can mcpm toolchain add cline-fork and pull a vetted manifest? Adds maintenance burden and a moderation policy; without it, ecosystem-discoverability is poor.

Owner: clever-fox-bridge

Sidecar vs centralised lock file new — S6

To detect drift and conflicts, the projector needs a lock file recording the last-known hash of each managed region. Sidecar (.mcp-manager.lock next to each tool's config) keeps the data local; centralised (~/.config/mcp-manager/projection.lock) is easier to audit but couples per-project work to a per-user file.

Owner: clever-fox-bridge

JetBrains XML projection in v1.0 or defer? new — S6

JetBrains IDEs store MCP config in XML inside the IDE config dir — fundamentally different parser, fundamentally riskier projection (XML schemas drift via IDE-side merge semantics that the user can't see). S6 puts the JetBrains family in Tier 1 because of user demand, but flags XML projection as the highest-effort tool in the catalog. Ship in v1.0 or defer to v1.1?

Owner: clever-fox-bridge

How to read each stream

Every stream follows the same four-stage flow. You can sample at any depth.

  1. research-*.html — raw factual landscape, every claim cited.
  2. analysis-*-tradeoffs.html — interpretation and tradeoffs, still neutral.
  3. matrix-*-ranking.html — interactive ranking matrix; drag weight sliders to re-rank live, click [n] evidence pills to jump to citations.
  4. recommendation-*-summary.html — the stream's recommendation with rationale linked to evidence pages and citations. The only place opinions appear.

Citations are footnotes at the bottom of each page; hover or focus any [n] to preview the source. Theme toggle in the top-right cycles light/dark/auto.
