Rust MCP Manager — v1.0 Ideation

Six independent, evidence-grounded design explorations for a Rust-based MCP Manager comprising a core library/daemon plus CLI, TUI, and GUI clients — conceptually "Docker for MCP servers". Each stream produces neutral research, tradeoff analysis, an interactive ranking matrix, and a recommendation with linked rationale. Streams run in parallel with no shared memory; convergences below emerged independently.

Addendum 2026-05-24 — Stream 6 added by user request

After the initial 5 streams completed, the user flagged a gap: the design covered how to read MCP server configs from existing hosts (Stream 1) but not how to project the canonical MCP Manager state back out to the many tools that consume MCP servers. Stream 6 (clever-fox-bridge) closed that gap: it catalogues 12 MCP-consuming tools, settles on managed-block as the default sync mode (Ansible-style fenced regions), picks TOML as the custom-toolchain spec format, and surfaces 6 scoping questions for the orchestrator.

Headline finding: schema drift means even bundled Tier-1 tool support has to be expressed as data-driven manifests, not hardcoded Rust — every Tier-1 tool ships schema changes every few months.

v1.0 lockdown — 2026-05-24 decisions

The product owner reviewed all 6 streams and resolved the following decisions. These are now committed for v1.0 and supersede any contradicting language in the original stream pages (kept as authored snapshots).

  1. Drop Windows. v1.0 ships macOS + Linux only. Removes named-pipes / SDDL / AppContainer complexity from S4 and S2. Windows installer story deferred indefinitely.
  2. Auto-spawn the daemon. mcpm exec auto-spawns mcpd on first call (~200ms one-time). On first GUI launch, if the OS has a service manager (systemd-user on Linux, launchd on macOS), prompt the user once: "register mcpd as a background service?" — opt-in, not default. Obsoletes the proposed "mcpd-lite" from S6 entirely.
  3. Toolchain scope is user-configurable per registered project. Both per-user and per-project canonical scopes supported; the user picks when registering a project. Lockfile location follows the scope: per-user → centralized at ~/.config/mcp-manager/projection.lock; per-project → sidecar at the project root (.mcp-manager.lock). Clients can also initialize/update via mcpm CLI to register a project + toolchain set.
  4. JetBrains XML projection ships in v1.0. Despite the higher implementation risk flagged by S6, JetBrains IDE support (IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand) is non-negotiable for v1.0.
  5. Curated community toolchain registry deferred to v1.1. See future features (v1.1).
  6. GUI stack: Actix-Web + Askama, served from inside mcpd. All 3 UI research agents reported back; the shootout ranks Actix at 8.57 / Dioxus-desktop at 8.13 / Tauri+Leptos at 6.71 on a 13-criterion UX-weighted matrix. Localhost SSR web app (Pi-hole / Sonarr pattern) with tray-icon helper + PWA manifest for "feels like an app". S5's earlier Tauri+Leptos recommendation is superseded.
  7. Daemon supervision surface is broad, not narrow. mcpd is a real process supervisor, not just a launcher: restart-on-crash with jittered exponential backoff + max-attempts within a sliding window, OOM detection (cgroupv2 on Linux; jetsam-inferred on macOS), append-only audit log of every state change, and tail-API access to three log streams (mcpd itself, each MCP server's stdout/stderr, and the audit log). See the "Daemon supervision surface" convergent card below for the full enumeration.

Convergent v1.0 design

Decisions where two or more streams arrived at compatible conclusions independently, or where one stream had decisive evidence. These should be treated as the working baseline for v1.0.

Daemon model

Long-lived background process is required. Recommended pattern: podman/conmon-style per-server supervisor rather than a single central daemon (dockerd).

Converged from S1 (lifecycle gap), S3 (library-only unfit), S4 (assumed long-lived).

Async runtime

Locked to tokio. The official rmcp Rust MCP SDK is tokio-native; using anything else would mean re-implementing the SDK or running dual incompatible runtimes.

Source: S3 · Constraint type: upstream dependency.

CLI

clap with derive macros. Consensus pick across the Rust ecosystem (Cargo, ripgrep, uv).

Source: S5.

TUI

ratatui + crossterm. Consensus pick (bottom, gitui, yazi, atuin, trippy).

Source: S5.

GUI

Actix-Web + Askama, served from inside mcpd on localhost:NNNN. Server-rendered Rust HTML + SSE for live updates + HTMX for interactivity. Zero IPC, single binary, single auth surface. The user visits a URL in their existing browser — Pi-hole / Sonarr / Jellyfin pattern. A small mcpd-tray helper + PWA manifest restore most of the "feels like an app" UX.

Free wins: browser-grade accessibility (the most accessible runtime ever shipped), 60ms first paint (vs. 350–450ms for Tauri options), opt-in --bind 0.0.0.0 unlocks LAN/mobile management on day one.

Source: ui-shootout (3-agent comparison, 2026-05-24). Supersedes S5's earlier Tauri+Leptos pick.

Client ↔ daemon wire

JSON-RPC 2.0 over Unix domain socket / Windows named pipe. JSON-RPC affinity is decisive — MCP itself uses JSON-RPC, so the daemon shares its parser/encoder between client-facing and MCP-server-facing code.

Auxiliary HTTP/SSE bridge is mandatory in v1.0 because the Tauri GUI's WebView cannot dial UDS.

Source: S4 · Constraint resolved by S5's Tauri choice.

Auth model

Filesystem-mode + peer-credentials check on UDS (SO_PEERCRED / LOCAL_PEERCRED) and restrictive SDDL on named pipes — kernel-enforced single-user auth, zero application-layer token logic for the local IPC path. Bearer token only for the HTTP/SSE bridge.

Source: S4.

Isolation

Two-tier: devenv (Nix) + OS sandbox primary (bubblewrap / sandbox-exec / AppContainer); Docker MCP Toolkit / Podman / pinned uvx-npx as escape hatch for non-Nix users.

Source: S2 · Forced by CVE-2025-6514 + supply-chain evidence.

Toolchain sync mode

Managed-block by default — Ansible-style fenced regions with begin/end markers. Pure-JSON tools degrade to sentinel-key fencing (Cursor) or sibling-file projection. Only strategy that simultaneously preserves hand-edits, stays idempotent, surfaces conflicts honestly, and works across TOML/YAML/JSONC/XML.

Behavioral asymmetry: additive-with-consent, subtractive-automatic. Adding a server prompts in N places; removing happens silently across N places. This rules out watch+reconcile as a default.

Source: S6.

Custom-toolchain spec

Declarative TOML (toolchain.toml) — the escape hatch for tools MCP Manager doesn't ship native support for. Comments are first-class, the Rust ecosystem already uses TOML (Cargo, mise, proto), and mcpd's own config is TOML — single-parser strategy minimises format surface.

Bundled tools also ship as TOML manifests, not hardcoded — schema drift in editors makes data-driven manifests the only sustainable option.

Source: S6.

Tool support tiers

Tier 1 (auto-detect + native projection): Claude Code CLI, Codex CLI, VS Code, Cursor, Zed, JetBrains family (IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand). JetBrains XML projection ships in v1.0 (user lockdown, 2026-05-24).

Tier 2 (opt-in projection): Windsurf, Continue, Cline, Goose, LibreChat, Claude Desktop.

Source: S6 + v1.0 lockdown.

Daemon UX: auto-spawn

The CLI mcpm exec wrapper auto-spawns mcpd if it isn't running (~200ms one-time, then a UDS connection). Subsequent clients (Zed, Claude Code, Cursor, …) get the already-running daemon for free. The proposed "mcpd-lite" alternative is obsolete.

On first GUI launch only, the GUI detects the OS's service manager (systemd-user on Linux, launchd on macOS) and prompts the user once: "register mcpd as a background service?". Opt-in, not default.

Source: S3 + v1.0 lockdown.

Toolchain scope: user-configurable per project

When the user registers a project with mcpm, they pick whether the canonical scope is per-user (one MCP toolset for all projects) or per-project (this project has its own toolset). Both are first-class. Default is per-user; opt-in to per-project at mcpm project init time.

Lockfile follows scope: per-user → ~/.config/mcp-manager/projection.lock; per-project → .mcp-manager.lock at the project root.

Source: S6 + v1.0 lockdown.

Platforms: macOS + Linux only

v1.0 ships macOS + Linux. Windows support is not in v1.0. Removes named-pipes / SDDL / AppContainer / Docker-Desktop-on-Windows complexity from the design space. UDS is the only IPC primitive; sandbox runtime is the macOS Sandbox + bubblewrap on Linux; service-manager integration is launchd + systemd-user.

Source: v1.0 lockdown (2026-05-24).

Daemon supervision surface (full v1.0 scope)

mcpd is a real process supervisor for the MCP servers under its management, not a thin launcher. Locked v1.0 capabilities:

  1. Start / stop — primitive. Triggered by client requests over JSON-RPC.
  2. Restart on crash, with jittered exponential backoff and max-attempts:
    • Backoff schedule: delay = min(base × 2^attempt × (1 + rand(0, 0.3)), cap). Tentative: base=1s, cap=60s. The 30% jitter prevents thundering-herd when many servers all crash together (post-sleep, post-network-flap).
    • Max-attempts within a sliding window: e.g. 5 restarts in 600s. Exceeding the budget marks the server failed and stops retrying — prevents infinite restart loops for a server that crashes immediately on every boot. User must explicitly mcpm restart <server> to clear failed state.
    • Modeled on systemd's Restart=on-failure + StartLimitBurst + StartLimitIntervalSec semantics.
  3. OOM handling:
    • Linux: per-server memory limits via cgroupv2 (memory.max); OOM kills observed deterministically via memory.events. Optional memory.high for soft throttling. Treated as a crash for restart purposes; audit-logged with the OOM cause.
    • macOS: weaker observability — no native OOM events API. v1.0 will infer OOM from SIGKILL with no signal info + recent memory pressure (read via host_processor_info). Per-server limits via posix_rlimit RLIMIT_AS if requested; otherwise jetsam decides. Audit log marks the cause "OOM (inferred)".
  4. Audit log — append-only JSONL of every state change: {ts, actor, event, server, details}. Events: server.spawn, server.stop, server.crash, server.oom, server.failed, config.change, secret.read, secret.write, projection.write. Default rotation: daily files, 90 days retained, located at $XDG_STATE_HOME/mcpd/audit/ (Linux) or ~/Library/Logs/mcpd/audit/ (macOS).
  5. Tail-API access to three log streams:
    • mcpd itself — structured Rust logs via tracing + a ring buffer (e.g. 10MB in memory + on-disk rotation).
    • Each MCP server — stdout + stderr captured by the supervisor through pipes; per-server ring buffer (e.g. 4MB in memory).
    • Audit log — same JSONL file, tailable live as new entries land.
    All three exposed via:
    • CLI: mcpm logs --follow [<server> | --daemon | --audit], with --since, --lines, --grep filters.
    • GUI (Actix): three SSE endpoints — /logs/daemon/stream, /logs/server/<id>/stream, /logs/audit/stream. The browser tab can show all three side-by-side in real time (this is the SSE+HTMX strength that won the GUI shootout).
    • Wire: JSON-RPC logs.tail method over UDS, returns a streaming response.

Source: user directive #3 (2026-05-24). Implementation owner: steady-bear-foundation.

Linux sandbox-root enumeration depth — tentatively "medium"

For each Tier-1 tool, hardcode its Snap package name and Flatpak app ID, check those well-known paths in addition to the native ~/.config/<tool>/ location. ~5–10 stats per tool, no filesystem walk. The list of Snap/Flatpak IDs is part of each tool's TOML manifest (per S6's data-driven-manifests decision). User confirmed this is the right tier of aggressiveness; remaining open detail is the per-tool manifest population.

How to read each stream

Every stream follows the same four-stage flow. You can sample at any depth.

  1. research-*.html — raw factual landscape, every claim cited.
  2. analysis-*-tradeoffs.html — interpretation and tradeoffs, still neutral.
  3. matrix-*-ranking.html — interactive ranking matrix; drag weight sliders to re-rank live, click [n] evidence pills to jump to citations.
  4. recommendation-*-summary.html — the stream's recommendation with rationale linked to evidence pages and citations. The only place opinions appear.

Citations are footnotes at the bottom of each page; hover or focus any [n] to preview the source. Theme toggle in the top-right cycles light/dark/auto.
