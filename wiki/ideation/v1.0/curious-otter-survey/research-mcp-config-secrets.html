Secrets and credentials: how they travel today

A factual look at how each host hands API keys to MCP servers, where those secrets actually live on disk, and the gaps the ecosystem hasn't yet closed.

The default: plaintext JSON

Across every major host, the common path is the same: a long-lived API key is pasted into a JSON or YAML config file in the user's home directory, in plaintext, with no encryption at rest. This is what the canonical Claude Desktop tutorial demonstrates with BRAVE_API_KEY in env. The community has flagged this as a systemic problem.

The risks documented in user-facing writeups:

  • Direct agent access — the same AI assistant that reads the config to start the server can read the config's secrets into its own context.
  • Prompt injection exfiltration — malicious websites or compromised packages can instruct the agent to print credentials from the file.
  • Filesystem exposure — any process running as the user can read the file path.
  • VCS leakage — project-scoped configs (Claude Code's .mcp.json, VS Code's .vscode/mcp.json, .cursor/mcp.json) end up committed when developers forget to gitignore.
  • Process listing exposure — env vars passed to children show up in ps aux, shell history captures export commands, no audit trail.

Keychain integration: present and absent

Present Claude Desktop DXT bundles

The .mcpb manifest's user_config field declares required inputs. Fields marked "sensitive": true are stored in the OS keychain (Keychain on macOS, Credential Manager on Windows) and injected via template literals like ${user_config.api_key}. This applies only to servers installed as Desktop Extensions, not to those added by hand-editing claude_desktop_config.json.

Present VS Code inputs

The inputs array supports type: "promptString" with password: true. VS Code stores the value in its workspace secret store and resolves ${input:id} at runtime — keeping the literal value out of the JSON file.

Present (partial) Claude Code OAuth

For remote MCP servers using OAuth, Claude Code stores the access token in the macOS Keychain or a platform credentials file — never in ~/.claude.json. Pre-configured client secrets passed via --client-secret are also keychain-stored. This applies only to OAuth tokens; raw API keys in env still live in plaintext.

Absent all other JSON configs

Claude Desktop (manual), Cursor, Cline, Continue (when not using Mission Control), Zed, Windsurf, and Goose all currently store API keys as plaintext in their config files. The Claude Code keychain feature request (Issue #15961) was filed and closed as "not planned".

Env-var leakage to child processes

For stdio servers, the standard pattern is to pass secrets in the env object of the config — which the host then sets in the spawned subprocess's environment. Consequences:

  • Secrets appear in ps -E / ps aux output on systems that show env vars.
  • Any child process forked from the MCP server inherits the same secrets — fan-out is uncontrolled.
  • The MCP server's own code can echo $API_KEY or printenv; with agent control, this is a single tool call.
  • For Streamable HTTP, the equivalent risk is having the bearer token live in the JSON file rather than a keychain-fetched header.

Rotation, revocation, audit

Rotation

No host surveyed offers a built-in "rotate this key" flow. Users must manually find every config file that holds the key, replace it, and restart. The complaint is enumerated in the keychain feature request: "Manual rotation friction — difficult to rotate keys without intervention."

Revocation

OAuth tokens can be revoked via the upstream provider; static API keys can only be invalidated server-side. There is no client-side revocation API in any host config schema.

Audit

No audit trail of which agent invoked which credentialed tool at what time. The transcript is the closest proxy; it is per-session and not centralized.

Workarounds in the wild

macOS Keychain via shell wrapper (Claude Desktop)

A documented community pattern is to set the command to /bin/sh and use an -c string that fetches the secret from Keychain at startup:

{
  "mcpServers": {
    "cloudflare": {
      "command": "/bin/sh",
      "args": [
        "-c",
        "CLOUDFLARE_API_TOKEN=$(security find-generic-password -a cloudflare -s api-token -w) exec node server.js"
      ]
    }
  }
}

Tradeoffs: portable to any secrets manager with a CLI (1Password, Bitwarden, AWS Secrets Manager), but adds roughly 30 ms of startup latency per server, and the secret still ends up in the child process's environment.

Proposed keychain:// URI scheme (Issue #15961, closed)

The feature request proposed first-class support for credential URIs resolved at server-spawn time:

{
  "mcp_servers": {
    "database": {
      "command": "db-mcp-server",
      "env": {
        "API_KEY": "keychain://service_name"   // macOS
      }
    },
    "analytics": {
      "env": { "TOKEN": "credential://target_name" }  // Windows
    },
    "reporting": {
      "env": { "SECRET": "pass://team/reporting" }    // Linux pass
    }
  }
}

Closed as "not planned" in the Claude Code repo. The need is real but the implementation venue has not been decided.

Smithery --config flag

Smithery CLI accepts a JSON config blob on the command line and writes it into the chosen client's config file. Avoids hand-editing but still ends in plaintext storage.
