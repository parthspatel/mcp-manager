Install friction

PATH inheritance failures on macOS — npx not found

The most-reported friction on macOS is that Claude Desktop (and other Electron-based hosts) does not inherit the user's shell PATH. Tools installed via Homebrew "keg-only" packages, NVM, or non-standard prefixes are invisible to the host even when which npx works in Terminal. The community remediation is to symlink the binary into /opt/homebrew/bin or /usr/local/bin, or to set PATH explicitly in each server's env block.

Windows MSIX virtualization — Edit Config opens the wrong file (Issue #26073)

On Windows MSIX installs of Claude Desktop, the in-app "Edit Config" button opens %APPDATA%\Claude\claude_desktop_config.json, but the application itself reads from the virtualized MSIX path %LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json. MCP servers fail silently with no error and no logs at the expected location. Users can lose hours before realizing the host is reading a different file than the one they're editing.

Developer Mode requirement (discussion #50)

Windows beginners hitting Claude Desktop reported the MCP "wrench" icon never appearing because Developer Mode was not enabled — a prerequisite that was not surfaced clearly in earlier docs. Chocolatey installations were also reported to create dependency conflicts that required reinstalling Node via winget.

uvx / npx-only distribution

The vast majority of community MCP servers ship as PyPI or npm packages run via uvx or npx -y. A user without Python or Node toolchains installed cannot run any of them. Anthropic's DXT bundles directly address this by packaging the runtime inside the bundle.

Lifecycle and supervision

Claude Desktop crashes with 2+ MCP servers (Issue #28211)

v1.1.4088 entered a crash-restart loop whenever two or more MCP servers were configured. Root cause: a Winston logger called util.inspect on an object with an undefined property descriptor, throwing on every startup. The only workaround was to keep exactly one server configured. Closed as "not planned" / invalid for the Claude Code repo, but the symptom is real and recurrent across versions.

Slow shutdown with multiple stdio servers (Issue #30267)

On Windows, Claude Desktop's beforeQuit phase synchronously calls mcp-shutdown, terminating each stdio child process sequentially. With multiple Node/Python child processes, quit can take 10+ seconds. This is a direct consequence of stdio being one-process-per-server with no parallel teardown in the host's lifecycle code.

Stdio servers are not auto-restarted

Claude Code documents that "stdio servers are local processes and are not reconnected automatically." HTTP and SSE servers get up-to-five-attempts exponential backoff, but a crashed stdio server stays dead until the user manually restarts the host or invokes /mcp.

Config edits require full restart

"Configuration changes: Restart the MCP client. Server code changes: Restart the client (for Claude Desktop, fully quit and reopen; closing the window is not enough)." The lack of hot reload is documented as expected behavior.

Debuggability

Logs are deep in the filesystem and per-host

Claude Desktop logs to ~/Library/Logs/Claude/mcp*.log on macOS or %APPDATA%\Claude\logs on Windows. The official debugging guide tells users to tail -F these files. Each host has its own log location with no shared schema.

stderr is the only structured channel — and not for HTTP

"All messages logged to stderr will be captured by the host application automatically… local MCP servers should not log messages to stdout, as this will interfere with protocol operation." For Streamable HTTP servers, stderr is not captured by the client at all — developers must use notifications/message log notifications or their own aggregation.

"Server disconnected" without distinction between never-started and crashed

The Claude client surfaces the same "MCP server disconnected" error whether the subprocess failed to spawn (ENOENT) or crashed after starting. Debuggers must consult per-server stderr logs to differentiate.

MCP Inspector is the recommended first stop

The official debugging guide names the MCP Inspector as the first tool to reach for. The Inspector spawns a web UI on port 6274 and a proxy on port 6277, supporting all three transports. The need for an external tool to debug is a signal in itself — there is no host-native equivalent.

Isolation and sandboxing

Only VS Code has a config-level sandbox flag

VS Code's sandboxEnabled: true on stdio servers is the only sandbox flag in any host schema surveyed. Other hosts inherit the user's full file and network access for every spawned server.

DNS rebinding warning in spec but enforcement varies

The MCP spec MUSTs Origin header validation for Streamable HTTP and SHOULDs localhost-only binding. Whether each host validates this on the client side or trusts the server to do so is opaque from outside.

Secrets (cross-link)

See the secrets page for the full enumeration. The hot summary of community complaints:

  • Plaintext API keys in ~/Library/Application Support/Claude/claude_desktop_config.json — readable by any process running as your user.
  • Keychain feature request closed as not planned despite 6+ months of community asks.
  • Env-var leakage into spawned children and into ps listings.

Multi-host duplication

Adding one server to three hosts means three edits in three different formats

A developer running Claude Desktop, Cursor, and Cline simultaneously must currently edit three files in three different locations to add the GitHub MCP server. Claude Desktop and Cursor share the mcpServers schema, easing copy-paste; Cline keeps the same schema but adds disabled/autoApprove; Continue requires an array instead of an object; Zed wants context_servers; VS Code wants servers.

Smithery exists because of this

Smithery's CLI explicitly markets itself as client-agnostic: smithery mcp add <url> --client claude|cursor. It edits the right host config file for the chosen client. This is a partial-solution: it covers registry-listed servers and a subset of clients.

Claude Code includes add-from-claude-desktop as a one-shot importer

The fact that Claude Code ships claude mcp add-from-claude-desktop (macOS + WSL only) confirms that even within a single vendor's product family, config has to be migrated rather than shared.

Schema portability hazards

Container shape (object vs array)

Continue uses an array for mcpServers; everyone else uses an object. Copying an object schema into a Continue YAML file silently breaks.

Top-level key

Zed (context_servers), VS Code (servers), and Goose (extensions) each use a different top-level key. Mass copy-paste is impossible.

Variable expansion syntax

Claude Code ${VAR} vs Cursor ${env:VAR} vs Continue ${{ secrets.X }} vs Windsurf ${file:PATH}. A config with secrets that worked in Cursor will not work as-pasted in Claude Desktop.

JSON pitfalls

Trailing commas, missing brackets, and lack of validation across all hosts means "the entire config can fail silently." Manual JSON editing remains the dominant install method.
