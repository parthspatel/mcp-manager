v1.0 / curious-otter-survey / recommendation

Stream 1 recommendation

What this stream concludes the v1.0 Rust MCP Manager should solve, ranked by impact, with rationale linked to evidence and explicit uncertainty calls.

Primary recommendation

v1.0 should ship as a canonical config store + projector (Interpretation A from the tradeoff page), with secrets resolved through OS-native credential stores and host-config files re-emitted on every change. Defer the "manager-as-uniform-proxy" architecture (Interpretation B/C) to v2 — it depends on transport parity that not every host has reached yet.

Concretely: one TOML/YAML source of truth, three behaviors — import (read existing host configs into the canonical store), emit (write per-host JSON / YAML on save), supervise (run a small daemon that resolves secrets and tracks server health out-of-band even when the host is closed).

Ranked gaps the manager should fill in v1.0

  1. Secrets out of plaintext (highest impact)

    The single most-cited pain in the corpus we surveyed. Every host except VS Code (inputs) and Claude Desktop's .mcpb bundles forces plaintext keys into JSON files in the user's home directory; the keychain feature request was closed as "not planned". A manager that injects keychain-stored secrets at server-spawn time (via the established /bin/sh -c "$(security find-generic-password ...)" wrapper pattern, generalized across macOS / Windows / Linux) makes a measurable improvement that no host has shipped.

    Evidence: secrets research, pain points. Citations: .

  2. One canonical schema with host-aware emission

    Six top-level keys (mcpServers, servers, context_servers, extensions, …), two container shapes (object vs array), four expansion syntaxes, and ten different file paths is what users juggle today. The manager owns one TOML/YAML file and writes correct host-shaped JSON/YAML on save. Smithery has validated this pattern for the registry-install slice; the manager generalizes it.

    Evidence: landscape, schema. Citations: .

  3. Real process supervision (restart, parallel teardown, health)

    Stdio servers are not auto-restarted by Claude Code; multi-server quit takes 10+ seconds on Windows because teardown is sequential; Claude Desktop has shipped crash-restart loops with multiple servers configured. A Rust daemon that supervises servers out-of-band (so the host crash doesn't kill them, and conversely a server crash doesn't crash the host) is a clean architectural fit.

    Evidence: pain points: lifecycle, transport constraints. Citations: .

  4. Unified logs and a debugger surface

    Every host writes logs to a different location; stderr capture varies; the Inspector exists precisely because in-host visibility is poor. The manager can offer a single mcp-mgr logs <server> view by capturing stderr at spawn time and surfacing it through its TUI / GUI — without requiring every host to add UI.

    Evidence: pain points: debugging. Citations: .

  5. Cross-host atomic operations (add to N hosts in one click)

    Add the GitHub MCP server to Claude Desktop, Cursor, and Cline today = three edits in three formats in three locations. Once the manager has per-host emitters (gap #2), this becomes a free feature: a checkbox grid of "where should this server be exposed?" with diff preview.

    Evidence: pain points: duplication. Citations: .

  6. MSIX / PATH detection on Windows + macOS

    The Windows MSIX double-path bug is a documented hours-of-debugging trap for users editing the wrong file. On macOS, hosts don't inherit shell PATH, so npx/uvx appear missing. A manager that pre-emits to both Windows paths (or detects which the host reads) and that injects PATH into the spawned process's env resolves both issues without host cooperation.

    Evidence: pain points: install. Citations: .

  7. Transport bridging for stdio-only hosts

    Several hosts (notably Claude Desktop in its user-edit JSON config, and Goose's older type: sse handling) can't speak Streamable HTTP directly to user-supplied URLs. Hosting a tiny stdio proxy that fronts a remote Streamable HTTP server lets users put remote servers in stdio-only hosts.

    Evidence: adoption matrix. Citations: .

What this stream argues v1.0 should not chase

Replacing host approval UI

Only the conversational surface can show "Claude wants to run delete_branch". The manager can express policy, not own the dialog.

Generic sandboxing

VS Code is starting to ship sandboxEnabled at the host layer. Stream 2 (stoic-badger-sandbox) is dedicated to this; this stream defers.

Runtime bundling beyond opt-in

Anthropic's DXT bundles a runtime per extension. Doing this for every server in v1.0 inflates the manager's footprint disproportionate to the benefit; an opt-in "ship a node runtime" toggle is enough.

A registry

Smithery and the official MCP servers registry exist. The manager should consume registries, not be one.

Uncertainty

  • Will Claude Code's .mcp.json become the de facto canonical schema? It is already the richest (OAuth metadata override, scope pinning, headersHelper, alwaysLoad, timeout, env-var expansion). If yes, the manager should mirror its field set; if a different host (or the spec itself) introduces an official config schema, that one wins. Confidence: medium.
  • How much config-edit drift is actually happening? The "user edits Cursor's UI after the manager has written the file" scenario may be common (Cursor's settings UI is prominent) or rare (most users prefer one path). The reconciliation cost depends on this. Confidence: low; user research needed.
  • Is OS keychain UX usable across Linux distros? macOS Keychain and Windows Credential Manager are standardized. Linux Secret Service exists but pass users may prefer that; a manager must abstract both. Confidence: medium.
  • Will Streamable HTTP win fast enough? If host parity arrives within 12 months, the v2 "uniform proxy" pivot becomes much easier. If not, v1.0's per-host emission remains the dominant value prop. Confidence: medium-high that parity will arrive — the spec already mandates it.
  • How much can be done without a daemon? The CLI / TUI / GUI could be thin clients to host config files only, no background process. But process supervision (recommendation #3) requires a daemon. The architecture choice trades simplicity (no daemon) against value (no in-band lifecycle improvements). Confidence: should be revisited by Stream 3 (steady-bear-foundation).

How this recommendation depends on other streams

  • Stream 2 (stoic-badger-sandbox) — owns the isolation question. This stream defers sandboxing to it.
  • Stream 3 (steady-bear-foundation) — owns the daemon-vs-library decision that gates Recommendation #3 (real process supervision).
  • Stream 4 (precise-crane-conduit) — owns the wire protocol between the canonical store and any client process; the schema we land on here feeds into that wire format.
  • Stream 5 (nimble-raven-toolkit) — picks the TUI / GUI frameworks that will render the diff-preview-before-emit UX recommended above.
