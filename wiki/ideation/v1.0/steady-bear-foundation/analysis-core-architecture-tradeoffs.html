Analysis — Crate boundaries and the API surface

This page is the bridge between the research pages (what's possible) and the recommendation page (what we should pick). It draws crate boundaries inside the workspace, explains why each boundary is where it is, and marks where the API surface that Stream 4 needs to consume lives. Tradeoffs only — no decisions yet.

What "CORE" includes (and excludes)

The core is everything below the IPC boundary that clients (CLI / TUI / GUI) cross to talk to the manager. The core does not:

  • Define the wire protocol between manager and client. That's Stream 4's territory. The core exposes a Rust trait API; Stream 4 picks how to serialize it (gRPC vs JSON-RPC vs custom).
  • Render UI. Streams 5's territory.
  • Define what a sandbox looks like — Stream 2 picks Nix/devenv/Docker/raw. The core just calls into a Sandbox trait.
  • Specify which host applications get adapters — Stream 1 produces the inventory. The core ships a HostAdapter trait plus one reference implementation.

The core does include: process supervision, transport handling, registry/config/journal state, secrets indirection, lifecycle reconciliation, the runtime, the per-MCP-server protocol speaker (if proxy mode), and the IPC server that clients connect to.

Why this split

  • mcp-proto exists separately from mcp-supervisor — so a future "lightweight client probe" tool can depend on protocol types without pulling in tokio child-process internals.
  • mcp-secrets is its own crate — because keyring has platform-conditional feature flags that no other crate should have to think about. Isolating it also makes auditing the secret-handling code path one-directory-shaped.
  • mcp-store separate from mcp-core — so the synchronous-vs-async question for SQLite is contained. If we pick rusqlite the store can wrap blocking calls in spawn_blocking internally and present an async surface; mcp-core doesn't know.
  • mcp-core as a real library, not just a daemon — embedded mode (library + ephemeral) and daemon mode (mcpd hosts it) both fall out of the same code path. Stream 4 only has to define the wire mapping once.
  • mcpd is thin — it owns the IPC socket lifecycle, the OS-service plumbing, and signal handling. It does not own MCP semantics.

Where the API surface lives

Stream 4 picks how to serialize the API; this stream defines its Rust shape. The shape we ship from mcp-core determines what every client must support, so it should be conservative.

Sketch of CoreApi

#[async_trait::async_trait]
pub trait CoreApi: Send + Sync + 'static {
    // Discovery
    async fn list_servers(&self) -> Result<Vec<ServerSummary>>;
    async fn get_server(&self, id: &ServerId) -> Result<ServerDetail>;

    // Lifecycle
    async fn install(&self, spec: InstallSpec) -> Result<ServerId>;
    async fn uninstall(&self, id: &ServerId) -> Result<()>;
    async fn start(&self, id: &ServerId) -> Result<()>;
    async fn stop(&self, id: &ServerId) -> Result<()>;
    async fn restart(&self, id: &ServerId) -> Result<()>;

    // Observation (streaming)
    fn subscribe_events(&self, filter: EventFilter)
        -> BoxStream<'static, Event>;
    fn subscribe_state(&self, id: &ServerId)
        -> watch::Receiver<ServerState>;

    // Host wiring
    async fn link_to_host(&self, host: HostId, id: &ServerId) -> Result<()>;
    async fn unlink_from_host(&self, host: HostId, id: &ServerId) -> Result<()>;

    // Inspection (matches mcp-inspector's use case)
    async fn list_tools(&self, id: &ServerId) -> Result<Vec<ToolDescriptor>>;
    async fn call_tool(&self, id: &ServerId, name: &str, args: Value)
        -> Result<ToolCallResult>;
}

The streaming methods (subscribe_events, subscribe_state) lean on Tokio's broadcast (for events) and watch (for state) — these are the canonical Tokio primitives for "many consumers, fire-and-forget" and "many consumers, latest-value" respectively.

For Stream 4: this trait is what the wire protocol needs to expose; any wire format (gRPC, JSON-RPC over Unix socket, custom binary) can be a thin translation. The streaming methods are why a request/response-only protocol (e.g. plain JSON-RPC) is awkward — server-sent events / bidi streams / SSE / WebSockets are needed.

Telemetry / observability story

Choosing tracing as the instrumentation layer buys three things at once:

  1. Internal journal — a custom tracing::Subscriber Layer funnels structured events into mcp-store's event table. Every #[instrument] in mcp-supervisor becomes a row.
  2. Local debug logs — tracing-subscriber's fmt layer for human-readable stderr in mcpd --foreground.
  3. Optional OTLP export — tracing-opentelemetry as a Layer, off by default; users who run Datadog/Honeycomb/SigNoz flip a config flag.

Bridges to keep in mind: tracing-log for crates that still use log (e.g. hyper), so we get unified output without forking those crates.
