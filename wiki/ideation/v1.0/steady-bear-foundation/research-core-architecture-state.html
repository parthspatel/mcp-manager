Research — State stores: registry, config, journal, secrets

The core owns four logically separate pieces of state. They have different read/write patterns, different durability requirements, and different exposure to clients — and conflating them into one store is the source of most "why is my CLI showing stale data" bugs in this class of tool. This page maps each store to candidate Rust crates, lays out a migration strategy for schema evolution, and discusses how the core's registry relates to host applications' own MCP config files.

Installed-server registry

The registry is the source of truth for "what servers does this user have installed and how are they invoked?". The shape closely mirrors a systemd unit file: a name, an immutable identity (registry URL + version + integrity hash), an exec spec, restart policy, and optional resource limits. Like Lima's templates, it should be replayable: if the registry is restored from backup, the supervisor can fully reconstruct managed servers without depending on its in-memory state.

The dominant patterns in similar tools: Docker uses BoltDB; podman uses BoltDB and then SQLite; cargo uses one TOML manifest per crate; rustup uses TOML; nix uses SQLite. SQLite-via-rusqlite is the most common "embedded persistent state in a Rust CLI/daemon" choice — it ships in 0 system dependencies if bundled, has decades of crash-safety hardening, and exposes a real query language that grows with the tool.

Config store + host-app linkage

Configuration has two distinct layers we should not collapse:

  1. Manager-internal config — the merged truth about each server (env vars, transport, sandbox profile, secret refs). Lives in the registry's database row or a side table.
  2. Host-app config files — the JSON/YAML files that Claude Desktop, Cursor, Cline, Continue, Zed, VS Code etc. each maintain. Stream 1 (curious-otter-survey) inventories these.

For v1, the manager's internal config is the source of truth, and the manager writes the host-app files (with a `# managed by mcp-manager` header so we can detect manual edits). This is the same approach nvm, rustup, and pyenv take to shell profile files: small, reversible, fenced edits driven by the tool. The alternative — the manager reads the host files and treats them as authoritative — fails fast because the host file formats diverge: Claude Desktop and Cursor differ enough that a unified read model needs per-host adapters anyway.

Adapter pattern for host files

trait HostAdapter {
    fn id(&self) -> HostId;
    fn config_path(&self) -> PathBuf;
    fn read(&self) -> Result<Vec<HostServerEntry>>;
    fn write(&self, entries: &[HostServerEntry]) -> Result<()>;
    fn supports_transport(&self, t: Transport) -> bool;
}

// each host (Claude Desktop, Cursor, Cline, …) ships one impl.

Event journal

The event journal serves three readers:

  • TUI tailing live, expecting sub-second latency.
  • CLI mcp logs <server> reading a windowed slice.
  • GUI rendering a timeline + filter UI.

Two existing designs to crib from. systemd-journald writes append-only binary files with indexed fields like PID, UID, and cgroup so queries by service/time are O(log n). conmon (podman's per-container monitor) writes each container's logs to a per-container file or directly into the systemd journal, capturing exit time and status code for later retrieval.

For MCP Manager, the closest Rust-native realization is: a SQLite table events(server_id, ts, level, kind, payload) with an index on (server_id, ts), plus a Tokio broadcast channel that lets live readers tail without polling. broadcast is the Tokio convention for "multi-consumer, fire-and-forget events", and bounded broadcast automatically drops the slowest receiver rather than blocking the writer. 

// fan-out journal
pub struct Journal {
    db:    SqlitePool,             // durable, queryable
    live:  broadcast::Sender<Event> // 1024-deep ring buffer
}

impl Journal {
    pub async fn record(&self, e: Event) -> Result<()> {
        sqlx::query("insert into events …").bind(&e).execute(&self.db).await?;
        let _ = self.live.send(e); // ignore "no subscribers"
        Ok(())
    }
    pub fn subscribe(&self) -> broadcast::Receiver<Event> { self.live.subscribe() }
}

Secrets vault

The keyring crate is the de facto cross-platform secrets store for Rust. It exposes a platform-independent Entry identified by a (service, user) pair and offers set_password / get_password / delete_password plus binary-secret variants. Supported backends:

  • macOS: Keychain Services
  • Windows: Credential Manager
  • Linux: Secret Service (dbus / zbus) and/or keyutils
  • Android: shared preferences store
  • Plus a SQLite-encrypted fallback (Turso) and a mock store for tests

The crate has no default features; the consumer must explicitly enable the platforms they intend to ship.

Secret indirection

A practical pattern is to store opaque references in the registry — e.g. {"api_key": "@keyring:openai/api_key"} — and resolve them at server-spawn time. This keeps secrets out of database backups, out of mcp config dump output, and out of crash reports. The supervisor reads the secret, places it into the child's environment via tokio::process::Command::env, and never logs the resolved value.

Schema migration

The state schema will change between v1 and v2; we should adopt a migration strategy before shipping rather than retrofit. Two ergonomic approaches in Rust:

  1. SQLite migration files — numbered SQL files (0001-init.sql, 0002-add-secret-refs.sql) applied in order with the version stored in PRAGMA user_version. sqlx's built-in migrator handles this; rusqlite_migration does the same for the sync stack.
  2. Tagged-enum serde versioning — for the JSON-ish parts (e.g. transport descriptors, host-app config payloads). serde-evolve formalizes the pattern: enum FileVN { V1(Schema1), V2(Schema2) } with From for V2 implementations; compile errors flag missing migration paths.

Combined: SQL DDL migrations for the registry / config / journal tables; serde-evolve enums for the structured columns whose shape will change without a DDL change (e.g. the transport descriptor field).

On-disk layout convention

Following XDG on Linux, Apple's recommendations on macOS, and Known Folders on Windows: 

$XDG_DATA_HOME/mcp-manager/       # ~/.local/share/mcp-manager on Linux
  ├─ state.db                     # SQLite: registry + config + journal
  ├─ servers/<id>/                # per-server scratch (logs overflow, caches)
  └─ migrations.log

$XDG_CONFIG_HOME/mcp-manager/     # ~/.config/mcp-manager
  └─ daemon.toml                  # daemon-level config (listen socket, log level)

$XDG_RUNTIME_DIR/mcp-manager/     # ephemeral, per-session
  └─ daemon.sock                  # IPC socket (Stream 4)

# secrets: OS keychain via `keyring` crate, never on disk

macOS maps to ~/Library/Application Support/mcp-manager/; Windows maps to %LOCALAPPDATA%\mcp-manager\. The directories or dirs crates already encapsulate these mappings.
