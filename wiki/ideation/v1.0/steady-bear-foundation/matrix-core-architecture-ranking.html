Ranking — Five architecture archetypes

Drag the weight sliders to re-rank live. Each cell's score is 0-5 against the criterion in the column header; cell footnotes link to the evidence pages where the score is justified. Scores are deliberately blunt — they encode "small / medium / large" not "37% better than 42%". Weights default to roughly even, with development velocity slightly emphasized because this is a v1.0.

How to read the criteria

Startup latency
How fast does a typical CLI invocation complete? Higher = faster.
Implementation complexity
How much code, how many edge cases, how hard to debug. Higher = simpler.
Multi-user support
Can multiple OS users on the same machine share installs and supervision? Higher = better support.
Security boundary
Does the design naturally enforce least-privilege between manager, MCP server, and client? Higher = stronger boundary.
Cross-OS support
How well does the pattern map onto macOS / Linux / Windows? Higher = fewer per-OS hacks.
Crash recovery
If the manager (or a server) crashes, how well does state survive? Higher = better recovery.
Telemetry/observability
How natural is it to expose a journal, live tail, metrics? Higher = better natural fit.
Dev velocity (v1)
How fast can a small team ship a credible v1.0 in this archetype? Higher = faster.

Archetypes explained

Daemon required (docker-style)

A persistent mcpd is mandatory; the CLI is a thin REST client. Closest precedent: dockerd.

Tradeoff Heavy on install ceremony (must register as service), strong on telemetry and supervision, single point of failure unless we add per-server shims.

Daemonless w/ optional daemon (podman-style)

CLI works without a daemon by running per-server monitors (conmon-like) when starting a server; an optional mcpd can be enabled for shared state / on-boot. Closest precedent: podman + conmon.

Tradeoff Best balance of "works out of the box" with "scales up to shared installs". More code than pure daemon because both paths must work.

Library + CLI only (cargo-style)

No background process. Every CLI invocation reads state files, performs the action, exits. Closest precedent: cargo, uvx.

Tradeoff Can't supervise long-running servers — fatal mismatch with MCP stdio servers that must outlive the CLI invocation. Could work if servers are started by host apps and the manager only tracks them.

Single binary w/ embedded daemon

One executable that auto-detects: if a daemon is already running, the CLI talks to it; otherwise the CLI starts one (in-process or as a background fork). The daemon is the same binary in a different mode.

Tradeoff Smallest install surface (one binary), highest dev velocity (no second crate to ship), still gets background work. Borrowing from tmux / nvim --listen patterns.

Microkernel w/ plugin runtimes

Tiny core that delegates almost everything (transports, sandboxes, host adapters) to dynamically loaded plugins. Closest precedent: containerd's plugin model; Lima's driver layer.

Tradeoff Maximum flexibility, but plugin loading + ABI stability + cross-OS dynamic loading is a meaningful body of work. Premature for v1.0.

Sensitivity notes

The ranking is most sensitive to dev velocity and security boundary. Cranking dev velocity up pushes the single-binary archetype to the top because it ships with the least new code; cranking security boundary up pulls the microkernel-with-plugin design upward (process-level isolation between sandboxes vs in-process). Cranking multi-user support up favors the docker-style daemon-required design because that's the one designed for shared access from day one.

Library-only ranks last across most reasonable weightings because the core's MCP-server-lifetime requirement (servers must outlive CLI invocations, per research · daemon-vs-library) cannot be satisfied without some background process — even if that process is a per-server conmon-like.
