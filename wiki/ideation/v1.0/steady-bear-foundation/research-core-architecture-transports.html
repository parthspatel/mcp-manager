Research — MCP transports and the manager's relationship to them

MCP servers speak one of two standard transports (stdio or Streamable HTTP, plus legacy HTTP+SSE). This page summarizes each transport from the spec, explains the major architectural fork — does the manager speak MCP to its servers (proxy mode) or only manage their lifecycle (supervisor mode)? — and considers the routing/multiplexing requirements implied by each choice.

stdio transport

The spec for the stdio transport is short and prescriptive:

  • The client launches the MCP server as a subprocess.
  • The server reads JSON-RPC messages from stdin and writes JSON-RPC messages to stdout.
  • Messages are individual JSON-RPC requests, notifications, or responses, delimited by newlines, and MUST NOT contain embedded newlines.
  • The server MAY write UTF-8 strings to stderr for logging; clients MAY capture, forward, or ignore them.
  • The server MUST NOT write anything to stdout that is not a valid MCP message.
  • The client MUST NOT write anything to the server's stdin that is not a valid MCP message.
  • Clients SHOULD support stdio whenever possible.

Practical implications for the manager:

  • Reading line-delimited JSON from a child is straightforward with tokio::io::BufReader::lines(); the manager should set a per-line cap so a malformed server can't OOM the manager.
  • Capturing stderr separately turns "server prints a warning" into a journal event (see event journal).
  • Backpressure is critical — if the manager doesn't drain stdout, the server's write() will block on a full kernel pipe buffer. Use a bounded reader task per child (cf. stdio backpressure).

Streamable HTTP transport

Streamable HTTP is the modern remote transport, introduced in the 2025-03-26 revision to replace HTTP+SSE. The full picture from the spec:

  • The server provides a single MCP endpoint path that supports both POST and GET methods (e.g. https://example.com/mcp).
  • Every client message is an HTTP POST. The body is a single JSON-RPC request, notification, or response.
  • The client MUST include Accept: application/json, text/event-stream.
  • For a JSON-RPC request, the server MUST either return Content-Type: application/json with a single response, or return Content-Type: text/event-stream and open an SSE stream that eventually contains the response.
  • Notifications / responses get HTTP 202 Accepted with no body.
  • The client MAY also issue an HTTP GET to open a server-initiated SSE stream for unsolicited server→client messages.
  • Sessions are tracked via an Mcp-Session-Id header assigned at InitializeResult; HTTP 404 in response indicates "your session is gone, re-initialize".
  • The protocol version is carried in MCP-Protocol-Version: 2025-06-18; an unknown value MUST be rejected with HTTP 400.

Security guardrails the spec calls out

"Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks. When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0). Servers SHOULD implement proper authentication for all connections."

These are server-side requirements, but the manager — when it launches a local Streamable HTTP server — should pick a localhost-only port and refuse to publish it externally without explicit opt-in.

Legacy HTTP+SSE

The 2024-11-05 transport ("HTTP+SSE") was a separate POST endpoint for client→server and a long-lived SSE stream for server→client. The spec marks it as deprecated in favor of Streamable HTTP but documents a backwards-compat probe sequence: try POSTing InitializeRequest first; if you get 4xx, fall back to issuing a GET and expecting an endpoint SSE event.

The manager should support reading old servers but should default new installs to Streamable HTTP. The mcp-inspector reference implementation already speaks all three transports.

Internal abstraction

Inside the manager, we want one trait that hides the transport so supervisor logic, health checks, and proxy logic don't care about the wire format. A sketch: 

#[async_trait::async_trait]
pub trait Transport: Send + Sync {
    /// Send one JSON-RPC frame; backpressure-aware.
    async fn send(&self, msg: JsonRpcFrame) -> Result<()>;
    /// Stream of frames from the peer.
    fn incoming(&self) -> BoxStream<'static, Result<JsonRpcFrame>>;
    /// Out-of-band shutdown.
    async fn shutdown(&self) -> Result<()>;
    /// Connection-level metadata (transport kind, peer pid, latency).
    fn meta(&self) -> TransportMeta;
}

pub enum TransportKind { Stdio, StreamableHttp, LegacyHttpSse }

The rmcp SDK already supplies concrete implementations: TokioChildProcess for stdio, plus transport-sse-server and transport-streamable-http-server features for the HTTP transports. Wrapping rmcp's transports in our own trait is mostly an exercise in trait-object dispatch.

Supervisor vs. proxy fork

The single biggest architectural decision in this stream is whether the manager speaks MCP to the servers it manages.

A. Pure supervisor

The manager only runs servers and tracks their lifecycle. Host applications connect directly to the server's transport (stdio over a spawned subprocess, or the server's HTTP endpoint). The manager edits the host's config files so they know how to reach each server.

  • + Minimal coupling to MCP semantics — the manager survives MCP version bumps without code changes.
  • + No extra hop, no latency overhead on every tool call.
  • − Can't centralize ping/health checks — has to rely on passive signals (process alive, stdio open).
  • − Stream 4's client API only reflects what the manager itself observes; tool-call audit happens only at the host.
  • − Cannot offer features like "one logical server backed by two physical replicas" or "fan one server's tools to multiple hosts on different transports".

B. Proxy (manager-as-MCP-client & -server)

The manager initializes its own MCP client connection to each managed server and exposes a single MCP endpoint per host. Every tool call hits the manager, gets logged, and is forwarded to the right server. This is exactly what mcp-inspector does for debugging.

  • + Built-in ping health, lifecycle hooks, tool-call audit, per-tool rate limiting, request transformation.
  • + Lets the manager expose Streamable HTTP to clients while servers speak stdio internally (transport bridging — same job as mcp-inspector's proxy).
  • + Stream 4 client API becomes "watch what the manager already saw"; no special hooks into MCP frames needed.
  • − Couples the manager tightly to MCP version evolution — every spec revision potentially needs SDK upgrades.
  • − Extra hop on every tool call (latency, though small for stdio→stdio).
  • − Bigger surface area: manager now has to implement valid MCP server behavior to its clients, including session management (Mcp-Session-Id) per the spec.

C. Hybrid (opt-in proxy)

Supervisor by default; proxy only when (a) the user opts in for audit/observability, or (b) the host can't reach the server's native transport (e.g. host wants Streamable HTTP, server is stdio-only). This is structurally what mcp-inspector already does for testing — a bridge layered on top of a registry. The manager can run identical code, just enabled per-server-per-host instead of universally.

Multiplexing & routing

If we pick proxy or hybrid mode, the spec's session model dictates how routing works. From the Streamable HTTP section: a manager-served session ID identifies a single host's logical connection; the manager MUST track that ID across requests and MUST NOT broadcast the same JSON-RPC message across multiple SSE streams.

Leveraging the rmcp SDK

rmcp is the official Rust MCP SDK, built on tokio. Its feature surface as of v1.7 (May 2026) covers:

  • Server, client, and procedural-macro crates (rmcp + rmcp-macros).
  • Built-in transports: stdio, TokioChildProcess wrapper, SSE server, Streamable HTTP server.
  • Tools, resources, prompts, sampling, roots, logging, completions, notifications, subscriptions, long-running tasks.

For supervisor mode, we use only TokioChildProcess + minimal initialization for ping. For proxy mode, the manager becomes both an rmcp client (to each managed server) and an rmcp server (to each connected host) — meaning the spec correctness is mostly the SDK's problem, not ours.
