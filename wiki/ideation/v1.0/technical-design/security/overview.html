Security — Facet Synthesis

Where the five security stances converge, where they diverge, and what gets adopted. The five essays — red-team, crypto-pedant, sandboxing-veteran, secrets-architect, audit-compliance — were written against an already-locked v1.0 surface: TUF-lite trust manifest with baked-in fallback (7-day TTL), minisign indexes and cosign-when-present packages, direnv-style sha256-pinned project-config trust, SecretStore + OsKeyringStore + EnvVarPassthrough via a layered store, SO_PEERCRED on the UDS, five isolation modes (devenv | docker | podman | uvx-npx | none) per server, append-only JSONL audit, no telemetry. Synthesis adopts within that envelope; it does not reopen the lockdown.

Where the five agree

The agreement surface is wider than any single essay lets on. All five agents — adversarial as their stances are — converge on a small set of load-bearing properties for v1.0. Treat the list below as invariants the implementation must preserve; everything else in this document is how we get there.

  1. Default-deny everywhere a default exists. Network egress off, filesystem scoped, isolation on, project configs untrusted until pinned, registries refused unless signed. Red-team frames this loudest; sandboxing-veteran bakes it into the Docker/Podman flag template; crypto-pedant mirrors it in the verifier (reject unknown alg, reject stale trust.toml for state-changing ops). Default-deny applies to bytes, namespaces, and algorithms uniformly.
  2. Cryptographic primitives are off-the-shelf. ed25519 for signatures, SHA-256 for hashes, no hand-rolled code. Crypto-pedant writes the rule; the other four endorse by reference. Where we wrap an OS facility (Keychain, libsecret), we accept its choice and document it.
  3. The MCP server is the adversary, not the dependency. Every essay assumes the installed package could be hostile and designs from there. Friendly-and-buggy is a special case of hostile not yet observed — red-team's framing, echoed by sandboxing-veteran's gradient and secrets-architect's intake discipline.
  4. Secrets cross the process boundary exactly once, via env at execve. Locked invariant from technical-design; all five agree. Secrets-architect and sandboxing-veteran coordinate the per-mode mechanism (env for level-0-to-2, --env-file /dev/fd/n for containers, fd-passing aspirational for v1.1).
  5. Audit log is JSONL, append-only, daily-rotated, with a hash chain. Locked surface said "append-only JSONL"; audit-compliance raised it to a hash chain and red-team + crypto-pedant agreed (SHA-256, per-line prev_hash, one signature per daily file). Secrets-architect drew a hard line on never logging secret values — fuzz-tested, not assumed.
  6. SO_PEERCRED + 0600 UDS perms suffices for IPC auth on a single-user laptop. No HMAC framing, no per-connection nonces over IPC itself. Crypto-pedant and sandboxing-veteran agree explicitly; red-team agrees with one caveat (a per-spawn nonce for server-to-daemon secret reads — see decisions below).
  7. No telemetry. Local audit is the system of record. All five honor the lock; audit-compliance makes the local log SIEM-exportable rather than treating absence-of-telemetry as a privacy floor.
  8. Every mitigation maps to a CI-enforced test. Red-team's THREAT_MODEL.md table codifies it; the others cite tests inline (no-secret-in-logs fuzz, sandbox-blocks-~/.ssh e2e, audit-chain replay).

Where they diverge

Five honest disagreements remain. Each is resolved under decisions; the divergence is documented here so the trade-off is explicit.

1. How strict is "fail-closed" on stale trust manifests?

Red-team wants fail-closed everywhere: stale trust.toml means no work. Crypto-pedant proposes the "fail-soft on cache, fail-closed on install" compromise: stale manifests still serve read-only ops (mcpm list, mcpm exec) but block state-changing ones (mcpm install, mcpm update) until refresh; hard ceiling of expires_at + 30d grace beyond which nothing verifies. Implementation adopts crypto-pedant's compromise. Red-team's strict line is unworkable for travel; the 30-day ceiling preserves the "publisher silent for a month; something is wrong" tripwire.

2. Per-spawn MCPM_INSTANCE_TOKEN nonce — yes or no?

Red-team's Tree 2 identifies the cross-server secret-leak path: server A reading server B's secrets over the same UDS, because SO_PEERCRED only attests UID. Mitigation: 32-byte nonce in each spawned server's env, mapped server-side to (token → server_name). Crypto-pedant calls this "cargo-culted crypto" and resists. Implementation sides with red-team: ~64 bytes per spawn + HashMap lookup closes a real same-UID class SO_PEERCRED cannot. It is not wire crypto; it is a server-instance identifier.

3. Per-server keychain namespacing — load-bearing or convenience?

Red-team argues per-server scoping is non-optional: keychain account is dev.mcp-manager/<server>/<name>; cross-server access requires secrets_from the user types by hand. Secrets-architect draws the same line. Implementation adopts without compromise; the locked schema currently leaves the door open to global-scoped secrets, and this decision closes it.

4. Sandbox-policy logging granularity

Audit-compliance wants both sandbox.allow and sandbox.deny. Sandboxing-veteran objects that per-syscall logging is unworkable (thousands per second from a Node MCP). Negotiated: log at policy granularity, not syscall, with a per-session bloom filter to dedupe. First-touch of a new path or destination logs once. The server.spawn record captures the materialised policy (bwrap argv hash, SBPL profile sha256, Docker run flags) so a later auditor can reconstruct the exact policy in force.

5. macOS Keychain accessibility constant

Crypto-pedant proposes kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. Secrets-architect proposes kSecAttrAccessibleWhenUnlocked. Implementation adopts secrets-architect's choice: threat model is stolen laptop, not remote-attacker-with-physical-access, and WhenUnlocked closes the "background reboot exposes secrets" gap. Both forbid iCloud Keychain sync — non-negotiable.

Decisions

Trust model end-to-end

Adopt. mcpm-trust keeps the v1.0 baked-in ed25519 root pubkey plus a baked-in revocation-only pubkey. On first run trust.toml is fetched (crypto-pedant's table); on network failure mcpmanagerd enters baked-in-fallback with a one-line warning every CLI call until refresh. Routine root rotation every 12 months; emergency rotation within 24h via a new trust.toml whose revoked_keys names the compromised key_id. Catastrophic root loss requires a binary reinstall — accepted single-publisher cost; threshold signing is a v2.0+ migration with the envelope already prepared for multi-sig.

Verifier order: parse → signature verify → now >= signed_at - skew → now < expires_at → version > previous_version. The monotonic-version check defends against replaying an old-but-valid trust.toml.

Per-package signature verification (algorithm-agility, revocation, offline)

Adopt. Every signed payload uses the agility envelope from crypto-pedant's design: explicit alg tied to a static allowlist (v1.0: ["ed25519"], never accept "none" — the JWT bug), key_id, signed_at, expires_at, payload_hash, payload_hash_alg. trust.toml records each key's alg; verification rejects on envelope.alg != key.alg.

Per-package signatures: minisign for tarball-and-index registries; cosign-when-present for OCI/Docker, with Rekor inclusion-proof required (per red-team) when the package's registry sets required_signatures = true. All three baked-in registries (official, github, docker) set it. Hash agility via string prefix ("sha256:9f4e2d...") so SHA-512/256 / SHA-3 migration is per-record.

Trust gate for project configs (direnv-style sha256-pinning)

Adopt with enumerated failure modes. Project-scope .mcp-manager.toml never applies until the user runs mcpm trust grant. The trust key is SHA-256(absolute-path) || SHA-256(canonical-JSON(parsed-TOML)): moving the repo invalidates the grant, semantic-equivalent re-formatting does not (canonical-JSON over parsed-TOML). The six failure modes from red-team's enumeration ship as named tests:

  • Fresh clone: refuse, prompt for mcpm trust grant.
  • Previously trusted, file modified: refuse, show diff vs. last trusted version, re-prompt.
  • Trusted file, path moved: trust invalidates (different path is different context).
  • trust.toml itself tampered: daemon enters "trust-degraded" mode; user-scope only; audit trust.tampered.
  • Project config requests an unsigned registry: refused. Project scope can use trusted registries; it cannot add new ones.
  • Project config requests isolation = "none": refused outright. none is user-scope only. Project author needs that, they put a note in the README; user opts in by setting isolation = "none" in their own user-scope config for that specific server.

Secrets storage and access (SecretStore, layered store, redaction)

Adopt. The SecretStore trait from secrets-architect's design: object-safe, async, returns Option<SecretString> from get(), never returns values from list(). SecretRef::Named { server, name } with #[non_exhaustive] so v1.1 can add VaultPath, OnePasswordItem, etc. without breaking external matches.

Layered chain: EnvVarPassthroughStore first (read-only override for CI), OsKeyringStore second (durable). Reads fall through; writes go to keyring only. Documented precedence — surprises kill secret hygiene.

Per-server scoping is mandatory. Keychain account is dev.mcp-manager.mcpmanagerd/<server>/<name>. A server can only request secrets in its own namespace. Cross-server access requires secrets_from = ["other-server.NAME"] in user-scope (not project-scope). Resolves red-team's "random-tool declares secrets = ["AWS_SECRET_ACCESS_KEY"]" footgun.

In-memory: every plaintext travels in secrecy::SecretString with zeroize on drop. Function signatures inside the secrets boundary take &SecretString, never &str; clippy::disallowed_types warns on raw String in those crates. tracing redaction layer rewrites known-secret field names (token, password, api_key, secret, authorization) to [REDACTED] as belt-and-suspenders. CI fuzz test writes random byte strings as secrets and greps every emitted log/audit line; match fails the build.

Intake paths: TTY via rpassword (reads /dev/tty, never echoes), --from-file, --from-env, --stdin. No --value=...; argv is broadcast.

Backend availability: macOS Keychain uses kSecAttrAccessibleWhenUnlocked, never Always, never iCloud Keychain. Linux requires a reachable Secret Service (libsecret / KWallet). If none, daemon emits a startup audit entry secret.backend.degraded (per crypto-pedant's silent-degradation concern) and refuses to write — the EnvVarPassthroughStore layer remains for the user who has explicitly exported secrets. No file-based fallback store; rolling our own keyring is the trap the OWASP cheat sheet warns about.

IPC auth (SO_PEERCRED + UID + per-spawn instance token)

Adopt with one layered addition. UDS at $XDG_RUNTIME_DIR/mcpmanagerd.sock with 0600 perms. SO_PEERCRED (Linux) / LOCAL_PEERCRED (macOS) on every accept; mismatched UID closes the connection and audit-logs auth.failed. No HMAC framing on the JSON-RPC wire — the kernel is the source of truth.

Per-spawn instance token (red-team's addition): when mcpmanagerd spawns server B, it generates a random 32-byte nonce, injects it into B's environment as MCPM_INSTANCE_TOKEN, and stores the mapping token → server_name in memory. Secret-read RPCs from a wrapper (mcpm exec) must present a token matching their declared server_name; mismatch denies and audit-logs. This closes the cross-server-as-same-UID class that SO_PEERCRED alone cannot. Tree 2's fifth leaf.

Bypass scenarios documented and tested: same-UID server-to-daemon spoofing (mitigated by the nonce above); PID reuse on Linux (we rely on UID, not PID, for auth — noted as a non-issue); macOS LOCAL_PEERPID race (same — UID-only); socket-file replacement (mitigated by O_EXCL on bind + sibling flock).

Sandbox / isolation per server (5 modes + escape paths)

Adopt the gradient. Five modes are not equivalents; they are levels on a gradient and the user must see which level a server runs at. Badge in the TUI; column in mcpm list; mcpm install echoes the resolved mode. Sandboxing-veteran's gradient is canon.

Default-mode selection algorithm ships as sandboxing-veteran's pick_default_isolation: manifest opinion → Docker → Podman → Devenv (with wrapper) → uvx-npx (only if version-pinned) → refuse to install. The refuse-to-install fall-through is load-bearing; without it, "we shipped a tool that defaults to whatever's on the path" is the failure mode.

FS deny-list in every mode that supports one: ~/.ssh, ~/.aws, ~/.config/gh, ~/.gnupg, ~/.netrc, ~/.password-store, ~/Library/Keychains (macOS), ~/.docker/config.json, ~/.kube, ~/.config/mcp-manager itself. Bubblewrap argv and SBPL profile templates ship pre-written in sandboxing-veteran's design; the SBPL profile is sha256-tracked in the lockfile so a swapped policy file is a tamper event (crypto-pedant's content-addressed policy point).

Escape paths documented per mode: kernel exploits (sandboxing-veteran); docker socket exposure (never mount /var/run/docker.sock, period); rootless subuid/subgid misconfig; sandbox-exec deprecation contingency (fall back to Docker on a future macOS that removes it).

Network egress controls (per server, default deny)

Adopt default-deny with declared egress. All sandboxed modes start with --unshare-net (bwrap) / (deny network*) (SBPL) / --network=none (Docker/Podman). The manifest declares allowed destinations as host:port pairs; the daemon enforces via slirp4netns + nftables on Linux, SBPL (allow network* (remote tcp "host:port")) on macOS, bridge + nftables for Docker (with Docker Desktop's macOS Linux-VM bridge as a documented limitation). For uvx-npx and none, egress is unenforced — the level-0/1 label is the consent.

Egress proxy for the allowlist case: tiny mcpm-egress-proxy Rust binary spawned alongside the server inside its netns; resolves names itself, never trusts the child's DNS, forwards only to allowed hosts (per red-team's allowlist design). Accepted limitation: DNS-over-TXT exfil to an allowed host is still possible; documented, not solved.

FS read/write scoping (per server)

Adopt scoped-default with user-grantable extensions. Every sandboxed server sees $XDG_DATA_HOME/mcpm/servers/<name>/ (rw) and a per-spawn tmpfs /tmp/mcpm-<name>-XXXXXX/ (rw). Read-only: /usr, /bin, /lib, /etc/ssl/certs, /etc/resolv.conf (proxied), /nix/store (devenv only). Deny: the FS deny-list from the sandbox decision. Extra paths require explicit user grant at install time ("this server requests read access to ~/Documents/notes/; allow?"), default no, audit-logged.

In docker / podman: image rootfs is read-only (--read-only), explicit --mounts only, tmpfs /tmp (size-bounded, nosuid,nodev). In devenv: bubblewrap binds $PROJECT_ROOT at /work read-write and presents a fake $HOME at /tmp/home — the real user home is invisible.

Audit log (append-only JSONL, hash chain, integrity)

Adopt the hash chain. Fourteen event types from audit-compliance's schema: daemon.start, daemon.stop, ipc.connect, trust.grant, trust.revoke, install.start, install.verify, install.commit, secret.set, secret.get, secret.unset, server.spawn, sandbox.deny, config.change. Required fields on every event: seq (uint64 monotonic), ts (RFC 3339 UTC ms), event, actor, outcome, details, prev_hash (hex SHA-256 of canonical previous record), v.

Canonicalisation: RFC 8785 (JSC) over the record minus prev_hash, then SHA-256(canonical_bytes || prev_hash_bytes). First line of each daily rotation file references the previous day's terminal hash, so the chain spans rotations transparently. Terminal hash of each closed daily file is signed once with an audit-only ed25519 key stored in the OS keychain under dev.mcp-manager.audit-key/private (crypto-pedant's compromise against per-line signing): one signing operation per day, not per event, no live signing key in process memory.

Durability: fsync before ack on every auth.failed, secret.get, secret.set, install.verify, trust.grant. Other events batch with a 100ms or 4KB flush bound. chattr +a where available (Linux with appropriate capability); macOS chflags uappnd applied where the user permits.

Verification tool: mcpm audit verify walks the chain offline, recomputes hashes, checks seq increment and ts monotonicity, exits 0 or 2. --json emits a SIEM-friendly report. Plain-text recipe (jq + sha256sum) shipped in docs so an auditor without mcpm can still verify. mcpm audit export --format=json|csv produces the SIEM ingestion package with a sidecar manifest (export sha256, seq range, hostname, mcpm version) — the FedRAMP evidence-package convention.

Spawn record contents: the materialised sandbox policy goes into details — bwrap argv hash, SBPL profile sha256, Docker run flags. "Spawned foo, isolation=docker" is unauditable; the flag set is. Single most important detail per sandboxing-veteran.

Out of scope for v1.0: external anchoring (Rekor, user-controlled remote). Daily anchor schema is reserved in the format so v1.1 can ship it without a schema version bump.

First-launch security prompts (--docker-enable, trust root)

Adopt four prompts — three from red-team plus the onboarding gradient picker from sandboxing-veteran:

  1. Trust the root manifest URL? Default yes; URL shown; fingerprint of the baked-in ed25519 root pubkey shown alongside (per crypto-pedant's draft prompt) with a website verification path. "No" puts the user permanently in baked-in-fallback mode.
  2. Default isolation mode for new servers? Detection-driven default: Docker if present, Podman if not, Devenv if Nix present, refuse-to-install otherwise. User can override via mcpm config set default_isolation later.
  3. Enable Docker for the docker registry source? Default no. If yes, daemon verifies docker info and remembers consent. The locked v1.0 --docker-enable behaviour.
  4. Allow env-var passthrough store? Default no. Yes requires explicit consent; audit-logged.

No "trust this prompt → auto-trust future prompts" toggle. Each consent is per-action. On installing a server resolved to isolation = "none" or "uvx-npx" while stronger is available: warning panel showing "this server has full host access. If you wanted Docker, install Docker and re-run". Confirm by typing the server name.

Binary code signing

Adopt per-platform. macOS: Apple Developer ID + notarization; hardened runtime; library validation; spctl --assess passes on every release. The notarization ticket's X.509/RSA-2048 layer is Apple's, documented. Linux: detached ed25519 minisign next to release tarball; both .tar.gz and SHA256SUMS signed; installer script verifies against baked-in pubkey. Release-signing key separate from trust.toml-signing key. Reproducible Linux build via Nix flake — the github:user/mcp-manager flake produces byte-identical to the official tarball.

Supply-chain pinning (Cargo.lock review)

Adopt the full hardening pass. Cargo.lock committed; cargo audit in CI on every push, blocks merge on RUSTSEC. cargo deny for license + advisory + ban policies; the policy file disallows build.rs network access (any transitive dep that adds a network-fetching build script is a blocker). cargo vet with audited entries for the mcpm-secrets, mcpm-trust, and JSON-RPC parser deps; broader deps inherit from Mozilla / Bytecode Alliance / Embark trust roots. SBOM emitted per release via cargo cyclonedx (CycloneDX JSON), shipped alongside the tarball.

Runtime-fetched packages (Python via uvx, Node via bun, containers) verify the upstream package manager's own checksums plus our per-package .minisig from the registry index — belt and suspenders. Tag-pinning is forbidden for container images; digest-pin in the lockfile only.

Open questions

Items not resolved here, with the resolution path called out so v1.0 ships with the door open.

  1. TUF timestamp role for v1.1. v1.0 collapses TUF into a single signed trust.toml with a 7-day TTL; an attacker who controls the network can serve an old-but-valid manifest until expiry. v1.1 adds a separately-signed timestamp.toml (hours-to-days TTL) pointing at the current trust.toml hash. The envelope schema is forward-compatible; no wire break required.
  2. fd-passing for secrets in the strong-isolation modes. v1.0 ships env injection in all five modes plus --env-file /dev/fd/n for Docker/Podman. The fd-passing convention (MCPM_SECRETS_FD=3) is documented for the rmcp SDK but not yet supported by it; once the SDK lands, secrets in bubblewrap / sandbox-exec stop touching /proc/self/environ.
  3. Manifest-driven requires_secrets declaration. Red-team and secrets-architect both want the manifest to enumerate which secret names a server is permitted to request; mcpmanagerd would refuse a secret.get for a name not declared. v1.0 ships the per-server keyring namespace which closes the main attack class, but the manifest declaration would let the trust gate and the secret store share a single source of truth. Land in v1.1 with the same envelope.
  4. SBPL sandbox-exec deprecation contingency. Apple deprecated sandbox-exec circa 2016 but it remains functional. v1.0 ships SBPL profiles plus a documented contingency to fall back to Docker on macOS if a future release removes it. Trigger: any macOS major release that breaks the profile loading; alert + auto-migration plan.
  5. External audit-log anchoring. Audit-compliance proposed an optional daily audit.anchor event the user can mirror to a path of their choosing (Dropbox, iCloud Drive, private gist). v1.0 reserves the schema; the actual emission lands when there's a confirmed user demand and a chosen offsite convention. v2.0 may layer optional Rekor anchoring for true external transparency-log semantics.
  6. Threshold root signing. A single root key is a single point of failure; the catastrophic-loss recovery is "users reinstall from the curl script". v2.0+ moves to m-of-n threshold signing via the algorithm-agility envelope's already-string-typed sig field. The condition for landing this is a second trusted publisher — until then, the operational complexity isn't justified.
  7. Side-channel exfil via stdout. An MCP can re-emit allowed-read file contents into the host LLM's context. We cannot stop this without solving alignment. Documented as an accepted limitation; the path-scoping decision above is the best mitigation v1.0 has.

Ranking matrix

Each stance scored 1–5 across six criteria (threat coverage, cryptographic rigor, isolation strength, secrets safety, auditability, UX friction — with UX friction inverted so lower is better, encoded as higher-is-better in the matrix). How to read this: no single stance wins on every axis, and that is the point. Red-team leads on threat coverage; crypto-pedant on cryptographic rigor; sandboxing-veteran on isolation; secrets-architect on secrets; audit-compliance on auditability. The implementation adopts each agent's strongest lane and reconciles where they conflict — that reconciliation is the decisions section.
