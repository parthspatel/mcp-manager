The Audit Compliance Specialist's Security

Append-only. Sequenced. Hash-chained. Every privileged action logged with a verifiable provenance trail. If a security team auditor cannot, six months from now, take a single JSONL file off a developer laptop and prove cryptographically that no entry has been removed, reordered, or fabricated, then v1.0 has not shipped an audit log — it has shipped a logfile, and that is a meaningfully smaller thing.

Thoughts

What an auditor will actually ask for

The mental model I use, the one I want the v1.0 design to survive, is: a SOC 2 Type II auditor walks up to one of our users six months after install and says "show me every MCP server that was granted secret access to OPENAI_API_KEY in the last quarter, who approved each grant, and prove to me the log has not been edited." Today, with the spec as written, we get to ninety percent of that answer — JSONL events exist, they record the actor and the outcome, they include a versioned schema — and we lose at the last ten percent, which is precisely the part the auditor cares about: integrity. A flat append-only JSONL is not tamper-evident. Any process that can write to ~/Library/Logs/mcpmanagerd/audit/ can also rewrite it. That is the gap I am here to close.

The v1.0 locked decision is "Audit JSONL append-only." Good. I am not arguing against JSONL — I am arguing that "append-only" without a sequence number and a hash chain is a property the filesystem can enforce in name only. On macOS, the user owns the file; chflags uappnd can be removed by the same user. On Linux, chattr +a requires root and is therefore not on the table for a user-space daemon. The only tamper-evidence we get for free is cryptographic, and cryptographic tamper-evidence is cheap: one SHA-256 per event, one monotonically increasing seq per event, one prev_hash field referencing the previous line. That is roughly forty bytes of overhead per event and it transforms the log from "a file we hope nobody edited" into "a Merkle-style append-only ledger anyone can verify with one command." This is the same construction Sigstore's Rekor transparency log uses, the same construction Certificate Transparency uses, the same construction Git uses for its object graph. It is not exotic. It is table stakes for any log that calls itself an audit log.

What "every privileged action" means in practice

I want fourteen distinct event types, no more, no fewer. The temptation in projects like this is either to log too little ("we'll add events as we need them") or to log too much ("every RPC call gets an audit event"). Both are wrong. Too little means the auditor cannot reconstruct the security-relevant timeline. Too much means signal-to-noise collapses, log files explode, and the developer experience pushes everyone toward --verbose=0 which is the same as having no log at all. The fourteen events I land on below are the ones where a privilege boundary is crossed: trust granted or revoked, signature verified or rejected, secret read or written, daemon started, IPC connection authenticated, sandbox escape detected, install initiated, configuration changed. Every line should be an answer to "what changed in the security posture?" and nothing else. Application-level telemetry (tool calls, completions) belongs in a separate stream that explicitly says it is not the audit log.

Provenance is half the audit

The other half — the half that is harder to do well — is install provenance. When github-mcp@1.4.2 appears in someone's servers.toml a year from now, the auditor needs to know: which registry did it come from? what was the package content-hash at install time? which signing key signed the TUF metadata? what was the mcpm binary's own code-signing identity when it performed the install? Without those four facts, "we installed github-mcp on this date" tells you nothing. With those four facts, you have a forensic chain that survives a supply-chain compromise — even if upstream is later revealed to have been backdoored on day N, you can prove that this install happened on day N-30 and pulled the pre-compromise content. The provenance record belongs inside the audit log, not next to it, because the audit log is already the integrity-protected stream and duplicating that integrity guarantee for a separate provenance file is wasted work.

Why local audit still matters even without telemetry

The v1.0 spec correctly says no vendor telemetry. I support that. But "no telemetry" does not mean "no audit" — quite the opposite. Without a central log shipper, the local log is the system of record. It must be exportable, verifiable, and structured well enough that a security team can ingest it into Splunk, Elastic, or whatever SIEM they use when they investigate an incident. That is what mcpm audit export --format=csv|json is for: not exfiltration, not phone-home, but the user choosing to hand their own log to their own security team when something has gone wrong, or — in the SOC 2 case — when an auditor asks. The export format must match what a SIEM expects (timestamps in RFC 3339, fields flattened to dotted notation, one row per event) so that the data is usable without a custom parser.

Arguments

Against red-team

Red-team's threat model is excellent — STRIDE, default-deny, attack trees — and I agree with it. Where we part company is on the role of the audit log under attack. Red-team treats the log as one of the things that must survive compromise; I treat it as the only thing that must survive compromise, because every other defensive layer (sandbox, trust gate, signature verification) can fail silently. The audit log is what tells you a layer failed. Red-team's paper draft mentions "tamper-evident audit trail" once and moves on. I want that phrase load-bearing. Specifically: when a malicious MCP attempts to read ~/.ssh/id_rsa and the sandbox blocks it, that block must produce a sandbox.deny event with the path, the syscall, and a hash-chained sequence number. When that same MCP later succeeds in convincing the user to grant it network access via the trust gate, the trust.grant event must reference the prior sandbox.deny events by sequence number so the auditor can see the escalation path.

Where red-team and I converge: the audit log is part of the threat model, not external to it. An attacker who can suppress audit events is an attacker who has already won. So the log file's own integrity must be a STRIDE-modeled property — Tampering, specifically — and we must specify what we do about it. My answer: hash chain plus a daily "anchor" event that the user can optionally email to themselves or commit to a private gist, which gives retrospective tamper-evidence even if the entire log file is later rewritten.

Against crypto-pedant

Crypto-pedant will want me to specify the hash algorithm, the canonicalization rule, and the signing model with surgical precision. Good. I will. SHA-256 for the chain (matches Rekor, matches CT, hardware-accelerated on every modern CPU, post-quantum concerns irrelevant on this timeline). JSON Canonicalization Scheme (RFC 8785) for the input bytes, because if we hash the literal JSONL line as written we are hostage to the serializer's whitespace and key ordering, and any pretty-printer becomes a tamper event. The prev_hash field is the SHA-256 of the canonical form of the previous record, hex-encoded lowercase, exactly 64 characters, no exceptions.

Where I push back on crypto-pedant: I do not want the local audit log signed by mcpmanagerd's own ed25519 key in v1.0. Signing implies a verifying party — and the only verifying party we have is the same machine, with the same key, which means an attacker who roots the machine forges signatures and we have gained nothing. Hash-chaining alone gives us tamper-evidence within the log; signing gains us nothing without an external trust anchor. If we want external trust, that is v2.0 territory and probably involves something like optional Rekor anchoring or a daily hash committed to a user-controlled remote (their own GitHub gist, their own S3 bucket). For v1.0 the chain is enough; let's not over-engineer.

Against sandboxing-veteran

Sandboxing-veteran wants Seatbelt profiles on macOS, bubblewrap or landlock on Linux, and per-server network egress controls. I agree with all of it. My contribution: every sandbox decision must be a logged event. Not just denials — allows too. Because the question an auditor asks is not "did your sandbox block anything?" but "show me everything the sandbox permitted." Without a complete record of allowed operations, a forensic investigation after a breach is reduced to guesswork. So sandbox.allow and sandbox.deny are both event types in my fourteen.

Sandboxing-veteran will rightly object that logging every sandbox decision is unworkable — a single Node-based MCP can produce thousands of syscalls per second. The compromise: sandbox decisions are logged at the level of policy, not per-syscall. When a new egress destination is allowed, log it once. When a new filesystem path is touched, log it once per session per path. The sandbox itself keeps a per-session bloom filter of already-logged decisions and emits only the first occurrence. This gives the auditor "MCP X touched paths Y, Z, W in this session" without the noise of "MCP X read Y eight thousand times." Volume becomes manageable; signal stays high.

Against secrets-architect

Secrets-architect's layered model — keyring for storage, env for injection at spawn, never plaintext on disk — is correct, and I take no issue with it. My contribution is at the seams: every secret-touching operation must be a logged event. secret.set, secret.get, secret.unset, secret.expose-to-server. The value is never logged. The identity of the secret (its name, e.g. OPENAI_API_KEY) is logged. The actor (the MCP server that requested it, or the user via mcpm secret set) is logged. The outcome — granted, denied, keychain-prompt-shown, keychain-prompt-cancelled — is logged.

Where I will push back on secrets-architect: there is a temptation to say "secret access is so high-volume we should sample." No. Secret access is the single most security-relevant event in this entire system. Every read, every write, every expose-to-child-process gets a line in the audit log. If that volume becomes a problem, the answer is rotation and compaction, not sampling. Sampling means the next time a secret is exfiltrated the auditor gets back "we logged 73% of the access attempts" and that is a job-losing sentence to put in front of a SOC 2 auditor.

Design

14 event types — JSONL schema

Each event is one JSONL line. Required fields on every event: seq (uint64, monotonically increasing from 1), ts (RFC 3339 UTC with millisecond precision), event (one of the fourteen below), actor ({kind: "user"|"daemon"|"server"|"mcpm-cli", id: string, pid: int?, uid: int?}), outcome ("success"|"denied"|"error"), details (event-specific object), prev_hash (hex SHA-256 of canonical previous record, all-zeros for seq=1), v (schema version, "1" for v1.0).

#EventTriggerRequired details
1daemon.startmcpmanagerd bootbinary_hash, binary_signing_id, version, cargo_lock_hash
2daemon.stopmcpmanagerd shutdownreason, uptime_s
3ipc.connectUDS acceptpeer_pid, peer_uid, peer_path, allowed
4trust.grantuser approves projectproject_path, scope, expires_at, prompt_id
5trust.revokeuser or expiryproject_path, reason
6install.startmcpm installregistry, package, version_constraint, requested_by
7install.verifysignature checkpackage, version, content_sha256, signing_key_id, tuf_root_version
8install.commitinstall completepackage, version, content_sha256, install_path
9secret.setkeyring writename, backend (keychain/secret-service/file), scope
10secret.getkeyring readname, requested_by, granted
11secret.unsetkeyring deletename, backend
12server.spawnMCP launchedserver_id, binary_hash, sandbox_profile, env_keys (names only)
13sandbox.denypolicy-blockserver_id, operation, target, reason
14config.changeservers.toml mutationpath, diff_hash, actor

Two things to call out. First, secret.get records the name and the requester but never the value, never even a hash of the value (because the keyspace is small enough that a SHA-256 of an API key is a plausible brute-force target — log the identity, not the material). Second, install.verify is the single most important event in the log for supply-chain forensics: it captures the content hash, the signing key, and the TUF root version at the moment of install, which is the entire forensic chain anyone will need a year from now when they ask "did we ship the backdoored version of github-mcp?"

Hash-chain construction

The chain is constructed as follows. For each event record R_n:

  1. Serialize R_n minus the prev_hash field to canonical JSON per RFC 8785 (sorted keys, no insignificant whitespace, UTF-8).
  2. Compute H_n = SHA256(canonical_bytes_of_R_n_without_prev_hash || prev_hash_bytes) where prev_hash_bytes is the 32-byte raw hash of the previous record (or 32 zero bytes if seq == 1).
  3. Set R_n.prev_hash = hex(H_{n-1}) for the next record; write R_n as a single JSONL line.
  4. fsync the line to disk. Audit events are durable before the operation that triggered them is acknowledged to the caller — a denied operation that does not show up in the log is worse than a denied operation that does not happen.

The fsync-before-ack rule matters more than it looks. If we ack a privileged operation before its audit event hits stable storage, then a crash between ack and write produces a missing event, and the chain stays intact only because the next event will reference the last successfully written hash. That is fine for liveness but bad for forensics — there is now an undetectable gap. Write-then-ack closes that gap.

mcpm audit verify

One CLI command, no flags by default, verifies the entire chain in the user's audit directory. Algorithm:

  1. Walk audit log files in seq-ascending order (audit-0000001-0099999.jsonl, audit-0100000-0199999.jsonl, ...).
  2. For each record, recompute the canonical hash; compare against the prev_hash stored in the next record.
  3. Verify seq increases by exactly 1 across records and across file boundaries.
  4. Verify ts is monotonically non-decreasing (clock skew protection).
  5. On any mismatch, print the seq, the expected hash, the observed hash, and exit with code 2 (chain broken). On success, print the seq of the first and last records, the terminal hash, and exit 0.

The tool is intentionally simple and offline. No network, no signing key needed. An auditor with the JSONL files and a copy of mcpm (or just jq and sha256sum; we will document the verification recipe in plain text) can reproduce the result. mcpm audit verify --json emits a structured report suitable for ingestion into a SIEM.

Rotation strategy

Rotation cannot break the chain. The rule: rotate by record count, not by file size or time. Every 100,000 records, close the current file and open audit-NNNNNNN-MMMMMMM.jsonl where N is the first seq in the file and M is the last. The first record of the new file still carries the prev_hash of the last record in the previous file, so the chain spans rotations transparently. Old files are never deleted by the daemon; mcpm audit prune --before=2025-01-01 is the user's explicit action, and the prune itself emits an event (event #14 config.change with details {"action": "audit-prune", "before": "..."}) before the files are removed, so the next-generation log retains the breadcrumb that earlier history was discarded.

Storage budget: at average ~500 bytes per record (verified empirically against the schema above), 100,000 records is roughly 50 MB per file. A heavy user generating 1,000 audit events per day will rotate every ~100 days and accumulate ~180 MB per year. Light users will produce ~5 MB per year. Both are within reason; neither needs compression in v1.0. (Compression of rotated-out files is a v1.1 nice-to-have.)

Compliance export format

mcpm audit export --format=json --since=2025-01-01 --until=2025-03-31 --out=q1-2025.json produces a SIEM-friendly file. The JSON variant is an array of records, fields flattened (no nested actor object — instead actor.kind, actor.id, etc. as top-level keys), timestamps in RFC 3339 with explicit Z suffix, and a header object at index 0 with the chain's terminal hash and the verification status at export time. The CSV variant uses the same flattened keys as column headers, with nested details JSON-encoded into a single details_json column (acceptable per OWASP's logging guidance because the structured fields auditors filter on — actor, outcome, event, ts — are first-class columns).

The export also emits a sidecar q1-2025.manifest.json with the export's own SHA-256, the seq range, the source machine identifier (hostname, not a stable user id), and the mcpm version. The manifest is what an auditor signs off on; the JSON/CSV is what their SIEM ingests. This two-file convention matches what FedRAMP assessors expect when they receive evidence packages.

Optional daily anchor (note for v1.0)

One thing I want in v1.0 but will accept as a v1.1 if scope is tight: a daily audit.anchor event that contains the previous day's terminal hash and the record-count range. Users who care about defense-in-depth can configure mcpmanagerd to also write each anchor line to a path of their choosing — a Dropbox folder, an iCloud Drive folder, a private GitHub gist they own. That gives external tamper-evidence without any vendor telemetry: the user themselves is the offsite party. The anchor itself is one extra event per day, ~200 bytes, no integration cost. Specifying it now even if we ship it later means the schema version stays at "1" rather than churning.
