The Sandboxing Veteran's Security

Sandboxing is a gradient, not a checkbox. devenv is reproducibility, not isolation. docker and podman are real sandboxes. uvx and npx are convenience — they isolate packages, not processes. The locked v1.0 modes (devenv | docker | podman | uvx-npx | none) are correct as a set; what matters now is how we wire each mode end-to-end so the user understands what they are buying, and so an attacker can't slip out the side of the weak ones.

I've shipped bubblewrap in distro-managed flatpaks, written SBPL profiles by reading sandboxd reject logs, debugged user-namespace mount loops in nsjail, run gVisor under k8s, and watched a Docker rootless install fail because /etc/subuid didn't have a row for the daemon UID. The instinct that pays off in every one of those: don't trust the label, trust the surface. A mode is only as strong as its weakest invariant — the one nobody documents.

Thoughts: where I'm coming from

The gradient nobody draws

Every sandboxing conversation I've been in eventually devolves into the same equivocation: "we sandbox the server, so it's safe." That sentence is meaningless without the gradient. Here is the gradient I carry around in my head, in plain language:

  1. Convenience — different packages don't trample each other's files, but they share the user's process, FS, and network. uvx, npx, pipx. The Python venv is the canonical example. uv docs are explicit that uvx "isolates" by venv, not by sandbox.
  2. Reproducible — the package's build inputs are pinned by hash, so two invocations produce the same binary, but the running process still has the user's full ambient authority. devenv/Nix lives here. Don't confuse build hermeticity with run-time confinement.
  3. Isolated (process-level) — the process is in its own PID/mount/net/IPC namespace or under a Mach-level sandbox profile. bubblewrap on Linux, sandbox-exec on macOS. The kernel mediates every syscall the process makes.
  4. Hardened (container-level) — the above, plus an explicit image layer with its own root FS, an OCI runtime mediating cgroups/capabilities/seccomp, and a per-container network namespace by default. Docker / Podman rootless.
  5. Microvm / kernel-divorced — gVisor (intercepting syscall layer), Kata (full kernel-per-container), Firecracker. Out of scope for v1.0 but worth naming so we know what we're not claiming.

In v1.0, modes are: none (level 1 at best, often level 0), uvx-npx (level 1), devenv (level 2), docker / podman (level 4). The user must see which level each server runs at. A badge in the TUI. A column in mcpm list. Anything less is misleading.

devenv is not a sandbox. Say it twice.

The Nix store is read-only by virtue of being declared so by convention and by file permissions; a malicious MCP server running inside a devenv shell still has full access to $HOME, can fork, can call connect(2) to anywhere, can read ~/.ssh/id_ed25519. The escape-hatch research page makes this point explicitly — "devenv naked: strong build reproducibility, weak run-time scoping. Acceptable on trusted dev machines but not a default" — and the recommendation summary echoes it: ship devenv-plus-sandbox, not devenv alone. stoic-badger recommendation. I want the v1.0 documentation to repeat this in plain English at the top of the isolation picker.

Modes have priors. Lean on them.

Each mode comes with sensible defaults that v1.0 should bake in instead of asking the user. docker: drop all capabilities, --read-only rootfs, --cap-drop=ALL --security-opt=no-new-privileges, the default seccomp profile, --network=none unless the manifest declares egress, and a tmpfs /tmp. podman: same flags, plus rootless by default. bubblewrap (when we ship it as the wrapper for devenv on Linux): --unshare-all, --die-with-parent, --new-session, PR_SET_NO_NEW_PRIVS, seccomp filter from fd. sandbox-exec: deny default, no exception. Defaults pay rent — they remove an attack surface even when the user accepts every other default.

Verify before launch, not during.

The trust gate fires before the sandbox starts. Signature verification on the package, sha256 pin on the project config, capability declaration check on the manifest — all of those happen in mcpmanagerd's own address space, against material it pulled into its own memory. Once we hand argv to execve, the sandbox is the boundary. There is no "verify inside the sandbox"; the sandbox cannot meaningfully self-verify. This ordering is non-negotiable: TUF verify → manifest schema validate → trust-gate check → derive sandbox policy → fork → drop privileges → exec. Any step out of order is a hole.

Arguments with my four peers

vs. red-team (default-deny, attacker mindset)

Red-team and I agree on the destination — deny by default, allow narrowly — but they keep wanting to push the gradient up one rung universally. "Why is uvx-npx even allowed? It's a level-1 sandbox. Ban it." I push back: a tool that refuses to support how 90% of MCP servers ship today gets uninstalled. The v1.0 isolation picker has to include uvx-npx; what we owe red-team is that the picker label says exactly what they're getting. Mine says: uvx-npx → "package isolation only — full host access". If a user picks that after reading that, we've shifted the responsibility correctly.

Where red-team wins outright: no none mode without an explicit confirmation prompt. none means the manager isn't even wrapping the process — the MCP server runs with the user's full ambient authority. mcpm install for a server whose manifest declares isolation = "none" must show a one-time confirm-by-typing-the-name dialog, not just y/N. And the TUI must badge that server red.

Where we still disagree: red-team wants --network=none as the universal default for docker/podman. I want --network=none unless the manifest declares network = ["api.github.com:443", …], in which case we either run with slirp4netns + nftables egress filter (Linux) or accept that Docker Desktop's bridge gives us host-list-only filtering (macOS). The middle ground is the right place: forcing --network=none would break every server that needs the internet, but the manifest must declare egress before we open it.

vs. crypto-pedant (TUF, ed25519, SHA-256)

Crypto-pedant cares about what we verify. I care about when. They want minisign on registry index, cosign on container images, sha256-pin on project config. Yes, all of it. My only addition: the verification result must be reified into the audit log with the key id and the digest, not just "ok." When a CVE-2025-style supply-chain incident lands on a registry, we need to be able to grep an installed user's audit log for "what version of foo did we actually ship and what key signed it on what date" without re-running the verifier (which by then may be using a rotated trust root).

Where we genuinely disagree: crypto-pedant wants binary code signing on the MCP server binary as well (Apple Developer ID notarization on macOS, gpg-signed Debian packages on Linux). I think that's the wrong layer for v1.0. We sign our binaries (mcpm, mcpmanagerd) because we ship them. The MCP server binaries come from registries we already verified at the index level (minisign + sha256 pin in the lockfile). Layering another signature on the server binary adds operational burden without adding trust — the index already pinned the artifact's sha256 and we already verified that on download. For mode docker/podman, cosign on the image is non-redundant because container registries are a separate trust domain from the MCP index; for uvx-npx, the registry-level signature is what's available and is sufficient.

vs. secrets-architect (keyring, env passthrough)

Secrets-architect and I have to coordinate. They own where the value lives; I own how it crosses the sandbox boundary. The technical-design doc already locks in "secrets never cross a process boundary except via env injection at spawn time" and "mcpmanagerd reads from the keychain and writes to the child server process's env when launching it. The wrapper mcpm exec never sees the value". technical-design.html invariants. That's right, but the mechanism differs per mode and we should write it down per mode:

ModeSecret-injection mechanismWhy this is the cheapest safe option
noneenv on the child via tokio::process::Command::env() directly.No wrapper; secret values live in the parent's memory until execve, never written to disk.
uvx-npxSame as none; the runner inherits env. Manager scrubs PATH to a pinned-runner path.uvx/npx pass env unchanged. Don't write secrets into the uv.lock or npx command line.
devenvdevenv shell --quiet -- env -i PATH=… <named-vars>=… <binary>. Inject via env -i to wipe ambient, then add only the declared list.devenv's own guidance is to load secrets at run-time, not bake them into the shell. devenv secrets guidance.
docker / podman--env-file <path-to-fifo> or repeated --env NAME on the run command. Do not pass -e NAME=VALUE: it shows up in ps on the host. Prefer --env-file /dev/fd/<n> with mcpmanagerd writing once and closing.Container env-file via fd never hits disk; --env NAME (no value) reads from the manager's env, which we control.

One specific disagreement: secrets-architect proposed mounting a tmpfs secrets/ directory into the container with each secret as a file. I reject that for v1.0. Files in a tmpfs are still in the container's view of the FS, so any code in the server that walks /secrets sees the full set; env injection scopes the leak per-var. Use a file-secret mount only when the server can't read env (a small subset).

vs. audit-compliance (log integrity, tamper-evident)

Audit-compliance wants every spawn, every secret read, every sandbox-policy mutation in the audit log with a hash chain. Yes — and the technical-design already commits to JSONL audit at $XDG_STATE_HOME/mcpmanagerd/audit/*.jsonl with daily rotation. technical-design.html state. My only addition for sandboxing: the audit record for server.spawn must include the materialized sandbox policy — the bwrap argv, the SBPL profile sha256, the Docker run flags — not just "spawned foo". A spawn line that says "foo, isolation=docker" is unauditable; one that says "foo, isolation=docker, args=[--cap-drop=ALL, --network=none, --read-only, --tmpfs=/tmp, --env-file=…]" lets a reviewer six months later answer "was this server constrained?". For sandbox-exec, log the profile sha256 and include the resolved -D parameter bindings — those are the actual policy at that moment.

Where we'll fight: audit-compliance wants tamper-evident hash-chained logs (each line includes prev-line-hash). I'm fine with that for v1.0 as long as the chain is append-only and verified at start-up, not as long as we're hashing inside the spawn hot-path. Single-user dev tool, not a SOC — the threat model is "user accidentally rm -rfs the audit log", not "nation-state edits jsonl files in place".

Design: the five-mode gradient, end to end

Comparison table — isolation / egress / FS / escape paths

Mode Isolation level Default network Default FS Escape paths to expect When v1.0 picks this by default
none 0 — process runs as user; no wrapper full host network full $HOME, full FS read any syscall; reads ~/.ssh, ~/.aws; writes anywhere user can; can fork-bomb never — requires explicit user opt-in with confirm-by-name
uvx-npx 1 — venv/package isolation only; runs as user full host network full $HOME, full FS read same as none; venv only stops package collisions, not the running process; CVE-2025-6514-class RCE if version not pinned when no Docker/Podman and no Nix; manifest must declare version = "<exact pin>" or install refuses
devenv 2 — reproducible build; plus bubblewrap on Linux / sandbox-exec on macOS as v1.0 default wrapper shared by default; manifest can declare --unshare-net on Linux or (deny network*) on macOS read-only /nix/store, project dir bind-mounted, tmpfs /tmp, $HOME mostly hidden shared /proc, /dev if we don't unshare carefully; user namespace + setuid binary tricks if we forget --die-with-parent and PR_SET_NO_NEW_PRIVS when user has Nix installed and the package has a profile in our curated library
docker 4 — full OCI: image, rootfs, namespaces, cgroups, capabilities, seccomp --network=none unless manifest declares egress; then bridge + outbound allow-list image rootfs read-only; explicit --mounts only; tmpfs /tmp kernel exploits (gVisor mitigates; we don't ship gVisor); Docker socket exposure (never mount /var/run/docker.sock); CVE in container runtime v1.0 default for new servers if Docker daemon detected
podman 4+ — same as Docker but rootless by default; user namespace always on same defaults as Docker; slirp4netns for user-mode networking same as Docker same as Docker plus rootless-specific (subuid/subgid misconfig, fuse-overlayfs perf cliff); no docker.sock equivalent v1.0 default for new servers if Podman detected and Docker not detected

Default-mode selection algorithm

For a server whose manifest does not pin isolation, mcpmanagerd picks at install time, deterministically: 

fn pick_default_isolation(detected: &Detected, manifest: &Manifest) -> IsolationMode {
    // 1. If the manifest declares it (registry author opinion), respect it.
    if let Some(m) = &manifest.isolation { return *m; }

    // 2. Prefer real sandboxes.
    if detected.docker_running && !detected.docker_desktop_blocked_by_org {
        return IsolationMode::Docker;
    }
    if detected.podman_rootless_ok {
        return IsolationMode::Podman;
    }

    // 3. Fall back to devenv if the user already has Nix.
    if detected.nix_installed && manifest.has_devenv_profile() {
        return IsolationMode::Devenv;  // wrapped in bubblewrap/sandbox-exec
    }

    // 4. Last resort: uvx-npx, but ONLY if version is exact-pinned.
    if manifest.version_is_exact_pin() {
        return IsolationMode::UvxNpx;
    }

    // 5. Refuse to install. Print actionable error.
    panic!("no sandbox available and version not pinned — refusing");
}

This algorithm is the difference between "we shipped a tool that defaults to safe" and "we shipped a tool that defaults to whatever's on the path". The fall-through to refuse-to-install at step 5 is the load-bearing line.

bubblewrap option set (Linux, used inside devenv mode)

The argv mcpmanagerd assembles before spawning a Nix-built MCP server. Comments inline; this is the literal default. 

bwrap \
  # rootfs: tmpfs, then bind only what we need
  --tmpfs / \
  --proc /proc \
  --dev /dev \
  --ro-bind /nix/store /nix/store        \  # Nix store, read-only
  --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --ro-bind /etc/ssl /etc/ssl            \  # TLS roots
  --ro-bind /etc/hosts /etc/hosts        \
  --tmpfs /tmp                           \  # writable scratch
  --tmpfs /var                           \
  --setenv HOME /tmp/home                \
  --dir /tmp/home                        \  # fake $HOME inside

  # project: read-write bind, single path (from manifest.work_dir)
  --bind "$PROJECT_ROOT" /work           \

  # namespaces: unshare everything by default
  --unshare-all                          \
  --share-net=no                         \  # net off unless manifest says yes
  --new-session                          \  # detach from terminal session
  --die-with-parent                      \  # exit when mcpmanagerd does
  --cap-drop ALL                         \
  --seccomp 3                            \  # filter fd 3 (we pass via dup2)

  --                                     \
  /nix/store/<hash>-mcp-server-foo/bin/mcp-server-foo

--die-with-parent is non-optional — without it, an orphaned sandboxed process survives mcpmanagerd crash and we have no UDS path to talk to it. --share-net=no uses the user namespace to drop net; if the manifest declares egress, we add a paired slirp4netns sidecar pinhole instead of --share-net=yes.

sandbox-exec profile template (macOS, used inside devenv mode)

One curated profile per server-shape (filesystem-only, network-only, mixed). mcpmanagerd resolves the profile path from the manifest and binds parameters at launch. 

; /etc/mcp-manager/profiles/mcp-server-default.sb
; Default deny-all, then allow narrowly. Apple deprecated sandbox-exec ~2016
; but it remains functional through current macOS. We carry a contingency
; plan to fall back to Docker on macOS if a future release removes it.
(version 1)
(deny default)
(debug deny)                          ; log denies to sandboxd

; --- execution
(allow process-exec
  (subpath (param "RUNNER_DIR")))     ; e.g. /nix/store/<hash>-mcp-server-foo
(allow process-fork)
(allow signal (target self))
(allow sysctl-read)

; --- filesystem
(allow file-read*
  (subpath "/usr/lib")
  (subpath "/usr/share")
  (subpath "/System/Library")
  (subpath "/Library/Apple")
  (subpath "/private/var/db/dyld")
  (subpath "/dev")
  (literal "/etc/resolv.conf")
  (literal "/etc/hosts")
  (subpath "/private/etc/ssl")
  (subpath (param "RUNNER_DIR")))     ; Nix store path

(allow file-read* file-write*
  (subpath (param "PROJECT_ROOT"))    ; manifest-declared work dir
  (subpath (param "STATE_DIR")))      ; per-server state dir under $XDG_STATE

; --- network: closed unless manifest opens it
; (allow network* (remote tcp "api.github.com:443"))  ; opt-in per manifest

; --- mach IPC: blocked except for log delivery
(allow mach-lookup
  (global-name "com.apple.system.notification_center")
  (global-name "com.apple.system.opendirectoryd.libinfo"))

; --- explicitly deny dangerous niches
(deny mach-priv-task-port)
(deny system-info)
(deny user-preference-read user-preference-write)

Invocation: 

sandbox-exec \
  -f /etc/mcp-manager/profiles/mcp-server-default.sb \
  -D RUNNER_DIR=/nix/store/<hash>-mcp-server-foo \
  -D PROJECT_ROOT=/Users/me/projects/foo \
  -D STATE_DIR=/Users/me/Library/Application\ Support/mcp-manager/state/foo \
  /nix/store/<hash>-mcp-server-foo/bin/mcp-server-foo

A deprecation warning prints to stderr on each invocation. mcpmanagerd swallows that line and emits a single audit-log entry at start-up noting the API status; no warning per spawn. If a future macOS removes sandbox-exec we degrade to Docker (with an alert), per the stoic-badger contingency. stoic-badger recommendation, sandbox-exec contingency.

Docker / Podman run flag template

The exact flags mcpmanagerd composes for isolation = "docker". Podman accepts the same set verbatim. The manifest can override individual flags but cannot weaken the security defaults below without an explicit allow_dangerous = true in the manifest (audit-logged). 

docker run \
  --rm \
  --read-only \                          # rootfs read-only
  --tmpfs /tmp:rw,nosuid,nodev,size=64m \
  --tmpfs /run:rw,nosuid,nodev,size=8m  \
  --cap-drop ALL \                       # no capabilities by default
  --security-opt no-new-privileges:true \
  --security-opt seccomp=default \       # Docker's default seccomp filter
  --pids-limit 256 \
  --cpus 1 \                             # mirrors Docker MCP Toolkit defaults
  --memory 2g \
  --user "$(id -u):$(id -g)" \           # never root inside
  --network none \                       # default; opened only if manifest declares
  --env-file /dev/fd/3 \                 # secrets via fd, never in argv or ps
  --mount type=bind,src="$PROJECT_ROOT",dst=/work,readonly=false \
  --label "mcp-manager.server=$NAME" \
  --label "mcp-manager.spec=$SPEC" \
  --name "mcpm-$NAME-$EPHEMERAL_ID" \
  "$IMAGE@$SHA256_DIGEST"                # always pinned by digest, never tag

Critical lines: --user $(id -u) (never run as root in the container, even rootless Docker), --mount instead of -v (explicit dst, type, ro flag), digest pin instead of tag (tag is mutable, digest isn't), --env-file /dev/fd/3 (the manager writes secrets to fd 3 and closes; the value never appears in docker inspect, never in ps, never on disk).

For Podman, replace docker with podman; on Linux this gives us slirp4netns user-mode networking automatically. Capability set is 11 default (vs Docker's 14) — we drop ALL anyway so this only matters if the manifest adds back specific caps. Podman rootless.

IPC auth across the sandbox boundary

The technical-design locks in UDS at $XDG_RUNTIME_DIR/mcpmanagerd.sock with SO_PEERCRED auth. technical-design.html wire protocol. The question for sandboxing: does SO_PEERCRED work across the sandbox boundary?

  • none / uvx-npx: same UID, same kernel, SO_PEERCRED returns the real UID. Works.
  • devenv (bubblewrap or sandbox-exec): same UID — bubblewrap inherits the user namespace by default, and sandbox-exec doesn't change credentials. SO_PEERCRED works. We just need to bind-mount the socket path into the sandbox (Linux: --bind $XDG_RUNTIME_DIR/mcpmanagerd.sock /run/mcpmanagerd.sock; macOS: SBPL (allow file-read* file-write* (literal "<sock-path>"))).
  • docker / podman: the container has its own UID namespace by default. Inside the container, id -u may be 1000 (mapped); outside, the kernel sees the host UID mapping. SO_PEERCRED on the host side returns the host UID, which we control because we set --user $(id -u). ✓ But: the socket must be mounted into the container. Mount it at a stable in-container path (/run/mcpmanagerd.sock) and tell the in-container MCP server to connect there.

Failure mode to handle: if a user runs --user root in the container (overriding our default), the host kernel sees host UID 0 over the bind-mounted socket, which doesn't match the manager's real UID, and we (correctly) reject. Audit: auth.failed.

Trust model end-to-end

Sequence diagram in prose, because the ordering is the whole point. For an mcpm install foo:

  1. Fetch index. mcpmanagerd downloads the registry index. mcpm-trust verifies the minisign signature against the baked-in root pubkey. technical-design.html mcpm-trust. Failure → abort, no sandbox launched yet.
  2. Resolve version. Manifest range ("^0.4") → exact version + sha256 from the lockfile. Both stored in lockfile.
  3. Download artifact. For uvx-npx: pin foo@1.2.3; PyPI/npm sha256 checked. For docker: pull by digest, not tag; cosign verify-blob against the publisher's pubkey if declared. For devenv: Nix store path is content-addressed by hash — sha256 verification is intrinsic.
  4. Validate manifest. Schema check (isolation ∈ five known modes; declared egress is well-formed; mounted paths are absolute and under $HOME).
  5. Project trust gate. If launching from a project scope, mcpmanagerd reads ~/.config/mcp-manager/trust.toml and compares sha256(.mcp-manager.toml). Mismatch → prompt user. technical-design.html trust file.
  6. Derive sandbox policy. From manifest + mode-default → bwrap argv / SBPL profile / docker flags.
  7. Audit-log decision. Single JSONL entry: server.spawn with {name, version, sha256, isolation, sandbox_policy_digest, secrets:[names], egress:[...]}.
  8. Spawn. execve after dropping privileges. Secrets injected via env at this moment, after the fork.

Step 5 is the trust gate for project configs. Step 1 is the trust gate for packages. Step 6 turns the validated material into a policy. Steps 1–6 must complete before step 8. No exceptions, no "run unsandboxed and verify in the background." The sandbox is the boundary; the boundary is set before execve or it isn't a boundary.

First-launch security prompts

The UX of sandboxing is half the security. Three prompts I want, exactly:

  1. On first mcpm install ever: a one-time onboarding screen explains the gradient (level 1 → level 4), shows what mcpm detected on the user's machine (Docker yes/no, Podman yes/no, Nix yes/no), and asks "default mode for new servers when manifest doesn't specify?". Default selection is the highest level we detected. The user can change this later via mcpm config set default_isolation.
  2. On installing a server with isolation = "none" or "uvx-npx" when stronger is available: warning panel showing "this server has full host access. If you wanted Docker, install Docker and re-run". Confirm by typing the server name. Logged.
  3. On --docker-enable=true for a previously non-Docker server: nothing scary — moving up the gradient is always fine. Just re-pull the image, re-derive the sandbox policy, re-spawn.

Binary code signing of our own binaries

Crypto-pedant covers the per-package side; my side is the mcpm and mcpmanagerd binaries themselves. On macOS: Developer ID signed + notarized, hardened runtime, library validation. On Linux: detached minisign signature next to the release tarball, sha256 in the release notes. Reproducible builds on Linux (Nix builds the binary) so any user can verify the sha256 themselves.

Supply-chain pinning

  • Cargo: Cargo.lock committed; cargo audit in CI on every push.
  • Container images: digest pin in the lockfile (never tag). cosign verify-blob in the install path. Docker rootless.
  • npm/PyPI for uvx-npx: registry index signature (minisign) over the index of (name, version, sha256); per-package sha256 verified after download. Refuse install if version is not exact-pinned. This is the single biggest delta from the status-quo "npx latest" anti-pattern (CVE-2025-6514 class). mcp supply-chain.
  • Nix store: content-addressed by definition; no extra signature layer required.
  • Our own deps: cargo deny for license + advisory checks; pinned rust-toolchain.toml; reproducible release builds.
