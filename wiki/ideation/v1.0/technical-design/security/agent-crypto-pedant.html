The Crypto Pedant's Security

ed25519 + SHA-256 + HMAC-SHA-256. No hand-rolled crypto. Algorithm-agility envelopes so we can rotate primitives without re-cutting binaries. Replay protection by construction. TUF-lite that documents exactly which TUF roles we omit and why. Key rotation as a planned operation, not a fire drill.

ed25519 (RFC 8032) SHA-256 (FIPS 180-4) HMAC-SHA-256 (RFC 2104) TUF reference spec minisign · cosign · sigstore

Thoughts

The pedantry, plainly

The v1.0 spec made the only two big calls correctly: it picked an established asymmetric primitive (ed25519 via minisign[1]) and a Merkle-ish trust manifest (TUF-lite[2]). That's the part I don't have to argue. What I do have to argue is that the spec is silent on the details that distinguish a system the EFF would link to from a system that gets a CVE in eighteen months: signing-envelope schema, replay window, canonical encoding of the bytes you're signing, algorithm-agility, and a written key-rotation runbook. Those are five places where amateurs lose and where the literature has unambiguous answers.

The Latacora rule

If it's not in "Cryptographic Right Answers,"[3] we don't ship it. That's not a rhetorical flourish — it's a checklist. The current Latacora answers for the operations we need are: ed25519 for signing, SHA-256 (or SHA-512/256) for hashing, HMAC-SHA-256 for MACs, ChaCha20-Poly1305 or AES-GCM for authenticated encryption, and Argon2id for password KDF. We use those exact primitives or we have a written justification for the deviation. We do not invent. We do not "improve." If a future Latacora update flips an answer, we have the algorithm-agility envelope ready to flip with it without a wire-format break.

The TUF-lite caveat the spec elides

"TUF-lite" sounds harmless but it is a load-bearing claim. Full TUF[2] defines five top-level roles — root, targets, snapshot, timestamp, plus optional delegations — each with a separate keypair, separate threshold, and separate expiration. Each role exists to defend a specific attack: root rotates keys; targets authorizes file hashes; snapshot defends against mix-and-match attacks; timestamp defends against freeze attacks. v1.0 collapses these into a single signed trust.toml. That is a defensible choice for our threat model (one publisher, low-frequency updates) only if we explicitly enumerate which attacks we accept. I want that enumeration in the docs, not implied by silence. A future v1.1 should add at minimum a separate timestamp role (a short-lived second signature attesting "this trust.toml was current as of X") because it is cheap and shuts down freeze attacks completely.

Replay, freshness, and the offline edge

Every signed manifest we issue MUST carry both signed_at (timestamp) and expires_at (TTL ceiling). The verifier checks now < expires_at and emits a warning if signed_at is older than the configured staleness threshold. The v1.0 spec mentions "7-day TTL" but doesn't name the field that carries it nor specify the precise verifier behavior. We need: parse → verify signature → verify now >= signed_at - skew → verify now < expires_at → verify version > previous_version. All four checks. The last one — monotonic version — is the one teams forget, and it is exactly what defends against an attacker replaying an old-but-still-valid trust.toml that contains a since-rotated-out compromised key.

Hand-rolled primitive count: target zero

I have read enough security postmortems[4] to set an internal budget: zero bytes of custom cryptographic code in v1.0. Every primitive is a thin Rust binding around an audited C library or a maintained pure-Rust crate. Specifically: minisign-verify[1] for ed25519 + BLAKE2b (its built-in pre-hash); sha2 (the RustCrypto crate) for SHA-256; ring (or the OS keychain) for HMAC; secrecy + zeroize for in-memory carriers. If we ever need to verify a cosign signature, we shell out to the cosign binary[5] rather than try to reproduce its verification logic ourselves. Subprocess invocation is fine; "I'll write a quick X.509 parser" is not.

Arguments

vs. red-team

We agree more than we differ. Red-team wants default-deny on every interface; I want default-deny on every cryptographic decision. Where we'll friction: red-team will probably push for fail-closed on every trust manifest staleness, on the grounds that a fail-open verifier is an attacker's playground. I'm sympathetic, but a strict fail-closed posture turns "user's laptop spent the weekend offline" into "every mcpm command errors out." The pedant's compromise is fail-soft on the cache, fail-closed on the install:

  • If trust.toml is stale (past expires_at) but we already have it cached, we still honor it for read-only operations (mcpm list, mcpm exec) and emit a structured warning.
  • If trust.toml is stale and the user runs mcpm install or mcpm update — operations that change trust state — we refuse and tell them to run mcpm trust refresh.
  • If trust.toml is past expires_at + grace_window (default 30 days), we refuse all signature verifications. This is the "the publisher has been silent for a month; something is wrong" tripwire.

The other place red-team will push: no exceptions for the baked-in-fallback mode. I'll defend an exception specifically for first-launch offline use because the alternative is unusable: a brand-new mcpmanagerd binary already contains the publisher's ed25519 root pubkey (embedded at compile time, in const ROOT_PUBKEY: [u8; 32] = …), so accepting the baked-in pubkey set is exactly accepting the binary you already trusted enough to execute. The TOFU window collapses to "you ran the installer." We log [root].mode = "baked-in-fallback" and warn every CLI invocation until the first successful refresh — that's the visible UX cost that keeps users honest.

vs. sandboxing-veteran

Sandboxing-veteran will tell us that no amount of cryptography saves us from a malicious MCP server that we cryptographically verified, signed by a publisher who just turned hostile. I agree. Cryptography says who; sandboxing says what. They're orthogonal layers and we need both. Where I'll push back is on the temptation to use cryptographic primitives inside the sandbox to do things they don't need to do — e.g., signing inter-process messages between mcpmanagerd and a sandboxed server, which adds latency, key-management complexity, and a new key-storage surface without buying real protection (the kernel already isolates these processes via UID and the bubblewrap mount namespace[6]). The UDS socket with SO_PEERCRED is the right primitive; HMACing every JSON-RPC frame would be cargo-culted-from-network-protocols crypto and we shouldn't do it.

One area where we genuinely overlap and should coordinate: seccomp profiles must be content-addressed. If a server's sandbox policy is stored on disk (rather than synthesized at runtime), its hash goes into the lockfile alongside the package checksum so a swapped-out policy file is detected as a tamper event. That's a sandboxing concern but it lives in the trust-and-hashing layer, which is mine.

vs. secrets-architect

Secrets-architect will own the keyring trait and the in-process secret carriers; I won't fight on those boundaries. Where I will pedant: what cryptography is the OS keyring using under the hood, and do we trust it?

  • macOS Keychain: items stored in the user keychain are encrypted with AES-256 under a key derived from the user's login password via PBKDF2-HMAC-SHA256 (with a per-keychain salt) and protected by the user keychain's auto-locking behavior[7]. That's defensible. The pedantic concern is: what's the per-item access ACL? We must set kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly — never kSecAttrAccessibleAlways, never iCloud-synced.
  • Linux libsecret / GNOME Keyring: the default backend uses AES-128-CBC + HMAC-SHA256, with the master key derived from the user's login password via PBKDF2-SHA256. Newer KWallet uses BlowFish (we should warn). The pedantic concern: if the user runs headless (no GNOME session, no D-Bus), libsecret falls through to "in-memory only" or fails outright. Our keyring backend must detect headless and refuse to start rather than silently storing secrets in /tmp.

Secrets-architect will probably propose env-var passthrough as a graceful-degradation mode for headless Linux. I'll accept that only with a startup-time audit-log entry secret.backend.degraded so the operator knows the keyring is not in use. Silent degradation is how secrets end up in shell history.

vs. audit-compliance

Audit-compliance will want a tamper-evident audit log; I want the same thing. We will negotiate one thing: which hash algorithm. I want SHA-256. Audit-compliance might propose SHA-512 for "more bits" or BLAKE3 for speed. Both are reasonable, but the pedant's reasoning chooses SHA-256:

  • SHA-256 is FIPS 180-4[8] and is the algorithm in every compliance framework I will ever be audited against.
  • SHA-512 buys us nothing at our scale (a few thousand events/day per user). The audit log is not a content-addressable store for petabytes of objects.
  • BLAKE3 is faster but its standardization story is weaker. We don't have a throughput problem; we have an explainability problem. SHA-256 explains in one line.

The hash-chain construction itself: each line e_n includes prev_hash = SHA-256(canonical_json(e_{n-1})). The first line of each daily file includes the previous day's terminal hash as prev_day_hash. That gives us cross-file tamper-evidence without requiring a single forever-growing file.

Where audit-compliance and I might diverge: they may want every audit line individually signed. I'll argue against that for v1.0 — the per-line ed25519 verification cost (~50µs) is fine, but the key would have to live in mcpmanagerd's process memory continuously, which is a new attack surface. Instead: sign the terminal hash of each daily rotation file when it closes (one signature per day, embedded in the next day's first record). That gives us tamper-evidence without a live signing key.

Design

TUF-lite spec — exactly what we keep and what we omit

Full TUF[2] defines four mandatory roles. We collapse them and we say so out loud:

TUF rolePurposev1.0 statusDeviation note
root Holds the public keys of all other roles; rotates trust Kept, but combined v1.0 trust.toml's [root] table holds the single publisher ed25519 pubkey. Rotation requires a new signed trust.toml whose old signature still verifies and whose root_pubkey field has changed. Clients must accept the new root iff (a) the file is signed by the old root, (b) version is monotonic, (c) within freshness window.
targets Authorizes file hashes (packages) Kept, in the same file Per-package signatures (minisign or cosign) live alongside each package. The trust.toml binds which registries are authoritative; per-package .minisig files bind which package bytes are authentic. Two-layer trust.
snapshot Pins the current set of versioned metadata files; defends against mix-and-match Omitted in v1.0 We have one metadata file (trust.toml) so there is nothing to mix-and-match between. If a future version splits trust into multiple per-registry files, we MUST add a snapshot role to bind them.
timestamp Short-lived signed assertion of "this is current"; defends against freeze attacks Omitted in v1.0; planned for v1.1 Today, freeze attacks are mitigated only by the 7-day TTL on trust.toml. An attacker who controls the network can serve an old-but-valid trust.toml for up to its TTL. v1.1 will add a separately-signed timestamp.toml with hours-to-days TTL pointing at the current trust.toml's hash.
delegations Lets targets delegate to sub-publishers Omitted, no planned addition Single-publisher model. If we ever federate, we revisit.

Threats v1.0 TUF-lite does defend:

  • Arbitrary key trust (you cannot trust a registry pubkey not in trust.toml).
  • Tampered package bytes (per-package .minisig verification at install time).
  • Rollback to an older trust.toml (monotonic version check).
  • Indefinite serving of a stale trust.toml (7-day TTL with hard refusal after 30-day grace).
  • Key compromise once detected (rotation: publish a new trust.toml signed by the old key but with a new root_pubkey; clients with the old key validate the rotation and switch).

Threats v1.0 TUF-lite does not fully defend:

  • Freeze attack within TTL window: an attacker who controls the network can pin clients to a known-stale trust.toml for up to 7 days. Mitigation: timestamp role in v1.1; until then, the TTL is the bound.
  • Mix-and-match attacks: not applicable in v1.0 (single metadata file). Becomes applicable in v1.1 if we split files.
  • Key compromise before detection: standard limitation of any signing system. Mitigated by short-lived keys and out-of-band revocation channel (the revoked_keys field, see below).

Algorithm-agility signing envelope

Every signature in the system uses the same envelope. This is the single most important pedantic intervention: it costs nothing today and saves a wire-format break the day NIST deprecates ed25519 in favor of ML-DSA[9]. 

{
  "v": 1,
  "alg": "ed25519",            // explicit algorithm identifier
  "key_id": "mcpm-root-2026a", // who signed (matches a key in trust.toml)
  "signed_at": "2026-05-24T14:33:01Z",
  "expires_at": "2026-05-31T14:33:01Z",
  "payload_hash": "sha256:9f4e2d…",  // hash of canonical-JSON(payload)
  "payload_hash_alg": "sha256",      // explicit hash algorithm
  "sig": "<base64 ed25519 signature over the canonical-JSON of all above fields except `sig`>"
}

Two layers of agility:

  1. Signature algorithm agility via alg: today "ed25519"; tomorrow possibly "ed25519ph" (pre-hashed), "ml-dsa-65", or a hybrid scheme. Verifier dispatches on alg from a static allowlist baked into the binary.
  2. Hash algorithm agility via payload_hash_alg: today "sha256"; future possibilities "sha512-256", "sha3-256". Lockfile checksums use the same string prefix (e.g., "sha256:9f4e2d…") so any future migration is a per-record opt-in.

The allowlist matters. A verifier that accepts any alg string the message claims is the textbook "alg=none JWT" bug[10]. Our allowlist for v1.0 is exactly ["ed25519"]; "none", "hmac-sha256", and unknown values are rejected with a structured error and an audit-log entry signature.alg.rejected. The keyset is tied to the algorithm: the trust.toml stores each key with its alg field, and the verifier requires envelope.alg == key.alg.

Canonical JSON for hashing — the one no one gets right

"Hash this JSON" is ambiguous because JSON has multiple valid serializations of the same logical value (key order, whitespace, number formatting, escape choices for non-ASCII). If two implementations disagree on serialization, signatures verify on one platform and fail on another. We pin a single canonical form and document it. The closest existing standard is JCS (JSON Canonicalization Scheme, RFC 8785[11]), which we adopt.

JCS in one paragraph (the rules we implement):

  • Object keys sorted in code-point order (UTF-16 code units).
  • No insignificant whitespace.
  • Numbers serialized per ECMAScript Number.prototype.toString(): integers in plain form, floats in shortest-round-trip form, no leading zeros.
  • Strings escaped per RFC 8259 §7 with only the minimum required escapes (\b \f \n \r \t \" \\ and \uXXXX for control characters < U+0020).
  • No trailing newline. UTF-8 output.

For TOML (canonical config), we don't hash the TOML directly — we hash the parsed value re-serialized as canonical JSON. That's important: TOML formatting (comment placement, key ordering, table style) is preserved by toml_edit for human round-trips, but for the hash we need a unique encoding. The v1.0 spec's prior_hash field for config.put CAS and the lockfile's checksum field both use this rule: hash = SHA-256(canonical-JSON(parsed-TOML)).

The trust-gate hash for project configs follows the same construction. trust.toml's per-project config_hash = SHA-256(canonical-JSON(parsed(.mcp-manager.toml))). This means a user who only re-orders sections in their .mcp-manager.toml doesn't trigger a re-prompt; a user who actually changes semantics does.

Key rotation timeline (the runbook, written in advance)

The single biggest failure mode I see in projects that "have a signing key" is that the key has been on one person's USB drive for three years and nobody has ever tested a rotation. We pre-commit a written rotation schedule:

EventCadenceProcedure
Routine root-key rotationEvery 12 monthsGenerate mcpm-root-YYYYa on an offline machine; sign new trust.toml with the outgoing key listing both old and new pubkeys; clients accept the rotation; after 90 days, publish trust.toml that drops the old key.
Routine package-signing-key rotationEvery 6 monthsGenerate mcpm-pkg-YYYYqN; sign new trust.toml listing it; old key valid for verifying historical packages; new packages signed with new key.
Emergency rotation (suspected compromise)Within 24h of detectionAdd compromised key_id to revoked_keys array in trust.toml; publish new trust.toml signed by an uncompromised key; binary release with shortened TTL (24h) until normal cadence resumes.
Catastrophic rotation (root key lost / compromised)Within 7 daysOut-of-band publication on GitHub release + website + Discord with new baked-in pubkey; users must reinstall from the curl script. This is the unavoidable cost of a single-root design; mitigated only by adding a threshold-signing setup in v2.0+.

Threshold signing for v2.0+ consideration. A single root key is a single point of failure. The TUF spec supports m-of-n threshold signing for every role[2]. We aren't doing it in v1.0 (operational complexity is real and we don't yet have a second trusted publisher), but the envelope schema's sig field is deliberately string-typed rather than fixed-length so a future schema can carry sig: ["base64sig1", "base64sig2"] with a threshold field in the corresponding key entry. The wire format won't break.

Key escrow. We will not escrow the root key with a third party — that's a phishing target. We will hold the root key offline on an air-gapped machine controlled by the maintainer, with a paper backup in a sealed envelope. This is identical to the operational posture of TUF's reference deployment for PyPI[12].

Revocation. trust.toml carries a revoked_keys array (list of key_id strings). A signed manifest whose key_id appears in revoked_keys is rejected even if the signature itself verifies. Revocation entries are sticky — once added, they never disappear from trust.toml (they accumulate). Clients with an old trust.toml that doesn't list the revocation are still protected by the freshness window — they can't be exploited indefinitely.

Secrets at rest — what the keyring is actually doing

I owe this section because secrets-architect will write the keyring trait but my section enumerates the cryptography happening one layer below. The user must be able to answer "what protects my GITHUB_TOKEN if my laptop is stolen?" without us shrugging.

PlatformBackendKDF (login → master)Item encryptionLock state
macOSKeychain Services (login keychain)PBKDF2-HMAC-SHA256 over login password[7]AES-256 (envelope) — per-item key wrapped by keychain master keyLocks on logout / sleep / configurable timeout
Linux (GNOME)gnome-keyring via libsecretPBKDF2-SHA256 (default 100k iterations)AES-128-CBC + HMAC-SHA256 (encrypt-then-MAC)Locks when D-Bus session ends
Linux (KDE)KWallet via libsecretHash chain over login password (weaker)BlowFish (legacy) or AES-256 (newer)Per-wallet timeout
Linux (headless)None safe———

Pedantic conclusions:

  • On macOS, set kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. Never kSecAttrAccessibleAlways. Never iCloud Keychain sync (we don't want our secrets in your other devices' keychains without consent).
  • On Linux, prefer GNOME keyring; KWallet acceptable; detect headless and refuse with a clear error (error: no secret backend available; install gnome-keyring or libsecret-1-0, or set MCPM_ALLOW_ENVVAR_BACKEND=1 to use env-passthrough mode).
  • In-process: every plaintext secret travels in secrecy::SecretString[13]. The Drop impl zeroes the backing memory. No Debug, no Display, no Serialize for the inner bytes.
  • At the spawn syscall boundary, we set the env-var via Command::env and immediately drop the SecretString. The child process inherits the env; our address space loses the bytes within microseconds.
  • We never write a secret to swap-space. mlock(2) the SecretString backing buffer? In v1.0 no — most users run without elevated capabilities. In v1.1 we can add mlock as a feature flag for users who have RLIMIT_MEMLOCK headroom.

Audit hash chain (SHA-256, daily rotation, terminal-signature)

Each audit-log line is a JSON object. The bytes that land on disk are minified JSON, one record per line (JSONL). The hash construction: 

// line N of file YYYY-MM-DD.jsonl
{
  "v": 1,
  "ts": "2026-05-24T19:15:02.413Z",
  "event": "server.spawn",
  "actor": { "kind": "client", "id": "zed-1.234.5", "pid": 84219 },
  "server": "github-mcp",
  "outcome": "ok",
  "details": { "singleton": true, "client_id": "shared" },
  "prev_hash": "sha256:<hash of canonical-JSON of line N-1, or "genesis" if N=0>",
  "seq": N
}

Verification: walk the file from line 0 to line N, recomputing prev_hash for each. Any mismatch indicates tampering (or corruption). At rotation time (midnight UTC), mcpmanagerd:

  1. Closes the current day's file.
  2. Computes terminal_hash = SHA-256(canonical-JSON(last_line)).
  3. Signs terminal_hash with an audit-only ed25519 key (separate from package signing, kept in OS keyring, generated on first start).
  4. Writes line 0 of the next day's file with prev_day_hash = terminal_hash and prev_day_sig = <base64 sig>.

This buys cross-file tamper evidence with a single signing operation per day. The signing key lives in the keyring (the same one storing user secrets, in its own namespace dev.mcp-manager.audit-key/private) so it's not in process memory continuously. We could go further (sign every record) but the cost/benefit isn't there at v1.0 scale. The current design lets a forensic auditor say: "the chain from day X to day Y is intact and each daily rotation's terminal hash is signed by a key the user can verify against the keyring's audit-key entry."

Supply-chain pinning — Cargo.lock and the canonical entry hash

Our own binary is built reproducibly from a Cargo workspace. Reproducibility requires that Cargo.lock pins every transitive dependency by exact version and SHA-256 of the published crate tarball. cargo does this for us. Where we layer in extra protection:

  • Vendored or pinned Cargo.lock in releases. Each release tarball ships its Cargo.lock alongside the binary. Users (or distros) building from source can verify they used the exact dep set we used.
  • cargo-vet or cargo-deny in CI[14]. cargo-vet requires a human-recorded review for every dependency upgrade; cargo-deny enforces license and CVE policies. For the v1.0 dependency set (around 200 transitive crates), the one-time setup of cargo-vet is a weekend; the ongoing cost is one extra review note per dep bump.
  • SBOM emission. Every release publishes a CycloneDX SBOM file (auto-generated by cargo-cyclonedx) listing every dep, its version, its license, and its checksum. This is the file SREs and security teams will ask for.
  • No build.rs code execution at install time. We compile to a single static binary; users never run cargo build. The build-time supply-chain attack surface is moved entirely to our CI environment, which is isolated and minimal.

For runtime-fetched dependencies (Python via uvx, Node via bun): we depend on the upstream package manager's own integrity guarantees. uvx pins by hash via the lockfile mechanism; bun does the same. We re-verify the final package tarball against the registry's per-package .minisig file before handing it to uvx/bun. Belt-and-suspenders.

Binary code signing

Distinct from package signing. This is "is the mcpmanagerd binary itself authentic?"

  • macOS. Apple Developer ID signature + notarization[15]. Without notarization, Gatekeeper refuses to launch from a curl install. The notarization ticket is RSA-2048 + SHA-256 under the hood (not our choice, Apple's). Worth noting in our docs that this is one place where the algorithm choice is Apple's, not ours.
  • Linux. ed25519 via minisign on the release tarball. The publisher key is the same one that signs trust.toml (or a separate mcpm-release-YYYYqN key — actually, separating release-signing from trust-signing is good hygiene; let's do separate keys). Both .tar.gz and SHA256SUMS are signed. Users can verify with minisign -V -P <pubkey> -m mcp-manager-1.0.0-x86_64-unknown-linux-gnu.tar.gz. The installer script does this automatically against the baked-in pubkey[16].
  • Why ed25519 over RSA-PSS for Linux? Smaller keys, faster verification, no parameter footguns (no choice of padding scheme, no hash-function choice, no MGF1 misconfig). ed25519 has exactly one mode of operation. RSA has dozens, half of which are broken in subtle ways. Latacora[3] says ed25519; we say ed25519.

IPC auth and the cryptographic root-of-trust prompt

The IPC layer is one of the few places I think the v1.0 spec is exactly right. SO_PEERCRED (Linux) and LOCAL_PEERCRED (macOS) gives kernel-attested UID; we trust the kernel; no shared secrets exchanged. There's no cryptography in the IPC layer at all, and that's the correct outcome. I would not introduce HMAC framing, channel binding, or per-connection nonces — they would add complexity and attack surface without addressing any real adversary model in a single-user setting.

The one cryptographic UX moment that matters: first launch. The user's first mcpm init establishes the root of trust. We need a prompt that is honest about what's happening without being incomprehensible. Draft text: 

$ mcpm init

mcp-manager establishes a chain of trust:
  - The binary you just ran is signed by the mcp-manager publisher key.
  - That key authorizes the registry pubkeys baked into this binary.
  - Those registry pubkeys authorize the MCP server packages you install.

Publisher key fingerprint (baked in this binary):
  RWQf6LRCGA9i23aNZqKEDxzZ6bC8x4Pw…  (ed25519, key_id mcpm-root-2026a)

You can verify this fingerprint matches the one on:
  https://mcp-manager.dev/keys/2026a

Proceed? [Y/n]

Three honest things in that prompt: (1) we name the fingerprint, not just "a key"; (2) we name the algorithm; (3) we point to an out-of-band verification channel (the website over HTTPS). The user who skips verification at least knows what they skipped. Power users can compare the fingerprint against a GPG-signed announcement we make to the GitHub releases page.

Putting it all together

Eight crypto primitives, all standard, all bound by explicit envelopes:

  1. ed25519 (RFC 8032[17]) — every signature: trust manifest, per-package, audit terminal-hash, binary release.
  2. SHA-256 (FIPS 180-4[8], RFC 6234[18]) — every hash: lockfile checksum, prior_hash CAS, audit chain, config trust gate.
  3. HMAC-SHA-256 (RFC 2104[19]) — keyring internals (libsecret); we don't construct HMACs ourselves but require the keyring backend to use HMAC-SHA-256 or stronger.
  4. PBKDF2-SHA256 / Argon2id — keyring login-password derivation (OS-provided; we don't choose this but document it).
  5. AES-256-GCM — OS keyring item encryption (OS-provided).
  6. BLAKE2b — minisign's pre-hash (transparent to us; minisign builds it in).
  7. JCS (RFC 8785[11]) — canonicalization of every signed payload.
  8. X.509 / RSA-2048 — macOS notarization (Apple's choice, not ours).

Every one of those has a published specification, multiple audited implementations, and a known threat model. We sit at the top of the stack and compose them; we never reach inside.

Three properties any future contributor must preserve:

  • Algorithm names appear in signed messages. Never trust a verifier that picks the algorithm from context.
  • Timestamps and expirations appear in signed messages. Never trust freshness from the transport.
  • The bytes we hash are canonical. JCS for JSON, parse-then-canonicalize for TOML, no string-concat hashing of structured data.

If we hold the line on those three, every other security claim in this document degrades gracefully when something inevitably surprises us.
