The Red Team's Security

Default-deny everywhere. The malicious MCP in a freshly-cloned project is not a hypothetical — it is the median case once this tool ships. The user who installed github-mcp from a typo-squatted registry, then opened a colleague's repo with a hostile .mcp-manager.toml, should still finish the day with ~/.ssh/id_rsa intact, ~/.aws/credentials intact, no out-bound exfiltration, and a tamper-evident audit trail showing exactly what was attempted. Anything less is a CVE waiting for a Mastodon post.

Thoughts

What v1.0 actually ships, threat-model-wise

A daemon that runs as the user, that can read every file the user can read, that can spawn arbitrary third-party code (MCP servers) which themselves request access to LLMs, local filesystems, shell, and sometimes network endpoints. That daemon mediates secrets out of the OS keychain and injects them into child processes as environment variables. The threat surface is not "is mcpmanagerd itself exploitable?" — that's the easy half. The hard half is: the MCPs are the attacker. Treat them as a hostile contractor's binary, because they are.

The v1.0 spec gets a lot right — TUF-lite registry signing, direnv-style project trust gates, SO_PEERCRED on the UDS, secrets only via env at spawn, no plaintext on disk outside the keychain. But the spec under-specifies the defaults that decide whether this product is "secure if you read the docs" or "secure if you do nothing." Those are different products. The latter is the only one worth shipping.

The bit nobody likes to say out loud

The MCP ecosystem in 2025–2026 looks like the npm ecosystem in 2014: trivially easy to publish, no meaningful identity, install commands that pipe into your shell. The recent CVE-2025-6514 in the mcp-remote proxy [1] — a remote-code-execution bug triggered by simply connecting to an untrusted MCP server — is not an outlier. It is the median case of a fast-moving ecosystem where security has been an afterthought[2]. We are downstream of all of that. Our threat model has to assume the package we just installed is hostile, not friendly-and-buggy. Friendly-and-buggy is a special case of hostile that happens not to have noticed yet.

The three doors we have to lock

  1. Inbound supply chain. Where do MCP packages come from, who signed them, what does "verified" mean operationally, and what happens when a maintainer's signing key is compromised? TUF-lite + minisign covers this if we get rotation right[3]. If we don't get rotation right, we have crypto-theatre.
  2. Project-config trust. A user clones a repo. The repo contains .mcp-manager.toml listing 14 MCPs and 6 registries. Right now, on the v1.0 design, what does mcpmanagerd do? The direnv pattern[4] is the correct answer — refuse to load anything until the user explicitly trusts a sha256 of the file — and I want to make sure it stays the correct answer when a UX person argues "this is annoying, can we autoload on `cd`?". No. The answer is no.
  3. Run-time isolation. The MCP is running. It is now the attacker. Can it read ~/.ssh/id_rsa? Can it open a socket to evil.example.com and exfiltrate? Can it read another MCP's secret? Can it write to ~/.bashrc? Every one of these answers must be "no by default; yes only when the user has opted in per-server, per-capability."

The threat-model document is the deliverable

We need docs/security/THREAT_MODEL.md as a first-class shipped artifact, not a wiki page that drifts. STRIDE per component[5], an attack tree per asset[6], and a mapping of every mitigation to a CI-enforced test. If we cannot test the mitigation, the mitigation is aspirational and should be labeled as such. The OWASP threat-modeling guidance[7] is the discipline we adopt. Shostack's "four-question framework" — what are we working on, what can go wrong, what are we going to do about it, did we do a good job? — is how we structure the doc[8].

What I keep finding myself arguing for

  • Isolation is on by default. The isolation = "none" config exists only as an escape hatch with a three-line warning banner every time it's used.
  • Network egress is off by default. Per-server allowlist of domains, denied unless the user opted in. The MCP that "just needs to call OpenAI" gets api.openai.com, not *.
  • Filesystem is scoped by default. The MCP sees its own $XDG_DATA_HOME/mcpm/servers/<name>/ and a user-configured allowlist of paths. Not $HOME. Never $HOME by default.
  • Project configs are untrusted until pinned. direnv's mental model transplanted to mcpmanagerd.
  • Secrets are scoped per-server. The github MCP gets GITHUB_TOKEN. It does not get AWS_SECRET_ACCESS_KEY, even if both exist in the keychain.

Arguments

vs. crypto-pedant

crypto-pedant will argue that TUF-lite, as the v1.0 spec describes it, is under-specified in exactly the places where it matters most: root-key rotation, threshold signing, and delegations. I largely agree with their position on the cryptographic primitives — minisign for offline-signed indexes is fine[9], cosign for OCI is fine[10] — but my push is about the operational layer they tend to under-cost. Specifically:

  1. A baked-in pubkey is a single point of failure. If our signing key leaks (laptop loss, CI compromise, supply-chain incident inside Anthropic-the-org or the maintainer team), every installed copy of mcpmanagerd is permanently keyed to the wrong root until the user re-runs the installer. We need a second baked-in revocation pubkey whose only job is to publish a "this root is dead, here is the new one" message that mcpmanagerd will accept out-of-band. crypto-pedant will say "this is what TUF root-key rotation already specifies" — and they are right, and we still need to make sure the v1.0 implementation actually ships it, not just refers to the spec.
  2. Per-package signatures must not be trusted if the signing key has been revoked. The v1.0 spec says "registry index signatures verified before parse; verify-when-present on underlying packages." Verify-when-present is dangerous unless we publish a list of packages where present-is-required. A malicious package without a signature is indistinguishable from a benign one published before the registry required signing. So: per-source policy, defaulting to required-signed for all three baked-in registries.
  3. Cosign verification of OCI MCP images must check sigstore-bundle, including Rekor inclusion proof [11]. Cosign's bare "valid signature" check is insufficient — Rekor is what gives us non-repudiation. crypto-pedant won't argue this; I'm flagging it because I want it called out in the threat model rather than handwaved.

Where I genuinely diverge from crypto-pedant: I will not lose sleep over post-quantum agility in v1.0. The threat model says "user's laptop in 2026"; the attacker is not a nation-state with a CRQC. Ed25519 is fine. Ship.

vs. sandboxing-veteran

sandboxing-veteran will spend their essay on the gradient between bubblewrap, firejail, and sandbox-exec, and on the strengths/weaknesses of each profile. I am with them on every technical detail. My push is about defaults, which sandboxing-veteran can sometimes treat as a policy debate rather than a technical one. It is technical: the default profile decides whether the mass-market user is safe.

Three places I will push:

  1. isolation = "none" must not be a silent option. The v1.0 spec includes "none" in the enum without saying when it's chosen or what UX guards it. I want: (a) every mcpm install that resolves to isolation = "none" emits a block-bordered warning in the CLI listing what protection is being skipped; (b) the audit log records isolation.disabled { server, requested_by, reason } on every spawn; (c) the TUI shows the lack of sandbox in red, not just a different label.
  2. The default devenv profile is too permissive if it inherits the user's $HOME. sandboxing-veteran's bubblewrap configuration must bind-mount $HOME/.ssh, $HOME/.aws, $HOME/.config/gh, $HOME/.gnupg, $HOME/.netrc, $HOME/.password-store, and the macOS Keychain sqlite files at $HOME/Library/Keychains as denied. This is the bog-standard sandbox profile the Flatpak community has been refining for years [12]; we don't have to reinvent it.
  3. macOS sandbox-exec is deprecated but works. sandboxing-veteran will note this; I want to make sure the threat model documents the contingency (Docker fallback on a future macOS that removes sandbox-exec) and that the project ships a test that the profile actually blocks the things we claim it blocks. Apple's own profiles are written in SBPL S-expressions, and the iSEC Partners audit [13] documents how easy it is to write a profile that looks restrictive but isn't.

vs. secrets-architect

secrets-architect will go deep on the keyring crate's quirks (libsecret prompt on Linux, org.freedesktop.secrets portal differences across GNOME/KDE/headless servers, SecItemCopyMatching ACL behaviour on macOS, the layered store ordering rules). I'm with them on all of it. My push is about worst-case access semantics:

  1. Per-server keychain scoping is non-optional for v1.0. The v1.0 schema currently allows a secret named GITHUB_TOKEN at the global scope, injected into any server that declares secrets = ["GITHUB_TOKEN"]. That is a giant footgun: the malicious random-tool-mcp can declare secrets = ["GITHUB_TOKEN", "AWS_SECRET_ACCESS_KEY", "SLACK_WEBHOOK_URL", …] and mcpmanagerd will happily hand them over. The fix is: secrets are owned by a server at write time (mcpm secret set --server github GITHUB_TOKEN), and the keychain account is dev.mcp-manager/<server>/<name>. A server can only request secrets in its own namespace; cross-server secret injection requires an explicit secrets_from = ["other-server.NAME"] directive that the user types by hand.
  2. The env-var passthrough store is a knife. The v1.0 spec includes EnvVarPassthroughStore as a read-only escape hatch. I want it default-off, opt-in per deployment via --enable-env-passthrough at daemon launch, and audit-logged on every read. Without that, the daemon happily reads GITHUB_TOKEN out of its own environment and injects it into any server that asks for it by name, defeating the per-server scoping above.
  3. Secrets at rest must respect Mozilla SOPS-style key-management hygiene for any v1.1+ external store (Vault, 1Password). The SOPS threat model is the right reference [14]: encrypted-at-rest, key access logged, rotation supported, and the encryption key is not the same as the decryption key for audit purposes.

vs. audit-compliance

audit-compliance will argue (correctly) that the v1.0 audit log is a JSONL file with daily rotation, and that this does not satisfy any tamper-evidence property — an attacker with write access to $XDG_STATE_HOME/mcpmanagerd/audit/ can simply edit it. I agree. My push is on the cheap mitigations we can ship in v1.0 without overengineering:

  1. Hash chain per file. Every line carries "prev_hash": "<sha256-of-line-before>". The first line in a file is sealed against the file name (date-stamp). Cheap, defeats casual tampering, doesn't require crypto-pedant-grade anchoring. The systemd journal's FSS (Forward-Secure Sealing) feature [15] is the reference design — we don't have to be as fancy, but the hash-chain idea is the same.
  2. fsync on every auth.failed and secret.read line. Batched otherwise. We accept the 5-10ms cost on security-critical events to make sure they hit disk before the attacker can clean up.
  3. Ship the audit-log replay tool with the daemon. mcpm audit replay --verify re-walks the hash chain and reports the first broken link. This is a one-evening implementation that moves us from "we have audit logs" to "we have audit logs with verifiable integrity."

Where I disagree with audit-compliance: I don't want to ship an OpenTelemetry exporter in v1.0. The MCP Manager threat model is a single-user laptop tool. Centralised audit aggregation is a v1.1+ concern when teams want it. Don't pay for what we don't need.

Attack trees (ASCII)

Three asset-rooted trees, written in the Shostack notation[6]. Each leaf is an atomic attacker action; each interior node is an AND/OR composition. M: mitigation reference.

Tree 1 — Asset: ~/.ssh/id_rsa exfiltrated to attacker-controlled endpoint

GOAL: attacker reads $HOME/.ssh/id_rsa
└── OR
    ├── Malicious MCP package reads file directly
    │   └── AND
    │       ├── Package installed
    │       │   └── OR
    │       │       ├── User installs from typo-squat                          (M: registry sig + name-claim)
    │       │       ├── User installs from compromised registry                (M: TUF root + rotation)
    │       │       └── Untrusted project config auto-installs                 (M: direnv-style trust gate)
    │       ├── Process can read the file                                      (M: sandbox FS deny-list)
    │       │   └── AND
    │       │       ├── Sandbox bypassed or not running
    │       │       │   ├── isolation = "none" (warn UX)                       (M: red banner + audit)
    │       │       │   ├── devenv profile mis-scoped                          (M: golden-test profile)
    │       │       │   └── bubblewrap kernel bug                              (M: cap-net-admin drop)
    │       │       └── File present at expected path                          (M: not in our control)
    │       └── Egress channel open
    │           ├── DNS exfil                                                  (M: netns deny + dnsmasq)
    │           ├── Direct TCP                                                 (M: netns deny by default)
    │           └── Side-channel via stdout to host                            (M: stdout filter on secret-shaped strings — best-effort)
    │
    ├── Compromised registry pubkey signs malicious package update
    │   └── AND
    │       ├── Private key leaks                                              (M: HSM-back; rotate; revoke list)
    │       ├── User auto-updates                                              (M: --accept-breaking off by default)
    │       └── Sandbox not deny-listing ~/.ssh                                (M: see above)
    │
    └── mcpmanagerd itself reads file (insider / RCE)
        ├── RCE in JSON-RPC parser                                             (M: serde + fuzz; no eval)
        ├── Path-traversal in projection writer                                (M: canonicalise; assert prefix)
        └── Symlink attack on canonical config                                 (M: open(NOFOLLOW); fsstat)

Tree 2 — Asset: cross-server secret leak (github-mcp reads aws-mcp's token)

GOAL: server A reads server B's secret
└── OR
    ├── A declares secrets = ["B.AWS_TOKEN"] and daemon honours it           (M: per-server namespace; cross requires `secrets_from`)
    ├── A reads env of B's process via /proc/PID/environ                    (M: bwrap --new-session; PID-namespace where available)
    ├── A reads B's stdout/stderr from shared log                           (M: per-server ring buffer; no cross-tail without explicit flag)
    ├── A reads OS keychain directly                                        (M: macOS ACL bind to mcpmanagerd binary signature; libsecret per-app collection)
    ├── A reads B's secret via UDS to mcpmanagerd                           (M: SO_PEERCRED — but A and B share UID; needs server-id token)
    │                                                                         IMPORTANT: SO_PEERCRED is insufficient here; need per-spawn nonce
    └── A reads B's secret out of a config file the user pasted into the prompt  (M: education + redaction in CLI; cannot fully mitigate)

The fifth leaf — "A reads B's secret via UDS to mcpmanagerd, because A and B share UID with the mcpm exec wrapper" — is the one v1.0 has to address explicitly. SO_PEERCRED proves the caller is the user; it does not prove which server's wrapper is calling. The mitigation is: when mcpmanagerd spawns server B, it generates a random 32-byte nonce, writes it into B's environment as MCPM_INSTANCE_TOKEN, and remembers the mapping token → server_name. Subsequent secret-reads over UDS from a wrapper that doesn't present a matching token are denied. This is cheap, layered defence-in-depth on top of SO_PEERCRED.

Tree 3 — Asset: audit-log integrity (attacker erases evidence)

GOAL: attacker deletes or modifies entries in audit/YYYY-MM-DD.jsonl
└── OR
    ├── Attacker has shell as the user (post-exploit MCP escape)
    │   ├── rm of audit file                                                (M: hash chain detects gap; mcpm audit replay)
    │   ├── edit in place                                                   (M: prev_hash mismatch on next entry)
    │   ├── truncate                                                        (M: file-name → first-line seal mismatch)
    │   └── append fake "ok" entry                                          (M: cannot recompute chain without prior valid hash)
    ├── Attacker has root (out of scope; we accept this loss)
    └── Race: daemon crashes mid-write
        ├── Partial line                                                    (M: line-length prefix; recovery skips & flags)
        └── Lost flush                                                      (M: fsync on auth.failed / secret.read)

Default-deny network & FS specs

Concrete profile that ships as the v1.0 default for any server with isolation = "devenv" on Linux. macOS gets the equivalent SBPL profile.

Network egress — default profile

[server.<name>.network]
mode = "deny"            # default. Other values: "allowlist" | "open"

# When mode = "allowlist", these and only these are allowed:
allowed_hosts = []       # e.g. ["api.openai.com", "api.anthropic.com"]
allowed_ports = [443]    # default https only
resolver      = "system" # or "dns-over-https://1.1.1.1"

# When mode = "open" — emit a warning at every spawn:
# WARNING: server <name> has unrestricted network access. Audit logs every connection.

Implementation: bubblewrap with --unshare-net by default. For allowlist mode, the server runs in a network namespace with a single egress proxy (mcpm-egress-proxy, a tiny Rust binary using tokio::net::TcpStream) that the daemon spawns alongside, accepts on a private UDS inside the namespace, and only forwards to allowed hosts. The proxy resolves names itself, never trusts the child's DNS[12]. On macOS, sandbox-exec with (deny network*) as the base and (allow network* (remote ip "...")) patches.

Filesystem scoping — default profile

[server.<name>.fs]
mode = "scoped"          # default. Other values: "open" (with warning)

# Always allowed (read+write):
#   $XDG_DATA_HOME/mcpm/servers/<name>/    — per-server data dir
#   /tmp/mcpm-<name>-XXXXXX/                — per-spawn scratch (tmpfs, deleted on exit)
# Always allowed (read-only):
#   /usr, /bin, /lib, /etc/ssl/certs, /etc/resolv.conf (proxied)
#   /nix/store (read-only, only if isolation = devenv)
# Always denied:
#   $HOME/.ssh
#   $HOME/.aws
#   $HOME/.config/gh
#   $HOME/.gnupg
#   $HOME/.netrc
#   $HOME/.password-store
#   $HOME/Library/Keychains              (macOS)
#   $HOME/.docker/config.json
#   $HOME/.kube
#   $HOME/.config/mcp-manager            — our own config is opaque to children

allowed_read  = []       # extra read-only paths the user grants
allowed_write = []       # extra writable paths the user grants

The allowed_read / allowed_write entries appear in the CLI install transcript as explicit prompts: "this server requests read access to ~/Documents/notes/; allow?" Default no. Each grant is audit-logged.

Trust-gate failure modes

The direnv-style project-trust gate has six failure modes I want to enumerate explicitly so the implementation can target each one with a test. The current v1.0 spec mentions the trust gate but doesn't enumerate.

  1. Fresh clone — no entry in trust.toml. Behaviour: daemon refuses to apply project scope. CLI shows warning: untrusted .mcp-manager.toml. Run `mcpm trust grant`. User must run an explicit command; no auto-trust, no "press y to accept." (direnv's lesson[4].)
  2. Trusted previously, file modified. Hash mismatch. Daemon refuses to apply project scope; CLI shows a diff vs. the previously-trusted version and asks the user to mcpm trust grant again. The diff is computed by the daemon and rendered by the CLI so the user can see what changed.
  3. Trusted file, path moved. Trust is keyed by sha256(absolute-path) + sha256(file content). Moving the repo to a different path invalidates the trust grant. This is correct: a different path is a different context.
  4. Trust file (trust.toml) itself corrupted or replaced. On daemon start, trust.toml is loaded with O_NOFOLLOW and its sha256 is compared against $XDG_STATE_HOME/mcpmanagerd/trust.toml.hash. Mismatch → daemon enters "trust-degraded" mode: no project configs apply, only user-scope config; audit-log trust.tampered. User must run mcpm trust reinit to re-baseline.
  5. Project config requests an unsigned registry. Refused. Even with trust granted, project configs cannot add registries whose pubkey isn't already trusted by the user at user-scope. Project scope can use registries the user trusts; it cannot add new ones. This is a hard line.
  6. Project config requests isolation = "none". Refused, period. isolation = "none" is user-scope only — a project cannot ask the user to run code unsandboxed. If the project author needs that, they put a note in their README; the user opts in by setting isolation = "none" in user-scope config for that specific server.

10 worst-case scenarios → mitigations

#ScenarioMitigation
1 User installs typo-squatted github-mc (missing p) from the official registry. Malicious code runs at first spawn. Registry index includes a name-claim record (similar to npm's package-namespace policy[16]); the official registry refuses to publish names within edit-distance 1 of popular names without a manual review. Sandbox limits damage even if installed: no SSH key access, no egress.
2 User clones contractor/data-pipeline.git which ships a hostile .mcp-manager.toml declaring 5 MCPs and a private registry. Trust gate refuses to load. User sees CLI warning. User reads the file (it's TOML, plain text). User chooses to trust or not. Even if trusted, malicious MCPs run under default-deny sandbox.
3 Malicious MCP, post-install, attempts to read ~/.ssh/id_rsa. bubblewrap (--unshare-all --bind …) / sandbox-exec deny. open(2) returns EACCES. Server's tool call fails. Audit log records the attempt as server.fs.denied at the seccomp / sandbox layer — if the platform supports such logging — else the deny is silent (acceptable).
4 Malicious MCP exfils data via DNS to attacker-controlled domain. Network namespace with --unshare-net by default; no DNS resolver available. With allowlist mode, the egress proxy resolves names itself and only forwards to allowed hosts. DNS-over-TXT exfil to allowed hosts is still possible — accepted limitation, documented.
5 Malicious MCP random-tool declares secrets = ["AWS_SECRET_ACCESS_KEY"] and asks mcpmanagerd to inject it. Per-server keychain namespacing. random-tool can only request secrets stored under dev.mcp-manager/random-tool/. Cross-server access requires explicit secrets_from = ["aws.AWS_SECRET_ACCESS_KEY"] in user-scope config (user-typed; project-scope cannot grant).
6 Attacker on shared multi-user system tries to talk to another user's mcpmanagerd. UDS at $XDG_RUNTIME_DIR with mode 0600 — kernel refuses connect for another UID. SO_PEERCRED verified on every accept as defence-in-depth. auth.failed audit event.
7 Maintainer's offline minisign key for the official registry is compromised. Attacker publishes a malicious update. Root-of-trust revocation publishes a new trust.toml at the well-known URL, signed by the (separate) revocation key, declaring the old key revoked. mcpm trust refresh picks it up. Until that happens, users on auto-update with --accept-breaking off are still pinned to known-good versions in their lockfile.
8 Malicious MCP package exploits a parser bug in mcpmanagerd's JSON-RPC handler and gains RCE in the daemon process. serde-based parser (no eval, no string interpolation), fuzz-tested with cargo-fuzz. Daemon runs as user, not root, so RCE here is "one tier up from the sandboxed MCP" — bad but bounded. Daemon binary has stack protector + ASLR + RELRO from Rust's standard release profile. No unsafe in the JSON-RPC parser (lint-enforced).
9 Attacker with brief filesystem-write access (e.g. evil USB stick, opened a tar from untrusted source) writes a file at ~/.config/mcp-manager/config.toml to register a malicious registry. Daemon detects on-disk hash drift via file_hash tracking. Next config.put with stale prior-hash returns E_CONFIG_CONFLICT. New registry entries trigger an explicit "new registry detected; verify and run mcpm registry verify <name>" warning. Best we can do; this scenario requires existing filesystem-write access, which is already a deeper compromise.
10 Sandbox-bypass via a kernel bug in bubblewrap or namespaces (e.g. CVE-2023-XXXX-class). Defence-in-depth: even if the sandbox is bypassed, secrets are still env-only at spawn (no on-disk plaintext), no network namespace means no egress, audit log records the spawn. Daemon does not run as root, so the bypass yields user-level access — what the attacker would have anyway if they were a normal user-level process. The asset value is then the secrets in the OS keychain, which require an unlock prompt on macOS / explicit collection unlock on Linux.

IPC authentication — bypass scenarios

SO_PEERCRED tells us the connecting process's UID/PID/GID; nothing more. Four bypass scenarios I want documented:

  1. Same-UID server-to-daemon spoofing. Already covered — any code running as the user can connect to the UDS. Mitigation is the per-spawn MCPM_INSTANCE_TOKEN nonce described in Tree 2 above.
  2. PID reuse on Linux. SO_PEERCRED returns the PID at connect time; if the process exits and a new one takes the PID, the kernel reports the original PID for the lifetime of the socket. Not a security issue (we want the original peer's UID, not the new PID's UID), but worth noting[17].
  3. macOS LOCAL_PEERPID race. LOCAL_PEERPID can be stale across process replacement (rare but documented). We rely on UID, not PID, for auth decisions.
  4. Socket-file replacement. If an attacker can replace the daemon's socket file (race between daemon-down and daemon-up), they can pose as the daemon. Mitigation: daemon creates the socket via bind with O_EXCL semantics inside $XDG_RUNTIME_DIR, fails to start if the file exists. The wrapper's auto-spawn logic uses flock(2) on a sibling lockfile to serialise.

First-launch security prompts

Three prompts on first mcpm init:

  1. Trust the root manifest URL? Default yes; "no" puts the user into baked-in-fallback mode permanently. URL is shown.
  2. Enable Docker for the docker registry source? Default no. If yes, daemon shells out to docker info to verify available, and remembers consent in ~/.config/mcp-manager/consent.toml. If no, the docker registry source is disabled until the user runs mcpm registry enable docker.
  3. Allow env-var passthrough store? Default no. Yes only if the user knows what it does. Audit-logged.

No "trust this prompt" → "auto-trust all future prompts" toggle. Each consent decision is per-action, following the OWASP guidance on consent dialogs[7].

Binary code signing & supply-chain pinning

  • macOS: Apple Developer ID signing + notarization. spctl --assess passes on every release. Stapled ticket inside the tarball.
  • Linux: minisign-signed tarballs[9] with the pubkey baked into the curl installer script (which itself is fetched over HTTPS with cert-pinning to GitHub Releases). Reproducible build via Nix flake; the github:user/mcp-manager flake should produce the byte-identical binary as the official release.
  • Cargo.lock is committed. No floating versions. Dependabot or cargo-audit[18] runs in CI, blocks merge on RUSTSEC advisories.
  • cargo-vet[19] for the top-50 transitive deps. Each one needs a trust assertion from a vetted source (Mozilla, Bytecode Alliance, Embark, or our own audit). Bound this scope tight — auditing every dep is impossible — but the deps in mcpm-secrets, mcpm-trust, and the JSON-RPC parser must be in the audited subset.
  • No build.rs network access. Lint-enforced via cargo-deny. If a transitive dep adds a network-fetching build script, it's a blocker.

Honest limitations & accepted risks

  • Side-channel exfil via stdout. An MCP can re-emit allowed-read file contents into the host LLM's context. We cannot stop this without solving alignment. Scope the read paths; document.
  • Prompt injection in tool descriptions. Out of our threat model; the host is responsible. Linked to upstream MCP-spec guidance[20].
  • The user is root on their own machine. isolation = "none" is loud, audited, never default. The user's right to shoot their own foot is respected.
  • OS keychain unlock is the user's responsibility. Idle-lock behaviour is OS-level; we document recommended settings.
