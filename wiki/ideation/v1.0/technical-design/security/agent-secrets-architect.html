The Secrets Architect’s Security

Layered SecretStore. secrecy::SecretString end-to-end. Redaction by default in every tracing span. Per-read audit on every keychain hit. TTY-only entry via rpassword; argv is never a transport. v1.0 doesn’t need a vault — it needs a discipline, and the discipline is the trait.

Thoughts

The lesson three production systems taught me

Every secrets bug I’ve shipped has fallen into one of four buckets: the secret leaked through a log line nobody thought to redact; the secret was read by code that had no business reading it; the secret lived in memory ten seconds longer than it needed to and showed up in a core dump; or the secret was set via a CLI flag and ended up in the shell history of the user’s laptop, the corporate MDM agent’s command-history collector, and a screenshot somebody pasted into Slack. Every one of these is a discipline problem, not a cryptography problem. v1.0 doesn’t need HSM-backed encryption. It needs four boring things done right: a typed wrapper that the compiler refuses to print, a tracing layer that filters those types, a TTY-only intake path, and an audit trail that records who-read-what-when.

Why the layered store is non-negotiable

I want one read path through the code — store.get(&ref) — that the rest of mcpmanagerd talks to. Behind that one call, I want the OS keyring as the durable backing store, the user’s shell environment as a read-only override for CI, and a clear, documented precedence rule so that nothing surprises anyone. The LayeredSecretStore with env-passthrough first, OS keyring second is exactly that[1]. The user who runs export GITHUB_TOKEN=… in CI has intentionally overridden the keychain; the user who hasn’t exported anything gets the keychain by default. Two layers, one rule, infinitely extensible: v1.1 plugs 1Password or Vault behind the same trait without touching mcpmanagerd’s spawn path[2].

Why secrecy earns its keep

The secrecy crate gives us three things we cannot get with String: a Debug and Display impl that prints [REDACTED] always; an expose_secret() call site that’s greppable in code review; and automatic Zeroize on drop so the page doesn’t survive a core dump[3][4]. That last property is the difference between “our process crashed” and “our process crashed and IT is now rotating eighteen tokens.” The discipline is: every function signature that touches a secret takes &SecretString or SecretString; nothing takes &str. clippy::disallowed_types can be configured to warn on raw String for crates inside the secret-handling boundary, which I want to enforce in CI.

Why argv is the cardinal sin

The first thing the v1.0 spec gets right is refusing --value=… on mcpm secret set. argv is broadcast: it shows up in ps, in shell history, in audit-collection MDM tools, in any sibling process’s /proc snapshot, and — on macOS without a hardening flag — in crash reporter dumps. OWASP’s Secrets Management Cheat Sheet is explicit about this[5]; so are 1Password, Doppler, and step-CLI’s own onboarding docs. The intake paths v1.0 allows are TTY via rpassword (reads from /dev/tty, never echoes, never lands in stdin buffers)[6], --from-file, --from-env, and --stdin. Four paths. None of them is argv.

Read-audit as the unsung half of the story

The keychain says “you read GITHUB_TOKEN.” mcpmanagerd’s audit log says “which MCP server, spawned by which IPC client, on behalf of which editor PID, read GITHUB_TOKEN at this timestamp, outcome ok.” The OS audit trail is half of one; ours is the other half. A user who runs mcpm audit tail --secret GITHUB_TOKEN should see a tight rhythm of reads bracketed by server spawns, and an unexplained read between spawns is a flag. The audit channel is owned by mcp-core (not by the SecretStore impl itself) so a buggy or hostile backend can’t suppress its own emissions. NIST SP 800-92 lays out the principles — append-only, integrity protected, structured — and we follow them at our scale[7].

The boundary between user and project secrets

I want this crisp: user secrets are scoped (server, name) in the user’s keychain, project secrets do not exist in v1.0. If a project’s .mcp-manager.toml says it needs GITHUB_TOKEN for the github server, it’s asking the user’s keychain for that name. There is no per-project secret store, no per-project keychain item, no per-project override. v1.1 may add project-scoped vault references (e.g. vault://team/proj/foo) behind the same trait — but in v1.0 the answer to “can a hostile .mcp-manager.toml exfiltrate a secret it shouldn’t have?” is “only if the user already set that secret for that server name, in which case the trust gate is the place to draw the line, not the secret store.” This keeps the threat model tight and the trust boundary single-purpose.

Arguments

Against red-team

Red-team will push for default-deny on secret reads themselves: a per-server allowlist of which secret names that server is permitted to request, enforced at store.get(), fail-closed. I agree with the principle and I want to ship a weaker form in v1.0. The strong form — a manifest-driven requires_secrets: […] declaration, mcpmanagerd refuses to spawn if the manifest doesn’t enumerate the secret, refuses to inject a secret not in the manifest — is exactly what we should do, because it lets red-team’s threat model and my secret model agree on a single source of truth (the manifest).

Where I push back: red-team will want a runtime confirmation prompt on first read of each secret (“the github server is requesting GITHUB_TOKEN, allow once / always / deny?”). I don’t want to ship that in v1.0. It teaches users to click through prompts (the macOS Keychain ACL anti-pattern), and the trust gate at config-import time is the right place to make that decision. v1.0 does the manifest enumeration; v1.1 can layer interactive confirmation on top if telemetry from real users shows the threat warrants it. The trust gate plus the manifest declaration plus the audit log is, I claim, enough for v1.0.

Against crypto-pedant

Crypto-pedant cares about the bytes at rest: the keychain encrypts with the user’s login key; libsecret encrypts with the session keyring; on Linux without a Secret Service we should fall back to an age-encrypted file on disk with a user-supplied passphrase. I disagree on the fallback. Rolling our own file-based encrypted store is exactly the trap the OWASP cheat sheet warns about[5]: we’d be writing key-stretching parameters, IV handling, key derivation, all the bits we wanted to avoid by using the OS keyring in the first place. The right v1.0 fallback when no Secret Service is reachable is to refuse to write and tell the user explicitly to install gnome-keyring or KWallet or KeePassXC with the Secret Service plugin enabled. The freedesktop Secret Service API is the standard interface every Linux desktop already implements[8]; we shouldn’t duplicate it badly.

What I do want from crypto-pedant’s playbook: zeroize on SecretString drop is non-negotiable, the keyring service string is namespaced (dev.mcpmanager) and pinned forever (renaming after release loses access to existing keychain items), and the kSecAttrAccessibleWhenUnlocked attribute on macOS is the right default[9] — not the more permissive kSecAttrAccessibleAfterFirstUnlock, which would let a stolen laptop’s background reboot expose secrets without the user logging in.

Against sandboxing-veteran

Sandboxing-veteran will argue that env-var injection is the weak point: in devenv and uvx-npx modes the child shares the parent’s namespace, so any sibling process can cat /proc/<pid>/environ and read the token. They’re right. The mitigation in v1.0 is to make the injection mode match the isolation mode:

  • devenv / none: env-var injection. The user has explicitly chosen no isolation; we’re not pretending otherwise. The /proc/<pid>/environ exposure is documented and the threat model labels this mode “reproducibility, not isolation.”
  • uvx-npx: env-var injection, same caveat. The audit log records the read; the user chose convenience.
  • docker / podman: --env-file via an unlinked tmpfs file descriptor, or better, the runtime’s built-in secret mount (--mount type=secret on Docker BuildKit / Podman). The secret is in the container’s environment, not in the daemon’s host shell.
  • sandbox-exec / bubblewrap: file-descriptor passing. Write the secret into a memfd (Linux) or an unlinked file (macOS), pass the fd to the child, set MCPM_SECRETS_FD=3. The MCP server SDK reads the fd at startup. This means the secret never lives in the process env at all — /proc/self/environ is clean. v1.0 ships this as the default for the strong-isolation modes.

Sandboxing-veteran will counter: “the SDK doesn’t support fd-passing yet.” True. v1.0 offers env injection in all five modes today and adds the secrets/-mount path for docker / podman; the fd-passing convention lands in v1.1 once we’ve coordinated with the SDK maintainers. The shape of the contract — MCPM_SECRETS_FD for fd-passing, MCPM_SECRETS_DIR for mount-passing, plain env vars otherwise — is documented up front so SDKs can target it.

Against audit-compliance

Audit-compliance wants tamper-evidence: a hash chain across audit entries, ed25519-signed roots, the works. I’m sympathetic but v1.0’s threat model doesn’t justify it. The audit log lives in the user’s home directory; an attacker with write access to it has already won at a deeper level than “forge an entry.” What I want from audit-compliance and will ship is: structured JSONL, schema version field, fsync on every write, append-only file mode on Linux (chattr +a when available), and a documented format so v1.1 can layer a Merkle chain on top without migrating the data. NIST SP 800-92’s log-management guidance is the reference[7]; the integrity-protected-storage half of that recommendation is v1.1.

Where we agree completely: no secret value, anywhere, in any log line, ever. The test suite includes a fuzz test that writes random bytes as secrets and greps every emitted log line and audit entry; a match fails the build. The tracing redaction layer (below) makes the default safe; the fuzz test makes sure no future contributor can accidentally undo it.

Design

The SecretStore trait

The minimal trait that v1.0 ships, and that v1.1+ backends extend. Async-trait because v1.1 has HTTP-backed stores; spawn_blocking wraps the synchronous keyring crate calls. Returns Option on get so the layered chain can fall through cleanly. 

use secrecy::SecretString;
use async_trait::async_trait;

#[non_exhaustive]
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum SecretRef {
    Named { server: String, name: String },
}

#[async_trait]
pub trait SecretStore: Send + Sync + 'static {
    fn id(&self) -> &'static str;
    async fn get(&self, r: &SecretRef) -> Result<Option<SecretString>, SecretError>;
    async fn set(&self, r: &SecretRef, value: SecretString) -> Result<(), SecretError>;
    async fn unset(&self, r: &SecretRef) -> Result<bool, SecretError>;
    async fn list(&self) -> Result<Vec<SecretRef>, SecretError>;
}

#[derive(Debug, thiserror::Error)]
pub enum SecretError {
    #[error("backend unavailable: {0}")] BackendUnavailable(String),
    #[error("read-only store")]          ReadOnly,
    #[error("backend error: {0}")]
    Backend(#[source] Box<dyn std::error::Error + Send + Sync>),
}

Notes the compiler enforces for us: SecretString is the only return type carrying a value, list() returns references (names) never values, and the trait is object-safe so mcpmanagerd holds a single Arc<dyn SecretStore>. #[non_exhaustive] on SecretRef lets us add e.g. VaultPath { mount, path, field } in v1.1 without breaking external matches.

LayeredSecretStore precedence

Read order is intentional and documented. v1.0’s chain is exactly: 

// Read: env-passthrough wins (user override), then keychain.
// Write: keychain only (env-passthrough is read-only).
let store: Arc<dyn SecretStore> = Arc::new(
    LayeredSecretStore::new()
        .with(EnvVarPassthroughStore)
        .with(OsKeyringStore)
);

The reason env wins: a user who has exported GITHUB_TOKEN in CI has chosen to override the keychain, and we honor that without surprise. mcpm secret list --show-env reveals the override explicitly so the user understands precedence at a glance. v1.1 swaps the chain for OnePasswordStore, VaultStore, etc., behind the same Arc with zero changes to mcpmanagerd’s spawn path[10].

Redaction tracing layer

The tracing ecosystem lets us install a layer that filters by field type. The shape: 

use tracing::field::{Field, Visit};
use tracing_subscriber::layer::{Context, Layer};

/// Recognizes SecretString-typed fields and rewrites their display to [REDACTED].
struct SecretRedactor;

impl<S> Layer<S> for SecretRedactor where S: tracing::Subscriber {
    // visit_event hook: walk the event's recorded fields, replace any
    // value whose type-name matches secrecy::SecretString (or whose
    // field name is on a deny-list such as "token", "password", "key")
    // with the literal string "[REDACTED]" before downstream layers
    // see it.
}

Belt-and-suspenders: (1) SecretString’s own Debug impl already prints [REDACTED][3], so even without the layer the field is safe in tracing::debug!("{:?}", s); (2) the layer adds a deny-list of field names (password, token, api_key, secret, authorization) that get redacted even if the developer accidentally passed a raw String; (3) the CI fuzz test writes random byte strings as secrets and greps every log/audit line for them.

In every mode, the SecretString in mcpmanagerd is dropped (and zeroized) immediately after spawn() returns. The audit emission happens before the spawn, so a failed spawn still records the read attempt and the failure outcome.

Keyring-unavailable fallback & first-launch UX

The fallback policy is conservative on purpose: we do not roll our own encrypted file store. The cases and behaviors:

  • macOS Keychain locked / ACL declined: the user’s system itself is asking permission. Surface the error verbatim (your keychain refused access — re-run after unlocking), do not retry, do not cache the credential anywhere. First launch on macOS includes a one-shot “mcpm wants to add an item to your keychain” prompt; the user clicks “Always Allow” once and subsequent reads are silent. This matches Keychain Services’ documented UX for signed apps[9].
  • Linux without Secret Service running: refuse-to-write with a structured error and installation hint. Specifically: no freedesktop Secret Service is reachable. Install gnome-keyring (or KWallet, or KeePassXC with the Secret Service plugin) and ensure it’s running in your session. Alternatively, export the secret as an environment variable: export GITHUB_TOKEN=<value>[8]. The env-passthrough store handles the alternative path without any further code.
  • CI environments / headless servers: rely entirely on EnvVarPassthroughStore. The CI cookbook documents the “export the secret” pattern as the supported flow; the keychain is for interactive workstations.
  • SSH session into a workstation: the keychain works if the user’s GUI session is running and unlocked (libsecret) or the keychain is unlocked (macOS). If neither, env-passthrough is the documented fallback. mcpm secret set over SSH refuses the interactive prompt unless stdin.is_terminal() succeeds[6]; the user is instructed to use --from-file, --from-env, or --stdin.
  • Code signing & first-launch: v1.0 ships a signed macOS binary (Developer ID) so first-launch doesn’t hit Gatekeeper’s quarantine path. Linux relies on the package manager’s own signing (apt/rpm/AUR). The keychain entry for mcpmanagerd is created at first mcpm secret set, not on daemon install; we don’t pre-populate empty keychain items.

Putting it all together: a single trait, a layered chain with explicit precedence, OS keyring as the durable backing store, env-passthrough as the documented escape hatch, secrecy::SecretString as the in-memory type, a tracing redaction layer plus a deny-list plus a fuzz test as defense in depth against log leakage, per-read audit entries on every keychain hit, TTY-only intake via rpassword, no argv anywhere, and a sandbox-mode-matched injection mechanism so the secret lives at the lowest scope the user’s chosen isolation supports. That’s the discipline. v1.0 doesn’t need more.
