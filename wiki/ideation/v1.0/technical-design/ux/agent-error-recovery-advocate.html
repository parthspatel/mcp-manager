The Error Recovery Advocate's UX

Every error has code, what-happened, why, what-to-do — and ends with the next command to run. The 12-row taxonomy is the contract; --json is the envelope; the mdbook is the runbook. Recovery is the product, not the apology.

Opening thoughts

Most developer tools treat errors as the place where the design ends — a stack trace, an exit code, maybe a sentence of apology, and then the user is on their own. MCP Manager cannot afford that posture. The whole point of the project is that setting up MCP servers is currently a disaster of secrets, runtimes, projection files, and editor restarts, and the failure modes of that disaster are exactly where users will form their opinion of mcpm. If we want the tool to feel kind and competent we have to design the unhappy path as carefully as the happy path. That means treating every error as a four-part artifact: a stable code (the E_* prefix that the docs and the JSON envelope agree on), a what-happened sentence in plain English, a why sentence that gives the user the mental model they need to not be confused next time, and a what-to-do line that names — or actually prints — the next command. Four fields, not three; the "why" is what separates an error message from a runbook.

The 12-row taxonomy already documented in ux-design.html is the right contract, and I am not arguing to expand it. Twelve is the right number — it covers the entire surface a v1.0 user will hit (secrets, OOM, crashes, config, registry, projection, project-trust, keychain, daemon version, spec) without sprawling into the long tail of "could happen, never will". My argument is that the existing taxonomy still reads as a list of meanings rather than a list of recoveries, and that the gap between those two shapes is exactly the gap between an apology and a fix. Each row currently has "Code · Meaning · Typical fix". I want to lock the contract to five columns: code, short_msg, what_happened, why, remedy + related_cmd. Same twelve rows, four times the actionability. Each row also pins to a one-page mdbook runbook at https://docs.mcp-manager.dev/errors/E_*; that URL ships in the error envelope so the JSON consumers (CI, editor extensions, future GUI) can deep-link directly into the documentation.

The second non-negotiable: the error message ends with a command. Not a suggestion, not a verb ("try restarting"), but the actual literal command, in a monospace block, ready to copy. The E_SECRET_MISSING example in the existing UX doc already does this — $ mcpm secret set GITHUB_TOKEN — and every other row must match that pattern. Where the next command is parametric (e.g. E_PROJECTION_DRIFT needs a tool name), we interpolate from the failed call's context. The TUI exposes this with a y binding that copies the suggested command to the clipboard, matching k9s's muscle memory for "copy the thing the modal is showing me". The CLI prints it on the last line of stderr, deliberately separated by a blank line so it's easy to spot in a wall of log output. When users tell other users how to recover, they'll do it by pasting the line we suggested. That's success.

The third non-negotiable: preview before destruction. mcpm update already shows a diff before applying; that pattern must extend uniformly to every destructive call. mcpm uninstall must list the files it will touch before asking the y/N; mcpm secret unset must show which servers depend on that secret before purging; mcpm registry remove must show how many installed servers came from that registry. Preview-before-destruction is part of the error-recovery surface because most "errors" the user reports will actually be self-inflicted: they ran a destructive command and the system did exactly what they asked. The cure is to make "exactly what they asked" visible in advance. GitHub CLI's paranoid --confirm flag — type the repo name back — is the right reference here for the truly irreversible cases (purge a secret, wipe state); the rest get a normal y/N with a list above it.

Fourth: no silent failure, ever. If we cannot do the thing, we refuse loudly and audit-log the refusal. If we successfully do the thing, we audit-log the success. The audit JSONL is the source of truth for "what happened, when" — and it must be readable by mcpm logs --audit with the same four-field shape as a live error (code, what, why, what-to-do-now-or-next-time). Stack traces stay in mcpm logs --daemon; the user-facing error UX is the curated subset. This is the RFC 7807 insight — separate the machine-readable problem details from the human-readable narrative, then make both available.

Fifth, and this is where my peers and I will fight the most: refusal is not an error. The trust gate refusing to load a cloned-elsewhere .mcp-manager.toml is a successful enforcement, not a failure — but the user-experience of that refusal must still be a four-field artifact. E_PROJECT_UNTRUSTED is a refusal, not a crash, and its recovery (mcpm project allow) is the user choosing to override. The empathy-led-designer is going to want gentler language for these; the mental-model-coach is going to want different names. I'll defend the structural pattern — refusal-with-recovery is still E_* shaped, still has a related_cmd, still ends with a next command — and yield on tone within that structure.

Arguments against my four peers

Against empathy-led-designer

The empathy-led designer will read the existing error taxonomy, recoil at the E_KEYCHAIN_UNAVAILABLE-style codes, and propose softening every message into prose: "We couldn't reach your keychain — here's what you can try." She is right about tone, and wrong about structure. Tone is paint; structure is plumbing. The E_* code must remain in the output, because the moment a user pastes the error into a search engine or a GitHub issue, they need the canonical lookup key. Stripe's error codes work for the same reason — card_declined is a contract between Stripe, the docs, support, and the developer. Strip it and you've broken the relationship. So my proposal to her: keep the code and rewrite the prose. The four-field shape is:

✗ E_SECRET_MISSING — github needs a token that isn't set up yet.

  What happened
    github won't start because GITHUB_TOKEN isn't in your keychain or environment.

  Why
    MCP Manager refuses to spawn servers with missing secrets — silently
    starting with a placeholder would leak into your editor as an
    authenticated session that isn't authenticated.

  What to do
    $ mcpm secret set GITHUB_TOKEN
    Then re-run:
    $ mcpm start github

  More:  https://docs.mcp-manager.dev/errors/E_SECRET_MISSING

The empathy designer gets her prose voice in "What happened" and "Why"; I get my code, my command, and my doc link. She'll also push to soften refuse to can't — and she should win that on E_KEYCHAIN_UNAVAILABLE (truly an external failure) but lose it on E_PROJECT_UNTRUSTED (we are deliberately refusing). The verb has to match the agency. Nielsen Norman's error-message guidelines are clear on this: errors should be polite, precise, and constructive — never euphemistic. Euphemism erases the user's mental model of what the system is doing, which is the opposite of empathy.

Where I cede ground: the order of fields can be reordered for kindness ("What happened" first, "Why" second, "What to do" last with visual prominence). The ✗ glyph can soften to • for refusals-by-design (project untrusted) and stay sharp for crashes (server failed). The TUI modal title can be "github needs a token" rather than "ERROR: E_SECRET_MISSING" — but the code stays in the body, above the fold. Tone is paint.

Against data-driven-pm

The data-driven PM will want a counter on each E_* code: how often does it fire, what's the recovery rate, what's the time-to-recovery. He will be tempted to add a network endpoint that ships this telemetry home. No. The product is local-first and privacy-respecting; the audit JSONL on the user's own disk is the only place this data exists. But within that constraint, his instinct is right, and we should harness it: mcpm doctor can read the user's own audit log and tell them what their top errors are over the last 30 days. That's a feature, not telemetry — the user gets to see their own pain points and we never know about it.

The audit-log entry shape I want for every error matches the four-field user-facing shape, so doctor's aggregation is trivial:

{"ts":"2026-05-27T14:33:12.118Z","level":"error","actor":"cli",
 "code":"E_SECRET_MISSING","server":"github","secret":"GITHUB_TOKEN",
 "what":"github won't start because GITHUB_TOKEN is not configured",
 "why":"missing-secrets refuse policy",
 "remedy_cmd":"mcpm secret set GITHUB_TOKEN",
 "doc":"https://docs.mcp-manager.dev/errors/E_SECRET_MISSING"}

This is RFC-7807-shaped (type, title, detail, instance) with concrete-recovery extension fields, which is exactly what RFC 7807 anticipates in its "extension members" section. Where the PM and I clash: he'll want a severity field with five levels (debug/info/warn/error/fatal); I'll push back to two (error and refusal) because the user doesn't care about our internal taxonomy of badness, only about whether they can move on. If doctor wants to compute trends, it can do so on the recovery latency (gap between the error line and the successful-retry line in the same actor's audit stream), not on a severity field we invented.

He'll also push for an --exit-code-stable contract so CI can branch on errors. That's a good fight to lose: each E_* maps to a stable exit code (the anyhow / color-eyre ecosystem makes this easy on the implementation side), and the --json envelope carries the code as a string so non-shell consumers don't need to memorize integers. The exit codes themselves are documented in the mdbook, alongside the error pages.

Against onboarding-specialist

The onboarding specialist's 60-seconds-to-value mandate will tempt her to swallow errors during onboarding — to keep the flow moving by silently retrying, picking defaults, or deferring problems. That instinct is wrong by an order of magnitude. The errors that hit during the first 60 seconds are the most teachable moments in the entire lifecycle of the tool; if we paper over them, we rob the user of the model they need for every subsequent error. The right move is the opposite: errors during onboarding get the most hand-holding, not the least.

Concretely, the four first-launch transcripts in the worst-case branches should each end with a recovery, not a failure:

  • Transcript W1 — keychain missing on Linux. mcpm init detects no libsecret / no kwallet, emits E_KEYCHAIN_UNAVAILABLE with a remedy that names the user's distro's keychain package (we know the distro from /etc/os-release). Recovery: print apt install gnome-keyring or equivalent, then mcpm init --resume.
  • Transcript W2 — registry unreachable on first sync. mcpm init hits E_REGISTRY_UNREACHABLE; the recovery is to offer offline mode (cached/baked-in registry index), audit-log the offline mode entry, and resume with a banner that the registry will refresh on next online use. Critically: do not hide the error. Onboarding tells the user: "we couldn't reach the registry; we'll proceed with the baked-in index. Run mcpm registry refresh when you're online."
  • Transcript W3 — service-register fails (no systemd, no launchd permissions). Detected, audit-logged as service.register.failed, recovery is "we'll run the daemon foreground for this session; to set up auto-start later, run mcpm doctor --fix-service". The onboarding does not abort.
  • Transcript W4 — project trust gate refuses a cloned .mcp-manager.toml. Not an error in the colloquial sense, but presented with the same four-field shape: E_PROJECT_UNTRUSTED + remedy + mcpm project allow.

Where she and I align: every error during onboarding should suggest a continuation, not just a fix. "Run X, then re-run mcpm init --resume" — that --resume flag is non-negotiable. It picks up at the step that failed, not from scratch. Idempotency is the substrate; resume is the affordance.

Against mental-model-coach

The mental-model coach will object to the E_ prefix on the grounds that codes are jargon. He'll propose human names: SecretMissing, ServerCrashed, RegistryUnreachable. He's half right. The codes work because they're greppable — across docs, audit logs, GitHub issues, and stack traces — and PascalCase names work equally well as long as we're consistent. The deeper objection is real though: the codes need to be nameable, not just unique. E_SPEC_UNSUPPORTED is fine; E_DAEMON_VERSION is bad — what about the daemon version? Stale? Future? Mismatched? I'll concede a rename to E_DAEMON_TOO_OLD and audit the rest of the taxonomy for similar ambiguity. Names should be self-describing the first time you read them; the runbook is for the second time.

The bigger fight is about the mental model the codes establish. The coach wants to group errors into a small number of kinds — "external resource", "user input", "internal", "policy refusal" — so users can route them mentally. I agree, and I want that to be a field in the JSON envelope: category: "external" | "input" | "internal" | "refusal". The taxonomy then teaches the user: "external" errors are the network's fault and retry is reasonable; "input" errors are yours and you should fix the input; "internal" errors are ours and you should file a bug; "refusal" errors are policy and you choose whether to override. That four-way split matches the four-part error structure (code/what/why/what-to-do) and gives the runbook a natural shelf taxonomy.

The coach will also push for the word "error" to disappear from refusals: a trust-gate refusal is not an error, it's a decision. I'll buy it: the TUI modal for E_PROJECT_UNTRUSTED should be styled distinctly (no red, no ✗) — a yellow gate icon, a clear "you can allow this" framing. The CLI can use a different glyph (⊘ for refusal vs ✗ for failure). The JSON envelope still carries the code; the human surface adapts its voice.

Design

Enriched 12-row error taxonomy

Five columns, twelve rows, frozen. The remedy column is now a literal copy-pasteable command (with <NAME>-style placeholders only where context isn't known). The related_cmd column points at the deeper subcommand the user runs to investigate or recover. The category column groups by mental model (external / input / internal / refusal). Every row links into a runbook page at docs.mcp-manager.dev/errors/E_*.

Code · cat.What happenedWhyRemedy (copy-pasteable)Related cmd
E_SECRET_MISSING
input		 Server requires a secret that isn't in the keychain or env. We refuse to spawn with a missing-value fallback — that would leak into the editor as an unauthenticated session. mcpm secret set <NAME> mcpm secret list
E_SERVER_OOM
internal		 Server was killed for OOM. Memory limit hit or system memory pressure. cgroup or RLIMIT_AS killed it. May be a leak, may be a too-tight limit. mcpm config put server.<name>.memory_max_mb 1024 mcpm logs <name> --since=10m
E_SERVER_FAILED
internal		 Server crashed too many times in the restart window; mcpmanagerd stopped retrying. 5 crashes in 60s exceeded the backoff budget. State is now failed; restart is manual to avoid log-flooding. mcpm restart <name> mcpm logs <name> --since=5m
E_CONFIG_INVALID
input		 Canonical config failed validation. TOML parse, schema, type, or constraint error. Validator runs on every write; bad config never lands on disk. mcpm config edit # error at line N:M shown above mcpm config validate
E_CONFIG_CONFLICT
internal		 Canonical config changed on disk while a concurrent put was in flight. CAS guard rejected your put because the file's hash moved (another tool, another shell, or $EDITOR raced). mcpm config get && # re-issue your change mcpm logs --audit --grep config.put
E_REGISTRY_UNREACHABLE
external		 Registry network fetch failed (DNS, TLS, 5xx, timeout). Network or upstream registry is down. Cached index is still usable for mcpm search. mcpm registry refresh --retry # or wait; cache still works mcpm registry list
E_REGISTRY_SIGFAIL
refusal		 Registry index signature did not verify against the trusted pubkey. Either the registry was compromised, the key was rotated upstream, or your trust manifest is stale. mcpm trust refresh && mcpm registry verify mcpm trust status
E_SPEC_UNSUPPORTED
refusal		 Server advertises an MCP spec version mcpmanagerd's allow-list doesn't accept. Future or deprecated spec; refusing prevents undefined-behavior bugs. mcpm config put server.<name>.spec "2026-03-15" # if you trust it mcpm test <name>
E_PROJECTION_DRIFT
refusal		 An editor config's managed-block was hand-edited; projection refuses to overwrite blind. You (or another tool) modified the block we own. Blind overwrite would lose your edit. mcpm projection diff <tool> && mcpm projection sync <tool> --force mcpm projection diff <tool>
E_PROJECT_UNTRUSTED
refusal		 Project config exists but wasn't trust-granted in this session. Cloned-from-elsewhere project configs can ship hostile MCP servers; we require explicit allow. mcpm project allow # reviews the config first mcpm project list
E_KEYCHAIN_UNAVAILABLE
external		 OS keychain service (libsecret / Keychain Services) is not reachable. The keyring daemon isn't running or isn't installed (common on minimal Linux installs). sudo apt install gnome-keyring # or use --from-env as escape hatch mcpm doctor --check=keychain
E_DAEMON_TOO_OLD
input		 mcpmanagerd version is older than the project's min_mcpd_version. The project config pinned a daemon feature you don't yet have locally. curl -fsSL https://mcp-manager.dev/install.sh | sh # or nix flake update mcpm --version

(Rename: E_DAEMON_VERSION → E_DAEMON_TOO_OLD for self-describingness, per the mental-model coach.)

--json error envelope schema

RFC-7807-shaped with concrete-recovery extensions. Every CLI subcommand with --json emits this on stderr (one JSON object per line if multiple) and exits with the stable exit code. The same shape is what mcpm logs --audit --json emits for any error event.

{
  "type":        "https://docs.mcp-manager.dev/errors/E_SECRET_MISSING",
  "title":       "github needs a token that isn't set up yet",
  "code":        "E_SECRET_MISSING",
  "category":    "input",
  "status":      "refused",       // "refused" | "failed"
  "exit_code":   13,
  "instance":    "urn:mcpm:server:github",

  "what":        "github won't start because GITHUB_TOKEN is not configured.",
  "why":         "Missing-secret refuse policy: we never spawn with a placeholder.",
  "remedy":      "Run `mcpm secret set GITHUB_TOKEN`, then `mcpm start github`.",
  "remedy_cmd":  "mcpm secret set GITHUB_TOKEN",
  "related_cmd": "mcpm secret list",
  "doc":         "https://docs.mcp-manager.dev/errors/E_SECRET_MISSING",

  "context": {
    "server":  "github",
    "secret":  "GITHUB_TOKEN",
    "scope":   "user"
  },
  "trace_id":   "01HXP3V8K2..."   // links to mcpmanagerd's tracing log
}

Notes on the shape:

  • type is the doc URL — directly clickable in modern terminals (most emit OSC 8 hyperlinks for URLs).
  • title is the human one-liner — also the TUI modal title.
  • code is the canonical lookup key.
  • category is the four-way split (external / input / internal / refusal).
  • status distinguishes refusal (policy worked correctly) from failure (something broke).
  • what, why, remedy are the human prose; remedy_cmd is the literal command (for clipboard).
  • context is event-specific and may include keys that violate "values never appear in audit fields" — implementations must scrub secret-typed fields here.
  • trace_id ties the user-visible error to the daemon's tracing logs for deep debugging.

Preview-before-destruction spec

Every destructive command emits a preview before prompting for confirmation. The preview must list (a) what files will change, (b) which entities will be removed or modified, (c) what is irreversible. The confirmation paranoia level scales with reversibility:

CommandPreview showsConfirm pattern
mcpm stop <server>(none — reversible)None
mcpm restart <server>(none — reversible)None
mcpm update [--all]Per-server diff: from version → to version, breaking-change flags, what tests will runEnter to apply; -y skips; --dry-run never prompts
mcpm uninstall <server>Which canonical config rows, which projection rows in which editor configs, which secrets become orphanedy/N
mcpm uninstall (the whole tool)All files in config dir, all projection edits to be reverted, whether audit + keychain are preserved (default yes)Type UNINSTALL
mcpm secret unset <NAME>Which servers depend on this secret (will start failing with E_SECRET_MISSING)Type secret name
mcpm registry remove <name>How many installed servers came from this registry (they'll lose update tracking)y/N
mcpm project allow --forceSHA256 of the toml + diff against any known-trusted prior versiony/N
mcpm config wipeEverything that will be deletedType WIPE

The preview itself is rendered by the same diff-printing code as mcpm update (uses git diff if available, falls back to a built-in colorized diff). The TUI version renders the preview in a modal with the same y-to-copy affordance — copy the preview, paste it into a chat with a teammate, get a second opinion before confirming.

mdbook runbook outline

One page per E_* code at docs.mcp-manager.dev/errors/E_*. Each page has the same six sections — the structure is itself a teaching tool, because users learn to know where to look:

  1. One-liner. The same title field from the JSON envelope. ("github needs a token that isn't set up yet.")
  2. When this fires. The precise conditions — what mcpmanagerd checked, what it found, what triggered the refusal/failure.
  3. Why we refuse / fail this way. The policy or fault model. ("We never silently fall back to a missing-value placeholder because…")
  4. Quick fix. The literal command, copy-pasteable. Same as remedy_cmd.
  5. If the quick fix doesn't work. The escalation path — related diagnostic commands, common gotchas, links to other E_* pages that often follow this one.
  6. Audit-log signature. The exact JSONL line shape the user will see in mcpm logs --audit --grep E_* — so they can write their own monitoring or scripts against it.

The runbook is part of the binary's distribution promise: when we ship a new E_* code, we ship a new runbook page in the same release. CI enforces this with a check that every E_* string anywhere in the source has a matching page in book/errors/. No code lands without a doc.

Component coverage

Onboarding flow

Errors during onboarding get a --resume affordance on every step. The init flow is broken into named stages (preflight, keychain, service-register, registry-sync, scaffold-config), each idempotent, each resumable. If any stage emits an E_*, the user gets the four-field error and a literal mcpm init --resume --from-stage=<name> command. Crucially, onboarding errors are presented in the same shape as runtime errors — users learn the format once.

TUI experience

Error modal: code top-left in monospace; title centered; What/Why/What-to-do as a vertical stack; the remedy command in its own bordered box at the bottom; y copies the command, Esc dismisses, l jumps to relevant logs, ? opens the runbook page in the system browser (falls back to $PAGER if no open/xdg-open). The ✗ badge persists in the left pane until the user takes an action — and clears on the next successful audit event for that entity. Refusals use ⊘ and a yellow accent; failures use ✗ and a red accent.

CLI experience

Stderr format follows the four-field template. Color is honored (NO_COLOR / --no-color). When stderr is not a TTY, ANSI codes are stripped automatically (matches no-color.org). --json swaps the prose for the envelope above. Exit codes are stable per E_* and documented in the mdbook.

Config files

E_CONFIG_INVALID is the showcase: validator emits line + column + the offending token, plus the closest valid alternative if it can guess one (typo-detection via Levenshtein distance against known keys). Error includes a mcpm config edit recommendation that opens $EDITOR with the cursor positioned at the offending line.

$EDITOR integration

If $EDITOR exits non-zero, that's not an error — the user just bailed. We preserve the temp file at a known path and tell them: "Your edits are in ~/.cache/mcpm/edit-XXXX.toml if you want to retry." If $EDITOR writes a file that fails validation, we re-enter the editor with the validation error injected as a TOML comment at the offending line. The temp file is never lost without the user explicitly saying so.

Idle TTL killings

Idle TTL is not an error — it's a normal lifecycle event. The audit log records it as server.idle_stop, not server.crash. The TUI shows it as idle status (not failed). The user sees no error UX. If the user tries to use a server that's TTL-stopped, the next request transparently spawns it back up — and the audit-log entry for that spawn includes reason: "wake-from-idle" so debugging "why are there so many spawn events?" is easy.

Singleton vs per-client collisions

If two clients both want a server with conflicting singleton settings, we emit E_SERVER_SINGLETON_CONFLICT — but only if the conflict is structural (incompatible flags). If both clients want singleton mode, we share the existing process (the whole point of singleton). The error case is rare but the audit log records every spawn decision with the client_id field so the user can answer "why is server X running 3 copies?" with mcpm logs --audit --grep server.spawn --server=X.

Update notifications

If mcpm update fails partway, we roll back atomically — and the error envelope's context field lists which servers were updated, which were reverted, and which were untouched. The user is never left in a half-state without knowing it. The audit log carries the full pre-update lockfile hash so the rollback is verifiable.

Accessibility commitments

Errors do not rely on color alone — every error has a glyph (✗ for failure, ⊘ for refusal) and a clear text label. Screen-reader-friendly: all four fields read in order, with semantic delimiters. The runbook URL is always available so users who prefer reading the docs to scanning a terminal modal have that option. --no-color + --no-glyph (for the rare terminal that mangles unicode) produces ASCII-only output that reads unambiguously.

Citations

  1. Nielsen Norman Group — Error-Message Guidelines. Four traits of a good error message: human language, polite, precise, constructive. Foundational reference for the four-field shape.
  2. RFC 7807 — Problem Details for HTTP APIs. The shape of {type, title, status, detail, instance} plus extension members; our --json envelope is a direct adaptation.
  3. Stripe — Error Codes Reference. Canonical example of a stable string-keyed error vocabulary that doc, support, and developer ergonomics depend on.
  4. GitHub CLI — gh repo delete. The paranoid --confirm-by-typing-the-name pattern we copy for irreversible operations (secret purge, full wipe).
  5. anyhow — Rust error handling library. The pattern of "errors are context-rich, chainable, but the user-facing presentation is a curated subset" matches our split between mcpm logs --daemon (rich) and the user-facing modal (curated).
  6. color-eyre — pretty-printing error reports for Rust. Reference for sectioned error output with help / suggestions / spans — directly informs the four-field template.
  7. no-color.org — the NO_COLOR standard. Honored universally; informs how the CLI strips ANSI when stderr is not a TTY.
  8. k9s — terminal UI commands reference. The hint-bar pattern, modal copy-to-clipboard (y) muscle memory, and "? opens help" are direct inspirations for the error modal UX.
  9. Dan Slimmon — Do-nothing scripting. The "every step is named, idempotent, and resumable" pattern that justifies mcpm init --resume --from-stage.
  10. AWS — Designing for Failure in the SDK. The principle that error UX is part of the SDK contract, not an implementation detail.
  11. Command Line Interface Guidelines — Errors. The "tell the user what to do next" rule that our remedy_cmd field operationalizes.
