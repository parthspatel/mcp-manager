The Onboarding Specialist's UX

60 seconds to first MCP. Five questions, not fifty. Detect over prompt. Preview before commit. The release gate is the wall-clock between curl | sh and an AHA-moment: the user watching Claude Code call the time MCP server they didn't know they'd just installed. Everything else in v1.0 is in service of that arc.

Thoughts

The north star: 60 seconds, one running MCP, one connected editor

Every product that has ever crossed the chasm has had a moment where the user, sometimes against their better judgement, leans forward and says "wait, that actually works." Activation people call this the "aha moment" — a phrase that has become so over-used it risks meaninglessness, but the underlying observation is true and load-bearing[1][2]. For MCP Manager v1.0, the AHA-moment is unambiguous: the user types one query in Claude Code (or Cursor, or Zed, or Codex) and the model invokes an MCP tool that we installed in the previous minute, returns a real answer, and the user understands that this is now a stable platform on which to install more servers. The release gate I want is wall-clock: 60 seconds, from the end of curl -fsSL https://install.mcp-manager.dev | sh to that first tool call returning data. That is the bar. Everything in this document is reverse-engineered from it.

Why 60 seconds and not 5 minutes

Stripe ships its CLI to be useful within seconds of installation[3]; Vercel's CLI puts you on a deployed URL faster than most tools render their splash screen[4]; GitHub CLI asks the questions it cannot infer and nothing more[5]. The pattern is consistent: the first encounter must be a working encounter, in seconds, not minutes. Five minutes is a coffee break and a Slack context-switch; sixty seconds is "the demo is still running" and the dopamine spike lands at peak attention.

The single highest-leverage move: detect, don't prompt

Every prompt in mcpm init costs the user attention. The empathy-led peer wants more "kind" prompts, the recovery-advocate wants more "did you mean…?" branches. I disagree with both at the margin: a prompt the user could have skipped because we knew the answer is not kind, it's lazy. The kindness is the inference. mcpm has access to $SHELL, $EDITOR, the filesystem (which editor configs exist?), which docker, uname, the canonical config paths of ~/.claude/ / ~/.cursor/ / ~/.config/zed/ / ~/.codex/, and the locale. From those signals we can pre-fill every answer that has a "right" default. The prompt becomes "I detected these three things; press Enter to accept" — a single keystroke instead of four.

The second highest-leverage move: install one trivial demo MCP automatically

The most user-hostile possible outcome of mcpm init is success with zero servers installed. The user has now configured a manager but has nothing to manage. They have to read more docs, decide which server to try, run another command, and re-attempt activation — all while their motivation is bleeding out. The fix is the oldest trick in onboarding playbooks: install a stub on their behalf. The community ships mcp-server-time (or equivalent — current-time, fortune, echo) that has zero secrets, zero config, zero permissions, and a single tool. mcpm init installs it by default, projects it into every detected editor, and the post-init message says "open Claude Code and ask it what time it is — that tool call goes through MCP Manager." That sentence is the AHA-moment, written in advance, and we control the path from "init complete" to "tool call returns" so tightly that we can measure it as a release gate.

Why a non-secret demo server matters

E_SECRET_MISSING is the single most common reason a first-launch dies — the user installs github-mcp, doesn't have a GITHUB_TOKEN, hits the error, leaves. A demo server with zero secret requirements sidesteps that path on first run. Users graduate to secret-requiring servers after the AHA has landed. This mirrors create-next-app: the starter app works locally with no configuration; env vars come later[6].

Preview-before-commit as the central trust mechanism

The locked spec's "show what you're about to change" principle is right but understated. On first launch the user has zero installed mental model of what files mcpm touches; if we just write 7 files across ~/.config/, ~/Library/Application Support/, ~/.claude/, and the project tree, the user feels invaded. The fix: a single "Here is the plan" screen that lists every file we will create or modify, with byte counts, before any write happens. Press Enter to apply. Press e to edit individual lines (toggle a projection off, change the demo server, etc.). Press q to abort with zero files written. This pattern is borrowed directly from terraform plan and from package managers like apt that show the change set before applying[7]. Combined with the idempotency guarantee already in the spec, the user can hit Enter knowing that worst case they can re-run.

What 5 questions look like (max — usually fewer)

The locked transcripts have 4 questions in Transcript 1, 3 in Transcript 3, 1 in Transcript 4, and 1 in Transcript 5. That's already lean. I want to compress further by collapsing Question 1 ("project into detected toolchains?") into the preview screen — show the user "we'll touch ~/.claude/mcp_servers.json and ~/.cursor/mcp.json" in the preview rather than asking up-front. That drops the lucky-day count from 4 to 3 prompts: docker-enable, demo-server, service-register. Each is a single keystroke with a sensible default. The hard cap is 5; the practical goal is 3.

What should NOT be surfaced on first run

Three locked-spec features that should be deliberately invisible during init:

  • Idle TTL. The fact that an unused server suspends after 1800s is operationally correct and conceptually irrelevant to a 60-second goal. Surfacing it confuses users who don't yet know what a server is in our world. It lives in advanced docs.
  • Singleton vs per-client process model. The default (singleton=true) is correct; the alternative is an edge case. Mentioning it costs us thirty seconds of attention for zero first-run value.
  • Telemetry. Because there is none (data-driven-pm's local-only metrics live entirely on the user's machine), there is no prompt. The only mention is a single line in the post-init "what just happened" message — "we collected zero data about you; metrics live in ~/.local/share/mcp-manager/metrics.db if you want to read them."

The four transcripts we owe the spec

The locked v1.0 spec names four first-launch transcripts (lucky-day, non-interactive, project-scope, cloned-from-elsewhere). I design each line-by-line in the design section with timing annotations. Three observations carry across all four: env-detection runs once at the top and pre-fills everything; the preview screen is identical in shape across all four (non-interactive echoes the preview to stderr); the post-init "Now what?" message ends with one mdbook URL — but the AHA arrives before they need it.

Arguments

Against empathy-led-designer

My empathy-led peer wants tone audits on every string, "kind defaults," extra confirmations so the user feels in control. We agree on 80% of substance — both reject error messages that read like dmesg. But where they want more moments of pause, I want fewer. Empathy is not synonymous with caution; sometimes empathy is "I respect your time enough to do the obvious work for you." Krug's rule — "Don't make me think" — applies[8]. A prompt with a default I'd accept 95% of the time is one I should not be shown at all.

Concretely, where I diverge:

  • Tone audits, yes; extra prompts, no. I will happily concede every word of every error message to my empathy-led peer. What I will not concede is splitting a single 3-keystroke decision into three separate "are you sure?" screens.
  • Confirmation friction matches reversibility (locked spec). The spec already nails this: y/N for delete, type-the-name for purge, type-WIPE for nuclear. First-launch mcpm init is the least destructive action in the entire tool — every file it writes is recoverable from --force backups. It does not need extra friction.
  • The empathy is the inference. The kindest thing we can do for a tired developer at 4pm on a Thursday is to not make them confirm that yes, they do have Claude Code installed, when we just read the directory three milliseconds ago.

Against data-driven-pm

My PM peer wants local-only metrics so we can answer "is the 60-second goal actually met?" without violating privacy. We agree completely on the goal. We diverge on the timing of when those metrics get collected and whether the user ever sees a prompt about them.

  • Zero telemetry prompt on first run, ever. If the metrics are truly local-only, there is nothing to consent to. Asking the user to "consent" to data they own and never leaves their machine creates the false impression that we're collecting something. We're not. The fact gets one line in the post-init message and a sentence in the docs.
  • Metric: time-to-first-tool-call, computed locally. mcpd records the wall-clock between the audit-log init.complete entry and the first server.tool_call entry. That delta is the user's personal 60-second-or-not number. mcpm status can show it. We never see it.
  • Don't put a "skip telemetry?" prompt in the 5-question budget. That's a question that doesn't deserve a slot because the answer is always the same: there's no telemetry to skip. Spending a prompt on it would be a wasted user attention unit.

Where my PM peer is right and I'm wrong: I would shortcut metric collection to "only collect if user has run mcpm init with the demo server." The PM is correct that we should collect the timing data unconditionally in the local audit log so a power user who wants to investigate their own setup can. I cede this.

Against error-recovery-advocate

My recovery peer wants the 12-row error taxonomy from the locked spec to grow more branches — more "did you mean…?", more interactive recovery flows, more in-init guidance for when things go wrong. We agree on the principle that every error must carry a fix. We diverge on where in the user journey those branches belong.

  • Make first-launch errors structurally impossible, don't recover from them. The 12-row taxonomy includes E_SECRET_MISSING (no secret in keychain), E_REGISTRY_UNREACHABLE (network), E_KEYCHAIN_UNAVAILABLE (Linux without libsecret). All three can hit a user during init. My answer: install the demo server, which requires zero secrets, ships with the binary (no registry fetch), and uses no keychain. The first-launch error rate for these three codes drops to zero by construction. Recovery branches matter on day 2; on day 1 we engineer them out.
  • The error taxonomy applies after the AHA. Once the user has seen the tool work, an E_SECRET_MISSING error on their second server install is a teachable moment — they understand what an MCP server is, what secrets are, why we need one. The same error on minute one is a wall.
  • One first-launch error I do want to handle gracefully: the editor we projected into wasn't actually running. mcpm can't auto-launch the editor, but the post-init message should say "if Claude Code is already open, restart it so it picks up the new server." That sentence prevents a confused user who got the projection right but didn't know to reload.

Where the recovery peer is right: a non-trivial fraction of users will hit locked libsecret or no GUI keychain. The demo server saves them on day 1; on day 2, their github-mcp install needs the recovery branches. Structural prevention on first run; recovery taxonomy from second run on.

Against mental-model-coach

My mental-model peer wants to fight every jargon term and rename our vocabulary so users acquire a correct mental model fast. We agree on this completely — "projection" is a load-bearing term, "managed block" is another, and we should both be religious about consistency. We diverge on how much vocabulary the user must acquire during init.

  • The init flow should teach zero concepts. Users learn vocabulary by needing it. On day 1, they need exactly two terms: "MCP server" (the thing being managed) and "editor" (the thing that calls the server). Everything else — registries, projection, isolation, devenv, scope — is not in the lucky-day script at all.
  • Project-scope adds exactly one concept: trust. The cloned-from-elsewhere transcript introduces "trust" the same way direnv does, because the user has a concrete reason to care (someone else's code is about to run). That's a justified vocabulary expansion. Anything more is premature.
  • "Toolchain" is wrong; say "editor." My mental-model peer is going to argue that "toolchain" is more accurate. They're right. But on first-run, the user knows "editor"; they don't know "toolchain." The internal docs and config files can say toolchain; the first-run prompts say editor.

Net concession to my peer: yes, the vocabulary we do introduce must be perfectly consistent — if we say "MCP server" once we never say "tool" or "plugin" to mean the same thing. I'll review every prompt string against their vocabulary doc.

Design

The AHA-moment definition

The AHA-moment is the first time the user observes their editor (Claude Code, Cursor, Zed, Codex) successfully invoke an MCP tool that mcpm installed. Concretely, in the local audit log we look for two adjacent events: 

2026-05-27T14:33:01Z  init.complete       scope=user demo_server=time
2026-05-27T14:33:48Z  server.tool_call    server=time tool=now editor=claude-code ok=true

Wall-clock delta: 47 seconds. That is the metric. The 60-second release gate is failed if, in our internal beta sample (N≥10 reasonable Mac/Linux laptops with Claude Code installed), the median delta exceeds 60 seconds. The metric is computed locally, on the user's machine, from the audit log they own. No data leaves the host.

Env-detection algorithm

Run once, at the very start of mcpm init, before any prompt. The detector emits a JSON blob that pre-fills every default. The algorithm is intentionally cheap (no network, no shelling out to package managers; just filesystem reads + which):

  1. OS + shell. uname -s → mac|linux. $SHELL → bash|zsh|fish|nu. $XDG_CONFIG_HOME falls back to platform-default.
  2. Editors. Probe canonical config paths:
    • Claude Code: ~/.claude/ exists
    • Cursor: ~/.cursor/ or ~/Library/Application Support/Cursor/ exists
    • Zed: ~/.config/zed/ exists
    • Codex CLI: ~/.codex/ exists, or which codex succeeds
    • VS Code: ~/Library/Application Support/Code/User/ or ~/.config/Code/User/ exists
  3. Docker. which docker succeeds AND docker info exits 0 (i.e., daemon is running, not just installed).
  4. Keychain. macOS always yes; Linux: secret-tool on PATH OR kwallet5 binary exists.
  5. Service manager. macOS launchd is always available; Linux: systemctl --user is-system-running doesn't error.
  6. Project context. If ./.mcp-manager.toml exists, switch to project-scope flow (trust-gate transcript). If ./.git exists, project-scope is offered as a non-default.
  7. Existing init. If $XDG_CONFIG_HOME/mcp-manager/config.toml exists, switch to idempotent re-run (print "already initialized" + sha + exit 0).

Output: a small TOML blob displayed at the top of the interactive flow ("We detected:"), and a JSON blob written to $XDG_STATE_HOME/mcp-manager/last-detect.json for debugging.

The five-question script

Worst case (everything detected, lucky day): 3 prompts. Hard cap: 5. The questions, in order, with their detection-default:

#QuestionDefault from detectSkippable?
1"Install the time demo MCP server so you can test the setup?"YNo — this is the AHA path. --no-demo opts out.
2"Enable the Docker MCP Catalog as an additional registry?"Y if docker daemon running, else N (skip question entirely)Yes (only asked if docker present)
3"Register mcpmanagerd to start at login?"N (auto-spawn covers the common case)Always asked; one keystroke to default-No
4(project-scope only) "Trust this project's MCP config?"N (direnv-style explicit allow)Only asked for project-scope; mandatory there

The locked spec's Transcript 1 has four prompts; my script has three on the lucky day (Q1, Q2 only if docker, Q3) and four max for any user. Question 5 is reserved and not shown on the lucky day.

Preview-before-commit spec

After all questions are answered (or for --defaults -y, immediately after detection), mcpm renders a single preview screen. Nothing has been written yet. The user can:

  • Press Enter — apply the plan.
  • Press e — open $EDITOR on the plan TOML; on save, re-render the preview with edits applied.
  • Press q — abort. No files written. Exit 0.
  • Press d — show a unified diff of every file we will create/modify against current state (current state being either empty or the previous config, in re-init).

The preview is structured as: header (target scope + version), files-to-create section (with byte counts), files-to-modify section (managed-block diff), background-effects section (service register? auto-spawn? demo install?), and a footer with the three keystrokes. Width: 80 cols. Renders identically in non-interactive mode but skips the keystroke handler.

60-second release gate

The release gate has two enforcement points:

  1. Internal beta dogfood metric. Before v1.0 ships, 10+ team members run the full curl | sh → mcpm init → first tool call path on personal machines (Mac + Linux mix, Claude Code + Cursor mix). Median wall-clock must be ≤ 60s. 90th-percentile must be ≤ 90s. We track in a shared sheet (filled in by hand from each tester's local audit log, which they own).
  2. Public-launch readiness check. The mdbook docs include a one-page "Quickstart" that the user can clock themselves; the page tells them "if this took you more than 90 seconds, we screwed up — please open an issue with your output."

Failing the gate blocks v1.0 release. Mitigations if the gate is failing: shrink the demo server's startup time (it's already <100ms), ship more pre-bundled binaries to skip download steps, drop a question, improve the projector to be parallel rather than sequential.

Accessibility commitments (first-run-specific)

The locked v1.0 spec's a11y commitments (color+glyph, NO_COLOR, keyboard-only) apply throughout. Three first-run-specific extras:

  • Screen-reader-friendly preview. The boxed preview ASCII renders an alternate plain-text version when NO_COLOR is set OR TERM=dumb OR $ACCESSIBILITY_MODE is exported. The plain-text version is the same content with no box-drawing characters.
  • Pace your own output. No timed animations or spinners during the wait between detect and first prompt. The status output is line-oriented so a screen reader can read it as it's written.
  • Locale honored. mcpm reads $LANG; if v1.0 only ships English (it does), the post-init message includes a "translations welcome" pointer for non-English users.

"Now what?" — linking into mdbook

The post-init message has exactly one outbound link: https://docs.mcp-manager.dev/v1.0/first-mcp. That page has three sections: (1) "you just installed the time server, here's how it works" — confirming the AHA they just had; (2) "your next install" — walking through mcpm install official/github-mcp with secrets; (3) "common patterns" — a small catalog. Update notifications are the only other in-flow link, surfaced by mcpm status when a new version is detected, never during init itself (we don't want to distract a fresh user with "you should upgrade me" before they've finished installing).
