UX — Facet Synthesis

Where the five UX stances converge, where they diverge, and what gets adopted into v1.0. The empathy-led designer, the data-driven PM, the onboarding specialist, the error-recovery advocate, and the mental-model coach each pulled on a different thread of the same garment. This page weaves them together, honors the locked v1.0 surface (TUI in ratatui, nineteen CLI subcommands, four onboarding transcripts, twelve-row error taxonomy, auto-spawn daemon, no telemetry, GUI deferred), and picks a position on the open naming fights.

Where the five agree

Despite their different vantage points, all five stances converge on the same six commitments. These are not voted; they are recurrent. If any one of them is missing from v1.0, the agent who would have written it walks away unhappy — and so will the user.

  1. Preview-before-destruction is universal. The empathy-led designer wants it for safety (empathy · design); the onboarding specialist wants it as the central trust mechanism on first launch (onboarding · preview); the error-recovery advocate wants it as the upstream remedy for "errors" that are really self-inflicted destructive commands (recovery · design). The pattern: every mutating command shows a textual plan (files created, files modified, services touched, secrets referenced) before any write happens, with friction scaled to reversibility — Enter for reversible, y/N for moderate, typed literal (UNINSTALL, WIPE) for irreversible. mcpm init itself adopts this: the four detected-editor projection-targets and the demo-server install are surfaced on a single preview screen before any file is written.
  2. Detection beats prompting; prompts are explained. The onboarding specialist's "kindness is the inference" (onboarding · detect) and the empathy-led designer's "one indented clause per default" (empathy · design) are the same move from two directions. mcpm init runs a cheap detector first — OS, shell, editors on disk, Docker daemon liveness, keychain availability, project context — and only asks questions whose answers it cannot infer. Every remaining prompt names why the default is what it is, in one indented sub-line.
  3. The error envelope is a four-field artifact. Code, what-happened, why, what-to-do — with the next command as a literal copy-pasteable string. The error-recovery advocate codifies it (recovery · design); the empathy-led designer's tone-audit table is what fills the human-prose fields (empathy · design); the data-driven PM logs the code (never the body) so the user can self-diagnose in mcpm doctor (pm · design); the mental-model coach insists the human title sits on the three-noun frame (coach · arguments).
  4. No telemetry ever leaves the machine — but local measurement is welcome. The "no telemetry" lock is treated as non-negotiable by every agent, including the PM whose job would normally argue otherwise (pm · thoughts). Local NDJSON event logging exists strictly to make the user smarter about their own setup (via mcpm doctor --history and mcpm support-bundle) and is gated behind a privacy checklist whose key rule is "no field that could embarrass the user if leaked": no argv, no paths, no secret names, no error message bodies, no cross-session correlation IDs.
  5. Refusal is not failure. Trust-gate refusals, projection-drift refusals, and registry-signature failures are policy succeeding, not the system crashing. The recovery advocate splits this into a status: refused | failed envelope field (recovery · design); the empathy-led designer splits glyphs (⊘ for refusal, ✗ for failure) and colors (amber vs. red); the mental-model coach insists "Allow this project's MCP config" replaces ambient "trust" verbiage in the prompt body (coach · design).
  6. Accessibility is a release blocker, not a polish item. Color-plus-glyph everywhere, NO_COLOR honored, keyboard-only operation, screen-reader-labelable glyphs, plain-text fallback for the boxed preview when TERM=dumb or NO_COLOR is set. The mental-model coach adds: every glyph has a one-word screen-reader label — ● is "running", not "filled circle".

Where they diverge

Three real disagreements survive the agreement above. Each requires a position; deferring would mean shipping inconsistency.

1. How many prompts should mcpm init ask? The empathy-led designer wants four prompts with explained defaults (empathy · design). The onboarding specialist wants three with a preview screen replacing the projection-target question (onboarding · five). The error-recovery advocate wants the prompts wrapped in named, resumable stages even if there are fewer of them (recovery · design). Resolution: three lucky-day prompts (demo-install, Docker registry only-if-detected, service-register) plus the always-present preview screen, with each prompt's default carrying an indented one-line "why this default" clause. The preview replaces the projection-target question on the lucky day; cloned-from-elsewhere and project-scope transcripts get their own trust prompt as the recovery advocate requires. Total user-visible questions: three on the lucky day, four max otherwise. This is fewer than the locked spec's Transcript 1 (which has four), and we want that compression — but each surviving prompt is explained.

2. Should v1.0 rename internal vocabulary on user-facing surfaces? The mental-model coach pushes a ten-row rename pass (coach · design); the data-driven PM resists pre-data renaming on the grounds that v1.0 locks muscle memory once (pm · arguments); the empathy-led designer is sympathetic but warns against name churn during the very first release. The synthesis takes a calibrated position, item by item, in decisions. Some renames are adopted (the ones that affect labels users read but not keys power users type); others are deferred to v1.1 (the ones that would create a compatibility scar); one is rejected (renaming the TOML key projection).

3. How heavy should first-launch error recovery be? The onboarding specialist argues for engineering errors out of the first 60 seconds by shipping a zero-secret demo server (onboarding · aha); the error-recovery advocate argues that first-launch errors are the most teachable moments and deserve the most hand-holding via named resumable stages with --resume --from-stage (recovery · arguments). Resolution: both. The demo server (a bundled time MCP with no secrets, no network, no permissions) ships in the binary and is installed by default during mcpm init; this engineers E_SECRET_MISSING and E_REGISTRY_UNREACHABLE out of the lucky-day first 60 seconds. The init flow is still broken into named idempotent stages (preflight, keychain, service-register, registry-sync, scaffold-config, demo-install, project-trust-or-skip) with --resume --from-stage=<name> so the worst-case branches (libsecret missing, no systemd permissions, registry unreachable) still recover cleanly. Structural prevention and graceful recovery — they are not exclusive.

Decisions, by UX surface

Onboarding flow (mcpm init, --docker-enable, first-launch UX)

The detector runs unconditionally at the top of mcpm init and writes its observations to last-detect.json for debug. Three lucky-day prompts: demo-server install (default Y, opt-out via --no-demo), Docker MCP Catalog registry (only asked if docker info returns 0; --docker-enable=true/=false overrides), background-service registration (default N, with the auto-spawn explanation). The preview screen sits between the last prompt and any disk write, listing every file we will create or modify with byte counts, and the install/skip lines for the demo server and service registration. Keystrokes on the preview: Enter applies; e opens $EDITOR on the plan TOML; d shows a unified diff; q aborts with zero files written. Non-interactive runs (--defaults -y) echo the preview to stderr and apply silently. After apply, the post-init message plants the three-noun model in six lines (Servers / Editors / Secrets) and gives one bridge sentence to the AHA-moment: "Open Claude Code (restart if it's already running) and ask it 'what time is it?' — that tool call goes through MCP Manager." The 60-second AHA target stands as an internal beta gate; we measure it locally from the user's own audit log.

TUI experience (the lazygit/k9s feel)

Three panes — Servers, Editors, Secrets — matching the three-noun mental model. The middle pane is renamed from "Toolchains" to "Editors" (adopted from the coach). Modifier-free single keys, q to quit, ? to open contextual help, Esc universally cancels. Error modal layout follows the four-field shape: title at top, What/Why/What-to-do stacked, remedy command in a bordered box, y copies the command (k9s muscle memory), l jumps to relevant logs, ? opens the runbook page. Glyphs: ● running, ○ stopped, ⚠ crashed (renamed from "failed", per coach), ⊘ refused (new — for trust-gate refusals and projection-drift). Color decays from red to amber once the user has acknowledged a row by viewing logs (empathy add, lifted from Linear). Idle-stopped servers show as idle in a neutral tone, not an error tone.

CLI experience (discoverability, error messages, exit codes, completion)

Nineteen subcommands, verbs-in-imperative-present, noun-then-verb for sub-namespaces (mcpm registry add, mcpm secret set). One adopted rename from the coach: mcpm outdated → mcpm check-updates, with outdated retained as an alias for v1.0 (this is the deviation from "lock muscle memory once" the PM warned about; outdated is genuinely an adjective in a list of verbs, and the alias preserves any pre-v1.0 muscle memory). delete is rejected as a verb anywhere; remove is used throughout. Stable exit codes per E_*; --json swaps human prose for the RFC-7807-shaped envelope. NO_COLOR and stderr-not-a-TTY auto-strip ANSI. Shell completion ships for bash, zsh, fish, nu (generated by clap). Every command's --help ends with three "common next steps" lines, never with just usage.

Config files (TOML schemas, per-OS paths)

Paths follow XDG on Linux and Apple's Application Support convention on macOS, both already in the locked spec. Generated configs include a one-sentence why-comment per non-obvious field — idle_ttl_secs = 1800 # auto-stop after 30 min idle; raise if your server is expensive to restart. The TOML keys themselves stay technical (singleton, idle_ttl_secs, projection, inherit) because power users read them twice and grep them often; only the user-facing label changes. Field-level validation runs on every write; the validator emits line + column + the closest valid alternative (Levenshtein-detected typos), and an invalid edit never lands on disk.

The 12-row error taxonomy (clarity, recovery steps)

Twelve rows stays — the PM's warning against bloat carries the day against the recovery advocate's instinct to grow it. The shape inside each row is the recovery advocate's five-column contract: code, short title (mental-model-coach-approved noun-and-verb sentence), what-happened, why, remedy command + related diagnostic command. One code rename adopted: E_DAEMON_VERSION → E_DAEMON_TOO_OLD (self-describing; the coach's audit caught the ambiguity). One new category field on the JSON envelope: external | input | internal | refusal (coach + recovery, agreed). The mdbook commitment: every E_* in source has a matching book/errors/E_*.md page enforced by CI; no error code lands without a runbook page. Every error string ends with a literal command on its own line, separated by a blank line, ready to copy.

The four first-launch transcripts

The locked four transcripts (lucky-day, non-interactive, project-scope, cloned-from-elsewhere) are kept. The lucky-day transcript adopts the onboarding specialist's compression (three prompts + preview screen + post-init three-noun teach) and the empathy-led designer's explained defaults. The non-interactive (CI/Nix/Ansible) transcript echoes the preview to stderr and exits silently in <2 s; --defaults -y is the contract. The project-scope transcript writes .mcp-manager.toml and .mcp-manager.lock and inherits the demo server so teammates re-AHA on every clone. The cloned-from-elsewhere transcript is the longest by design (the trust friction is the feature); it lists every local-executable server explicitly by path, offers y/n/e/r where r opens the local executable in $EDITOR for review before deciding, and records the granted-at timestamp + SHA256 in the trust file.

Trust gate UX

Adopted as the coach proposes at the prompt level: the verb stays mcpm trust at the subcommand layer (and mcpm project allow as the canonical alias the recovery advocate's remedies point at) but the user-facing prompt text in the cloned-from-elsewhere transcript is "Allow this project's MCP config?" with an explicit list of what's being allowed. The prompt body names the registry signer, the trust-manifest refresh date, what changed since the last time the user trusted a config from the same source. Refusal is glyphed ⊘ and styled amber, not red. Trust records SHA256 + path + granted-at; mcpm trust status shows the full ledger.

mcpm.toml inheritance UX

TOML key inherit = "all" | [...] | "none" stays unchanged. The init prompt phrases it as a question: "Use your global servers in this project?" with answers "all", "some" (drops into a multi-select), "none". The default is "all" because that matches the locked spec's stance that user-scope is the base layer and project-scope overlays. Project-scope conflicts (same server name in user and project) resolve project-wins with a one-line audit log entry every time it happens, so a confused user can run mcpm logs --audit --grep inherit.override to see which servers got overridden when.

$EDITOR integration

If $EDITOR is unset, the error message is the empathy-led designer's rewrite — "I tried to open your editor but $EDITOR isn't set. Try export EDITOR=vim (or your favorite), or pass --no-editor to print the config to stdout instead." If $EDITOR exits non-zero, the temp file persists at a documented path and the user is told where. If $EDITOR saves a file that fails validation, we re-enter the editor with the validation error injected as a TOML comment on the offending line; the user's edits are never lost without their explicit consent. e on the preview screen and e on the trust prompt both spawn $EDITOR on the pertinent artifact.

Idle TTL (when surfaced?)

Never surfaced during onboarding. The onboarding specialist's argument wins outright: the user does not yet know what a server is; surfacing the auto-stop policy is premature complexity. The TOML key remains idle_ttl_secs; the TUI displays the value as "Auto-stop after 30 min" (coach rename adopted on the label only). When an idle stop fires, the audit log records server.idle_stop and the TUI's status bar shows a one-line breadcrumb for 10 seconds — "Stopped github (idle 30m). It'll start again on next use." — converting a surprising silence into a known-quantity event. This is the empathy-led designer's idle-TTL notification, adopted verbatim.

Singleton vs. per-client (CLI surface, explanation; renaming?)

The TOML key singleton = true stays (no rename — implementer-facing, grep-friendly, already shipping). The TUI checkbox label uses the coach's plain-English form: "Share one process across editors" (with the inverse "Give each editor its own copy"). The init flow never asks about it; the default singleton = true serves 90%+ of users. The only error-path surface is E_SERVER_SINGLETON_CONFLICT (structural conflict between clients), and its remedy points at mcpm config put server.<name>.singleton false with a plain-English why: "this server keeps per-editor state and needs each editor to get its own process." A power-user reading the doc comment in their config TOML sees both the key and the explanation; a first-time user never has to learn the word "singleton" at all.

Position on the mental-model coach's proposed renames

The coach proposed ten user-facing renames. Synthesis position: adopt seven, defer two to v1.1, reject one.

  • Adopted (TUI/prompt/error-title only, TOML keys unchanged):
    • "Toolchains" pane → "Editors" — restores the three-noun symmetry; no compat cost.
    • idle_ttl_secs = 1800 in TOML displayed as "Auto-stop after 30 min idle" in the TUI and prompts.
    • singleton = true in TOML labelled "Share one process across editors" in TUI/prompts.
    • inherit rephrased to "Use your global servers in this project?" in the init prompt; TOML key unchanged.
    • "failed" status word → "crashed" everywhere (TUI, error titles, audit log human prose).
    • "drifted" → "edited outside" (TUI status, error titles); audit-log enum stays drift_detected.
    • E_DAEMON_VERSION → E_DAEMON_TOO_OLD (the only code-level rename — self-describingness wins; the lock isn't violated because no published release ships the old name).
  • Deferred to v1.1 (locking muscle memory matters; revisit with local-event data):
    • "projection" → "sync" as a user-facing verb. The coach is right that "sync" is more familiar, but rebranding mid-stream while the locked spec, technical design, and audience docs all use "projection" creates documentation churn the PM rightly resists. We adopt the label "Editors" for the pane the projection touches, and we use "sync to editor" as a description verb in TUI hint lines, but the subcommand, the TOML key, the error code (E_PROJECTION_DRIFT), and the doc-page noun all stay "projection" for v1.0. v1.1 reconsiders with data.
    • Splitting "trust" into "allow" (project) and "keys" (registry). The recovery advocate's mcpm project allow remedy line is already in place; the subcommand alias mcpm project allow exists; full subcommand-rename to mcpm keys for registry pubkeys is deferred.
  • Rejected:
    • Renaming the TOML key projection itself. The technical design names this as the central data-model concept, and renaming a foundational key in v1.0 would ripple through architecture docs, schemas, and audit-log enums. The asymmetry the coach himself proposes (technical key + user-friendly label) is exactly the right ratio; we hold it firmly. The label-layer renames above carry the user-facing burden; the key carries the implementer-facing burden.

mdbook docs site (information architecture)

The IA follows the coach's three-noun-first structure with the empathy-led designer's emotional-journey overlay. Top-level chapters:

  1. What is MCP Manager? — one page, the three-noun diagram, <90 seconds reading time.
  2. Install MCP Manager — curl one-liner, Nix flake, verify with mcpm status.
  3. Servers — full lifecycle: install, list, update, remove.
  4. Editors — auto-detection, projection mechanics in user terms, drift recovery.
  5. Secrets — OS keychain, env-var fallbacks for CI/headless, why we refuse the placeholder fallback.
  6. Projects — per-repo configs, the trust gate, sharing with teammates.
  7. The TUI — keymap, panes, log multiplexing.
  8. If something's wrong — error codes (the 12 rows, one page each at /errors/E_*), what each means in plain English, recovery steps. (Empathy: name it the way users will phrase it, not "Troubleshooting".)
  9. Reference — full TOML schema, all CLI flags, audit-log format, the NDJSON event schema, exit codes.
  10. Concepts (optional reading) — daemon architecture, projection mechanics, refcounting, spec negotiation. Tagged "optional".

Update notifications/UX

When a newer mcpm is available, show it once on the next interactive run, in muted text, with the install command, never as a modal, never as a blocker. Never shown during mcpm init itself (a fresh user does not need "you should upgrade me" on first encounter). The phrasing avoids the daemon noun: "MCP Manager update available (v1.0.2 → v1.0.3). Run mcpm update --self to install." If the user hits E_DAEMON_TOO_OLD from a project config's min_mcpd_version, the error message names the version asymmetry concretely and gives the one-line install command, acknowledging that some users have their own install method (Nix, brew, asdf) without insisting on ours.

Accessibility commitments

Color-plus-glyph everywhere (no information conveyed by color alone). NO_COLOR honored, auto-stripped when stderr is not a TTY. Keyboard-only operation in the TUI. Every glyph has a one-word screen-reader label (●=running, ○=stopped, ⚠=crashed, ⊘=refused). Plain-text fallback for boxed previews when TERM=dumb or NO_COLOR is set or $ACCESSIBILITY_MODE is exported. No timed animations or spinners between detection and the first prompt — the status output is line-oriented so a screen reader reads it as it's written. High-contrast theme tested with a screen reader. The release-blocker commitment: a regression in screen-reader behavior is a release-blocker, not a "nice to have". $LANG is honored even though v1.0 ships English only; the post-init message includes a translations-welcome pointer.

Local-only measurement (the PM's contribution, scoped)

Local NDJSON event log at $XDG_STATE_HOME/mcp-manager/events.ndjson (Linux) or ~/Library/Application Support/mcp-manager/events.ndjson (macOS). Mode 0600 on creation, 50 MB rotation cap. Schema frozen at v1.0, gated behind the PM's privacy checklist (no argv, no paths, no secret names, no error bodies, no cross-session correlation). The empathy-led designer's caveat is honored: this exists strictly to serve the user, not to seed a future telemetry pipeline. mcpm doctor --history reads the file and surfaces patterns (recurring errors, time-of-day clustering, abandoned onboarding, drift after edit, trust regret). mcpm support-bundle packages the events log + daemon ring buffer + version + trust status into a tarball the user inspects before attaching to a bug report. The user can disable the log with one TOML line; the act of disabling is itself audit-logged. The post-init message names the file path and invites the user to read it: "we logged seven events about your setup at ~/.local/state/mcp-manager/events.ndjson — open it to see what was captured." The user is a co-author of their own observability, not a research subject.

Open questions for v1.1

  • Does "projection" actually need to die in user-facing surfaces? Deferred above. Once we have local-event data on how often users edit the projected files (a signal the PM's schema captures via config.field_edited on the projected paths) and how often E_PROJECTION_DRIFT fires, we revisit. If drift is rare, the noun has earned its keep. If drift is frequent and users abandon recovery, the rename pays for itself.
  • Should there be a single end-of-onboarding "did this help?" prompt? The PM rejected it; the empathy-led designer is sympathetic but unsure. v1.0 ships without it; v1.1 reconsiders if the local-event funnel shows a meaningful abandonment cliff between init-complete and first-tool-call.
  • Sub-codes inside the 12-row taxonomy. The recovery advocate's instinct to add E_KEYCHAIN_UNAVAILABLE.libsecret / .kwallet / .macos_locked sub-codes is deferred until local-event evidence shows users actually need the disambiguation. The PM's discipline holds.
  • An interactive "first server install" follow-on after the demo server. Once the demo-server AHA-moment lands, should we offer a guided mcpm install official/github-mcp flow on the same screen? The onboarding specialist wants to keep init's surface tight; the empathy-led designer wants to bridge to the second command. v1.0 ships a "Try: mcpm install ..." pointer; v1.1 evaluates whether to make it interactive.
  • A "what changed in this release" summary on first run after update. The empathy-led designer's principle (never blocking, never modal) suggests yes; the PM wants it gated behind the local-event log so we don't show it to users who already saw the release notes elsewhere. Deferred.
  • Internationalization beyond English. v1.0 ships English only with translations-welcome pointer. v1.1 considers a translation file mechanism that does not balloon the binary.

Ranking matrix

Each stance scored 1-5 across seven UX criteria. Sliders re-weight in real time. The matrix is a tool for testing intuitions, not a verdict — every locked decision above is the result of synthesis across at least three of the five stances, not the highest-scoring single stance.
