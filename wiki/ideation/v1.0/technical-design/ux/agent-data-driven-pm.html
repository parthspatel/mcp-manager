The Data-Driven PM's UX

"No telemetry" is not the same thing as "no measurement." It is the same thing as "measurement that the user owns." The locked v1.0 decision rules out anything leaving the user's machine, ever — and I agree with that decision; arguing against it would be a misread of the room. But the decision does not abolish my job. It re-targets it. The instrument I am building is not a dashboard in Amplitude; it is a single newline-delimited JSON file at ~/.local/state/mcpm/events.ndjson, owned by the user, readable by the user, attachable to a bug report only if the user chooses. From that one file, every UX question my four peers are about to argue about becomes answerable — not from anecdote, not from "I think users feel," but from jq.

Thoughts

Let me say the uncomfortable thing first. Product management without measurement is just opinion theatre. Five UX agents (counting me) are about to argue for four days about whether mcpm init should auto-detect Claude Code first or ask for a name first; whether the trust gate should be three-key (y/n/e) or two-key; whether the per-server idle_ttl_secs default of 1800 is "fine" or "user-hostile." Every one of those debates is winnable with one week of any real user activity data. Without that data, the loudest agent wins. I refuse to be that agent, and I refuse to let the loudest agent win. So my contribution to this debate is not a louder voice. It is the infrastructure that makes the next debate quieter.

Here is what I have to internalize before I write a single line of design. The v1.0 locked decision is non-negotiable: no telemetry to vendor servers, ever. The product overview and technical design both state this in the strongest possible terms, repeated in the audience-facing docs. I will not relitigate it. The product overview is right — a developer tool for managing other developer tools, sitting in the trust path between editors and arbitrary MCP servers, cannot be the entity that exfiltrates anything. The moment mcpmanagerd opens a socket to telemetry.mcp-manager.dev, the entire trust story collapses, and rightly so. The right reference for the posture I want to occupy is Tailscale's: their data plane has never carried user content, and they make that promise legible — auditable, even — through architecture rather than through a checkbox. We can do the same. We will do the same.

But "no telemetry" is a constraint, not a goal. The goal is: the user's experience should improve over time, even if Anthropic never sees a single byte of usage data. Those two things sound contradictory only if you have been working in the SaaS world too long. They are not contradictory. They are reconciled by the Local-First Software paper out of Ink & Switch: data the user produces should live, by default, in a file the user owns, in a format the user can read, on the user's machine. The user gets the value; the vendor does not get the data. That essay is from 2019 and it is still the cleanest articulation of where I sit philosophically. The CLI/TUI surface MCP Manager is building is a local-first product almost by accident — the daemon is on localhost, the secrets are in the OS keychain, the configs are on disk in TOML. Adding a local event log is not a violation of that posture; it is a completion of it.

So my position is this. mcpm writes events — to $XDG_STATE_HOME/mcp-manager/events.ndjson on Linux, ~/Library/Application Support/mcp-manager/events.ndjson on macOS — every time something interesting happens. "Interesting" means: command invoked (name only, never argv), command finished (duration, outcome enum), error raised (taxonomy code only, never message body), onboarding step entered, onboarding step completed, projection applied, secret operation outcome, TUI key pressed (key name only, never log content), follow-mode toggled. The file is newline-delimited JSON. The schema is documented, frozen at v1.0, and visible in mcpm help events. The user can cat it. The user can jq it. The user can rm it; it gets recreated empty and life goes on. The user can disable it entirely with mcpmanagerd.events_disabled = true in ~/.config/mcp-manager/config.toml, and that flag is itself audit-logged because turning off your own measurement is a thing future-you might want to ask past-you about.

The litmus test I apply to every field in the schema is the one from the GDPR data-minimization principle: could a leak of this file embarrass the user? Not the vendor — the user. If the answer is "maybe," the field does not get logged. That is why we hash command-shape (the command + its flag set, not its argv) but never log the argv itself; why we log that a secret operation happened but never the secret name; why we log error code E_KEYCHAIN_UNAVAILABLE but never the keychain backend's error string (which on Linux can occasionally include filesystem paths). Apple's privacy-by-design framing calls this "on-device intelligence": the user's machine learns from the user's behavior; nothing leaves. That is precisely what I am proposing.

The killer feature this unlocks is mcpm doctor. Today, mcpm doctor as sketched in the technical design is a static system check — does the keychain exist, is the daemon running, is the trust manifest current. That is fine, and it is what every doctor command does (Homebrew, Flutter, rustup). But static checks miss the most useful thing a doctor can tell a user, which is: "based on your recent behavior, here is the pattern you keep hitting." Example output I want to make possible: "You've hit E_KEYCHAIN_UNAVAILABLE 4 times in the last 7 days, all between 09:00 and 09:30 — your keychain is locked at login until you first interact with it. Consider running security unlock-keychain login.keychain in your shell profile, or move the affected secrets to env-var fallbacks." That is a real diagnosis. Without local events, there is no way to write it. With local events, it is a one-page Rust function over a streaming NDJSON reader.

The other killer feature is mcpm support-bundle. Today, when a user files a bug, the maintainer's first three replies are "what version are you on," "what command did you run," and "can you paste the logs." If we make a single command — mcpm support-bundle — package the user's events.ndjson (last 7 days, redacted to the schema), the daemon logs (already log-ring-buffered, redacted), the version, the OS, and the trust-manifest status into a single tarball, the user can attach that to the GitHub issue once and the maintainer has everything they need. Crucially, the user opens the tarball first and inspects it. Nothing leaves their machine until they choose to upload it. This is the pattern Sentry's CLI got right and that Datadog Agent's diagnose subcommand got right: the support bundle is a file, not an HTTP POST. The user attaches it; the user controls it.

One concession. I would be lying if I said I never wished we had aggregated, anonymized, k-anonymous usage data from a real user population. There is a reason every product manager since the early 2010s has fallen in love with telemetry pipelines: they collapse a feedback loop that is otherwise weeks long into hours. The "Telemetry as a Tax" essays in the open-source community argue persuasively that this tradeoff is fundamentally exploitative when the user did not buy into it, and they are right; the Homebrew analytics fight in 2016 demonstrated that even well-intentioned, aggregated, opt-out telemetry generates a community trust crisis that takes years to repair. The locked decision in v1.0 is the right one because it is unambiguous and because it sets us up to never have that fight. Good. I will work inside it, and I will work hard inside it, because there is more leverage in local measurement than the team currently appreciates.

Arguments with peers

Against empathy-led-designer

We agree on more than we disagree on. Kind defaults, gentle tone, no shaming language in errors — yes to all of it. Where we will fight is over verifiability. The empathy-led designer's instinct is to say "we'll know it's kind when users tell us." That is a fine sentiment for a startup with a thousand users in a Slack community. It does not scale to an open-source distributable that we expect to ship to tens of thousands of developers most of whom we will never speak to. "Kindness" must be operationalized into something measurable, even if the only person measuring it is the user.

My specific ask of the empathy-led designer: every kind-default decision should generate an event the user can later inspect. The trust gate offers y/n/e; we log trust.gate.choice with outcome enum (accept, reject, edit, esc). The user, four months from now, can ask their own events file "have I ever rejected a project config? did I edit one before accepting?" and the answer is in the data. The kindness is not just in the prompt wording; it is also in the fact that the prompt's outcomes are recoverable. The empathy-led designer's tone audit becomes their tone audit, on their machine, with their history — not a panel of strangers' aggregated reactions. That is more empathetic, not less. The user's relationship with the tool becomes legible to the user themselves.

Where I push back: tone audits without instrumentation cannot detect drift. If a future contributor changes an error message from "the secret you wanted is missing" to "no secret found," the empathy-led designer cannot catch that in code review of every PR forever. But a local event with error.code = E_SECRET_MISSING, abandon_rate visible in mcpm doctor can flag a regression locally if the error suddenly correlates with an abort. Empathy with instrumentation is durable; empathy without it is brittle.

Against onboarding-specialist

The onboarding-specialist's target is 60 seconds to value. I love the target. I will help them prove they hit it. Today, "60 seconds to value" is a number nobody measures because we cannot measure it. With the local event log, every mcpm init emits step-entered + step-completed events with timestamps. A user who runs the lucky-day flow can jq their own events and see exactly where their 60 seconds went. The onboarding-specialist gets to claim the number; the user gets to verify it.

The specific commitment I want from the onboarding-specialist's design: every prompt in mcpm init emits an event with a stable name. onboarding.step.scope, onboarding.step.toolchain_detect, onboarding.step.docker_prompt, onboarding.step.service_register, and the matching .entered / .completed pair. The funnel is then trivially reconstructable, locally, from the file. If a user gives up at onboarding.step.docker_prompt they will find the event with no matching completion and the user themselves can debug it. We expose mcpm doctor --onboarding which reads the events and reports: "your onboarding took 47 seconds; the slowest step was toolchain detection at 12 seconds."

Where we disagree: the onboarding-specialist will want to add a "did this help?" prompt at the end of the flow ("yes / no / kinda"). I will resist that aggressively. A satisfaction prompt that nobody ever reads is condescending; a satisfaction prompt whose data goes nowhere is worse. Instead, the post-init summary should print one literal sentence: "mcpm logged 7 events about your setup at ~/.local/state/mcpm/events.ndjson — open it to see what was captured." That sets the precedent for the entire product. The user is not a research subject; the user is a co-author of their own observability.

Against error-recovery-advocate

The 12-row error taxonomy in the current UX design is good. The error-recovery-advocate will want to grow it to 25 rows. I want to know, before they do, which of the original 12 rows actually fires in practice. Without data, error taxonomy bloat is the most insidious form of UX debt: every row added is a row maintained, translated, documented, and tested. Without local event counts, we cannot tell E_REGISTRY_SIGFAIL apart from E_PROJECTION_DRIFT on a frequency basis — and they probably differ by three orders of magnitude in real usage.

My specific ask: every error emission writes error.code, error.recovered (boolean: did the user run the suggested next command within 5 minutes?), and error.recovery_attempt (which command did they run after the error?). The user, four weeks in, can run mcpm doctor --errors and see: "you've hit E_CONFIG_INVALID 17 times; you recover via mcpm config edit 16 of those; in the one outlier you ran mcpm uninstall --keep-config — that's worth investigating." The recovery-advocate's taxonomy work becomes verifiable against the user's own behavior. They get to claim "my recovery paths work" and the user can confirm or deny it from their own machine.

Where we will fight: the recovery-advocate's natural instinct is to add even more sub-codes — E_KEYCHAIN_UNAVAILABLE.libsecret, E_KEYCHAIN_UNAVAILABLE.kwallet, E_KEYCHAIN_UNAVAILABLE.macos_locked. I will resist that without local count evidence. A taxonomy is a UX surface; a UX surface is a thing you can be wrong about; being wrong is fine if the data tells you and expensive if it does not.

Against mental-model-coach

The mental-model-coach owns naming and jargon. I will ask them to operationalize one thing: which commands actually get typed? If 80% of users only ever invoke 4 of the 19 subcommands, the help-text screen needs to lead with those 4 and demote the other 15. We cannot know which 4 without measurement, and we cannot measure remotely. So the local events file has command.invoked with a name-only field (never argv), and mcpm help in some future v1.1 can sort its example list by the user's own most-used commands. The mental model is built by the user's behavior, in the help text the user sees, on the user's machine.

The mental-model-coach's specific naming choices — projection vs sync, trust vs allow, idle_ttl_secs vs idle_timeout_seconds — are all locally testable in a soft way: log config.field_edited events when a user edits a TOML field via $EDITOR integration (we know what changed because we already do the validation diff). If users edit idle_ttl_secs with anomalous frequency, that is a signal the default is wrong or the name is wrong. The user can see this in their own events. They can investigate it themselves.

Where we disagree: the mental-model-coach will want to rename things in v1.0. I will push back unless we have a precommitment to measure-then-rename in v1.1, because v1.0 is the moment we lock muscle memory and we should lock it once. Bad names with data beat good names without data.

Design — event schema, doctor analysis, support bundle

The event log file

Path: $XDG_STATE_HOME/mcp-manager/events.ndjson on Linux, ~/Library/Application Support/mcp-manager/events.ndjson on macOS. Rotation: 50 MB cap, after which the oldest 25 MB are deleted in place. The rotation point itself is logged as an event named events.rotation, because anything else creates a confusing gap. The file is owned by the user (mode 0600 on creation), written by mcpmanagerd through an append-only file handle that holds an advisory flock for each write. The CLI subcommands also write directly when invoked, using the same advisory lock; this avoids a daemon round-trip on every invocation and matches the architecture Tailscale uses for its local CLI bookkeeping.

Schema (frozen for v1.0)

One JSON object per line. Required fields on every event:

{
  "ts":           "2026-05-27T14:33:01.482Z",
  "v":            1,
  "event":        "command.completed",
  "duration_ms":  142,
  "outcome":      "ok"
}

Optional fields, by event family:

# command.* events
"command":      "mcpm.install"           # name only, no argv
"flag_shape":   "scope+runtime"          # SORTED flag-name set
"outcome":      "ok" | "error" | "abort"
"error_code":   "E_SECRET_MISSING"       # if outcome=error; taxonomy code only

# onboarding.step.* events
"step":         "toolchain_detect"
"phase":        "entered" | "completed" | "aborted"

# tui.key.* events
"key":          "l"                      # raw key name; never the log content
"pane":         "servers" | "logs" | "secrets" | "toolchains"

# error.* events
"error_code":   "E_KEYCHAIN_UNAVAILABLE"
"recovered":    true                     # did user run suggested fix within 5 min?
"recovery_cmd": "mcpm.secret.set"        # name only

# secret.* events  (NEVER the secret name; only OUTCOME)
"op":           "set" | "unset" | "list"
"outcome":      "ok" | "keychain_unavailable" | "user_cancel"

# projection.* events
"tool":         "claude-code" | "cursor" | "zed"
"action":       "sync" | "drift_detected" | "force"

# trust.* events
"choice":       "accept" | "reject" | "edit" | "esc"
"config_hash":  "8a9f2d…"                # already a hash; same one in trust.toml

The privacy checklist (every event must pass)

  1. No filesystem paths. Not in any field, not in any error code. Paths leak project names, employer names, and personal directory structure.
  2. No argv. Ever. The command name (mcpm.install) is fine; the argument (official/github-mcp@^0.4) is not. The CLI surface decides what is identifying; the schema cannot.
  3. No secret names. "GITHUB_TOKEN" is identifying. "secret.set outcome=ok" is not.
  4. No error message bodies. Only taxonomy codes. The body of E_KEYCHAIN_UNAVAILABLE on Linux can include a libsecret path; the code does not.
  5. No content from log streams. The TUI emits tui.key.f when the user toggles follow mode; it does not emit anything about what was on screen.
  6. Hashes are deterministic but not reversible. flag_shape is the sorted, hyphen-joined list of flag names (e.g. scope+runtime) — a low-cardinality fingerprint, not a hash of the entire command line.
  7. The user can disable it entirely. One line of TOML: events_disabled = true. The fact of disabling is itself audit-logged, so future-you can see when past-you turned it off and why (the audit log records the editor invocation).
  8. The file is human-readable. Newline-delimited JSON, not Protocol Buffers, not SQLite, not Parquet. The user opens it in less. That is the entire point. The NDJSON convention is documented and widely supported.

What we do NOT measure

  • Anything about which MCP servers a user installs. Server names are identifying (org names, project names). We log command=mcpm.install but not the source.
  • Per-server uptime, error counts, or invocation counts. Those are interesting to us; they would help us prioritize fixes. They are also a fingerprint. A user who runs jira-mcp and internal-pr-mcp together has a different fingerprint than one who runs github-mcp alone.
  • Hostnames, IPs, network identifiers. Nothing about the machine's network position.
  • Timing precise enough to fingerprint. We log duration_ms rounded to the nearest millisecond, not nanoseconds. Microbenchmarking is not the goal; UX is.
  • Anything cross-session-correlatable. No install ID, no session ID, no machine ID. The events are an unkeyed stream of facts about this machine, joinable only by the user themselves.

mcpm doctor as event-pattern analyzer

The doctor command grows a new mode. mcpm doctor with no flags runs the existing static checks (daemon up, keychain reachable, trust manifest valid). mcpm doctor --history additionally reads the events file and surfaces patterns. The patterns we look for in v1.0 (each a single jq-style pass over the file, no ML, no inference):

  • Recurring error. Same error_code hit ≥ 3× in the last 7 days. Suggest the fix the taxonomy already documents.
  • Recurring time-of-day error. Same error_code consistently within a 60-minute window of the day. Suggest a possible environment cause (keychain lock at login, VPN reconnect, scheduled job).
  • Abandoned onboarding. An onboarding.step.*.entered event with no matching .completed or .aborted within 5 minutes. Offer to resume.
  • Slow command. A command.completed with duration_ms > 3× the median for that command. Suggest mcpm logs --daemon.
  • Drift after edit. A projection.drift_detected within 24h of a config.field_edited. Suggest mcpm projection diff.
  • Trust regret. A trust.choice = accept followed within 24h by an explicit revoke. (Useful UX learning for the user themselves.)

Worked example output:

$ mcpm doctor --history

   ✓ daemon running (since 2 hours ago)
   ✓ keychain reachable
   ✓ trust manifest valid (refreshed 6h ago)

   Patterns from your recent activity:

   ⚠ E_KEYCHAIN_UNAVAILABLE hit 4× in the last 7 days.
     All occurrences between 08:51 and 09:14 local time.
     Possible cause: keychain is locked at login until first interactive use.
     Try:  security unlock-keychain ~/Library/Keychains/login.keychain-db
     Docs: https://docs.mcp-manager.dev/v1.0/errors/keychain-unavailable

   ℹ onboarding.step.docker_prompt took 38s (median for this step: 9s).
     If Docker isn't useful for you, set docker_enable = false in
     ~/.config/mcp-manager/config.toml to skip the prompt on re-init.

   ℹ projection drift detected on cursor 2 days ago, not resolved.
     Run: mcpm projection diff cursor

mcpm support-bundle

The support-bundle subcommand packages the events log, the daemon log ring buffer, the trust manifest status, and the version into a single tarball. Nothing leaves the machine. The user attaches the tarball to a GitHub issue if they choose. The pattern is the one Datadog's agent diagnose codified and that Sentry's CLI ships variations of: support data is a file the user inspects, not an HTTP POST the vendor intercepts. 

$ mcpm support-bundle

   This will package the following into a tarball you can attach to a bug report:

     events.ndjson           ~/.local/state/mcp-manager/events.ndjson
                             (last 7 days, 1,847 events, 240 KB)
     daemon.log              ~/.local/state/mcp-manager/audit/daemon.log
                             (last 24h, 1.2 MB)
     servers/                last 24h of per-server ring buffers (4 files, 3.1 MB)
     trust.status            registry pubkey trust status (no secrets)
     version.txt             mcpm 1.0.0, mcpmanagerd 1.0.0

   None of this leaves your machine. You attach the tarball yourself if you choose.

   Inspect first?  [Y/n]: Y

   $ less ~/Downloads/mcpm-support-bundle-20260527T143301.tar.gz

   Looks fine? Open the GitHub issue tracker?  [y/N]:

The bundle contents are exactly the schema-restricted events; there is no separate "send more detail" mode. We do not have a bigger version of the data to give the maintainer. What the user sees is everything that exists. This is the property that distinguishes a privacy-preserving telemetry posture from a privacy-theatre one: the file the user inspects is the data, not a redacted view onto a richer dataset held elsewhere.

What the user does with all this

The bet I am making is the same one k9s makes when it shows local-only counters in its status bar, and the same one Vim makes when it lets you grep :history. Most users will never open the file. That is fine. The 5% who do will be the people writing blog posts, opening high-quality bug reports, contributing PRs, and answering other users' questions on the issue tracker. Local-first measurement creates a high-signal subset of users who can answer their own questions and help others answer theirs. That subset compounds. It is worth more than aggregate dashboards a vendor controls but a user has never read.

My closing pitch to the four peers: every one of your UX claims becomes verifiable, locally, by the very user you are designing for. The empathy-led designer's tone choices are checkable by the user's own abandon rate. The onboarding-specialist's 60-second target is checkable by the user's own timestamps. The error-recovery-advocate's recovery paths are checkable by the user's own follow-up commands. The mental-model-coach's naming choices are checkable by the user's own edit frequency. None of this data leaves the machine. All of it leaves the user smarter about their own tools. That is the kind of product management I want to do — the kind I think we can only do, given the locked decision — and I think it is better than the one we would do with a vendor pipeline anyway.
