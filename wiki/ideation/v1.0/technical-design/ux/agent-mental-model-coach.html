The Mental Model Coach's UX

Server. Editor. Secret. Three nouns. Everything else is invisible or perfectly metaphored. If a user has to learn one of our internal words to do their job, we have failed the design brief.

Thoughts

I have read the v1.0 product overview, the technical design, and the ux-design document end to end. The architecture is, in my honest assessment, very strong: a canonical store, projected fan-out to editors, a daemon that brokers stdio, secrets in the OS keychain, three persistent TOML files. The plumbing is right. The shape of the surface area is right. But the words on that surface — the words that show up in TUI labels, error codes, TOML keys, CLI flags, and (most importantly) docs introductions — are not yet ready for a user who has never read our docs. And that is the only audience that matters for the first ninety seconds of an install.

A mental model is not what the system is; it is what the user believes the system is, derived from the names and labels we expose. Don Norman's framing in The Design of Everyday Things is the foundational text here: the system image — every word, glyph, and prompt the user encounters — is the only thing standing between the designer's model and the user's model. If our system image leaks designer-words, the user constructs a designer-shaped mental model, which is a mental model of a thing they have to learn rather than a thing they can use. Every leaked CS term — "singleton", "projection", "idle TTL", "refcount", "managed-block hash" — costs us minutes of orientation and trust that we never get back. (See Norman, Nielsen Norman Group's "Mental Models" article, and Adam Wathan's Refactoring UI chapter on labels.)

So my job in this debate is the unglamorous one: I am the name-naysayer. I am the person who reads the technical design with a marker and circles every word that came from a Rust struct field instead of a kitchen-table sentence. I do not want to soften the engineering — the engineering is good — I want to translate it. The right mental model for the user of MCP Manager is three nouns: servers (things that provide tools), editors (apps that consume those tools, like Claude Code or Cursor), and secrets (the credentials a server needs to do its job). One sentence should bind them: "MCP Manager runs MCP servers on your machine, connects them to your editors, and stores their secrets safely." If a user reads that sentence and then opens the TUI, they should see three panes labelled Servers, Editors, Secrets — and that is exactly what the current TUI mock shows. Good. But the middle pane is currently called "Toolchains", which is a fourth noun nobody asked for, and the right pane talks about "projection drift", which is a phrase only the implementer's mother could love.

The specific words I am going to push to rename, with rationale, are five: projection, idle TTL, singleton, toolchain, and inherit. Each one is a CS-correct term that earns its keep in the codebase but ambushes a first-time user. I will also push to make the 19-command CLI verb-tense-consistent (it is mostly there, with two outliers I want to fix), and I will propose a three-page mdbook IA whose top-level sections are literally Servers, Editors, Secrets. The trust gate has its own naming problem I want to address — "trust" alone is too ambient; we should say what we are trusting about, which is the project config. And the singleton flag, which lives in TOML as singleton = true, should surface in the TUI and docs as something a human would actually say out loud, like "share one process across editors" with the inverted form "give each editor its own copy".

Two principles run underneath all of this. First: the user's vocabulary is sovereign. We do not get to teach them ours; we earn their attention by speaking theirs. Second: a TOML key is allowed to be technical because power users will read it twice; a TUI label is not, because a novice will read it once and decide whether to quit. So the rename strategy is asymmetric — keep the implementer-friendly key in the file (with a doc comment), and rename only the user-facing surface (labels, prompts, error messages, help text). This is the same split Kubernetes makes between API-level spec.template.spec.containers[].image and user-level kubectl get pods: power users see structure, novices see verbs. We can do both.

One last note before I argue with my peers: this stance is not about being cute. I am not asking for clever names. I am asking for boring names — names so obvious they vanish. "Auto-stop after 30 min" is a boring label, and that is precisely why it works. "Idle TTL: 1800" is a clever-feeling label that makes the user feel stupid for not knowing what TTL means. Boring is kind. Clever is hostile. We are going for kind.

Arguments against my four peers

Against empathy-led-designer

The empathy-led-designer's instinct — kind defaults, audited tone, no exclamation points where a period will do — is right and complementary to mine. I would never argue against compassionate copy. My pushback is on precedence: tone audit is what you do after the nouns are right. If we tune the tone of an error message that contains "projection drift detected", we end up with a kind, warm, polite message that the user still cannot read. A friendly sentence built on a hostile noun is still hostile. So I want the rename pass to land before the tone pass. If you read E_PROJECTION_DRIFT as "the editor's config file was hand-edited and now disagrees with what MCP Manager last wrote there", you can spend your tone budget on softening the action ("would you like to keep the hand edit or restore the managed copy?") rather than apologizing for the concept. Kindness compounds with clarity; it cannot substitute for it. Don Norman has a phrase for this: "the trouble with making things foolproof is that fools are so ingenious" — which I always read as a backhanded reminder that the engineer who chose the word "projection" thought they were being precise, and they were, in their dialect. The empathy-led-designer's job is to make our voice kind. My job is to make sure that voice has anything kind to say.

Concretely: I'll defer to empathy-led-designer on the tone of every prompt and the wording of every confirmation. I just want a veto over the nouns those prompts contain. We split the work cleanly along that seam.

Against data-driven-pm

Local-only metrics are a fine idea — counters of how many times mcpm install succeeds versus fails, how often the trust gate is hit, how often a user opens the TUI versus invokes the CLI. I have no architectural objection. My pushback is on what the metrics are allowed to do. Metrics tell you where users got stuck; they do not tell you why. If 40% of first-time users abandon onboarding at the trust-gate prompt, the data-driven-pm's instinct will (correctly) be to flag the prompt for redesign. But the redesign has to be conceptual, not just visual. The reason users will abandon at "trust this project config?" is not that the prompt is ugly; it is that the word "trust" without an object is too abstract to act on. They are being asked to make a security decision with no scaffolding. So I want metrics to inform rename decisions, not replace them — and I want it stipulated that we will rename a label before we instrument it. Otherwise we end up A/B testing two equally confusing labels and declaring a "winner" that is still confusing.

The deeper philosophical point: Jakob Nielsen's heuristic #2, "match between system and the real world", is not a hypothesis to test — it is a constraint to satisfy. We do not test whether "Auto-stop after 30 min" beats "Idle TTL: 1800s" in click-through. We rename it because TTL is jargon and "auto-stop" is plain English, and we move on to the next problem. Metrics are for things real users are doing in the wild; they are not a substitute for not embarrassing ourselves on the way out the door.

Against onboarding-specialist

The onboarding-specialist's "60 seconds to value" target is a beautiful constraint, and the existing mcpm init flow — five prompts, all with sensible defaults, -y to accept them all — is already very close. My pushback is on what value we deliver in those 60 seconds. The current init flow asks: name, scope, projection targets, docker, service-register. That is correct sequencing for getting the daemon running, but it does not build the mental model. The user finishes init and knows the daemon is alive, but they do not yet have the three-noun frame in their head. So the first mcpm command they type after init is going to be a guessing game.

I propose we cheaply add one line of teach-as-you-go to the init output:

✓ Initialized.

  MCP Manager runs three things for you:
    Servers  — the tools your editor can call (`mcpm install` to add one)
    Editors  — the apps that use those tools (we connected 3 already ✓)
    Secrets  — the credentials your servers need (`mcpm secret set NAME`)

  Try:  mcpm install official/github-mcp@^0.4

This is six lines of output. It costs nothing. It plants the three-noun model in the first 30 seconds, so the next 30 seconds are guided by it. Without this, the onboarding-specialist's 60-second target is a 60-second time-to-daemon, not a 60-second time-to-mental-model. The latter is what makes the next hour of use feel natural; the former just makes the first minute feel snappy.

The onboarding-specialist may counter that adding text makes onboarding feel slower. I disagree — six lines of plain English read in under three seconds, and they replace twenty minutes of later confusion. The Mozilla Developer Network's onboarding research and the GitHub CLI's gh auth login flow both demonstrate that a single sentence of context-setting after a successful init increases downstream completion. We are not making init slower; we are making the second command faster.

Against error-recovery-advocate

The error-recovery-advocate wants every error to have a clear next step, an obvious recovery path, and a taxonomy that supports machine parsing. I am in violent agreement. My pushback is on the names of the codes themselves. The current 12-row taxonomy has codes like E_PROJECTION_DRIFT and E_SPEC_UNSUPPORTED and E_KEYCHAIN_UNAVAILABLE. The recovery advocate's job is to make sure each code carries a "what to do" — and the current taxonomy does that well. My job is to make sure each code carries a "what happened" that the user can read without consulting docs. E_PROJECTION_DRIFT is a category, not a sentence. The sentence is "an editor's config file no longer matches what MCP Manager last wrote there, because someone hand-edited it". That sentence belongs in the user-facing message; the code can stay as a stable identifier for log parsers and our docs.

So I propose a two-layer error taxonomy: the codes stay (engineers and log parsers need stable identifiers), but the human title of each error gets a noun-and-verb sentence that builds on the three-noun model. E_PROJECTION_DRIFT → "Editor config edited outside MCP Manager". E_SERVER_OOM → "Server ran out of memory". E_SECRET_MISSING → "Secret not found in keychain". Each title sits in the same plane as the three nouns; each fix sentence is one imperative verb. The error-recovery-advocate keeps their taxonomy; I just want a column added between the code and the explanation that holds the user-friendly title.

One specific disagreement: I do not want errors to include the underlying internal vocabulary even in the fix-suggestion line. A user who reads "the projection failed to sync; run mcpm projection diff" has to learn what a projection is to follow the advice. Better: "the editor config was hand-edited; run mcpm sync diff cursor". If we rename the verb from "projection" to "sync" (or "link"), the entire error path becomes legible without a glossary.

Design proposals

The three-noun mental model (ASCII relationships)

Every doc page, every TUI screen, every help-text intro should reinforce this picture. It is the whole product, drawn in one breath:

     ┌─────────────┐
     │   EDITORS   │   Claude Code, Cursor, Zed, …
     │             │   (what the user opens to write code)
     └──────┬──────┘
            │  uses tools from
            ▼
     ┌─────────────┐
     │   SERVERS   │   github-mcp, postgres-mcp, filesystem-mcp, …
     │             │   (managed by `mcpm`; provide the tools)
     └──────┬──────┘
            │  needs
            ▼
     ┌─────────────┐
     │   SECRETS   │   GITHUB_TOKEN, ACME_DB_URL, …
     │             │   (stored in your OS keychain)
     └─────────────┘

Three nouns, two arrows, one sentence each. No fourth concept. The daemon, the projection, the lockfile, the trust manifest, the spec version — all of it sits underneath this picture as plumbing the user never has to name unless something goes wrong.

Subcommand verb-consistency audit

The CLI's 19 top-level subcommands are mostly clean already. Verbs are imperative present-tense ("install", "start", "stop", "restart", "update"). The two outliers I flag:

  • mcpm outdated — this is an adjective, not a verb. Every other top-level command is a verb. Replace with mcpm check-updates or mcpm preview-updates (rhymes with mcpm update). Keep outdated as an alias for one release for backwards compat with anyone who lifted it from the brainstorm doc.
  • mcpm status — fine, but inconsistent with mcpm list which we don't have. Either add mcpm list as an alias (for muscle memory from ls, kubectl get, docker ps), or document that status is the single source of truth. I lean toward adding the alias.

The exec/test/config/project/registry/secret/trust subcommands all use noun-then-verb subcommand patterns (mcpm registry add, mcpm secret set), which matches kubectl and gh conventions and is fine. The verb set is consistent: add/remove/list/set/get/unset/refresh/verify/edit. I would specifically reject any attempt to use delete in some places and remove in others — pick one. remove is the more common verb in package managers (npm, cargo, apt); use remove throughout.

mdbook IA outline (Servers, Editors, Secrets at the top)

The mdbook table of contents should not start with "Installation" → "Configuration" → "Architecture". That is implementer order. The user's first question is "what does this thing do?", and the answer is the three nouns. Proposed top-level chapters:

  1. What is MCP Manager? — one page, three nouns, the ASCII diagram above. Total reading time: 90 seconds.
  2. Install MCP Manager — curl one-liner, Nix flake, verify with mcpm status.
  3. Servers — install, list, update, remove. The whole lifecycle of an MCP server. (This is where mcpm install through mcpm uninstall live.)
  4. Editors — what editors are auto-detected; how MCP Manager keeps editor configs in sync; what to do when an editor config gets hand-edited.
  5. Secrets — how secrets are stored (OS keychain), how to set / list / remove them, how to use environment-variable fallbacks for CI.
  6. Projects — per-repo configs, the trust gate, sharing config with teammates.
  7. The TUI — keymap, panes, log multiplexing.
  8. Troubleshooting — error codes (the 12-row taxonomy), what each one means in plain English, recovery steps.
  9. Reference — full TOML schema, all CLI flags, audit-log format. This is the deep-end pool for power users.
  10. Concepts (optional reading) — daemon architecture, projection mechanics, refcounting, spec negotiation. Tagged "optional reading" because the user does not need any of this to use the tool.

Notice the symmetry: chapters 3, 4, 5 are exactly the three nouns. Chapter 2 is install. Chapter 1 is the model. Chapters 6–9 are layers on top. Chapter 10 is the engine room, gated behind a label that says "you don't need this". The IA is the mental model, externalised.

Update notifications — preserve the noun-count

Update notifications (when mcpm detects a newer mcpmanagerd version) should not introduce a fourth noun. The current phrasing "mcpmanagerd update available" forces the user to know what mcpmanagerd is. Rephrase: "MCP Manager update available (v1.0.2 → v1.0.3). Run mcpm update --self to install." The user only ever needs to know about one product: MCP Manager. The daemon is plumbing.

Accessibility commitments (mental-model angle)

The existing accessibility commitments are good (color + glyph, NO_COLOR, keyboard-only, high-contrast theme). I'll add one mental-model-shaped commitment: every glyph has a one-word screen-reader label. ● is "running", not "filled circle". ○ is "stopped". ⚠ is "crashed". The glyph and the word converge on the same mental concept. This is the same principle ARIA labels enforce on the web — a sighted user and a screen-reader user should arrive at the same noun.

Summary of the rename pass — what changes, what doesn't

Changes: TUI pane title ("Toolchains" → "Editors"), four status words ("failed" → "crashed", "drifted" → "edited outside", "sync" → "linked", "projection" → "sync" as a verb), the idle-TTL label, the singleton-flag label, the inherit-mode prompt, one CLI subcommand rename (outdated → check-updates, with alias), all 12 error-code titles, all init-flow prompts, the mdbook IA top-level chapter ordering.

Does not change: any TOML key, any CLI subcommand below the rename above, the architecture, the daemon name (internally), the error codes themselves (only their titles), the lockfile format, the trust file format, the keymap, the keychain integration. The implementation is untouched; only the surface words change.

This is a one-week pass for a careful copyeditor with vetoes from engineering on anything that would break compat. The payoff is permanent: every new user from the day this lands forward arrives with the right three-noun model in their head, and every later release inherits that vocabulary by gravity.

  2. Don Norman, The Design of Everyday Things (revised ed., Basic Books, 2013) — chapter 1 establishes the three-models framework (designer's model, system image, user's model); the whole book is the philosophical backbone of this stance.
  3. Adam Wathan & Steve Schoger, Refactoring UI — the chapter on naming and labeling is the practical bridge between "good design principles" and "actually shipped labels". The "boring beats clever" heuristic I cite comes from here.
  4. Nielsen, "10 Usability Heuristics for User Interface Design" (NN/g, updated 2024) — heuristic #2 ("match between system and the real world") is the formal name for what I am doing in the rename table.
  5. k9s CLI documentation — Commands and navigation — k9s established the lazygit/k9s-class TUI pattern MCP Manager's TUI is modeled on, and its naming conventions (resources, namespaces, contexts) are studiously plain-English. A direct precedent for keeping CS internals out of TUI labels.
  6. Kubernetes, "kubectl Conventions" — the noun-then-verb subcommand pattern (kubectl get pods, kubectl create deployment) is the model for mcpm registry add, mcpm secret set, etc. Also the source of the "alias list to get" precedent I cite.
  7. Martin Fowler, "TwoHardThings" — the famous Phil Karlton attribution: "There are only two hard things in Computer Science: cache invalidation and naming things." This stance exists because we're choosing not to ship the second hard thing onto our users.
  8. "Command Line Interface Guidelines" (clig.dev) — the most thorough modern style guide for CLI naming and behavior. Specifically the "Naming" and "Help" sections inform the verb-consistency audit and the subcommand structure.
  9. GitHub CLI documentation — gh auth login is a direct precedent for the kind of teach-as-you-go init output I'm proposing. Its prompts model the product's mental structure (host, protocol, scope) in plain English.
  10. mdBook documentation — the IA outline I propose maps directly onto how mdBook's SUMMARY.md is structured; the "Concepts (optional reading)" pattern is borrowed from the Rust Book's own structure (chapters 1–3 are usage; chapter 19's "Advanced Features" is gated under "optional").
