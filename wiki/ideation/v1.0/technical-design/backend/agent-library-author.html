The Library Author's Backend

Public API is forever. The other four backend agents are debating runtime tactics, kernel primitives, and event journals; I am debating what gets exported with pub. If we get the wire crate wrong, every alternative client written against MCP Manager v1.0 dies on the rocks when we ship v1.1. Tiny mcpm-protocol, deliberately stable; everything else can churn behind it.

Thoughts

The v1.0 spec already pinned the right structural decision: mcpm-protocol is the small, stable, public surface; mcpm-client is the in-tree convenience layer that wraps it (per-crate table). What it did not pin is the discipline that makes that structural decision actually pay off five years from now. Without that discipline, mcpm-protocol drifts into "whatever the daemon happens to need this week," picks up a tokio dependency because somebody hand-wrote an async stream impl, accidentally re-exports a 30-variant Error enum that we then can't extend without a major bump, and at v1.4 we discover we cannot rename a field anybody might be matching on. I have seen this happen in three of the last four crates I shipped. The defaults of the Rust ecosystem tilt toward fragility: pub enum E { A, B } is exhaustive unless you say otherwise; pub struct S { pub x: u32 } is constructible by name unless you say otherwise; pub trait T is implementable by anyone unless you say otherwise. Every default in Rust says "you are stuck with this forever." Library authors must consciously reverse each one.

My core position: everything public in mcpm-protocol must be designed under the assumption that tomorrow we'll need to add a variant, a field, or a method without breaking the world. That single discipline drives every concrete choice that follows: #[non_exhaustive] on every public enum and struct, sealed traits for "we want to add methods later" patterns, no leaked transitive dependencies, no exposed re-exports of types from crates we don't control, no async on the wire-type crate (the type definitions are sync data; the I/O happens in mcpm-client), and cargo-semver-checks in CI as a hard gate. The Cargo team have explicitly endorsed this tool and Cargo itself uses it on its own library components[semver-checks].

The other axis I obsess over is the 0.x vs 1.0+ contract. Cargo's semver page is explicit that 0.x treats minor as breaking and patch as compatible, but at 1.0 the rules tighten dramatically: adding a public enum variant, adding a non-defaulted method to a trait, even widening a field's type from u32 to u64 becomes major[cargo-semver]. The trap is shipping a crate at 1.0.0 before its public surface has been adversarially reviewed for "what can we never change?". My recommendation: mcpm-protocol starts at 0.1 and stays at 0.x through v1.0, v1.1, and maybe v1.2 of the binary. We only bump mcpm-protocol to 1.0 when we have a deprecation cycle behind us and external clients in the wild verifying that what we marked stable actually is. mcpmanagerd itself ships at 1.0 because the user-facing binary needs the marketing signal; the wire crate, which third parties Cargo-depend-on, does not get to share that bath water.

Finally: the "double-version" question. The spec adds a custom mcpm_wire_version on every JSON-RPC message (wire section). That's good — it gives us in-band detection of drift — but it's not enough on its own. We also need mcpm-protocol's Cargo version to track the wire version cleanly. A third party who pins mcpm-protocol = "1.2" in their Cargo.toml must get exactly the same set of methods + types that a daemon advertising mcpm_wire_version = "1.2" understands. Two version numbers for the same thing are a debugging tax; we make them identical. The version of the binary (mcpmanagerd 1.4.3) is a separate axis and can drift faster.

Arguments against peers

vs tokio-pragmatist

The tokio-pragmatist will want mcpm-protocol to expose ergonomic streaming wrappers using tokio:: sync, tower::Service, and futures::Stream. They will argue this is idiomatic and that forcing every consumer to wire up their own stream-of-frames adaptor is busy-work. They are right about the busy-work. They are wrong about where it goes.

Where I'll concede: the convenience layer absolutely belongs in the tree. mcpm-client should expose a tokio-flavoured API: Client::tail_logs(&self, server: &str) -> impl Stream<Item = Result<LogLine, Error>>, the dial-or-auto-spawn dance baked in, retry policies, all of it. First-party clients (the CLI, the TUI, a future GUI) should depend on mcpm-client and never see the raw frame format. That's exactly what the v1.0 spec already says.

Where I'll dig in: the wire-types crate mcpm-protocol must not depend on tokio. Not transitively, not optionally, not behind a feature flag enabled by default. The reason is concrete: someone will want to build a non-async mcpm-aware tool — a CI gate that introspects a project's lockfile, a static analysis pass, a Python binding via PyO3 that runs in a synchronous request handler, an `embeddedfile`-style status probe written in C calling our types through bindgen. The moment mcpm-protocol pulls tokio into its compile graph, every one of those use cases either gains 80 transitive crates of build cost or becomes impossible. Serde supports no_std cleanly via feature flags[serde-no-std], and we should at minimum ship mcpm-protocol with default-features = ["std"] and a working no_std profile (no alloc is unrealistic since we have String and Vec in payloads; alloc yes, std optional).

The async streams the tokio-pragmatist wants live in mcpm-client, where churn is fine. We can rev the stream ergonomics every six months without breaking anyone who only depends on the wire types. That's the entire point of the split.

vs systems-veteran

The systems-veteran preaches sans-I/O cores and explicit state machines — and they're right that the supervisor's lifecycle should be a state machine, not a tangle of Mutex<HashMap<String, ServerHandle>>. Where we'll clash is the encoding of those state machines in the public API.

Concretely: the systems-veteran will propose exposing the supervisor's state machine as a public type, perhaps something like pub enum ServerState { Spawning, Running, IdleTimerArmed, RestartingBackoff(Duration), OomFailed, Stopped } so that callers can match on it for diagnostic UIs. This is a load-bearing public surface decision. Today there are six states; tomorrow we add Quarantined (server flagged by registry audit) and WarmRestart (config change, no full crash) and we've broken everyone who matched on the enum.

My counter: every public enum that represents a state, an error, a kind, or a category gets #[non_exhaustive]. RFC 2008 is the canonical reference and it stabilized cleanly[rfc-2008]; downstream pattern matches require a wildcard arm and our future-self gets to add variants in minor releases. Same goes for any public struct in mcpm-protocol where we might add fields — ServerDetail, InstallResult, LogLine — every one of them #[non_exhaustive], constructed internally via builder or with a private constructor, never with struct literal syntax from outside.

Where I'll partially yield: the systems-veteran's event journal is exactly the right shape for diagnostics, and the journal entries should be a public type in mcpm-protocol so that external observers can subscribe. But that just makes the #[non_exhaustive] discipline more urgent: AuditEvent will grow new variants every release.

vs kernel-hacker

The kernel-hacker lives for cgroup v2 events, RLIMIT_AS plumbing, and macOS jetsam inference. Excellent. These belong inside mcpm-supervisor as private implementation. The public surface should be a single behavior-level concept: OomDetected with platform-detail in an opaque details map.

Where we'll clash: the kernel-hacker will want to expose, say, CgroupV2OomEvent { count: u32, last_seen: Instant } as a typed event variant, because that's what the kernel actually told them. The first time we run on a cgroup v1 kernel that variant becomes nonsensical, and the first time we add jetsam-inference on macOS we now need a parallel variant JetsamInferred { signal: i32, mem_pressure: bool, rss_pct: f32 }. Five years from now the audit log enum has 14 platform-specific variants and removing any of them is a major bump.

My pattern: one variant per behavior class (ServerCrash, ServerOom, ServerStopped), each holding a #[non_exhaustive] struct that carries platform-specific detail in a stable shape (an oom_signal: OomSignal enum that is itself #[non_exhaustive] with variants like CgroupV2OomKill, RLimitSigkillInferred, JetsamInferred, future). That way: (a) downstream code matching on the high-level variant keeps working; (b) downstream code that wants to drill into the platform detail must already be doing wildcard matches; (c) we can add a new kernel feature (memory.swap.events, PSI integration, eBPF probes) without bumping major. Behavior-class enums are stable; the detail structs grow.

Cargo's semver reference is explicit that adding new public items is minor, but extending an existing exhaustive enum is major[cargo-semver]. The kernel-hacker's instinct ("expose the truth") and my discipline ("expose a forward-compatible shape") only conflict at the boundary; inside mcpm-supervisor they get to be as truth-y as they like.

vs boring-tech-defender

Of all four peers I'm closest to the boring-tech-defender — we both push for less public surface. Where we diverge: I think the small extra effort of #[non_exhaustive], sealed traits, and cargo-semver-checks in CI is cheaper than the boring-tech alternative of "just refuse to make anything public until v2." Refusing to make things public is the right move for 90% of types; the remaining 10% (wire types, error kinds, audit-event enums) are public no matter what we do because they cross the JSON-RPC boundary, and pretending otherwise just means the boundary types live as serde_json::Value blobs with stringly-typed event names. That trades static verification for "we'll catch it in tests if we're disciplined." We will not catch it.

Where I cede the point: mcpm-client's convenience layer should be ruthlessly minimal at v1.0. Three operations: connect() with auto-spawn, call::<Method>() for unary RPC, stream::<Method>() for streaming. No retry policies hidden behind config (let callers pass a tower retry layer if they want). No global state. No magic. The boring-tech-defender's distrust of "convenience layers that grow into frameworks" is dead right; mcpm-client is allowed to grow only as far as duplication between CLI and TUI actually justifies. Every helper goes through the test "does this remove three or more lines of duplication in mcpm-cli?" and dies otherwise.

A specific agreement-with-fortification: the boring-tech-defender will reject tower::Service as overengineering for an internal IPC dispatcher. I agree, but the JSON-RPC handler dispatch table inside mcpm-daemon is not public surface. It can be a giant match on method name, or a typed router, or a procedural macro — all internal. The wire types it accepts and returns are public; the dispatch mechanism is private. Public/private discipline matters everywhere, but only the public side gets the #[non_exhaustive] tax.

Design — per crate

I'll go through the 11-crate workspace and call out the public-API discipline each crate needs. The two crates I own most strongly are mcpm-protocol (the locked-down wire crate) and mcpm-secrets (the SecretStore trait, which is the only trait we ship to be implemented by users).

mcpm-protocol — the small, stable, public surface

The hard line: mcpm-protocol exports only what crosses the JSON-RPC boundary. Method names as string constants, request/response/error types, the event-stream payload types, the wire-version constant. Nothing else. No clients, no helpers, no traits that downstream consumers might want to impl. 

// crates/mcpm-protocol/Cargo.toml
[package]
name    = "mcpm-protocol"
version = "0.1.0"      # stays 0.x until v1.2-ish of mcpmanagerd
edition = "2024"
description = "Wire types for the mcpmanagerd JSON-RPC API. Stable. Tiny."
license = "Apache-2.0"
rust-version = "1.80"   # MSRV pinned and tested in CI

[features]
default = ["std"]
std     = ["serde/std", "serde_json/std"]
alloc   = ["serde/alloc"]
# No `tokio` feature. No `async` feature. Wire types are pure data.

[dependencies]
serde      = { version = "1", default-features = false, features = ["derive"] }
serde_json = { version = "1", default-features = false, features = ["alloc"] }
# That's it. No tokio. No tower. No tracing. No thiserror in the API surface
# (we use thiserror internally but its error types are not re-exported).

The Cargo book is explicit that adding required features is a breaking change[cargo-semver], so we ship the std feature default-enabled from day one and accept that someone needs to opt out for embedded use. Microsoft's Rust engineering training has a chapter on exactly this no_std + feature verification[ms-rust-eng]; we follow their playbook including cargo hack check --each-feature in CI.

Now the types. Every public enum: #[non_exhaustive]. Every public struct: #[non_exhaustive]. Constructors take builders or factory functions that we can keep evolving: 

// crates/mcpm-protocol/src/lib.rs (excerpt)
#![cfg_attr(not(feature = "std"), no_std)]
extern crate alloc;
use alloc::string::String;
use alloc::vec::Vec;

/// The wire version. Bumped in lock-step with the crate's Cargo version.
/// Clients send this on every request; daemons echo it on every response.
pub const WIRE_VERSION: &str = "0.1";

#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct ServerSummary {
    pub name: String,
    pub state: ServerState,
    pub version: String,
    // future fields go here; downstream cannot construct by struct-literal
}

#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(rename_all = "snake_case")]
pub enum ServerState {
    Running,
    Stopped,
    Crashed,
    Starting,
    // future variants: Quarantined, WarmRestart, etc.
}

#[derive(Debug, thiserror::Error, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(tag = "code", content = "details")]
pub enum WireError {
    #[error("config conflict (prior_hash mismatch)")]
    ConfigConflict { current_hash: String },
    #[error("server not found: {name}")]
    ServerNotFound { name: String },
    #[error("unknown method: {0}")]
    UnknownMethod(String),
    #[error("wire-version mismatch: client={client}, daemon={daemon}")]
    WireVersionMismatch { client: String, daemon: String },
    // ...
}

/// Method-name constants. Stable. New methods are minor bumps.
pub mod method {
    pub const SERVER_LIST: &str = "server.list";
    pub const SERVER_GET: &str = "server.get";
    pub const SERVER_START: &str = "server.start";
    // ...
}

Things I deliberately keep out of mcpm-protocol: no Client struct, no async fn, no impl Future, no transport abstraction, no tracing spans woven through types, no secrecy::SecretString in public payloads (we use opaque String at the wire and the caller wraps it in SecretString on their side). The principle: nothing in this crate's public types should require the consumer to also depend on a specific runtime, allocator, or logging framework.

Versioning policy in one sentence: mcpm-protocol's Cargo version equals WIRE_VERSION at all times. They bump together, they ship together, and they age together.

mcpm-secrets — the only trait we publish for users to implement

SecretStore is the one type we ship that users are expected to extend. The v1.0 backends are OsKeyringStore, EnvVarPassthroughStore, and LayeredSecretStore wrapping them. The whole point of having a trait is that v1.1 will add 1Password, Bitwarden, Vault, Doppler, and a long tail of enterprise vaults. The trait must be designed so that adding a method later doesn't break every implementor.

Two patterns for that: sealed traits (only the parent crate can implement) and trait methods with default implementations. Sealed is wrong here — we explicitly want third parties to implement this trait. So every method gets a default. The definitive guide to sealed traits[sealed-guide] lays out the trade-off cleanly: sealed is for "I am the only one allowed to add types"; defaulted methods are for "anyone can implement, and I can extend the trait without breaking them." 

// crates/mcpm-secrets/src/store.rs
use secrecy::SecretString;
use async_trait::async_trait;

/// A backend that can store and retrieve named secrets.
///
/// Implementors must provide `get` and `set` at minimum. Every method below
/// has a default; adding new methods to this trait in future MINOR releases
/// is non-breaking because all implementors automatically inherit the default.
#[async_trait]
pub trait SecretStore: Send + Sync {
    /// Fetch a secret by name. Returns Ok(None) if not present.
    async fn get(&self, name: &str) -> Result<Option<SecretString>, SecretError>;

    /// Store a secret. Replaces existing value at the same name.
    async fn set(&self, name: &str, value: SecretString) -> Result<(), SecretError>;

    /// Remove a secret. Returns Ok(false) if not present.
    async fn unset(&self, name: &str) -> Result<bool, SecretError> { Ok(false) }

    /// List secret names (never values).
    async fn list(&self) -> Result<Vec<String>, SecretError> { Ok(Vec::new()) }

    /// Future v1.1: rotate, ttl, audit_id. All defaulted.
    async fn rotate(&self, _name: &str) -> Result<(), SecretError> {
        Err(SecretError::Unsupported { op: "rotate" })
    }
}

#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum SecretError {
    #[error("backend error: {0}")]
    Backend(String),
    #[error("operation not supported: {op}")]
    Unsupported { op: &'static str },
    // future variants
}

The pattern: every method except the two required ones has a default. rotate() in particular defaults to Err(Unsupported), which is the right semantic — the caller asks "can you rotate?" and the backend says "no." When v1.1 adds refresh() for token-bearing stores, every existing implementor automatically inherits an Unsupported default and nothing breaks.

One subtle point: I use async_trait here, not native async-trait. As of Rust 1.75 native async-fn-in-trait is stable, but it imposes object-safety restrictions that bite when we want to dyn-dispatch Box<dyn SecretStore>. async_trait macro-expands to a Box<dyn Future>, which costs a heap allocation per call but makes the trait actually usable as a dyn-object. That's the right trade-off for a backend trait — these calls are not in any hot path, and dyn-dispatch is what makes LayeredSecretStore and runtime plug-ins work.

mcpm-client — the convenience layer that churns

The hard line in the other direction: mcpm-client is allowed to break minor-to-minor. It is documented as such in the crate's README, its crates.io description, and its rustdoc top-level module comment. First-party consumers (CLI, TUI, future GUI) treat it as an internal helper; third parties are pointed at mcpm-protocol instead. 

// crates/mcpm-client/src/lib.rs (sketch)
//! Convenience layer over `mcpm-protocol`. **Not stable across minor versions.**
//! Third parties building alternative mcpmanagerd clients should depend on
//! `mcpm-protocol` directly. This crate exists for CLI/TUI/GUI use only.

pub use mcpm_protocol as wire;  // re-export the entire stable surface

pub struct Client { /* tokio UDS handle, retry policy, etc. */ }

impl Client {
    pub async fn connect() -> Result<Self, ConnectError> { /* dial-or-spawn */ }
    pub async fn server_list(&self) -> Result<Vec<wire::ServerSummary>, CallError> { /* */ }
    pub fn logs_tail(&self, name: &str)
        -> impl futures::Stream<Item = Result<wire::LogLine, CallError>> { /* */ }
}

The re-export of mcpm_protocol as wire is the key ergonomic move: first-party code writes client.server_list() and gets back Vec<wire::ServerSummary> without two separate Cargo dependencies in scope. But the types they're handling are still the stable ones from mcpm-protocol; the churn is only in the methods.

mcpm-core — internal canonical state, no public surface to speak of

mcpm-core is consumed only by mcpm-daemon. Its public surface should be the absolute minimum: a ConfigStore entry point, a Lockfile entry point, an AuditSink entry point. Nothing exported with pub unless mcpm-daemon actually uses it. Everything else is pub(crate). If someone in v1.1 wants to write their own alternative daemon, they re-implement against mcpm-protocol + mcpm-secrets + mcpm-supervisor; they do not Cargo-depend on mcpm-core as a library.

The CAS guard prior_hash on config.put needs one public type: 

#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct ConfigSnapshot {
    pub content: String,
    pub hash: String,
    pub scope: ConfigScope,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(rename_all = "snake_case")]
pub enum ConfigScope { User, Project, Merged }

Both live in mcpm-protocol (they cross the wire). mcpm-core reads and writes them but doesn't re-export anything.

mcpm-supervisor — public methods are behavior, not mechanism

Behind the public API of mcpm-supervisor, the kernel-hacker gets to do whatever they want with cgroup v2 event fds, RLIMIT_AS bookkeeping, and jetsam inference. The public surface exposes behavior: 

pub trait Supervisor: Send + Sync {
    async fn spawn(&self, spec: &SpawnSpec) -> Result<ServerHandle, SupervisorError>;
    async fn stop(&self, handle: &ServerHandle, grace: Duration) -> Result<(), SupervisorError>;
    async fn watch(&self, handle: &ServerHandle) -> impl Stream<Item = SupervisorEvent>;
}

#[non_exhaustive]
pub enum SupervisorEvent {
    Spawned   { pid: u32, ts: SystemTime },
    Crashed   { detail: CrashDetail },
    OomKilled { detail: OomDetail },
    Stopped   { reason: StopReason },
}

#[non_exhaustive]
pub struct OomDetail {
    pub signal: OomSignal,
    pub rss_at_kill_bytes: Option<u64>,
    pub last_log_line: Option<String>,
}

#[non_exhaustive]
pub enum OomSignal {
    /// cgroup v2 memory.events.oom_kill incremented. Deterministic.
    CgroupV2OomKill { count: u32 },
    /// RLIMIT_AS-based SIGKILL inference (cgroupv1 or old kernels).
    RLimitSigkillInferred,
    /// macOS heuristic: SIGKILL + mem pressure + RSS > 80% of limit.
    JetsamInferred { mem_pressure: bool, rss_pct: f32 },
    // future: PSI, eBPF, etc.
}

The kernel-hacker writes OomSignal::CgroupV2OomKill when the kernel told them; otherwise RLimitSigkillInferred or JetsamInferred. When we add PSI integration in v1.1, that's a new variant on the #[non_exhaustive] enum and it's a minor bump. Downstream pattern matches already have a wildcard arm.

mcpm-daemon — binary crate, zero public library surface

Binary crates can publish library targets, but I'd argue mcpm-daemon should explicitly opt out: [lib] stanza omitted, main.rs only. Nothing inside the daemon is intended for re-use by other crates. The line "no public surface" is enforced by the build system, not just by convention.

mcpm-registry, mcpm-projector, mcpm-logs, mcpm-trust — internal helpers, pub(crate) by default

Same pattern: minimal public surface, only what mcpm-daemon needs. Each crate exposes one or two entry types (RegistrySource trait, ProjectionTarget trait, LogSink, TrustVerifier). All #[non_exhaustive]. The RegistrySource trait is sealed to our crate in v1.0 (mod private { pub trait Sealed {} } superbound) because v1.0 only supports the three baked-in registries; if v1.1 opens it up for third-party registry sources, we unsealed it then. The Cargo book's semver page lists "unsealing a trait" as a minor-safe change[api-guidelines-future]; sealing-then-unsealing is the conservative direction.

The ProjectionTarget trait in mcpm-projector is the one I'd argue we keep sealed even in v1.1 — managed-block projection requires understanding our internal config schema, and we don't want third parties writing "creative" projection adapters that break on schema evolution. Bundled per-editor logic, data-driven from manifests/toolchains/, is sufficient extension surface.

CI gates — making the discipline mechanical

Discipline that depends on humans remembering is doomed. Three CI gates make this mechanical:

  1. cargo-semver-checks on every PR that touches mcpm-protocol or mcpm-secrets. Configured to deny for these two crates. Companies like Amazon and Google use cargo-semver-checks to prevent accidental breakage[semver-checks]; we adopt the same gate. Other crates (mcpm-core, mcpm-supervisor, etc.) run it at warn level so we see what's churning but aren't blocked.
  2. cargo hack check --each-feature on mcpm-protocol in CI to verify that the no_std feature combination actually compiles, per Microsoft's Rust training chapter[ms-rust-eng]. Without this, the no_std support silently bitrots the first time someone adds a std::collections::HashMap to a public type.
  3. A "public-surface diff" check that runs cargo public-api against the previous release and emits a PR comment showing every added/removed/changed public item. Not a hard gate — adding public items is fine — but a forcing function for review. It's the kind of thing that makes a maintainer pause when they accidentally re-exported something they meant to keep private.

The deprecation pipeline

Final piece: we will get something wrong. When we do, we need a deprecation path that doesn't break consumers. The pattern:

  1. v1.4 ships the new shape alongside the old; old gets #[deprecated(since = "1.4", note = "use Foo::v2 instead")].
  2. v1.5 keeps both, deprecation warnings fire louder in rustdoc and crate-level docs.
  3. v2.0 removes the old shape. Major bump. Documented in CHANGELOG with migration commands.

Effective Rust's chapter on semver[effective-rust-semver] is the right operational reference for our reviewers. Every public-API PR description has a checkbox: "I have read Effective Rust item 21 and considered whether this change is minor or major." That's not bureaucracy; it's how the discipline propagates to new contributors.

What I'm consciously not doing

A few patterns I'd like to use but am declining for v1.0:

  • Typestate. A ServerHandle<Running> vs ServerHandle<Stopped> type-state design would catch a lot of bugs at compile time. Across an IPC boundary it's incoherent — the wire types are data, the type-state doesn't survive serialization. So I keep type-state inside the daemon's private code (mcpm-supervisor) and use plain runtime enum state on the wire.
  • Generics on public types. Tempting to make SecretStore generic over an Error type the implementor chooses. Don't. A concrete SecretError with #[non_exhaustive] is easier for users and easier to extend; the parameterization saves us nothing.
  • Feature flags as semver escape hatches. Some crates use #[cfg(feature = "unstable")] to ship experimental APIs without the semver weight. We could do this for mcpm-protocol, but I'd rather force ourselves to think before shipping. Experimental APIs go in mcpm-client (which churns anyway) until they bake.

Cross-references

  • The tokio-pragmatist's convenience-layer design — agreed, but the layer lives in mcpm-client, not mcpm-protocol.
  • The systems-veteran's state-machine encoding — agreed, but every public enum representing a state gets #[non_exhaustive].
  • The kernel-hacker's platform-specific event detail — lives in an inner OomSignal enum that is itself #[non_exhaustive]; the outer SupervisorEvent::OomKilled variant stays stable.
  • The boring-tech-defender's minimalism — agreed, plus cargo-semver-checks in CI to make minimalism mechanical rather than aspirational.

  4. Definitive guide to sealed traits in Rust (Predrag Gruevski). Walks through the supertrait-pattern for sealing and explains when to seal vs when to use defaulted methods. We seal RegistrySource and ProjectionTarget in v1.0; we deliberately do not seal SecretStore because users implement it.
  5. cargo-semver-checks. The linter we run in CI as a hard gate on mcpm-protocol and mcpm-secrets. Detects accidental semver violations (3% of releases ship them per the project's own research). Cargo itself uses it; we follow that lead.
  6. Serde — no_std support. The recipe for shipping mcpm-protocol with alloc-only feature configuration so it builds in embedded / bindgen / FFI use cases that need our wire types but don't want std.
  7. Microsoft Rust Engineering — no_std and feature verification. Operational playbook for verifying that no_std + feature flag combinations actually compile in CI via cargo hack check --each-feature. Without this, no_std support silently rots.
  8. Rust RFC 1105 — API evolution. The original framework for what counts as "breaking" in a Rust API: signatures, traits, lifetimes, type inference. Predates most modern tooling but its taxonomy is still the basis of cargo-semver-checks' rules.
  9. Effective Rust — Item 21: Understand what semantic versioning promises. The operational chapter: when to bump major, the asymmetry of "easy to add, hard to remove," and how to design APIs so that you reserve the right to evolve them. Recommended reading for every PR reviewer touching public surface.
  10. SemVer in Rust: Tooling, Breakage, and Edge Cases (FOSDEM 2024). Empirical look at how often Rust crates break semver in practice and which categories of change cause the most surprises. Validates the case for CI tooling over human discipline alone.
  11. Pre-RFC: Sealed traits via #[non_exhaustive] (Rust Internals). Discussion of language-level support for sealing, including why the supertrait pattern is the current best practice. We follow the supertrait pattern; if/when the language adopts a first-class mechanism we migrate.
  12. Turning a Rust struct into an enum is not always a major breaking change (Predrag Gruevski). Edge cases in semver classification; argues why a careful API design lets you make changes that look major but are actually minor. Useful for thinking about ConfigSnapshot-style types where we might want to add an enum'd scope later.
