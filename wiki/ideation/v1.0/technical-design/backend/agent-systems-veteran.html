The Systems Veteran's Backend

Every I/O fails. Power dies mid-write(2). The user pulls the laptop lid down between rename(2) and the directory fsync(2). mcpmanagerd gets SIGKILL'd while a child PID is half-spawned. None of this is exotic. A v1.0 daemon that intends to live across laptop sleeps, OS upgrades, and the inevitable kill -9 needs the same discipline the database people figured out four decades ago: make the state machine explicit, the journal append-only, and recovery a tested code path.

Thoughts

I have shipped daemons. Several. The one habit I notice in every codebase that survives more than two years is that the people who wrote it eventually wrote a recovery loop — a function that takes the on-disk state and reconstructs the in-memory state from scratch — and they ran it on every cold start, not just after a crash. Codebases that did not do this slowly accumulated drift: in-memory structures whose only ground-truth was "what the previous process happened to mutate". Those codebases eventually develop a class of bug nobody wants to debug: "we restarted, and now the audit log says we own a PID that doesn't exist".

The v1.0 spec is broadly excellent and the lockdown choices are pragmatic. But reading technical-design.html with my paranoid hat on, three things scare me, in increasing order:

  1. The supervisor's state is implicit in tokio task graphs. "One tokio task per managed process" (per-crate table) is fine until mcpmanagerd restarts. What is the source of truth that says "before the restart, github-mcp had refcount=3, idle timer firing at T+1700s, restart-attempt counter at 2 within the last window"? Tokio tasks die with the process. The audit log captures the events but it's append-only JSONL, not a queryable projection. If we don't replay the journal to rebuild that supervisor state on boot, we have just signed up for a class of subtle bugs that show up only after laptop sleep, OS upgrade, or daemon segfault — exactly the cases v1.0 promises auto-spawn covers.
  2. "Atomic temp-rename" is necessary but not sufficient for config writes. Flow A says mcpm-core writes the canonical config via temp-rename. POSIX rename(2) atomicity does not transitively guarantee durability across crashes unless we fsync the directory after the rename[1]. A laptop lid-close after the rename but before the directory entry hits disk leaves you with the old file. This is the bug every node-write-file-atomic clone has rediscovered.
  3. OOM detection, restart backoff, and the singleton refcount are three independent state machines, but the spec sketches them as procedural flow. Flow D ("crash → restart with backoff"), Flow B step 9 (idle TTL), and the OOM table all interact: an OOM kill increments the restart counter, which may push the server into failed, which must clear the idle timer, which must surface in the TUI's server.list snapshot. Right now these read like prose. They need to be one explicit enum ServerState with all valid transitions enumerated and a property test that fuzzes the transitions and asserts invariants.

My worldview: a daemon is a state machine plus an I/O wrapper. Build the state machine first, make it pure (no .await, no tokio::process), property-test the hell out of it, then wrap it. This is the sans-I/O discipline that Brett Cannon documented for Python protocols[2] and that the hyperium/h2 crate adopted at the heart of Rust's HTTP/2 stack[3]. The runtime — tokio in our case — is a transport, not the architecture.

Pair that with an event journal: every state transition is appended to an on-disk log before the in-memory state advances. Restart = replay. This is older than ARIES and the database literature spelled it out in detail in 1992[4]; SQLite's WAL mode is the same idea applied to a single file[5]. We are not building a database, but we are building a daemon that promises lifecycle coherence across crashes, and the same primitives apply at a smaller scale.

My peers will accuse me of over-engineering for a 10s-of-MCPs scale. That criticism is reasonable in shape but wrong in detail. Sans-I/O cores and event journals are not a cost at v1.0 — they're a structure that makes everything else easier. They turn crash-recovery from a hope into a cargo test target. They let tokio-pragmatist's tower middlewares run on top of a state machine they can't corrupt. They let library-author publish mcpm-protocol as a stable surface because the protocol's state machine is a typed crate, not a memo. And they cost maybe 800 LoC across mcpm-core and mcpm-supervisor.

Arguments

Against tokio-pragmatist

My pragmatist colleague will reach for tokio + tower + tracing and lean on idiom: tokio::spawn per supervised child, tokio::select! on the child's exit + idle timer + shutdown signal, a layered tower service for the JSON-RPC handlers. I agree with every individual choice. I disagree with the implied architecture.

The pragmatist's tokio::select! is where state goes to die. When you write 

tokio::select! {
    result = child.wait()       => on_child_exit(result),
    _      = idle_timer.tick()  => on_idle(),
    _      = shutdown.cancelled() => on_shutdown(),
}

…you have just stuffed a state machine into a future and made it inaccessible to everything else. The refcount lives in some shared Arc<Mutex<HashMap<…>>>; the idle-timer cancellation lives in the local task; the "is this server in the middle of being restarted" boolean lives in a third place. After a mcpmanagerd restart, none of this is on disk. Tokio docs themselves note that cancellation safety is subtle and that graceful shutdown across many tasks requires explicit CancellationToken plumbing[6] — which is the smell that the state is in the wrong place.

The fix is to flip the polarity. mcpm-supervisor exposes a pure Supervisor struct whose method signatures are fn on_child_exit(&mut self, id, status) -> Vec<Action>, fn on_tick(&mut self, now) -> Vec<Action>, fn on_exec_request(&mut self, server) -> Vec<Action>. Action is an enum: SpawnChild, SendSignal(pid, signal), StartIdleTimer(id, secs), CancelIdleTimer(id), MarkFailed(id, reason), AppendJournal(entry). A thin tokio shell turns those Actions into actual syscalls and timers. The pragmatist's tokio::select! still exists — it just becomes a dumb dispatch loop that drains an action queue. The state machine itself is testable without spawning a process.

That's the hyperium/h2 playbook: the connection state machine lives in proto/streams/state.rs as a pure enum, and the tokio-aware I/O layer drives it with bytes-in / bytes-out[3]. We get cancellation safety for free because the state machine doesn't await anything. We get property tests for free because the state machine is a function.

See also tokio-pragmatist's design — I expect we'll converge on "yes, tokio runs the shell; the kernel of supervision is pure".

Against library-author

Library-author wants mcpm-protocol tiny, stable, #[non_exhaustive], semver-disciplined. Good. I want all of that plus a property: every wire enum has a corresponding state-machine enum in mcpm-core or mcpm-supervisor, and the relationship is enforced by a test rather than memorized by humans. The wire schema is a projection of internal state; if the projection drifts, debugging is hell.

The specific risk: library-author's instinct is to define ServerStatus as a flat enum in mcpm-protocol — say { Stopped, Running, Failed, OomKilled } — and let the daemon map its internal state onto it. That mapping is the bug-farm. Internally we'll have a richer state with attempt counters, idle deadlines, and "this server is mid-restart" flags. Squashing all of that to four variants for the wire is fine, but only if the squash is a typed impl From<internal::ServerState> for protocol::ServerStatus with exhaustive pattern matching. A property test compares "internal state after N journal-replay events" against "wire status returned from server.list" and asserts the mapping is total.

I also want a wire-level conformance test driven by the journal. Every protocol method has a property: "if the daemon is in state S, and method M is called with args A, the result R and journal-delta J are deterministic functions of (S, M, A)". Property-test that with proptest, including the streaming logs.tail handler[7]. This protects library-author's stable-surface promise: the protocol doesn't drift because the semantics are pinned in tests, not just the wire shape.

The disagreement is a small one: library-author thinks discipline around the wire types is enough. I think the wire types are a window onto the state machine, and you need to property-test the window — otherwise you ship a stable wire that means slightly different things in different versions. Cross-ref: library-author's design.

Against kernel-hacker

Kernel-hacker will fight for cgroupv2 memory.events, eBPF for tracing, RLIMIT_AS fallbacks, and macOS jetsam heuristics — all of which v1.0 already specifies (Flow D). We agree on the primitives. We disagree on where they live in the architecture.

Kernel-hacker's instinct is to embed the OOM-detection logic in the supervisor task — a tokio task per child that calls inotify_init1 or kqueue, parses the cgroup event stream, and decides "this was OOM, increment the restart counter". I want that logic in a pure function: 

// in mcpm-supervisor, sans-I/O core
pub fn classify_exit(
    exit_status: ExitStatus,
    oom_signal:  Option<OomEvidence>,   // gathered by the I/O layer
    last_rss_pct: Option<u8>,
    pressure_recent: bool,
) -> ExitClass {
    use ExitClass::*;
    match (exit_status.signal(), oom_signal) {
        (Some(libc::SIGKILL), Some(OomEvidence::Cgroup)) => OomKill,
        (Some(libc::SIGKILL), None) if pressure_recent
            && last_rss_pct.is_some_and(|p| p > 80)        => ProbableOom,
        (Some(libc::SIGKILL), _)                            => UnknownKill,
        (Some(sig), _)                                      => Signal(sig),
        (None, _) if exit_status.success()                  => CleanExit,
        (None, _)                                           => ErrorExit(exit_status.code()),
    }
}

That's the entire macOS jetsam heuristic from Flow D, but it's a pure function I can property-test with all 24=16 combinations of inputs, including the cases the spec doesn't enumerate ("what if cgroup reports OOM but the exit was SIGSEGV?"). The I/O layer's job is just to populate OomEvidence. Kernel-hacker's instinct lumps these together; my instinct splits them so the policy is testable and the platform-specific I/O is swappable.

The same logic applies to backoff: mcpm-supervisor's pure core computes fn next_delay(attempt: u32, base: Duration, cap: Duration, jitter: f64) -> Duration. It doesn't sleep; it returns a number. The I/O layer turns that number into a tokio::time::sleep. Property test: for any (attempt, base, cap, jitter), the result is in [0, cap] and is monotonically non-decreasing across attempts (within the jitter window). That's the kind of invariant kernel-hacker thinks is "obvious" until a misplaced minus sign turns the backoff negative and you get a tight respawn loop on a customer's machine.

Cross-ref: kernel-hacker's design — we will agree on the syscalls; I want them living behind a pure decision layer.

Against boring-tech-defender

Boring-tech-defender will argue: line-delimited JSON over UDS, no journal, no state machine, just a hash map and rewrite the config file when it changes. Ship it. I respect the instinct. It's wrong specifically for the parts where the spec already commits to consistency.

The v1.0 spec already has CAS-style prior_hash guards on config.put (decision #6, resolved 2026-05-24). That's a small piece of optimistic concurrency control bolted onto the config layer. It only works if config.get returns a hash that remains valid until the next mutation. Without a journal — without a serialized stream of "config mutated at this hash → that hash" — two concurrent writers can each observe the same prior_hash, both pass the CAS check, and the second write silently wins. The spec says "atomic temp-rename" prevents that, which is true on a single host with a single filesystem if and only if we hold an OS file lock during the read-hash-write sequence. The journal is a cleaner primitive: every config change appends a journal entry under a daemon-held lock, and prior_hash is the LSN of the last entry. The boring solution becomes the correct solution.

The other place boring-tech-defender's instinct breaks is the audit log itself. The spec already commits to append-only JSONL with daily rotation. Congratulations — we have a journal. It just doesn't have a schema for "this is a state transition the daemon must replay on restart". My ask is small: reserve a subset of the audit log's event field for state-machine events (server.spawn, server.stop, server.refcount-delta, server.restart-scheduled), and define recovery as "replay all such events since the last checkpoint". This costs maybe 200 lines of code on top of what the spec already specifies.

I will concede this: we do not need RocksDB, sled, or a real WAL implementation. JSONL + fsync + directory-fsync after rotation is enough for 10s of MCPs at v1.0 scale. Boring stack, principled use. Cross-ref: boring-tech-defender's design.

Design

1. Sans-I/O cores in two crates

Two crates get explicit sans-I/O cores. Everything else is glue.

CratePure coreI/O shell (separate file in same crate)
mcpm-core Config validation (fn validate(toml: &str) -> Result<ConfigDoc, Vec<Diag>>); CAS guard logic (fn check_prior(hash, doc) -> CasOutcome); journal-event projection (fn project(events: &[JournalEvent]) -> CoreState); lockfile resolution (fn resolve(config, registry_snapshot) -> Lockfile). fs.rs — atomic-write with directory-fsync; mmap of the audit JSONL; tokio stream that decodes the file into JournalEvents for projection.
mcpm-supervisor enum ServerState (below); fn step(state, event) -> (NewState, Vec<Action>); fn next_delay(attempt, …) -> Duration; fn classify_exit(…) -> ExitClass; fn refcount_delta(state, delta) -> (NewState, Vec<Action>). process.rs — tokio::process::Command; cgroup setup; signal delivery; journal.rs — appends the journal entries the pure core emits.

No tokio::spawn inside the pure-core modules. No async fn. The pure cores expose synchronous functions that operate on &mut Self and emit Vec<Action>. The shell drains the action queue against tokio.

2. Explicit state types

The supervisor's ServerState is the load-bearing type. Yoshua Wuyts' state-machine essays in Rust make a strong case for enum-based modeling with explicit transitions[8]; we follow that shape verbatim. Stable variant tags are critical because the journal serializes them. 

// mcpm-supervisor/src/state.rs (sans-I/O)
#[derive(Debug, Clone, Eq, PartialEq, Serialize, Deserialize)]

    Stopped,

    Running    { spawn_id: SpawnId, pid: u32, refcount: u32,

    Restarting { spawn_id: SpawnId, attempt: u32, backoff_until: Timestamp,
                 last_exit: ExitClass },
    Failed     { reason: FailureReason, attempts: u32, window_start: Timestamp },

pub enum Event {
    SpawnRequested { client_id: ClientId, server: ServerName, now: Timestamp },
    SpawnSucceeded { spawn_id: SpawnId, pid: u32, now: Timestamp },
    SpawnFailed    { spawn_id: SpawnId, error: SpawnError, now: Timestamp },
    ChildExited    { spawn_id: SpawnId, class: ExitClass, now: Timestamp },
    RefcountInc    { spawn_id: SpawnId, client_id: ClientId, now: Timestamp },
    RefcountDec    { spawn_id: SpawnId, client_id: ClientId, now: Timestamp },
    IdleFired      { spawn_id: SpawnId, now: Timestamp },
    StopRequested  { spawn_id: SpawnId, graceful: bool, now: Timestamp },
    BackoffElapsed { spawn_id: SpawnId, now: Timestamp },

3. Event-journal schema (re-using mcpm-logs)

The spec already promises an append-only JSONL audit log ($XDG_STATE_HOME/mcpmanagerd/audit/YYYY-MM-DD.jsonl). We reuse it. We carve a sub-namespace of event values that the supervisor's recovery loop replays. The audit log gains a single new field — lsn, a monotonic 64-bit counter — to give every event a stable identity: 

{
  "ts":   "2026-05-24T19:15:02.413891Z",
  "lsn":  17394021,
  "event":"supervisor.spawn_succeeded",   // namespace: supervisor.*  ← replayable
  "actor":{ "kind":"internal" },
  "server":"github-mcp",
  "outcome":"ok",
  "details":{
    "spawn_id":"01J9KX2H8…",              // ULID
    "pid": 84219,
    "attempt": 0,
    "isolation":"devenv",
    "env_hash":"sha256:abcd…"             // hash of the resolved env map, not the env itself
  },
  "v":1
}

Replayable events (supervisor.* namespace): spawn_requested, spawn_succeeded, spawn_failed, child_exited, refcount_inc, refcount_dec, idle_scheduled, idle_cancelled, idle_fired, restart_scheduled, restart_attempted, marked_failed, stop_requested. Non-replayable (secret.read, config.change, projection.write, auth.failed, etc.): observability only.

A checkpoint is written every N=1000 events or 60 seconds, whichever comes first. The checkpoint serializes the full HashMap<ServerName, ServerState> plus the LSN it was taken at. On daemon start, recovery loads the latest checkpoint and replays all supervisor.* events with lsn > checkpoint.lsn. This is identical in spirit to ARIES "REDO from last checkpoint"[4] but vastly simpler because we don't have multi-resource transactions; we have a single in-memory map.

4. Recovery sequence

mcpmanagerd starts. The recovery sequence is: 

1. Acquire flock on $XDG_RUNTIME_DIR/mcpmanagerd.lock. (existing dial-or-spawn invariant)
2. Open audit/YYYY-MM-DD.jsonl in append mode; fsync the directory before any writes.
3. Load the most recent checkpoint at $XDG_STATE_HOME/mcpmanagerd/checkpoints/latest.cbor.
   If none, start from empty state.
4. Read all audit lines with lsn > checkpoint.lsn. Filter to supervisor.* namespace.
5. For each event in order, call:
       (state, _) = step(state, event, &policy_for(event.server));
   We discard the Action vec during replay — those actions already happened the first time.
6. After replay, scan the resulting state map. For every server in Running { pid, .. }:
       a. Probe pid with kill(pid, 0). If ESRCH, the process is gone — synthesize a
          ChildExited { class: UnknownKill } event and step the machine again, write the
          synthesized event to the journal.
       b. If alive, attempt to reattach: open the child's stdio FIFOs from
          $XDG_RUNTIME_DIR/mcpmanagerd/stdio/<spawn_id>/.
          If reattach fails, treat as ChildExited.
7. For every server in Restarting { backoff_until }: if backoff_until is in the past,
   synthesize BackoffElapsed. Otherwise re-arm the tokio timer.
8. For every server in Running { idle_deadline: Some(t) }: if t in the past, synthesize
   IdleFired. Otherwise re-arm the timer.
9. Open the UDS listener. Start accepting clients.
10. Write a supervisor.recovery_complete event.

Step 6 is the key bit kernel-hacker and I agree on: PIDs survive the daemon's death. macOS and Linux both keep child processes alive when their parent dies (the kernel re-parents them to PID 1). We can probe with kill(pid, 0) and, if alive, reattach. The spawn_id ULID lets us distinguish "the PID I had before" from a "a new process that happens to be reusing that PID". This is the same trick conmon uses to survive podman restarts[9].

5. Property-test strategy

Three test layers, all using proptest[7]:

  1. Per-function properties. next_delay is monotonic and bounded. classify_exit never returns OomKill without OomEvidence::Cgroup. step(state, event) never produces a state whose internal invariants (refcount > 0 ⟹ Running) are violated.
  2. State-machine sequential testing via proptest-state-machine[10]. Generate sequences of Events and compare the resulting state against a model implementation (a hand-written, inefficient reference machine). Shrink to minimal failing sequences. The model captures the spec; the implementation captures performance. They should agree.
  3. Crash-then-recover. Generate an event sequence, split it at a random index, serialize the journal up to the split, run recovery, then run the rest of the sequence. The final state must equal the state of a single uninterrupted run. This is the property database recovery papers call "crash equivalence"; without it, we have no evidence that recovery actually recovers.

Test goal: at least 1000 generated cases per property per CI run; shrunk failing cases committed as regression seeds. Empirically, the first time you run #3 against any non-trivial state machine, it finds bugs. This is the difference between "crash-recovery works because we thought about it" and "crash-recovery works because we proved it".

6. Atomic file writes, properly

mcpm-core's atomic writes follow the recipe LWN published in 2009 and that npm's write-file-atomic rediscovered fifteen years later[1]: 

fn atomic_write(path: &Path, bytes: &[u8]) -> io::Result<()> {
    let dir = path.parent().expect("path has parent");
    let tmp = NamedTempFile::new_in(dir)?;            // same filesystem
    tmp.as_file().write_all(bytes)?;
    tmp.as_file().sync_all()?;                        // fsync the data
    tmp.persist(path)?;                               // atomic rename
    File::open(dir)?.sync_all()?;                     // fsync the directory entry
    Ok(())
}

The directory-fsync is the line everyone forgets. It's also the line that turns "atomic on most filesystems most of the time" into "atomic on POSIX as specified". On macOS we additionally call F_FULLFSYNC via fcntl on critical paths (the canonical config, the checkpoint file). Cost: a few ms per write. Benefit: the config never half-writes across a power loss.

7. Per-component application

ComponentHow sans-I/O + journal applies
mcpm-core Pure config validation; CAS-guard logic; journal projection. The prior_hash CAS becomes prior_lsn internally — same shape on the wire, stronger guarantee underneath (LSN linearizes config mutations against journal order, eliminating the read-after-write window).
mcpm-daemon Implements the recovery sequence above as a synchronous bootstrap before the tokio runtime serves clients. Auto-spawn semantics use flock(2) on a sibling lockfile (spec already specifies this); the recovery sequence is what makes auto-spawn safe, because the auto-spawned daemon reconstructs full state before answering anyone.
mcpm-protocol Wire types versioned; mcpm_wire_version per spec. Adds checkpoint_lsn to daemon.status so observability tools can see "is the daemon caught up?". Adds a documented E_CONFIG_CONFLICT code with the current prior_hash returned so clients can resolve cleanly.
mcpm-client Auto-spawn dance plus a recovery probe: after auto-spawning, wait for daemon.status to report recovery_complete before sending any mutating call. This handles the "I spawned mcpmanagerd, but it's still replaying its journal" race that v1.0 currently elides.
mcpm-supervisor All discussed above. The supervisor is the largest piece of sans-I/O surface and the primary beneficiary of property testing.
mcpm-registry BM25 search and version resolution are already pure. The cache refresh path (network) needs explicit "stale-while-revalidate" semantics: if the network fails, the daemon must never silently serve a stale index — it must label the index as stale in RegistryEntry::freshness so the client can warn. Journal entries: registry.refresh_attempted, registry.refresh_succeeded, registry.refresh_failed.
mcpm-secrets SecretStore trait is already a clean abstraction; what's missing is a test double that lets us property-test the supervisor against secret-failure modes. Add InMemorySecretStore and FailingSecretStore for tests. The trait's fetch returns Result<SecretString, SecretError>; the supervisor's step machine handles every variant. Property: no secret value ever appears in any Action serializable form. Fuzz-test the journal serializer to confirm.
mcpm-projector Managed-block sync is naturally idempotent: read, diff, write. Sans-I/O fits perfectly — fn compute_managed_block(canonical: &ConfigDoc, current_file: &str, tool: ToolId) -> (NewFileContents, DiffSummary). Property: applying the function twice equals applying it once. Property: a manual edit outside the managed-block fence is preserved exactly. Journal entries: projection.write with managed_hash before/after.
mcpm-logs Three-stream tail API: pure ring buffer + on-disk rotation, fed by tokio file streams. Audit JSONL is the journal in disguise — the same writer with a different consumer. Rotation logic: on day-boundary, fsync the closing file, fsync the directory, open the new file. Crash mid-rotation is recoverable because the LSN is monotonic across files.
mcpm-trust Pure: fn verify(manifest_bytes: &[u8], root_pubkey: &PublicKey) -> Result<TrustManifest, VerifyError>. The baked-in-fallback mode is a single boolean in the trust state. Journal entry: trust.refresh_succeeded, trust.refresh_failed, trust.fallback_engaged. The "fetched ↔ baked-in-fallback" state transition is itself a tiny state machine — property-test it.

8. What this buys us

  1. Crash recovery is a tested code path. Property #3 (crash-equivalence) runs in CI every commit. If we break recovery, the build is red before the bug ships. Joe Armstrong's "let it crash" philosophy[11] only works if you have crashed enough times in test to trust the restart.
  2. Restart-during-restart is well-defined. A user runs mcpm restart github-mcp while the supervisor is in Restarting { backoff_until }. The state machine has a single answer to this. The current spec implies an answer; we make it explicit.
  3. The audit log gains a second consumer. Before: humans read it. After: humans and the daemon read it. The format hardens, because regressions in the format break the daemon and not just the user's grep.
  4. Debug aid: time-travel. Replay the journal in a test harness against the sans-I/O core. Reproduce a user's failure deterministically from their audit log (with secret-hashes redacted). The on-call experience improves dramatically.
  5. The wire protocol gets a free invariant. Every server.list response is, by construction, a projection of a journal-replayable state. There is no in-memory shadow state that could disagree with the on-disk truth.

9. Cost estimate

Rough lines of code, on top of the pragmatist's baseline:

  • mcpm-supervisor: ~600 lines of pure state machine, ~300 lines of test (proptest harness + reference model). The I/O shell shrinks proportionally — most of what tokio-pragmatist would put in the supervisor moves to the shell as dumb dispatch.
  • mcpm-core: ~150 lines for the LSN-based journal index + checkpoint serializer.
  • mcpm-logs: ~50 lines for the directory-fsync-on-rotate path; the rest of the code is unchanged.
  • mcpm-daemon: ~200 lines for the recovery bootstrap. Most of this is the PID-probe-and-reattach loop.

Total: ~1300 lines, mostly testable in milliseconds. Compared to a v1.0 codebase that the spec sizes at ~50-80kLoC, this is a 1.5–2.5% tax. The payoff is that the supervisor's behavior under crash, OOM, restart, and laptop-sleep is no longer hand-waved — it's cargo test-able.

10. What I'm explicitly not proposing

  • Not proposing we move to SQLite, RocksDB, or sled. The append-only JSONL + checkpoint is sufficient at our scale. SQLite WAL mode would be the natural next step at 1000s of MCPs[5]; v1.1 territory.
  • Not proposing two-phase commit or any distributed-systems machinery. Single host, single daemon, single writer for the journal.
  • Not proposing the typestate pattern (one Rust type per state). Enum-based modeling is enough for our complexity; typestates would force us into PhantomData gymnastics with no win on testability at this scale.
  • Not changing the wire protocol's user-facing semantics — only adding checkpoint_lsn to daemon.status and the recovery_complete readiness signal.

Net: small architectural surgery, no scope creep. The result is a v1.0 daemon you can pull the plug on, plug back in, and walk away from confident that the next user invocation will see coherent state.
