The Kernel Hacker's Backend

cgroups, RLIMITs, jetsam, signals. Performance under load is a moral question; OOM detection is not a polling problem; orphaned descendants are unforgivable. The supervisor is where the kernel meets the daemon — and it has to be right.

Thoughts

The spec hand-waves the part of the system that decides whether your laptop melts. OOM detect appears in a box in the architecture diagram and the implementation-level decisions accordion claims it is "resolved." It is not resolved. "Watch memory.events.oom_kill increment" is a sentence, not a design. There is a kernel-side dance — fanotify vs inotify vs epoll on the pseudo-file, the POLLPRI wake on cgroup.events, the fsnotify path through kernfs — and we have to pick exactly one. I will pick.

The product asks for "10s of MCPs" supervised by a single daemon, restart-on-crash with jittered backoff, per-process memory caps, OS-correct OOM attribution, and graceful idle-TTL teardown. That is an industrial-strength supervisor. It is also a supervisor we cannot crib from systemd because we are running in --user mode; on macOS we have neither systemd nor cgroups at all. The supervisor must be portable but not the lowest-common-denominator portable. We commit to per-OS specialisation.

My commitments before I argue with my peers:

  • cgroup v2 first. Linux 4.5+ has had it; 5.8+ has all the controllers we need at the unprivileged delegated level. We open memory.events with O_RDONLY|O_NONBLOCK, register it with epoll_ctl for EPOLLPRI, and read on wakeup. That is the deterministic OOM signal. No polling, no memory.peak guesswork.
  • cgroup v1 is dead, but we degrade. CentOS 7 reaches EOL in 2024-06; RHEL 7 in 2024-06. Anyone still on it gets RLIMIT_AS + SIGKILL inference. The "may have been OOM" warning is a feature, not a bug.
  • macOS jetsam is best-effort. Apple is hostile to processes asking "did I just get killed for memory pressure?" The three-condition heuristic in the spec (SIGKILL + memory-pressure signal + RSS > 80%) is the right shape; I'll tighten it with proc_pid_rusage(RUSAGE_INFO_V4) instead of last-known-RSS.
  • Descendants must die with the daemon. PR_SET_PDEATHSIG on Linux; an explicit sentinel-pipe watchdog in the spawned wrapper on macOS (no PDEATHSIG equivalent there). Without this, we will leak processes on daemon crash, and the user will hate us.
  • Wakeup discipline. One tokio task per managed process is a fine abstraction for the application layer, but at the kernel-boundary we coalesce: one epoll fd shared across all memory.events watchers, one signal-coalescing reaper, one signalfd (or, on macOS, one kqueue).

The four people who will disagree with this essay are: an idiomatic-async-Rust person who wants me to "just spawn a task per process and await on it"; a sans-I/O purist who wants the cgroup logic in a pure state machine away from the syscall; a library author who wants this stuff hidden behind a trait; and a boring-tech defender who will try to convince me that RLIMIT_AS is enough on Linux too. They are all wrong in different ways. Let me show them.

Arguments against my four peers

vs tokio-pragmatist

The pragmatist says: one tokio::process::Command per server, await on the spawned handle, react to exit, profit. This is fine for the happy path. It is wrong for OOM, and it is wrong for orphan reaping.

OOM-vs-crash is not visible from the await. On Linux you can read WIFSIGNALED and WTERMSIG and see SIGKILL, but so does a manual kill -KILL from a user. The kernel never tells you "this was the OOM killer" through wait4 — it tells you that through cgroup.events's oom_kill counter, or through memory.events.oom. You have to read the file, and you have to read it at the moment the kernel sets POLLPRI on the corresponding inode, because the file is rewritten not appended. Miss the wake-up — e.g., because your tokio executor was busy — and a subsequent crash will read a stale value and misattribute.

Therefore: the OOM detector is its own task, owned by mcpm-supervisor, that drives a single epoll file descriptor through a dedicated tokio task running on a tokio "blocking" slot. It cross-references against the descendant-watcher: when the spawned handle's await resolves, it does not immediately classify the exit — it sends a "descendant X exited with signal Y at instant T" event through a small mpsc channel to the classifier, which reads the cgroup file, joins on instant, and decides server.crash vs server.oom.

Orphan reaping. Tokio's spawned handle internally does the waitpid, but only if the daemon is alive to call it. The pragmatist hand-waves the daemon-crash case: "the OS will reap them when the daemon dies." No. On Linux, if our daemon dies and the descendant is in --user systemd's reaping scope, fine; if we are not under systemd-user (e.g., the user ran mcpmanagerd & manually from a shell) the descendant is reparented to PID 1 (or in some configurations to the user's session leader) and continues to run, holding ports, holding API keys, holding RAM. The fix is prctl(PR_SET_PDEATHSIG, SIGKILL) on Linux in the descendant, done inside the posix_spawn file_actions / fork()+exec() window before execve. tokio::process::Command does not let you do this directly. We use std::os::unix::process::CommandExt::pre_exec on the underlying std::process::Command before wrapping it as a tokio Command, or we drop to nix::unistd::fork + nix::sys::prctl::set_pdeathsig. I prefer the pre_exec approach — it stays inside the tokio Command idiom but lets us call prctl in the descendant after fork but before exec.

Wakeup amplification. Idiomatic tokio is one task per concern. With 30 MCPs, the pragmatist's design has 30 descendant-watchers, 30 stdout pumps, 30 stderr pumps, 30 cgroup-events watchers, 30 idle timers. 150 tasks. Each write to stdout from a managed process potentially wakes the executor, walks the task into a ready-queue, runs it, and goes back to sleep. The cost is spurious wakeups when there is no downstream consumer (e.g., no logs.tail subscriber). I want a single per-server "stdio aggregator" task with internal channels, and a daemon-wide signal/cgroup-events reactor task with a small dispatch table. Fewer tasks; bounded wakeup count per second; better cache locality.

vs systems-veteran

The veteran says: "sans-I/O cores; event journal; explicit state machines." Yes, mostly. The supervisor's per-server lifecycle (Spawning → Running → Draining → IdleTimer → Stopped, with BackoffWait and Failed) is exactly the kind of thing that should be a state machine — pure, exhaustively-matched, journaled, and unit-testable without spawning processes.

Where we disagree is the boundary. The veteran will push the cgroup-events parser into the pure core: "parse a string, emit an event." That is right. But the watch — the epoll_ctl(ADD, fd, EPOLLPRI), the read() after wakeup, the inode-revoked recovery when the cgroup is destroyed and recreated — that is irreducibly I/O. The boundary is: 

// Pure (lives in mcpm-supervisor/src/state.rs)
enum SupervisorEvent {
    DescendantExited { pid: Pid, status: ExitStatus, instant: Instant },
    CgroupOomKill { server: ServerName, count: u64, instant: Instant },
    MacosMemoryPressure { level: PressureLevel, instant: Instant },
    IdleTimerFired { server: ServerName },
    StartRequest { server: ServerName, client: ClientId },
    StopRequest { server: ServerName, graceful: bool },
}

impl SupervisorCore {
    // pure: (state, event) -> (new state, Vec<Action>)
    pub fn step(&mut self, ev: SupervisorEvent) -> Vec<Action> { /* ... */ }
}

Everything in SupervisorEvent is pre-digested by the I/O shell. The shell owns the epoll fd, the signalfd on Linux, the kqueue on macOS, and the spawned tokio process handles. It emits events; it does not branch on state. That keeps the veteran happy and keeps the kernel-shaped code where it has to be.

Where the veteran is wrong: he will want to journal every wakeup. We must not. The cgroup-events file gets rewritten in-place by the kernel; if we journal the full read on every POLLPRI wake, we are journalling kernel implementation detail. We journal only deltas: "oom_kill went from 0 to 1 for server X." That's a sans-I/O concern (delta computation) but it lives just above the read, in the shell, because we need the previous value to compute the delta and that previous value is part of the supervisor's working state, not part of its journal.

vs library-author

The library author wants the supervisor wrapped in a trait so other people could implement it. They will write something like: 

pub trait ProcessSupervisor: Send + Sync {
    fn spawn(&self, spec: ServerSpec) -> Result<ManagedHandle>;
    fn observe_oom(&self) -> impl Stream<Item = OomEvent>;
    // ...
}

This is the wrong abstraction. There is one supervisor implementation per OS, and the differences between Linux-with-cgroupv2, Linux-with-cgroupv1, and macOS are not "swap a trait implementation" — they are different control planes. cgroup v2 has hierarchical delegation and unified memory/cpu/io controllers; cgroup v1 has independent hierarchies per controller and a different file layout (memory.limit_in_bytes vs memory.max); macOS has none of this. Hiding that behind a trait pretends the supervisor is portable code with platform-specific impls. It isn't. It is platform-specific code with a common configuration surface.

The right abstraction is:

  • mcpm-protocol exposes configuration: memory_max_mb, restart.attempts_max, idle_ttl_secs, singleton. These are wire-stable.
  • mcpm-supervisor internally has #[cfg(target_os = "linux")] and #[cfg(target_os = "macos")] modules. The SupervisorCore state machine is shared; the I/O shell is per-OS, compile-time selected.
  • On Linux there is one more runtime branch: cgroup v2 (preferred) vs cgroup v1 (fallback). That branch happens once at daemon startup — we probe /sys/fs/cgroup/cgroup.controllers (v2 marker) and switch the shell's backing impl.

Where the library author is right: mcpm-protocol needs to carry enough information that a third-party client can render OOM events meaningfully. So the wire payload for server.oom needs oom_kill_count, memory_high_breaches, and a platform tag ("cgroup-v2" | "cgroup-v1" | "macos-jetsam") so the UI can disclaim accordingly. That belongs in mcpm-protocol, semver-stable.

vs boring-tech-defender

The boring-tech defender will say: "setrlimit(RLIMIT_AS) works on every Unix since 1990. Use it everywhere. cgroups is fashion." This is wrong in three measurable ways.

First, RLIMIT_AS limits address space, not RSS. A process that mmaps a 4 GiB file but only faults 50 MiB worth of pages does not consume 4 GiB of memory — but it trips RLIMIT_AS at mmap time. Many Python MCPs do exactly this (numpy memmaps, large tokenizer files). With RLIMIT_AS = 512 MB, perfectly innocent servers will fail to start.

Second, RLIMIT_AS kills the process with no warning. cgroup v2's memory.high is a soft limit: when the cgroup crosses it, the kernel throttles the process by stalling allocations (memory reclaim is forced into the allocation path). The process slows down but does not die. We can observe memory.events.high and emit a warning to the user: "github-mcp is approaching its memory limit." That is a vastly better UX than "your server vanished."

Third, RLIMIT_AS gives us no way to attribute the kill. As above: SIGKILL exit from RLIMIT looks identical to SIGKILL from user, from OOM, from the OOM killer, from systemd-oomd. cgroup v2 distinguishes them perfectly.

So: on Linux with cgroup v2 (the overwhelming majority of users in 2026), we use memory.max for the hard limit, memory.high for the soft warning, and memory.events for attribution. We use RLIMIT_AS only as the fallback on cgroup v1.

Where the boring defender is right: we should not depend on a fashion-of-the-month cgroups library. The cgroups-rs crate in the v1.0 deps table is a thin wrapper that has had API churn. I would rather we do raw filesystem operations — std::fs::write("/sys/fs/cgroup/.../memory.max", "536870912") — than carry a transitive dep that breaks. The cgroup v2 ABI is stable; the pseudo-filesystem is the API. Code directly to it.

Concrete design

Spawn sequence

Every spawn goes through the same path regardless of singleton mode. The supervisor's spawn() shell function is: 

┌──────────────┐                ┌──────────────┐               ┌──────────────┐
│ Supervisor   │                │ Linux kernel │               │ spawned proc │
│ (I/O shell)  │                │ (cgroup v2)  │               │ (MCP server) │
└──────┬───────┘                └──────┬───────┘               └──────┬───────┘
       │  mkdir(/sys/fs/cgroup/mcpmanagerd.slice/  │                        │
       │        server-<name>.scope)               │                        │
       ├──────────────────────────────────────────►│                        │
       │  write memory.max = N                     │                        │
       ├──────────────────────────────────────────►│                        │
       │  write memory.high = N * 0.9              │                        │
       ├──────────────────────────────────────────►│                        │
       │  open memory.events O_NONBLOCK            │                        │
       ├──────────────────────────────────────────►│                        │
       │  epoll_ctl(ADD, fd, EPOLLPRI)             │                        │
       │                                                                    │
       │  clone3(CLONE_INTO_CGROUP, …) (Linux 5.7+)                         │
       │     pre_exec: prctl(PR_SET_PDEATHSIG, SIGKILL);                    │
       │               prctl(PR_SET_NAME, "mcp-srv:<name>");                │
       │               sched_setaffinity(...) if pinned                     │
       ├──────────────────────────────────────────────────────────────────►│
       │                                                                    │
       │  (fallback path: write cgroup.procs = <pid> after spawn)           │
       ├──────────────────────────────────────────►│                        │
       │                                           │                        │
       │  ◄────── ready, on epoll ──────────────  │                        │
       │                                                                    │

Two ordering points matter:

  1. cgroup must be created and configured before the spawn. If we spawn first and migrate the descendant into the cgroup after, there is a window where it can allocate beyond memory.max and crash before the limit takes effect. The window is small but not zero. Pre-create.
  2. The descendant must be in the cgroup before any meaningful work. The clean way to do this is with clone3(CLONE_INTO_CGROUP, …) on Linux 5.7+. That gives us atomic "fork into this cgroup", no race. cgroups-rs doesn't expose it; we use the nix crate's binding (or raw syscall(SYS_clone3, …)) and treat the older-kernel path as the post-spawn-write-cgroup.procs fallback. 
use std::os::fd::AsRawFd;
use nix::sys::epoll::{Epoll, EpollEvent, EpollFlags, EpollCreateFlags};

pub struct SupervisorShell {
    epoll: Epoll,
    // Map epoll user-data → which server's memory.events fired
    cgroup_watchers: HashMap<u64, ServerName>,
    // Last observed counter values; the kernel rewrites the file in place,
    // so we compute deltas at every wake.
    last_oom_kill: HashMap<ServerName, u64>,
    last_high_breach: HashMap<ServerName, u64>,
}

impl SupervisorShell {
    pub fn watch_cgroup(&mut self, server: ServerName) -> nix::Result<()> {
        let path = format!(
            "/sys/fs/cgroup/mcpmanagerd.slice/server-{}.scope/memory.events",
            server.as_str()
        );
        let fd = OpenOptions::new()
            .read(true)
            .custom_flags(libc::O_NONBLOCK | libc::O_CLOEXEC)
            .open(&path)?;
        let token = self.next_token();
        let ev = EpollEvent::new(EpollFlags::EPOLLPRI, token);
        self.epoll.add(&fd, ev)?;
        self.cgroup_watchers.insert(token, server);
        Ok(())
    }
}

cgroup v2 OOM detection

The kernel signals changes to memory.events via POLLPRI on the file descriptor — not POLLIN. This is the same mechanism used for sysfs attribute changes. The standard idiom is: 

/* From kernel Documentation/admin-guide/cgroup-v2.rst:
 *
 *   The notifications generated on cgroup v2 interface files (memory.events,
 *   cgroup.events) follow the POLLPRI/EPOLLPRI semantics for "out-of-band"
 *   data: poll() returns POLLPRI when the file's contents have changed
 *   since last read. The reader must read() and seek back to 0 (or re-open).
 */

int memory_events_fd = open(
    "/sys/fs/cgroup/mcpmanagerd.slice/server-foo.scope/memory.events",
    O_RDONLY | O_NONBLOCK | O_CLOEXEC);

struct pollfd pfd = { .fd = memory_events_fd, .events = POLLPRI };

while (poll(&pfd, 1, /* timeout = */ -1) > 0) {
    if (pfd.revents & POLLPRI) {
        char buf[512];
        lseek(memory_events_fd, 0, SEEK_SET);
        ssize_t n = read(memory_events_fd, buf, sizeof(buf));
        /* parse: lines of "key value\n", e.g.:
         *   low 0
         *   high 0
         *   max 0
         *   oom 0
         *   oom_kill 1
         */
        parse_and_dispatch(buf, n);
    }
}

In Rust, we drive this through tokio's AsyncFd, which wraps any file descriptor and lets us await readable() / writable() readiness. EPOLLPRI is not directly exposed by tokio's AsyncFd (which is hard-coded to EPOLLIN/OUT), so we use a dedicated OS thread that owns the epoll fd and forwards events through a tokio mpsc channel. That is simpler than wrestling with tokio internals, has predictable wakeup behaviour, and isolates the kernel-shaped code to one thread: 

// Dedicated OS thread, not a tokio task.
// One per daemon; handles all cgroup memory.events fds and signalfd.
fn run_supervisor_reactor(
    epoll: Epoll,
    state: Arc<Mutex<SupervisorShell>>,
    tx: tokio::sync::mpsc::Sender<SupervisorEvent>,
) {
    let mut events = [EpollEvent::empty(); 64];
    loop {
        let n = match epoll.wait(&mut events, EpollTimeout::None) {
            Ok(n) => n,
            Err(nix::Error::EINTR) => continue,
            Err(e) => { error!(?e, "epoll_wait failed"); break; }
        };
        for ev in &events[..n] {
            // POLLPRI bit on a cgroup memory.events fd?
            if ev.events().contains(EpollFlags::EPOLLPRI) {
                let token = ev.data();
                let mut sh = state.lock().unwrap();
                if let Some(server) = sh.cgroup_watchers.get(&token).cloned() {
                    if let Ok(delta) = sh.read_memory_events_delta(&server) {
                        if delta.oom_kill_delta > 0 {
                            let _ = tx.blocking_send(SupervisorEvent::CgroupOomKill {
                                server,
                                count: delta.new_oom_kill,
                                instant: Instant::now(),
                            });
                        } else if delta.high_breach_delta > 0 {
                            // soft-limit warning, not a kill
                            let _ = tx.blocking_send(SupervisorEvent::CgroupMemoryHigh {
                                server, instant: Instant::now(),
                            });
                        }
                    }
                }
            }
            // signalfd events — SIGCHLD path:
            if ev.data() == SIGNALFD_TOKEN {
                drain_signalfd(&tx);
            }
        }
    }
}

Why a dedicated thread, not a tokio task? Because epoll_wait with a None timeout blocks the calling kernel thread. On a multi-threaded tokio runtime that blocks one of the worker threads and degrades the rest. Tokio's spawn_blocking is meant for this, but we want a long-lived dedicated thread with a stable identity for the OS, not a thread from a pool. One thread, lifetime of the daemon, sole owner of the epoll fd.

What about cgroup.events? Same mechanism but a different file: populated and frozen keys, useful for the "is this cgroup empty?" check we need when implementing graceful drain. We watch both: memory.events for OOM, cgroup.events for population.

cgroup v1 / RLIMIT_AS fallback

Probe at daemon startup: 

pub enum LinuxCgroupMode {
    V2 { root: PathBuf },     // unified hierarchy at /sys/fs/cgroup
    V1 { memory: PathBuf },    // legacy split hierarchies
    None,                      // no cgroups available (containerized in a way
                               // that hides them, etc.)
}

pub fn detect_cgroup_mode() -> LinuxCgroupMode {
    // v2 marker: /sys/fs/cgroup/cgroup.controllers exists
    if std::fs::metadata("/sys/fs/cgroup/cgroup.controllers").is_ok() {
        return LinuxCgroupMode::V2 { root: PathBuf::from("/sys/fs/cgroup") };
    }
    // v1 marker: /sys/fs/cgroup/memory/memory.limit_in_bytes
    if std::fs::metadata("/sys/fs/cgroup/memory/memory.limit_in_bytes").is_ok() {
        return LinuxCgroupMode::V1 {
            memory: PathBuf::from("/sys/fs/cgroup/memory")
        };
    }
    LinuxCgroupMode::None
}

On the V1 and None branches we fall back to RLIMIT_AS in the spawn pre-exec: 

unsafe fn preexec_set_rlimit(memory_max_bytes: u64) -> std::io::Result<()> {
    use libc::{setrlimit, rlimit, RLIMIT_AS};
    // We use RLIMIT_AS rather than RLIMIT_DATA: address-space includes mmap
    // regions, which matters more for Node/Python servers than data segment.
    // Trade-off acknowledged: mmap-heavy servers may fail to start. Document
    // this in the per-server "isolation limit" warning surfaced by the CLI.
    let rl = rlimit {
        rlim_cur: memory_max_bytes,
        rlim_max: memory_max_bytes,
    };
    let rc = setrlimit(RLIMIT_AS, &rl as *const _);
    if rc != 0 {
        return Err(std::io::Error::last_os_error());
    }
    Ok(())
}

On crash classification under the RLIMIT_AS path: we observe WIFSIGNALED && WTERMSIG == SIGKILL. We cannot distinguish OOM-from-RLIMIT vs OOM-killer vs user-SIGKILL. We emit server.crash with a sub-field oom_likely: "yes-no-perfect-signal" when the last RSS sample (taken by us, polled from /proc/[pid]/status at 1 Hz during the process's lifetime) was above 80% of the configured limit within the last 30 seconds — same heuristic we use on macOS, applied here because we have no better signal. The audit detail carries "may have been OOM, no perfect signal on this kernel".

macOS jetsam inference

macOS jetsam is the kernel's memory pressure killer; it lives in xnu's kern_memorystatus.c. It is not user-controllable in any documented way for non-Apple processes. We cannot subscribe to "your descendant was jetsamed." What we can observe:

  • System memory pressure level via the DISPATCH_SOURCE_TYPE_MEMORYPRESSURE dispatch source. This gives us DISPATCH_MEMORYPRESSURE_NORMAL | WARN | CRITICAL as a delta-fired signal. We hold one source for the lifetime of the daemon and stamp a "last critical-pressure timestamp" continuously.
  • Per-descendant resource usage via proc_pid_rusage(pid, RUSAGE_INFO_V4, ...), which returns a rusage_info_v4 struct including ri_resident_size (current RSS), ri_lifetime_max_phys_footprint (peak), and ri_pageins. We sample this at 1 Hz per managed process during its life.
  • Exit signal via waitpid: WIFSIGNALED && WTERMSIG == SIGKILL with no WCOREDUMP. jetsam delivers SIGKILL; an unrelated SEGV would set WCOREDUMP (subject to ulimit -c).

The classifier: 

fn classify_macos_exit(
    exit: ExitStatus,
    last_rss_bytes: u64,
    memory_limit_bytes: Option<u64>,
    last_critical_pressure_at: Option<Instant>,
    exit_instant: Instant,
) -> CrashOrOom {
    // Condition (a): SIGKILL without core dump
    let sigkill = matches!(exit.signal(), Some(libc::SIGKILL))
                  && !exit.core_dumped();
    // Condition (b): system memory pressure CRITICAL within the last 30s
    let pressure_recent = last_critical_pressure_at
        .map(|t| exit_instant.duration_since(t) <= Duration::from_secs(30))
        .unwrap_or(false);
    // Condition (c): last-known RSS exceeded 80% of the configured limit
    let rss_high = match memory_limit_bytes {
        Some(limit) => last_rss_bytes > (limit * 8 / 10),
        // No limit configured: fall back to "process was using > 1 GiB"
        None => last_rss_bytes > 1_073_741_824,
    };

    if sigkill && pressure_recent && rss_high {
        CrashOrOom::Oom { reason: "jetsam-inferred" }
    } else if sigkill {
        CrashOrOom::Crash { hint: "sigkill, but inferred-not-oom" }
    } else {
        CrashOrOom::Crash { hint: exit_string(&exit) }
    }
}

Why all three? Because each individually has false positives. SIGKILL alone is delivered by the user, by activity monitor's force-quit, by an editor crashing and tearing down its descendant group. Memory pressure alone says nothing about our process — some other process could be the cause. High RSS alone is normal for many MCPs (codebase-indexers, code-graphs). The conjunction is strong evidence; nothing in user-space gives us certainty.

We also expose proc_pid_taskinfo for richer diagnostics in the audit log — thread counts, virtual size, dirty page count. Apple's libproc headers document these. We don't classify on them, but they help the user understand "what was this process doing right before it died?"

Signals + reaper

The daemon's signal-handling discipline:

  • SIGCHLD: drain via waitpid(-1, &status, WNOHANG) in a loop until 0. We do this from the supervisor reactor thread, woken via signalfd (Linux) or kevent on EVFILT_PROC + NOTE_EXIT (macOS). Coalescing is mandatory: a burst of 10 exits delivers as few as one SIGCHLD.
  • SIGTERM: initiate graceful shutdown. Send SIGTERM to every managed process, wait up to graceful_timeout (default 10s), then SIGKILL survivors. Then exit.
  • SIGINT: same as SIGTERM. For users hitting Ctrl-C on a foreground daemon.
  • SIGHUP: re-read canonical config. Used by daemon.reload. Reuses the config-change code path.
  • SIGPIPE: ignore. We get this on broken UDS connections; we want EPIPE from write, not a death.
  • SIGUSR1: dump supervisor state to stderr for debugging (off by default; doc-as-undocumented). Useful when someone hits "the daemon is weird" and we say "kill -USR1 $(pgrep mcpmanagerd) and send us the log."
use nix::sys::signal::{SigSet, Signal};
use nix::sys::signalfd::{SignalFd, SfdFlags};

fn install_signal_handling() -> nix::Result<SignalFd> {
    // Block these signals on the main thread; signalfd is the only path.
    let mut mask = SigSet::empty();
    mask.add(Signal::SIGCHLD);
    mask.add(Signal::SIGTERM);
    mask.add(Signal::SIGINT);
    mask.add(Signal::SIGHUP);
    mask.add(Signal::SIGUSR1);
    mask.thread_block()?;
    // SIGPIPE: ignore process-wide. EPIPE from write() is what we want.
    unsafe { libc::signal(libc::SIGPIPE, libc::SIG_IGN) };
    SignalFd::with_flags(&mask, SfdFlags::SFD_NONBLOCK | SfdFlags::SFD_CLOEXEC)
}

The signalfd is registered on the same epoll as cgroup events. One reactor; one event source per file descriptor; clean dispatch.

On macOS there is no signalfd. We use kqueue EVFILT_SIGNAL filters. kqueue is the right answer: it integrates with the same kqueue we use for exit notification (EVFILT_PROC + NOTE_EXIT) and gives us a single reactor pattern that mirrors the Linux epoll loop.

PR_SET_PDEATHSIG. On Linux, every spawned descendant immediately calls: 

/* in the descendant, after fork() and before execve() */
prctl(PR_SET_PDEATHSIG, SIGKILL, 0, 0, 0);
/* If the parent (mcpmanagerd) dies for any reason, the kernel delivers
 * SIGKILL to this process. Per prctl(2):
 *   "Set the parent-death signal of the calling process to sig..."
 *   "...delivered when the thread that created the calling process
 *    terminates."
 * Note the "thread" caveat: we ensure the daemon's main thread is the
 * spawner. We do not spawn from arbitrary tokio worker threads.
 */

On macOS there is no equivalent. The closest is the SIGTERM-on-parent-die behavior from launchd if we register as a service, but that only applies when launchd itself launches the daemon. For the mcpm-auto-spawned daemon case (the common path) we need a userspace workaround: each spawned descendant is passed a sentinel pipe whose write end the daemon holds. A small wrapper in the descendant does a read(sentinel) in a background thread; an EOF on the sentinel (because the daemon died and closed all its fds) triggers the wrapper to kill(getpid(), SIGKILL).

This is uglier than PR_SET_PDEATHSIG but it's the macOS-correct pattern, used by Docker Desktop, by VS Code's process explorer, by every native macOS tool that needs supervisor semantics without launchd. Document it; test it; live with it.

Idle TTL + singleton refcount

The spec describes the refcount semantics correctly: refcount → 0 starts the idle timer; new client cancels it; timer fires → graceful stop. The kernel-shaped details:

  • Process indexing. Singleton: one entry per ServerName in a HashMap<ServerName, ProcessHandle>. Per-client (singleton = false): HashMap<(ServerName, ClientId), ProcessHandle>. ClientId is the connection-id we assign at UDS accept time, stable for the lifetime of that mcpm exec invocation. We do not derive it from the peer pid (which can be reused) but from a per-connection monotonic counter.
  • Idle timer. One tokio::time::Sleep per server (singleton) or per process (per-client). We do not poll. The supervisor's state machine carries idle_until: Option<Instant>; on refcount-zero it sets the field; on refcount-up it clears the field; the reactor selects on the soonest idle_until across all servers and wakes once.
  • Graceful stop. When the idle timer fires, we send SIGTERM, wait graceful_timeout_secs (default 5 for idle stop, configurable), then SIGKILL. During the wait the server can flush, close database handles, etc. We then rmdir the cgroup directory; the kernel rejects this if the cgroup is non-empty, so it serves as a population check.
  • Negative idle_ttl_secs = never stop. Implementation: idle_until is never set; the field stays None. The state machine simply doesn't have a transition to set it when idle_ttl_secs < 0.
  • idle_ttl_secs = 0 = stop on refcount-zero. Implementation: on refcount-zero we immediately enqueue a StopServer { graceful: true } action. No timer.

Log rotation atomicity

The spec calls for daily rotation of the audit log (YYYY-MM-DD.jsonl) and ring-buffer-backed per-server logs with 16 MiB on-disk rotation. The kernel-relevant correctness points:

  • Audit log. Open with O_APPEND | O_CREAT | O_CLOEXEC. O_APPEND guarantees that concurrent writes from multiple threads are atomically positioned at the current end-of-file by the kernel; we do not need a userspace mutex around the write call itself. We do still serialize because we want to flush() the userspace buffer at controlled boundaries (the 100 ms / 4 KiB threshold), so the lock protects the BufWriter, not the file. fsync is on a 1 s timer (not per-event) to bound durability loss to one second; we accept this for telemetry-style data.
  • Daily rotation correctness. The rotation logic runs once per minute (cheap). It compares the current UTC date to the date encoded in the open log path. If different: open the new path (atomic O_CREAT | O_EXCL first, fall back to O_APPEND | O_CREAT if another writer beat us), flush the old buffer, fsync the old fd, swap the open fd, close the old fd. Any concurrent writer that grabbed the lock before us writes to the old file (correct — that's the file for "now"); any that grabbed after writes to the new file. No interleaving across day boundaries. We use a single shared mutex around the fd-swap step; the fast path (regular append) is lock-free thanks to O_APPEND's kernel-side ordering.
  • Per-server stdout/err logs. Ring buffer in memory (4 MiB default) with a backing file on disk that rotates at 16 MiB. Same O_APPEND pattern. No O_DIRECT: direct I/O bypasses the page cache, which is the opposite of what we want for tail-following (the logs.tail RPC consumer expects fresh data to be available immediately, served from cache).
  • fsync discipline. Audit log: fsync every 1 s and on graceful shutdown. Per-server logs: fsync only on graceful shutdown. Reasoning: audit-log data is the security record, worth one second of latency-window data loss; per-server stdout/err is debugging telemetry, worth the throughput improvement of not syncing.

Cross-component decision table

Crate Kernel-hacker call Rationale
mcpm-core Owns the journal/audit-log write path. O_APPEND append, 1 s fsync. No direct kernel concerns beyond filesystem atomicity. Audit is a security record; durability bounded; never on the fast path.
mcpm-daemon Owns the signalfd / kqueue reactor thread, the UDS accept loop, the SO_PEERCRED check on every accept. Sets process name via prctl(PR_SET_NAME) at startup so ps shows mcpmanagerd. The daemon is the single signal sink; the only place that owns process-wide signal disposition.
mcpm-protocol Adds platform: "cgroup-v2" | "cgroup-v1" | "macos-jetsam" tag on server.oom events; adds memory_high_breach_count for the soft-limit-warning event. Clients need to render disclaim text. Wire-stable.
mcpm-client Auto-spawn: flock(2) on a sibling lockfile ($XDG_RUNTIME_DIR/mcpmanagerd.spawn.lock) with LOCK_EX | LOCK_NB; on success, fork+exec mcpmanagerd; on failure, sleep 50 ms and re-attempt UDS connect. Cap at 100 retries (5 s budget). Prevents thundering-herd of two mcpm invocations both spawning the daemon. The lock is a file lock so it survives crashes.
mcpm-supervisor This essay. Home.
mcpm-registry HTTP fetches use rustls + a fixed CA bundle. Stream-to-disk via tempfile + rename(2) for atomic install. Verify minisign signature before the rename. Atomic-rename is the only POSIX guarantee we have for "either old or new, never half-written."
mcpm-secrets Plaintext lives in secrecy::SecretString until the spawn syscall. Inject via envp in the spawn call — the env is built in the parent's address space, then passed across the execve argv/envp protocol. Parent's SecretString is dropped (zeroed) immediately after spawn returns. Minimises the time plaintext is resident. Cannot avoid memory pages being readable by ptrace-capable processes in the parent's namespace, but bounds the window.
mcpm-projector Managed-block writes use tempfile + rename(2) + fsync(parent_dir) to guarantee crash consistency. On macOS the fsync on parent dir is a no-op as documented; we still call it for portability. Editor configs are user-visible; a half-written one is a worse failure than no update.
mcpm-logs O_APPEND + bounded mutex on fd-swap during rotation. 1 s fsync for audit; on-shutdown fsync for stdout/err. Detailed above.
mcpm-trust Minisign verification of trust.toml happens in-process, no subprocesses. The signature is read into memory; the public key is baked-in (a const &[u8]); minisign-verify runs purely in-process. Fewer attack surfaces than calling out to minisign(1).

What I am explicitly not designing

  • CPU limits. v1.0 spec doesn't ask for CPU caps; cgroup v2 makes them easy (cpu.max) but the failure mode of "MCP uses too much CPU" is much less catastrophic than memory. Defer to v1.1.
  • I/O limits. Same. io.max exists in cgroup v2; the use case is unclear for v1.0.
  • Network namespaces. Stream 2 (sandboxing) owns this. The supervisor does not put descendants in network namespaces; that's bubblewrap / sandbox-exec territory.
  • seccomp filters. Same — sandbox layer.
  • Live OOM-killer disabling. Some distros disable global OOM killer for cgroups via memory.oom.group. We do not touch this; we accept the default (kill the whole cgroup on OOM — which is what we want, since each cgroup is one MCP).
