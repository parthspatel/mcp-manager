The Boring Tech Defender's Backend

Five-ish subcommands. Line-delimited JSON-RPC 2.0 over a UNIX domain socket. tokio::process::Command. std::fs when async earns nothing. TOML files instead of databases. No plugin system. No protobuf, no Cap'n Proto, no gRPC. The simplest design that meets the locked v1.0 decisions, shipped on time, beats the clever one that ships next quarter — or, more likely, never.

Thoughts

Four startups. Four corpses. The most recent one died because three engineers spent eleven weeks rewriting a perfectly fine PostgreSQL-and-Redis stack into a custom Raft-backed event-sourced thing nobody asked for. The first one died because we adopted Thrift in 2014 when JSON would have been fine. The other two are too embarrassing to recount. In every case the technology was excellent. The judgment was not. So when I read the v1.0 spec for MCP Manager, my first job is not to admire it. My first job is to ask: what can we cut and still ship something useful in v1.0?

The locked decisions are already pleasingly conservative. macOS + Linux only. No telemetry. Apache 2.0. Tens of MCPs, not thousands. Curl + Nix, not a self-updater. JSON-RPC 2.0 over UDS. Files on disk. tokio::process. No GUI in v1.0. These are good locks. They came from someone who has shipped before. My job here is to defend them against the inevitable scope creep that arrives once five engineers start drawing boxes on a whiteboard. The pressure to add complexity is constant; the discipline to refuse it has to be louder.

"Choose Boring Technology" by Dan McKinley[1] is the load-bearing essay of my worldview. The argument is simple: every team has a finite budget of innovation tokens. Spend them on the parts of your product that are actually novel. Spend them on the part where the user gets value. MCP Manager's novelty is orchestration of MCP servers for ten editors with one config. That's where the innovation tokens go. Everything else — IPC, config format, process supervision, log rotation, secret storage, registry fetch — should be the most boring, well-trodden choice we can find. JSON over UDS. TOML files. tokio::process. keyring crate. tracing. Done.

Hillel Wayne's writing on essential vs. accidental complexity[2] is the other half. A custom binary protocol is accidental complexity. A custom reaper is accidental complexity. A plugin trait object that can swap secret backends at runtime is accidental complexity. The user does not care. They want mcpm install github-mcp to work in ten seconds and never think about it again. Every keystroke we ask the user to learn, every config schema we ask them to internalize, every error message they have to look up — that's the real budget. Engineering cleverness that doesn't translate to a user-visible hour saved is, definitionally, waste.

Rich Hickey's Simple Made Easy[3] distinguishes "simple" (un-braided, one concern per thing) from "easy" (familiar). The mistake we make in Rust shops is reaching for "easy" — the crate everybody knows, the macro everybody uses — when "simple" would serve us better. But the converse trap is just as bad: building a "simple" abstraction (a clever Transport trait with three implementations) when one concrete implementation would have been both simpler and easier. Defaulting to the concrete first, then extracting an abstraction only after the second use case actually arrives, is the boring path. We have one transport (UDS). We have one IPC format (line-delimited JSON-RPC). We don't need an enum yet.

Kernighan's lever[4]: "Debugging is twice as hard as writing the code in the first place. Therefore, if you write the code as cleverly as possible, you are, by definition, not smart enough to debug it." This is the single most useful sentence in our profession. Every time someone on this team reaches for unsafe, or zero-copy deserialization, or a sans-I/O core that requires its own mental model, I want them to repeat that sentence three times before opening their editor. The fact that we could shave 40µs off a method dispatch with custom framing is not a reason to do it. We will spend that 40µs back, with interest, the first time someone has to bisect a state-machine bug at 11pm.

The Hyrum-rule corollary[5]: every observable behavior of your API will be depended on by someone. The smaller and more boring the public surface, the fewer accidental promises we make. mcpm-protocol should be tiny. The fewer types, the better. Each method we add to the wire is a permanent commitment. Treat it as a one-way door.

So my position for this debate is: the v1.0 design as locked is already close to right, but it has crept in three or four places where my peers will push it further into cleverness. I will push back on each, hard. The default answer to "should we add X?" in v1.0 is no, and the burden of proof is on the person proposing X to show a user-visible benefit measured in hours saved, not microseconds or lines of code.

Arguments against my four peers

vs. tokio-pragmatist — "idiomatic async Rust" can mean over-engineered

I agree with my tokio-pragmatist peer on 90% of things: tokio for the runtime, tracing for logs, tower patterns where they actually help. Where I push back is the temptation to reach for the full tower stack — middleware layers, service traits, retry/timeout/buffer/load-shed wrappers — for a daemon that handles, at peak, a few dozen connections per minute from clients on the same machine. Half the tower ecosystem is designed for HTTP services facing the public internet at meaningful QPS. We are not that. We are one user, one socket, ten editors. tower::Service is a generalization we don't need yet.

Concretely: a JSON-RPC handler dispatch table built as a HashMap<&'static str, fn(Request) -> BoxFuture<Result>>, wrapped in a single tokio::spawn per accepted connection, is fine. It's twenty lines. It has no layers. It logs via tracing::info_span!. It does not need a Layer. The day we need rate-limiting or auth-aware middleware is the day we add it — and that day, in v1.0, is not coming because the auth is "the kernel says you're the same UID" (SO_PEERCRED) and the rate limit is "the user's hands."

I'll also push back on async-everywhere. tokio::fs::read_to_string is async, sure, but reading a 4KB TOML config off a local disk has no business being async. The blocking call takes microseconds. Using tokio::task::spawn_blocking just to satisfy the runtime is worse than the synchronous call. Async pays its keep when you have I/O concurrency to exploit; for a one-shot CLI dispatch that reads one file, parses it, writes another, and exits, std::fs is correct. The "everything must be async because tokio" instinct produces code that is harder to read, harder to test (Rust async ecosystems still have rough testing edges[6]), and not meaningfully faster.

And on streaming: my peer will want logs.tail to use a bidirectional stream with backpressure tokens, ack windows, the whole thing. I'll counter: JSON-RPC notifications on the same UDS connection, written one line at a time, with the bounded tokio::sync::mpsc we already have, is the boring answer. If the client can't keep up, the channel fills, the producer awaits — backpressure is free. We don't need a protocol-level flow control window. We have OS-level TCP-equivalent backpressure on a UDS for the same reason: the kernel will not let the writer outrun the reader.

vs. systems-veteran — sans-I/O is a beautiful idea that costs more than it saves

Sans-I/O is genuinely elegant. The hyper team uses it, h2 uses it, quinn uses it[7]. When it works, it gives you a state machine you can test exhaustively without spinning up tokio. I respect this. But I have watched three projects adopt sans-I/O and end up with a state machine that is more complex than the I/O it replaced, because now every byte enters and exits the machine as a typed event, every partial parse needs a buffered-not-yet-ready state, and every test is a sequence of "feed these bytes, assert this state" assertions that are coupled to internal representation.

For a JSON-RPC server reading line-delimited frames off a UDS, the I/O is the boring part. tokio::io::BufReader::new(stream).lines() gives you an async iterator of Strings. Parse each line with serde_json::from_str. Done. The "state machine" is: read a line, dispatch, write a line. There is no protocol state worth modeling separately. Sans-I/O is the right answer when the protocol has its own framing layer with cross-frame state (HTTP/2 multiplexing, QUIC connection setup). It is the wrong answer when the protocol is "one line, one message" and the connection is "the user's CLI subprocess."

On the event journal: my systems-veteran peer will want a write-ahead log with sequence numbers, replay-on-startup, and a "rebuild in-memory state from the journal" startup path. I'll counter with a simpler model: the canonical state is the TOML files on disk. The audit log is append-only JSONL for humans and security review, not for daemon state reconstruction. On startup, mcpmanagerd reads config.toml, builds in-memory state from it, and that's the recovery path. If the daemon crashes mid-write, the atomic-temp-rename pattern means we never have a half-written config. Recovery is "re-read config.toml." We do not need a journal for state; we need a journal for auditing, which is what the existing JSONL audit log already does. Conflating the two would couple the daemon's startup correctness to the audit log's format, and then we'd be stuck with a schema we can never change.

vs. library-author — public API discipline is good; pre-publishing it is bad

My library-author peer cares about a clean public API and stable semver — values I share. The disagreement is about which crates are public. The mcpm-protocol split is correct: tiny, stable, semver-disciplined, for third-party clients. I'm with that. What I'll push back on is the temptation to make every crate in our workspace publishable to crates.io with a polished docs.rs page. We don't have third-party users of mcpm-supervisor or mcpm-logs. We never will. Those are internal. They should be publish = false in Cargo.toml, free to churn, free to refactor when we learn something. Polishing their interfaces preemptively is wasted effort that creates the wrong incentives: once a crate looks public, somebody starts treating it as public, and then we are committed to its shape.

Concretely: only two crates in our workspace should be publish = true in v1.0: mcpm-protocol (tiny wire types, semver-disciplined) and possibly mcpm-cli as a binary distribution. Everything else: publish = false, doc(hidden) on items we don't want documented, and a top-of-file comment that says "internal, do not depend on this from outside the workspace." This is what rustc does. It's what the Rust standard library does. It's what cargo does. We should do the same.

The library-author peer will also want a #[non_exhaustive] sprinkled on every public enum and struct so future variants can be added without a major-version bump. I agree for mcpm-protocol. I disagree for everything else, because everything else is not public. #[non_exhaustive] on internal types adds friction for our own code (we have to use .. in match arms, we can't construct things outside the defining module without builders) and buys us nothing because we control all the call sites.

Finally, on convenience layers vs. wire types: I support the mcpm-protocol / mcpm-client split exactly as the technical design has it. Wire types are the load-bearing surface; the client is allowed to churn. Treat the wire crate like an IETF spec, and the client crate like a CLI utility.

vs. kernel-hacker — cgroups are fine; reinventing the supervisor is not

My kernel-hacker peer is going to argue for clever OS-primitive use: cgroups for memory limits, eBPF for OOM detection, pidfd_open for child process tracking, kqueue on macOS for event-driven supervision. Some of this is good. Some of it is over-engineered.

What I support: cgroup v2 memory limits on Linux. They work, they're well-tested, they degrade gracefully with the cgroups-rs crate. The fallback to RLIMIT_AS on legacy cgroup v1 distros (the spec already documents this) is correct boring engineering.

What I push back on: writing our own process reaper. tokio::process::Command already handles SIGCHLD, zombie reaping, exit-status collection, and gives us a Child we can .wait().await on. We do not need pidfd_open in v1.0. We do not need signalfd. We do not need a custom prctl(PR_SET_CHILD_SUBREAPER) dance. The tokio team has already debugged the corner cases we would otherwise rediscover at 2am the night before launch. Read the tokio process docs[8] and follow them. The restart-on-crash policy is: spawn → tokio task watches → child exits → check backoff window → re-spawn. The whole supervisor is maybe 300 lines of Rust. Add cgroup attachment and OOM detection on top, another 200 lines. That is the entire mcpm-supervisor crate. If it gets bigger, we're overdoing it.

On macOS OOM detection: the spec already pragmatically settles for "all three of: SIGKILL + memory pressure within 30s + RSS > 80% of limit." That is exactly the boring, pragmatic, won't-be-perfect-but-will-ship answer. My kernel-hacker peer will want to look at jetsam telemetry via private APIs or kperf. Those break between macOS releases. We are not in that game. Document the heuristic, log "may have been OOM" when we're unsure, move on.

On SO_PEERCRED for auth: I support it. That's already boring tech — it's been in Linux since 1.0 and on macOS via LOCAL_PEERCRED for ages. One getsockopt call per connection, compare to the daemon's UID, done. No bearer tokens, no TLS, no cert rotation. The kernel is the source of truth. This is the boring answer and it is also the correct answer.

The minimum-viable backend

The locked v1.0 decisions already do most of my work. Here I'll walk through each of the ten crates and call out, for each, the simplest implementation that meets the requirements — and, where I can, identify a deliberate cut from what a more ambitious team would have built. Every cut needs a justification grounded in "user-visible benefit not earned."

mcpm-core — TOML files. That's it.

Owns canonical config (~/.config/mcp-manager/config.toml), the lockfile, the audit log sink, and the in-memory registry of running servers. Reads files with std::fs. Writes with the atomic-temp-rename pattern: write to config.toml.tmp.<pid>, fsync, rename(2). POSIX guarantees rename atomicity on the same filesystem[9]. No SQLite. No embedded KV store. No state machine library. The "in-memory registry of running servers" is a HashMap<String, ServerState> protected by a tokio::sync::Mutex. If contention ever shows up in a flame graph (it won't, the QPS is single-digit), we can switch to dashmap.

Cut: no schema migration framework. v1.0 ships with one config schema. When v1.1 changes it, we write a one-shot mcpm migrate command. Frameworks like Diesel migrations are appropriate when you're at v17; we're at v1.

mcpm-daemon → mcpmanagerd — line-delimited JSON-RPC over UDS, period

The whole IPC layer fits in roughly the following structure. I'm sketching it because the conversation tends to drift toward complexity unless you can point at the simple version and say "this works." Listen on the UDS. SO_PEERCRED check on accept. Spawn a tokio task per connection. In each task: BufReader::lines() yields one JSON-RPC message per line[10]. serde_json::from_str into a Request enum. Match on method name. Call the handler. Serialize the response with serde_json::to_string, write the line, flush.

For streaming methods (logs.tail): the handler returns an mpsc::Receiver<LogLine>. The connection task pumps from it, serializing each line as a JSON-RPC notification with a correlation field tying it to the original request id. Client cancels by closing the socket — the task notices on the next write, drops the receiver, log producer notices the dropped channel and stops sending. End-to-end backpressure for free. No flow-control protocol on top.

Framing: line-delimited. Not length-prefixed. Not Content-Length headers (which LSP uses[11] — a sensible choice for LSP, but unnecessary here because JSON-RPC requests are usually small and we control both ends). One JSON object per line, newline-separated. Anything serde-able that contains an unescaped newline inside a string is normal-escaped by serde. The framing fits on a postcard.

Cut: no MessagePack, no CBOR, no protobuf "for performance." Wire-format performance is not our bottleneck. The bottleneck is process startup, registry fetch, sandbox setup. JSON parsing of a 200-byte request is nanoseconds. Optimizing this is choosing the wrong battle.

mcpm-protocol — minimum viable type set

The smallest stable surface I can defend. Roughly: 

// In mcpm-protocol/src/lib.rs

#[derive(Serialize, Deserialize)]
#[serde(tag = "method", content = "params")]
pub enum Request {
    #[serde(rename = "server.list")]   ServerList,
    #[serde(rename = "server.start")]  ServerStart { name: String },
    #[serde(rename = "server.stop")]   ServerStop { name: String, graceful: bool },
    #[serde(rename = "install")]       Install { source: InstallSource },
    #[serde(rename = "logs.tail")]     LogsTail { stream: LogStream, follow: bool },
    #[serde(rename = "config.get")]    ConfigGet { scope: Option<Scope> },
    #[serde(rename = "config.put")]    ConfigPut { scope: Option<Scope>, content: String, prior_hash: String },
    #[serde(rename = "secret.set")]    SecretSet { name: String, /* value via streaming param */ },
    #[serde(rename = "secret.list")]   SecretList,
    #[serde(rename = "registry.search")] RegistrySearch { query: String, source: Option<String> },
    #[serde(rename = "projection.sync")]  ProjectionSync { tool: Option<String> },
    #[serde(rename = "project.detect")]   ProjectDetect { cwd: PathBuf },
    #[serde(rename = "daemon.status")]    DaemonStatus,
    // ... a few more from the technical-design wire spec
}

#[derive(Serialize, Deserialize)]
pub struct Response<T> {
    pub jsonrpc: &'static str,    // always "2.0"
    pub mcpm_wire_version: &'static str,
    pub id: serde_json::Value,
    #[serde(flatten)]
    pub body: ResponseBody<T>,
}

That's most of the public surface. #[non_exhaustive] on the public enums so we can add methods in minor versions. Semver discipline: adding variants is a minor bump; removing or renaming is major. We will resist the urge to add a method until a real user need shows up. Every method is a permanent promise (Hyrum[5]).

Cut: no codegen from a schema file (OpenAPI, JSON Schema, protobuf). The types are the schema; serde_json derives the wire format from them. If a third party needs a TypeScript or Python client, they can write one from the docs. We are not Stripe. We do not need a 14-language SDK.

mcpm-client — the dial-or-auto-spawn dance, retry, error mapping

Lives in-tree, churns freely. Wraps mcpm-protocol. Single public entrypoint: Client::connect() -> Result<Client>, which tries to dial the socket, falls back to fork+exec mcpmanagerd, polls for the socket for up to 5 seconds, retries the dial. flock on a sibling lockfile prevents two parallel mcpm invocations from racing to spawn two daemons. Method calls become client.server_list().await -> Result<Vec<ServerSummary>> — one Rust function per wire method. Streaming methods return impl Stream<Item = Result<LogLine>>.

Cut: no async trait for "the client" so it can be mocked. We use #[cfg(test)] integration tests with a real daemon spawned in a temp directory. Mocking a UDS client trait is the kind of thing that looks elegant in slides and creates four hours of "why doesn't the mock match the real behavior?" debugging in practice. A real daemon, fast to start (sub-200ms), is the better test seam.

mcpm-supervisor — the simplest restart policy that meets the spec

One tokio task per managed child. The task: 

loop {
    let child = Command::new(...).spawn()?;
    let exit = child.wait().await?;
    record_audit(server.name, exit);
    if exit.success() { break; }            // clean shutdown, don't restart
    if !restart_policy.should_retry(&state) { mark_failed(); break; }
    sleep(backoff(state.attempt)).await;
    state.attempt += 1;
}

Add the cgroup attachment as a wrapper around spawn(): create a cgroup, attach the child PID before exec, watch memory.events for OOM events. The OOM watcher is another tokio task that loops on inotify-style events from the cgroup. On macOS, the OOM watcher is replaced by the three-signal heuristic (SIGKILL + memory pressure + RSS>80%) the spec already pinned. Total LOC for mcpm-supervisor: I bet under 800 including OOM detection.

Cut: no custom process group / session leader fanciness in v1.0. tokio::process spawns with the same session as the daemon, signals propagate via group only if we ask. The default is fine. If we ever need "kill the whole tree including bash subshells the MCP server spawned," we add setpgid at that point. Not before.

Cut: no health checks beyond "is the process alive." Per-server health endpoints would be nice but they're a v1.1 feature. Every MCP server we know of either responds to JSON-RPC or it doesn't; if we can talk to it, it's alive.

mcpm-registry — least code for three sources

One trait, three implementations. The trait is small: 

trait RegistrySource {
    async fn search(&self, query: &str) -> Result<Vec<Entry>>;
    async fn fetch_index(&self) -> Result<Index>;   // cached on disk
    async fn install(&self, entry: &Entry) -> Result<InstalledPackage>;
}

Three implementations: OfficialRegistry (HTTP fetch + minisign verify), GitHubRegistry (a curated list at a known URL, same as official but a different baked-in pubkey), DockerRegistry (subprocess to cosign verify for OCI image signature + docker pull). Multi-source search is a fan-out then a sort by (priority, score). BM25 over the cached indexes is provided by the tantivy crate or, simpler still, a hand-rolled BM25 in 100 lines because our corpus is small (the entire registry index fits in memory). I'd default to the hand-rolled version because tantivy is a hefty dependency for a few thousand documents.

Cut: no lazy/incremental index updates. On TTL expiry, re-fetch the whole index. Indexes are small (tens of KB). Caching is "the file on disk." If we ever ship a registry with 100k entries, we'll revisit.

mcpm-secrets — do we even need a trait in v1.0?

This is where I push back the hardest. The spec lists SecretStore trait + OsKeyringStore + EnvVarPassthroughStore + LayeredSecretStore. That's four types for what is, in v1.0, one concrete behavior: "read/write the OS keychain via the keyring crate; if the user opted into env-var passthrough, also look up env vars."

My proposal: in v1.0, ship one concrete type. Call it SecretStore. It has an env_passthrough: bool field. Its get method does: 

fn get(&self, name: &str) -> Option<SecretString> {
    if self.env_passthrough {
        if let Ok(v) = std::env::var(name) { return Some(SecretString::new(v)); }
    }
    self.keyring_entry(name).get_password().ok().map(SecretString::new)
}

That's the whole API. No trait. No dyn dispatch. No layered-store composition. When v1.1 adds 1Password support, then we extract a trait, because at that point we have two concrete implementations and the trait pays for itself (Rule of Three[12] — wait for the third use case before abstracting; or, since we'll only have two at that point, the second use case combined with a clear roadmap for the third).

Cut: the trait. Inline the keychain logic. Save 200 lines, 1 indirection layer, 1 mental model. When the next backend arrives, refactor — that's a 30-minute change in Rust with a good IDE.

mcpm-projector — file-rewrite-on-change, dumb as a hammer

For each editor: read its config file, find the BEGIN MCP MANAGED BLOCK / END MCP MANAGED BLOCK fence (the managed-block pattern[13] — boring tech borrowed from Ansible, Puppet, and a thousand dotfile managers), replace the contents between the fences with the projected config, write back atomically. The per-editor logic (where the file lives, what format inside the block, JSON vs. XML vs. YAML vs. JetBrains XML) is data-driven from TOML manifests in manifests/toolchains/. The Rust code is a generic block-replacer; the per-editor knowledge lives in TOML.

Cut: no LSP-style diagnostic emission for "your editor config has a syntax error." If it does, we tell the user "your ~/.cursor/mcp.json isn't valid JSON; can't manage it." Three sentences. Move on.

mcpm-logs — files and seek, not a database

Three streams per server: stdout, stderr, audit. Each backed by an in-memory ring buffer (Vec<LogLine> with a write index) plus on-disk rotation (every N MB or daily, rename to .1.gz, .2.gz, …). logs.tail is implemented as: stream the in-memory ring to the client, then if follow: true, subscribe to new writes via a tokio::sync::broadcast channel and pump those too.

Cut: no log indexing, no full-text search over historical logs, no log-query DSL. Users who want that pipe the file through grep or ripgrep. They already know how. We do not need a JQL.

mcpm-trust — do we even need this in v1.0?

The hardest call. The spec calls for TUF-lite[14] — a fetched trust.toml that lists registry pubkeys, refreshable via HTTP, with a 7-day TTL and fallback to baked-in keys on network failure. The reason TUF exists is to handle key rotation and compromise. Both real risks.

My pushback is not "remove TUF-lite" — it's "make sure the implementation is as boring as the spec implies." Specifically: do not implement the full TUF metadata hierarchy (root.json, targets.json, snapshot.json, timestamp.json with role delegation and threshold signing). We don't need that in v1.0. What we need:

  1. Baked-in root pubkey in the binary (one minisign pubkey, 32 bytes).
  2. Fetch trust.toml from a known URL; verify with the baked-in pubkey.
  3. Cache it on disk with a TTL; refresh on TTL expiry.
  4. On any network failure, fall back to baked-in pubkeys for the 3 default registries.

That's not TUF. That's a signed-document fetch with a TTL. Calling it "TUF-lite" is fine for marketing; just don't actually pull in the tough crate or implement role-delegation metadata. Three hundred lines of Rust, leaning on minisign-verify[15], replaces a 10k-LOC TUF implementation we'd otherwise have to debug.

Cut: role delegation, threshold signing, freeze attacks, mirror metadata. All real TUF features. None earn their keep against the v1.0 threat model (one user, one machine, trying to install MCP servers from a small set of well-known registries we control the root keys for).

Subcommand surface — twelve is acceptable, eight would be better

The spec lists twelve subcommands on the CLI: install, search, test, logs, secret, registry, project, update, init, uninstall, exec, tui. I'm pleasantly surprised it's not more. I'd consider three consolidations:

  • Merge install and update: mcpm install <name> installs or updates. mcpm install with no args updates everything. --accept-breaking opts into major upgrades. Saves a subcommand and matches how brew, apt, and npm already behave for "install something you already have."
  • Move init behavior into first-run-of-anything-else: any subcommand on a system without a config triggers the init flow inline. Saves the user a step.
  • Keep exec separate: it's load-bearing for editor integration. Don't touch.

Net: from 12 to 10. Not dramatic; not nothing. Every removed subcommand is a row in the help text the user no longer has to read.

What we deliberately do not have in v1.0

  • No plugin system. Not as a feature, not as an internal trait scaffolded "for later." When a real plugin use case shows up (a customer pays us for one), we add a trait. Until then, every internal interface is a concrete type.
  • No metric collection. The tracing spans give us structured logs; if a user wants Prometheus, they can grep them.
  • No web UI. Locked decision. Respect it.
  • No remote daemon. UDS only. No "mcpm connect ssh://server" mode. If you want that in v1.x, you tunnel the socket yourself with ssh -L.
  • No multi-user mode. One user, one UID, one daemon. SO_PEERCRED enforces this and we lean on it.

The shape of the team I'd hire to build this

Two engineers. Three at most. One full-time on mcpm-daemon + mcpm-supervisor + mcpm-core (the spine). One full-time on mcpm-cli + mcpm-projector + mcpm-registry (the user-facing leaves). A third part-time on mcpm-trust + mcpm-secrets + release engineering. v1.0 ships in three months with that team because we are not building a Cap'n-Proto-and-eBPF spaceship. We are building a daemon that reads files, spawns processes, and writes to a socket. That is fundamentally a small problem.
