Backend — Facet Synthesis

Where the five backend stances converge, where they diverge, and what gets adopted into the v1.0 build. The five essays cover the same eleven-crate workspace from radically different angles — idiomatic async, sans-I/O purism, public-API discipline, kernel-primitive maximalism, and ruthless scope-cutting — yet they agree on more than they fight about. This page picks winners and writes them down.

Points of agreement

A surprising amount. Four of the five essays were written to argue, but on the structural shape of the v1.0 backend they line up tightly. The disagreements are about where abstractions live, not whether we adopt them.

  1. Tokio is the runtime; no alternatives. Five-for-five. The pragmatist frames it as inheriting the runtime rmcp chose; the veteran wants tokio relegated to a "shell" but still depends on it; the library-author keeps tokio out of mcpm-protocol but expects it in mcpm-client; the kernel-hacker grumbles about its task-per-concern overhead but uses tokio::process::Command; the boring-tech-defender picks tokio because it is now the boring choice for async Rust.
  2. JSON-RPC 2.0 over a UNIX domain socket. Nobody proposes gRPC, MessagePack, Cap'n Proto, or binary framing. The pragmatist would frame with LengthDelimitedCodec; the defender prefers line-delimited frames; both agree the wire format is plain JSON over UDS.
  3. mcpm-protocol is the only crate that must keep semver discipline. The library-author argues this loudest, but the pragmatist, the veteran, and the defender all explicitly endorse the split: tiny stable wire crate, churny convenience client. Even the kernel-hacker concedes that mcpm-protocol needs forward-compatible OOM-event payloads.
  4. The supervisor needs an explicit state machine. The veteran makes the strongest case, but the pragmatist agrees on enum-based modeling, the library-author wants the state types #[non_exhaustive], and the kernel-hacker wants a sans-I/O classifier so platform code stays swappable. Five-for-five on "no hash map of magic strings."
  5. cgroup v2 first, RLIMIT_AS fallback, macOS three-signal heuristic. The kernel-hacker owns the detail; everyone else aligns. The locked v1.0 decision is already this; the synthesis just adopts the kernel-hacker's specific dispatch (POLLPRI on memory.events, in-process polling with deltas).
  6. SO_PEERCRED for IPC auth, no bearer tokens, no TLS. Mentioned approvingly by the pragmatist, the kernel-hacker, and the defender. Locked. Owned by the security facet, but the backend implements it as a tower::Layer or one syscall in the accept loop.
  7. Atomic temp-rename for every config and projection write. Spec already says so. The veteran tightens it (directory-fsync after rename; F_FULLFSYNC on macOS for canonical paths); the pragmatist agrees and adds sync_all on the temp file before rename; the kernel-hacker ratifies the same recipe. Five-for-five.
  8. thiserror in libraries, anyhow in binaries. The pragmatist articulates this as the error-type-discipline rule; the library-author makes it load-bearing for mcpm-protocol; the systems-veteran and boring-tech-defender both implicitly accept it. Nobody wants Box<dyn Error> at module boundaries.
  9. No SQLite, no RocksDB, no sled in v1.0. Even the veteran, who is the most crash-recovery-paranoid voice, explicitly declines to reach for an embedded database — JSONL plus directory-fsync is enough at our scale. Five-for-five.
  10. The audit log is JSONL with daily rotation, append-only, single-writer. All five agree on the disk shape; the only dispute is whether the supervisor also replays it on boot (covered in disagreements below).
  11. Secrets stay typed and zeroed. secrecy::SecretString through the resolver; plaintext only at the execve envp boundary. Mentioned by the pragmatist, the library-author, the kernel-hacker, and tacitly by everyone else.

Points of disagreement

Six live tensions where the stances genuinely diverge. For each, the synthesis pick is recorded in the decisions section below.

1. Should the daemon replay the audit log on boot to rebuild supervisor state?

  • Systems-veteran: Yes. The audit log is a journal; supervisor.* events are replayable; recovery is "load checkpoint, replay events, probe live PIDs, reattach or synthesize ChildExited." This is the only way "auto-spawn" is safe across daemon crashes.
  • Tokio-pragmatist: No. At 10s-of-MCPs scale the supervisor state is small and re-derivable from config.toml; journaling restart-attempt history is over-engineering. If the daemon dies, the children die with it (PR_SET_PDEATHSIG) and we re-spawn fresh.
  • Boring-tech-defender: Agrees with the pragmatist. Canonical state is the TOML files; recovery is "re-read config.toml." Coupling daemon boot to audit-log format is a Hyrum-rule trap.
  • Library-author and kernel-hacker are neutral on the journal but both want the supervisor's state machine to be pure and testable regardless.

2. tower::Service dispatch vs a hand-rolled match

  • Tokio-pragmatist: Full tower stack — peer-cred auth, tracing span, audit emission, concurrency limit as composable Layers. Tests stack the service directly without going through UDS.
  • Boring-tech-defender: A HashMap<&'static str, fn(Request) -> BoxFuture<Result>> wrapped in one tokio::spawn per connection. Tower is for HTTP services at meaningful QPS; we have one user and ten editors.
  • Library-author says the dispatch mechanism is private and can be either — the wire types it accepts and returns are what matters.

3. cgroups-rs crate vs raw pseudo-filesystem writes

  • Tokio-pragmatist: Use cgroups-rs (or a maintained fork). Don't hand-parse the pseudo-FS unless we hit a real ceiling.
  • Kernel-hacker: Code directly to the cgroup v2 ABI. cgroups-rs has had API churn; the pseudo-filesystem hasn't. std::fs::write on memory.max is more boring than a crate that wraps the same write.
  • The defender is silent on which crate but would agree with the kernel-hacker that fewer transitive deps is better; the library-author is silent.

4. SecretStore as a trait at v1.0 vs a concrete struct

  • Library-author: Ship the trait from day one with defaulted methods so v1.1 backends (1Password, Bitwarden, Vault) can land without breaking implementors. The trait is the one extension point we explicitly publish.
  • Boring-tech-defender: Rule of Three. One concrete SecretStore struct with an env_passthrough: bool field. Extract a trait when the second backend actually arrives.
  • The pragmatist and veteran both assume the trait shape because they want test doubles and spawn_blocking wrapping.

5. JoinSet-driven concurrency vs a dedicated reactor thread for OOM

  • Tokio-pragmatist: One JoinSet<ChildOutcome> per supervisor; per-child task does tokio::select! over cancel / oom-watch / child.wait(). Pure tokio idiom.
  • Kernel-hacker: A dedicated OS thread owns epoll; EPOLLPRI on memory.events is not exposed by tokio's AsyncFd, so wrestling the runtime to do what a 50-line reactor thread does cleanly is wasted complexity. Forward events into tokio via mpsc.
  • Veteran is neutral (it's I/O-shell territory); library-author cares only that the OOM-event payload is #[non_exhaustive]; defender would accept either if the surface area is small.

6. Public surface for mcpm-client

  • Library-author: mcpm-client is in-tree, may be publish = true for first-party docs but is documented as "not stable across minor versions." Re-export mcpm-protocol as wire for ergonomics.
  • Boring-tech-defender: publish = false on everything except mcpm-protocol and possibly mcpm-cli as a binary distribution. Polishing internal crates creates the wrong incentives.
  • Tokio-pragmatist: Don't ship two stable surfaces; mcpm-client churns. Aligned with the defender on the spirit.

Per-component decisions

For each of the eleven crates (we cover mcpm-cli only where it touches the backend), one adoption call. Citations point back to the agent whose argument carried the day.

mcpm-core

Decision: Pure data + tokio::fs + the veteran's atomic-write recipe: write to tmp, fsync the temp file, rename(2), fsync the parent directory, on macOS additionally F_FULLFSYNC on the canonical config path. CAS guard prior_hash stays as the wire shape; internally it is computed over the canonical-serialized bytes (not the file bytes) to match the projection-sync invariant.

Carries the day: the systems-veteran on durability; the boring-tech-defender on "no schema migration framework, just mcpm migrate when v1.1 needs it."

mcpm-daemon

Decision: Adopt the pragmatist's tower stack — PeerCredAuthLayer, TraceLayer, AuditLayer, ConcurrencyLimitLayer, then handlers. tower earns its keep because audit + tracing + peer-cred are three orthogonal concerns we already need; composing them as layers is cheaper than threading them through 30+ method handlers. The defender's objection is acknowledged: we cap the stack at the four layers above and resist further "free middleware."

Signal handling and shutdown follow the kernel-hacker's signalfd/kqueue reactor pattern but wrapped in tokio's signal::unix API where it suffices (SIGTERM, SIGINT, SIGHUP); only the SIGCHLD drain and EPOLLPRI on memory.events drop down to the dedicated OS thread.

Carries the day: tokio-pragmatist for the dispatch shape; kernel-hacker for the signal/reactor split.

mcpm-protocol

Decision: Follow the library-author's discipline verbatim. No tokio dep (default-features = ["std"], alloc-only profile works for FFI consumers). #[non_exhaustive] on every public enum and struct. Sealed traits for things only we should implement (none in v1.0, but the pattern is reserved). Method names live as pub const strings in a method module. The Cargo version equals WIRE_VERSION; starts at 0.1.0 and stays 0.x through v1.2-ish of the binary. cargo-semver-checks is a hard CI gate on this crate only.

Forward-compat tolerance: #[serde(default)] on optional params (per the pragmatist's asymmetry argument) rather than deny_unknown_fields. Validation lives at the daemon's handler boundary, not in the deserializer.

Carries the day: library-author on the discipline; pragmatist on forward-compat.

mcpm-client

Decision: In-tree, publish = true (so docs.rs renders), but the crate-level rustdoc says "not stable across minor versions; third parties wanting a stable surface depend on mcpm-protocol." Re-export mcpm_protocol as wire. The dial-or-auto-spawn dance lives here: flock(2) on $XDG_RUNTIME_DIR/mcpmanagerd.spawn.lock with LOCK_EX | LOCK_NB to prevent the thundering-herd race, fork+exec the daemon, poll UDS for up to 5 seconds with 50ms sleeps. Per the kernel-hacker and defender.

Streaming methods return impl futures::Stream<Item = Result<LogLine>>. No retry policy is hidden behind config — the caller passes a tower::retry layer if they want one (per library-author).

mcpm-supervisor

This is the largest synthesis decision; the spec already locks the externals, so the synthesis is about where each piece lives. The structure adopted is the veteran's sans-I/O core + I/O shell split, with the pragmatist's JoinSet/CancellationToken living inside the shell, and the kernel-hacker's syscalls living inside the shell's platform module.

mcpm-registry

Decision: One internal RegistrySource trait, sealed in v1.0 (per library-author), three concrete implementations: official, GitHub-curated, Docker. BM25 is hand-rolled over the cached index (~100 lines, per defender); we do not pull tantivy for a corpus of a few thousand entries. Network fetches use reqwest with rustls; minisign verification happens before any temp-file is promoted via rename(2) (per kernel-hacker). Stale-while-revalidate semantics with an explicit freshness field, per veteran — never silently serve stale.

mcpm-secrets

Decision: Ship the trait from day one, but with a single concrete LayeredSecretStore backing it for v1.0. The boring-tech-defender's objection (Rule of Three) loses to the library-author's argument that this is the extension point we publish — third-party implementations are exactly the use case. Methods have defaults so v1.1 can add rotate / refresh non-breakingly. Sync keyring calls are wrapped in spawn_blocking (per pragmatist) so the trait surface stays async. Plaintext lifetime is bounded: SecretString through the resolver, dropped (zeroed) immediately after the execve envp is built (per kernel-hacker).

mcpm-projector

Decision: Stateless per-editor adapters, fenced managed-block sync, quick-xml for JetBrains XML to avoid injection, atomic temp-rename with directory-fsync. Pure function fn compute_managed_block(canonical, current_file, tool) -> (NewFileContents, DiffSummary) in the sans-I/O core (per veteran); the I/O shell drives tokio::fs. ProjectionTarget trait stays sealed in v1.0 — third-party projection targets are not a v1.0 use case (per library-author).

mcpm-logs

Decision: Three streams, one tokio::sync::broadcast::Sender per stream class. Slow tail-clients see BroadcastStreamRecvError::Lagged(n) and the synthesis surfaces this as a LogLine::lagged(n) sentinel rather than dropping silently (per pragmatist). Audit JSONL is single-writer via mpsc, flushed every 100ms or 4KB. O_APPEND on the file plus a userspace mutex around the buffer-flush; fsync every 1s on the audit log, on-shutdown only for per-server stdout/err (per kernel-hacker's discipline). Daily rotation logic compares UTC date once per minute; rotation grabs the mutex only to swap the fd.

mcpm-trust

Decision: The defender's "300-line signed-document fetch", not a real TUF implementation. Baked-in root pubkey (one minisign 32-byte key); fetch trust.toml from a known URL; verify with minisign-verify in-process; cache on disk with 7-day TTL; periodic refresh task on a CancellationToken child (per pragmatist); on network failure, fall back to the baked-in pubkeys for the three default registries. The pure verification function lives in a sans-I/O module so the fetched-vs-fallback transition is itself a tiny state machine (per veteran).

Crates not directly synthesized here (mcpm-cli and the binary-only mcpmanagerd stanza of mcpm-daemon) are owned by the frontend and DevOps facets respectively.

Open questions

Items where the five essays disagreed strongly enough that the synthesis cannot pick a winner without human judgment. Each lays out the trade-off; none block v1.0 alpha.

OQ-B-1. Do we ship mcpm-client to crates.io?

The library-author wants it published with a "not stable" disclaimer in the docs; the defender wants publish = false until a third-party use case appears. Trade-off: publishing gives us free docs.rs rendering and lets external CLI authors experiment without source-tree cloning. Not publishing prevents the wrong incentive (treating it as a stable surface) and reduces accidental promises under Hyrum's law. Lean: publish at 0.x with a prominent README banner and a module-level deprecation hint when matched against by external dependents — capture the docs.rs benefit without committing.

OQ-B-2. Is the cost of property-test infrastructure worth it at 10s-of-MCPs scale?

The veteran's three-layer proptest harness (per-function, sequential state-machine, crash-equivalence) is the single biggest engineering investment in this synthesis: ~1300 LoC of pure-core + ~300 LoC of test harness. The defender would argue that integration tests with a real daemon (spawned in a tmpdir per the library-author's example) catch the same bugs at a fraction of the engineering cost. Trade-off: proptest finds shrinkable failing sequences that integration tests rarely surface; integration tests catch coupling bugs proptest misses. Lean: proptest for the supervisor's step function and classify_exit / next_delay (the three places with the highest combinatorial surface); integration tests for everything else. Skip the crash-equivalence property until v1.1 because we decided against audit-log-replay-on-boot.

OQ-B-3. How aggressively do we instrument with tracing spans in v1.0?

Pragmatist wants #[instrument] on every handler with structured fields (request id, client id, server name) so future tracing-opentelemetry integration is "free." defender warns that span proliferation is the tracing equivalent of premature optimization — every span is a runtime cost, and most never get queried. Trade-off: spans are cheap (~50ns each on a release build) but the structured-fields discipline costs review attention. Lean: spans on RPC handler boundaries and supervisor state transitions; not on inner loops or the OOM-watch thread. Defer otel exporter wiring to v1.1 alongside the locked decision on telemetry (currently locked off — only reopened if user feedback demands it).

OQ-B-4. tokio::sync::broadcast vs per-subscriber bounded mpsc for logs.tail?

Broadcast gives lossy backpressure (Lagged(n)) cleanly per the pragmatist; the defender argues that one bounded mpsc per subscriber gives blocking backpressure with simpler semantics. Trade-off: with broadcast, a slow TUI tail loses lines but never blocks the producer; with mpsc, a wedged subscriber wedges the producer. For a log stream the former is correct; for an audit stream the latter is. Lean: broadcast for stdout/stderr tails; single-writer mpsc for audit; this is already the synthesis above, but it's worth flagging as an open call because the alternative reads simpler and a future maintainer may want to revisit.

OQ-B-5. Should mcpm-protocol ship a no_std + alloc-only profile from day one?

The library-author argues yes — it costs little now and protects future FFI / PyO3 / WASM consumers; the defender argues YAGNI — we have zero embedded use cases on the roadmap. Trade-off: the cost is one feature flag and one cargo hack check --each-feature CI job; the value is contingent on use cases that may never materialize. Lean: ship the feature, add the CI job, accept the small overhead. Removing no_std support later would be a breaking change; adding it later is harder than people think because every accidental std::collections usage in a public type has to be unwound.

OQ-B-6. Sealed vs unsealed RegistrySource trait

The synthesis picked sealed in v1.0 per library-author's conservative direction. But the spec's "3 default registries" lock could be read as forward-looking — if v1.1 wants community registries, unsealing is non-breaking (cargo book confirms) and we lose nothing by leaving it sealed for now. Lean: hold the seal for v1.0; revisit at v1.1 if registry pluggability becomes a real ask.

Ranking matrix

Weights are tunable — drag the sliders to re-rank stances against your priorities. The default weights bias toward reliability and simplicity, matching the v1.0 lock ("10s of MCPs, ship in a quarter, no telemetry"). Pushing performance up rewards the kernel-hacker; pushing API stability up rewards the library-author; pushing simplicity up rewards the boring-tech-defender. The pragmatist is the centre of gravity at default weights, which is consistent with how much of their design ended up in the decisions above.
