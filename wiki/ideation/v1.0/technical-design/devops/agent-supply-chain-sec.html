The Supply Chain Sec's DevOps

Signed everything. SBOM at every release. Reproducible builds. cargo-deny, cargo-vet, cargo-audit, cosign, minisign — the boring, well-trodden supply-chain stack, applied without exception. mcpm is in the business of installing other people's code on developers' laptops, which makes us — and our own release pipeline — a high-value target. Treat it like one.

Thoughts

The north star

MCP Manager is a package manager for code that executes on the developer's machine. Every MCP server we install is, by definition, going to read files, talk to the network, hold OAuth tokens, and execute as the user. The awesome-mcp-servers long tail is going to include genuinely malicious entries within weeks of mass adoption — the same way npm, PyPI, and Cargo all attracted typo-squat campaigns within their first wave of mainstream traction[1]. If we don't bake supply-chain integrity into v1.0, we will be retrofitting it at 3am after the first credible incident.

The v1.0 spec correctly locked the high-level decisions: TUF-lite for the registry index, minisign for index signing, cosign-when-present for OCI packages, baked-in pubkey fallback for first-run[2]. The argument is over HOW — what concretely we sign, what SBOM format, what SLSA level we target, what cargo-vet trust set we adopt, whether mcpm verifies its own binary on every spawn (no), and how mcpm uninstall tears down trust state without leaving orphaned keys behind.

Initial reaction to the v1.0 spec

Three places where the spec is right and we should reinforce, three places where it's silent and we'll fill in:

  • Right: minisign for the index. ed25519, 32-byte pubkey, no PKI, no X.509 disasters, no expiry surprises. The Rust client (minisign-verify) is sans-I/O, 600 lines, audited[3]. The spec's choice is the conservative-but-correct one.
  • Right: cosign when present. Sigstore is excellent but its trust roots (Fulcio, Rekor) introduce dependencies we don't control. Treating cosign as an additional verification path for OCI packages — never a sole one for our own releases — is the right hedge[4].
  • Right: baked-in pubkey fallback for first-run. The spec already encodes "trusted-baked-in-only" mode for offline boot; we extend the same principle to the installer script.
  • Silent on SBOM format. The spec mentions SBOMs nowhere. We commit to CycloneDX 1.5 JSON, generated by cargo-cyclonedx, attached to every GitHub release[5].
  • Silent on SLSA level. We target SLSA Build Level 3 via GitHub's slsa-framework/slsa-github-generator, gated behind a CI workflow with the standard provenance attestation[6].
  • Silent on cargo-vet. We import Mozilla's, Google's, Bytecode Alliance's, and Embark's audit sets and write our own deltas. ~600 transitive crates → ~50 unique deltas we own[7].

Threats we are actually modelling

Concrete threat actors we design against — not generic "hackers", but the specific failure modes that have hit comparable ecosystems in the last 24 months:

  1. Compromised dependency in Cargo.lock. The 2024 xz-utils incident is the canonical example[8]. A long-term contributor inserts a backdoor; lockfile pins the version; build artifacts ship the backdoor. Our defense: cargo-vet + Mozilla/Google audit sets + manual review of every net-new transitive added to Cargo.lock.
  2. Registry-server compromise. Attacker takes over registry.mcp-manager.dev or its CDN; serves a backdoored trust.toml. Defense: minisign-signed index, root key on hardware token (YubiKey FIPS), key never on a network-reachable host, baked-in pubkey shipped in the binary so a compromised CDN cannot replace it.
  3. Compromised installer.sh CDN. Classic curl | sh failure mode. The user trusts https://mcp-manager.dev/install.sh; attacker has DNS/TLS or CDN access; user pipes attacker script to sh[9]. Defense: the installer downloads the tarball + .minisig, verifies against a pubkey embedded in the installer text (not fetched), and the installer itself ships as a single self-verifying file that the user can shasum against a value published on the release page.
  4. Backdoored MCP server in a registry. Out of scope for v1.0 to fully prevent (we can't audit all third-party MCPs), but in scope to signal trust state clearly: every install shows signature-status (signed-by-publisher, signed-by-registry, unsigned), and unsigned installs require an explicit --allow-unsigned flag[10].
  5. Insider/maintainer compromise. Our own commit signing keys are GPG-protected on YubiKeys; tagged releases require commit-sig verification in CI; releases additionally require co-signing by a second maintainer after v1.0 GA (single maintainer is fine for pre-release).
  6. Build-time tampering. A compromised GitHub Actions runner injects code at build time. Defense: SLSA L3 provenance + reproducible builds. Any third party can rebuild our v1.0.0 tarball with the same toolchain and get a bit-identical artifact; non-reproducibility is itself an alarm[11].

Key concerns about the v1.0 baseline

Three places where I think the spec is too relaxed:

  • The installer pubkey lives in shell. If we embed the minisign pubkey as a constant in install.sh, anyone who can replace install.sh on the CDN can also replace the pubkey. Mitigation: publish the SHA-256 of install.sh on the release page, in the GitHub release body (different storage), in a tweet from a verified account, and in the README. Multiple-witness corroboration is cheap.
  • "verify-when-present" on packages is a footgun. The spec's phrasing implies: if cosign metadata exists, verify; if not, install anyway. That's TOFU at the package level, dressed up. We refine: signature-status is part of the displayed install confirmation; unsigned-by-default-policy can be made registry-wide (per-registry-source require_signatures = true); the default for the three baked-in registries is require_signatures = "publisher-or-registry".
  • No SBOM for the MCP servers we install. v1.0 won't ship MCP-server SBOMs (third parties don't yet provide them at scale), but we should display the field in the install output (SBOM: not available) so users see the absence and demand presence. The asymmetry is fine; the silence isn't.

Arguments

Against nix-purist

The nix-purist wants flakes-as-the-only-distribution. I am sympathetic — flakes give us reproducibility for free, content-addressed packages, and a runtime closure that's audit-friendly[12]. But: forcing nix on every user of mcpm is incompatible with the 10-minute first-launch UX target the v1.0 spec commits to. Nix's install footprint is ~600MB, the daemon is mandatory, and the onboarding flow ("install nix; enable flakes; nix profile install") is a multi-screen prerequisites checklist before the user has typed mcpm once.

What I do take from the purist: reproducible builds are not optional. We don't need nix to get them — we need SOURCE_DATE_EPOCH in CI, --locked on cargo, a pinned rustc, and a sorted-input build graph[13]. The Reproducible Builds project documents the practical recipes for Rust binaries; we follow them. CI runs a "build twice on two different runners, diff the bytes" step on every release tag; non-reproducibility blocks the release.

Where I cede ground: a nix flake as a second distribution channel is correct (the spec already says so). Flakes give nix-using power users an audit-clean install. We commit to maintaining flake.nix at parity, with flake.lock checked into the repo and updated by Renovate via signed commits. See nix-purist's design for the flake details.

Against distro-packager

The distro-packager wants .deb and .rpm with FHS-compliant paths, systemd units in /usr/lib/systemd/user/, man pages under /usr/share/man, and ideally getting into Debian/Fedora main repos. I respect this; distro repos are the gold standard for "verified by someone who is not the upstream" and they bring along their own supply-chain attestation (signed package databases, reproducibility infrastructure, security teams).

But for v1.0 the cost is steep: every distro has a different policy, packaging review takes 6–18 months for first inclusion, and we don't yet have the API stability story to justify it (a mcpm in Ubuntu LTS for 5 years means 5 years of back-compat support we can't yet commit to). We ship .tar.gz + minisig and a .deb/.rpm built from the same artifact, hosted on our own apt/yum repository — signed with the same pubkey set — but we don't pursue inclusion in distro main repos until v1.1.

Where the packager is right: FHS paths matter. /usr/local/bin/mcpm by default; ${XDG_CONFIG_HOME:-$HOME/.config}/mcp-manager/ for config; ${XDG_STATE_HOME:-$HOME/.local/state}/mcpmanagerd/ for state; ${XDG_RUNTIME_DIR}/mcpmanagerd.sock for IPC. The installer script respects $PREFIX. Man pages generated at build time via clap_mangen ship in the tarball. See distro-packager's design.

Against sre-hawk

The sre-hawk wants observability everywhere — Prometheus metrics endpoint, OpenTelemetry traces, structured-log forwarding to Loki/Splunk/Datadog. The instinct is correct for a production service; the scope is wrong for our threat model. We are a per-developer daemon, not a fleet service. The hawk's observability proposals introduce a network egress path (otlp://collector:4317) that becomes itself a supply-chain concern: now the daemon talks to "some collector" the user configured, which is a new attack surface (rogue collector exfiltrates secrets via spans).

Where I push back hard: no telemetry, ever (v1.0 spec, explicit). The audit log on disk + the tracing daemon log + the per-server stdout/err rings are the only sources of truth, and they live on the user's disk only. If a downstream SRE wants to forward them, they can tail -F the JSONL and ship it themselves. The daemon never opens an outbound network connection except (a) for registry index refresh — to a small allowlist of HTTPS URLs in trust.toml — and (b) for installer downloads. Both are signature-verified, both are user-initiated.

Where I cede ground: structured audit-log format must be amenable to off-line ingestion. JSONL with stable schema, a published CycloneDX-style version field, and a documented "audit log format" page in the mdbook. The hawk's argument that "if you have audit logs but no schema, they're useless" is correct. See sre-hawk's design.

Against curl-installer-defender

The curl-installer-defender wants the install path to remain curl … | sh, friction-free, no signature dance for the user. I agree about friction; I disagree about where the friction is hidden. A curl … | sh that doesn't verify anything is an unforgivable starting position for a tool that itself installs other people's code; the optics alone would tank our security credibility on the first HN post.

The defender's reasonable position is: the installer script itself embeds the pubkey, verifies the downloaded binary, and the user sees zero extra steps. That's exactly what we ship. The argument is then whether the user should also verify the installer script's hash before running it. My take: the installer script will publish its hash on the release page (multiple-witness), but we don't require the user to check it in the happy path — we instead make verification trivial for users who care: curl … | sha256sum --check <(curl …sha256sum.txt) is documented under "verifying" in the README.

Where I cede ground: we don't make the user paste a pubkey, don't require GPG, don't introduce a key-management workflow on first install. The pubkey is embedded; verification is silent unless it fails. The defender is right that we lose users at every friction step. See curl-installer-defender's design.

Design

Signing flow — what gets signed by whom

Two layers of signatures, two trust roots, no overlap:

│                                                                       │
│  KR  release-signing  ed25519  YubiKey FIPS  ────── signs ──┐        │

│                                                          │  │        │

│   ├─ if minisign-attested: minisign -V (publisher pubkey from index)  │

└──────────────────────────────────────────────────────────────────────┘

Key management policy (one page, written down, lived)

  • Two root keys, two purposes. Release-signing (KR) signs binary artifacts. Trust-manifest signing (KT) signs trust.toml and per-source registry indexes. Separation of duties: even if KR is compromised, attacker cannot replace the registry index without also compromising KT.
  • Hardware tokens. Both private keys live on YubiKey FIPS 5C NFC tokens. The maintainer (just me at v1.0) holds two physical tokens; the spare is in a bank deposit box. The pubkeys are 32 bytes each, printed on the release page, embedded in the binary, in the installer, and tweeted from @mcp_manager.
  • Rotation policy. Annual rotation by default; emergency rotation on any whiff of compromise. Rotation procedure: generate new keypair on a fresh YubiKey; publish "rotation manifest" signed by both old and new keys (so clients can chain trust); ship a patch release with the new pubkey embedded; revoke old key after 90-day grace period.
  • No key in CI. CI does not have access to KR or KT. Release tagging happens locally on a Mac with the YubiKey inserted; the resulting .minisig files are pushed to the GitHub release manually. CI's role is restricted to building, generating SBOM + provenance, and verifying that the maintainer's signed tag matches the artifact hashes — never producing the signature itself.

SBOM — schema choice and content

CycloneDX 1.5 JSON, generated by cargo-cyclonedx[5]. Why CycloneDX over SPDX:

DimensionCycloneDX 1.5SPDX 2.3
Rust ecosystem toolingcargo-cyclonedx, mature; first-class crates.io supportcargo-sbom exists; lighter ecosystem
Format ergonomicsJSON-first; compactTag-value or JSON; verbose
Vulnerability mappingVEX integration native (cyclonedx-bom-tool)Externalized to SPDX-License-Expression + advisory feeds
Adoption in our threat-model peer-groupSigstore, Docker, Anchore, SnykLinux Foundation reference; NTIA minimum elements

We attach the CycloneDX SBOM to every GitHub release. The SBOM is itself signed by KR; its filename matches the binary it describes (mcp-manager-1.0.0-aarch64-apple-darwin.cdx.json + .minisig). Users running mcpm self check --sbom get a printed table of the daemon's own dependencies, cross-referenced against the embedded SBOM.

Reproducible build flags

The Reproducible Builds project's documentation for Rust binaries gives us the recipe[11]. In .cargo/config.toml: 

# .cargo/config.toml
[build]
# Sort all derived paths for determinism.
rustflags = [
    "--remap-path-prefix", "${HOME}=~",                 # strip home dir
    "--remap-path-prefix", "${CARGO_HOME}=~/.cargo",    # strip cargo cache path
    "--remap-path-prefix", "${PWD}=/build",             # canonical build dir
    "-C", "link-arg=-Wl,--build-id=none",               # strip build-id (Linux ELF)
    "-C", "strip=symbols",                              # strip symbols on release
]

[profile.release]
codegen-units = 1                                       # deterministic codegen
lto           = "fat"                                   # link-time optimisation
panic         = "abort"
strip         = "symbols"
debug         = false

[net]
offline = true                                          # CI passes pre-fetched cache;
                                                        # no surprise network in build

And in the CI workflow:

# .github/workflows/release.yml (excerpt)
env:
  SOURCE_DATE_EPOCH: ${{ github.event.head_commit.timestamp }}
  CARGO_NET_OFFLINE: "true"
  CARGO_INCREMENTAL: "0"
  RUSTC_BOOTSTRAP: "0"

steps:
  - uses: actions/checkout@v4
    with:
      persist-credentials: false
  - name: Pin toolchain
    run: rustup toolchain install 1.86.0 --profile minimal
  - name: Pre-fetch deps
    run: cargo fetch --locked
  - name: Build
    run: cargo build --locked --release --offline
  - name: Verify reproducibility
    run: |
      # Build twice; diff the bytes.
      cp target/release/mcpmanagerd /tmp/first
      cargo clean
      cargo build --locked --release --offline
      diff /tmp/first target/release/mcpmanagerd  # exit 0 expected
  - name: Generate SBOM
    run: cargo cyclonedx --format json --output-pattern flat
  - name: SLSA provenance
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
    with:
      base64-subjects: ${{ steps.hash.outputs.hashes }}

SOURCE_DATE_EPOCH is honored by cargo for timestamping (e.g. archives), by rustc's internal debuginfo, and by the GNU/clang toolchains we link against[13]. The build-twice step is our canary: if the diff is non-empty, the release is blocked and a human investigates. In practice the non-reproducibility tail in Rust is small (llvm hash-table iteration order is the usual suspect); pinning codegen-units = 1 kills most of it.

cargo-vet trust set

cargo-vet[7] tracks human review of every transitive crate in Cargo.lock. We don't review all ~600 transitives from scratch; we import audits from organisations whose review processes we trust: 

# supply-chain/config.toml
[cargo-vet]
version = "0.10"

[imports.mozilla]
url = "https://raw.githubusercontent.com/mozilla/supply-chain/master/audits.toml"

[imports.google]
url = "https://raw.githubusercontent.com/google/supply-chain/main/audits.toml"

[imports.bytecode-alliance]
url = "https://raw.githubusercontent.com/bytecodealliance/wasmtime/main/supply-chain/audits.toml"

[imports.embark]
url = "https://raw.githubusercontent.com/EmbarkStudios/rust-ecosystem/main/audits.toml"

[imports.zcash]
url = "https://raw.githubusercontent.com/zcash/rust-ecosystem/main/audits.toml"

[policy.default]
audit-as-crates-io = true
criteria           = ["safe-to-deploy"]

[policy."mcpm-protocol"]
# Public crate; require an extra criterion.
criteria = ["safe-to-deploy", "crypto-safe"]

Roughly 90% of transitive crates are covered by imports. The remaining ~50 require a human audit (us); we record audits in supply-chain/audits.toml and re-vet on every cargo update. CI fails if cargo vet reports an unaudited delta — this is the strict gate that prevents the xz-style "long-time maintainer adds a backdoor in version N+1" attack: the diff between N and N+1 is unvetted by definition until we explicitly review it.

cargo-audit + automated CVE feed

cargo-audit[15] runs on every PR and daily on the main branch. The daily run files a GitHub issue on any new RUSTSEC advisory affecting Cargo.lock, tagged security, auto-assigned. If the advisory's severity is High or Critical, a release is cut within 7 days.

The install.sh in detail

The installer script does three things, in this order:

#!/usr/bin/env bash
# install.sh — mcp-manager.dev/install.sh
# SHA-256 of this file is published on the release page, in the GitHub release
# body, and tweeted from @mcp_manager. Multiple-witness corroboration.
set -euo pipefail

# 1. Embedded minisign pubkey (KR). Bytes baked into the script itself,
#    not fetched from network. If install.sh is tampered with, the user's
#    second-witness check (sha256sum) catches it.
PUBKEY="RWQf6LRCGA9i5+vP3LkVa3sFi6m6xn2K/UfdkqYZsLW3W7sxKqaP4yGv"
VERSION="${MCPM_VERSION:-1.0.0}"
PREFIX="${PREFIX:-/usr/local}"

# 2. Detect platform.
case "$(uname -s)-$(uname -m)" in
  Darwin-arm64)  PLAT="aarch64-apple-darwin" ;;
  Darwin-x86_64) PLAT="x86_64-apple-darwin" ;;
  Linux-aarch64) PLAT="aarch64-unknown-linux-gnu" ;;
  Linux-x86_64)  PLAT="x86_64-unknown-linux-gnu" ;;
  *) echo "unsupported platform: $(uname -s) $(uname -m)"; exit 1 ;;
esac

# 3. Download artifact + signature; verify; install.
TMPDIR="$(mktemp -d)"
trap 'rm -rf "$TMPDIR"' EXIT

base="https://github.com/user/mcp-manager/releases/download/v${VERSION}"
TARBALL="mcp-manager-${VERSION}-${PLAT}.tar.gz"

curl -fsSL "${base}/${TARBALL}"          -o "${TMPDIR}/${TARBALL}"
curl -fsSL "${base}/${TARBALL}.minisig"  -o "${TMPDIR}/${TARBALL}.minisig"

# Use the bundled minisign-verify if not installed; vendored in the tarball
# of the previous version. Bootstrap problem solved by first installing
# minisign via the OS package manager OR shipping a vendored static binary.
if ! command -v minisign >/dev/null; then
  echo "installing minisign first..."
  if [ "$(uname -s)" = "Darwin" ]; then brew install minisign
  elif command -v apt-get >/dev/null;  then sudo apt-get install -y minisign
  elif command -v dnf >/dev/null;      then sudo dnf install -y minisign
  else echo "minisign not found; install it from https://jedisct1.github.io/minisign/"; exit 1
  fi
fi

minisign -V -P "${PUBKEY}" -m "${TMPDIR}/${TARBALL}"  \
  >/dev/null || { echo "FATAL: signature verification failed"; exit 2; }

tar -xzf "${TMPDIR}/${TARBALL}" -C "${TMPDIR}"
install -m 0755 "${TMPDIR}/mcp-manager-${VERSION}-${PLAT}/mcpm"           "${PREFIX}/bin/mcpm"
install -m 0755 "${TMPDIR}/mcp-manager-${VERSION}-${PLAT}/mcpmanagerd"    "${PREFIX}/bin/mcpmanagerd"

echo "mcpm installed to ${PREFIX}/bin"
echo "next: mcpm init"

Three subtle hardenings: set -euo pipefail upfront (cheap, catches the classic curl-pipe-bash race where a truncated download still executes); trap … EXIT for tempdir cleanup; install -m 0755 instead of cp so we never leave a partial-write executable in $PATH.

The auto-spawn question: do we verify the daemon binary on every spawn?

No. The daemon binary's signature is verified at install time and at update time, full stop. Verifying on every spawn would add 50–200ms to mcpm exec latency (we'd need to mmap + ed25519-verify a 15MB binary), which blows our 50ms p99 budget. The trust boundary is: if /usr/local/bin/mcpmanagerd has been tampered with, an attacker already has root (or write access to /usr/local/bin), which means the game is over independently of mcpm.

We do, however, verify installed MCP server packages on every install and on every update — those are the third-party artifacts. The daemon's own integrity falls under "the user's OS integrity," which is out of scope.

Update mechanism — signature at every step

v1.0 does not ship a self-updater. Users re-run the installer for a new version. v1.1's mcpm self update will:

  1. Fetch the latest version manifest from trust.mcp-manager.dev/v1/releases.json (signed by KT).
  2. If newer than current, fetch the appropriate tarball + .minisig (signed by KR).
  3. Verify against the daemon's baked-in pubkey for KR.
  4. Atomic swap: write to /usr/local/bin/mcpmanagerd.new, rename over the old binary, send SIGHUP to the running daemon (it re-execs itself).
  5. Audit-log self.update { from: "1.0.0", to: "1.1.0", sig_verified: true, sbom_hash: "..." }.

mdbook docs hosting — security advisories section

The mdbook published to https://docs.mcp-manager.dev/ hosts the user-facing docs and one critical security section:

  • /security/ — SECURITY.md as an MD page in mdbook
  • /security/advisories/ — every advisory we've ever published, indexed by MCPM-YYYY-NNN with CVE cross-references
  • /security/pubkeys/ — current and historical signing pubkeys (multiple-witness)
  • /security/sbom/ — link to the SBOM for every release
  • /security/slsa/ — the SLSA provenance for every release, with one-paragraph human explanation
  • /security/reporting/ — security@mcp-manager.dev + ASCII-armored PGP key for reports + a TLS-terminated form for users without PGP

mdbook itself is built in CI from the source repo; the GitHub Pages deployment is signed via a GitHub Actions OIDC token. We embed the SHA-256 of the deployed site root in the daemon binary so mcpm docs verify can confirm the docs the user is reading match the docs we published. (Diminishing return; documented but not blocking.)

Service-string namespace decision

The OS keychain service strings carry trust implications: dev.mcp-manager.mcpmanagerd is what mcpmanagerd uses; if some other process steals this string, it can read mcpmanagerd's secrets via SecItemCopyMatching (macOS) / secret_password_lookup_sync (Linux libsecret). Mitigation:

  • macOS: the keychain ACL is set so only the binary signed with our Apple Developer ID can read entries under this service string. Apple's keychain ACL enforces this against the calling binary's signature.
  • Linux libsecret: libsecret has no per-process ACL; mitigation is filesystem permissions on $XDG_RUNTIME_DIR/keyring-... and the secret-tool / libsecret being authenticated by D-Bus session ownership (same UID).
  • Domain namespace: we own mcp-manager.dev; reverse-DNS as service prefix is unambiguous. Any future fork or rename gets its own prefix.

mcpm uninstall — leave no trust state behind

Uninstall is a security operation, not just a file-deletion: leftover trust roots and orphan pubkeys are the supply-chain equivalent of a forgotten authorized_keys entry. The complete teardown:

  1. Stop and disable the service-manager unit (launchctl unload / systemctl --user disable).
  2. Remove the daemon binary, the CLI binary, the man pages, the shell completion files.
  3. Remove ~/.config/mcp-manager/ entirely (with --keep-config opt-out for power users).
  4. Remove $XDG_STATE_HOME/mcpmanagerd/ (logs + audit + cached trust state).
  5. Remove keychain entries by namespace prefix. We enumerate every dev.mcp-manager.mcpmanagerd/* entry and delete each; we do not blanket-delete all entries in case the user has unrelated secrets there. Confirmation prompt lists each entry by name.
  6. Unproject every projection — managed-block sync writes an empty managed region to every editor config we previously touched (the projection lockfile gives us the exact list).
  7. Remove the projection lockfile after the unprojection completes.
  8. Print a list of what was removed; print a final reminder: "Your installed MCP servers' own data (e.g., the github-mcp's cache directory) was not removed; manage those separately." Some MCPs may have their own secrets/keychain entries under separate service strings — out of our scope to touch.

Audit-log uninstall.start and uninstall.complete (the latter is the last entry written; the audit log file itself is the second-to-last thing deleted; the parent state dir is removed last). Forensic trail preserved up to the moment of teardown.

What I explicitly will NOT do

  • No GPG. Minisign is strictly better at our scope. GPG's web-of-trust is irrelevant for a single-organisation publisher; key ring management is a UX disaster.
  • No X.509 / PKI for our own keys. ed25519 pubkeys are 32 bytes; we don't need a CA hierarchy. Sigstore uses Fulcio for its own reasons; we use it only on the verification side, not the publication side.
  • No self-hosted CA / TUF root ceremony with multiple keyholders at v1.0. Single maintainer, single hardware token, documented rotation plan. Multi-keyholder ceremony comes when we have multiple maintainers; doing it earlier would be theatre.
  • No cargo install as a documented path. cargo install mcp-manager from crates.io has weak signing guarantees; we won't recommend it. Users who do it anyway get a build from source; we'll publish to crates.io but not promote it.
  • No package-manager auto-update via system updaters in v1.0. No apt repo with unattended-upgrades enabled; we don't want users to get a security update they didn't read. Update is opt-in.
  • No spawn-time daemon-binary verification. See above; explicitly off the table for performance reasons.

Cross-references to other facets

The IPC trust boundary (SO_PEERCRED + 0600 socket perms) belongs to security facet; we depend on it but don't own it. The first-run trust-bootstrap flow (offline → baked-in pubkeys) is a UX-facet concern in its messaging — the warning text, the mcpm trust refresh prompt — and a supply-chain concern in its fail-soft logic. Reproducibility verification belongs to nix-purist's design as well: their flake gives us a parallel reproducibility check we can run on every release tag.

Summary in one sentence

Two ed25519 root keys on hardware tokens; minisign signs everything that ships; CycloneDX SBOM and SLSA L3 provenance attached to every release; cargo-vet + cargo-deny + cargo-audit form a per-PR gauntlet; reproducible builds with SOURCE_DATE_EPOCH are non-negotiable; uninstall is a security operation that tears down keychain namespaces and projection state without leaving orphans.
