Thoughts

The 3am test

The way I evaluate any operational design is the 3am test: someone is paged because their workflow broke; the only context they have is a log file, a state file, and a tired brain. Can they fix it without me? For MCP Manager that means: the daemon is logging, the audit log is intact, and a single subcommand (mcpm doctor) enumerates every plausible thing that could be wrong. There is no "phone home" — there is no Anthropic, no vendor backend, no Sentry — because the v1.0 spec locked no telemetry[1]. Fine. That means the local artifacts (logs, audit, doctor output, runbook) carry all of the diagnostic weight that a vendor SaaS would normally absorb. They have to be excellent.

The v1.0 spec is already in good shape on the bones: three log streams (daemon / per-server / audit), append-only audit JSONL, ring buffers, a streaming logs.tail RPC[2]. What the spec doesn't quite say yet — and where I want to push hard:

  1. Every daemon log line must be JSON (one object per line), with a stable schema. Not "structured-ish via tracing's default format" — JSON, always, in production. Charity Majors and Honeycomb have been preaching this for a decade: high-cardinality structured events beat free-form text by orders of magnitude when you are reasoning about failure modes[3]. Cindy Sridharan's writing makes the same point from the SRE side — observability is not "metrics + tracing + logs", it is "the ability to ask new questions of your system without re-deploying"[4]. At 3am, the only way to ask new questions is to jq over JSON.
  2. The audit log is the source of truth for "what did mcpmanagerd actually do?" It needs sequence numbers (so a missing line is detectable), a hash chain (so tampering is detectable), and append-only file semantics (so a crash mid-write doesn't corrupt the previous lines). This is the same shape as Linux auditd's journal[5] or the Chronicle / Sigstore Rekor transparency log[6], just scoped to a single user's machine.
  3. mcpm doctor exists from day one. Every Unix tool that I trust at 3am has a "tell me what's wrong" subcommand: brew doctor, git fsck, kubectl get events, systemctl status --all, docker system info. The v1.0 spec doesn't list doctor in its CLI surface[2] and that's the one omission that genuinely makes me nervous. We add it.
  4. Log rotation must never lose bytes. The naive pattern — logger > log.txt + cron mv log.txt log.1 — drops in-flight writes between the rename and the next reopen on many systems. Real rotation is "rename, signal the writer to reopen, and copy out-of-band"[7]. Tail readers (the TUI's logs.tail stream) have to cope with the rename atomically. This is solvable but it needs explicit design.

Why journald-compatible matters, but is not required

On Linux with systemd, mcpmanagerd registered as a systemd --user unit will have its stdout/stderr piped into the journal by default[8]. If we emit JSON-per-line on stdout, journalctl --user-unit mcpmanagerd --output=json Just Works. That's a huge ergonomic win for our Linux users: they don't have to know where our log files live; they already know journalctl. On macOS, the same pattern works for launchd (StandardOutPath + StandardErrorPath in the plist), though there's no equivalent indexed query — they get a file. So our design constraint is: emit JSON-per-line on stdout to be friendly to journald, AND also tee to our own files (because journald isn't universal and per-server log isolation matters). Belt and braces.

What the locked "no telemetry" decision actually costs us

I have nothing against the no-telemetry stance — it's the right call for a tool that handles secrets and runs on developer machines[9]. But I want to name what it costs, so we can design around it:

  • We don't know our error rates in the field. If 30% of users hit a registry-refresh failure tomorrow, we won't see it until they email us. Mitigation: mcpm doctor --share produces a redacted bundle the user can paste into a GitHub issue, with a documented schema in the runbook. We push users to be the telemetry channel, opt-in per-incident.
  • We can't proactively detect a CVE-impact wave. If rmcp ships a CVE and 8% of users are on a pinned-old version, we don't know which ones. Mitigation: documented mcpm doctor output that prints the version + a "compare against the latest at..." URL the user can hit themselves.
  • Our supportability is bounded by the quality of our local artifacts. This is the through-line of everything below. If mcpm doctor + the runbook can't talk a user through a problem, we have no fallback.

Where I diverge from the other four agents

nix-purist wants everything reproducible — flakes, devenv, hermetic. I love it for the build but I will fight hard against making any operational tool depend on a flake. The doctor has to work on a machine where the user might have broken their nix setup. distro-packager wants deb/rpm/FHS — yes, I want this too for ops sanity, but only as a second install channel after the curl-installer (because most v1.0 users will not be on a distro that has us packaged yet). supply-chain-sec wants signed everything — I want this too and I want the SBOM signed and reproducibly built. curl-installer-defender wants frictionless install — I agree the curl-installer is the right primary channel, but only if it leaves behind a doctor-checkable artifact (an installation receipt) so we can detect "this binary was installed by the curl-installer at version X, signed by minisign key Y, on date Z". The curl-installer's output is what I care about; the input is fine.

Arguments

Against nix-purist

I respect the nix-purist's instinct: a flake locks every input, hermetic builds give us reproducibility, devenv gives us a clean dev shell, and the supply chain becomes a graph rather than a wish. For the build side, I'm with you. Where I push back is the operational side. Imagine the 3am scenario: a user's MCP server stopped working. They run mcpm doctor. The doctor needs to read its own config, hit the keychain, list installed servers, parse the audit log — fast — and tell the user what's wrong. The doctor must not depend on a working nix store. If the user has a broken nix profile or their flake registry is unreachable, the diagnostic tool that exists to fix problems can itself be the problem. So: yes to nix for build + reproducible CI; no to nix as a runtime dependency of operational tooling.

Concrete ask of nix-purist's design: the binary mcpmanagerd we ship must be a fully-statically-linked-or-rpath-OK ELF/Mach-O, runnable on a stock macOS / stock Ubuntu / stock Fedora without any nix in PATH. The flake is an alternative install channel for users who want reproducibility — not the only channel, and not a runtime dep. If your design accommodates that, we're aligned.

Where I cede ground: I want the build to be flake-able for CI, because a reproducible build is the only honest way to claim a meaningful SBOM[10]. How we build doesn't have to constrain where we run.

Against distro-packager

The distro-packager wants FHS layout, deb/rpm, proper systemd units shipped by the distro. I'm 80% in agreement — this is the right path for the second year of MCP Manager, when Debian / Fedora / Arch volunteers start packaging us. But for v1.0 I want to push back on three specifics.

One: don't put logs in /var/log/mcpmanagerd/ for a user-mode daemon. The daemon is per-user (single-user SO_PEERCRED auth, by the v1.0 spec[2]). /var/log is system-mode by convention[11]. The right home is $XDG_STATE_HOME/mcpmanagerd/logs/ (default ~/.local/state/mcpmanagerd/logs/), per the XDG Base Directory spec[12]. The v1.0 spec already uses XDG; let's keep doing that. A future v1.x system-mode daemon (multi-user) would justify /var/log; v1.0 is per-user.

Two: the systemd unit should be a --user unit, not a system unit. The packager's instinct to ship a system unit means root-owned mcpmanagerd or per-user-instance complications. systemctl --user enable mcpmanagerd with the unit file at /usr/lib/systemd/user/mcpmanagerd.service is the right shape[13]. StandardOutput=journal + StandardError=journal; logs route to the per-user journal; journalctl --user-unit mcpmanagerd --output=json gives the operator a queryable stream for free. This is exactly the win I want from JSON-per-line logging.

Three: the .deb/.rpm postinstall scripts must be idempotent and survive a botched install. If postinstall fails halfway, the package manager must be able to retry. The audit log entries for install.start / install.complete from the daemon are different from the OS package-manager's view of "is the binary installed?" — both views need to be correct independently. (And honestly, this is why the curl-installer is friendlier for v1.0: one tarball, one minisign signature, one extract. The deb/rpm path is for distro-natives who already know how to recover, but it adds combinatorial test surface we shouldn't pay yet.)

Where I cede ground: I want man pages, a proper FHS-respecting layout for system files (binaries in /usr/local/bin; user state in XDG), and a documented systemd-user unit file shipped in the tarball. The distro-packager's discipline is exactly what makes the runbook readable a year from now.

Against supply-chain-sec

We agree on more than we disagree. Sign the binaries (minisign for Linux, Apple notarization + Developer ID for macOS). Sign the registry indexes. Verify-when-present on packages. Generate and sign an SBOM[14]. Where I want a sharper line is at the operational end: signatures are pre-incident artifacts, but the SRE cares about post-incident verifiability. Two specific asks:

One: the audit log itself should be hash-chained. Every line includes seq (monotonic per-day) and prev_hash (sha256 of the previous line, base64). If anything tampers with the log, the chain breaks; if anything was dropped (e.g. a write happened during a power loss), the seq numbers gap. This is the Linux auditd approach[5] simplified for our scale: we don't need a kernel-side audit ring, but we do need the SRE-grade "did the log lie to me?" check. This works because we're append-only[2]. mcpm doctor verifies the chain on demand.

Two: SBOM verification has to be doable by the user, not just by us. Sign the SBOM with the same minisign key we sign the tarball with. Publish the public key fingerprint in the README and on every release page. mcpm doctor prints the binary's SBOM hash + the public-key fingerprint it was verified against. The user can pin both in their threat model.

Where I cede ground on supply-chain-sec: their instinct to insist on Sigstore-everywhere is correct in spirit but premature in v1.0 — sigstore's keyless flow requires a working OIDC at sign time[15], which is fine for our CI but not something we should require for users of the registry. minisign for our own signing (zero infra, one keypair) + cosign-verify-when-present for OCI registry sources is the right v1.0 shape.

Against curl-installer-defender

The curl-installer-defender is right that curl … | sh is the most frictionless install path, and right that the friction in alternative paths (homebrew formula approval, distro packaging cycles, MS Store) is real and the dominant install channel for a v1.0 dev tool is the one-liner. I'm not arguing against that. What I want is an operational receipt: after install, on disk, there's a file like ~/.local/state/mcpmanagerd/install-receipt.json that records:

  • install channel ("curl" | "nix" | "deb" | "rpm" | "manual"),
  • tarball URL + sha256 + minisign verifying key fingerprint + signature-verification timestamp,
  • binary location + sha256 at install time,
  • installer version + git-sha,
  • signature of the receipt itself (HMAC over the above using a per-install random key, so the file isn't trivially editable without us noticing — though a sophisticated attacker can always swap the whole thing; this is anti-mistake, not anti-attacker).

mcpm doctor reads the receipt and verifies the binary on disk still matches the recorded sha256. If a user is on a machine where someone (themselves, last quarter) overwrote /usr/local/bin/mcpmanagerd with a debug build, doctor flags it.

Second ask: the curl-installer prints, on success, the exact journalctl / log show command they should bookmark, and the path to the audit log. This is the single highest-leverage thing the installer can do for future debuggability — make sure the user knows where to look before they need to.

Where I cede ground: the curl-installer's friction-minimisation is in fact the right primary path, and I don't want to gate it on signing them up for an account, sending telemetry, or any other friction-add. The receipt is purely a local artifact.

Design

JSON log schema (daemon stream)

Every line on the daemon's log stream (whether to stdout/journald or to logs/daemon-YYYY-MM-DD.jsonl) is a single JSON object, one per line, never spanning newlines. tracing-subscriber with the json formatter does this for free[16]. The schema: 

{
  "ts":        "2026-05-27T19:15:02.413913Z",     // RFC3339 UTC, microsecond precision
  "level":     "INFO" | "WARN" | "ERROR" | "DEBUG" | "TRACE",
  "target":    "mcpm_supervisor::child",          // module path; matches tracing's `target`
  "event":     "server.spawn"                     // controlled vocabulary; see below
              | "server.exit"
              | "server.oom"
              | "server.restart"
              | "rpc.call"
              | "rpc.error"
              | "config.reload"
              | "registry.refresh"
              | "trust.refresh"
              | "doctor.run"
              | "log.rotate"
              | "secret.read"            // never logs values, only names
              | "auth.failed",
  "outcome":   "ok" | "error" | "denied" | "miss" | "lagged" | null,
  "server":    "github-mcp" | null,               // server name when relevant
  "client_id": "claude-code/1.2.3" | "cli" | "tui" | null,
  "pid":       84219,                             // mcpmanagerd's pid
  "child_pid": 84992,                             // child server's pid when relevant
  "req_id":    "req_01HF9XYZ...",                 // correlation id across the request
  "span":      "rpc.server.start",                // current tracing span name
  "msg":       "spawned github-mcp under devenv profile",
  "fields":    {                                  // event-specific payload
    "isolation": "devenv",
    "duration_ms": 87,
    "exit_code": null
  },
  "err":       null                               // structured error object on level=ERROR
}

Fixed-vocabulary event is the load-bearing design choice. Free-text searches over logs scale to about 100 servers before they collapse; structured event names scale to a million. The vocabulary is enumerated, versioned (v field at file header), and reviewed at every release.

Where the lines go. The daemon writes to both stdout (so journald/launchd capture it) AND ~/.local/state/mcpmanagerd/logs/daemon-YYYY-MM-DD.jsonl with daily rotation. Belt and braces; the file is the canonical replay artifact, journald is the queryable index for Linux users.

Audit JSONL with hash chain

The audit log is structurally similar to the daemon log but with stricter guarantees: append-only, sequence-numbered, hash-chained. One file per day under ~/.local/state/mcpmanagerd/audit/YYYY-MM-DD.jsonl. The shape: 

{
  "v":         1,                                // schema version
  "seq":       4129,                             // monotonic per-day; resets to 0 at file open
  "ts":        "2026-05-27T19:15:02.413913Z",
  "actor":     { "kind": "cli"|"tui"|"editor"|"daemon-internal",
                 "id":   "zed/0.150.3",
                 "pid":  84219,
                 "uid":  501 },
  "event":     "server.spawn" | "server.crash" | "server.oom"
              | "secret.read" | "secret.write" | "secret.delete"
              | "config.change" | "projection.write"
              | "service.register" | "service.unregister"
              | "project.trust" | "auth.failed"
              | "registry.refresh" | "registry.add" | "registry.remove"
              | "install.start" | "install.complete" | "install.fail"
              | "update.start"  | "update.complete"  | "update.fail"
              | "doctor.run"    | "uninstall",
  "server":    "github-mcp" | null,
  "outcome":   "ok" | "denied" | "backend-error" | "miss",
  "details":   { ... event-specific },
  "prev_hash": "sha256:9f4e2d8c...",             // sha256 of previous line's canonical-JSON
                                                 //   (or "GENESIS" for seq=0)
  "line_hash": "sha256:6a1b3f0e..."              // sha256 of this line's canonical-JSON
                                                 //   excluding the line_hash field itself
}

Why both seq and prev_hash? The seq number detects gaps (a missing line in the middle: seq jumps from 50 to 52). The prev_hash detects tampering (someone edited line 17 in place: line 18's prev_hash no longer matches). Together, they detect both append-then-truncate attacks and in-place rewrites. Linux's auditd uses a similar approach[5]; Sigstore's Rekor uses a Merkle tree[6] for the same property at scale. A daily hash chain is the right scale for one developer's daemon.

Day-boundary handling. When the local clock crosses midnight UTC, the daemon closes the current day's file (fsync), opens the next day's file with seq=0 and prev_hash="GENESIS", and writes a final line to the previous day's file: {"event":"audit.day-close","seq":N,"line_hash":"...","total_lines":N+1,"sha256_file":"..."}. The opening line of the new day references the previous file's closing line_hash in its prev_hash (cross-file chain), so the chain spans days, not just within them.

Verifier. mcpm doctor runs the chain verifier as part of its checks; mcpm audit verify is a dedicated subcommand. Verifier output names the first broken line by seq + offset.

Lossless log rotation

Naive rotation loses bytes when a writer doesn't reopen its FD on rename. The right pattern is the logrotate(8) + copytruncate dance, or — better, since we control the writer — rename + signal-driven reopen[7]:

  1. The writer (mcpmanagerd's mcpm-logs crate) holds an FD on daemon.jsonl.
  2. The rotator (a tokio task on a daily timer, or triggered by file-size threshold) calls rename("daemon.jsonl", "daemon-YYYY-MM-DD.jsonl"). The writer's open FD still points to the old inode; writes continue to land in the renamed file.
  3. The rotator sends an internal RotateSignal to the writer over a tokio channel. The writer opens a fresh daemon.jsonl and swaps FDs atomically. No bytes between rename and reopen are lost — they went to the renamed file.
  4. The tailer (the logs.tail RPC subscriber) gets a structured {"event":"log.rotate","old_path":"...","new_path":"...","new_inode":...} notification in its stream so a TUI can re-open the new file if it wants to follow on disk.

Per-server logs (one file per managed MCP server, under logs/<server>/) follow the same pattern. Rotation is size-based (default 16MB) or daily, whichever comes first. Old logs are gzipped after rotation, retained for log_retention_days (default 14), then deleted.

Health endpoints (Unix-socket only)

Two new RPC methods on the UDS-only socket, called by mcpm doctor and mcpm status: 

// Daemon-level health
daemon.status            -> {
  ok:              true,
  uptime_secs:     33120,
  socket_path:     "/run/user/501/mcpmanagerd.sock",
  active_servers:  6,
  failed_servers:  1,
  audit_seq:       4129,
  audit_chain_ok:  false,                  // recomputed lazily; cached
  last_chain_ok_at:"2026-05-27T15:00:00Z",
  config_hash:     "sha256:...",
  config_loaded:   "2026-05-25T...",
  warnings:        ["projection.drift: cursor", "audit.chain.break: 2026-05-27 seq=4129"]
}

// Per-server health, EXPLAINS failure modes
server.<name>.status     -> {
  name:                "notion-mcp",
  state:               "running"|"restarting"|"failed"|"stopped"|"spawning",
  pid:                 84992,             // null if not running
  client_refcount:     2,
  uptime_secs:         8730,
  last_health_check:   { ts: "...", ok: true, latency_ms: 14 },
  restart_attempts:    { window_start: "...", count: 3, max: 5 },
  memory:              { current_mb: 87, peak_mb: 248, limit_mb: 256 },
  isolation:           "devenv",
  last_exit:           null,              // populated when in failed/stopped
  last_5_log_lines:    [ ... ],
  warnings:            []
}

Note the explanation orientation: last_5_log_lines is embedded directly in the health response so the caller doesn't have to make a second RPC. warnings is an array of human-readable strings keyed off the same controlled-vocabulary events used in the log schema. SREs reading this output get the "why" not just the "down".

journald / launchd integration

The systemd-user unit (/usr/lib/systemd/user/mcpmanagerd.service when packaged; ~/.config/systemd/user/mcpmanagerd.service when the curl-installer drops it): 

[Unit]
Description=MCP Manager daemon
Documentation=https://docs.mcp-manager.dev/runbook
After=default.target

[Service]
Type=notify
ExecStart=/usr/local/bin/mcpmanagerd
Restart=on-failure
RestartSec=2s

# Logs route through journald; we emit one JSON object per stdout line.
StandardOutput=journal
StandardError=journal
SyslogIdentifier=mcpmanagerd

# Resource hygiene
MemoryHigh=200M
MemoryMax=512M
TasksMax=200

# Filesystem hardening (where applicable for a user daemon)
ProtectHome=read-only
ProtectSystem=strict
ReadWritePaths=%h/.config/mcp-manager %h/.local/state/mcpmanagerd

[Install]
WantedBy=default.target

Type=notify means mcpmanagerd calls sd_notify(READY=1) when the UDS is bound and listening[13]. journalctl --user-unit mcpmanagerd --output=json gives operators a structured-log query for free.

On macOS, the launchd plist at ~/Library/LaunchAgents/dev.mcp-manager.mcpmanagerd.plist mirrors the same: RunAtLoad, KeepAlive with SuccessfulExit, StandardOutPath and StandardErrorPath pointing at our log files (no journald equivalent). EnvironmentVariables sets XDG_STATE_HOME if not already set, so paths are consistent with the Linux side.

Auto-spawn race + lockfile

The v1.0 spec's auto-spawn behavior[2] notes that flock(2) prevents two parallel mcpm invocations from racing to spawn two daemons. From an SRE angle, I want a sharper picture of what happens when the race does hit the lock:

  1. Both mcpm clients try to connect to the socket, both fail with ENOENT.
  2. Both try to flock(2) ~/.local/state/mcpmanagerd/spawn.lock exclusively.
  3. Whichever wins forks+execs mcpmanagerd. The loser blocks on the flock with a 5-second timeout.
  4. The winning daemon binds the socket, calls sd_notify(READY=1) (or writes spawn.lock.ready marker on non-systemd hosts), and releases the flock.
  5. The losing mcpm wakes, sees the ready marker, retries connecting, succeeds.
  6. If the winning daemon failed to bind within 5s (port-already-in-use, permission error), the loser releases the flock, logs {"event":"daemon.spawn.race.timeout"}, and surfaces an actionable error: "another process tried to start mcpmanagerd but didn't become ready in time. Check journalctl --user-unit mcpmanagerd."

Crash-during-spawn recovery. If the winning daemon crashes after binding but before serving a request, the socket file remains on disk (the kernel doesn't auto-clean UDS files on process exit). The next mcpm client gets ECONNREFUSED rather than ENOENT. The auto-spawn logic must handle both: treat ECONNREFUSED the same as ENOENT for purposes of spawning, but log a higher-severity event {"event":"daemon.spawn.stale-socket","outcome":"ok"} so we can audit how often this happens. mcpm doctor reports stale-socket-recovery counts in the last 7 days.

Rolling daemon update

v1.0 spec says we don't ship a self-updater[2], but the user-driven re-curl path still has a hot question: what happens to the running mcpmanagerd when the binary on disk is replaced? Options:

  • Option A (chosen): the installer doesn't stop the daemon. It atomically replaces the binary via rename(2) (so any process with the file open continues running the old image). It then prints: "mcpmanagerd is running an older version; restart with mcpm daemon restart when convenient. Active MCP servers will be re-spawned on restart." This is the same shape as `apt-get upgrade` + needs-restart.
  • Option B (rejected): the installer stops the daemon, replaces, restarts. Rejected because it forces an interruption to every editor's MCP session at install time — and the user may have just been demoing to a customer.

On mcpm daemon restart, the daemon goes through a graceful shutdown:

  1. Stop accepting new RPC connections; daemon.status reports state: "draining".
  2. Notify every logs.tail subscriber with {"event":"daemon.shutdown.imminent","grace_secs":10} so TUIs can show a banner.
  3. For each managed MCP server: send SIGTERM, wait up to shutdown_grace_secs (default 5s), then SIGKILL.
  4. Audit log: {"event":"daemon.shutdown","outcome":"ok","servers_stopped":N}.
  5. fsync the audit log file. Close FDs. Exit 0.
  6. systemd-user / launchd restarts the daemon. New process picks up the new binary. Reads canonical config. Re-spawns servers marked autostart = true. Audit: {"event":"daemon.boot","version":"1.0.1","prev_version":"1.0.0"}.

A future v1.1 feature would be a true zero-downtime hand-off via SCM_RIGHTS-passing of child stdio FDs between old and new daemon processes (the systemd socket-activation trick[8]). Out of scope for v1.0.

mcpm uninstall correctness

A subcommand the v1.0 CLI list includes[2] but doesn't specify the semantics of. My take: uninstall does the obvious thing, asks before deleting anything irreversible, and leaves an audit trail. 

$ mcpm uninstall
this will:
  - stop mcpmanagerd (currently running, pid 84219)
  - unregister the systemd-user unit
  - remove the binary at /usr/local/bin/mcpmanagerd and /usr/local/bin/mcpm
  - keep these (default; pass --purge to remove):
      ~/.config/mcp-manager/                  (your config + lockfile)
      ~/.local/state/mcpmanagerd/audit/       (audit history)
      ~/.local/state/mcpmanagerd/logs/        (daemon + per-server logs)
      OS keychain entries (12 secrets)        (only `mcpm secret unset` removes these)
  - DOES NOT touch the per-editor projections in:
      ~/.cursor/mcp.json (will keep the static MCP entries we projected)
      ~/.config/Claude/claude_desktop_config.json
      ...
    To remove these, run `mcpm projection unsync --all` BEFORE uninstall.

confirm? [y/N]

Logs are retained by default. Rationale: if uninstall is happening because of a problem, the user (or the support thread) may want to look at the audit log a week later. --purge removes everything including keychain entries (with a separate y/N prompt for that, since secrets cannot be recovered).

Last act of the uninstall is to write a final audit line: {"event":"uninstall","outcome":"ok","purge":false,"audit_kept":true,"logs_kept":true}, fsync, then drop the binary. The audit file now ends with a clear marker.

What happens to mcpm exec shims in editor configs? If mcpm is uninstalled while a projection points at it, the next time the editor spawns the MCP, it'll fail with "command not found". The uninstall preamble explicitly warns about this and points the user at mcpm projection unsync --all as the first step. (We can't run unsync automatically because some users will reinstall in 30 minutes and want the projections preserved.)

Runbook outline (mdbook section)

The mdbook at docs/ needs a Runbook section, not just an installation guide. The chapter shape: 

Runbook
├── Daily operations
│   ├── Where are the logs?
│   ├── How to read the audit log
│   ├── `mcpm doctor` interpretation
│   └── `mcpm status` cheatsheet
├── Common failures
│   ├── "Daemon won't start"
│   │   - check journald / launchd
│   │   - socket already in use → mcpm doctor will say
│   │   - permission denied on socket dir → fix XDG_RUNTIME_DIR
│   ├── "MCP server keeps restarting"
│   │   - check `mcpm doctor` for OOM signal
│   │   - check the server's per-server log for the panic
│   │   - increase memory_max_mb if appropriate
│   ├── "Secret not found"
│   │   - keychain locked? (macOS Touch ID, gnome-keyring not unlocked)
│   │   - secret name typo: `mcpm secret list`
│   ├── "Projection drift"
│   │   - someone edited an editor config outside mcpm
│   │   - `mcpm projection diff <tool>` to see the delta
│   │   - `mcpm projection sync <tool>` to overwrite (or move their edits inside the managed block)
│   └── "Audit chain broken"
│       - usually means the file was edited externally (text editor, recovery tool)
│       - `mcpm audit verify --explain` shows the first broken seq
│       - chain cannot be repaired; subsequent lines are still chained from the break onward
├── Incident response
│   ├── How to bundle data for a support ticket: `mcpm doctor --share`
│   ├── How to roll back to a previous version
│   ├── How to start mcpmanagerd in debug mode
│   └── How to disable auto-spawn temporarily
├── Recovery procedures
│   ├── Corrupt config → restore from `~/.config/mcp-manager/config.toml.bak`
│   ├── Lost keychain → re-run `mcpm secret set` for each
│   └── Lost lockfile → `mcpm sync` re-derives
└── Reference
    ├── Log event vocabulary
    ├── Audit event vocabulary
    ├── Exit codes
    └── Environment variables

Style: every chapter section opens with a one-line "you'll see this when..." and ends with "to fix:" + an exact command. Google's SRE Book makes this a central tenet of operational documentation[17]: a runbook entry should be actionable in under 2 minutes by an oncall who has never seen this specific failure before.

The runbook source lives in the same repo as the code so it ships in lockstep. Every PR that adds a new log event or audit event must update the Reference appendix in the same commit (CI check: enumerate all tracing::event!(... "..." ) calls' event names, diff against the mdbook reference; fail if any new ones are missing from the docs).

Pulling it together: end-to-end 3am scenario

Imagine: a developer wakes to find their morning standup is broken because Cursor can no longer reach github-mcp. They run: 

$ mcpm doctor
  ... [WARN] server github-mcp restarted 4 times in 600s
  ... [FAIL] secret GITHUB_TOKEN read failed: keyring locked

$ mcpm doctor --explain GITHUB_TOKEN
  GITHUB_TOKEN was last read 14h ago, before macOS rebooted at 02:14.
  The system keychain is locked after reboot; unlock with Touch ID or password.
  → fix: run any keychain-touching command, e.g.
          `security unlock-keychain ~/Library/Keychains/login.keychain-db`

$ # they unlock, then:
$ mcpm restart github-mcp
  github-mcp restarted; health check ok in 230ms

No vendor was contacted. No telemetry was sent. The audit log records the entire sequence. The doctor command did the diagnostic work that a SaaS error tracker would do. The runbook explains how to interpret the doctor's output if the user has never seen this failure before. This is the operational property that justifies "no telemetry": we built the diagnostic capacity into the tool.
