The Nix Purist's DevOps

flake.nix is the build. devenv.sh is per-server isolation. Cachix carries the binaries. Curl is the courtesy. Everything else — deb packaging, FHS layouts, hand-rolled minisign keys, ad-hoc shell installers — is a re-implementation of what Nix already does correctly. We are shipping a developer-facing supervisor on top of Rust and Tokio; reproducibility is not a "nice to have" property of the release pipeline, it is a load-bearing claim about what users get when they run mcpm install <server>. The honest way to keep that claim is to let Nix make it.

flake.nix = canonical build devenv per-server cachix substituters curl = wrapper

Thoughts — where the stance comes from

The v1.0 lockdown table commits to "curl … | sh installer + Nix flake. No Homebrew, no App Store." Read literally that is a tie. Read in the context of stoic-badger-sandbox's recommendation — "devenv as the reproducibility layer, OS sandbox as the run-time layer" — it is not a tie. Stream 2 already made Nix a load-bearing dependency of the isolation story. Per-MCP-server devenv.nix profiles pin the Python interpreter, the Node runtime, the system libraries, and the transitive package closure for every supervised process. The Nix store is already in our critical path on every machine that uses the primary isolation tier. Pretending the curl installer is co-equal — instead of "the path for users who refuse Nix" — means we accept reproducibility for the MCP servers we supervise but discard it for the supervisor itself. That is incoherent.

Nix flakes pin every input by content hash and produce a derivation that is, by construction, a pure function of its inputs.nix-flakes-determinate A build run on my laptop in 2026-05 and yours in 2027-08, given the same lock file, produces byte-identical artifacts — same mcpmanagerd, same mcpm, same embedded resources. This is the property that audit logs, deterministic SBOMs, and reproducible-builds claims all rely on.reproducible-builds-spec A tarball produced by GitHub Actions and signed with minisign can claim the same property but cannot demonstrate it without orchestration we have not yet written. Nix demonstrates it by default.

The locked decisions also commit us to "auto-spawn daemon" and "no telemetry, ever." Auto-spawn means mcpm exec must find mcpmanagerd on $PATH in a deterministic place; no telemetry means we cannot phone home to discover where the user put the binary. A nix profile install creates a per-user generation that puts both binaries on $PATH with no global state mutation, and exposes them via the user's profile garbage-collection root.nix-manual-profiles A nix profile rollback is one command. The curl installer can match that functionally only by re-writing the relevant /usr/local/bin symlinks atomically and tracking previous installations in a side state file we have not yet designed. We would be re-inventing Nix profiles — badly.

This is not "Nix supremacism." The Nix learning curve is real; stoic-badger conceded that explicitly. The position I hold is more modest: the Nix flake should be the primary distribution channel because it is the only one that can keep our reproducibility claims honest. The curl installer is a courtesy — a thin wrapper that either (a) shells out to nix profile install when Nix is present or (b) downloads the appropriate static-linked artifact otherwise. The static artifacts themselves are produced by the same flake via pkgsCross and uploaded to the GitHub release; the curl installer never has its own independent build path, so we do not double the maintenance surface.

The interesting consequence is for the supply chain. Today's plan layers minisign on top of GitHub releases — a perfectly fine choice for the curl path, but it is solving a problem that Nix already solved differently. Nix has a substituter-trust model: signed binary caches identified by a public key.cachix-docs A user who adds cache.mcp-manager.dev as a substituter and trusts our public key has the same guarantee as a user who verifies a .minisig file — with the additional property that all transitive Nix-built dependencies inherit the same trust model. The two systems are complementary, not duplicative. The fix is to let Nix do Nix and minisign do the static-tarball envelope, and to be precise about which artifact is signed by what.

Finally, the 11-crate workspace is exactly the shape that flakes were designed to build. crane or naersk turn a Cargo workspace into a graph of per-crate Nix derivations, which means CI builds are cached per-crate, not per-workspace. A change to mcpm-projector rebuilds only mcpm-projector and the two binary crates that depend on it. On a CI matrix with macOS and Linux, both x86_64 and aarch64, that is the difference between a 4-minute incremental build and a 25-minute clean build.crane-docs

Arguments against my peers

Versus distro-packager (FHS, deb/rpm)

The distro-packager wants /usr/bin/mcpmanagerd in a .deb repository, a systemd unit shipped via dh_installsystemd, and an apt-managed update path. The appeal is real: it is what every Linux user expects of every other tool. But three things break this for v1.0:

  1. We do not ship a system service. mcpmanagerd is a per-user daemon. Its socket lives in $XDG_RUNTIME_DIR/mcpmanagerd.sock, its config in ~/.config/mcp-manager/, its secrets in the user keychain. A system-wide .deb install puts the binary in /usr/bin but does not give the user a service — the user still must systemctl --user enable something. The packaging buys us nothing the curl tarball does not already buy us, while adding a multi-distro build matrix (deb × rpm × arch × obs × aur).
  2. The MCP server side cannot use distro packages anyway. The MCP servers we supervise are pinned via devenv profiles — we cannot accept "the system's Python 3.11" because a server tested against 3.11.6 cannot promise behaviour against 3.11.13 with different OpenSSL linkage. Distro packages are antithetical to pinned reproducibility, and pinned reproducibility is the product. If the system Python is unfit for purpose for the supervised processes, the system package manager is unfit for purpose for the supervisor.
  3. Nix is multi-distro by construction. One flake builds for Ubuntu 22, Ubuntu 24, Debian 12, Fedora 40, Arch, NixOS, and macOS, with one CI matrix entry per architecture, not per distro × architecture. The deb/rpm path is at least 8x the matrix.

My counter-proposal: if distro packages are wanted, they should be a community contribution wrapping the static tarballs we already produce. We should not own them. Nix is the path we maintain.

Versus sre-hawk (observability, on-call)

The SRE wants Prometheus endpoints, structured-JSON logs to stdout, OpenTelemetry trace export, a /healthz. Everything they want is correct; almost none of it ships in v1.0 (the locked decisions explicitly defer "Observability (Prometheus, OpenTelemetry)" to v1.1). The collision with my position is narrow but real: the SRE wants their pipeline to ingest the binary's logs in a uniform shape regardless of how it was installed. That is a packaging-shaped concern.

Nix helps here, not hurts. A flake produces identical binaries on identical inputs — so the SRE can pin the version they have audited and substitute it from their internal Cachix without trusting a third-party build pipeline.cachix-docs The append-only JSONL audit log defined in the technical design lands at $XDG_STATE_HOME/mcpmanagerd/audit/*.jsonl regardless of install channel; that path is the SRE's ingestion point. What I push back on is the suggestion that we should ship a "production" build that differs from the "dev" build. We should not. One flake, one binary, one set of features; the SRE pipes the JSONL into Loki/Vector/whatever and we are done.

Versus supply-chain-sec (minisign, cosign, SBOM)

The supply-chain agent is my closest ally, but we will disagree on which signature is canonical. They will argue that minisign over the release tarballs is the right primary — small, auditable, no PKI ceremony, single-file public key.minisign-home I agree that minisign on the tarballs is correct. What I add is: that signature is not the only one, and for Nix users it is not the primary one.

Nix's substituter-trust model uses Ed25519 keypairs to sign every path entering a binary cache.cachix-docs A Nix-installed mcpmanagerd is verified path-by-path by nix copy against the cache key; minisign over the tarball is not in that path. The two systems should coexist: minisign signs the curl-tarball envelope, the Nix store substituter key signs every Nix-built path. The flake's GitHub release workflow produces both in the same run, so we are not running two pipelines. Importantly, the same artifact goes into both: the static binary in the tarball is bit-identical to the binary in the Nix store (the tarball is just nix-store --export-equivalent layout).

On SBOM: the supply-chain agent will want CycloneDX or SPDX. Nix already has provenance — every store path is a function of its inputs — but the world wants the SPDX format. I propose nix-sbom or sbomnix as the export bridge: take the flake's output, walk the derivation graph, emit SPDX 2.3 JSON.sbomnix-tiiuae This is auto-generated at release time, not hand-curated. No human ever maintains a list of "deps we ship," because the flake is the list.

Versus curl-installer-defender

This is the real argument. The curl installer defender will say: most developers do not have Nix and never will; the curl installer is the path 95% of users take; therefore the curl installer must be primary in design, not in afterthought. I do not disagree about the user share. I disagree about what "primary" means.

Primary should mean "the source of truth for what gets built." The curl installer can deliver the binary to 95% of users and the canonical build can still be the flake, because the curl installer downloads tarballs that the flake produces. Concretely:

  • One CI workflow. Triggered by tag push. Runs nix flake check on macOS + Linux, x86_64 + aarch64. On success, runs nix build .#mcpmanagerd .#mcpm for each system, packages each result into a tarball with SHA256SUMS, signs each tarball with minisign, uploads to the GitHub release. Same CI run pushes the Nix outputs to cache.mcp-manager.dev (cachix).
  • Curl installer is a 40-line shell script that detects OS+arch, downloads the right tarball, verifies the minisign signature against a baked-in pubkey, untars to $PREFIX/bin, prints "next steps."
  • If nix is on $PATH when the curl installer runs, it can optionally shell out to nix profile install after asking the user. ("We detected Nix — install via Nix for reproducible upgrades? [Y/n]")

The curl installer defender's worry — "Nix takes 20 minutes to install and most users will rage-quit" — is a real concern, and my proposal does not require any user to install Nix. They never see Nix. They curl … | sh, they get a binary, they run mcpm init, they are done. Nix is an internal build-system choice, exactly the way Rust is an internal language choice. We do not require users to install rustc either.

Where we agree: the user-facing CLI flow is curl … | sh for the median user. Where we disagree: the build pipeline's canonical artifact, the SBOM source, the CI gate, and the reproducibility claim live in the flake, not the shell installer.

Design

flake.nix outline

Single repository-root flake.nix. Inputs pinned by content hash. Outputs: packages (the two binaries), devShells (developer environment), checks (nix flake check gates), nixosModules (declarative service config for NixOS users), overlays (so downstream flakes can compose us). Crane handles the Rust workspace so per-crate caching survives across CI runs.crane-docs 

{
  description = "MCP Manager — supervisor for Model Context Protocol servers";

  inputs = {
    nixpkgs.url      = "github:NixOS/nixpkgs/nixos-unstable";
    flake-utils.url  = "github:numtide/flake-utils";
    rust-overlay.url = "github:oxalica/rust-overlay";
    crane            = { url = "github:ipetkov/crane"; inputs.nixpkgs.follows = "nixpkgs"; };
    advisory-db      = { url = "github:rustsec/advisory-db"; flake = false; };
    devenv.url       = "github:cachix/devenv";
  };

  outputs = { self, nixpkgs, flake-utils, rust-overlay, crane, advisory-db, devenv }:
    flake-utils.lib.eachSystem [
      "x86_64-linux" "aarch64-linux"
      "x86_64-darwin" "aarch64-darwin"
    ] (system:
      let
        pkgs = import nixpkgs {
          inherit system;
          overlays = [ (import rust-overlay) ];
        };
        rust = pkgs.rust-bin.stable."1.82.0".default;
        craneLib = (crane.mkLib pkgs).overrideToolchain rust;

        # Common source filter: only what affects the build.
        src = craneLib.cleanCargoSource ./.;
        commonArgs = {
          inherit src;
          strictDeps = true;
          buildInputs = with pkgs; [ openssl ]
            ++ pkgs.lib.optional pkgs.stdenv.isDarwin pkgs.libiconv
            ++ pkgs.lib.optional pkgs.stdenv.isDarwin pkgs.darwin.apple_sdk.frameworks.Security;
          nativeBuildInputs = [ pkgs.pkg-config ];
        };

        # Build deps once, reuse across binary builds — this is the cache win.
        cargoArtifacts = craneLib.buildDepsOnly commonArgs;

        # Per-crate outputs. crane uses cargo metadata to find binary crates.
        mcpmanagerd = craneLib.buildPackage (commonArgs // {
          inherit cargoArtifacts;
          pname = "mcpmanagerd";
          cargoExtraArgs = "-p mcpm-daemon";
          meta.mainProgram = "mcpmanagerd";
        });
        mcpm = craneLib.buildPackage (commonArgs // {
          inherit cargoArtifacts;
          pname = "mcpm";
          cargoExtraArgs = "-p mcpm-cli";
          meta.mainProgram = "mcpm";
        });

      in {
        packages = {
          inherit mcpmanagerd mcpm;
          default = mcpm;            # `nix run` → CLI
          # Composite output: both binaries in one derivation, for `nix profile install`.
          mcp-manager = pkgs.symlinkJoin {
            name = "mcp-manager";
            paths = [ mcpmanagerd mcpm ];
            postBuild = ''
              # Validate that the two binaries are content-addressable peers:
              # they MUST share the same crate-graph hash. This catches drift
              # if someone publishes one without the other.
              test -x $out/bin/mcpmanagerd
              test -x $out/bin/mcpm
            '';
            meta.description = "MCP Manager — mcpmanagerd + mcpm CLI";
          };
        };

        checks = {
          inherit mcpmanagerd mcpm;
          # Per-crate test runs reuse the cargoArtifacts cache.
          test     = craneLib.cargoNextest (commonArgs // { inherit cargoArtifacts; });
          clippy   = craneLib.cargoClippy  (commonArgs // {
                       inherit cargoArtifacts;
                       cargoClippyExtraArgs = "--all-targets -- --deny warnings"; });
          rustfmt  = craneLib.cargoFmt { inherit src; };
          # Reproducibility gate: build twice, diff outputs. Catches non-determinism early.
          audit    = craneLib.cargoAudit { inherit src advisory-db; };
        };

        # Developer environment — `nix develop`.
        devShells.default = devenv.lib.mkShell {
          inherit pkgs;
          inputs = { inherit nixpkgs; };
          modules = [{
            languages.rust.enable  = true;
            languages.rust.channel = "stable";
            packages = with pkgs; [
              cargo-nextest cargo-deny cargo-machete cargo-audit
              mdbook minisign sbomnix
            ];
            pre-commit.hooks.clippy.enable  = true;
            pre-commit.hooks.rustfmt.enable = true;
            pre-commit.hooks.deadnix.enable = true;
          }];
        };

        # NixOS / nix-darwin module: declarative service config for the daemon.
        # Users who want mcpmanagerd as a user-service on NixOS get a one-liner.
        nixosModules.default = import ./nix/module.nix self;
      });
}

Notes worth surfacing:

  • One source filter, two binary builds. cargoArtifacts is computed once and reused by both mcpmanagerd and mcpm — this is what makes CI fast on the 11-crate workspace. A change to mcpm-projector invalidates exactly the artifacts that depend on it; everything else is a cache hit.crane-docs
  • The checks attrset is the CI gate. A single nix flake check invocation runs clippy, rustfmt, nextest, cargo-audit, and per-binary build. The CI workflow is essentially three lines: install Nix, run nix flake check, push to cachix.
  • The composite mcp-manager output is what nix profile install consumes. Putting both binaries under one symlinkJoin means upgrades and rollbacks treat them as a unit, which matches the mcpm-protocol wire-compat contract.
  • The nixos module is the NixOS user's equivalent of the launchd/systemd-user registration the daemon does automatically on first launch.

Per-server devenv.nix profile sketch

The mcpm-supervisor crate, when launching an MCP server with isolation = "devenv", materialises a per-server profile under ~/.config/mcpm/profiles/<name>/ (3 files: devenv.nix, devenv.yaml, devenv.lock) and evaluates it. The lock file is what gives us byte-identical environments across machines.devenv-home The example below is the github-mcp Python server, but the shape is the same for Node, Bun, or native binaries (Stream 2 has full per-language examples at stoic-badger-sandbox / per-server). 

# ~/.config/mcpm/profiles/github-mcp/devenv.nix
# Generated by `mcpm install github-mcp` — do not hand-edit.
{ pkgs, lib, config, inputs, ... }:
{
  # Pinned interpreter, pinned uv.
  languages.python.enable  = true;
  languages.python.version = "3.11.6";
  packages                 = [ pkgs.uv pkgs.git ];

  # Force uv to use Nix-provided Python — no curling random interpreters.
  env.UV_PYTHON_DOWNLOADS = "never";
  env.UV_LINK_MODE        = "copy";

  # The supervisor injects secrets via env at spawn time — devenv does NOT
  # see plaintext. The values land in this process's env via the OS keychain
  # passthrough (mcpm-secrets), never in the devenv.nix file.
  env.GITHUB_TOKEN = "@@MCPM_SECRET_GITHUB_TOKEN@@";  # placeholder, never persisted

  # The supervised process. devenv defines it; mcpm-supervisor exec's it.
  processes.mcp-server.exec = ''
    exec uv run --frozen python -m mcp_server_github --transport stdio
  '';

  # Mark the profile as managed by mcpm so editing surfaces a warning.
  enterShell = ''
    echo "Managed by mcp-manager. Edit via 'mcpm config edit github-mcp'." >&2
  '';
}

Each server's profile is composable from a baseline. The mcpm-projector emits the devenv.nix from a TOML manifest in manifests/toolchains/<server-kind>.toml, so a server author who publishes to our registry ships a TOML, not a Nix expression. This keeps the "Nix learning curve" cost on us, not on server authors — which matches the constraint stoic-badger-sandbox conceded: "never make a Nix expression the first thing the user has to read."

CI matrix (single nix flake check)

Four runners, one workflow, one command per runner. The matrix is system × bin, not distro × bin × build-tool. Cachix Action handles cache push-on-success.cachix-action-gh

RunnerSystemCommandWhat runs
GitHub Actions ubuntu-latestx86_64-linuxnix flake check -Lclippy · rustfmt · nextest · audit · build mcpmanagerd · build mcpm
GitHub Actions ubuntu-latest (qemu)aarch64-linuxnix build .#mcpm-manager --system aarch64-linuxbuild only (tests on native runners only)
GitHub Actions macos-14aarch64-darwinnix flake check -Lfull check
GitHub Actions macos-13x86_64-darwinnix flake check -Lfull check

Reproducibility gate: a fifth job runs nix build --rebuild .#mcp-manager on Linux and asserts that the SHA256 of the output path matches the first job's output. If they differ, the build is non-deterministic and CI fails. This is the same idea as the reproducible-builds.org double-build check, but enforced by Nix's path-equality semantics.reproducible-builds-spec

Binary cache (cachix) flow

Every successful nix flake check on the four runners pushes its result paths to cache.mcp-manager.dev, signed with our Ed25519 substituter key.cachix-docs Users with Nix get cache hits transparently. Users without Nix get the same artifact via the tarball path. 

# What a Nix-using developer puts in their nix.conf to get our cache:
substituters       = https://cache.nixos.org https://cache.mcp-manager.dev
trusted-public-keys = cache.nixos.org-1:6NCHdD59X431o0gWypbMrAURkbJ16ZPMQFGspcDShjY=
                      mcp-manager.dev-1:<our-ed25519-public-key>

The cache itself can be hosted on Cachix (managed) or Hercules CI (self-hosted) — both speak the same protocol.hercules-ci-binary-cache For v1.0 we use Cachix because the team's setup time is zero. Migration to Hercules later is a config change, not a re-architecture, because the cache is the binary substituter protocol — the producer side is identical.

The trust composition with minisign is clean:

  • Curl path: static tarball → minisign signature against baked-in pubkey → user untars to $PREFIX/bin. No Nix involved.
  • Nix path: store path → cachix substituter signature against trusted Ed25519 pubkey → nix copy into local store → nix profile install exposes both binaries on $PATH. No minisign involved.
  • Both paths produce the same binary. The Nix derivation that builds mcpmanagerd is the same one whose output gets packed into the tarball. SHA256 of the binary is identical regardless of which path the user came through. This is the property that makes the dual path honest.

SBOM export from Nix

Nix's store paths are the SBOM — every derivation's inputs are content-addressed and visible in the dependency graph. The translation to SPDX or CycloneDX is mechanical. We use sbomnix, which walks the flake's output derivation and emits SPDX 2.3 JSON.sbomnix-tiiuae 

# Added to flake.nix outputs:
apps.sbom = {
  type = "app";
  program = let
    sbomScript = pkgs.writeShellScriptBin "gen-sbom" ''
      ${pkgs.sbomnix}/bin/sbomnix \
        --type=runtime \
        --csv=mcp-manager.csv \
        --cdx=mcp-manager.cdx.json \
        --spdx=mcp-manager.spdx.json \
        .#mcp-manager
    '';
  in "${sbomScript}/bin/gen-sbom";
};

Run as nix run .#sbom in CI on every tag. The resulting mcp-manager.spdx.json and mcp-manager.cdx.json are attached to the GitHub release alongside the tarballs and their minisign signatures. The supply-chain agent gets their CycloneDX without any of us hand-curating a dependency list.

Service manager interaction (launchd + systemd-user)

The locked design says: "Auto-spawns from mcpm exec; optional service-manager registration on first launch (opt-in)." On a Nix-installed system this composes cleanly:

  • Nix profile install places mcpmanagerd at ~/.nix-profile/bin/mcpmanagerd (a symlink into /nix/store). The launchd plist or systemd-user unit references this symlink path. Profile rollback updates the symlink atomically; the service definition does not change.
  • On NixOS / nix-darwin, the nixosModules.default output exports a declarative service: a user adds services.mcpmanagerd.enable = true; to their config and the service unit is written into the system declaratively. No imperative "mcpm wrote a plist into ~/Library/LaunchAgents"; the state is part of the user's NixOS config and gets rolled into their generation.
  • For non-NixOS Nix users, the mcpm CLI's first-launch interactive prompt ("Register mcpmanagerd with launchd as a background service? [y/N]") still works — it just writes the plist pointing at the profile symlink. mcpm uninstall then becomes "remove the plist, run nix profile remove mcp-manager." The audit event service.unregister fires either way.

devenv-as-isolation versus systemd

A subtle point: devenv profiles are not a service-manager replacement. The supervised MCP-server process inside a devenv profile is still spawned by mcpm-supervisor's tokio task and watched by it — devenv just hands us a pinned environment to spawn into. The OS sandbox (bubblewrap on Linux, sandbox-exec on macOS) wraps the devenv-spawned process. So the layering is: launchd/systemd-user runs mcpmanagerd; mcpmanagerd runs each MCP server inside a devenv-pinned shell, inside an OS sandbox. Three nested concerns, three layers, no conflation.

Update mechanism — nix profile upgrade

The technical design says v1.0 "does not ship a self-updater." That is correct for the curl path: users re-run the curl script and the new tarball lands. For the Nix path, the update is one command: 

$ nix profile upgrade mcp-manager

This re-resolves the flake's reference, downloads the new version from cache.mcp-manager.dev (cache hit if we have built it; cache miss falls back to local build), updates the profile generation, and swaps the symlinks atomically. If the new version misbehaves, nix profile rollback reverts. The user never has to think about "did the tarball download corrupt?" because Nix verifies every path against the substituter signature before swapping. This is the model version-management uses for MCP servers — "range in manifest, exact in lockfile" — applied to the supervisor itself: the flake input declaration is the range, the flake.lock is the exact pin.

Renovate's vocabulary maps cleanly onto Nix semantics. The version-management recommendation classifies updates as patch / minor / major / digest / spec-bump. For a Nix-installed user, those map to: same flake.lock hash within a semver range (patch/minor), flake-output rename (major), nixpkgs revision bump with no functional change (digest), and downstream-server spec change (orthogonal — that is per-server, not per-supervisor).

Cross-platform — what differs in the flake

Almost nothing. Two macOS-specific lines: libiconv and the Security framework via darwin.apple_sdk.frameworks. Everything else is shared. The flake-utils.lib.eachSystem wrapper handles the cross-product for us. macOS's launchd integration lives in a runtime code path in mcpm-daemon, not in the build — the binary detects its platform and writes the right service file. The flake builds the same binary for both.

Service-string namespace — dev.mcp-manager is correct

The technical design uses dev.mcp-manager.mcpmanagerd for keychain entries and (presumably) launchd labels. This is reverse-DNS, conventional, and aligns with Nix flake attribute naming: github:user/mcp-manager maps semantically to "the mcp-manager project at the dev domain." A flake's outputs are namespaced by attribute path (e.g. packages.x86_64-linux.mcpmanagerd), so the reverse-DNS form in OS-level service strings is the right shape to mirror that — both spaces use a hierarchical, namespace-collision-free convention. I would not switch to bare mcp-manager; the qualified form survives multi-tool installs on a single machine (e.g. if a future fork uses the bare name).

mdbook docs hosting

The locked decision says "mdbook docs in repo." Nix builds them: add an mdbook derivation to the flake outputs. 

packages.docs = pkgs.stdenv.mkDerivation {
  name = "mcp-manager-docs";
  src  = ./docs;
  nativeBuildInputs = [ pkgs.mdbook ];
  buildPhase   = "mdbook build";
  installPhase = "cp -r book $out";
};

CI builds nix build .#docs on every PR and publishes the result to GitHub Pages (or an equivalent). The docs build is reproducible; the same Markdown produces the same HTML byte-for-byte. No "works on my machine" drift between contributor toolchains.mdbook-docs

mcpm uninstall on Nix

The locked UX says mcpm uninstall "Removes MCP Manager. Unregisters from service manager, stops daemon + servers, removes config dir, preserves audit log + keychain." On a Nix-installed system this becomes:

  1. mcpm uninstall stops the daemon, unregisters the launchd/systemd-user service (audit: service.unregister), removes ~/.config/mcp-manager/ (unless --keep-config).
  2. It then prints, but does not run: nix profile remove mcp-manager. The user runs that to remove the binary itself.
  3. The user can later nix profile rollback to restore everything (including the binary) if they regret it. This is a strictly better property than the curl path, which has no undo.

The reason mcpm uninstall does not itself run nix profile remove is that doing so requires nix on $PATH at uninstall time and assumes the binary was installed via Nix (it might have been installed via the curl wrapper that called nix profile install automatically, but the user might not remember). Printing the command is honest; running it is presumptuous. The CLI's prompt asks ("Detected Nix install; remove via nix profile remove mcp-manager? [Y/n]") and runs it on confirmation.

Auto-spawn daemon — binary path resolution

The technical design says mcpm-client's connect() auto-spawns mcpmanagerd on ENOENT/ECONNREFUSED. The lookup is: (1) try $XDG_RUNTIME_DIR/mcpmanagerd.sock; (2) on failure, fork+spawn. For "fork+spawn" we need the path to the daemon binary. On a Nix profile install, this is ~/.nix-profile/bin/mcpmanagerd (a symlink); on a curl install, it is /usr/local/bin/mcpmanagerd (a real file). The CLI does which mcpmanagerd via $PATH — the same as any other tool. The user's shell $PATH is what makes this work; Nix profiles add ~/.nix-profile/bin to $PATH at user-login time, the curl installer's $PREFIX/bin path is already there for any sane $PREFIX. No special-casing in the daemon-spawn code; it is the same code path for both install channels.

Why this is the honest design

Every claim we want to make about MCP Manager — reproducible, auditable, isolated, secret-safe, no-telemetry — rests on the build being a pure function of its inputs. The lockfile schema in the technical design ("range in manifest, exact in lockfile") is a recapitulation of the flake-lock idea. The audit log's promise that "we know what ran" requires "we know what was installed." The substituter-trust model gives us a primitive that says "this binary came from this set of inputs, signed by this key." We are not building a new trust-system; we are inheriting the one Nix has already debugged for fifteen years. The curl installer can ship the artifact, but the flake produces it — and that is the relationship that should be primary in our heads, even when it is invisible to the median user.
