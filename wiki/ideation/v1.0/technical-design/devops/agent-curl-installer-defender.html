The Curl Installer Defender's DevOps

One line. Fresh macOS or Linux box. It works. The user types curl -fsSL https://mcp-manager.dev/install.sh | sh, the script verifies itself against a published signature, downloads a deterministic tarball, verifies it against a minisign-signed SHA256SUMS, drops two binaries into $PREFIX/bin, writes a PATH snippet to the right rc file, registers a launchd / systemd-user unit, and prints a single helpful next-step. That is the entire UX contract. v1.0 ships it, tests it on a fresh-VM matrix every release, and nobody — neither the Nix purist nor the FHS packager nor the supply-chain-sec auditor — has yet shown me a 2026 install flow with a better latency-to-first-success budget.

Thoughts

The "curl-pipe-shell considered harmful" essay is older than git's main-default rename, and every junior security blogger reheats it once a year. The core complaint — that an attacker who controls the install host can ship code that runs as the current user — is true. It is also true of brew install, of nix profile install, of every apt mirror, of every container registry, and of every CI runner that curls its own bootstrap. The argument from "curl|sh is the worst" proves far too much; once you accept that you do, in fact, trust the upstream you are installing software from, the question is no longer "should I trust this transport" but "is this transport the most legible, the most inspectable, and the most reproducible given the trust I have already extended?". For a single static binary with no native compilation, no per-distro packaging dance, and no runtime dependency graph, the answer is yes.

The genre I am defending is not the cowboy script that sudo rm -rf's half your /usr and writes random init files. The genre I am defending is the rustup / starship / nvm / flyctl / tailscale style of installer: a hundred-and-fifty lines of POSIX shell, defensive set -eu, an arch detector, a TLS-pinned fetch, a checksum verify, an atomic mv into $PREFIX/bin, and a single "you may need to source ~/.zshrc" stinger. Rustup has run this play since 2016 on every major Linux distro, every macOS version, and inside every CI provider on Earth without anyone losing sleep. The bar for "responsibly done curl|sh" is high but it is not hypothetical — there are working models we can borrow and improve.

My peers will try to drag this debate into the deep water of supply-chain provenance and reproducible builds, and I will meet them there: I agree we should publish a SHA256SUMS, sign it with minisign, optionally cross-sign with cosign-keyless, attach an SBOM via syft/spdx, and notarize the macOS binaries against Apple's notary service. None of that is in tension with curl|sh. All of it can be done inside the installer's verification step, because the installer itself is a tiny program whose entire job is "fetch one tarball, verify two signatures, extract, atomic-move, register service, print next step." It is much easier to audit a 200-line shell script than it is to audit a 12,000-line Nix derivation that overrides three transitive C compilers because one of them depends on Bash 5.2.15 instead of 5.2.21.

The other thing my peers will pretend not to notice is the user. The user is sitting at a fresh macOS box at 11pm and just wants the demo to work. They will not install Nix. They will not install Homebrew if they do not already have it. They will not sudo apt install mcpm if we are not in their distro's repos — and we will not be, because v1.0 cannot get into Debian stable in any reasonable timeframe and getting into the AUR / Fedora COPR / homebrew-core involves social processes that take months. The only install path that works at the moment of first contact is curl|sh. Every other path requires that the user has already bought into a meta-installer that, itself, was installed via — what do you suppose? — a curl|sh script of someone else's design. Homebrew is literally installed by /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)". Nix on macOS is installed by curl --proto '=https' --tlsv1.2 -sSf -L https://install.determinate.systems/nix | sh -s. The argument that "curl|sh is irresponsible" cannot survive contact with the actual ecosystem because the ecosystem is built on it.

So my position is not "curl|sh is fine, ship it and run." My position is "curl|sh, signed, verified, dry-runnable, with a published checksum of the install.sh itself, with a fresh-VM CI matrix that catches regressions, with a clean uninstall, is the right v1.0 transport — and the rest is engineering." The rest of this document is that engineering.

What "responsible" means in concrete terms

  • The install.sh itself is reproducible. Each release publishes install.sh alongside install.sh.sha256 and install.sh.minisig in the GitHub Release. Paranoid users curl … > install.sh; minisign -V -P <baked-pubkey> -m install.sh; sh install.sh.
  • Binaries are signed twice. macOS binaries are notarized via Apple Developer Program (so Gatekeeper does not block them); Linux tarballs are minisigned with a key whose fingerprint is published in the project README, in the GitHub repo description, and in the website's TLS-served /.well-known/minisign-pubkey.
  • The installer dry-runs. curl … | sh -s -- --dry-run prints every action — every file it would write, every directory it would create, every service-manager unit it would register — and exits 0 without touching the filesystem.
  • The installer is overridable. --prefix=/opt/mcpm sets install root. --no-service skips launchd / systemd-user registration. --no-path skips the rc-file PATH snippet. --version=1.0.3 pins a release. --no-modify-path is an alias to match rustup's vocabulary, so users with muscle memory don't have to learn ours.
  • The installer is reversible. Every file the installer touches is recorded in ~/.local/share/mcp-manager/install-manifest.json; mcpm self-uninstall reads that manifest and removes exactly what was installed — no shotgun rm -rf.
  • The installer is observable. MCPM_VERBOSE=1 curl … | sh turns on set -x; every downloaded URL, every checksum verify, every mv, every chmod is printed to stderr. No telemetry — that's a permanent project decision — but you can see what it did, in real time, in your terminal.

Arguments vs. peers

vs. nix-purist — "curl|sh is sketchy, flakes are reproducible"

My friend the Nix purist is going to say that nix profile install github:user/mcp-manager gives them a content-addressed, bit-identical install that the curl script cannot match. They are right on the technical claim and wrong on its relevance. Nix is the second channel — v1.0 ships both, this is not either-or. But Nix cannot be the first channel because the on-ramp to Nix is itself a curl|sh installer. The Determinate Systems installer that everyone actually uses on macOS in 2026 is curl … | sh. The official Nix installer at nixos.org/download is also curl … | sh. If "curl|sh is sketchy" then Nix's own bootstrap is sketchy. Pick one.

Reproducibility-for-the-user is a separate axis from reproducibility-for-the-distributor. Our binaries are built reproducibly from a pinned rust-toolchain.toml, a pinned cargo lockfile, and a pinned Nix flake that produces the release artifact set. The curl installer fetches that exact artifact. The user gets the same bytes as the Nix user — they just don't have to install a 1.2GB store and a daemon to get them. The Nix channel is for the 5% of users who want flake-pinned reproducibility for their own CI/devshells; the curl channel is for the 95% who want a working binary in 8 seconds.

Also: devenv is great. It's also what we use for the per-MCP-server isolation layer (see stoic-badger-sandbox). The presence of Nix inside the product for sandboxing does not imply the installer should be Nix-only. Different layers, different constraints.

vs. distro-packager — "ship deb/rpm/AUR, follow FHS, install manpages"

The distro-packager is going to argue that the One True Way is to get into apt, dnf, pacman, and homebrew-core, so that users on each platform use their native package manager. They will cite FHS, /usr/share/man/man1/mcpm.1.gz, polkit policies, and the joys of Debian's two-year stable cycle. Three problems:

  1. Cadence mismatch. v1.0 will iterate. We expect to ship patch releases every 1–2 weeks for the first six months. Debian stable does not move at that cadence; users would be a year out of date. Even rolling-release distros (Arch, Fedora Rawhide) require a packager to update the spec, and the packager is not us — it's a volunteer who may be on vacation when CVE-2026-X drops.
  2. Per-distro fragmentation. A native .deb has to declare Depends: on the libc version, on libsecret, on systemd. An .rpm has to differentiate between RHEL 8, RHEL 9, Fedora 39, and openSUSE. We would either ship 12 different packages or pick one and abandon the rest. The static-Rust binary in a tarball solves this once.
  3. FHS is fine but optional. We respect XDG for config ($XDG_CONFIG_HOME/mcp-manager/), state ($XDG_STATE_HOME/mcp-manager/), and runtime ($XDG_RUNTIME_DIR/mcpmanagerd.sock). We default $PREFIX to $HOME/.local (per XDG) on Linux and /usr/local on macOS. Manpages can ship inside the tarball at share/man/man1/mcpm.1.gz; the installer can drop them into $PREFIX/share/man with a tiny manpath hint. The distro-packager's concerns are addressed; their preferred vehicle (distro repos) is not.

If a third-party packager wants to ship us in the AUR or in nixpkgs or in MacPorts, we welcome it. We will not block them. We will not be them in v1.0.

vs. sre-hawk — "observability, on-call, what happens at 3am?"

The SRE worries that without telemetry we won't know when installs fail. The project decision is "no telemetry, ever" (locked) — so the SRE has to accept that the failure-mode visibility we get is via voluntary user reports on the issue tracker. Within that constraint, the curl installer is the most debuggable install path possible: it is 200 lines of POSIX shell, every action is a single command, MCPM_VERBOSE=1 dumps set -x to stderr, and the user can paste the entire trace into a GitHub issue. Compare that to debugging a .deb postinst failure, which buries errors in /var/log/apt/term.log behind two layers of dpkg trigger machinery.

For the daemon side, the installer registers a launchd plist on macOS / systemd-user unit on Linux. Both come with native journaling — log show --predicate 'subsystem == "dev.mcp-manager"' on macOS, journalctl --user -u mcpmanagerd on Linux. That's the on-call story: users on-call for their own machine use OS-native tools; we don't reinvent a logging pipeline; the SRE gets exactly the observability stack their OS already gives them.

The installer also writes ~/.local/share/mcp-manager/install.log with timestamps for every step — a poor-person's tracing for the install itself, survivable across terminal closes. That's enough to debug 95% of install failures from a user-pasted log.

vs. supply-chain-sec — "curl|sh is irresponsible, where's the SBOM, cosign-keyless this"

This is my dance partner. The supply-chain-sec critic and I actually want most of the same things — we differ only on which knobs to turn. Let me concede the genuine points and then push back on the rhetoric.

Conceded:

  • We publish SHA256SUMS and SHA256SUMS.minisig. The installer verifies the tarball's hash against SHA256SUMS, and verifies SHA256SUMS against the baked-in minisign pubkey. Two-step verify, exactly as the JSON Resume ecosystem and the minisign upstream do.
  • We publish an SBOM (spdx-json) per release via syft, attached to the GitHub Release as mcp-manager-1.0.0.spdx.json.
  • We sign tarballs with cosign-keyless (Sigstore / Fulcio) in addition to minisign, so users who already trust the Sigstore root of trust can verify via the public-good transparency log. Both signatures are checked when both verifiers are present; minisign is the required path because it has no network dependency.
  • macOS binaries are notarized via Apple's notary service. Gatekeeper does not block them on first run.
  • The installer pins TLS 1.2+ (curl --tlsv1.2 --proto '=https'), rejects redirects to non-HTTPS, and uses --fail-with-body to surface HTTP errors loudly rather than piping HTML into sh.

What I won't concede:

  • That the user must have cosign or gpg already installed for the installer to be "responsible." The minisign verification is performed by a statically linked verify-only helper embedded in the installer (via a signed sidecar binary that we fetch and run). No pre-existing crypto tooling required. The supply-chain-sec critic loses the "users don't have minisign installed" lever.
  • That distributing via curl|sh is meaningfully more risky than distributing via Homebrew, Nix, or any other package manager. They all ultimately resolve to "download bytes from a server controlled by the upstream, run code derived from those bytes." The difference is layers of abstraction, not threat model. The threat model collapses to "do you trust the publisher's signing key?" which is identical across transports.
  • That we should require GPG. GPG's web of trust is dead, key servers are dead, and the typical user cannot meaningfully participate in it. Minisign is a single Ed25519 keypair with a published fingerprint — the simplest crypto that works. See "The PGP Problem".

Design

install.sh — annotated outline

The installer is a single POSIX-sh file, ~250 lines, under website/install.sh in the repo, served from https://mcp-manager.dev/install.sh via the project's static site host. It does no sudo by default (installs to $HOME/.local on Linux, /usr/local on macOS where the user has write access via /usr/local/bin being writable on macOS Apple-Silicon defaults — or to $HOME/.local if not). It does no compilation. It does one download-and-verify of a sidecar verifier, one of the SHA256SUMS+signature, and one of the tarball. 

#!/bin/sh
# install.sh — mcp-manager v1.0
# https://mcp-manager.dev/install.sh
# SPDX-License-Identifier: Apache-2.0

set -eu

# ----- Config -----------------------------------------------------------------
MCPM_VERSION="${MCPM_VERSION:-latest}"
MCPM_PREFIX="${MCPM_PREFIX:-}"          # auto-detected below
MCPM_NO_SERVICE="${MCPM_NO_SERVICE:-0}"
MCPM_NO_PATH="${MCPM_NO_PATH:-0}"
MCPM_DRY_RUN="${MCPM_DRY_RUN:-0}"
MCPM_VERBOSE="${MCPM_VERBOSE:-0}"
MCPM_BASE_URL="${MCPM_BASE_URL:-https://github.com/mcp-manager/mcp-manager/releases}"
MCPM_MINISIGN_PUBKEY="RWQf6LRCGA9i53mlYecO4IzT51TGPpvWucNSCh1CBM0QTaLn73Y7GFO3"
# ^ baked-in trust anchor; rotation requires a new install.sh release

# ----- Arg parsing ------------------------------------------------------------
while [ $# -gt 0 ]; do
  case "$1" in
    --version=*)        MCPM_VERSION="${1#*=}";;
    --prefix=*)         MCPM_PREFIX="${1#*=}";;
    --no-service)       MCPM_NO_SERVICE=1;;
    --no-path|--no-modify-path) MCPM_NO_PATH=1;;
    --dry-run)          MCPM_DRY_RUN=1;;
    --verbose|-v)       MCPM_VERBOSE=1;;
    --help|-h)          usage; exit 0;;
    *) err "unknown flag: $1"; exit 2;;
  esac
  shift
done
[ "$MCPM_VERBOSE" = "1" ] && set -x

# ----- Detect OS + arch -------------------------------------------------------
detect_target() {
  os=$(uname -s | tr '[:upper:]' '[:lower:]')
  arch=$(uname -m)
  case "$os" in
    darwin) os_triple="apple-darwin";;
    linux)  os_triple="unknown-linux-gnu";;
    *) err "unsupported OS: $os (only macOS and Linux are supported)"; exit 1;;
  esac
  case "$arch" in
    x86_64|amd64)  arch_triple="x86_64";;
    aarch64|arm64) arch_triple="aarch64";;
    *) err "unsupported arch: $arch"; exit 1;;
  esac
  TARGET="${arch_triple}-${os_triple}"
}

# ----- Resolve version --------------------------------------------------------
resolve_version() {
  if [ "$MCPM_VERSION" = "latest" ]; then
    # Follow the /latest redirect to get the tag
    MCPM_VERSION=$(curl --tlsv1.2 --proto '=https' -fsSLI -o /dev/null \
      -w '%{url_effective}' "$MCPM_BASE_URL/latest" | sed 's#.*/tag/##')
  fi
  case "$MCPM_VERSION" in v*) ;; *) MCPM_VERSION="v$MCPM_VERSION";; esac
}

# ----- Pick prefix ------------------------------------------------------------
default_prefix() {
  if [ -z "$MCPM_PREFIX" ]; then
    case "$(uname -s)" in
      Darwin) MCPM_PREFIX="/usr/local";;
      Linux)  MCPM_PREFIX="$HOME/.local";;
    esac
  fi
  BIN_DIR="$MCPM_PREFIX/bin"
  MAN_DIR="$MCPM_PREFIX/share/man/man1"
  STATE_DIR="${XDG_STATE_HOME:-$HOME/.local/share}/mcp-manager"
  # Writability check; fall back to ~/.local if not writable
  if ! mkdir -p "$BIN_DIR" 2>/dev/null; then
    warn "$BIN_DIR not writable; falling back to \$HOME/.local"
    MCPM_PREFIX="$HOME/.local"
    BIN_DIR="$MCPM_PREFIX/bin"
    MAN_DIR="$MCPM_PREFIX/share/man/man1"
    mkdir -p "$BIN_DIR"
  fi
}

# ----- Fetch + verify ---------------------------------------------------------
fetch() {
  # $1 = URL, $2 = output path
  curl --tlsv1.2 --proto '=https' --fail-with-body -sSL "$1" -o "$2"
}

download_artifacts() {
  TMP=$(mktemp -d)
  trap 'rm -rf "$TMP"' EXIT
  TARBALL="mcp-manager-${MCPM_VERSION#v}-${TARGET}.tar.gz"
  REL="$MCPM_BASE_URL/download/$MCPM_VERSION"
  step "downloading tarball + signatures"
  fetch "$REL/$TARBALL"             "$TMP/$TARBALL"
  fetch "$REL/SHA256SUMS"           "$TMP/SHA256SUMS"
  fetch "$REL/SHA256SUMS.minisig"   "$TMP/SHA256SUMS.minisig"
  # Sidecar verify helper — tiny static binary that does minisign + sha256.
  # Signed itself by the same trust anchor; we verify it against an embedded
  # hash baked into install.sh at release time.
  fetch "$REL/mcpm-verify-${TARGET}" "$TMP/mcpm-verify"
  chmod +x "$TMP/mcpm-verify"
  expected_verify_hash="$EMBEDDED_VERIFY_HASH"  # patched in by release pipeline
  actual="$(shasum_256 "$TMP/mcpm-verify")"
  [ "$expected_verify_hash" = "$actual" ] || die "verify-helper hash mismatch"
}

verify_artifacts() {
  step "verifying SHA256SUMS signature"
  "$TMP/mcpm-verify" minisign \
      --pubkey "$MCPM_MINISIGN_PUBKEY" \
      --signature "$TMP/SHA256SUMS.minisig" \
      --message "$TMP/SHA256SUMS"
  step "verifying tarball checksum"
  "$TMP/mcpm-verify" sha256sum \
      --sums "$TMP/SHA256SUMS" \
      --target "$TMP/$TARBALL"
}

# ----- Extract + install ------------------------------------------------------
install_files() {
  step "extracting"
  mkdir -p "$TMP/extract"
  tar -xzf "$TMP/$TARBALL" -C "$TMP/extract"

  manifest="$STATE_DIR/install-manifest.json"
  mkdir -p "$STATE_DIR"
  printf '{"version":"%s","files":[' "$MCPM_VERSION" > "$manifest.tmp"
  first=1
  install_one() {
    src="$1"; dst="$2"; mode="$3"
    if [ "$MCPM_DRY_RUN" = "1" ]; then
      echo "  [dry-run] install $src -> $dst (mode $mode)"
    else
      install -m "$mode" "$src" "$dst"
    fi
    [ $first -eq 0 ] && printf ',' >> "$manifest.tmp"
    printf '"%s"' "$dst" >> "$manifest.tmp"; first=0
  }
  install_one "$TMP/extract/bin/mcpm"          "$BIN_DIR/mcpm"          0755
  install_one "$TMP/extract/bin/mcpmanagerd"   "$BIN_DIR/mcpmanagerd"   0755
  mkdir -p "$MAN_DIR"
  install_one "$TMP/extract/share/man/man1/mcpm.1.gz" "$MAN_DIR/mcpm.1.gz" 0644
  printf ']}\n' >> "$manifest.tmp"
  mv "$manifest.tmp" "$manifest"
}

# ----- PATH snippet -----------------------------------------------------------
write_path_snippet() {
  [ "$MCPM_NO_PATH" = "1" ] && return 0
  case "$BIN_DIR" in
    /usr/local/bin) return 0 ;;   # already on PATH virtually everywhere
  esac
  shell_name=$(basename "${SHELL:-/bin/sh}")
  case "$shell_name" in
    bash) rc="$HOME/.bashrc" ;;
    zsh)  rc="${ZDOTDIR:-$HOME}/.zshrc" ;;
    fish) rc="$HOME/.config/fish/conf.d/mcp-manager.fish" ;;
    *)    warn "unrecognised shell ($shell_name); add $BIN_DIR to PATH manually"; return 0 ;;
  esac
  snippet_begin="# >>> mcp-manager >>>"
  snippet_end="# <<< mcp-manager <<<"
  if [ -f "$rc" ] && grep -q "$snippet_begin" "$rc"; then
    return 0   # idempotent
  fi
  mkdir -p "$(dirname "$rc")"
  if [ "$shell_name" = "fish" ]; then
    cat >> "$rc" <<EOF
$snippet_begin
fish_add_path -g $BIN_DIR
$snippet_end
EOF
  else
    cat >> "$rc" <<EOF
$snippet_begin
case ":\$PATH:" in *":$BIN_DIR:"*) ;; *) export PATH="$BIN_DIR:\$PATH" ;; esac
$snippet_end
EOF
  fi
}

# ----- Service-manager registration -------------------------------------------
register_service() {
  [ "$MCPM_NO_SERVICE" = "1" ] && return 0
  case "$(uname -s)" in
    Darwin) register_launchd ;;
    Linux)  register_systemd_user ;;
  esac
}

# ----- Final message ----------------------------------------------------------
print_next() {
  cat <<EOF
mcp-manager $MCPM_VERSION installed to $BIN_DIR.

  next:  $BIN_DIR/mcpm init
         (or restart your shell so '$BIN_DIR/mcpm' is on PATH)

docs:    https://mcp-manager.dev/docs
issues:  https://github.com/mcp-manager/mcp-manager/issues
EOF
}

main() {
  detect_target
  resolve_version
  default_prefix
  download_artifacts
  verify_artifacts
  install_files
  write_path_snippet
  register_service
  print_next
}
main "$@"

The script is wrapped in main "$@" at the end, so a partial download (e.g. dropped connection mid-pipe) does not cause partial execution: sh only invokes main once the whole file is read into memory. That's the same defense rustup uses; see "Don't pipe to your shell" for the cautionary tale and rustup's own rustup-init.sh for the canonical mitigation.

Tarball layout

Deterministic. Sorted file order. Pinned mtimes (1970-01-01) for reproducibility. Two binaries, one manpage per command, plus a versioned README + LICENSE + SBOM-pointer. No install-script-inside-the-tarball; the install logic lives only in install.sh so it's auditable in one place.

│   └── mcpmanagerd         (statically-linked Rust binary, ~16 MB)
├── share/

Built via tar --sort=name --owner=0 --group=0 --numeric-owner --mtime='@0' -czf on Linux, and an equivalent invocation on macOS via bsdtar's --options gzip:compression-level=9 + explicit-uid/gid flags. The release pipeline diffs every artifact byte-for-byte against the previous build to catch non-determinism regressions (see reproducible-builds.org/docs/archives).

PATH-rc snippet logic

Detect $SHELL via basename. Write a fenced snippet (begin/end markers) into the right rc file. Idempotent — grep for the begin marker before writing. The snippet uses POSIX case to guard against re-adding to PATH on every shell start. For fish, write to ~/.config/fish/conf.d/ (single-purpose file, no fencing needed). For unrecognised shells (csh, nu, …), print a warning with the line the user should add manually — do not write to a random rc file we don't understand.

--dry-run semantics

Every state-mutating function checks $MCPM_DRY_RUN and prints [dry-run] + the action instead of executing. Read-only steps (download to $TMP, verify signatures, detect arch, resolve version) still run because the user wants to see them work. Exit code: 0 if dry-run reached print_next without error, non-zero on any verification failure. The net effect: curl … | sh -s -- --dry-run tells you "this is exactly what I would have done, and yes, the signature was good."

--prefix semantics

--prefix=/opt/mcpm sets $MCPM_PREFIX, then $BIN_DIR=$PREFIX/bin, $MAN_DIR=$PREFIX/share/man/man1. Writability is tested; if the prefix is not writable by the current user, we fall back to $HOME/.local with a warning. We never escalate to sudo automatically — the user can pre-create the prefix with the right perms if they want a system-wide install.

Service-manager registration

On macOS: install ~/Library/LaunchAgents/dev.mcp-manager.mcpmanagerd.plist, then launchctl bootstrap gui/$UID it. The plist sets KeepAlive=false because we want auto-spawn-from-mcpm-exec, not always-running. RunAtLoad=false. The plist is templated by install.sh to substitute $BIN_DIR/mcpmanagerd as the program path.

On Linux: install ~/.config/systemd/user/mcpmanagerd.service, then systemctl --user daemon-reload && systemctl --user enable mcpmanagerd.socket (socket-activated; the daemon spawns only when something connects to $XDG_RUNTIME_DIR/mcpmanagerd.sock). Socket activation is the right primitive here — it matches the auto-spawn semantics perfectly, and it's already what systemd.socket(5) is designed for.

--no-service skips both. The user can run mcpmanagerd in a terminal manually for development.

Auto-spawn confirmation

After registration, the installer runs mcpm doctor (a built-in self-test). It verifies: (a) mcpmanagerd binary is launchable, (b) socket path is writable, (c) for systemd: the .socket unit is enabled, (d) for launchd: the LaunchAgent is loaded. If anything fails, the installer prints a clear remediation and exits non-zero. The user is never left in a "installed but mysteriously not working" state.

Update mechanism

mcpm self-update re-fetches install.sh (with verification of its own signature against the baked-in trust anchor inside the running mcpm binary) and runs it with the same prefix as the original install. Internally this is just "re-run install.sh in-place, with $MCPM_PREFIX set from the install manifest." We do not ship a separate updater; the installer is the updater. This is the rustup model (rustup self update; see rustup docs) and it's correct because it means one code path to audit, not two.

mcpm self-update --check compares installed version to $MCPM_BASE_URL/latest (via a HEAD redirect, same as install.sh's version resolver) and prints a diff. No automatic background updates. No phone-home. The user pulls when they want to pull.

Uninstall correctness

mcpm self-uninstall reads $STATE_DIR/install-manifest.json, removes exactly the files it lists, tears down the launchd / systemd-user unit, optionally removes the PATH snippet (idempotent — finds the fenced block and removes it), and prints "uninstalled. ~/.config/mcp-manager/ and ~/.local/share/mcp-manager/ left intact; rm them by hand if you want to fully reset."

We deliberately do not nuke the user's config or secrets in ~/.config/mcp-manager/. The principle is "uninstall the program, preserve the data." Users who want a clean reset can run mcpm self-uninstall --purge for the kitchen-sink variant — which asks "Are you sure? Y/N" with no default. Even --purge never touches ~/Library/Keychains or libsecret; secrets stay where the OS put them and the user can remove them via OS-native UI.

There is no separate uninstall.sh. The uninstaller lives inside the mcpm binary because (a) it has access to the install manifest, (b) it can use the same Rust code that wrote the launchd plist to remove the launchd plist, (c) it's one fewer signed shell script to maintain. If the user has lost their mcpm binary somehow, they can re-run install.sh and then uninstall — install.sh is idempotent.

Service-string namespace decision

Reverse-DNS, locked: dev.mcp-manager.mcpmanagerd for the launchd label and macOS subsystem id; mcpmanagerd for the systemd-user unit name (systemd doesn't use reverse-DNS by convention). The project domain mcp-manager.dev is owned; the reverse is unambiguous; it does not collide with com.modelcontextprotocol or anything Anthropic-shaped. Audit logs and tracing subsystems use the same reverse-DNS identifier.

mdbook docs hosting

Docs live at docs/ in the repo as mdbook source. mdbook build in CI produces book/; GitHub Pages (or Cloudflare Pages) serves it at https://mcp-manager.dev/docs/. The installer's "next:" message links to it. Docs are versioned per release — /docs/v1.0/, /docs/latest/ redirects to current. mdbook is the right choice because it's Rust-native, it ships a built-in search, and the output is fully static (no JS framework dependency, no CDN — matches the project's no-CDN constraint).

SBOM + supply-chain summary

  • Per release: mcp-manager-1.0.0.spdx.json via syft, generated from the Cargo.lock + the build environment.
  • SHA256SUMS covers every tarball + the SBOM + install.sh itself.
  • SHA256SUMS.minisig via minisign with the baked-in pubkey.
  • SHA256SUMS.sig via cosign-keyless (Sigstore) as a parallel verification path; rekor transparency log entry recorded.
  • macOS binaries notarized (Apple Developer Program); stapled-ticket inside the tarball so first-run works offline.
  • Reproducible-build attestation (SLSA L3 target): provenance attached via GitHub's attest-build-provenance.

Cross-platform completeness

Four release tarballs cover the v1.0 surface: macOS x86_64, macOS aarch64, Linux x86_64-gnu, Linux aarch64-gnu. We do not ship musl-static Linux tarballs in v1.0 — glibc is fine, our Rust binaries link the system libc dynamically, but everything else is statically linked. If users on truly minimal systems (Alpine without glibc compat) need musl, that's a v1.1 add. Windows is never. (Locked.)
