The Distro Packager's DevOps

Curl and Nix are locked. Fine. But "we ship a tarball" is not a distribution strategy — it's a TODO list. This deep dive is about the standards that every binary on a Linux box is judged against: FHS, XDG Base Directory, systemd unit semantics, deb and rpm policy. And the equivalent rigor for macOS: launchd, reverse-DNS, and the sandbox-shaped holes Apple drilled into /usr/local. The product promises a clean uninstall. That promise is half the work.

Thoughts — the packager's worldview

I have built deb, rpm, and Arch packages for a living. The fastest way to lose a packager's trust is to invent your own filesystem layout. The second fastest way is to leave files behind when the user removes you. The third fastest way is to lie about what state you own.

MCP Manager arrives in the world with two distribution channels — curl … | sh and a Nix flake — and the explicit rejection of Homebrew, the Apple App Store, and (implicitly, for now) deb/rpm. That is a defensible starting position; it is not a finishing position. Real Linux distributions ship rolling kernels, audited package managers, dependency graphs, and an expectation that an installable thing follows the rules. If MCP Manager wants Debian, Ubuntu, Fedora, RHEL, and Arch users to feel at home — and we do, because that is where the developers we are courting actually live — then the curl path must still produce a file layout that those users recognise. And we must leave room for distro maintainers (Debian DPL, Fedora packagers, Arch TU) to package us downstream without rewriting our install logic.

The Filesystem Hierarchy Standard, version 3.0, gives us the answer for almost every file we will ever write. Binaries go in /usr/local/bin (curl-installed, "local to this host") or /usr/bin (when a distro packager picks us up). State that survives reboots goes in /var/lib for system services, but we are a user daemon, so it goes in $XDG_STATE_HOME — defaulting to ~/.local/state. Configuration goes in $XDG_CONFIG_HOME — defaulting to ~/.config. Cached, recomputable data goes in $XDG_CACHE_HOME — defaulting to ~/.cache. Runtime sockets and PID files go in $XDG_RUNTIME_DIR — typically /run/user/$UID on modern systemd-logind systems, tmpfs-backed, cleared on logout. Manpages go in share/man/man1 (for the user-facing CLI) and share/man/man5 (for the config-file format).

Curl-installer-defender will object that this is more complexity than the MVP needs. They are wrong. The XDG variables are eight lines of code in a shell installer; the FHS path mappings are a fifteen-line lookup table. The payoff is that every reasonable Linux tool — from git to rustup to direnv — already obeys these conventions, and our users will notice if we do not.

Then there is macOS. Apple does not have FHS; Apple has the "macOS File System Hierarchy" with /Applications for GUI apps, /Library/LaunchDaemons and /Library/LaunchAgents for system services, and a strong cultural preference for reverse-DNS bundle IDs everywhere a name appears: keychain services, launchd labels, group containers. Homebrew has trained two generations of macOS developers that /usr/local/bin is fine for command-line tools — but System Integrity Protection made /usr/local writable only outside the sealed system volume, and on Apple Silicon Homebrew quietly moved its prefix to /opt/homebrew. Since we have banned Homebrew, we have to decide our own prefix. My recommendation in §design: install to /usr/local/bin on both macOS and Linux for the curl path (with a --prefix escape hatch), launchd label dev.mcp-manager.mcpmanagerd, systemd unit mcp-manager.service for the user instance. That is the principle of least surprise on each platform.

The last piece of my worldview is uninstall correctness. If mcpm uninstall says it removed the daemon, it had better have removed the daemon — including the launchd plist, the systemd user unit, the socket file, the audit log, the cached registry indexes, the trust manifest, and the keychain entries (with confirmation, because those are user secrets). The way you guarantee this is not by hoping — it is by maintaining an install manifest: every file you have ever written is enumerated with absolute path, hash, and creation timestamp, and uninstall walks that manifest. Debian's dpkg --listfiles is the gold standard. We should match it.

Arguments with the 4 peers

vs curl-installer-defender — "the installer is 60 lines of bash, don't ruin it"

Their pitch: the curl installer should be ruthlessly simple. Detect arch, download tarball, verify signature, extract to /usr/local/bin, print "next steps". Sixty lines of POSIX shell. Anything more is enterprise-y rot.

I do not disagree with the bones of this. I disagree that "minimal" excuses "wrong". The curl installer must do four things that curl-installer-defender's sketch elides:

  1. Respect $XDG_* env vars when present, fall back to the documented defaults when not. This is two additional lines: : ${XDG_CONFIG_HOME:=$HOME/.config} and similar.
  2. Write an install manifest to $XDG_STATE_HOME/mcp-manager/install.manifest: every file that the installer dropped on disk, with its absolute path and sha256. mcpm uninstall reads this manifest. Without it, "clean uninstall" is a lie.
  3. Be idempotent. Re-running the installer must not duplicate manpages, must not stack a second PATH entry in shell rc files, must not leave a half-written binary. The recipe: write to a tempfile adjacent to the target, then mv (atomic rename, POSIX guarantees no torn file).
  4. Detect previously-installed mcpm at a non-default prefix. If we have an install manifest saying mcpm lives in /opt/mcpm and the user re-runs the installer with no --prefix, we must either honor the previous prefix or print a loud warning. Silent side-by-side installs are how users end up with three copies of a binary on their PATH.

None of this is enterprise rot. It is the difference between an installer that works and one that we will be apologising for in GitHub issues for the next two years. curl-installer-defender can win on ergonomics — yes, we should keep the curl pipe short and the prompt count low — but the installer's output still has to satisfy a packager's audit.

vs nix-purist — "you don't need FHS if you have Nix"

Their argument is correct for their users. Nix users live in /nix/store/<hash>-mcp-manager-1.0.0/ and that is fine. Nixpkgs has a recommended layout for derivations and we will follow it: a single derivation building the workspace, separate outputs for the daemon and the CLI, manpages under $out/share/man.

The problem is that ≥ 95% of our target users are not on NixOS. They run Ubuntu, Pop!_OS, Fedora Workstation, Arch on a ThinkPad, or macOS. For them, Nix is a tool they have heard of, not one they use. The FHS layout is what the underlying OS expects; the XDG vars are what their other dev tools obey. Telling them "just install Nix first" is a 700 MB onboarding tax that loses us most of the market.

Where I agree with nix-purist is on reproducibility. The release pipeline must produce bit-identical artifacts from a clean checkout. We use cargo build --locked --release with --remap-path-prefix to scrub build-host paths from the binary, and we publish the SLSA provenance attestation alongside each release. The Nix flake is the reference reproducible build; the tarball we curl-install is verified against the flake's output hash in CI.

vs sre-hawk — "where are the metrics, where is the on-call runbook"

sre-hawk will ask: how does the on-call know mcpmanagerd is healthy? Where does it emit metrics? What is the log volume budget? They will want Prometheus, OpenTelemetry, structured JSON logs to stdout, journald integration on Linux, unified-log integration on macOS.

Half of this is deferred to v1.1 by the lockdown. No Prometheus, no OTLP. Fine. But on the distro side I can give sre-hawk two things for free:

  1. journald integration on Linux. If we are running under systemd-user (which is the recommended deployment), our stdout/stderr is automatically captured by journald and tagged with our unit name. The on-call runs journalctl --user-unit=mcp-manager.service and gets timestamped, filterable, persistable logs for free. We need to ensure our tracing-subscriber formatter emits machine-readable JSON when $JOURNAL_STREAM is set, and human format when not. Six lines of Rust.
  2. unified-log integration on macOS. Same trick: log show --predicate 'subsystem == "dev.mcp-manager"'. We use the OSLog framework via the oslog crate to emit structured events that Console.app can filter.

These cost nothing — we are emitting the logs anyway — and they let sre-hawk stop screaming about observability for v1.0. The Prom endpoint can wait.

vs supply-chain-sec — "minisign and cosign and SBOMs, oh my"

supply-chain-sec wants signed artifacts (we have that with minisign on tarballs and Apple notarization on macOS binaries), they want SBOMs (we should generate CycloneDX or SPDX as part of the release pipeline), and they want a Sigstore transparency log entry per release.

We agree on all three. My contribution as a distro packager: the package metadata files themselves are partial SBOMs. A deb's control file lists dependencies; an rpm's %files + %requires sections list every file and every linked library; an Arch PKGBUILD's depends array gives the same. When a packager-downstream user runs dpkg -L mcp-manager or rpm -qV mcp-manager, they are pulling our SBOM out of the package format itself. Even though we are not shipping deb or rpm directly in v1.0, the cargo-deb / cargo-generate-rpm / cargo-aur recipes should be in the repo so downstream maintainers can build packages from cargo install-ready source with one command.

For the curl path: alongside the release tarball, publish a mcp-manager-1.0.0.cdx.json CycloneDX SBOM generated by cargo cyclonedx. Reference it from a Provenance: field in the GitHub Release notes. That gets us supply-chain-sec's minimum bar without a new build dep.

Design — paths, units, recipes, uninstall

FHS / XDG path table

Every file MCP Manager writes to disk maps to one of these locations. The "macOS equivalent" column shows where the same purpose lands on Apple systems — not different code paths in the daemon, but different defaults the same XDG-aware code resolves to.

Purpose Linux (curl install) Linux (distro pkg) macOS XDG var
mcpm binary /usr/local/bin/mcpm /usr/bin/mcpm /usr/local/bin/mcpm —
mcpmanagerd binary /usr/local/libexec/mcp-manager/mcpmanagerd /usr/libexec/mcp-manager/mcpmanagerd /usr/local/libexec/mcp-manager/mcpmanagerd —
Manpages (CLI) /usr/local/share/man/man1/mcpm.1 /usr/share/man/man1/mcpm.1 /usr/local/share/man/man1/mcpm.1 —
Manpages (config formats) …/share/man/man5/mcp-manager.toml.5 …/share/man/man5/mcp-manager.toml.5 …/share/man/man5/mcp-manager.toml.5 —
Shell completions (bash) /usr/local/share/bash-completion/completions/mcpm /usr/share/bash-completion/completions/mcpm /usr/local/etc/bash_completion.d/mcpm —
User config ~/.config/mcp-manager/config.toml ~/.config/mcp-manager/config.toml ~/.config/mcp-manager/config.toml $XDG_CONFIG_HOME

Two design notes on this table. First, mcpmanagerd goes in libexec, not bin — it is invoked indirectly via the mcpm CLI's auto-spawn flow and via the service manager, not directly by humans. The FHS specifically calls out libexec for "binaries run by other binaries". Second, the macOS UDS socket lives under ~/Library/Application Support/mcp-manager/ because $XDG_RUNTIME_DIR is not standard on macOS and /var/run/user/$UID/ does not exist. ~/Library/Application Support is Apple's official location for app-private state.

Service-string namespace decision

systemd: mcp-manager.service (no reverse-DNS prefix). Systemd's convention follows package-name conventions — git ships git-daemon.service, docker ships docker.service. A reverse-DNS prefix in the unit name would look weird and break tab-completion. The PartOf / Documentation / WantedBy fields encode our project identity; the unit name encodes the user-facing noun.

launchd: dev.mcp-manager.mcpmanagerd (reverse-DNS, lowercase). launchd's Label key is a global namespace; collisions are real. Apple's documentation explicitly recommends reverse-DNS for the same reason application bundle IDs use it. Picking dev.mcp-manager as our DNS root (rather than e.g. com.mcpmanager) signals project-not-corporation; the .mcpmanagerd suffix matches the binary name.

Keychain service: dev.mcp-manager.mcpmanagerd on macOS and the matching libsecret schema name on Linux. Consistent across platforms makes the secrets-lifecycle audit log readable; matching the launchd label means a single grep over log show output traces both daemon events and keychain access events.

systemd unit (Linux user instance)

The unit is a user-level unit (lives in ~/.config/systemd/user/ or /usr/lib/systemd/user/), not system-level. MCP Manager manages your dev environment; it does not need root and must never run as root. Use socket activation so the daemon starts only when something actually connects. 

# mcp-manager.service
# User-instance systemd unit. Install to ~/.config/systemd/user/
# Enable with: systemctl --user enable --now mcp-manager.socket

[Unit]
Description=MCP Manager daemon (mcpmanagerd)
Documentation=man:mcpmanagerd(1) https://mcp-manager.dev/docs/
After=default.target
PartOf=mcp-manager.service

[Service]
Type=notify
NotifyAccess=main
# Path to the daemon binary, started by systemd:
StartCommand=/usr/local/libexec/mcp-manager/mcpmanagerd --systemd
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s

# Security hardening (see systemd.exec(5))
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=read-write
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK
RestrictNamespaces=true
LockPersonality=true
MemoryDenyWriteExecute=false  # tokio JITs nothing, but rmcp may
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM

# Resource limits (per the v1.0 NFR table)
MemoryHigh=512M
MemoryMax=1G
TasksMax=512

# State / log paths
Environment=XDG_STATE_HOME=%h/.local/state
Environment=XDG_CACHE_HOME=%h/.cache
Environment=XDG_CONFIG_HOME=%h/.config

[Install]
WantedBy=default.target

Note: StartCommand= in the example above is a stand-in for the real systemd directive (the one whose name begins with Ex) — the same name pattern used by other process-launch directives in the unit vocabulary. See systemd.service(5) for the canonical spelling.

And the companion socket unit for socket activation:

# mcp-manager.socket
# Socket-activated startup. Daemon is launched on first connect; idles out
# back to inactive when refcount-and-idle-timer says so.

[Unit]
Description=MCP Manager UDS socket
PartOf=mcp-manager.service

[Socket]
ListenStream=%t/mcp-manager/mcpmanagerd.sock
SocketMode=0600
DirectoryMode=0700
RemoveOnStop=true
PassCredentials=true     # we use SO_PEERCRED in-process

[Install]
WantedBy=sockets.target

%t resolves to $XDG_RUNTIME_DIR (typically /run/user/$UID); %h to the user's home. Socket activation means: the user runs systemctl --user enable --now mcp-manager.socket; systemd creates the socket; on first connect systemd starts the daemon; mcpmanagerd receives the listening fd via sd_listen_fds() (the --systemd flag tells our code to pick that up instead of calling bind() ourselves). When the daemon's idle timer fires, it exits cleanly; systemd holds the socket open and re-activates next time. No "always on" RAM cost for a user who isn't actively using MCP servers.

launchd plist (macOS user agent)

The macOS equivalent: a LaunchAgent (not LaunchDaemon — agents run as the user, daemons run as root). Install location is ~/Library/LaunchAgents/dev.mcp-manager.mcpmanagerd.plist; launchctl bootstrap gui/$UID registers it. 

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>dev.mcp-manager.mcpmanagerd</string>

  <key>ProgramArguments</key>
  <array>

    <string>--launchd</string>
  </array>

  <!-- Socket-activated equivalent on macOS: launchd creates the socket
       and passes its fd via LAUNCH_DAEMON_SOCKET_NAME. -->
  <key>Sockets</key>
  <dict>
    <key>Listener</key>
    <dict>
      <key>SockPathName</key>
      <string>/Users/USERNAME/Library/Application Support/mcp-manager/mcpmanagerd.sock</string>
      <key>SockPathMode</key>
      <integer>384</integer>  <!-- 0600 octal -->
      <key>SockFamily</key>
      <string>Unix</string>
    </dict>
  </dict>

  <!-- Launch on demand from the socket, not at login. -->
  <key>RunAtLoad</key>
  <false/>
  <key>KeepAlive</key>
  <false/>

  <!-- Resource limits -->
  <key>SoftResourceLimits</key>
  <dict>
    <key>NumberOfFiles</key>
    <integer>1024</integer>
  </dict>

  <!-- Logging: unified log via OSLog crate. These paths catch only
       early-startup output before the OSLog handler is wired. -->
  <key>StandardOutPath</key>
  <string>/Users/USERNAME/Library/Logs/mcp-manager/mcpmanagerd.stdout.log</string>
  <key>StandardErrorPath</key>

</dict>
</plist>

The USERNAME token is templated at install time — mcpm's service-registration code reads $HOME and substitutes. The plist must be re-templated on mcpm uninstall only to locate the file for removal; installs themselves should write the resolved-absolute-path version.

Build & release pipeline

Four artifact streams produced from a single tagged release, in a single GitHub Actions workflow:

  1. Tarballs (curl-installer payload). cargo build --locked --release --target $TARGET for each of the four targets, then bundle bin/ + libexec/ + share/man/ + share/bash-completion/ into a tarball with the FHS structure baked in. Sign with minisign. Publish to GitHub Releases.
  2. deb recipes via cargo-deb. The [package.metadata.deb] table in the binary crates' Cargo.toml declares assets (the same FHS layout, but rooted at /usr/ instead of /usr/local/), maintainer-scripts (postinst registers the systemd user unit; prerm unregisters), and Depends: line. cargo deb --target x86_64-unknown-linux-gnu --no-build consumes the already-built binaries. We do not upload the .deb to an apt repo in v1.0; we ship it as a release artifact so downstream packagers (Debian, Ubuntu) can use it as a starting point.
  3. rpm recipes via cargo-generate-rpm. The [package.metadata.generate-rpm] table defines %files, scriptlets, and Requires:. Same philosophy: ship .rpm as a release artifact; let Fedora packagers upstream it.
  4. Arch PKGBUILD. We hand-maintain a pkg/PKGBUILD in the repo (Arch's cargo-aur tool is fine but more friction than just writing twenty lines of PKGBUILD). On release we run a step that bumps pkgver, computes sha256sums against the tarball, and pushes to the AUR repo (aur.archlinux.org/mcp-manager.git). This is the only downstream channel we maintain ourselves — AUR has no gate and the Arch community expects the upstream to keep the PKGBUILD warm.

All four streams are produced from the same source commit and the same already-built binaries; we never recompile per package format. Reproducible build flags (--remap-path-prefix, SOURCE_DATE_EPOCH) are set in the workflow. Each artifact ships with an SBOM (CycloneDX JSON) generated by cargo cyclonedx and a SLSA provenance attestation.

Code signing per platform

  • macOS: hardened-runtime build, signed with Developer ID Application certificate, notarized via notarytool, stapled. The curl installer verifies the notarization ticket on extract; the user can also right-click → Open without the Gatekeeper scare on first run.
  • Linux tarballs: minisign signature on the tarball and on SHA256SUMS. Public key baked into the installer script and documented at https://mcp-manager.dev/release-key.pub.
  • Linux .deb: if/when we publish to an apt repo (v1.1+), sign the repository's Release file with GPG and the .deb files themselves with debsign. For v1.0 we ship the .deb unsigned-as-a-deb but signed-as-a-tarball-equivalent via minisign on the SHA256SUMS file.
  • Linux .rpm: sign with GPG via rpmsign; the public key is at the same URL as the minisign key.
  • Touch ID on macOS: deferred to v1.1 per the lockdown (best-effort in v1.0). When implemented, the keychain ACL on each secret entry will require kSecAttrAccessibleWhenUnlockedThisDeviceOnly plus kSecAttrAccessControl with biometryAny.

Update mechanism

v1.0 does not ship a self-updater. Users update the same way they installed:

  • Curl path: curl -sSf https://mcp-manager.dev/install.sh | sh re-run.
  • Nix: nix profile upgrade mcp-manager or nix flake update.
  • Downstream deb/rpm: apt upgrade / dnf upgrade / pacman -Syu.

The installer detects in-place upgrades (manifest exists, version differs), calls mcpm daemon stop via the existing UDS socket if the daemon is running, replaces the binary atomically, and prints "restart with systemctl --user restart mcp-manager.socket (or launchctl kickstart -k gui/$UID/dev.mcp-manager.mcpmanagerd)".

A future mcpm self update subcommand (v1.1) maps to Renovate's vocabulary — major/minor/patch — using the same classification we already do for MCP servers per Agent D's versioning recommendation.

mdbook docs hosting

The mdbook source lives in docs/ in the repo. Build with mdbook build in CI; publish to https://mcp-manager.dev/docs/ via GitHub Pages or Cloudflare Pages (no telemetry; static hosting). The published manpages link back to the relevant docs chapter via the SEE ALSO section. The installer's "next steps" output points at the docs URL. Don't ship a second docs build process for downstream packagers — they will use the upstream URL.

Uninstall enumeration spec

The contract for mcpm uninstall: on completion, no file written by mcpm or by mcpmanagerd remains on disk, no service-manager registration remains, no PATH entry remains. The audit log is preserved by default (it is user data) but removed if the user passes --purge. Keychain entries are removed only on --purge and require an interactive confirm.

The enumeration:

PhaseWhat we removeSource of truth
1. Stop the daemon Send daemon.stop via UDS; wait up to 10s; SIGTERM the pid; wait 5s; SIGKILL. Then close the socket. UDS connect / PID file
2. Unregister from service manager Linux: systemctl --user disable --now mcp-manager.socket mcp-manager.service; remove the unit files. macOS: launchctl bootout gui/$UID/dev.mcp-manager.mcpmanagerd; remove the plist. Service-manager presence check
3. Remove on-disk artifacts Every file listed in $XDG_STATE_HOME/mcp-manager/install.manifest. Includes binaries, manpages, completions, unit files, plist files. Install manifest written by installer
4. Remove projected configs For each editor in ~/.config/mcp-manager/projection.lock: open the editor's config file, strip the managed-block fenced region (between the # BEGIN mcp-manager and # END mcp-manager markers), write back. Never touch unmanaged content. projection.lock
5. Remove cache + state (optional, on --purge) ~/.cache/mcp-manager/, ~/.local/state/mcp-manager/ (including audit log). XDG path conventions
6. Remove user config (optional, on --purge) ~/.config/mcp-manager/. XDG path conventions
7. Remove keychain entries (optional, on --purge, interactive confirm) Every entry under service dev.mcp-manager.mcpmanagerd on macOS / libsecret schema on Linux. Enumerate via SecItemCopyMatching / libsecret search
8. Remove PATH entries If installer added /usr/local/bin to a shell rc file (only does this if it was missing), reverse that edit by looking for the fenced block we wrote. Otherwise no-op. install manifest's shell-rc edit record
9. Verify clean Re-scan all of the above locations; if any expected-removed file remains, exit non-zero with a list. This is the test-suite assertion that proves the contract. self

The packaged versions (deb / rpm / Arch) don't need this manifest — the package format already tracks every file. dpkg -L mcp-manager or rpm -ql mcp-manager or pacman -Ql mcp-manager is the manifest. So mcpm uninstall first checks: "am I package-managed?" If yes, it refuses with "use apt remove / dnf remove / pacman -R instead." That is the single most important sentence on this page. We must not double-uninstall a package-managed copy.

Manpages

Every subcommand of mcpm gets a manpage in section 1. The config-file formats (config.toml, .mcp-manager.toml, trust.toml, lockfile) get manpages in section 5. We generate from clap's clap_mangen in a build script (build.rs) — no hand-written nroff. The config-file manpages are hand-authored markdown converted to nroff via pandoc -s -t man in CI.

The recipes-in-tree posture is deliberate. We are not asking ourselves to maintain an apt repo (signing, hosting, mirroring — all real work). We are asking ourselves to make it trivial for a downstream maintainer to do that work. cargo deb --no-build and cargo generate-rpm run in eight seconds from a clean tarball. Anyone who wants an apt repo can stand one up over an afternoon.

The principle in one paragraph

MCP Manager v1.0 ships via curl + Nix, but every file it places on disk respects the conventions that every other tool on the user's machine respects. FHS for system paths, XDG for user paths, reverse-DNS on macOS, plain-package-name on systemd, install manifest as ground truth, uninstall walks the manifest. Downstream packagers get cargo deb/cargo generate-rpm/PKGBUILD recipes in-tree so they can ship us through their channels with zero upstream coordination. We do not pretend to ship every package format ourselves; we make sure we are shippable in every package format.
