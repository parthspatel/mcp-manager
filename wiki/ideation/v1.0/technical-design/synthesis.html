Preamble — how to read this

MCP Manager v1.0 was specified in three layers of increasing detail:

  1. The v1.0 hub — a 20-row locked-decisions table and the in/out/never scope.
  2. The audience-facing product overview, technical design, and UX design — engineer-facing source of truth.
  3. This sub-wiki — five facets (backend, frontend, devops, security, UX), five stances per facet debating, five facet overviews picking winners, and this document consolidating everything across facet boundaries.

The v1.0 spec said what. The facet overviews said how. This synthesis says how across facet boundaries, where one facet's choice constrains another's. It is the document the implementation team should read after the v1.0 spec — and the document that will be cross-checked against the eventual Cargo workspace at every milestone.

Where you see a citation like backend/overview.html#decisions, that is the per-facet synthesis. Where you see backend/agent-tokio-pragmatist.html#design, that is the underlying stance essay whose argument carried that decision. Anchors point to specific reasoning, not whole pages.

Locked v1.0 inputs were treated as inputs by all 25 agents and remain inputs here. No decision in this synthesis re-opens the lockdown. Where the synthesis recommends a change to a v1.0 detail (never a v1.0 lock), it shows up in the Diffs section.

Per-crate deep dive

Eleven crates in the mcpm-* workspace, in dependency order. Each section gives a responsibility statement, a public-API sketch, internal modules, dependencies, test strategy, and any crate-local open questions. Crate-by-crate, this is the implementation contract.

mcpm-core

Responsibility: Config schemas, validation, CAS guard, canonical-JSON hashing, the sans-I/O slices of the supervisor's and projector's state machines. mcpm-core never opens a socket and never spawns a process; it manipulates bytes.

Public API sketch: UserConfig, ProjectConfig, LockfileEntry, TrustFile, AuditRecord, ServerSpec, ProcessKey, plus the supervisor's ServerState / Event / Action trio, plus the projector's compute_managed_block pure function. Validation methods return Result<Validated<T>, ValidationError> using thiserror.

Internal modules: config (TOML schemas + parsers), canonical (RFC 8785 canonical-JSON for hashing — used by CAS, trust.toml pinning, and audit-log hash chain), cas (the prior_hash guard), state (supervisor state machine), projection (managed-block compute).

Dependencies: serde, serde_json, toml, sha2, thiserror. No tokio. No I/O.

Test strategy: property-tested with proptest on the supervisor step(), classify_exit(), and next_delay() functions (backend synthesis ratified this); golden-file tests on TOML serialization round-trips; canonical-JSON conformance vectors against the RFC 8785 test suite.

mcpm-daemon

Responsibility: The mcpmanagerd binary's main; the JSON-RPC server over UDS; the tower middleware stack; lifecycle (boot, auto-spawn race, graceful drain); the per-process signal handlers; the dedicated OS thread that owns the cgroup-v2 memory.events reactor.

Public API sketch: Binary crate. Internal-only types (HandlerCtx, PeerCred, layer types). The wire surface is mcpm-protocol.

Middleware stack (in order, per the backend synthesis): PeerCredAuthLayer → TraceLayer → AuditLayer → ConcurrencyLimitLayer → handler. Four layers, deliberately capped; future "free middleware" is rejected by default.

Lifecycle:

  1. Parse argv (almost none); read user config; validate.
  2. Bind UDS at $XDG_RUNTIME_DIR/mcpmanagerd.sock (Linux) or ~/Library/Application Support/mcp-manager/mcpmanagerd.sock (macOS); O_EXCL bind plus sibling flock(2) to detect stale sockets.
  3. If running under systemd-user with socket activation, accept the listen fd from sd_listen_fds() instead; same for launchd via launch_activate_socket().
  4. Spawn the OOM-watch OS thread (Linux only; macOS path is different — see supervisor).
  5. Install signal handlers (SIGTERM, SIGINT, SIGHUP, SIGCHLD) — tokio's signal::unix where it suffices; raw signalfd only for SIGCHLD draining per the kernel-hacker.
  6. Call sd_notify(READY=1) (systemd-user) or no-op (launchd); enter the accept loop wrapped in the tower stack.
  7. On shutdown signal, root CancellationToken fires; graceful drain with 5s deadline; SIGTERM children, SIGKILL on overrun.

Auto-spawn race: documented under TUI startup flow. flock(2) on a sibling lockfile; 5-second timeout; stale-socket recovery treats ECONNREFUSED the same as ENOENT but audit-logs at higher severity.

Dependencies: tokio (rt-multi-thread + macros + signal + fs + io + net + process + sync + time), tower, tracing, tracing-subscriber, serde_json, nix, mcpm-core, mcpm-protocol, mcpm-supervisor, mcpm-registry, mcpm-secrets, mcpm-projector, mcpm-logs, mcpm-trust.

Test strategy: integration tests spawn the daemon in a tmpdir under a tokio test runtime; the library-author's spawn-in-tmpdir pattern is canonical. Tower stack also testable directly without UDS (call Service::call on the constructed stack).

mcpm-protocol

Responsibility: Wire types and method constants. The smallest, most stable crate in the workspace. No business logic; no I/O; ideally no tokio.

Public API sketch: Per-method request/response types (e.g., ServerListRequest / ServerListResponse); the streaming method sentinel (LogLine::lagged(n)); the method module with pub const SERVER_LIST: &str = "server.list" for each of the ~30 methods; a WIRE_VERSION constant.

Discipline (per the backend synthesis adopting the library-author's rules verbatim):

  • #[non_exhaustive] on every public enum and struct.
  • #[serde(default)] on optional params; do NOT use deny_unknown_fields (forward-compat asymmetry from the pragmatist).
  • Sealed traits for things only the daemon should implement (reserved but unused in v1.0).
  • cargo-semver-checks is a hard CI gate on this crate only.
  • Crate version starts at 0.1.0 and stays 0.x through v1.2-ish of the binary, then graduates to 1.0.0 when the surface stabilizes.

no_std + alloc profile: ship from v1.0 per open question OQ-B-5 leaning yes. One feature flag (std, default-on); a cargo hack check --each-feature CI job. Cost is small; protects future FFI/PyO3/WASM consumers.

Dependencies: serde, serde_json only. No tokio.

Test strategy: JSON conformance vectors (parse and re-emit); semver-check gate; check that std::collections doesn't accidentally appear in any public type when the std feature is off.

mcpm-client

Responsibility: In-tree Rust client library over mcpm-protocol. Provides Client::connect(), the auto-spawn dance, streaming method helpers, and thin retry wrappers. Used by mcpm-cli, the TUI app, and (eventually) third-party integrations.

Public API sketch: One Client struct with one method per RPC. Streaming methods return impl futures::Stream<Item = Result<LogLine>>. Re-exports mcpm_protocol as wire for ergonomics.

Stability disclaimer: Crate-level rustdoc says "not stable across minor versions; third parties wanting a stable surface depend on mcpm-protocol." publish = true at 0.x so docs.rs renders, but the README banner and the doc warning are prominent. (Per OQ-B-1 leaning publish-with-disclaimer.)

Auto-spawn dance: flock(2) on $XDG_RUNTIME_DIR/mcpmanagerd.spawn.lock with LOCK_EX | LOCK_NB to prevent thundering-herd; fork+ exec the daemon if we win the lock; poll UDS for up to 5s with 50ms sleeps; give up with E_DAEMON_UNREACHABLE if the daemon never appears. Daemon binary lookup is which mcpmanagerd via $PATH — no Nix-vs-curl branching (devops synthesis).

Dependencies: tokio, serde_json, thiserror, mcpm-protocol, nix.

Test strategy: integration tests; mocks via constructing a tower service and calling it directly without UDS (faster, more granular).

mcpm-supervisor

Responsibility: Process lifecycle. Spawning, supervising, restarting, OOM-classifying, idle-stopping, singleton-refcounting, descendant-lifetime-guaranteeing. The single most complex crate.

Architecture: veteran's sans-I/O core + pragmatist's JoinSet/CancellationToken shell + kernel-hacker's platform module. Sans-I/O core lives in mcpm-core::state; the supervisor crate is the I/O shell.

Public API sketch: Supervisor::new(config) -> Self, Supervisor::start(&mut self, key: ProcessKey) -> Result<()>, Supervisor::stop(&mut self, key, grace: Duration), Supervisor::status(&self, key) -> ServerStatus, Supervisor::events(&self) -> broadcast::Receiver<SupervisorEvent>.

The sub-decisions table (verbatim from backend synthesis, summarized):

Test strategy: proptest on the three sans-I/O pure functions; integration tests that spawn fake-MCP binaries from a fixture directory. Skip the crash-equivalence property test (per OQ-B-2; deferred to v1.1).

mcpm-registry

Responsibility: Index fetch, signature verification, package install, version pinning, search. Three default registry implementations behind a sealed trait.

Public API sketch: Registry::search(query, limit) -> Vec<PackageHit>, Registry::resolve(spec, want) -> ResolvedPackage, Registry::download_and_verify(resolved, dest_dir) -> VerifiedTarball, Registry::list_installed() -> Vec<InstalledPackage>.

RegistrySource trait: sealed in v1.0 (per OQ-B-6 lean; unsealing is non-breaking, so we can revisit at v1.1). Three concrete impls: OfficialRegistry, GitHubRegistry, DockerCatalogRegistry.

Source URI shape: The TOML table form with string-sugar fallback is locked in the v1.0 spec. The crate parses both into the same internal SourceUri struct.

Search: hand-rolled BM25 over the cached index (~100 LoC per the boring-tech-defender); we do not pull tantivy for a corpus of a few thousand entries.

Network: reqwest with rustls (no OpenSSL). Stale-while-revalidate semantics with an explicit freshness field per the veteran; never silently serve stale.

Verification ordering: minisign-verify BEFORE temp-file rename(2); cosign-when-present required for Docker MCP Catalog packages with Rekor inclusion proof (per the security synthesis).

Dependencies: reqwest, rustls, minisign-verify, optional cosign-verify (feature-flag), serde, tracing, mcpm-core, mcpm-trust.

mcpm-secrets

Responsibility: Secret storage with the layered store. Ships the SecretStore trait from day one even though we have only one concrete implementation in v1.0 — this is the published extension point.

Public API sketch: 

#[async_trait]
pub trait SecretStore: Send + Sync {
    async fn get(&self, r: &SecretRef) -> Result<Option<SecretString>, SecretError>;
    async fn set(&self, r: &SecretRef, v: SecretString) -> Result<(), SecretError>;
    async fn unset(&self, r: &SecretRef) -> Result<(), SecretError>;
    async fn list(&self, scope: &ScopeFilter) -> Result<Vec<SecretRef>, SecretError>;
    /// Default: returns Err(SecretError::Unsupported). v1.1 backends can override.
    async fn rotate(&self, r: &SecretRef) -> Result<(), SecretError> {
        Err(SecretError::Unsupported)
    }
}

#[non_exhaustive]
pub enum SecretRef {
    Named { server: String, name: String },
    // v1.1: VaultPath, OnePasswordItem, BitwardenId, ...
}

Layered chain: EnvVarPassthroughStore first (read-only override for CI), OsKeyringStore second (durable). Reads fall through; writes go to keyring only. Per-server scoping is mandatory: keychain account is dev.mcp-manager.mcpmanagerd/<server>/<name>; a server can only request secrets in its own namespace; cross-server access requires secrets_from = ["other-server.NAME"] in user-scope (never project-scope) per the security synthesis.

macOS Keychain accessibility: kSecAttrAccessibleWhenUnlocked (per the secrets-architect; defended against crypto-pedant's stricter alternative because the threat model is stolen laptop, not remote-with-physical-access). Never kSecSynchronizable; iCloud Keychain sync is non-negotiably off.

Linux Keychain: libsecret (Secret Service); KWallet detected and warned about (lock prompts every session is a UX disaster); explicit refuse-to-write with secret.backend.degraded audit if no backend is reachable, rather than rolling our own keyring file.

In-memory hygiene: secrecy::SecretString through every function signature; zeroize on drop; clippy::disallowed_types bans raw String in this crate. A tracing redaction layer rewrites known-secret field names (token, password, api_key, secret, authorization) to [REDACTED] as belt-and-suspenders. CI fuzz test: write random secret values, grep every emitted log/audit line for a match; build fails if any byte sequence leaks.

Intake paths: TTY via rpassword (reads /dev/tty, never echoes); --from-file, --from-env, --stdin. No --value=...: argv is broadcast to every process on the machine via ps.

Dependencies: secrecy, zeroize, keyring (cross-platform OS-keyring wrapper), rpassword, async-trait, tracing, mcpm-core.

mcpm-projector

Responsibility: Managed-block sync into editor configs (Claude Code, Cursor, Zed, JetBrains XML, VSCode). Stateless per-editor adapters; fenced managed-block semantics; quick-xml for JetBrains XML (DOM-aware, no injection); atomic temp-rename with directory-fsync.

Public API sketch: Projector::list() -> Vec<EditorTarget>, Projector::diff(canonical) -> Vec<PendingChange>, Projector::sync(canonical) -> Result<SyncReport>.

Pure function: compute_managed_block(canonical, current_file, target) -> (NewFileContents, DiffSummary) in mcpm-core::projection. The I/O shell drives tokio::fs.

ProjectionTarget trait: sealed in v1.0 (third-party projection targets are not a v1.0 use case per library-author).

Editor-specific quirks:

  • Claude Code: ~/.claude/settings.json (per-user) and per-project .claude/settings.json. JSON; managed block via comment-fenced JSON impossible; instead we use a top-level "mcpm.managed" key whose value is a JSON object, and we leave the surrounding keys untouched.
  • Cursor: ~/.cursor/mcp.json. Same JSON-top-level-key pattern.
  • Zed: ~/.config/zed/settings.json. Same.
  • JetBrains: ~/Library/Application Support/JetBrains/<product>/options/mcp.xml (or Linux equivalent); XML; quick-xml parses; managed-block fence is an XML comment pair <!-- BEGIN mcpm managed --> ... <!-- END mcpm managed -->; we only edit the slice between fences.
  • VSCode: via the Continue extension at ~/.continue/config.json, JSON-top-level-key pattern.

Atomicity: per backend synthesis: write to tmp in same dir; fsync the tmp file; rename(2); fsync the parent directory; on macOS additionally F_FULLFSYNC on the canonical config path.

Drift detection: on every projection.sync call, compare the current managed block bytes to the canonical-computed bytes. If different, audit-log projection.drift_detected and report in SyncReport; the user sees this in mcpm status as "edited outside" (per the UX synthesis rename from "drifted").

mcpm-logs

Responsibility: Daemon log, per-MCP stdout/stderr capture, audit JSONL, log rotation, the logs.tail streaming API.

Three log streams:

  1. Daemon log (mcpmanagerd's own). Routed to stdout when running under systemd-user or launchd (so journalctl --user-unit mcp-manager --output=json and Apple's unified log Just Work) AND to $XDG_STATE_HOME/mcp-manager/daemon.log as JSONL. Per the devops synthesis.
  2. Per-MCP stdout. Captured to $XDG_STATE_HOME/mcp-manager/servers/<name>.stdout.log with daily rotation.
  3. Per-MCP stderr. Same shape, different file.

Audit JSONL: append-only, single-writer, daily rotation. Per the security synthesis the audit gains a hash-chain: every record carries seq (monotonic per-day) and prev_hash (SHA-256 of the canonical-JSON of the previous record). Day-boundary records cross-reference into the previous day's final record so the chain is unbroken across files. mcpm audit verify verifies; mcpm test --diagnostic includes a chain check.

logs.tail streaming: the daemon uses tokio::sync::broadcast::Sender per stream class. Slow tail-clients see BroadcastStreamRecvError::Lagged(n) and the synthesis surfaces this as a LogLine::lagged(n) sentinel rather than dropping silently per the pragmatist. Single-writer mpsc for audit (blocking backpressure: we must not lose audit lines).

Rotation: rename-then-signal-reopen lossless rotation. Compare UTC date once per minute; rotation grabs the file mutex only to swap the file descriptor. Per the kernel-hacker.

mcpm-trust

Responsibility: The TUF-lite trust manifest. Baked-in root pubkey (ed25519, 32 bytes) PLUS a baked-in revocation-only pubkey (per the security synthesis); fetched trust.toml with 7-day TTL; baked-in-fallback mode for offline; periodic refresh task.

Public API sketch: TrustStore::current(&self) -> TrustView, TrustStore::verify_index(&self, idx, sig) -> Result<()>, TrustStore::verify_package(&self, pkg) -> Result<()>, TrustStore::refresh(&self) -> Result<RefreshOutcome>.

Verifier order: parse → signature verify → now ≥ signed_at − skew → now < expires_at → version > previous_version (monotonic; defends against old-but-valid replay).

Stale-trust policy: fail-soft on read-only ops (mcpm list, mcpm exec); fail-closed on state-changing ops (mcpm install, mcpm update); hard ceiling of expires_at + 30d beyond which nothing verifies. Compromise from the security synthesis tension 1; rejects red-team's strict fail-closed (unworkable for travel) and crypto-pedant's no-ceiling lean.

Algorithm-agility envelope: { "alg": "ed25519", "key_id": "...", "signed_at": ..., "expires_at": ..., "payload_hash": "sha256:9f4e2d...", "payload_hash_alg": "sha256", "sig": "..." }. Static allowlist ["ed25519"] for v1.0; never accept "alg": "none" (the JWT bug class). Per the security synthesis.

Project-config trust gate: the trust key is SHA-256(absolute-path) || SHA-256(canonical-JSON(parsed-TOML)). Moving the repo invalidates the grant; semantic-equivalent re-formatting does not (because we canonical-JSON the parsed TOML, not the raw bytes).

mcpm-cli

Responsibility: The mcpm binary. CLI parsing (clap-derive), 19 subcommands, output formatting, completion generation, manpage generation, the TUI app entry. The only binary the user invokes directly.

Output modes: per the frontend synthesis: --format=human|json|ndjson|yaml|tsv, default human on TTY, auto-degrade to tsv when stdout is not a TTY. Pipe-detection is the auto-default. --plain is an explicit screen-reader-friendly mode (no Unicode glyphs, prose line endings).

Exit codes: aligned with sysexits.h (64-78); each E_* error maps to a specific exit code documented in the runbook. Per the cli-unix-purist.

stdout vs stderr: stdout is data; stderr is chatter. The JSON error envelope goes to stdout (so it can be piped to jq); human prose error messages go to stderr. Progress, spinners, and confirmations always to stderr.

TUI: the TUI app entry. Refuses to start when stdin/stdout isn't a TTY, $TERM=dumb, $CI is set, or --no-tty is passed. Three panes: Servers, Editors, Secrets (the "Toolchains" rename to "Editors" per the UX synthesis). Modifier-free single-key actions, q to quit, ? opens contextual help, Esc universally cancels.

The "20th subcommand" question: resolved by absorbing the doctor flow into mcpm test --diagnostic per the frontend synthesis. The subcommand count stays at 19; the diagnostic output is the row-by-row chain check that the onboarding-novice's transcript proposed.

Dependencies: clap (derive), clap_complete, clap_mangen, ratatui, crossterm, tokio, tracing-subscriber, mcpm-client, mcpm-protocol, mcpm-core.

Per-flow deep dive

The v1.0 spec sketched five end-to-end flows. This section extends each with the synthesis-level detail accumulated above. Where a flow crosses facet boundaries (most do), the synthesis specifies who owns which step.

1. mcpm install <source>

  1. mcpm-cli parses argv; converts a string-sugar URI to the canonical SourceUri table form.
  2. mcpm-client connects (auto-spawns daemon if needed).
  3. mcpmanagerd peer-cred-auths the UDS; tower stack records audit install.start.
  4. mcpm-trust validates the current trust manifest; refuses if stale beyond the 30-day ceiling.
  5. mcpm-registry resolves the spec to a concrete package + version + hash; downloads the tarball; minisign-verifies BEFORE temp-file rename(2); cosign-when-present required for OCI packages with Rekor inclusion proof.
  6. mcpm-core validates the package's manifest; computes prior_hash on the current config.toml; emits the config.put with the CAS guard.
  7. mcpm-projector recomputes the managed block for each editor target; atomically writes; emits projection events.
  8. mcpm-supervisor spawns the server (sandboxed per the isolation mode); injects MCPM_INSTANCE_TOKEN nonce; reports state.
  9. Audit install.complete with the resolved version, content hash, signing key id, and supervisor outcome.
  10. mcpm-cli renders the human-readable summary; on TTY, prints the AHA-moment hint ("Try: ask Claude Code 'what time is it?'" for the bundled demo).

2. mcpm exec <server> -- <tool>

The exec path is the only one the AI-editor SDK invokes directly. Performance-sensitive. Locked end-to-end p99 budget: 50ms.

  1. Client opens UDS (already open if persistent).
  2. Tower stack: SO_PEERCRED check (UID match), trace span, audit exec.start, concurrency limit.
  3. Supervisor looks up the ProcessKey (singleton or per-client); spawns if not running.
  4. Secret resolver builds the env: layered SecretStore resolves each secret; SecretString through the resolver; dropped immediately after execve envp is built.
  5. For containerized isolation modes: --env-file /dev/fd/N from a pipe the daemon writes (per security synthesis). Never argv-injection of secret values.
  6. Spawn (cgroup-attached on Linux; RLIMIT_AS-set on cgroup-v1 or macOS). PR_SET_PDEATHSIG in pre_exec (Linux); sentinel pipe handshake (macOS).
  7. Tool call routes through the spawned MCP server; stdout JSON-RPC response is parsed and re-emitted to the client; audit exec.complete.

3. mcpm secret set <server>.<name>

  1. mcpm-cli opens /dev/tty via rpassword; reads the value without echo.
  2. Client calls secret.set with the SecretRef::Named { server, name }; the value travels as a SecretString serialized into the JSON-RPC payload — the only place plaintext crosses the wire (UDS, 0600, local-only, peer-cred-attested).
  3. Daemon receives; secrets crate writes to keyring with per-server-scoped account dev.mcp-manager.mcpmanagerd/<server>/<name>.
  4. Audit secret.set with the scope (never the value).
  5. CI fuzz test injected random byte sequences; greps audit/log for matches; build fails if any leak.

4. Crash → restart → max-attempts → Crashed

  1. Spawned child exits abnormally (non-zero status, SIGKILL, or jetsam).
  2. Linux cgroup-v2 path: OOM-watch thread reads memory.events; if oom_kill delta > 0, classify as CrashOrOom::Oom { reason: "cgroup-oom-kill" }; mpsc-forward to the supervisor.
  3. cgroup-v1 / macOS path: three-signal heuristic per the kernel-hacker; jetsam-inferred on full conjunction.
  4. Supervisor's pure classify_exit consumes the platform classification + last-RSS + exit signal and emits Event::ChildExited { kind: Crash | Oom | GracefulStop }.
  5. Pure step() consumes the event; if attempt count < attempts_max in window: emit Action::ScheduleRestart { delay: next_delay(...) } and transition to Restarting { attempt }. Else emit Action::TransitionToFailed and transition to Failed { reason }.
  6. I/O shell handles the action: tokio::time::sleep(delay); respawn; audit each transition.
  7. On Failed: mcpm status shows Crashed (user-facing rename per UX synthesis); TUI glyph ⚠; the error envelope's remedy points at mcpm test <name> --diagnostic.

5. TUI startup with auto-spawn race

  1. User runs mcpm (no subcommand).
  2. mcpm-cli checks: is stdin/stdout a TTY? Is $CI set? Is $TERM=dumb? Is --no-tty set? Any "yes" → print help to stderr and exit non-zero.
  3. mcpm-client tries to connect to the UDS. If ENOENT/ECONNREFUSED: try to acquire flock(2) on $XDG_RUNTIME_DIR/mcpmanagerd.spawn.lock non-blocking-exclusive.
  4. Won the lock: fork+exec which mcpmanagerd; release lock; poll UDS for up to 5s with 50ms sleeps.
  5. Lost the lock (another client is spawning): poll UDS for up to 5s.
  6. Connect; tower stack peer-cred-auths.
  7. ratatui initializes; three panes (Servers, Editors, Secrets); status line shows daemon version + connection state.
  8. First-frame paint: every glyph has a one-word screen-reader label; NO_COLOR respected; --plain mode degrades to prose-style.

Per-facet pull-ups

Each facet's net additions to the v1.0 spec, compressed into one paragraph. For full reasoning, follow the link to the facet overview.

Backend — facet overview

Adopts tower middleware (four layers, deliberately capped) for the daemon dispatch; JoinSet+CancellationToken in the supervisor's I/O shell with the pure state-machine core in mcpm-core; dedicated OS thread for the cgroup-v2 OOM reactor (not a tokio task — AsyncFd doesn't surface EPOLLPRI cleanly); raw cgroup pseudo-FS writes (no cgroups-rs); SecretStore trait from day one; sealed RegistrySource and ProjectionTarget for v1.0 (unsealing is non-breaking); no audit-log replay on boot — re-derive state from config.toml.

Frontend — facet overview

Three discrete output modes (TTY default → visual, pipe → TSV, --plain → screen-reader prose); folds mcpm doctor into mcpm test --diagnostic to preserve the 19-subcommand contract; adopts the :-palette + browse-mode TUI command palette dispatching through the same registry as the CLI; status-line + bottom hint bar are non-negotiable discoverability layers; $VISUAL → $EDITOR → vi fallback chain; default TTY palette is green/red with Okabe-Ito and high-contrast as bundled alternatives (revisited on user research).

DevOps — facet overview

Curl + Nix as dual-primary install (byte-identical artifact, CI-enforced); minisign on the tarball envelope (no GPG); cosign-when-present additive for OCI packages with Rekor inclusion proof; reverse-DNS dev.mcp-manager.mcpmanagerd for macOS launchd label, Keychain prefix, libsecret schema; systemd-user socket-activated mcp-manager.service on Linux (bare name, systemd convention); reproducible builds non-negotiable with a build-twice CI gate; AUR PKGBUILD in v1.0, deb/rpm recipes shipped as release artifacts (no apt/dnf repos owned by us); $PREFIX defaults /usr/local on macOS, $HOME/.local on Linux with auto-fallback; SLSA L3 provenance; CycloneDX 1.5 SBOM via cargo-cyclonedx.

Security — facet overview

Per-spawn MCPM_INSTANCE_TOKEN nonce as a layered addition on top of SO_PEERCRED — closes the cross-server-as-same-UID secret-read class; per-server keychain namespacing mandatory; cross-server access requires user-scope secrets_from opt-in (never project-scope); fail-soft on stale trust for read-only ops + fail-closed for state-changing ops + hard 30-day ceiling; algorithm-agility envelope on every signed payload ({alg, key_id, signed_at, expires_at, payload_hash, payload_hash_alg, sig}); audit JSONL gains hash-chain (seq + prev_hash); macOS Keychain kSecAttrAccessibleWhenUnlocked; iCloud Keychain sync forbidden; project-scope cannot request isolation = "none"; sandbox-policy logging at policy granularity (not syscall) with bloom-filter dedupe.

UX — facet overview

Three lucky-day onboarding prompts + a universal preview screen + the post-init three-noun teach (Servers / Editors / Secrets); a bundled zero-secret demo "time" MCP installed by default on mcpm init so the first-launch AHA happens in 60 seconds without secrets or network; four-field error envelope (code / what / why / remedy-as-literal-command) with category field (external / input / internal / refusal); refusal ≠ failure visually (⊘ + amber for refusal; ✗ + red for failure); the "Toolchains" TUI pane renamed to "Editors"; "failed" → "crashed" and "drifted" → "edited outside" in user-facing surfaces (TOML keys unchanged); E_DAEMON_VERSION → E_DAEMON_TOO_OLD as the one code-level rename (no published release ships the old name); local NDJSON event log at $XDG_STATE_HOME/mcp-manager/events.ndjson for self-diagnosis (no telemetry); idle-TTL surfaced as "Auto-stop after N min" in TUI labels (TOML key unchanged); "projection" rename deferred to v1.1 pending local-event data.

Consolidated open questions

Items that the synthesis cannot decide without human judgment, fresh data, or v1.0 alpha feedback. Each is non-blocking. Re-open at v1.1 planning.

  1. OQ-1 (Backend) — Publish mcpm-client to crates.io? Lean publish at 0.x with a "not stable" banner to capture docs.rs benefit. Trade-off: Hyrum's law vs free third-party-experimentation. See backend OQ-B-1.
  2. OQ-2 (Backend) — How aggressive with tracing spans in v1.0? Lean: spans on RPC handler boundaries and supervisor state transitions; not on inner loops or the OOM-watch thread. Defer otel exporter to v1.1. See backend OQ-B-3.
  3. OQ-3 (Backend) — broadcast vs bounded mpsc for logs.tail? Lean: broadcast for stdout/stderr (lossy backpressure correct); bounded mpsc for audit (blocking backpressure mandatory). Already adopted; flagged because a future maintainer may want to revisit. See backend OQ-B-4.
  4. OQ-4 (Frontend) — Default TTY palette? Lean: visual-designer's green/red as default; Okabe-Ito and high-contrast as bundled alternatives. Revisit on user research. See frontend.
  5. OQ-5 (DevOps) — Two-key signing separation? Lean: single key in v1.0 (single-maintainer reality); v1.1 splits into release-signing + trust-manifest-signing. See devops.
  6. OQ-6 (DevOps) — Distro inclusion (deb/rpm) ownership? Lean: we ship recipes in-tree, downstream volunteers own apt/dnf repos. AUR exception (low maintenance burden, no gate). See devops.
  7. OQ-7 (DevOps) — Self-update mechanism for v1.0? Lean: no self-updater in v1.0; users re-run curl install or nix profile upgrade. v1.1 reconsiders if user feedback demands. See devops.
  8. OQ-8 (Security) — TUF timestamp role? Lean: omit in v1.0 (single publisher; envelope's signed_at/expires_at suffices for replay defense); v1.1 adds the timestamp role if we move to threshold signing. See security.
  9. OQ-9 (Security) — fd-passing for secrets? Lean: env-var in v1.0 for every isolation mode (env for level-0-to-2; --env-file /dev/fd/N for containers); fd-passing aspirational for v1.1 once MCPM_SECRETS_FD spec is stable. See security.
  10. OQ-10 (UX) — "projection" rename to "sync" in user-facing surfaces? Lean: defer to v1.1 with local-event data on how often users edit projected files and how often E_PROJECTION_DRIFT fires. See ux.
  11. OQ-11 (UX) — Internationalization beyond English? Lean: v1.0 ships English only with translations-welcome pointer; v1.1 considers a translation file mechanism that doesn't balloon the binary. See ux.
  12. OQ-12 (UX) — Sub-codes inside the 12-row taxonomy? Lean: hold the 12 rows; the recovery-advocate's instinct to split (e.g., E_KEYCHAIN_UNAVAILABLE.libsecret) defers until local-event evidence shows users actually need the disambiguation. See ux.
