The Onboarding Novice's Frontend

Examples in every --help. Errors that suggest the next command. A tutorial mode that builds the mental model before the user has to commit to anything. I am the agent who downloaded mcpm an hour ago, doesn't know what JSON-RPC is, has never typed launchctl bootstrap in their life, and just wants to connect Claude Code to a GitHub MCP and feel productive. Everything below is in service of that human, because if we lose them at mcpm init, the other 18 subcommands never get to prove themselves.

Thoughts

Here is the truth that the rest of this team — peers and architects — keeps wanting to forget: the first hour of a user's relationship with a tool decides whether they ever use it again. Steve Krug's book is literally titled Don't Make Me Think, and Krug's rule one is the single sharpest piece of UX writing ever shipped on a glossy paperback. We've all read it. We don't all act on it. I'm here to act on it.

Look at the locked design. mcpm ships 19 top-level subcommands. That's more than Git's plumbing/porcelain split was in 2005, and Git has spent two decades training developers on it. A novice opening mcpm --help for the first time will see a wall of nineteen things and most of them — exec, projection, trust, registry verify, outdated — make zero sense if you don't already know what MCP Manager does. The Microsoft CLI guidelines explicitly call out that a help screen should be "task-oriented, not feature-oriented." We are currently feature-oriented. That's a debt I want to start paying down today.

Two structural design choices have already been made that I have to work inside, and I want to name them up front so I'm not arguing against locked decisions:

  1. 19 subcommands stays. I don't get to hide exec, projection, or trust. They exist because mcpmanagerd needs them. What I can do is hide them from the novice's first impression — by what mcpm with no args shows, by what mcpm help with no topic shows, and by how the --help-me tutorial introduces them in waves of "now you need this."
  2. The TUI is lazygit/k9s-style. A novice probably won't even open it on day one. Cool. But the moment they do — probably triggered by an error message saying "for a richer view, run mcpm tui" — we have ~10 seconds before they bail. The bottom hint bar earns its keep here, and a one-time first-launch tour overlay is non-negotiable, with a do-not-show-again checkbox.

What I want, in priority order: (1) every --help ends with three real worked examples, not synopsis-only — Stripe CLI does this and the difference between Stripe's CLI onboarding and AWS's is night and day; (2) every error message ends with the literal next command to run, copy-pasteable; (3) mcpm --help-me opens a guided tutorial TUI that takes the user from zero to "Claude Code can call a GitHub tool" in under five minutes; (4) mcpm init shows a preview before committing, because nothing kills trust like a tool that wrote files in your home directory before you knew it was going to.

I'll also push hard on what GitHub CLI calls "the empty-state principle": every screen where the user has nothing yet should explain what they could have and how to get there. mcpm status with no servers configured shouldn't say "no servers." It should say: "You don't have any MCP servers configured yet. Run mcpm search github to find one to install, or mcpm install official/github-mcp if you already know what you want." That's three lines of code that saves a Slack message to a teammate.

One more thing before I go to bat with my peers. The "doctor" command pattern — brew doctor, flutter doctor, rustup check, nvm doctor — does not appear anywhere in the locked v1.0 CLI surface, and that's a gap. Novices break their setups in dozens of tiny ways: missing keychain, wrong $EDITOR, registry unreachable, launchd plist not loaded. They need one command that says "here's everything that's wrong with your installation and how to fix each thing." I'd argue this is the 20th subcommand. I'll defend that position below.

Arguments with peers

vs. vim-power-user

My friend the modal-keyboard absolutist will tell me that --help-me is condescending and that real developers read the man page. I will counter with: your version of "real developers" is a survivorship-biased view of the ones who never bounced off your tool. Vim itself has a built-in tutor (vimtutor) that every Vim user I respect has gone through at least once, including emacs holdouts who wanted to know what the fuss was about. There is no incompatibility between "the TUI is keyboard-first lazygit-style for daily use" and "the TUI has a one-time guided tour the first time it opens." Those two things compound — the tour teaches the keybindings the power-user wants people to memorize, so by lesson three the user is hitting l for logs and s for start without thinking.

Concrete compromise I'll offer: the --help-me tutorial mode is opt-in, never auto-launches on second run (only the first), and a single keystroke (q) exits it permanently. The hint bar and the keymap modal (?) — those are the power-user's terrain and I won't touch them. We agree that ? shows the full keymap, that the hint bar is context-aware, and that no modal dialog ever steals focus during normal flow.

Where we'll fight: I want mcpm with no arguments to print a friendly orientation, not the bare 19-command list. Power-user wants the bare list (matches Git, Cargo, kubectl). I'll concede that mcpm --help shows the bare list — that's what aliased keystrokes expect — but mcpm with literally no arguments shows: top three "next likely commands" based on whether init has been run, whether any servers are installed, and whether any are running. GitHub CLI does this, and it's universally praised. The cost is two lines of branching in main.rs. The benefit is the novice doesn't have to interpret nineteen one-line descriptions on first contact.

vs. accessibility-advocate

Accessibility is the ally I want, not the peer I fight. Almost everything they ask for I already want. NO_COLOR respected — yes. Status conveyed by both color and glyph — yes (the UX-design page already mandates this). Screen-reader-friendly stdout — yes, especially for the non-interactive flows my novices will paste into ChatGPT to debug.

Where we genuinely disagree: animated progress indicators during mcpm install. Accessibility-advocate will want a static line that updates only on state change. I want a Stripe-CLI-style spinner because novices read static output as "did the command hang?" The win-win is the existing universal flag --quiet — but I want the default to be the spinner, and the spinner to degrade to plain text under NO_COLOR or when stdout is not a TTY. clig.dev explicitly supports this pattern.

We'll fight one more skirmish over --help-me's tutorial TUI: I want a "press SPACE to continue" pacing model where each lesson waits for an input. Accessibility-advocate may want auto-advance with a configurable delay. My answer: auto-advance is hostile to screen-reader users (they haven't finished reading when the screen changes), so SPACE-to-advance is actually the accessible choice. Hope I've won them over with that.

vs. cli-unix-purist

The Unix-purist is going to read this whole document and say: "Why is this tool printing emoji checkmarks? Why is it suggesting next commands? Stdout is a pipe, behave like one." I'll grant their core point: when stdout is not a TTY, mcpm becomes a different program. No spinner, no checkmarks, no "Next:" hints, no colors, no friendly framing — pure machine-readable output. We already have --json as a universal flag for the strict-machine case. What I want to nail down with the purist is the auto-detection branch: isatty(STDOUT_FILENO) at startup, and adapt every output decision off that. clig.dev calls this the "humans first, machines second" principle but it's really "humans on a TTY, machines on a pipe."

Where the purist and I genuinely diverge: I think error output should always include the next-command hint, even when piped. The argument: if a script catches a non-zero exit, the developer reading the logs to debug it benefits from seeing the suggested fix. The purist will say: "errors go to stderr, and stderr should be the error code and the message, period." Concession I can offer: the next-command hint goes to stderr but after a blank line, so a script that does cmd 2>error.log and parses the first line of error.log only sees the proper error. The hint is for the human reading the file later.

We agree on this: mcpm --version prints one line of version info and exits, no decoration. mcpm status --json emits parseable JSON with no human framing. mcpm install with stdout piped doesn't show a spinner. $NO_COLOR, $CI, and $TERM=dumb all flip the humanism off.

vs. visual-designer

Visual-designer will want box-drawing characters, careful column alignment, theme support, and probably a sparkline somewhere. I want all of that — provided it never costs information density on a small terminal. Specifically: on an 80-column terminal (still the default in many places, especially over SSH), the tutorial-mode TUI has to fit. I'll insist on this.

Where I'll push back: I do not want a visual-designer-style "welcome" splash screen with ASCII art on first mcpm launch. We have ten seconds of attention. Spending three of them on art is a cost we can't pay. The first thing a novice sees is information they need.

Where I'll concede: yes, color it nicely; yes, support a dark-mode theme; yes, use box-drawing for the tutorial overlay so it's visually distinct from the panes underneath; yes, a status-glyph-plus-color combo (per the locked a11y commitments). What I will not trade away: the bottom hint bar in the TUI stays one row tall. No multi-line "tip of the day" banner. The hint bar is the user's lifeline; it has to be uniformly placed every time.

Design

Below: the four onboarding transcripts I want to ship in v1.0, the tutorial-mode TUI sketch, the --help-me command, and a worked set of error messages with recovery commands. The transcripts overlap with the ones in the UX design page and the onboarding research recommendation — what's new here is the novice-lens annotation on every prompt.

Transcript 1 — mcpm init (interactive, lucky day, novice)

The user has never run mcpm before. They've just installed it via Homebrew. They open a terminal, type mcpm with no arguments, and we hand-hold from there. 

$ mcpm

mcpm v1.0.0 — Docker-style management for MCP servers
You haven't run setup yet. To get started:

  mcpm init           First-time setup (interactive, ~30 seconds)
  mcpm --help-me      Guided tutorial (~5 minutes, builds your first server)
  mcpm --help         Full command reference (19 commands)

Pick one or run `mcpm help` to learn more.

$ mcpm init

Welcome to MCP Manager. This will set up your machine to manage
Model Context Protocol servers and project them into your editors.

We'll write to:
  ~/.config/mcp-manager/config.toml          (your preferences)
  ~/.config/mcp-manager/trust.toml           (registry signatures)
  ~/Library/Application Support/mcp-manager/audit.log   (1 line)

Nothing else will be touched until you say so. Press Ctrl-C any time to bail.

[1/5] What name should I use to greet you? [Parth Patel]: ⏎

[2/5] Setup scope: where should this configuration live?
        user      Your personal MCP setup, applies to every project (recommended)
        project   Per-repo setup, lives in .mcp-manager.toml in this directory
      Choose [user]: ⏎

[3/5] I detected these editors on your machine:
        ✓ Claude Code CLI    (~/.claude/)
        ✓ Cursor             (~/Library/Application Support/Cursor/)
        ✓ Zed                (~/.config/zed/)

      Should I project MCP servers into all three? [Y/n]: ⏎
      (You can change this any time with `mcpm projection`)

[4/5] Docker is installed. Enable the Docker MCP Catalog as a server registry?
      This gives you access to Docker's official MCP server list. [y/N]: ⏎

[5/5] Register mcpmanagerd as a background service so it survives logout?
      You don't need this for daily use — `mcpm exec` starts the daemon
      on demand. Registering only matters if you want fast cold-starts
      between long gaps. [y/N]: ⏎

About to write:
  ~/.config/mcp-manager/config.toml          (new, 412 bytes)
  ~/.config/mcp-manager/trust.toml           (new, 1.1 KB)
  ~/Library/Application Support/mcp-manager/audit.log   (new, 1 line)

  Editors that will sync MCP servers: claude-code, cursor, zed
  Registries subscribed: official
  Service registration: skipped (daemon auto-spawns)

Looks good? [Y/n]: ⏎

✓ Wrote ~/.config/mcp-manager/config.toml
✓ Wrote ~/.config/mcp-manager/trust.toml
✓ Refreshed trust.toml (4 registry pubkeys, valid until 2027-05-27)
✓ Projected canonical state into 3 editor configs

You're set up. Some good next steps:

  mcpm search github       Find MCP servers related to GitHub
  mcpm install official/github-mcp    Install the official GitHub server
  mcpm --help-me           Run the guided tutorial if you'd like a tour

Done in 0.18s.

Annotations on this transcript, from the novice's lens:

  • Bare mcpm with no args is an orientation page, not a usage error. It detects that init hasn't been run and tells the user the three things they could do next. (This is the GitHub CLI pattern; see citations.)
  • The "we'll write to" preview comes before the first question. Novices want to know what's about to happen to their disk before they commit even one keystroke. This is direct application of Krug rule one — don't make them wonder.
  • Each prompt has a bracketed default, and a single ⏎ accepts. create-next-app does this; npm init does this. It's the lowest-friction interaction model still possible.
  • The "scope" question has explanations of both choices on the prompt line itself, not "see the docs." Novices don't go to docs — they just pick whichever sounds less scary and live with the consequences. Explaining inline is the difference between "user (recommended)" being chosen knowingly versus accidentally.
  • The service-manager question explicitly de-emphasizes itself ("you don't need this for daily use"). This is where peer agents have argued I'm being too friendly. I'm not — I'm protecting the user from a choice they don't yet have the context to make well.
  • The "looks good?" pre-commit confirmation is non-negotiable. The novice has now answered five questions; they need a single "yes, do the thing" before bytes hit the disk. This is the preview-before-commit principle from Stripe CLI and Vercel CLI.
  • Each line of "Next:" is a literal copy-pasteable command, not "consider installing some servers." The novice's mouse is on their trackpad ready to triple-click.

Transcript 2 — mcpm install official/github-mcp (first server, novice)

User has finished init and is following the "next" suggestion. They've never installed an MCP server before. They don't know what a registry is, what a runtime is, or what a signing key is. 

$ mcpm install official/github-mcp

Resolving official/github-mcp@latest from registry 'official' ... 0.4.2 ✓
Verifying minisign signature (key RWQabc…) ... ok ✓
Verifying SHA-256 checksum ... ok ✓

About to install:
  Server name:    github-mcp           (you can rename with --name)
  Version:        0.4.2                (pinned in lockfile)
  Source:         official/github-mcp  (community registry)
  Runtime:        devenv               (sandboxed; no Docker required)
  Required secrets: GITHUB_TOKEN       (you don't have this set yet)

Looks good? [Y/n]: ⏎

✓ Downloaded github-mcp 0.4.2 (3.2 MB)
✓ Verified signature
✓ Wrote ~/.config/mcp-manager/config.toml
✓ Updated lockfile
✓ Projected into claude-code, cursor, zed

Almost ready. github-mcp needs a secret you don't have yet:
  GITHUB_TOKEN  (a personal access token from github.com/settings/tokens)

To set it now:
  mcpm secret set GITHUB_TOKEN

Once set, you can verify the server works:
  mcpm test github-mcp

Or just open Claude Code — the server will start automatically when called.

Things I want to call out here:

  • "Required secrets: GITHUB_TOKEN (you don't have this set yet)" is the single most important line in this entire transcript. Novices install things, then nothing works, and they don't know why. Telling them before install completes that they'll need a token, plus the URL where to get one, plus the literal command to set it, eliminates a 20-minute frustration loop.
  • "Runtime: devenv (sandboxed; no Docker required)" — the parenthetical defends the choice. Novice doesn't know what devenv is, but "no Docker required" answers the question they were about to ask.
  • "Looks good?" again. Same principle: never commit without an explicit OK on the first interaction. Once the user has done this two or three times they can use -y.
  • The final paragraph offers two paths: set the secret now, or just go use Claude Code and let it discover the missing secret organically. Both are valid; both are surfaced.

Transcript 3 — Cloned-from-elsewhere project (trust gate)

Most stressful scenario for a novice. They've git clone'd a repo their teammate shared. They cd in. Suddenly mcpm starts asking about trust and signatures. I want this to feel friendly, not scary. The direnv-style trust gate is non-negotiable for safety, but it's also the moment we most risk the novice giving up. 

$ cd /work/cloned-from-github
$ mcpm status

This project has an MCP Manager config you haven't seen before:
  Path:    /work/cloned-from-github/.mcp-manager.toml
  Author:  alice@acme.com  (from the git log, not verified)

Before mcpm activates it, here's what it would do:
  Add 1 new server:        acme-db (postgres-mcp 0.3.4 from 'official')
  Override 1 existing:     github (restrict to /work/cloned-from-github)
  Inherit mode:            "all" — your user-scope servers stay available

This config doesn't run any local executables from the repo itself, which
is the most common scenario where you'd want to read the code first.

What would you like to do?
  y) Trust this exact config and apply it (sha256: 8a9f2d…)
  n) Ignore the project config for this session
  e) Edit it in $EDITOR before deciding
  ?) Explain trust gates in more detail

Choose [n]: ?

About trust gates
─────────────────
When you clone a repo with an .mcp-manager.toml file, mcpm doesn't apply
it automatically — because that file could declare servers that read your
filesystem, call external APIs, or run code from the repo itself.

Saying "yes" stores a sha256 hash of the file in your trust list. If the
file ever changes (e.g. a teammate updates it), mcpm asks you again.

You can change your mind any time:
  mcpm project allow         Trust the current project's config
  mcpm project deny          Remove trust for the current project

This is the same model `direnv` uses for shell env vars. It exists to
protect you, not slow you down — if you're working in your own repos
all day, you'll see this prompt once per project.

Choose [n]: y

✓ Recorded trust in ~/.config/mcp-manager/trust.toml
✓ Activated project config
✓ Projected into claude-code, cursor, zed

Almost ready. acme-db needs a secret you don't have yet:
  ACME_DB_URL  (your local postgres connection string)

To set it:
  mcpm secret set ACME_DB_URL

What matters here:

  • The fourth option in the prompt — ? for "explain trust gates" — is the friendly novice escape hatch. direnv famously assumes you already know what direnv does. We can't. The ? answer is short (eight lines of plain prose), names the analogy (direnv), and gives the user the commands to change their mind later. After reading it, the user types y with confidence, not because they got tired of reading.
  • "This config doesn't run any local executables from the repo itself" is a safety reassurance. The onboarding research recommendation specifically called out local executables as the riskiest case. Here we tell the novice this is not that case, so they can relax. Conversely, if it were that case, we'd shout it.
  • "alice@acme.com (from the git log, not verified)" — naming who wrote the file gives social context without overclaiming authentication.
  • Default is "n", not "y". Per accessibility-advocate's likely-correct point: if the user just spams ⏎, the safe thing happens. Saying yes is a typed key.

Transcript 4 — Hit an error, recover (E_SECRET_MISSING)

The novice tries to use the server in Claude Code; Claude Code calls mcpm exec github-mcp; the server can't start because GITHUB_TOKEN isn't set. mcpm reports back via stderr; the user runs mcpm status to see what's wrong. 

$ mcpm status

Servers:
  github-mcp  ⚠ failed     last error: E_SECRET_MISSING (12:34:01)
  acme-db     ●● running    14m

Editors: claude-code (synced), cursor (synced), zed (synced)
Daemon:  mcpmanagerd 1.0.0, running 14m, PID 47821

⚠ One server has a problem. Run `mcpm logs github-mcp` for details
   or `mcpm doctor github-mcp` for a guided fix.

$ mcpm doctor github-mcp

Checking github-mcp ...

  ✓ Config valid                 (~/.config/mcp-manager/config.toml)
  ✓ Lockfile entry present       (0.4.2, sha256 matches)
  ✓ Binary downloaded            (~/.cache/mcp-manager/devenv/github-mcp/)
  ✓ Signature verified           (registry 'official', key RWQabc…)
  ✓ Runtime available            (devenv profile present)
  ✗ Secret GITHUB_TOKEN missing  (not in keychain, not in environment)

1 problem found:

  Missing secret: GITHUB_TOKEN
  ────
  github-mcp's config declares it needs GITHUB_TOKEN. It's not in your
  OS keychain (we checked Keychain Services) and not in your shell
  environment (we checked at daemon spawn time).

  To fix:
    mcpm secret set GITHUB_TOKEN

  This will prompt you for the value (input is hidden) and store it in
  your macOS Keychain. You only need to do this once.

  Get a token at: https://github.com/settings/tokens
                  Required scopes: repo, read:user

After setting the secret, re-run:
  mcpm restart github-mcp

Things to notice in this transcript:

  • I'm proposing a 20th subcommand: mcpm doctor, modeled on brew doctor, flutter doctor, rustup check, and npm doctor. It does deep diagnostics on a single server (or the whole installation). The locked 19-subcommand list doesn't include it, but I think this is the case where we add one. mcpm test exists, but it spawns the server and checks if it speaks MCP — that's a smoke test, not a diagnostic. doctor walks the chain (config → lockfile → binary → signature → runtime → secrets) and tells you the first thing that broke. I'd happily merge it with mcpm test if naming has to stay at 19 — call the combined command mcpm test by default, and add a --diagnostic mode that runs the whole chain.
  • "Get a token at: https://github.com/settings/tokens" with required scopes is the kind of hand-holding that pays for itself a hundred times. The Stripe CLI does this for every API key it asks you to set.
  • The error tells the user what we checked, not just what's missing. "Not in your OS keychain (we checked Keychain Services) and not in your shell environment (we checked at daemon spawn time)" — this is reassurance the tool did its homework, and it teaches the novice the mental model for where secrets live.

The --help-me tutorial mode

My signature ask. Vim has vimtutor; I want mcpm --help-me. It's an opt-in TUI walkthrough that takes the user from zero to "I just connected an MCP server and called it from Claude Code." It's not auto-launched; novices type the words because they want it. Five lessons, each ~60 seconds. 

$ mcpm --help-me

┌─ MCP Manager · guided tour ───────────────────────────────────────┐
│                                                                   │
│  Lesson 1 of 5: What is MCP Manager?                              │
│                                                                   │
│  MCP Manager (mcpm) is a tool for managing Model Context          │
│  Protocol servers. MCP servers are little programs that give      │
│  AI assistants like Claude Code access to specific tools and      │
│  data — your GitHub repos, your database, your filesystem.        │
│                                                                   │
│  Without MCP Manager, each AI tool (Claude Code, Cursor, Zed)     │
│  has its own config for which MCP servers it knows about.         │
│  MCP Manager keeps ONE config and projects it into ALL of them.   │
│                                                                   │
│  Think of it like Homebrew, but for AI assistant capabilities.    │
│                                                                   │
│                                                                   │
│  ──── progress ────                                                │
│  ●●○○○                                                            │
│                                                                   │
├───────────────────────────────────────────────────────────────────┤
│ SPACE next · b back · q quit tour · ? what does each key do      │
└───────────────────────────────────────────────────────────────────┘

Lesson plan:

  1. What is MCP Manager? The orientation paragraph above. No interaction needed; just SPACE to advance.
  2. Your first command: mcpm search. The tour drops the user into a real mcpm search github, shows them the BM25 results, and explains what each column means.
  3. Install something. The tour offers to install filesystem-mcp (no secret required, no network calls — the most "Hello World"-y MCP server we have). User says yes; tour runs the install for them and explains each line of output as it happens.
  4. Open the TUI for the first time. Tour launches mcpm tui with a special first-launch overlay (described below) and shepherds the user through the panes.
  5. Use it from Claude Code. Tour shows the projected config in ~/.claude/mcp.json, points at the new filesystem entry, and tells the user to open Claude Code and ask "list files in /tmp" to verify everything works.

Important properties of --help-me:

  • SPACE to advance, not auto-advance. Already argued; accessibility-advocate agrees.
  • Real commands, not simulations. When lesson 3 says "we're going to install filesystem-mcp," it actually installs filesystem-mcp. The user comes out of the tour with a working setup, not just having watched a demo.
  • Every lesson has a q escape hatch that exits cleanly, leaving whatever was installed installed. If the user bails at lesson 3, they still have filesystem-mcp.
  • Tour state persists. ~/.config/mcp-manager/state.toml records that the tour was completed (or which lesson the user quit at). Running mcpm --help-me again offers to resume or restart.
  • Tour is offered exactly once after mcpm init as part of the "Next:" suggestions. It is never forced on the user — no autorun, no popup.

First-launch TUI overlay

When the user opens mcpm tui for the first time (or via lesson 4 of the tour), a translucent overlay appears for ten seconds — or until any key is pressed. It points at three things and gives a one-line label for each. Then it dissolves and the lazygit-style TUI is in front of them. 

┌─ MCP Manager ────────────────────── github · 12:34:08 ┐
│ Servers ▸                       │ Logs · github         │
│ ──────  ←── three panes here    │                       │
│   github     ●● running         │   ↑                   │
│   filesystem ●● running         │   logs / details      │
│   sqlite     ●○ stopped         │   appear on the right │
│                                 │   for the selected    │
│ Toolchains ▾                    │   entity              │
│                                 │                       │
│   ✓ claude-code  sync           │                       │
│                                 │                       │
├─────────────────────────────────┴───────────────────────┤
│ ? help · / search · enter view · l logs · s start · q quit │ ←── always-on hints
└─────────────────────────────────────────────────────────┘

  Press ? at any time for the full keymap. Press any key to dismiss.

Three callouts, one sentence each, gone in ten seconds. Visual-designer can theme this however they want; I just want the structural decision locked in: first-launch is annotated; second-launch is naked.

Examples in every --help

Every single subcommand's --help ends with at least three real examples. Not placeholder syntax — real arguments. This is the Stripe CLI standard and the Microsoft Command Line Guidelines standard. The example for mcpm install --help is already in the UX-design page. I want to lock in the rule: any future PR that adds a subcommand without three worked examples in --help is blocked.

Error UX — worked examples

Five errors from the 12-row taxonomy, written the way I want them in v1.0. Each follows the format: code · what · why · what to do next. 

$ mcpm start github-mcp

✗ Failed to start github-mcp  (E_SECRET_MISSING)

  github-mcp's config declares it requires this secret:
    GITHUB_TOKEN  — not in keychain, not in environment

  To fix:
    mcpm secret set GITHUB_TOKEN

  Then re-run:
    mcpm start github-mcp

  Need a token? https://github.com/settings/tokens (scopes: repo, read:user)

$ mcpm install corp/internal-mcp

✗ Failed to install corp/internal-mcp  (E_REGISTRY_UNREACHABLE)

  I tried to fetch the index from:
    https://internal.example.com/mcpm-registry

  ... and got: connection refused (errno 111)

  This usually means:
    1. You're not on the corporate VPN (try: connect to VPN, retry)
    2. The registry is down (check #infra Slack channel)
    3. Your registry URL is wrong (check: mcpm registry list)

  Your cached index from 2 days ago is still searchable:
    mcpm search internal-mcp --source corp

  To retry once the registry is back:
    mcpm install corp/internal-mcp

$ mcpm install official/github-mcp

✗ Failed to install official/github-mcp  (E_REGISTRY_SIGFAIL)

  The downloaded package's signature didn't verify with the trusted
  public key for registry 'official'.

  This could mean:
    1. A new key was rotated in (most common — fix below)
    2. The package was tampered with (rare; report it)

  To refresh the trusted-key manifest:
    mcpm trust refresh

  Then retry:
    mcpm install official/github-mcp

  If the failure persists after `mcpm trust refresh`, do NOT install
  with `--accept-unsigned`. Report it:
    https://github.com/mcp-manager/mcp-manager/issues

$ mcpm secret set GITHUB_TOKEN
Enter value for GITHUB_TOKEN: (input hidden)

✗ Failed to store secret  (E_KEYCHAIN_UNAVAILABLE)

  I couldn't reach your OS keychain.

  On Linux, mcpm uses libsecret. The d-bus secret service wasn't
  running or wasn't accessible. Most distros need one of:

    sudo apt install gnome-keyring        (Debian/Ubuntu)
    sudo dnf install gnome-keyring        (Fedora)
    sudo pacman -S gnome-keyring          (Arch)

  Then log out and back in, OR start it manually:
    /usr/bin/gnome-keyring-daemon --start --components=secrets

  Escape hatch (less secure; only for testing):
    mcpm secret set GITHUB_TOKEN --from-env GITHUB_TOKEN
    (reads the value from your shell env instead of keychain)

Pattern across all of these:

  • Error code on the first line, in parentheses after the failure summary.
  • "What I tried" — the literal URL, the literal arg, the literal line/column. The user shouldn't have to guess what mcpm did.
  • "This usually means" with a numbered list of possibilities, ordered by frequency.
  • "To fix" with literal copy-pasteable commands.
  • "To retry" with the literal command to re-run after the fix.
  • External links where helpful (token URL, GitHub issues URL).
  • An escape hatch where one safely exists (--from-env for keychain failures).
  • An anti-escape where one would be dangerous ("do NOT install with --accept-unsigned" on signature failure).

$EDITOR fallback for novices

The TUI's e key opens $EDITOR. cli-unix-purist insists this is correct. I agree. But novices on macOS often don't have $EDITOR set, in which case $EDITOR resolves to nothing and the user gets a cryptic shell error. My fix:

  • If $EDITOR is unset and we're on macOS, try in order: code -w (VS Code in wait mode, since most Claude Code users have VS Code), cursor -w, nano. Tell the user which fallback we used.
  • If $EDITOR is unset on Linux, try: nano, vi. Same disclosure.
  • On first use, after the editor closes successfully, print: "Tip: set $EDITOR in your shell rc to choose your preferred editor. Currently using: code -w."
  • Add a fallback config setting [ui] preferred_editor = "code -w" so the user can override in config.toml rather than environment, for the novices who don't know what a shell rc is.

Project-scope mental model

Novices struggle with the user/project inheritance model. My pitch: borrow Python's venv mental model, which most developers have already internalized. The three inherit modes map to:

  • inherit = "all" ≈ a venv with --system-site-packages
  • inherit = ["s1", "s2"] ≈ a venv that only pulls in named packages from system
  • inherit = "none" ≈ a vanilla venv (full isolation)

I want this analogy in mcpm help project verbatim, because explaining new concepts in terms of concepts the user already knows is the single highest-leverage move in technical writing. ("Like X, but for Y" — see citations.)

Summary of asks

  1. Bare mcpm with no args is an orientation page, not a usage error.
  2. Every --help ends with 3 real worked examples. PR rule.
  3. Every error has code · what · why · what-to-do-next. 12 errors, 12 copy-pasteable next commands.
  4. mcpm --help-me launches a 5-lesson opt-in tutorial TUI. SPACE-paced, real commands, resumable state.
  5. First-launch TUI overlay with three callouts, dismissable, never shown again.
  6. Preview-before-commit on mcpm init, with literal byte counts, before any disk write.
  7. Trust gate prompt has a ? "explain" option that defines the trust model in 8 lines.
  8. 20th subcommand: mcpm doctor (or fold into mcpm test --diagnostic) that walks the failure chain and reports the first broken link.
  9. $EDITOR fallback chain with disclosure of which editor we used and how to set the env var.
  10. Project-scope mental model documented as "like venv" in mcpm help project.
