The Accessibility Advocate's Frontend

Color is decoration, not data. NO_COLOR is honored everywhere. Every state carries a text label. Every mouse gesture has a keyboard equivalent. Output piped to cat reads as coherent prose to a screen reader. If a colorblind developer or a Braille-display user cannot use mcpm for their day job, we have shipped a broken product — and there are more of them than the locked decision tables admit.

Thoughts & threat model

The locked accessibility commitments in the UX design page are directionally right but operationally thin. "Color AND glyph" is two words; making that hold across 19 subcommands, a ratatui TUI, mdbook docs, error modals, trust prompts, $EDITOR re-entries, and project-scope diff rendering is the job. This brief is that job, written in the voice of the user we keep forgetting: the one who cannot see the green dot.

The threat model has four concrete personas, none of them edge cases:

  1. The deuteranope. ~6% of men of Northern European descent have red-green color vision deficiency.[1] A "● running" in green and a "● failed" in red look identical to them. If they ever shipped to production based on a green dot, we hurt them.
  2. The Braille-display user / screen-reader-piped operator. Modern terminal screen readers (VoiceOver in Terminal.app, Orca with gnome-terminal, NVDA with WSL terminals on Linux GUIs) read the textual content of the terminal buffer. ANSI escape sequences are invisible to them; only the literal characters matter. A status indicator that is "green + space" with no text label reads as silence.
  3. The motor-impaired keyboard-only user. Cannot click the TUI. Cannot double-click. Cannot right-click for a context menu. Trackballs and head-pointers exist but are slow; keyboard remains the accessible path. Every mouse interaction must have a discoverable key equivalent.
  4. The CI / log-aggregation pipeline. Not a human, but exhibits the same constraints: cannot see color, parses output as text, breaks when status is encoded in ANSI rather than tokens. The same fix that helps the screen reader helps grep, jq, and Datadog.

The unifying principle: information that exists only in color is information that doesn't exist for a meaningful slice of users. WCAG 2.1's "Use of Color" success criterion 1.4.1 states it directly: color must not be the only visual means of conveying information, indicating an action, prompting a response, or distinguishing a visual element.[2] The web has known this for two decades; CLI tools largely ignored it; we will not.

What the locked decision already gets right

  • The UX design page already commits to NO_COLOR + --no-color and an always-paired color-and-glyph status convention. Good baseline.
  • The TUI hint bar is context-aware and always visible — a discoverability win that doubles as an accessibility win (no hidden state).
  • The error taxonomy uses textual codes (E_SECRET_MISSING, etc.). Codes are screen-reader gold — they're discrete tokens that read cleanly, unlike paragraphs of stylized prose.
  • Every interactive flow has a non-interactive flag equivalent (--defaults -y). Automation + accessibility share the same affordance.

What the locked decision under-specifies (where I push)

  • "Best-effort screen-reader support" is not a specification. Define what "best-effort" means: what reads, what doesn't, what flag to pass.
  • The 8-color base palette must be colorblind-safe. Not "uses 8 colors" — uses these specific 8 colors, and never relies on red-vs-green as the only distinction.
  • --plain mode is not in the universal-flags list. --no-color strips ANSI but keeps Unicode box-drawing, glyphs, spinners. A screen-reader needs a stricter mode where the buffer is plain ASCII prose. Add --plain.
  • The TUI accessibility story has a specific name: high-contrast theme + tab traversal + announce-on-change. Ratatui doesn't ship a11y primitives out of the box; we'll build them from existing patterns (tmux's accessibility, lazygit's bare-tty fallback, k9s monochrome theme).
  • Trust prompts must be unambiguous without color. A bold red "DANGER" header that's actually bold red is just bold to a deuteranope. The word DANGER must do the work.

Arguments with the four peers

vs. vim-power-user — keyboard-first is half the answer

We agree on more than we disagree. Vim power users and keyboard-only-by-necessity users want the same thing: every action reachable by a key. The fight is over discoverability. The vim aesthetic hides affordances behind two-character mnemonics that you "just know." That works for the population that already knows. It excludes everyone else — including the screen-reader user who needs the key map read to them, and the cognitive-disability user who can't hold a 60-key cheat sheet in working memory.

My ask of vim-power-user: keep your modal keys, but require the hint bar to remain on by default (no :set hint=off as the default), require ? to open a fully readable keymap modal (not a dense table — labeled sections with a heading every screen reader can land on), and accept that the TUI announces state transitions to stderr when run with --announce so a sighted-and-blind pair-programming session can hear what changed. Vim itself has spent the last decade improving accessibility for these exact reasons.[6]

Concrete asks for vim-power-user:

  • Don't make modal-counts (e.g. 3r for "restart third server") the only way to operate on the Nth item. Arrow + Enter must always work.
  • The status line at the bottom must contain words, not just colored cells. "RUNNING" not "[●]".
  • When NO_COLOR is set, modal indicators (current mode: normal/insert/visual) must be textual, not just chromatic.

vs. onboarding-novice — we are natural allies

Onboarding-novice's hand-holding pushes for the same explicit-state-in-text that I push for. The novice who doesn't know what a "running" server means and the screen-reader user who can't see the green dot both need the word "running" written out. The novice's "explain what just happened in plain language" and the blind user's "tell me what changed" are the same feature.

Where I will push novice toward more accessibility: don't use emoji to carry state. Onboarding loves emoji — checkmarks, rockets, party poppers. Screen readers either silently drop these or read them with vendor-specific names ("rocket ship") that don't carry the intended meaning. Restrict emoji to a small vocabulary with explicit text alternates: 

# Bad (state is in the emoji, the word is decorative or missing)
🚀 Launched!

# Good (text carries state, glyph is enhancement)
LAUNCHED  servers started: 3 of 3

The aws configure + terraform init + npm init -y prior art that novice cites all share a property: their state transitions are verbs in plain text first, then glyphs second.[7] Keep that property.

vs. cli-unix-purist — we share a covenant

The Unix purist's mantra is "do one thing well, write to stdout, errors to stderr, be silent on success." That mantra is an accessibility manifesto in disguise. A program that respects $NO_COLOR, writes parseable output, separates streams, and stays silent on success is one that a screen reader can navigate. The Unix world figured this out by accident in 1975; the GUI world is still catching up.

Where we have a genuine disagreement: --json versus --plain. The purist will argue that --json is sufficient: machine-readable, parseable, no color, no Unicode. But JSON is unreadable as prose. A screen reader piping mcpm status --json | cat will read literal braces, commas, quotes, and field names. That's worse than the colored output, not better.

The proposal: three output modes, not two.

  • --json — machine consumption. JSON to stdout. Already locked.
  • --no-color — strip ANSI but keep human formatting (boxes, spinners, Unicode). The default when NO_COLOR is set in the environment.
  • --plain — plain ASCII, no boxes, no spinners, one statement per line, screen-reader friendly. The default when stdout is not a TTY.

The purist gets pipe-friendliness; I get screen-reader-friendliness. Same output, same flag, two readings. The CLIG (Command Line Interface Guidelines) project endorses exactly this layering.[3]

vs. visual-designer — the hardest debate

Visual designer wants information density, semantic color, visual hierarchy through hue. I want every hue to be redundant — present as well as a text label, never instead of one. The conflict is real but tractable.

Three concessions I will make to visual designer:

  1. Color remains as enhancement. Status is "● RUNNING" — the dot is colored (green when colors are on); the word does the carrying. When color is off, the word still works. When color is on, the eye finds it faster.
  2. I do not insist on monochrome by default. The default theme can use color. I insist only that the information not require it.
  3. Unicode glyphs are fine where the screen-reader story is good. The glyph ● (U+25CF BLACK CIRCLE) reads as "black circle" in most screen readers — not great but not gibberish. Reserve ⚠ and ✗ for error states where the literal name ("warning sign") matches the meaning.

Three pushes I will not yield on:

  1. No red-green pairs as the sole distinction. Use orange-vs-blue, or green-vs-magenta, both of which survive the most common color-vision deficiencies.[4]
  2. WCAG AA contrast (4.5:1) in the dark theme. Light-on-dark with sufficient contrast is a baseline, not a choice. Apple's HIG, Microsoft's Fluent UI, and the W3C all converge on this number.[5]
  3. No information conveyed by gradient or saturation alone. A 200-ms fade from gray to green to indicate "starting → running" is invisible to screen readers and to anyone whose terminal doesn't render gradients. Use discrete state words.

Concrete design

Status rendering — the canonical convention

Every state across the CLI, TUI, error modals, and JSON output uses the same triple: glyph, word, color. The word is the source of truth. The glyph and color are decoration that vanishes safely.

State Glyph (Unicode) Word Default color (24-bit) Colorblind-safe?
running● U+25CFRUNNING#005f87 deep blueYes
starting◐ U+25D0STARTING#0087af cyanYes
stopped○ U+25CBSTOPPED#5f5f5f grayYes
failed✗ U+2717FAILED#d75f00 orangeYes
warn / drifted⚠ U+26A0WARN#af8700 amberYes
unknown / pending?UNKNOWN#8a8a8a grayYes

Note what's not in this table: green and red as the primary failure-vs-success pair. The Okabe-Ito palette[4] (the de-facto standard for colorblind-safe scientific plotting) uses orange and blue precisely because they survive deuteranopia, protanopia, and tritanopia. Our running-vs-failed pair becomes deep blue (●) RUNNING and orange (✗) FAILED. The eye still distinguishes them at a glance. The deuteranope still distinguishes them at a glance. The screen reader reads the word.

NO_COLOR + --no-color + --plain — the behavior table

Condition ANSI color Unicode glyphs Box drawing Spinners Output
TTY, no env, no flags (interactive default) YesYesYesYes Pretty + colorful
NO_COLOR=1 set (env, any value) NoYesYesYes Per no-color.org spec
--no-color flag NoYesYesYes Identical to NO_COLOR=1
Not a TTY (piped to cat, grep, …) NoNoNoNo Auto-degrades to --plain
--plain flag NoNoNoNo Plain ASCII prose, one statement per line
--json flag NoNoNoNo JSON to stdout, all human text to stderr
TERM=dumb NoNoNoNo Same as --plain
Inside a CI environment variable detected (CI=true, GITHUB_ACTIONS, …) Yes (CI logs can render ANSI)YesYesNo (spinner = noise) Color kept, animation off

The pipe-detection rule is the one that closes 80% of the gap. When stdout isn't a TTY, default to --plain. The CLI Guidelines[3] explicitly recommend this: "Disable any features intended only for an interactive session. […] suppress decorative formatting, progress bars, and spinners when output is not a TTY." It also means that mcpm list | cat and mcpm list --plain produce the same output — which means the screen reader on a TTY that pipes through cat for navigation gets clean text without the user knowing the trick.

Concrete rendering examples

Default (colors on, TTY). The visual designer's preferred rendering. Boxes, glyphs, ANSI color, but every state still labeled in words:

$ mcpm status
   NAME         STATE      UPTIME    PID    LAST ERROR
   github       ● RUNNING  14h 22m   71421  —
   filesystem   ● RUNNING  3d  04h   71422  —
   sqlite       ○ STOPPED  —         —      —
   github-pr    ✗ FAILED   —         —      E_SERVER_OOM (5/5 restarts)
   acme-db      ⚠ WARN     1m 03s    71430  starting…

NO_COLOR=1. Same glyphs and layout, no ANSI escape codes emitted. A screen reader reading the visible buffer sees identical structure; the word is still the carrier.

--plain mode. No glyphs, no box-drawing, no alignment via Unicode spaces. One statement per server. Each line stands alone. This is what mcpm status | cat produces by default, and what a Braille display navigates line-by-line:

$ mcpm status --plain
github: RUNNING, uptime 14h22m, pid 71421.
filesystem: RUNNING, uptime 3d04h, pid 71422.
sqlite: STOPPED.
github-pr: FAILED. Last error: E_SERVER_OOM (5 of 5 restarts in window).
acme-db: WARN. Uptime 1m3s, pid 71430. Currently starting.

Note the prose-style trailing punctuation. A screen reader running this through a TTS engine produces coherent sentences instead of staccato tokens. The error code (E_SERVER_OOM) reads cleanly because it's underscore-separated rather than camelCase or hyphenated — screen readers split underscores into pauses that the reader can parse as "E underscore SERVER underscore OOM."

Trust prompt — unambiguous without color. The original UX-design rendering uses bold colored letters for y/n/e. Watch what changes in the accessible rendering:

$ cd /work/cloned-from-github
mcp-manager: detected new project config:  /work/cloned-from-github/.mcp-manager.toml
             servers declared:             1 added (acme-db), 1 override (github)
             inherit mode:                 "all"
             registry sources:             official (trusted)
             secrets referenced:           ACME_DB_URL (not in your keychain)

UNTRUSTED PROJECT CONFIG. This file was created elsewhere and could
execute arbitrary processes. Review before trusting.

  [Y] Trust this exact config (sha256 8a9f2d…)
  [N] Reject for this session (default)
  [E] Open in $EDITOR before deciding
  [D] Show full diff against the empty baseline

Choose [Y/N/E/D] (default N):

Four changes from the locked rendering. (1) The header literally says UNTRUSTED — no color needed. (2) Each option is on its own line with a bracketed letter, mirroring git rebase --abort and apt install conventions that have decades of accessibility testing behind them.[8] (3) The default is explicit ("default N") so a user who can't see which letter is highlighted-as-default still knows. (4) A "show full diff" option was added — the most accessible safe-default is "let me see everything before I decide."

TUI accessibility — what ratatui does and doesn't give us

Ratatui is a TUI library; it draws cells with attributes (fg, bg, bold, underline, …) to a terminal buffer via crossterm. It does not emit any structured a11y tree. There is no equivalent of the web's ARIA, no native accessibility API like macOS's NSAccessibility. The screen reader sees whatever characters are in the terminal buffer.[9]

That constrains us, but it also clarifies the work. Every TUI accessibility win comes from one of five techniques:

  1. Make the buffer self-describing. The currently-focused pane has a textual header saying so ("FOCUSED: Servers"), not just a highlighted border. The currently-selected row has its text prefixed with >, not just inverse video. A screen reader stepping through the buffer reads "FOCUSED Servers / github RUNNING 14h / > sqlite STOPPED" and the user knows where focus is.
  2. Mirror state transitions to a sidecar stream. When the user presses r to restart, the TUI does its visual thing — but also writes "restarted github" to stderr if --announce is set. A blind user can run mcpm tui --announce 2> ~/.mcpm-announce.log in one terminal and tail -f ~/.mcpm-announce.log | espeak in another. Crude but functional. The Linux world has used this pattern for emacspeak-style assistive listening for decades.[10]
  3. Keyboard parity for every mouse gesture. The locked UX design already commits to this in principle. Make it explicit per gesture:
    Mouse gestureKeyboard equivalent
    Click pane to focusShift+Tab cycles panes
    Click row to selectArrow keys / j/k
    Double-click row to drill inEnter
    Mouse wheel scroll logPgUp/PgDn, g/G
    Click tab in right paneTab cycles log streams
    Option/Alt+drag for text select:copy command-mode (v1.1)
  4. High-contrast theme as a first-class citizen. The locked UX page mentions high-contrast as a bundled theme. Spec it: foreground #ffffff on background #000000 in dark mode, #000000 on #ffffff in light mode, no intermediate grays for any state-carrying element, status colors restricted to the four Okabe-Ito-derived hues that retain ≥7:1 contrast (WCAG AAA) against both backgrounds.[5]
  5. No flashing, no auto-update churn. Spinners update at most 4× per second; status flips don't animate; tail-follow doesn't redraw whole rows, only appends lines. WCAG 2.3.1 bars flashing above 3 Hz (seizure threshold). We stay well under.[11]

The TUI in --plain + --non-interactive mode. If a screen-reader user really wants the TUI's data without the TUI's interactivity, offer a "list-once" degraded form:

$ mcpm tui --plain --once
MCP MANAGER STATUS as of 2026-05-27 12:34:08.

Servers (4 total):
  github: RUNNING for 14 hours 22 minutes (pid 71421). No errors.
  filesystem: RUNNING for 3 days 4 hours (pid 71422). No errors.
  sqlite: STOPPED. Last ran 2 hours ago.
  github-pr: FAILED with E_SERVER_OOM after 5 of 5 restarts in the
    last 5 minutes. Investigate with: mcpm logs github-pr.

Toolchains (3 total):
  claude-code: in sync.
  cursor: in sync.
  zed: DRIFTED. Managed block in ~/.config/zed/settings.json was
    hand-edited. Review with: mcpm projection diff zed.

Secrets (2 total):
  GITHUB_TOKEN: set.
  SQLITE_PATH: set.

End of status.

Help system + mdbook

mcpm help output is already pretty good — the EXAMPLES section is prose, the SEE ALSO links are flat. Two additions:

  • No ANSI styling in --help by default. The Python world standardized on this via Click and argparse; the Rust ecosystem is splitting on it (clap supports color, many projects disable by default).[12] Default off; opt in via --color.
  • mdbook output accessibility. mdbook's default theme already meets WCAG AA contrast in light and dark modes. Verify with axe-core in the build pipeline.[13] Any architecture diagrams (the big ASCII box in technical-design.html, for example) must have a text description in a <figcaption>-equivalent below them so the screen reader gets the semantics without re-rendering the boxes.

Error UX — codes are the accessibility win we already have

The error taxonomy (12 codes from E_SECRET_MISSING to E_DAEMON_VERSION) is one of the strongest accessibility features in the design and nobody framed it that way. Discrete codes read aloud cleanly. They're searchable, copy-pasteable, googleable. A screen reader user hearing "E underscore SECRET underscore MISSING" can paste that exact string into a search engine; a user hearing "the server requires a secret that isn't available" cannot.

Keep the codes prominent. Two refinements:

  1. Always print the code first, on its own visual line, before the prose explanation. Screen reader users get the actionable token before the friendly paragraph.
  2. The TUI error modal's "copy with y" should copy the code + fix command, not just the fix command. That way the clipboard contains the searchable identifier too.
┌─ ERROR ─────────────────────────────────────────────────────┐
│ E_SECRET_MISSING                                            │
│ Failed to start github: required secret not available.      │
│                                                             │
│ Missing: GITHUB_TOKEN (not in keychain, not in env)         │
│                                                             │
│ Fix:   mcpm secret set GITHUB_TOKEN                         │
│                                                             │
│ Then:  mcpm start github                                    │
│                                                             │
│ [y] copy fix to clipboard   [l] view server logs   [Esc] dismiss │
└─────────────────────────────────────────────────────────────┘

Onboarding transcripts — strip the color-dependency

The four onboarding transcripts in the UX design page use checkmarks (✓) liberally. That's fine — ✓ U+2713 reads as "check mark" in VoiceOver and Orca. What's not fine is the implicit assumption that a sequence of green checkmarks means "everything succeeded." Make each transcript line carry the verb in text: 

# Current (relies on glyph color):
   ✓ Wrote ~/.config/mcp-manager/config.toml
   ✓ Wrote ~/.config/mcp-manager/trust.toml

# Accessible (verb in text, glyph is decoration):
   OK  wrote ~/.config/mcp-manager/config.toml
   OK  wrote ~/.config/mcp-manager/trust.toml

# Or, in --plain mode:
   Wrote ~/.config/mcp-manager/config.toml.
   Wrote ~/.config/mcp-manager/trust.toml.

When something fails, the verb changes ("FAILED to write…", "SKIPPED because…"). The glyph changes too, but the verb is doing the work. A user piping the onboarding output to a file and reading it later with a screen reader gets coherent sentences.

Project-scope inheritance — explained in text, not just by nesting

The locked design renders the three inherit modes ("all", allowlist, "none") with prose. Good. The risk is that the diff output for what a project-scope file does often relies on indentation and color to show "this came from user, this overrides, this is project-only." Indentation reads poorly in screen readers (the leading whitespace is silent). Color is invisible to the deuteranope.

Render project-scope reasoning with explicit per-line tags:

$ mcpm project show --plain
Project: /work/acme-project (sha256 8a9f2d…)
Inherit mode: all
Effective servers (4 total):
  [USER]               github         official/github-mcp 0.4.2
  [USER+PROJECT]       github         + allowed_paths from project (override)
  [USER]               filesystem     official/filesystem-mcp 0.2.1
  [PROJECT]            acme-db        official/postgres-mcp 0.3.0
  [USER, DISABLED]     sqlite         disabled by project config

Each row's source is in a labeled bracket. A blind reviewer of someone else's project config can audit it line-by-line: "the github server has additional allowed_paths from the project; the acme-db server is project-only; sqlite is disabled by the project." No color or indentation required.

$EDITOR integration — keep the user's tools

Spawning $EDITOR for config edits is itself an accessibility win: the user's editor is already configured for their assistive tech. The blind vim user has spent years tuning vim with Vimspeak; the JAWS-on-VS-Code user has VS Code's accessibility settings dialed in. We respect that by not building a custom editor.

Two small additions:

  • When re-entering the TUI after a save fails validation, the error modal must include the line/column of the offending TOML node in text — never as a colored highlight in a tiny preview pane that screen readers can't navigate.
  • If $EDITOR is unset, fall back to $VISUAL, then vi (which ships everywhere and has Vimspeak compatibility), never a built-in TUI text editor. The absence of $EDITOR is more often a screen-reader user's deliberate choice than a missing dependency.

Summary of asks beyond the locked design

  1. Add --plain to the universal flags list. Define it as no-color + no-Unicode + no-box-drawing + no-spinners + prose-style line endings.
  2. Auto-degrade to --plain when stdout is not a TTY (the implicit default that pipes already imply).
  3. Specify the Okabe-Ito-derived colorblind-safe palette as the default. Document red-green pairs as forbidden for state-carrying elements.
  4. Ship a high-contrast theme that meets WCAG AAA (7:1) contrast for every state-carrying element.
  5. Add --announce to the TUI for sidecar-stream announcements of state transitions.
  6. Refine the trust prompt: textual UNTRUSTED header, one option per line, explicit default, add a "show diff" option.
  7. Keep error codes prominent; print them before prose; copy them with the fix command.
  8. Strip emoji-as-state-carrier from onboarding output. Verbs first, glyphs second.
  9. Add explicit source-bracket tagging to project-scope inheritance output. Indentation doesn't speak.

None of these break the locked decisions. Every one of them is a refinement that costs a small amount of code and a small amount of design care, and buys us a user base we currently exclude by default.
