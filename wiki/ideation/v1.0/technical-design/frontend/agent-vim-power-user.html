The Vim Power User's Frontend

Modal. Dense. Single-key. The TUI should feel like lazygit, not a wizard. The mouse is a courtesy, not a contract. Every common action is reachable from the home row in two keystrokes or fewer, every uncommon action is reachable from : with completion, and the chrome stays out of the way of the data. If a user can run nvim, helix, tmux, k9s, and lazygit without a manual, they should be able to run mcpm's TUI within a minute.

stance: vim-power-user facet: frontend modal navigation j/k aliases : command palette / search mouse opt-in

Thoughts

The locked baseline is already good. ux-design.html#tui commits to ratatui + crossterm, a single-screen lazygit/k9s shape, mouse + keyboard both supported, and a keymap that already names l e r d s, ?, /, q, j/k/h/l, g/G, n/N, Tab / Shift+Tab. The decisions I would have fought for have already been made. So what's left is HOW: how the modal states compose, how : works, how the command palette competes with the hint bar without doubling chrome, and how every single one of the 19 CLI subcommands is reachable from inside the TUI without invoking the CLI under the hood.

Three references frame everything I write below:

  • lazygit — single-screen, panes you cycle with Tab, single-key actions on the focused pane, : opens a command-line for everything that doesn't have a hotkey, ? opens a contextual cheatsheet that changes per pane. The hint bar at the bottom is the single most-discoverable affordance in any TUI I've used.
  • k9s — : jumps to a resource kind by name with completion (:pod, :svc), / filters the current view, and the status line tells you which cluster/namespace you're in. The modal mental model is "the cursor is always in Normal mode; you opt into : or / for input".
  • Helix — modern modal editor whose selection-first grammar (action verbs always apply to the focused selection) maps cleanly onto our TUI: every action key applies to the entity under the cursor in the focused pane. No prefix keys. No leader.

The single biggest design lever I want to pull is making Normal mode the only mode the user sees by default. /, :, and e (which spawns $EDITOR) are the only escapes; everything else is single-key in Normal. That keeps the mental model flat: the TUI has exactly four states — Normal, Search (after /), Command (after :), and Modal (any transient dialog: confirm-delete, edit-validation-error, help, error overlay). The state diagram in § Modal state diagram has four boxes and that's it.

The second lever: : is the universal escape hatch. Every CLI subcommand that makes sense interactively is reachable as a palette command. That means :install, :search, :registry add, :secret set GITHUB_TOKEN, :project allow, etc. The palette is a single ratatui-rendered input line at the bottom of the screen — same row as the hint bar — that swaps in when : is pressed and swaps out on Enter or Esc. The implementation reuses the same internal command registry the CLI uses; we are not building two command systems. (This dovetails with what cli-unix-purist will argue for the CLI side.)

The third lever, which the locked baseline already grants: mouse is opt-in. The ux-design page says "Mouse is enhancement, never required" — I agree, but I want to take it further: add a :set mouse off (and tui-mouse = false in tui-theme.toml) so that users on tmux + remote SSH can opt out of bracketed-paste / SGR mouse capture entirely and reclaim native terminal copy-paste. The existing Option/Alt-drag bypass is nice but only partially solves this; a permanent off switch is the real keyboard-first answer.

Final framing: the vim power user stance is not "make it look like vim". It's "respect the grammar that users already have in their fingers". j/k for line, g/G for top/bottom, / for find, n/N for next/previous match, :q for quit, Esc to cancel, Ctrl+D / Ctrl+U for half-page scroll. None of these cost the novice anything (they still have arrows + the hint bar + mouse) and all of them are free wins for the millions of developers who already type them all day.

Arguments against the other four stances

vs. accessibility-advocate

accessibility-advocate is going to argue (correctly) that color must never be the only carrier of information, that NO_COLOR must be respected, that screen-reader compatibility matters, and that low-contrast palettes hurt low-vision users. I agree on all of that — modal navigation has nothing to do with monochrome rendering. The friction point is going to be: does modal navigation hurt screen-reader users?

My answer: no, modal navigation is actively easier for screen readers than rich mouse-driven UIs. Every state transition in my design is announced by a visible status-line change (NORMAL → : → NORMAL), every action has an audible keystroke that maps to a single concept, and there is no hidden context. The Orca + Speakup screen readers handle terminal applications by reading the framebuffer. As long as we keep the status line at a fixed row and write state changes there, the screen reader will pick them up.

Where I would concede: a --reduce-motion / tui-animation = false flag that disables any animated transitions (we don't have many — the spinner during mcpm update, the pane-focus border highlight). And a config-driven keymap (~/.config/mcp-manager/tui-keymap.toml) so users who can't easily press j/k (e.g. one-handed users) can remap to other keys. The Helix remapping doc is the model.

Where I would not concede: I will not give up j/k as the default aliases for arrow keys. Arrow keys are still there. j/k are additions, not replacements. A user who can't press j/k never has to. A user who can gets a hand-rest-friendly home-row shortcut for free.

vs. onboarding-novice

onboarding-novice will argue: "the average user has never opened lazygit, doesn't know j/k, panics when a TUI doesn't tell them what to do, and quits within 30 seconds". That user exists and matters. The locked baseline already handles them: hint bar always visible, context-aware affordances, ? opens a full keymap modal, every TUI action also has a CLI equivalent. I want to add one more affordance for them: a discoverability mode in the command palette.

The : palette in my design has two modes: fuzzy (default, like fzf) and browse (toggle with Ctrl+B). Browse mode shows the entire command list grouped by category — install, lifecycle, logs, secrets, project, registry — with descriptions. A novice presses : on a blank palette, hits Ctrl+B, and gets a vertical menu of every action they could possibly want, with arrow-key navigation. A power user just types :inst<Tab> and is done.

Where I would concede: a "did you mean" prompt when a typo'd command is run. :isnatll should suggest :install. clap already does this for the CLI; we reuse the same Levenshtein-distance library inside the palette.

Where I would not concede: the default state is Normal mode with no overlay. I will not open a tutorial overlay on first launch. The hint bar is the tutorial. Onboarding belongs in mcpm init (a CLI flow), not in the TUI. The TUI is for operating an already-set-up system. If the user opens the TUI and has zero servers, the body of the Servers pane reads (no servers — press : install or run `mcpm install <source>`) and that's sufficient.

vs. cli-unix-purist

We are the closest allies in the room. cli-unix-purist will argue: "everything must be pipeable, --json everywhere, stdout for data and stderr for diagnostics, no ANSI on stdout when not a TTY". I agree with all of it — that's the right CLI design and I'd vote yes on every plank. The only friction is going to be: how do we reconcile a 19-subcommand CLI with my preference for a unified : palette in the TUI?

Answer: the palette is a thin wrapper around the same command names. The CLI invokes cmd::run("install", args); the palette invokes cmd::run("install", args) against the same dispatch table. We are not maintaining two grammars. The palette is the CLI with auto-completion, command discovery, and live feedback. (This matches how k9s presents :resourceKind commands and how lazygit's command-line shows up.)

Where I'd concede: the 19-command count is one too many for me. I'd merge start, stop, restart into a single mcpm lifecycle <action> <server> with three short aliases — but the spec already names them as separate top-level commands, so this is futile to relitigate. I drop it. Same logic on mcpm tui vs. mcpm-with-no-args: I'd argue the no-arg invocation should launch the TUI directly (avoiding the explicit tui subcommand) and the spec already says that. Good.

Where I'd push back: I want a few quality-of-life features cli-unix-purist might scoff at because they're "interactive". (1) mcpm logs <server> without --follow should still be tail-able-default if isatty(stdout); cli-unix-purist would say it should always dump-and-exit. The compromise: dump-and-exit when not a TTY, tail -f-like when a TTY. (2) mcpm status on a TTY shows colorized glyphs; on a pipe it dumps plain text. cli-unix-purist agrees with the latter half and tolerates the former.

vs. visual-designer

visual-designer will argue for density-by-design: typographic hierarchy, hand-tuned column widths, color theory, a thoughtful 256-color palette, careful use of dim/bold/italic. I support all of this — density is a vim virtue. The friction will be: visual-designer wants to make decisions about color and chrome that I will sometimes find too maximalist for keyboard-first operation.

Where I agree: status indicators use color AND glyph (already locked). ● running, ○ stopped, ⚠ failed. Three-tier color palette (default / high-contrast / monochrome). Hand-tuned column widths in the Servers pane (name width wraps name; status is fixed; uptime is right-aligned tabular). Borders are single-line box-drawing, not double-line, not Unicode-light-shade-noise.

Where I'd push back: no nested bordered subpanes. lazygit's mistake (in my view) is the occasional doubled border when a sub-modal opens inside a pane. We render modals as overlays centered on the screen with a single shadowed border, not as inner sub-panes. Less chrome, more content.

Also: I want dim used liberally for non-actionable metadata (14h uptime, registry name) and reserved colors only for status. Color fatigue is real; a rainbow TUI is just as unreadable as a no-color one.

Design

TUI layout

The locked baseline ASCII sketch in ux-design.html is good but lacks the modal-state affordances. Here's my refined version with status-line and palette treatments called out.

Notable differences from the baseline sketch:

  • Status line in the title bar: mode (or focused entity name) shown on the left, clock on the right. Mode replaces entity-name when in SEARCH / COMMAND / MODAL.
  • Hint bar always starts with the mode tag (NORMAL by default). When : is pressed, the hint bar transforms into the command palette — same row, same chrome, no extra screen real estate.
  • Pane separators are ──────, single-line. The focused pane is indicated by a brighter border AND a ▸ caret next to the pane title (color + glyph; a11y-correct).
  • Right pane is a single buffer with tab strip on top. Tab strip shows the current stream and its scroll state (● = following, ○ = paused).

Modal state diagram

Four states. Two-letter transitions on every edge.

            ┌───────────────┐
            │    NORMAL     │  ← default
            │  (j/k focus,  │
            │   l/e/r/d/s,  │
            │   Tab cycles) │
            └───┬───────┬───┘
        '/' ↓   │       │   ↑ Esc
                ↓   ':' ↓    │  (Esc anywhere returns to NORMAL)
        ┌───────┐   ┌───────────┐
        │ SEARCH│   │  COMMAND  │  ← palette
        │ (n/N) │   │ (Tab cyc) │
        └───┬───┘   └─────┬─────┘
       Enter↓             ↓Enter
            └──┐    ┌─────┘
               ↓    ↓
        ┌──────────────┐
        │    MODAL     │  ← confirm / error / help-modal / edit-validation
        │  (Esc / y/N) │
        └──────────────┘

Notes:

  • Esc always returns to NORMAL. There is no nested modal. If a modal spawns another modal (e.g. error overlay during edit-validation), the first is closed first. One-modal-at-a-time keeps the mental model clean and matches lazygit's behavior.
  • e spawns $EDITOR — this is a process suspension, not a mode change. ratatui releases the alternate screen, $EDITOR runs, on exit we restore the alternate screen and re-enter NORMAL. If $EDITOR exits non-zero we show a MODAL with the error.
  • Spinner during long ops (:install, :update) does not count as a mode. The user is still in NORMAL and can keep navigating; the spinner is in the status line.

Command palette spec

Command registry shape (Rust sketch)

// crate: mcpm-tui · module: palette
pub struct Command {
    pub name: &'static str,            // "install"
    pub aliases: &'static [&'static str],// &["i", "add"]
    pub category: Category,             // Lifecycle | Install | Discovery | …
    pub summary: &'static str,          // one-line desc
    pub args: ArgSpec,                  // parsed via the same clap derive
    pub run: fn(Ctx, ArgValues) -> Result<Outcome, Error>,
}

// All 19 CLI subcommands are registered here at compile time.
// The CLI and the palette dispatch through the same table.

Completion strategy

  1. Stage 1 — command: fuzzy-match against name + aliases. Top-3 shown.
  2. Stage 2 — args: once a command is matched, complete its positional and flag args. install <source> queries the registry cache; logs <server> queries the live server list; secret set <NAME> queries the keychain index.
  3. Stage 3 — values: for enum flags like --runtime devenv|docker|podman|uvx-npx|none, complete the value set.

History + audit

  • Per-session command history; persisted to tui-history on graceful exit. Up to 500 entries, LRU.
  • Every palette command that writes to canonical state is audit-logged with source = "tui-palette". This matches CLI audit entries' source = "cli" and the daemon's source = "daemon". Audit-log parity is a security ask; we'd want this anyway.

CLI shape — short notes from this stance

19 subcommands is acceptable, slightly bloated. The locked baseline names them. My stance-specific additions:

  • Every long flag should have a short alias. Locked baseline has -v / -q / -y. Add: -f (= --force where used), -S (= --scope), -r (= --runtime), -n (= --name). Vim users want short flags; power users typing mcpm install x -Sproject -rdocker is real.
  • Output piping must be sacred. If stdout is not a TTY, never emit ANSI, never emit progress spinners, never emit table-formatted output by default — emit either TSV or JSON (with --json). This aligns with cli-unix-purist; the locked spec already commits to --json everywhere.
  • mcpm with no args launches the TUI (already locked). I'd argue we should keep mcpm tui as a synonym, not a separate subcommand surface; just a shortcut for those who want explicitness. Cost: 0 lines of clap config.
  • Add mcpm completions <shell> — clap-derive generates these for free. Vim users want zsh + fish + bash completions on tap.

Onboarding for power users

The four onboarding transcripts in ux-design.html cover the lucky-day, non-interactive, project-scope, and cloned-elsewhere cases. From the power-user angle, two refinements:

  1. Honor $VISUAL before $EDITOR. Vim users distinguish between $VISUAL (full-screen) and $EDITOR (line-mode ed). mcpm's e action should check $VISUAL first, fall through to $EDITOR, then to vi. This matches git var's GIT_EDITOR resolution.
  2. Cloned-from-elsewhere trust gate keystrokes are wrong. The current sketch shows [y/n/e]. Power users will reflexively type q to bail and get nowhere. Add q = "no" (synonym for n), ? = "show me the diff first", and ! = "trust forever (no re-prompt on hash change)" (with a warning that this is the dangerous escape hatch and is audit-logged). Discoverable but matches vim's danger-tier keystrokes.

Trust-gate sketch (revised)

$ cd /work/cloned-from-github

      servers:   1 added (acme-db), 1 override (github)

Power-user $EDITOR integration

When the user presses e on a server entity:

  1. mcpm extracts the [server.<name>] stanza to $TMPDIR/mcpm-edit-<hash>.toml, prefixed with a # DO NOT EDIT THE HEADER COMMENTS banner that includes the entity name, scope, and a vim: ft=toml modeline.
  2. mcpm releases the alternate screen, runs ${VISUAL:-${EDITOR:-vi}} "$tmpfile", awaits exit.
  3. On success exit + content-changed: validate via config.validate; if OK, atomic-write back; mcpmanagerd reload; audit-log.
  4. On validation failure: spawn a MODAL overlay with the validator error pointing at line:col. User presses e to re-enter the editor on the same tmpfile (changes preserved), or Esc to discard.
  5. On editor non-zero exit: discard.

This matches how gh, click.edit, and edit (the Rust crate) handle editor suspension. There is no novelty here, which is exactly the point.

Project-scope behaviors

From this stance, project-scope (.mcp-manager.toml) is mostly a backend concern, but the TUI needs three power-user affordances:

  • Status line shows the active scope. When inside a directory with a trusted project config, the title bar reads mcpm · github · running · 14h · scope:project (acme). When in user scope, scope:user. Always visible. Single glance to know "am I about to mutate user state or project state?".
  • :project diff palette command — shows the overlay between user and project canonical state, with + / - / ~ markers per server. Vim users will :!git diff if we don't give them this.
  • Name-override servers are marked. When the user has [server.github] in their user config AND the project has [server.github] with overrides, the entity name in the Servers pane gets a small (overridden) tag. Power users want this signal explicit.

Error UX — keyboard-first treatment

The 12-row error taxonomy in ux-design.html#errors is well-designed. From this stance, the additions:

  • Error modal is single-key navigable. y = copy the suggested-fix command (this matches the locked baseline). l = jump to relevant logs. e = open the offending config file in $EDITOR if the error is E_CONFIG_INVALID. Esc = dismiss. ? = open the docs page for this error code in $BROWSER or w3m if no $BROWSER.
  • Error badge in the Servers pane is single-character. ✗ next to the server name, color red. Pressing Enter on that server jumps directly into the error modal.
  • CLI errors must exit with distinct exit codes. E_SECRET_MISSING = exit 3, E_CONFIG_INVALID = exit 4, E_REGISTRY_* = exit 5, etc. Documented in mcpm help exit-codes. Power users script around this.

Help system

  • ? in TUI opens a context-sensitive keymap modal — shows only keys applicable to the focused pane / entity. Pressing ? again toggles to the full keymap. Pressing q or Esc closes.
  • mcpm help <topic> on the CLI prints rich help with 3+ worked examples per subcommand (already locked). Add: mcpm help cookbook shows multi-command recipes.
  • mdbook at docs.mcp-manager.dev/v1.0/, linked from every error code and every --help output. Already locked. From the vim stance: every mdbook page must have a print-friendly variant for w3m / links / lynx users (mdbook ships this for free). I want users to be able to read docs without leaving the terminal.

Net design summary (vim-power-user stance)

  • 4-state modal: NORMAL / SEARCH / COMMAND / MODAL. Esc always returns to NORMAL.
  • j/k/h/l + arrows + g/G + Ctrl+D/U + 1-4 pane-jump + Tab / Shift+Tab cycling.
  • : opens a command palette with fuzzy completion, browse mode (Ctrl+B), history (↑↓ / Ctrl+R), and shell-out (:!).
  • / opens incremental search. n/N next/previous. Esc cancels.
  • Mouse on by default but trivially disabled via :set mouse off or tui-theme.toml.
  • $VISUAL → $EDITOR → vi fallback for e editing. Validation modal with re-edit on failure.
  • Status line shows mode + entity + scope + clock. Hint bar shows context keys + transforms into palette on :.
  • Error modals: y copy fix, l logs, e edit, ? docs, Esc dismiss.
  • Reserved keys for v1.x: v . m % x D. Don't bind them now.
