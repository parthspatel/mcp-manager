The Visual Designer's Frontend

Layout is craft. Colour is meaning. Unicode is the icon set. Misalignment is a sin. The other four agents in this facet will argue about what users do; my job is to fight for what users see — every pixel, every glyph, every column-boundary, every named hex value. A terminal is a 2-D canvas with a rigid character grid; treating it like a stream of println!s is malpractice.

Thoughts

Every objection I get to taking visual design seriously in a TUI follows the same pattern: "it's just text, why are you drawing colour swatches?" The pattern is wrong. A terminal cell is not a unit of text; it's a unit of visual real estate, sized by the user's font metrics, painted by ANSI escape codes, framed by box-drawing characters, and read in the same Z-pattern as any other 2-D layout. Lazygit, k9s, btop, helix, and zellij are not popular because they "work in a terminal"; they are popular because they treat that terminal as a designed canvas. The crap in this category — the tools that wrap top with a curses border — fail not on features but on visual literacy.

So what does visual literacy mean for mcpm?

  1. Panel proportions are decisions, not accidents. The spec hand-waves the layout as "single-screen, lazygit/k9s style" but the actual split has to be measured. lazygit ships a 5-pane sidebar that defaults to roughly 30% of width with a stacked-cards arrangement; k9s ships a single primary table at ≈90% with command/log panels appearing on demand. Our domain (three concern groups on the left, one log/detail pane on the right) sits between those — and I will defend 30 / 70 at standard width (≥ 120 cols), collapsing to 40 / 60 on narrow terminals (80–119 cols), and a stacked single-pane layout below 80 cols. [1] [2]
  2. Colour is meaning — and meaning needs a contract. Right now the UX spec says "● running, ○ stopped, ⚠ failed". Good start, not a system. I want a published, themed, eight-name palette where every name maps to a meaning, not a hue: fg-default, fg-muted, fg-faint, accent, success, warn, danger, info. Themes are mappings from those eight names to ANSI / truecolor values. That's the same discipline IBM Carbon, GitHub Primer, Tailwind, and (in TUI-land) the Catppuccin / Tokyo-Night / Solarized families all enforce. [3] [4]
  3. Unicode is the icon library. A terminal can't load SVG, but Unicode 15 has 149,000 codepoints and a generous slice of them are semantically perfect: box-drawing, block elements, miscellaneous symbols, geometric shapes. I will pick a 30-glyph vocabulary and never deviate. If a user has NO_GLYPH=1 or runs with --ascii, every glyph has a fixed-width ASCII fallback. Mixing emoji into a TUI is amateur hour — emoji are double-width on most fonts, break grid alignment, and render inconsistently across Terminal.app, iTerm2, Alacritty, WezTerm and tmux. [5] [6]
  4. Without colour, hierarchy still works. Bold for primary, default-weight for secondary, dim for tertiary, italic for explanation, underline for the focused item or hyperlink. Any screen I design must remain legible if you set NO_COLOR=1 and run on a monochrome terminal — that's not just an accessibility check, it's a structural check that hierarchy isn't leaning on colour. [7]
  5. The status line is a permanent reading surface. Whatever the user is doing, the bottom of the screen must answer four questions: what's focused, what keys apply, is there work in flight, are we connected to mcpmanagerd. Helix taught me this; so did Vim's airline. The status line is not garnish; it's the persistent UI affordance. [8]

The good news: ratatui already gives us the primitives — Style, Modifier::BOLD, Modifier::DIM, Modifier::UNDERLINED, Color::Indexed for the 256-colour cube, Color::Rgb for truecolor, Block::borders with the box-drawing set of my choice. ratatui's Layout system is a real constraint solver (percentages + min/max lengths), not a guess. We can do this properly. [9]

The bad news: nobody else on this project has loaded "visual designer" as their primary frame. Without a strong pull from this corner, mcpm will ship as another lazygit-shaped blob with the default ratatui blue-on-black border style, looking like a Rust crate's README example. That would be a crime; lazygit is good in spite of its default look, not because of it.

Arguments

To the vim-power-user: density is your friend, not your goal

We agree on more than we disagree on. Modal navigation, hjkl/arrows, : command palette, no mouse-required affordances — yes. But I want to push back on the implicit equation density = quality. k9s at default density is a wall of evenly-weighted text; new users bounce off it. The lazygit team explicitly chose lower density and a coloured "current selection" stripe; that's what made it the gateway TUI for non-vim users. [10] For mcpm, density should be a user setting, not a hard-coded value. Bundled presets: density = "compact" (k9s-equivalent: 1 row per server, no empty rows between sections), density = "comfortable" (the default; 1 blank row between Servers / Toolchains / Secrets sub-panes; sub-pane titles in bold underline), density = "roomy" (Helix-style; extra row below each item showing the inline status). All three should be one-line changes in tui-theme.toml.

You will also push for hiding the bottom hint bar to reclaim a row; I will fight you on this. The bar is the discoverability layer. We can compromise: hint_bar = "auto" shows on first 24h of usage and hides after, but pressing ? resurfaces it for the rest of the session. That's a Helix-pattern. The bar should be one row, never two; rotating contents based on the focused pane lets us fit everything.

To the accessibility-advocate: I'm your structural ally, not your competitor

We are perfectly aligned on NO_COLOR and colour-blind palettes; what I want to add is why those constraints make the design better for everyone. The discipline of "every state must survive both the colour-blind test and the monochrome test" is what forces us to ship glyphs alongside colour. The discipline of "every pane border is high-contrast against its background" forces us to pick a real border token, not a hue. The high-contrast theme isn't an alternate; it's the regression test for the default theme.

Specific deliverables I'd commit to in your facet's favour:

  • Bundled monochrome theme is identical to default with all eight semantic tokens collapsed to fg-default/fg-muted/fg-faint on bg-default/bg-elev. If any screen breaks in this mode, the screen is wrong.
  • Bundled high-contrast theme uses pure black / pure white / pure ANSI primary colours, all WCAG AA at 16 px or larger. No "elev-1" / "elev-2" backgrounds — flat surfaces only. [11]
  • A colour-blind safe palette (theme = "okabe-ito") based on the eight-colour palette by Okabe & Ito that's tested across all three common dichromacies. [12]
  • Every glyph in the standard set has both a Unicode and an ASCII form. --ascii picks the ASCII form for the CLI; tui-theme.toml sets glyphs = "ascii" for the TUI. No "experimental" or "fancy nerd-font" mode in v1.0 — the standard set works in vanilla Terminal.app on a fresh macOS install. (Nerd Fonts are wonderful but not portable.)

To the onboarding-novice: visuals carry tone, and tone carries trust

You want examples, walkthroughs, and discoverable affordances; I want to argue that visual tone does half your work for you. The four onboarding transcripts in the UX spec — lucky-day interactive, full non-interactive, project-scope, cloned-project trust — each need a different visual tone, and the tonal difference must be designed, not accidental.

  • Lucky-day interactive: warm and chatty. Indented two spaces, default-weight text, accent colour only on the prompt-arrow (←) and the ✓ success rows. Feels like a helpful colleague. Tone-source: npm init, aws configure, Stripe CLI's first run.
  • Non-interactive: terse, single line of confirmation. No banner, no welcome, no encouragement — this is a CI / Nix surface and any garnish is friction.
  • Project-scope: same tone as lucky-day but framed as a "joining the project" ritual. A small ASCII-box at the bottom telling the user to commit the file. The box says "share with your team" — that framing communicates that .mcp-manager.toml is a team artefact.
  • Cloned-project trust gate: this one is visually different. Yellow warning rule across the top. Bold heading. The list of changes is presented as a diff (colour-coded green/red for added/removed servers). The choice prompt is right-aligned and bracketed: [y/n/e]:. Tonally: an airlock, not a tutorial. The user must read this; the visuals make them slow down.

To the cli-unix-purist: I respect your pipes, you respect my colours

I am with you on every pipeable surface. --json on every read command. Sysexits.h exit codes. --no-color auto-detected when stdout is not a TTY. --ascii for grids that need to survive tr and awk pipelines. [13]

Where we'll fight: I refuse to let the TTY surface degrade to your aesthetic. When the user runs mcpm status in a real terminal, I want:

  • A table with proper column alignment (using tabwriter-style padding, not naïve \t).
  • Status glyphs in the first column (●/○/⚠/✗).
  • Server name in bold, registry source in dim, uptime in default weight.
  • The "last error" column truncated at column-width with a Unicode ellipsis (…); full text is in mcpm logs <server>.

That same command in a pipe — mcpm status | grep github — produces plain UTF-8 text with no escape codes (auto-detected via isatty(stdout)), tab-separated columns, no glyphs (or ASCII glyphs if the user pinned --ascii). That's not a degraded experience; it's the correct experience for that context. Auto-detection means you never have to remember a flag.

At standard width (120 cols), the left pane is 40 characters, which is not exactly 30% of 120 — it's 33%. The visual 30 / 70 split is achieved because the right pane has lower character density (longer rows, more whitespace), making it feel proportionally larger. This is deliberate: real readers don't measure columns, they sense weight. We tune to weight, not arithmetic.

Visual logic: section headings are bold + underlined; flag names are accent-coloured (so the eye finds them); inline comments above example commands are dim; example commands themselves are default foreground. No section dividers are needed — typography carries the hierarchy. The output renders acceptably in NO_COLOR mode because bold + underline survive.

6. Trust-gate prompts — visual clarity, not scary

The cloned-project trust gate is the single most security-sensitive UI in mcpm. It should feel like an airlock: deliberate, slow, well-lit. Tone: clear and respectful, not alarmist. The user is about to let a third-party config influence their environment; we want them to read it, not panic-press y. 

$ cd /work/cloned-from-github

┌─────────────────────────────────────────────────────────────────┐
│  ⚠  New project config detected                                  │
└─────────────────────────────────────────────────────────────────┘

  Path:       /work/cloned-from-github/.mcp-manager.toml
  Hash:       sha256:8a9f2d1b4c…
  Inherit:    "all" (your user-scope servers will overlay)

  Changes vs. your user config
    + server.acme-db          postgres-mcp@^0.3   (devenv)
    ~ server.github           overrides: allowed_paths

  Registries this config wants
    ✓ official   (trusted, baked-in pubkey)

  Secrets referenced
    ⚠ ACME_DB_URL  (not yet in your keychain — will prompt on first start)

  This is the first time mcpm has seen this config. Trust it?

    y   yes, trust this exact config (records hash in trust.toml)
    n   no, ignore for this session
    e   open in $EDITOR before deciding

  [y/n/e]:

Visual choices: warning rule across the top (warn-coloured, not danger; this isn't a failure, it's a decision); diff-style indicators for additions/overrides (familiar from git); the choice prompt is bracketed and the three letters are accent-coloured so they pop. No flashing, no banner, no "are you sure?". The visual weight matches the cognitive weight.

The three inherit modes ("all" / allowlist / "none") are an abstract concept to most users. mcpm config show --layered renders them as a layered diff so the user can see what's coming from where. 

$ mcpm config show --layered

  registry      official            [from user]

Three semantic colours, three meanings: bold heading is the server name; success-green marks values contributed by the project (the closer scope, "winning" if there's a conflict); info-blue marks user-scope contributions that survive to the merged view. The right column is dim, so the eye finds the colour first.

9. $EDITOR integration — preview mode

The TUI doesn't have a visual presence inside $EDITOR, but it owns the before-and-after framing. When the user presses e in the TUI, we render a one-line spinner row in the bottom hint bar: 

│ ◐ editing github in nvim · save and quit to apply · Esc in nvim to cancel  │

On editor exit: 

│ ✓ github reloaded · 1 line changed · validation OK · audit-logged             │

…or, on validation failure, the modal-overlay form of E_CONFIG_INVALID, with the offending line in danger colour and a e retry hint.

11. The status line — always four answers

│ ● daemon · github · 14h uptime · 27 tools · ? help · / search · l logs · q quit │
        ↑          ↑                          ↑
        |          focused entity             context-aware key affordances
        daemon-health indicator (red ● if disconnected)

The four answers — daemon connection, focused entity, what's possible, what's universal — are visually grouped left-to-right with U+00B7 (·) as the separator. When mcpmanagerd disconnects, the leftmost ● turns danger-red and the whole status line gets a subtle red underline; the rest of the screen freezes its data display (dim) until reconnection. This is the single most important visual signal in the app: "my source of truth is gone".

12. What I am explicitly not doing

  • No animations beyond a 4-frame spinner. No throbbers, no progress-bar shimmer. Movement is reserved for the spinner and for genuine state transitions (a row colour-change when a server goes from running to failed).
  • No Nerd Font private-use codepoints. They are gorgeous; they are unsupported in the macOS default Terminal. We are not making users install a font to use a system tool. (Side note: the nerd-fonts theme can be a v1.x community contribution.)
  • No emoji. Even where the standard glyph would be replaceable (⚠ vs ⚠️), the emoji variation selector produces inconsistent grid alignment across terminal emulators and font fallback chains. [15]
  • No truecolor-only design. Every screen degrades gracefully through truecolor → 256-color → 8-color → mono. We test on all four.
  • No themes that override the eight semantic tokens with surprising mappings. success is always a green-ish hue; danger is always a red-ish hue; warn is always an orange/yellow hue. Themes vary saturation and lightness, not semantics.

13. Tying it back to the v1.0 spec

The UX design page already lists three bundled themes (default, high-contrast, monochrome) and commits to "color is never the only carrier of information." Good — my contribution here is to make that operational with:

  1. An eight-token semantic palette with three reference themes filled in to the hex value.
  2. A 30-glyph standard set with codepoints, fallbacks, and assigned meanings.
  3. A measured panel-proportion table by terminal width.
  4. A severity × glyph × colour matrix for the 12-row error taxonomy.
  5. Four onboarding visual tones, with concrete formatting choices for each.
  6. A density-preset knob to defuse the lazygit-vs-k9s aesthetic argument.
  7. A four-answer status line with an explicit daemon-disconnect failure mode.

None of this is gold-plating. Every item exists in lazygit, k9s, helix, btop, or zellij in some form. The work here is to assemble the right subset and commit to it. The cost of not doing this work is that mcpm ships looking like a Rust crate's example output — which would betray everything else this project has decided about UX being a first-class concern.
