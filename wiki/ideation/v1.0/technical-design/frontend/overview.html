Frontend — Facet Synthesis

Where the five frontend stances converge, where they diverge, and what gets adopted in v1.0. Five perspectives — vim-power-user, accessibility-advocate, onboarding-novice, cli-unix-purist, and visual-designer — were asked to fight for their constituency inside the locked v1.0 envelope: ratatui + crossterm TUI, clap-derive CLI with 19 subcommands, lazygit/k9s single-screen shape, mouse + keyboard, macOS + Linux, no telemetry. This synthesis picks winners per sub-decision, names the live tensions, and parks what we can't decide yet under open questions.

Agreement — convergence

The encouraging discovery from reading all five briefs side-by-side is that the structural debates were already settled by the locked v1.0 UX page. None of the five agents tried to relitigate ratatui vs. tview, single-screen vs. wizard, mouse+keyboard vs. keyboard-only, or the 19-subcommand surface. Every fight that remains is about refinement: which knob defaults which way, what gets a flag equivalent, what the bottom hint bar says when the focused server is failed. That's a much better place to negotiate from than "should we have a TUI at all."

Six convergent principles emerged across all five briefs, in many cases word-for-word:

  1. Color is decoration; the word is the carrier. Every stance agreed status must be conveyed by glyph + word + color, never color alone. The accessibility-advocate argued this on WCAG 1.4.1 grounds; the visual-designer agreed because color discipline produces better visual hierarchy; the cli-unix-purist agreed because the data on stdout shouldn't be a Unicode character; the vim-power-user agreed because dim+bold modal hierarchy survives NO_COLOR; the onboarding-novice agreed because spelled-out verbs ("RUNNING", "FAILED") read better aloud than colored dots.
  2. Every interactive flow has a non-interactive flag equivalent. The cli-unix-purist makes this a contract; the accessibility-advocate notes it doubles as keyboard-only support; the onboarding-novice accepts the contract as long as the interactive path stays user-friendly; the visual-designer treats non-interactive as "the CI-and-Nix aesthetic"; the vim-power-user already lives in CI-land. No live disagreement.
  3. Pipe-detection is the right auto-default. When isatty(stdout) is false, mcpm becomes a different program: no color, no spinner, no glyphs, no boxes, no progress chatter on stdout. All five stances endorse this; the only quibble is whether the plain mode is named --plain (accessibility), --ascii (visual-designer), or auto-implied by !isatty (purist). The synthesis below picks one.
  4. Error codes are an asset, not a sin. The 12-row E_* taxonomy from ux-design.html#errors gets unanimous praise. Accessibility-advocate frames it as "screen-reader gold"; cli-unix-purist as "the basis for sysexits mapping"; onboarding-novice as "the hook the recovery transcript hangs off"; vim-power-user as "exit-code branching for shell wrappers"; visual-designer as "the right size of severity vocabulary for a modal-overlay treatment."
  5. The TUI never autolaunches. Every stance independently arrived at this rule. Bare mcpm with no args prints help (to stderr) and exits. mcpm tui is the only entry point into the interactive surface, and it refuses to start when stdin/stdout isn't a TTY, when $TERM=dumb, when $CI is set, or when --no-tty is passed.
  6. Trust the user's editor. All five briefs say "spawn $EDITOR; don't invent a TUI text editor." The vim-power-user and onboarding-novice both add the $VISUAL → $EDITOR → vi fallback chain that matches git-var(1); accessibility-advocate cites it as "the user's editor already has their assistive-tech setup"; cli-unix-purist documents $MCPM_EDITOR as the in-house override; visual-designer designs the "editing… save and quit to apply" status-line indicator.

Two more convergences worth flagging because they're often missed in TUI design and everyone agreed unprompted: the bottom hint bar must always be visible and context-aware (it's the discoverability layer for novices, the muscle-memory reinforcement for vim users, the keyboard map for screen-reader users, and the visual rhythm anchor for the designer); and the ? key in the TUI must open a full keymap modal, not just a help URL. Both of these are already in the locked spec; the synthesis ratifies them louder.

Disagreement — live tensions

Three real disagreements survived the convergence pass. Each needs a per-component decision below; this section names them honestly.

Tension 1 — The default output mode on a TTY

The visual-designer wants the default mcpm status on a TTY to render a padded table with glyphs in the first column, server name in bold, registry in dim, ellipsized "last error" column, ANSI color throughout. The cli-unix-purist wants the same TTY output to be a tab-separated table with no chrome, on the theory that a user who later does mcpm status | tee out.log shouldn't end up with mojibake in their log file. The accessibility-advocate wants a third mode — --plain — that drops Unicode glyphs entirely so a Braille display reads sentences instead of "black-circle filled space github filled space running."

The compromise: three discrete modes, one auto-detection rule. Default on a TTY: visual-designer's rendering wins. Pipe-detected (i.e., stdout is not a TTY): degrade to TSV with no chrome (cli-unix-purist wins). --plain flag exists as an explicit opt-in for screen-reader users who want prose even on a TTY (accessibility-advocate's add). Pipe-detected output is identical to --plain, which means mcpm status | cat and mcpm status --plain produce the same bytes — a property the screen-reader user can exploit without learning a new flag.

Tension 2 — Onboarding's "20th subcommand" doctor

The onboarding-novice argues for an mcpm doctor command that walks the failure chain (config → lockfile → binary → signature → runtime → secrets) and points at the first broken link. The locked v1.0 spec names 19 subcommands; adding a 20th breaks that contract. The cli-unix-purist counters that mcpm test <server> already exists and can absorb diagnostic depth via a --diagnostic flag. The vim-power-user is indifferent. The accessibility-advocate and visual-designer want something like doctor because the diagnostic output is manifestly easier to read and to render with severity glyphs than a 12-step debugging session.

The synthesis: fold the doctor flow into mcpm test <server> --diagnostic so the subcommand count stays at 19. The diagnostic output uses the same row-by-row chain the onboarding-novice's transcript shows, with the same ✓/✗ indicators visual-designer specified. mcpm test without --diagnostic stays the lightweight smoke test (spawn → initialize → tools/list → report) the locked spec describes.

Tension 3 — Browse mode in the TUI command palette

The vim-power-user proposes a : command palette with two modes: fuzzy (default) and browse (toggled with Ctrl+B). Browse mode shows the full grouped command list with descriptions — a gift to novices and screen-reader users. The onboarding-novice loves browse mode and wants it discoverable from the help bar. The cli-unix-purist is skeptical of TUI-only affordances that don't map back to the CLI. The visual-designer wants the browse-mode panel to be a styled overlay with proper typography. The accessibility-advocate is fine with it as long as the same data is reachable via mcpm help on the CLI.

Synthesis: adopt the palette + browse-mode, with the constraint that every palette command dispatches through the same internal command registry the CLI uses (vim-power-user's explicit ask). Browse mode reuses the prose from mcpm help <subcommand>, so maintaining one keeps the other in sync. Bottom hint bar advertises the toggle when in the palette: : cmd · Ctrl+B browse · Tab complete · Esc cancel.

Decisions — per-component picks

Eight components, one approach each, with rationale. Links go to the carrying agent's #design section.

1. mcpm-cli — 19 subcommands, output, completion, exit codes

Adopt the cli-unix-purist's 9-point CLI charter as the spec. Every subcommand supports --format=human|json|ndjson|yaml|tsv (default human on TTY, tsv when piped). Exit codes follow sysexits.h (64–78) with the mapping table in the purist's brief. stdout is data; stderr is chatter; the JSON error wrapper goes to stdout so it can be piped. mcpm help X and mcpm X --help produce byte-identical output. Manpages are generated from the same clap AST via clap_mangen. Shell completions ship for bash, zsh, fish, elvish, and powershell via clap_complete, with dynamic completion against mcpmanagerd's cached registry index when the daemon is up.

The vim-power-user's "every long flag has a short alias" ask is folded in; the onboarding-novice's "every --help ends with 3 worked examples" rule is locked as a PR-rule. The accessibility-advocate's --plain flag is added to the universal-flags list and auto-implied when stdout is not a TTY. The visual-designer's --ascii flag is added as a sibling: --no-color strips ANSI but keeps Unicode glyphs; --ascii strips both. The matrix of NO_COLOR / --no-color / --plain / --ascii / pipe-detect is in the accessibility brief's "behavior table" — that table is the spec.

2. TUI app — lazygit/k9s layout, modal model, keymap

Adopt the vim-power-user's four-state modal model (NORMAL / SEARCH / COMMAND / MODAL) with Esc always returning to NORMAL. The keymap extends the locked baseline with: g/G, Ctrl+D/Ctrl+U, digits 1–4 for direct pane focus (k9s-style), Tab/Shift+Tab per the locked spec, t for test and u for update on the focused entity, i as Enter alias. Arrow keys remain first-class equivalents to j/k/h/l.

Layout uses the visual-designer's measured proportions: 40-column fixed left pane at ≥120 cols (visual 30/70 because the right pane has lower density), 36 cols at 100–119, 32 cols at 80–99, stacked single-pane below 80. Density is a user setting (compact / comfortable / roomy) with comfortable as default. The status-line / hint bar fuses the vim-power-user's mode tag with the visual-designer's four-answer structure: daemon-health glyph · focused entity · scope indicator · context-aware key hints.

Mouse stays on by default per the locked spec but is trivially disabled via :set mouse off in the palette (vim-power-user's compromise). The Option/Alt drag bypass for native terminal selection stays. Pane separators are single-line box-drawing per visual-designer's standard glyph set.

3. Help system — mcpm help, --help, mdbook

Adopt the cli-unix-purist's dual contract: mcpm help X and mcpm X --help produce byte-identical output; both go through $PAGER when stdout is a TTY. The onboarding-novice's three-worked-examples rule is locked in; the visual-designer's typographic hierarchy (bold + underlined section heads, accent-colored flag names, dim inline comments) renders on TTY and degrades cleanly. ? in the TUI opens a contextual keymap modal with sections a screen reader can land on (accessibility-advocate's structural ask).

mdbook at docs.mcp-manager.dev/v1.0/ remains the deep-docs surface; every error code and every --help output links into it. Print-friendly mdbook rendering is verified for w3m/lynx/links per the vim-power-user; mdbook theme passes WCAG AA contrast per the accessibility-advocate; ASCII architecture diagrams get <figcaption>-equivalent text descriptions.

4. Error UX — 12-row taxonomy presentation

Adopt the visual-designer's severity × glyph × color matrix for which errors get modal overlays vs. inline blocks. Critical errors (E_SERVER_OOM, E_SERVER_FAILED, E_REGISTRY_SIGFAIL) get TUI modals; informational ones (E_REGISTRY_UNREACHABLE) stay as status-line notices. Layered on top: the accessibility-advocate's rule that the error code appears first, on its own visual line, before the prose, and is included when the user presses y to copy the suggested fix to the clipboard. The onboarding-novice's error template — code · what we tried · why · what to do · what to retry — is the prose schema for every error.

The vim-power-user's single-key navigation inside the error modal (y copy, l logs, e edit offending config when applicable, ? docs, Esc dismiss) is the keystroke spec. The cli-unix-purist's machine-readable error payload (error.code, error.exit_code, error.suggested[]) is the JSON contract. Stack traces never appear in user-facing output — they live in mcpm logs --daemon at trace level.

5. Onboarding — four worked transcripts

Adopt the onboarding-novice's four transcripts as the canonical reference, with three structural overlays. From cli-unix-purist: every prompt has a flag equivalent (the table in his non-interactive flags section is the contract). From accessibility-advocate: verbs first, glyphs second ("OK wrote ~/.config/...", not "✓ Wrote"); checkmark stays as decoration. From visual-designer: each transcript has a designed tone (lucky-day = warm, non-interactive = terse, project-scope = ritual, cloned-project = airlock); the cloned-project trust gate gets the warn-rule visual treatment.

The novice's --help-me tutorial mode is adopted as opt-in: never autolaunched, q exits cleanly, SPACE-paced (accessibility-advocate's reasoning: auto-advance is hostile to screen-reader users), real commands not simulations, state persisted to ~/.config/mcp-manager/state.toml for resume. The first-launch TUI overlay (three callouts, dismissable, never re-shown) is adopted. The "mcpm with no args is an orientation page" pattern is adopted (vim-power-user concedes since mcpm --help still produces the bare list).

6. $EDITOR integration

Adopt the cli-unix-purist's resolution order: $MCPM_EDITOR → $VISUAL → $EDITOR → vi. Temp file lives in $TMPDIR at mode 0600 with a .toml suffix and a header banner including vim: ft=toml modeline (vim-power-user). On editor exit non-zero: abort, print the temp-file path to stderr for recovery. On exit zero with changed content: validate, atomic write back, audit-log, mcpmanagerd reload. On validation failure: TUI modal with the line:column pointer (visual-designer's danger-coloured offending line), e re-enters the editor with changes preserved.

The onboarding-novice's fallback chain for macOS users with no $EDITOR set is adopted as opt-in via [ui] preferred_editor in config.toml, not auto-magic — the cli-unix-purist's concern about surprising the user wins on the default. The "Tip: set $EDITOR" disclosure after first use stays. mcpm config edit --in-place reads TOML from stdin for CI use.

7. Project-scope behaviors

Adopt the layered overlay model as locked in the UX config section, with three rendering improvements from the synthesis. From accessibility-advocate: per-line source tags ([USER], [PROJECT], [USER+PROJECT], [USER, DISABLED]) on mcpm project show --plain so indentation isn't the only signal. From visual-designer: mcpm config show --layered uses three semantic colors (success-green for project-wins, info-blue for user-survives, dim for keys) plus bold for server names. From vim-power-user: the TUI title bar shows scope:user or scope:project (acme) at all times; a :project diff palette command surfaces the overlay.

The onboarding-novice's "like venv" mental-model analogy is locked verbatim into mcpm help project: inherit="all" ≈ venv with --system-site-packages, allowlist ≈ named system packages, "none" ≈ vanilla venv. The cli-unix-purist's mcpm project diff exit-code contract (0 if no drift, EX_CONFIG 78 if drift) is the CI hook.

8. Trust gate prompts

Adopt the direnv-style sha256 pinning from the locked spec, rendered per the visual-designer's airlock treatment (yellow warn-rule, diff-style additions/overrides, bracketed accent-coloured choice letters). Layered on: from accessibility-advocate: a textual UNTRUSTED header (color is not the only signal), one option per line, explicit default ("default N"), a [D] "show full diff" option added. From onboarding-novice: a ? "explain trust gates" option in the prompt — pressing it prints eight lines of plain prose naming the direnv analogy and the commands to change one's mind later. From vim-power-user: q aliases to n; danger-tier ! for "trust forever" stays an audit-logged escape hatch.

Non-interactive equivalents from cli-unix-purist: --trust-from-file=PATH (file contains expected sha256, CLI fails on mismatch), --expected-sha=sha256:<hex>, --force (audit-logged loudly), and the belt-and-suspenders MCPM_AUTO_TRUST_PROJECTS=1 + --allow-auto-trust double-opt-in. Default refusal exits EX_NOUSER (67) so CI can branch on it.

Open questions

Five questions the synthesis cannot close without either more research or a project-level decision. None blocks v1.0 implementation; each gets a default position and a re-visit trigger.

  1. Does v1.0 ship the --announce sidecar stream? The accessibility-advocate's emacspeak-style "TUI writes state transitions to stderr when --announce is set" is a low-cost win for screen-reader users but adds a code path. Default position: ship in v1.0 because the implementation is <100 LoC and the user base is real. Re-visit if implementation cost balloons.
  2. Does the --help-me tutorial bundle into v1.0 or slip to v1.1? The onboarding-novice's five-lesson tutorial is the largest single feature add in this synthesis. Default position: v1.0 ships lessons 1–3 (orient, search, install); lessons 4–5 (TUI tour, Claude Code verification) defer to v1.1. Re-visit at feature freeze.
  3. YAML output format — ship or defer? The cli-unix-purist argued for five formats (human/json/ndjson/yaml/tsv) with the caveat that YAML is droppable. Default position: ship human/json/ndjson/tsv in v1.0; defer YAML to v1.1. Four formats covers every cited use case; the fifth pays for itself when users start asking.
  4. Themed color palette — Okabe-Ito as the default, or as a bundled alternative? The accessibility-advocate wants deep-blue / orange as the default running/failed pair (colorblind-safe); the visual-designer's default theme uses green/red. They both agree the high-contrast and Okabe-Ito themes ship; they disagree on the default. Default position: visual-designer's green/red default ships; Okabe-Ito is one of the three bundled themes and is recommended in the docs. Re-visit if user research surfaces a colorblind-base in the first 100 users.
  5. Hint-bar auto-hide after first 24h. The visual-designer proposed an hint_bar = "auto" mode that hides after a day, resurfacing on ?. The vim-power-user is open to it; the accessibility-advocate is wary. Default position: v1.0 ships hint bar always-on; "auto" mode is a v1.x community-driven config knob.
