The CLI Unix Purist's Frontend

--json everywhere. Meaningful exit codes aligned with sysexits.h. stdout is for data; stderr is for chatter. mcpm list | jq … must Just Work. Honor NO_COLOR, PAGER, EDITOR, and XDG_CONFIG_HOME. The TUI is a feature, not a tax — never the default when stdin isn't a TTY.

Thoughts

The UX design page shows a CLI with good instincts: --json on the few places where omitting it would be grossly negligent (status, test, search, outdated), NO_COLOR respected, $EDITOR spawned for edits, paranoid patterns for destructive ops. That's good — and nowhere near enough.

My stance is that every subcommand emits structured output on request. Not just the ones the designers happened to think of. That includes mcpm install (return the resolved version, package id, runtime, and projection targets), mcpm secret set (return backend, key id, and a SHA-256 of the value for CI verification), mcpm init (return the absolute paths of every file written for direnv-style wrappers), and yes, even mcpm tui via --list-keymap --json so a11y tooling can derive an alternative surface. The TUI itself isn't pipeable; the knowledge it contains is.

mcpm will live in other people's automation: Nix flakes, Makefiles, Dockerfiles, devcontainer postCreate hooks, CI runners, project bootstrap scripts, direnv hooks, chezmoi templates. None of those callers want to parse colored, prompt-flavoured human prose. They want mcpm status --json | jq '.servers[] | select(.state == "failed")' to Just Work in v1.0 — not "deferred to v1.1." The Heroku CLI style guide[5] says "Always have --json"; GitHub CLI does it with --json field1,field2 --jq ...[6]; Stripe CLI returns JSON by default and renders pretty only on TTY[7]. That's the bar.

The other thing that matters — and which the UX design page underplays — is stdin/stdout/stderr discipline. The UX design's "lucky-day interactive" init transcript writes "✓ Wrote ~/.config/mcp-manager/config.toml" to what looks like stdout. It must not. That progress chatter belongs on stderr. The thing on stdout — if anything — is the absolute path of the written file, one per line, so a wrapper script can pipe them into git add, chmod, a backup, or whatever. The Twelve-Factor App[9] and the classic Unix-philosophy literature[1] have been clear about this since the 1970s: data goes to stdout; everything else goes to stderr.

Exit codes are the other place we can do better than the lazy default. Most CLIs exit 0 on success and 1 on absolutely-anything-else, throwing away information. sysexits.h[2] has been on every Unix since BSD 4.3 and offers a perfectly serviceable taxonomy (64–78, full table below). A Makefile that wants to retry on transient failures but fail loudly on config errors can do mcpm test foo; case $? in 0) ;; 75) retry ;; *) exit $? ;; esac. That's a legitimately useful workflow we'd deny users by exiting 1 for everything.

Finally: the TUI must not autolaunch. If stdin isn't a TTY, or $TERM=dumb, or $CI is set, or --no-tty is passed, bare mcpm prints help to stderr and exits EX_USAGE. Never silently stall waiting for a key. The UX-design page is silent on this; I'm making it a tested invariant.

Arguments against my peers

vs. vim-power-user — keyboard-first, modal TUI

We agree 90% of the time. Where we diverge: vim-power-user's worldview assumes users live in the TUI. Most heavy users will never open it — they'll invoke mcpm from a Makefile, CI runner, or fresh shell out of direnv. The TUI is a discoverability and power-debug tool; the CLI is the load-bearing surface.

Concretely: vim-power-user wants bare mcpm to drop you into the TUI. I want bare mcpm to print help (to stderr) and exit EX_USAGE. If a user wants the TUI they type mcpm tui — same as k9s[11], lazygit[12], or btop. The cost of the hijack is that mcpm on a non-TTY CI runner would stall or bail with a vague error. Modal command lines inside the TUI (:-prefix) are fine, but every TUI action must have a CLI sibling so I can pipe data in via mcpm projection apply --from-stdin.

vs. accessibility-advocate — NO_COLOR, screen readers

Near-total agreement. NO_COLOR[3] is sacred; $COLORTERM for capability detection is fine; color is never the only carrier of information. Where I push further: --json is the screen reader's best friend. A blind developer doesn't want to parse a colored table out of aria-live regions — they pipe through jq and have a shell function that reads aloud with say or espeak. Cheaper, more robust, and more dignified than a special "accessible TUI mode" in v1.x. Every --json emitter is implicitly an a11y feature, which lets blind users skip the TUI entirely with no loss of functionality.

vs. onboarding-novice — discoverability, hand-holding

Sharpest disagreement. onboarding-novice's instinct is to make the interactive mcpm init the primary path, with the non-interactive variant an afterthought for "advanced users." I think it's the reverse: the non-interactive variant is the contract; the interactive variant is a convenience wrapper that collects answers and then calls the same underlying logic. The reason is testability — interactive flows can't be tested for parity, so if 1,000 users onboard interactively and 10 via --defaults -y, the non-interactive path bit-rots invisibly until Nix/devcontainer/CI users find it broken weeks after release.

I'm also opposed to "auto-detection prompts" that surprise the user. The UX-design "Detected: Docker. Enable Docker MCP Catalog as a registry? [y/N]" prompt is fine if it has a flag equivalent — --docker-enable=true|false|auto — with auto as default. Under -y, auto resolves to the registry's recommendation (likely false for paranoid defaults), with the decision printed to stderr for auditability. No silent enrollments.

vs. visual-designer — layout balance, color theory

I respect the work. My only ask: output is data first, visual second. The status glyphs (●, ○, ⚠) are accessible and meaningful, but the --json output must emit {"state":"running"|"stopped"|"failed"}, not the Unicode character. The human renderer derives the glyph from the data; the data is never the glyph. Second: pipes truncate at terminal width. A 120-column padded table that looks great in iTerm becomes garbled in mcpm status | tee output.log opened elsewhere. Default human output detects isatty(stdout) and downgrades to plain when piped — what ls, Stripe[7], gh[6], and kubectl get[13] all do.

Design — concrete decisions

Output modes — one flag, five formats

Every command that produces structured output accepts --format (or its synonyms --json, --yaml, --ndjson, --tsv). The universal flag --format=human|json|ndjson|yaml|tsv wins over the convenience aliases. Default is human when isatty(stdout), otherwise tsv. Rationale: a fresh user running mcpm status gets the pretty table; a script running mcpm status through a pipe gets parseable TSV without having to remember to pass a flag. This is the ls precedent, and it's been uncontroversial for forty years.

  • human — colorized, padded, glyph-rich. The current designs.
  • json — a single JSON object or array, pretty-printed by default, compact with --compact. Schema is stable per major version (--schema prints the JSON Schema for the active command).
  • ndjson — one JSON object per line. The right default for streaming commands (mcpm logs --follow --format=ndjson); each log entry is one line, ready for jq or Vector or Promtail.
  • yaml — same shape as json, YAML serialization. For users who pipe to yq or hand-edit the output. Optional; we can drop it if anyone protests, but the implementation cost is <200 LoC.
  • tsv — tab-separated, one row per record, no header by default (header with --header). The Unix-tool-friendly default. Tab-separated because spaces appear in server names; commas appear in registry URLs; tabs are the safe choice.

Exit codes — aligned with sysexits.h

sysexits.h[2] defines exit codes 64–78. We use those as the base layer and reserve 1–9 for the common-case codes a shell user expects. mcpm never exits with values outside this table.

CodeConstantWhen mcpm uses it
0EX_OKSuccess.
1(generic)Reserved for explicit policy-failure cases — e.g. mcpm test foo returns 1 when the server failed its health check but the CLI itself worked fine. Lets callers do mcpm test foo || retry without confusing "the CLI broke" with "the server failed."
2EX_USAGEArgument parsing errors — clap already exits with 2 by default[4]. Keep it.
64EX_USAGESame as 2 — but used by some callers historically. We accept that there's overlap; clap wins.
65EX_DATAERRE_CONFIG_INVALID (canonical config failed validation) and any "input was syntactically wrong" error.
66EX_NOINPUTProject config file declared but not on disk; --secrets-from-file=PATH file missing; etc.
67EX_NOUSERE_PROJECT_UNTRUSTED — semantically "the calling identity is not authorized for this project config."
68EX_NOHOSTE_REGISTRY_UNREACHABLE — a remote we needed couldn't be resolved or reached.
69EX_UNAVAILABLEE_KEYCHAIN_UNAVAILABLE and E_DAEMON_UNAVAILABLE (mcpmanagerd not running and couldn't be spawned).
70EX_SOFTWAREInternal panic, unexpected deserialization failure, anything that means "this is our bug, file a report."
71EX_OSERROS-level failure — launchctl / systemctl rejected our service registration, fork failed, etc.
72EX_OSFILEA required OS file (e.g. the UDS socket directory under $XDG_RUNTIME_DIR) is missing or wrong-permissioned.
73EX_CANTCREATWe tried to create ~/.config/mcp-manager/config.toml and couldn't (disk full, EACCES).
74EX_IOERRRead/write failure on a file that exists and we own — usually disk full mid-write.
75EX_TEMPFAILTransient failure; the caller should retry. Registry index fetch returned 503, daemon was restarting, etc. Distinguished from EX_NOHOST (which is "the remote isn't there at all").
76EX_PROTOCOLE_SPEC_UNSUPPORTED and E_REGISTRY_SIGFAIL — protocol-level rejection, the remote spoke wrong.
77EX_NOPERMSandbox refused (Linux bubblewrap dropped a capability we needed), Keychain access denied by TouchID, etc.
78EX_CONFIGE_CONFIG_CONFLICT, E_PROJECTION_DRIFT, E_DAEMON_VERSION — "the configuration of the system as a whole is inconsistent."
130(SIGINT)User pressed Ctrl+C. Standard shell convention (128 + signal); enforced by clean signal handling rather than letting Rust panic with abort.
143(SIGTERM)Same convention, for daemons or other termination signals.

The exit-code-to-error-code mapping is one-to-many: every error code from the UX-design taxonomy maps to exactly one exit code (table above), but multiple error codes can share an exit code. Callers who need fine-grained discrimination use --format=json and read the error.code field. Shell users who want a quick "did it work? did it maybe-fail?" can branch on the exit code alone.

TTY discipline — when (not) to launch the TUI

The TUI is opt-in via mcpm tui. Bare mcpm with no args prints help to stderr and exits 2 — the git precedent. In addition, mcpm tui itself refuses to launch when any of these are true:

  • !isatty(stdin) or !isatty(stdout) — print to stderr "mcpm tui requires a TTY; use mcpm status --json for scripted access" and exit EX_USAGE.
  • $TERM=dumb — same.
  • $CI, $BUILDKITE, $GITHUB_ACTIONS, or $GITLAB_CI is set — same. (Following the well-trodden is-ci heuristic.)
  • --no-tty is passed explicitly — same.

Conversely, no other subcommand implicitly launches the TUI. mcpm install with a missing required secret does not "drop the user into the TUI to fix it"; it exits EX_CONFIG with a clear error and a suggested command. This is the cargo model[8]: every subcommand is single-shot and predictable.

Schemas live in crates/mcpm-protocol/schemas/v1/ next to the wire-protocol schemas. They're emitted from a single schemars-derive on the same Rust types the CLI uses internally, so drift is impossible: if you change a field in the Rust struct, the JSON schema regenerates on next build.

Shell completions — generate, ship, install

clap_complete[4] handles this for free. Completions for Bash, Zsh, Fish, Elvish, and PowerShell generated at build time and shipped under share/mcpm/completions/; the installer script symlinks into the right completion dir. mcpm completions <shell> emits to stdout for sourcing; mcpm completions install auto-detects $SHELL and writes the file.

Completions are smart, not dumb. mcpm install <TAB> queries mcpmanagerd's cached registry index (no network) and returns matching packages. mcpm start <TAB> returns names of stopped servers. mcpm secret set <TAB> returns secret names declared by installed servers but not yet set in the keychain. mcpm project allow <TAB> auto-completes to the project config path discovered by walking from cwd. Implementation: clap_complete::dynamic with a 50ms-deadline UDS roundtrip to the daemon; falls back to static completions when the daemon isn't up. This is the level fly, gh, and kubectl ship; users expect it.

mcpm help vs. --help parity, and manpages

Two contracts:

  1. mcpm help <subcommand> and mcpm <subcommand> --help produce byte-identical output. (Test enforced.) Reason: users come from different traditions — git users type git help X, GNU-tools users type X --help, BSD-tools users type man X. Don't make them learn ours.
  2. mcpm ships manpages. mcpm(1) is the top-level summary; mcpm-install(1), mcpm-status(1), etc. for each subcommand. Generated at build time from the same clap AST via clap_mangen. Installed under share/man/man1/. The installer script registers them with the user's $MANPATH or /usr/local/share/man/man1.

mcpm help output goes through $PAGER when stdout is a TTY, identical content to stdout when piped. Examples are real (with real arguments) — the UX design already commits to this, I'm just ratifying.

Pipe-friendliness — recipes that must work in v1.0

Every line below is a tested invariant in CI: 

# Restart every failed server
mcpm status --json | jq -r '.data[] | select(.state == "failed") | .name' | xargs -r mcpm restart

# Export a registry's full package catalog as TSV for a spreadsheet
mcpm search --source=official '*' --format=tsv --header > catalog.tsv

# Pipe logs into a structured log aggregator
mcpm logs github --follow --format=ndjson | vector --config vector.toml

# Diff your project config against your teammate's
mcpm config get --scope=project --format=yaml > theirs.yaml
diff theirs.yaml <(mcpm config get --scope=project --format=yaml)

# Migrate secrets between machines (without ever printing the secret)
ssh oldhost 'mcpm secret list --json' | jq -r '.data[].name' | \
  while read s; do ssh oldhost "mcpm secret get $s --format=raw" | mcpm secret set "$s" --from-stdin; done

# Trust a teammate's project config from a known-good SHA in a commit
echo "sha256:$EXPECTED_SHA" > /tmp/expected
mcpm project allow --trust-from-file=/tmp/expected || exit 78

# Check if mcpm needs an update, machine-readable
mcpm outdated --json | jq -e '.data | length == 0'  # exit 0 = all up to date

# Tag a release: ensure all servers are healthy first
mcpm status --json | jq -e '.data | all(.state == "running")' || exit 1

$EDITOR integration — the rules

  • Resolution order: $MCPM_EDITOR, $VISUAL, $EDITOR, vi. ($VISUAL before $EDITOR is POSIX precedent.)
  • Invoke via $SHELL -c only when the value contains shell metacharacters; else direct exec. Pass exactly one argument: an absolute path to a temp file in $TMPDIR at mode 0600 with a .toml suffix for syntax detection.
  • On editor exit non-zero: treat as abort; temp-file path printed to stderr for recovery. On exit zero with changed content: validate before commit. On validation failure: re-spawn the editor with the error appended as a comment block at the top.
  • Non-interactive equivalent: mcpm config edit --in-place reads TOML from stdin, validates, writes atomically. This is what CI uses.

Project-scope behaviors — pipeable diff/list

mcpm project list --json emits every .mcp-manager.toml in the trust database, with paths, hashes, and last-allowed timestamps. mcpm project diff [<path>] emits a unified diff (default) or a structured diff (with --format=json) of the project config against the trusted-on-record version, so you can detect drift in CI. Both commands return EX_OK (0) when there's no drift and EX_CONFIG (78) when there is, so a shell-level if mcpm project diff; then … Just Works.

Trust-gate prompts — non-interactive equivalent

The interactive [y/n/e] prompt for "trust this project config" gets these non-interactive variants:

  • mcpm project allow --trust-from-file=PATH — the file contains the expected SHA-256 (one line, format sha256:<hex>). CLI computes the project config's actual hash, compares, exits EX_OK if match, EX_NOUSER (67) if not. Audit-logged either way.
  • mcpm project allow --expected-sha=sha256:<hex> — same semantics, inline hex. Useful when the trust SHA comes from a git commit message or PR body.
  • mcpm project allow --force — unconditional trust grant, audit-logged loudly with granted_by: "forced". Discouraged but available.
  • MCPM_AUTO_TRUST_PROJECTS=1 — environment-driven blanket auto-trust, only respected if mcpm is also running with --allow-auto-trust. The belt-and-suspenders is intentional: a malicious project README can set the env var, but it can't set the CLI flag. (We follow the direnv precedent here.)

The --trust-from-file flag is the right one for CI runners and devcontainer postCreate hooks: the expected SHA is committed to the repo in (say) .mcpm-trust, the bootstrap script invokes mcpm project allow --trust-from-file=.mcpm-trust, and if anyone tampers with .mcp-manager.toml without updating .mcpm-trust, the bootstrap fails loudly.

The most important property: the human and the script see the same exit code. A user typing echo $? after a refused trust prompt sees 67; a CI runner running mcpm project allow --trust-from-file=… on a tampered project sees the same 67. No mode bifurcation.

Error UX — machine-parseable error codes

I align with the UX design's E_* taxonomy but add a few invariants:

  • Every error code is documented in mcpm help errors and on the docs site (docs.mcp-manager.dev/v1.0/errors/E_SECRET_MISSING).
  • The --format=json error wrapper (above) includes the exit_code field redundantly so a single jq read can branch on it without invoking echo $?.
  • The suggested array in the error payload is machine-readable: each entry is a shell-quote-safe command. A user wrapper can do mcpm install foo --format=json || jq -r '.error.suggested[0]' | sh if it wants to chain the suggested fix.
  • Stack traces never appear in the user-facing error. They go to the daemon log (mcpm logs --daemon) at trace level, and are surfaced only when MCPM_LOG=trace is set.

Pager and color discipline

  • mcpm help and mcpm logs --tail N (without --follow) pipe through $PAGER when stdout is a TTY, never otherwise.
  • If $PAGER isn't set we use less -FRX — F = exit immediately if output fits on one screen, R = pass through ANSI color codes, X = don't init/deinit the terminal (preserves scrollback).
  • Color is on by default when stdout is a TTY and NO_COLOR is unset and $TERM isn't dumb. We never write 256-color or truecolor escapes when $COLORTERM says otherwise.
  • --no-color as a flag is accepted and ratchets through to the daemon (logs from mcpm logs --daemon --no-color are stripped server-side, since the daemon also colorizes when it knows the receiving client wants colors).

Summary — the 9-point CLI charter

  1. Every subcommand supports --format=human|json|ndjson|yaml|tsv.
  2. Exit codes follow sysexits.h; mapping documented and tested.
  3. stdout is data; stderr is chatter — incl. error cases (JSON error payload goes to stdout so it can be piped).
  4. No banner, no telemetry, no surprises. Bare mcpm prints help to stderr and exits 2.
  5. The TUI never autolaunches. mcpm tui is the only entry point; it refuses to start when stdin isn't a TTY.
  6. Every interactive flow has a flag equivalent.
  7. $EDITOR, $PAGER, $VISUAL, $NO_COLOR, $XDG_* honored. Documented in mcpm help env.
  8. Shell completions for five shells, dynamically aware of daemon state.
  9. mcpm help X ≡ mcpm X --help byte-identical; manpages generated and installed.

Ship that and mcpm sits on the same shelf as gh, fly, aws, stripe. Skip any of it and it feels like an early-2010s npm subcommand wrapper.
