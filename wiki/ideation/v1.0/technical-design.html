Key invariants

  • mcpd is the single authority over canonical state. CLI/TUI/external clients always talk to mcpd over UDS; no client reads/writes the canonical TOML directly (except $EDITOR via the edit-and-reload flow, which is mediated).
  • Secrets never cross a process boundary except via env injection at spawn time. mcpd reads from the keychain and writes to the child server process's env when launching it. The wrapper mcpm exec never sees the value.
  • One server, one process, one supervisor. If Cursor and Claude Code both want the github MCP, mcpd hands them stdio-pipes to the same spawned process. No duplication.
  • All state mutations are audit-logged. Every config.change, secret.read, server.spawn, projection.write, service.unregister emits a JSONL line with timestamp + actor + event-specific payload.

mcpd Binary entrypoint. Loads config, starts the tokio runtime, hosts the UDS server, wires together all the other crates. Implements service-manager (launchd/systemd-user) registration. S3

mcp-secrets SecretStore trait + OsKeyringStore (macOS Keychain via SecItemAdd/CopyMatching; Linux libsecret via the keyring crate) + EnvVarPassthroughStore + LayeredSecretStore composition. Plaintext values in secrecy::SecretString with zeroize. C
mcp-projector Reads the canonical config + project state; writes editor configs using managed-block fenced regions. Per-editor logic is data-driven from TOML manifests in manifests/toolchains/. Supports both bundled Tier-1 editors and user-authored custom manifests. S6
mcp-registry Multi-source federation. One RegistrySource trait; per-source adapters for the 3 baked-in registries (official, github, docker) plus user-added private sources. BM25 local search over cached indexes. Pubkey verification via mcp-trust. A
mcp-logs Three log-stream sinks (mcpd's tracing logs, per-server stdout/err, audit log). Each backed by a ring buffer (~4-10MB) + on-disk rotation. Exposes a logs.tail RPC method on the wire (streaming). directive #3
mcp-trust TUF-lite trust verification. Holds the baked-in root pubkey; fetches + verifies trust.toml at install + refresh-on-TTL. Also implements project-config trust gate (sha256-pin in ~/.config/mcp-manager/trust.toml). A + UX design

Wire protocol (mcpm ↔ mcpd)

JSON-RPC 2.0 over Unix domain socket. No HTTP, no TCP, no WebSocket. Single socket: $XDG_RUNTIME_DIR/mcpd.sock (macOS: ~/Library/Application Support/mcp-manager/mcpd.sock; Linux: $XDG_RUNTIME_DIR/mcpd.sock or /run/user/UID/mcpd.sock).

Authentication

  • Socket file permissions: 0600, owned by the user running mcpd. No further auth needed for any client running as the same UID.
  • Defensive secondary check: every accepted connection's peer credentials are verified via SO_PEERCRED (Linux) / LOCAL_PEERCRED (macOS getsockopt). Mismatched UID → close connection + audit-log auth.failed.
  • No bearer tokens, no shared secrets. The kernel is the source of truth for "is this caller me?". Per S4's auth research.

Versioning

The wire schema lives in the mcp-protocol crate. Its version is independent of mcpd's release version. JSON-RPC 2.0's jsonrpc field is always "2.0"; we add a custom "mcpm_wire_version" to every request and response so clients/daemons can detect drift early. The wire-version compat policy follows semver: minor versions add methods; major versions remove or rename them. Per S4's versioning research.

Streaming

logs.tail uses a streaming response (a single JSON-RPC request followed by a stream of partial notifications on the same connection). The client can cancel by closing the connection. mcpd applies backpressure via the bounded tokio channel feeding the response.

Auto-spawn behavior

mcp-client's connect() implements: (1) try connecting to mcpd.sock; (2) if ENOENT or ECONNREFUSED, fork+spawn mcpd as a background process; (3) wait up to 5s for the socket to appear (poll every 50ms); (4) retry connection. flock(2) on a sibling lockfile prevents two parallel mcpm invocations from racing to spawn two daemons.

End-to-end data flows

Flow A: mcpm install github-mcp

  1. mcpm parses args → builds install JSON-RPC request.
  2. mcp-client dials UDS (auto-spawns mcpd if absent).
  3. mcpd receives → mcp-registry searches across active sources (BM25 over cached indexes; refreshes if TTL expired).
  4. Pubkey verified via mcp-trust (lookup in cached trust.toml).
  5. mcp-registry resolves the version (range → exact via the registry's index).
  6. Package downloaded (Python via uvx, Node via bun, native binary via curl + minisign verify).
  7. mcp-core writes a new [server.github-mcp] stanza to canonical config (atomic temp-rename).
  8. mcp-core updates lockfile with resolved version + checksum.
  9. mcp-projector runs projection.sync for every enabled projection target (Cursor, Claude Code, …) using managed-block writes.
  10. Audit-log entries: install.start, config.change, projection.write × N tools, install.complete.
  11. mcpd returns InstallResult with the resolved version + a list of missing secrets.
  12. mcpm prints the result; if missing secrets, prints the exact mcpm secret set X commands to run.

Flow B: Editor spawns an MCP server via mcpm exec

  1. Editor's MCP config (projected by mcp-projector) reads command = "mcpm", args = ["exec", "github-mcp"].
  2. Editor spawns mcpm exec github-mcp as a child process, pipes stdio.
  3. mcpm exec dials mcpd. Auto-spawns daemon if not running (200ms one-time + flock).
  4. JSON-RPC server.start → mcpd looks up the server config.
  5. mcpd checks if the server is already running (cached process). If yes, reuses it; if no, calls mcp-supervisor to spawn.
  6. mcp-supervisor:
    • Resolves secrets via mcp-secrets. Audit: secret.read for each.
    • Builds env-var injection map. Plaintext lives in secrecy::SecretString until the spawn syscall.
    • Spawns inside isolation wrapper (devenv profile + bubblewrap, etc.).
    • Audit: server.spawn.
    • Tokio task watches the child: stdout → mcp-logs, stderr → mcp-logs, exit → restart policy.
  7. mcpd creates a pipe pair and tells mcpm exec: "your stdio is now linked to the server."
  8. mcpm exec becomes a stdio relay: editor's stdin → mcpd → server stdin; server stdout → mcpd → editor's stdout. Bytes flow.
  9. When editor exits, mcpm exec closes; mcpd decrements the server's refcount. If refcount → 0 and the server has no other clients, supervisor keeps it running for a configurable idle TTL (default: forever — server stays alive between editor sessions).

Flow C: mcpm secret set GITHUB_TOKEN

  1. mcpm reads the value via rpassword (TTY only, hidden input). Value lives in secrecy::SecretString.
  2. mcpm dials mcpd; sends secret.set { name: "GITHUB_TOKEN" } followed by the value as a streaming parameter (length-prefixed, never logged).
  3. mcpd's handler resolves the active SecretStore (LayeredSecretStore writes only to OsKeyringStore; EnvVarPassthroughStore is read-only).
  4. OsKeyringStore calls SecItemAdd (macOS) / libsecret_password_store_sync (Linux). Service: dev.mcp-manager.mcpd, account: <global>/GITHUB_TOKEN (or <server-name>/GITHUB_TOKEN for per-server scoping in v1.1).
  5. Audit: secret.write { name: "GITHUB_TOKEN", store: "os-keyring", outcome: "ok" }. Value never appears in any audit field.
  6. mcpd returns success. mcpm zeroes its copy of the value and exits.

Flow D: Server crash → restart with backoff

  1. mcp-supervisor's tokio watcher sees the child process exit with non-zero status.
  2. Audit: server.crash { name, exit_code, signal?, last_log_line }.
  3. Supervisor checks restart policy: how many attempts in the last window_secs?
  4. If attempts < attempts_max: compute delay = min(base × 2^attempt × (1 + rand(0, 0.3)), cap). Sleep. Re-spawn (same secrets, same isolation).
  5. If attempts ≥ attempts_max: mark server failed in registry. Stop retrying. Audit: server.failed { attempts, window }. TUI shows the failure with the last log line; user must run mcpm restart github-mcp explicitly to clear.
  6. If the child was OOM-killed (Linux: memory.events.oom_kill incremented; macOS: SIGKILL + recent memory-pressure → inferred): audit server.oom instead of server.crash, count toward attempts, otherwise same flow.

Flow E: mcpm tui opens, user navigates

  1. mcpm subprocess starts ratatui app. Captures terminal alternate-screen + mouse events via crossterm.
  2. App opens UDS connection to mcpd. Subscribes to server.list + logs.tail "combined" streaming.
  3. Three left panes render from server.list / projection.list / secret.list snapshots.
  4. User presses ↓ to focus a server; right pane updates to logs.tail "server:<name>". Old subscription is dropped.
  5. User presses e: app suspends terminal, spawns $EDITOR /tmp/mcpm-edit-XXXX.toml as a foreground child. On editor exit, app validates via config.validate RPC, then commits via config.put (atomic). Re-enters alternate screen.
  6. User presses q: app drops streams, restores terminal, exits.

Security

  • Defense in depth on the IPC layer: 0600 socket perms + SO_PEERCRED + structured-log of every connection accept/reject.
  • No plaintext secrets on disk outside the OS keychain. Audit-log NEVER contains secret values (fuzz-tested invariant).
  • Project-config trust gate for any cloned-from-elsewhere .mcp-manager.toml; sha256-pinned, audit-logged.
  • Registry index signatures verified before parse; verify-when-present on underlying packages.
  • Code-signed macOS binaries (Apple Developer Program + notarization). Linux: minisign-signed tarballs.
  • No CVE-track inheritance: we don't ship a TCP-bound HTTP server in v1.0, eliminating the CVE-2025-6514 attack surface entirely.

Semver policy

  • Major (X.0.0): wire-protocol breaking changes; canonical-config schema breaking changes. Rare.
  • Minor (1.X.0): new features, new wire methods (additive), new config keys (with sensible defaults). Most releases.
  • Patch (1.0.X): bug fixes, security fixes, manifest updates (new editors supported, new MCP spec versions in the allow-list).

Update mechanism

v1.0 does not ship a self-updater. Users update by re-running the curl installer (or nix flake update). A future version may add mcpm self update for the curl-installed users; this would download + verify + atomically swap the binary.

Implementation-level open questions

These are decisions that don't need product-owner input, but engineers will hit them. Captured here for early thought rather than mid-implementation surprise.

Idle-server termination policy

Servers with refcount=0 (no editor connected) currently stay alive forever. Should we add a configurable idle-TTL after which the supervisor stops them gracefully? Pro: memory hygiene for users with 20+ rarely-used servers. Con: cold-start cost when an editor reconnects. Suggested default: 30min idle → stop; configurable per-server via [server.<name>].idle_ttl_secs.

cgroupv2 unavailability on older Linux distros

cgroupv2-only distros (recent Ubuntu, Fedora) are fine. Distros still on cgroupv1 (older RHEL/CentOS) lose per-server memory limits and OOM detection. Options: (a) fall back to RLIMIT_AS + SIGKILL-with-warning detection (degrades gracefully but no perfect OOM signal), (b) refuse to start with a clear error, (c) attempt to detect cgroupv1 and use it (high implementation cost, low return).

macOS jetsam OOM-inference heuristic

macOS doesn't expose a clean OOM-kill event. We infer from SIGKILL + recent memory pressure (host_processor_info). What's the right heuristic threshold for "recent" and "high"? Initial guess: SIGKILL + memory-pressure within last 30s + server's last-known RSS > 80% of any limit. Calibrate after we have real telemetry — but oh wait, we have no telemetry. So: calibrate by user reports.

Trust manifest fetch on first run (network bootstrap)

First-run mcpm init needs to fetch trust.toml to seed its trust state. If the user is offline, what happens? Options: (a) refuse to init with a clear error + hint to retry, (b) init in "trusted-baked-in only" mode (no registry refresh; only the 3 default sources at their baked-in pubkeys; warn on every CLI call until refreshed), (c) silently use baked-in pubkeys without warning. Recommend (b).

Concurrent config.put from CLI + TUI + $EDITOR

If the TUI is running and the user simultaneously hand-edits config.toml in vim, the two writes race. Mitigation: every config.put includes the prior file_hash (CAS-style). If hash mismatches, the put fails with a clear "config changed on disk" error and the TUI re-reads + offers to merge or discard. This is fail-safe but the error UX needs work.

What ships in mcp-protocol vs mcp-client?

The split matters: mcp-protocol is the public-facing wire crate (third parties depend on this if they build alternative clients). mcp-client is the in-tree convenience layer used by mcpm. mcp-protocol should be small and stable; mcp-client can churn freely.
