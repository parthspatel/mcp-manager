Key invariants

  • mcpmanagerd is the single authority over canonical state. CLI/TUI/external clients always talk to mcpmanagerd over UDS; no client reads/writes the canonical TOML directly (except $EDITOR via the edit-and-reload flow, which is mediated).
  • Secrets never cross a process boundary except via env injection at spawn time. mcpmanagerd reads from the keychain and writes to the child server process's env when launching it. The wrapper mcpm exec never sees the value.
  • Singleton-by-default, per-client opt-out. By default (singleton = true in a server's config), if Cursor and Claude Code both want the github MCP, mcpmanagerd hands them stdio-pipes to the same spawned process. mcpmanagerd maintains a refcount per server; each mcpm exec increments, each editor exit decrements. When refcount → 0, the supervisor starts an idle timer (see idle_ttl_secs in the config schema). On the next mcpm exec, the refcount increments and the timer is cancelled; if the timer fires first, the server is gracefully stopped. Per-server singleton = false flips this: each mcpm exec invocation gets a fresh process, indexed by (server_name, client_id) in the supervisor. Useful for stateful or sandboxed servers where crash blast-radius matters more than memory savings.
  • All state mutations are audit-logged. Every config.change, secret.read, server.spawn, projection.write, service.unregister emits a JSONL line with timestamp + actor + event-specific payload.

Wire protocol (mcpm ↔ mcpmanagerd)

JSON-RPC 2.0 over Unix domain socket. No HTTP, no TCP, no WebSocket. Single socket: $XDG_RUNTIME_DIR/mcpmanagerd.sock (macOS: ~/Library/Application Support/mcp-manager/mcpmanagerd.sock; Linux: $XDG_RUNTIME_DIR/mcpmanagerd.sock or /run/user/UID/mcpmanagerd.sock).

Authentication

  • Socket file permissions: 0600, owned by the user running mcpmanagerd. No further auth needed for any client running as the same UID.
  • Defensive secondary check: every accepted connection's peer credentials are verified via SO_PEERCRED (Linux) / LOCAL_PEERCRED (macOS getsockopt). Mismatched UID → close connection + audit-log auth.failed.
  • No bearer tokens, no shared secrets. The kernel is the source of truth for "is this caller me?". Per S4's auth research.

Versioning

The wire schema lives in the mcpm-protocol crate. Its version is independent of mcpmanagerd's release version. JSON-RPC 2.0's jsonrpc field is always "2.0"; we add a custom "mcpm_wire_version" to every request and response so clients/daemons can detect drift early. The wire-version compat policy follows semver: minor versions add methods; major versions remove or rename them. Per S4's versioning research.

Streaming

logs.tail uses a streaming response (a single JSON-RPC request followed by a stream of partial notifications on the same connection). The client can cancel by closing the connection. mcpmanagerd applies backpressure via the bounded tokio channel feeding the response.

Auto-spawn behavior

mcpm-client's connect() implements: (1) try connecting to mcpmanagerd.sock; (2) if ENOENT or ECONNREFUSED, fork+spawn mcpmanagerd as a background process; (3) wait up to 5s for the socket to appear (poll every 50ms); (4) retry connection. flock(2) on a sibling lockfile prevents two parallel mcpm invocations from racing to spawn two daemons.

First-run trust bootstrap (offline-safe)

mcpm init needs the trust manifest to seed registry pubkeys. If the user is offline at first run:

  1. mcpm-trust attempts to fetch trust.toml from the baked-in URL.
  2. On any network failure (DNS, TLS, 4xx/5xx, timeout), fall back to "trusted-baked-in only" mode: use only the 3 default registry pubkeys baked into the mcpmanagerd binary. Set [root].mode = "baked-in-fallback".
  3. In this fallback mode, no registry can be refreshed and no user-added registries can be verified. Every mcpm CLI invocation prints a one-line warning at the top: warning: trust manifest never fetched; using baked-in keys only. Run `mcpm trust refresh` when network is available.
  4. Once a successful refresh happens (manually via mcpm trust refresh, or automatically on the next online mcpm call), [root].mode flips to "fetched" and the warning stops.

End-to-end data flows

Flow A: mcpm install github-mcp

  1. mcpm parses args → builds install JSON-RPC request.
  2. mcpm-client dials UDS (auto-spawns mcpmanagerd if absent).
  3. mcpmanagerd receives → mcpm-registry searches across active sources (BM25 over cached indexes; refreshes if TTL expired).
  4. Pubkey verified via mcpm-trust (lookup in cached trust.toml).
  5. mcpm-registry resolves the version (range → exact via the registry's index).
  6. Package downloaded (Python via uvx, Node via bun, native binary via curl + minisign verify).
  7. mcpm-core writes a new [server.github-mcp] stanza to canonical config (atomic temp-rename).
  8. mcpm-core updates lockfile with resolved version + checksum.
  9. mcpm-projector runs projection.sync for every enabled projection target (Cursor, Claude Code, …) using managed-block writes.
  10. Audit-log entries: install.start, config.change, projection.write × N tools, install.complete.
  11. mcpmanagerd returns InstallResult with the resolved version + a list of missing secrets.
  12. mcpm prints the result; if missing secrets, prints the exact mcpm secret set X commands to run.

Flow B: Editor spawns an MCP server via mcpm exec

  1. Editor's MCP config (projected by mcpm-projector) reads command = "mcpm", args = ["exec", "github-mcp"].
  2. Editor spawns mcpm exec github-mcp as a child process, pipes stdio.
  3. mcpm exec dials mcpmanagerd. Auto-spawns daemon if not running (200ms one-time + flock).
  4. JSON-RPC server.start → mcpmanagerd looks up the server config.
  5. mcpmanagerd consults the server's singleton setting:
    • singleton = true (default): look up the server in the per-name process map. If a process is already running, hand this client a stdio pipe to it (bump refcount, cancel any idle timer). If not, call mcpm-supervisor to spawn a fresh process and store it under the server's name.
    • singleton = false: always spawn a fresh process for this client. The supervisor indexes the new process by (server_name, client_id) rather than by server name alone. idle_ttl_secs applies per-process; each instance has its own timer.
  6. mcpm-supervisor:
    • Resolves secrets via mcpm-secrets. Audit: secret.read for each.
    • Builds env-var injection map. Plaintext lives in secrecy::SecretString until the spawn syscall.
    • Spawns inside isolation wrapper (devenv profile + bubblewrap, etc.).
    • Audit: server.spawn { singleton: bool, client_id: "<uds-peer-id>|shared" }. singleton=true spawns log client_id="shared"; singleton=false spawns log the actual client identity (the peer-credentialed connection that triggered the spawn). Makes the audit log self-describing for debugging "why are there N processes?".
    • Tokio task watches the child: stdout → mcpm-logs, stderr → mcpm-logs, exit → restart policy.
  7. mcpmanagerd creates a pipe pair and tells mcpm exec: "your stdio is now linked to the server."
  8. mcpm exec becomes a stdio relay: editor's stdin → mcpmanagerd → server stdin; server stdout → mcpmanagerd → editor's stdout. Bytes flow.
  9. When editor exits, mcpm exec closes; mcpmanagerd decrements the server's refcount. If refcount → 0 and the server has no other clients, the supervisor starts an idle timer of [server.<name>].idle_ttl_secs (default 1800s / 30 min). idle_ttl_secs = 0 stops the server immediately when refcount drops to 0; negative keeps the server alive forever (useful for "always warm" servers like an LSP-backed code-graph). On any subsequent mcpm exec, the refcount increments and the timer is cancelled.

Flow C: mcpm secret set GITHUB_TOKEN

  1. mcpm reads the value via rpassword (TTY only, hidden input). Value lives in secrecy::SecretString.
  2. mcpm dials mcpmanagerd; sends secret.set { name: "GITHUB_TOKEN" } followed by the value as a streaming parameter (length-prefixed, never logged).
  3. mcpmanagerd's handler resolves the active SecretStore (LayeredSecretStore writes only to OsKeyringStore; EnvVarPassthroughStore is read-only).
  4. OsKeyringStore calls SecItemAdd (macOS) / libsecret_password_store_sync (Linux). Service: dev.mcp-manager.mcpmanagerd, account: <global>/GITHUB_TOKEN (or <server-name>/GITHUB_TOKEN for per-server scoping in v1.1).
  5. Audit: secret.write { name: "GITHUB_TOKEN", store: "os-keyring", outcome: "ok" }. Value never appears in any audit field.
  6. mcpmanagerd returns success. mcpm zeroes its copy of the value and exits.

Flow D: Server crash → restart with backoff

  1. mcpm-supervisor's tokio watcher sees the child process exit with non-zero status.
  2. Audit: server.crash { name, exit_code, signal?, last_log_line }.
  3. Supervisor checks restart policy: how many attempts in the last window_secs?
  4. If attempts < attempts_max: compute delay = min(base × 2^attempt × (1 + rand(0, 0.3)), cap). Sleep. Re-spawn (same secrets, same isolation).
  5. If attempts ≥ attempts_max: mark server failed in registry. Stop retrying. Audit: server.failed { attempts, window }. TUI shows the failure with the last log line; user must run mcpm restart github-mcp explicitly to clear.
  6. If the child was OOM-killed, audit server.oom (instead of server.crash), count toward the restart-attempts budget, otherwise same flow. OOM detection per platform:
    • Linux + cgroupv2 (modern Ubuntu / Fedora / Arch): watch memory.events.oom_kill increment. Deterministic.
    • Linux + cgroupv1 (legacy distros — older RHEL, CentOS 7, etc.): per-server memory limits via RLIMIT_AS + observe SIGKILL on child exit. Emit a "may have been OOM, no perfect signal on this kernel" warning in the audit details. Graceful degradation.
    • macOS: no native OOM event. Inferred from all three: SIGKILL on child exit + memory-pressure within the last 30 s (host_processor_info) + server's last-known RSS > 80% of any configured limit. If all three match, classify as server.oom; otherwise server.crash.

Flow E: mcpm tui opens, user navigates

  1. mcpm subprocess starts ratatui app. Captures terminal alternate-screen + mouse events via crossterm.
  2. App opens UDS connection to mcpmanagerd. Subscribes to server.list + logs.tail "combined" streaming.
  3. Three left panes render from server.list / projection.list / secret.list snapshots.
  4. User presses ↓ to focus a server; right pane updates to logs.tail "server:<name>". Old subscription is dropped.
  5. User presses e: app suspends terminal, spawns $EDITOR /tmp/mcpm-edit-XXXX.toml as a foreground child. On editor exit, app validates via config.validate RPC, then commits via config.put (atomic). Re-enters alternate screen.
  6. User presses q: app drops streams, restores terminal, exits.

Security

  • Defense in depth on the IPC layer: 0600 socket perms + SO_PEERCRED + structured-log of every connection accept/reject.
  • No plaintext secrets on disk outside the OS keychain. Audit-log NEVER contains secret values (fuzz-tested invariant).
  • Project-config trust gate for any cloned-from-elsewhere .mcp-manager.toml; sha256-pinned, audit-logged.
  • Registry index signatures verified before parse; verify-when-present on underlying packages.
  • Code-signed macOS binaries (Apple Developer Program + notarization). Linux: minisign-signed tarballs.
  • No CVE-track inheritance: we don't ship a TCP-bound HTTP server in v1.0, eliminating the CVE-2025-6514 attack surface entirely.

Semver policy

  • Minor (1.X.0): new features, new wire methods (additive), new config keys (with sensible defaults). Most releases.

Update mechanism

v1.0 does not ship a self-updater. Users update by re-running the curl installer (or nix flake update). A future version may add mcpm self update for the curl-installed users; this would download + verify + atomically swap the binary.

Implementation-level decisions all 7 resolved 2026-05-24

Seven engineering-level decisions originally flagged for thought, now resolved. Each summarises the decision and points at the body section where the resolution is fully captured.

✓ Per-server singleton vs per-client process model resolved

Per-server [server.<name>].singleton in canonical config. Default true: one process shared across all mcpm exec invocations, with refcount + idle timer. singleton = false: each mcpm exec invocation spawns its own fresh process; the supervisor indexes processes by (server_name, client_id); idle_ttl_secs applies per-process. Trade-off: shared mode minimises memory and crash blast-radius is one editor down; per-client mode N× the memory but a crashing server only affects one editor's session. Suitable per-server (e.g. read-only filesystem MCP → singleton; sandboxed code-execution MCP → per-client). Captured in user-scope config schema, Flow B step 5, and the "Singleton-by-default" invariant.

✓ Idle-server termination policy resolved

Per-server [server.<name>].idle_ttl_secs in canonical config. Default 1800 (30 min): when refcount → 0, start an idle timer; if the timer fires, stop the server gracefully; if a new mcpm exec arrives first, cancel the timer. idle_ttl_secs = 0 means "stop immediately when refcount = 0" (for memory-hungry servers); negative means "never stop" (for always-warm servers). Captured in the user-scope config schema and Flow B step 9.

✓ cgroupv2 unavailability on older Linux distros resolved

Fall back to RLIMIT_AS + SIGKILL-with-warning detection. Degrades gracefully — per-server memory limits still work; OOM detection is best-effort (we observe SIGKILL but cannot definitively attribute to OOM, so audit entries carry a "may have been OOM, no perfect signal on this kernel" warning). Captured in Flow D step 6 and the per-platform OOM table.

✓ macOS jetsam OOM-inference heuristic resolved

Classify as server.oom iff all three: (a) child exit by SIGKILL with no exit code, (b) host_processor_info reports memory-pressure within the last 30 seconds, (c) the server's last-known RSS exceeded 80% of any configured memory limit (or the system's per-process default). Otherwise classify as server.crash. Captured in Flow D step 6.

✓ Trust manifest fetch on first run (network bootstrap) resolved

Fall back to "trusted-baked-in only" mode on network failure. Only the 3 default registry pubkeys baked into the mcpmanagerd binary are valid; no user-added registries can be verified. Every mcpm CLI invocation prints a one-line warning until mcpm trust refresh succeeds. [root].mode in trust.toml flips from "baked-in-fallback" to "fetched" on first successful refresh. Captured in the trust-file schema + the "First-run trust bootstrap" sub-section.

✓ Concurrent config.put race resolved

CAS-style guard: every config.put RPC includes a prior_hash field (required). If the on-disk file's hash doesn't match, the put returns E_CONFIG_CONFLICT; the caller (TUI / CLI / $EDITOR wrapper) re-reads via config.get and offers to merge or discard. config.get returns a snapshot containing {content, hash} so every reader has the hash it needs for the next write. Captured in the wire protocol definitions for config.get and config.put.

✓ mcpm-protocol vs mcpm-client split resolved

mcpm-protocol is the small, stable, public surface — wire types only, required features only, semver-disciplined. Third parties depend on it directly to build alternative clients. mcpm-client is the in-tree convenience layer — first-party only, churns freely, wraps mcpm-protocol with retry policies, streaming-RPC ergonomics, error-mapping, and the dial-or-auto-spawn dance. Captured in the per-crate table.
