Recommendation — Tauri 2 + Dioxus

Verdict: recommend dioxus-desktop standalone, not Tauri-wrapped. Dioxus already uses Wry/Tao under the hood (the same WebView engine Tauri does)[1]. Wrapping it in Tauri adds glue without changing the runtime profile for macOS+Linux v1.0. The case for Tauri-wrapping is mostly about bundling/plugins, and those wins don't outweigh the cost of an extra IPC boundary for an in-process Rust UI. Blitz/Dioxus Native is genuinely exciting but pre-alpha[2] — revisit in 6–12 months.

Pros

  • Best dev loop in Rust UI, period. Subsecond Rust hot-patching (dx serve --hotpatch) lets you edit Rust function bodies and see the change without losing app state[3]. Combined with stable RSX hot-reload, the inner-loop iteration speed beats anything else in Rust GUI as of 2026[4].
  • Single-language stack. Shared mcp-core crate, shared serde types, no ts-rs codegen, no node_modules. The UI and the rest of the workspace are one Cargo build[5].
  • No IPC boundary in dioxus-desktop. Event handlers run as native Rust closures; you can construct a hyper client to mcpd's UDS directly inside use_resource. No #[tauri::command], no JSON encode/decode round trip just to talk to your own process[1].
  • WebView a11y for free. Dioxus inherits WKWebView's accessibility tree on macOS and WebKitGTK's on Linux. VoiceOver, Orca, and IME (CJK input) all work without per-component wiring — one of only four Rust GUIs that pass the boringcactus 2025 a11y+IME label test[6].
  • Full CSS for theming. Tailwind v0.7 is zero-config[4]; @media (prefers-color-scheme: dark) for system dark-mode; standard web layout primitives. No bespoke DSL to learn.
  • Idiomatic live updates. Signals + use_resource + use_future compose naturally with async streams from mcpd's SSE events. Re-renders are component-scoped, so log-tail panels updating 10x/sec don't tax the rest of the UI[7].
  • Clean license. MIT/Apache-2.0 dual everywhere — Dioxus core, Wry, Tao, Blitz — no GPL/commercial entanglement[8].
  • Optional web build for free. The same component tree compiles to WASM if MCP Manager ever wants to expose the GUI against a remote mcpd[4].

Cons

  • Pre-1.0. Dioxus is at 0.7.9 as of May 2026[9]. Minor-version upgrades (0.6→0.7) historically introduce macro/API breakage. Budget for a yearly migration sprint.
  • The "Tauri + Dioxus" combo is community-supported only. No official create-tauri-app template; the canonical glue is the third-party Desdaemon/tauri-dioxus repo[10]. Tauri maintainers explicitly say "Dioxus has its own desktop framework"[11]. If you pick this combo, you own the integration.
  • Blitz/Dioxus Native is not ready. Missing event types (mouseover, forms), missing input widget variants, no a11y, "performance has not been a focus"[2]. Looking at the CSS support matrix[12] still shows gaps in May 2026.
  • Hiring pool is small. Rust developers who specifically know Dioxus are rare. React-shaped components soften the ramp, but it's still a project-specific dialect.
  • WebView idle RAM (~60–100 MB) is higher than pure-native frameworks (egui/iced sit closer to 30–50 MB). Acceptable for a desktop daemon manager; not acceptable for an embedded device.
  • Smaller ecosystem of vetted plugins. Tauri ships first-party HTTP, Store, FS, Shell, Updater, Notification, OS info, Stronghold/Keyring plugins. Dioxus relies on the broader Rust crate ecosystem, which is fine but less curated for desktop UX needs[13].
  • No marquee Dioxus shipping app at scale. Named users (Huawei internal, Airbus/ESA collision-avoidance, Satellite.im[14]) are credible but not Spacedrive-tier visible. Tauri has a longer public production track record.

Gotchas (the things that bite you in production)

  • Subsecond is experimental. Worth budgeting a 1-day spike to confirm it's reliable on the team's macOS Apple Silicon machines before depending on it. If it's flaky, you fall back to stable RSX hot-reload (which is still very good).
  • WebKitGTK quirks on Linux. WebKit on Linux has historically lagged WebKit on macOS — font rendering, hardware acceleration, and tab focus edge cases. Test on all target distros early. (This is a WebView-family problem, not Dioxus-specific.)
  • macOS notarization is your job. dx bundle produces .app/.dmg[15] but you wire codesign + notarytool yourself. Tauri's bundler has slightly more polished notarization automation if you wrap.
  • Don't subscribe to SSE from the WebView side if you can avoid it. Native EventSource works but reconnection logic, backpressure, and event-buffer growth are easier to manage in a tokio task in the Rust process[16].
  • Secrets in URL fragments. If you ever pass secrets as Dioxus router params, they end up in WebView history. Use signals + use_context instead.
  • Bundle size creeps with assets. The Dioxus runtime is small (~8 MB) but embedded CSS/fonts/icons compound quickly. Use asset!() with hashing rather than raw include_str! for cache-friendliness.

When to pick this stack

  • You have a small (1–4 person) Rust-fluent team that wants one language for the whole project.
  • Iteration speed on UI is a P0 — log-tail layouts, server-row designs, secret-editor forms are going to change weekly.
  • You value the option to ship a web build of the GUI without rewriting.
  • You're comfortable with a pre-1.0 framework that ships breaking changes between minors but has commercial backing (YC + named institutional users).
  • You don't need an exhaustive plugin marketplace — most desktop needs are met by direct Rust crates.

When NOT to pick this stack

  • You need to ship to Windows in v1 with the smoothest possible packaging story — Tauri's Windows tooling is more mature (though out of scope per the orchestrator's constraint).
  • Your team has deep React/TypeScript expertise and zero Rust frontend experience — Tauri+React is faster to onboard for that profile.
  • You require AAA accessibility certifications beyond what a WebView provides (very rare).
  • You want to ship a fully native, non-WebView UI in v1 — Dioxus Native isn't ready; choose iced or egui instead.
  • You can't tolerate breaking changes between minor versions in a critical dependency.

Why dioxus-desktop standalone, not Tauri-wrapped

This is the load-bearing call, so let me lay it out explicitly.

Dioxus-desktop already uses Wry/Tao — the exact crates Tauri uses for WebView abstraction and windowing[1]. So at the bottom of the stack, Tauri-wrapping doesn't change anything. What you'd be adding is:

  1. An extra serialization boundary between WASM frontend and Rust host — Tauri commands are always JSON over IPC[13]. Dioxus-desktop has no such boundary; components run as native Rust.
  2. The Tauri capabilities/permissions ACL — useful for sandboxing untrusted frontend code, but Dioxus-desktop's frontend IS your Rust code; sandboxing yourself doesn't help.
  3. The Tauri plugin ecosystem — Store, Shell, Updater, etc. These are real wins but most have direct Rust equivalents you can use without wrapping (e.g., the keyring crate, tokio::process, the self_update crate)[17].
  4. Tauri's bundler — more polished notarization automation. Marginal advantage over dx bundle[15]; not a deciding factor.

None of these are worth paying the integration tax. The Desdaemon/tauri-dioxus template exists[10] but is community-maintained — you'd own keeping it current as both projects evolve.

The only scenario where Tauri-wrapping wins: if you decide v1.0's GUI should be web-tech-built (React/Vue/Svelte) and v2.0 might migrate part of the frontend to WASM/Dioxus. Then a Tauri shell lets you mix. That's not the MCP Manager v1 reality — the project is Rust-first, the team is small, and the GUI is the visual front door for an all-Rust workspace.

So: dioxus-desktop standalone is the recommendation. Tauri-wrapping is a viable second-best if the team wants the plugin ecosystem badly enough to absorb the IPC overhead. Blitz/Dioxus Native is a future option to track but explicitly not for v1.
