GUI stack shootout

User direction (2026-05-24): "We need to be OBSESSED about UX." Three parallel research agents evaluated Tauri+Leptos, Tauri+Dioxus, and Actix-Web+Tera/Askama against MCP Manager's needs on macOS + Linux. This page synthesizes their scorecards into a single comparison and recommendation.

100 citations across 3 stacks 3 standardized scorecards 13-criterion ranking matrix Decision: Actix + Askama (GUI inside mcpd)

Verdict

Ship Actix-Web + Askama as a localhost SSR app served from inside mcpd. Weighted score 8.57 / 10 against Dioxus-desktop's 8.13 and Tauri+Leptos's 6.71. The win is broad (8 of 13 criteria) and robust to reasonable weight tuning. The single weakness — "feels like a native app" — is real but offset by zero-IPC simplicity, a free LAN/mobile path, browser-grade accessibility, and the fastest first-paint of the three.

Runner-up: Dioxus-desktop standalone (not Tauri-wrapped — dioxus-desktop already uses the same Wry/Tao runtime as Tauri). Pick this if the "browser tab" UX is unacceptable to product positioning and you accept Dioxus's pre-1.0 yearly-migration cost.

Architectural implications of "GUI inside mcpd"

Agent 3's recommendation isn't just "use Actix-Web" — it's "make the GUI part of the daemon binary." This is a deeper architectural call that composes elegantly with the v1.0 lockdown decisions:

One process, zero IPC

HTTP request handlers in Actix call mcpd-core Rust functions directly. No JSON-RPC encode/decode, no UDS round trip, no #[tauri::command] bridge. Wire-format drift is impossible because there is no wire.

Auto-spawn becomes trivial

Lockdown decision #2 said "mcpm exec auto-spawns mcpd." With Actix-inside-mcpd, "launching the GUI" IS "launching the daemon." The boot-flow race condition the other stacks have to handle (GUI starts before mcpd is ready) does not exist here.

Mobile / LAN day-one

An opt-in --bind 0.0.0.0 turns the GUI into a tool you can use from your phone, tablet, or any other machine on the LAN. Tauri and Dioxus would each need a separate mobile build (months of work) to match this. For "Docker-for-MCP-servers" management, this is a real differentiator.

Single auth surface

One bearer token on first launch (Pi-hole pattern), one set of permission checks. Tauri and Dioxus each need separate auth on the IPC layer and the optional HTTP/SSE bridge — two surfaces, two failure modes.

SSE is native, not bolted-on

actix-web-lab::sse + tokio::sync::broadcast + hx-ext="sse" makes log tails and status updates one-liners on both client and server. WebKitGTK SSE quirks (Tauri+Leptos's main risk) go away — every browser supports SSE natively.

Extractable later (low cost)

If "GUI bug crashes daemon" becomes a real problem in production, extracting Actix into a separate mcpd-ui binary that talks to mcpd over UDS JSON-RPC is a clean refactor — the HTTP API stays identical for users.

Honest tradeoffs — the browser-tab tax

Actix wins the matrix, but the win comes with three specific UX taxes worth naming explicitly. "OBSESSED about UX" doesn't mean ignoring these — it means addressing them.

Tax 1: No dock / taskbar icon, no native menubar

A browser tab is not "an app." There's no Cmd-Tab destination unless the user makes a Chrome SSB / Safari shortcut / Firefox PWA. They will have to. Mitigations:

  • Ship a small mcpd-tray helper binary on macOS (~2MB, uses tray-icon crate) that lives in the menubar, shows "running / stopped", and has an "Open UI" menu item. Linux: same crate works on most desktops.
  • Ship a PWA manifest so users who want a dock icon can install the localhost app to their dock with one click.

Tray + PWA together get most of the "real app" feel back. Not all of it.

Tax 2: Cmd-W can kill the UI mid-task

Browsers' close-tab UX doesn't honor beforeunload reliably for confirmed-edit workflows. If a user is editing a server config and Cmd-Ws the tab, their changes are gone unless we autosave aggressively.

Mitigations: design every edit flow as "save-on-blur" (debounced, no explicit Save button) so there's nothing to lose. This is good UX policy regardless of stack.

Tax 3: No global hotkeys, no native notifications

Browser tabs can't bind global hotkeys. Native notifications work only via the (still-flaky-on-Linux) Web Notifications API.

Mitigations: notifications aren't a v1.0 requirement (mcpd already logs to systemd-journal/launchd-stdout). Global hotkeys: out of scope for v1.0. If demand emerges in v1.1, ship a small CLI subcommand (mcpm hotkey) that registers OS-level hotkeys and emits events into the running mcpd.

Tax 4: DNS rebinding (security)

A malicious website the user visits could theoretically craft requests against localhost:NNNN. Standard mitigations: Host: header allowlist (refuse anything except localhost / 127.0.0.1 / [::1]), per-session bearer token from URL, no CORS by default. GitHub Security: DNS rebinding explained.

Sensitivity analysis

Is the Actix win robust, or fragile to weight choices? Three scenarios:

ScenarioWeight changeOutcome
"Native feel is everything" theming_native_feel weight → 0.30 (was 0.08); reduce others proportionally Dioxus wins; Actix drops to 3rd or 2nd. This is the threshold: if you'd weight native-feel at ~3×+ the current 8%, the choice flips.
"Hot reload uber alles" hot_reload_quality weight → 0.20 Dioxus catches up to Actix but still doesn't pass it. Actix's broad win on too many other dimensions is hard to undo with one criterion.
"Hiring pool dominates" team_hiring_pool weight → 0.20 Actix lead grows (it has the largest hiring pool).

Translation: the only way to topple Actix in this comparison is to commit to "the UI must feel like a real native app" as the primary criterion. That's a legitimate product call — if you make it, Dioxus-desktop is your stack.

Open questions for the orchestrator

Is "browser tab" UX acceptable to v1.0 product positioning?

This is the load-bearing question. If yes → ship Actix. If no → ship Dioxus-desktop and pay the dev-loop / hiring / mobile-path costs. Recommendation: yes — MCP Manager is a developer power-tool, not a consumer app. Sonarr/Radarr/Pi-hole/Jellyfin have validated this UX pattern with developer audiences for a decade.

LAN binding: default-on, opt-in, or Tailscale-only?

Localhost-only is the safe default for v1.0. An mcpm gui --bind 0.0.0.0 flag unlocks LAN; a future mcpm gui --bind tailscale0 binds to the user's Tailscale interface only. Mobile access via Tailscale would be the v1.1+ delight feature.

Tray icon: ship in v1.0 or defer to v1.1?

Tray adds ~2MB and a small dependency surface but materially changes the "feels like an app" perception. Recommendation: ship in v1.0. A localhost web app without a tray icon is the experience that tipped Sonarr/Radarr towards "weird invisible service" perception in their early years.

Future "Tauri shell" upgrade path?

Agent 3 flagged this: if "browser tab" complaints become real, a thin Tauri shell could wrap the same Actix server in a WebView, no UI rewrite needed. The Tauri binary just points its WebView at localhost:NNNN and ships the daemon as a sidecar. Captured in future features (v1.1).
