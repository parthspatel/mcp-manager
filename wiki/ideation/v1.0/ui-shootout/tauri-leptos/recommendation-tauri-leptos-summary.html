Recommendation — Tauri 2 + Leptos

The bottom-line scorecard plus an opinionated pros/cons/gotchas writeup, intended to be read against the sibling stack pages (Tauri+Dioxus and Actix+Tera) when the orchestrator synthesizes the final pick.

Bottom line

Tauri 2 + Leptos is the pure-Rust front-to-back stack with the strongest type-safety story of the three candidates, a small native footprint, and inherited OS-WebView accessibility — but it pays for that with a slower dev loop than JavaScript frontends, a Tauri docs surface that lags the Leptos release line[?], and a hiring pool an order of magnitude smaller than React/TS. Recommended only if the team is committed to a Rust-first identity across mcpd, CLI, TUI, and GUI; otherwise Tauri+TS frontend strictly dominates on dev velocity and ecosystem depth.

Pros

  • Shared types with mcpd are real and load-bearing: a single mcpd-protocol crate is imported by daemon, CLI, TUI, and the Leptos WASM. Wire-format drift is a compile error, not a runtime bug[?].
  • Small footprint: 8–15 MB installer, 30–60 MB idle RAM — single-digit-percent of an equivalent Electron build, and small enough to be a casual install for a developer tool[?][?].
  • Accessibility is "free": the OS WebView's accessibility tree and IME handling are inherited, and pass the boringcactus a11y bar that 94% of pure-native Rust frameworks fail[?].
  • First-party packaging on both target OSes: tauri build produces signed/notarized .app/.dmg, .AppImage, and .deb with one config[?][?][?].
  • Permissive license throughout: Tauri MIT/Apache-2.0, Leptos MIT, Trunk + cargo-leptos + wasm-bindgen all MIT/Apache-2.0. No GPL contamination[?].
  • Streaming is a solved problem via tauri::ipc::Channel — designed for exactly the log-tail use case we need, with binary-format ordered delivery[?].
  • Sidecar mcpd is a one-line config in Tauri + a shell-plugin spawn call; the daemon-not-ready boot case is trivial to handle[?].

Cons

  • Hot-reload is slow by 2026 standards: 3–4s incremental rebuilds for Rust changes, vs. sub-100ms for TS/Vite[?]. CSS hot-reloads instantly, which softens the blow but doesn't eliminate it.
  • Hiring pool is tiny: Rust + WASM + Leptos's statically-typed view tree is a narrow intersection. You cannot post a job and expect inbound; you onboard existing Rust devs into Leptos (precedent: ~2 months for two engineers[?]).
  • SSR is officially unsupported in the Tauri shell: the Tauri Leptos guide explicitly says use SSG/CSR[?]. Half of Leptos's marketing surface (server functions, streaming HTML, hydration) is off-limits inside Tauri.
  • Docs lag the framework: the Tauri integration guide is pinned to Leptos 0.6 while the framework is on 0.8.x with a 0.9 alpha[?].
  • No flagship app on this exact combination: lots of Tauri+React/Vue/Svelte apps, lots of standalone Leptos web apps, but the Tauri+Leptos intersection has demos and small commercial apps, not a consumer flagship[?].
  • WebKitGTK fragmentation on Linux: different distros ship different WebKitGTK versions and SSE/streaming behavior varies; no first-party Tauri SSE plugin yet (open feature request)[?].

Gotchas

  • Bundle two binaries, not one: if mcpd is shipped as a sidecar, your .app contains both MCP Manager.app/Contents/MacOS/mcp-manager-gui and the sidecar mcpd binary suffixed with target-triple (e.g. mcpd-aarch64-apple-darwin)[?]. Both need to be signed.
  • WASM bundle size discipline matters — the regex crate alone adds ~500KB to a WASM binary[?]. Audit dependencies and use feature flags aggressively.
  • Universal macOS binaries double bundle size; consider shipping separate aarch64 and x86_64 builds rather than a fat binary[?].
  • Developer ID certs expire every 5 years — diary it; a quiet expiry breaks CI and ships unsigned builds[?].
  • EventSource on WebKitGTK works but is more fragile than on WKWebView; prefer the Channel API for hot streaming paths.
  • Leptos 0.7's statically-typed view tree produces excellent runtime ergonomics but verbose compiler errors when you accidentally try to store views in signals; expect a "where did my AnyView go?" learning curve[?].

When to pick this stack

  • The team's identity is "we are a Rust project, end to end" — including in-browser code.
  • Wire-format correctness between mcpd and the GUI is a top-3 concern, and you want compile-time guarantees, not runtime tests.
  • Footprint matters — you target developer-tool installs where 100 MB Electron apps are unacceptable.
  • The team already has 2+ senior Rust engineers willing to spend ~2 months ramping on Leptos.
  • You're willing to accept a 3–4s incremental dev loop in exchange for the type guarantees.

When NOT to pick this stack

  • You need to staff the GUI team beyond founder-level — the Leptos hiring market is too thin.
  • UI iteration speed is the bottleneck (heavy design phase, frequent visual tweaks, designers in the loop).
  • The team is primarily web-frontend and would prefer to write TS/React with shared types via codegen — Tauri+React with TauRPC gives you 80% of the type-safety for 20% of the friction.
  • You want or need to reuse a substantial React/Vue component library (auth flows, code editors, charting) — the Leptos ecosystem of pre-built components is much smaller.
  • You expect to ship a browser-only fallback for users who don't install the desktop app — that strictly favors the Actix+Tera stack.

Verdict

Tauri 2 + Leptos is a credible pick that is hard to recommend without a strong organizational commitment to Rust everywhere. The single load-bearing argument is shared types with mcpd; everything else (footprint, packaging, a11y, license) is matched or beaten by Tauri+TS-frontend. If the orchestrator weights "shared types with the daemon" as a top-3 axis, this stack wins; if it weights "dev velocity" or "hiring", Tauri+Dioxus (similar Rust-everywhere with a more relaxed signal model) or Tauri+TS-React (mainstream) is probably the better answer.
