Research — fit with MCP Manager v1.0

The SSR stack collapses several MCP Manager problems into single bullet points (real-time, IPC, accessibility) and creates a small cluster of new ones (no native window, tray story, localhost security). This page works through each in turn.

Architecture: GUI inside mcpd, or separate process?

Two viable shapes:

AspectA — GUI lives inside mcpdB — GUI is a separate Actix process talking to mcpd via UDS
IPCNone. Handlers call mcpd modules directly. Zero serialization, zero boundary.JSON-RPC over UDS (already exists). Handlers wrap RPC calls.
Process lifecycleOne PID. mcpd dying = GUI dying.Two PIDs. GUI can restart without restarting servers.
"daemon not yet running"Moot. The GUI IS the daemon.Need to handle gracefully — auto-spawn mcpd on first GUI request.
Blast radiusGUI bug → daemon crash → MCP servers killed.GUI bug → only the GUI process restarts.
Auth modelSingle bearer token in mcpd config.Two layers — GUI-to-user (bearer) AND GUI-to-mcpd (UDS peer-cred).
Binary countOne (mcpd).Two (mcpd, mcpd-ui).
Compile timeWorse — every UI change rebuilds mcpd.Better — UI iterates independently of daemon.
Type sharingDirect imports.Shared crate for DTOs, or duplicate types.

Recommendation: A (inside mcpd) for v1.0, with the option to extract later. Rationale:

  • The IPC story is the single biggest qualitative advantage of this stack over Tauri — choosing B throws it away.
  • v1.0 doesn't need to survive GUI-process restarts; we are not yet at "Docker Desktop" scale of UI complexity.
  • If the daemon-crash-takes-down-UI risk becomes real, extracting later is straightforward because the HTTP API is the boundary — we ship the same routes, just hosted by a separate binary that calls mcpd's existing JSON-RPC over UDS.

Tray / menubar story and "discoverability"

The single biggest UX wart of "the UI is a browser tab" is discoverability: there's no app icon, no Spotlight result, no dock badge. The user opens a terminal, runs mcpm gui, and a browser tab appears at http://127.0.0.1:7777. That works for developers; it's hostile to anyone else.

Three discoverability layers, in increasing investment:

  1. CLI launcher (v1.0 minimum). mcpm gui opens the default browser to http://127.0.0.1:7777/?token=.... If mcpd isn't running, spawn it. If a tab is already open at that URL, reuse it (browsers do this automatically in most cases).
  2. Tray icon (v1.0 stretch). Use tray-icon (Tauri-org-maintained, 1.87M downloads/month) to add a menubar entry on macOS and an AppIndicator on Linux . Menu items: Open in browser, Status: 3 servers running, Restart mcpd, Quit. The macOS main-thread requirement complicates integrating tray into mcpd itself — likely we ship a tiny mcpd-tray helper binary that talks to mcpd via UDS .
  3. PWA install (v1.1+). Ship a web app manifest with display: standalone, icons at the standard sizes, and theme color. Chrome/Edge let users "Install App" from the address bar; the result is a dock icon with a standalone window, no browser chrome, that *feels* like a native app . The macOS Safari PWA story is weaker but improving. This is the cheapest path to "looks like an app in the dock" — no Rust changes needed.

Layers 1 and 3 cost a day of work each. Layer 2 (tray) is a week or two due to the cross-platform event-loop gymnastics; recommend deferring tray to v1.1 and ship v1.0 with CLI + optional PWA install.

Auth on localhost

"It's only on localhost, so it's safe" is wrong, and has been wrong since DNS rebinding became a known attack class. A malicious web page can resolve a name to 127.0.0.1 and trick the user's browser into hitting http://127.0.0.1:7777/api/servers/X/delete with the user's session cookies attached .

The defense-in-depth recipe (all three layers, not one-of):

  1. Bind 127.0.0.1 only by default. 0.0.0.0 is opt-in via a config flag with a big warning. Refuse to start with 0.0.0.0 unless a bearer token is set.
  2. Validate the Host header. Reject requests where Host is not exactly localhost:7777, 127.0.0.1:7777, or [::1]:7777. This kills DNS rebinding cold — the attacker's DNS name will be in the Host header and we drop the request .
  3. Bearer token in URL on first launch. On mcpm gui, generate a random token, store its hash, and open the browser to http://127.0.0.1:7777/?token=<raw>. The page captures the token into localStorage and sets it as Authorization: Bearer <raw> on every fetch (or as a same-site Strict cookie). Token rotates on each mcpd restart unless persisted.

Pi-hole v6 ships almost exactly this: a password set at install time, used to gate the web UI . The MCP Manager twist is that we want zero-config — the user doesn't see the token unless they're being deliberate.

Stretch: for the "GUI is inside mcpd" architecture, we could expose the bearer over the existing UDS interface and have the CLI fetch it via UDS peer-credentials (only the user owning the socket can read the token). This eliminates the "token visible in process listing" leak.

The "browser is not really my app" UX problem

Several taxes the SSR stack pays:

  • Focus stealing. Opening a new browser tab steals focus from whatever the user was doing. There's no native way to "raise the existing MCP Manager window" — at best, an existing tab gets focus if the browser deduplicates URLs.
  • Accidentally closed. The user hits cmd-w by reflex and closes the tab in the middle of editing a config. No native "are you sure?" — though we can hook beforeunload if there are unsaved changes.
  • No global hotkey. No cmd-shift-M to "show MCP Manager." A tray icon helps; OS-level hotkeys require native code.
  • No dock badge for unread notifications. PWA install gets us a dock icon but the badging API is browser-limited.
  • No system file picker integration. File uploads go through the HTML <input type="file"> dialog. No "drop into the dock icon."
  • No native notification permission UX. Browsers gate notifications behind their own permission prompt.

None of these are dealbreakers; all of them are real. The PWA-install path (Chrome/Edge) recovers a few — dock icon, standalone window, file system access — but not all .

Mobile path — managing MCP servers from a phone

This is the SSR stack's killer differentiator. If the user opts in to LAN binding (--bind 0.0.0.0 with a bearer token), the same UI is reachable from any device on the network — phone, tablet, the laptop in the other room. The Tauri stacks would require a full mobile-app build (iOS+Android, App Store / Play Store, code signing) to match this. The SSR stack gets it for free, because the browser is the runtime.

What's needed:

  • Mobile-responsive CSS — the templates need a small-screen layout. Trivial with modern CSS grid + flexbox.
  • Tap-friendly controls — 44px minimum hit targets, no hover-only interactions.
  • HTTPS for LAN access — self-signed certs are user-hostile; the better path is "use Tailscale" or "use mkcert in dev." Production-grade is "we don't bind 0.0.0.0 — point Tailscale Funnel/Caddy at us."
  • Mobile-safe SSE — phones aggressively kill background connections. The 10s heartbeat ping mitigates; long-tail UX may need fallback to polling.

v1.0 ships mobile-responsive CSS but does not ship LAN binding by default. Mobile is documented as "set --bind 0.0.0.0 and use a bearer token; or front it with Tailscale."

The "no native app" tradeoff

What you give upWhat you get
Native window chrome~30 MB less RAM than a WebView app idle
Dock/launchpad presence (without PWA install)Distribution via brew install mcpm — no signing, no notarization, no DMG
Global hotkeys, dock badgingLAN/mobile access as a first-class feature, not a port
Native file picker / drag-drop into dockScreen-reader and IME quality far beyond anything Rust GUI toolkits offer
Native notifications without permission promptsSingle Rust binary, no Node/Vite/Trunk in the build chain
"Feels like a Mac app"Compatible with every browser-based dev tool ecosystem — extensions, devtools, screen recorders

The blunt question is whether MCP Manager's job is to feel like a Mac app, or to be a power tool for managing servers. If it's the latter — and the comp set is Docker Desktop's UI, plus all of Jellyfin/Sonarr/Pi-hole — then "browser tab" is not just acceptable, it's correct.

Why SSE fits MCP Manager perfectly

Every interactive MCP Manager surface fits the "server pushes a stream, browser appends to a DOM node" pattern:

  • Log tails: server emits LogLine; client appends to a <div sse-swap="log" hx-swap="beforeend">.
  • Server status changes: server emits StatusUpdate; client swaps the badge in the table row.
  • Resource graphs: server emits per-second CPU/RAM samples; client appends to a sparkline.
  • mcpd lifecycle events: server emits "server X exited with code 137"; client toast-notifies.

This is the exact pattern actix-web-lab::sse + tokio broadcast channels are built for . In Tauri, the equivalent is tauri::ipc::Channel — works, but requires marshalling through the WebView's IPC protocol. Here, it's just HTTP/1.1 and an event listener.
