Research — Actix-Web, Tera, Askama, HTMX in 2026

A localhost SSR app for MCP Manager is a stack of four well-understood pieces — an HTTP server, a template engine, a real-time push channel, and (optionally) a sprinkle of client-side JS. None of these are exotic. All four are mature in 2026, with clear winners that the wider Rust web ecosystem has converged on.

Actix-Web in 2026

Actix-Web is the oldest of the still-mainstream Rust web frameworks (originally 2017) and remains the raw-throughput leader in 2026: independent benchmarks show ~20k req/s sustained vs Axum's ~18k, with idle RAM in the 50–80 MB range under load . The latest stable line is 4.x (4.13.0 released February 2026); there is no 5.0 yet . Total downloads on crates.io are past 68M, and the project is dual-licensed MIT-or-Apache-2.0 .

The architectural quirk worth knowing is that Actix spawns N single-threaded Tokio runtimes (one per physical core) with tasks pinned per thread. Axum uses a single multi-threaded work-stealing runtime . For MCP Manager this matters less than people think — we'll have ~1–4 long-lived SSE connections, not 100k concurrent HTTP requests. 

// Actix-Web hello — for context.
use actix_web::{get, web, App, HttpServer, Responder};

#[get("/api/servers")]
async fn list_servers(state: web::Data<McpdState>) -> impl Responder {
    web::Json(state.servers.snapshot().await)
}

#[actix_web::main]
async fn main() -> std::io::Result<()> {
    let state = web::Data::new(McpdState::open().await?);
    HttpServer::new(move || App::new().app_data(state.clone()).service(list_servers))
        .bind(("127.0.0.1", 7777))?
        .run()
        .await
}

The 2026 consensus is roughly: Actix if raw throughput matters and you don't mind the older actor-era idioms; Axum if you want the tokio/tower ecosystem alignment and a more modern API surface . For a localhost admin UI both are massively overprovisioned. We pick Actix here because (a) the SSE story via actix-web-lab is first-class , (b) mcpd's existing HTTP/SSE bridge was likely already built on it or can be without rewriting, and (c) raw perf is never the bottleneck in a localhost-only world.

Tera — runtime templating

Tera is a Jinja2/Django-style template engine maintained by Vincent Prouillet, who also created the Zola static site generator — Tera and Zola evolve together . Templates are loaded at runtime from disk (or globbed at startup), supporting inheritance, macros, filters, tests, and includes — anyone fluent in Jinja or Django will be productive in an hour.

The 2026 status: v1 is frozen, v2 is on crates.io with a migration guide; both lines remain available . Tera has a built-in auto_reload mode that re-reads templates on file change — meaning you can edit HTML and just refresh the browser, no recompile . That is its decisive dev-loop advantage over Askama. 

// Tera — runtime templates, no compile-time checking.
use actix_web::{web, HttpResponse, Result};
use tera::{Context, Tera};

async fn server_list(tera: web::Data<Tera>, state: web::Data<McpdState>) -> Result<HttpResponse> {
    let mut ctx = Context::new();
    ctx.insert("servers", &state.servers.snapshot().await);
    let body = tera.render("servers/list.html", &ctx)
        .map_err(actix_web::error::ErrorInternalServerError)?;
    Ok(HttpResponse::Ok().content_type("text/html").body(body))
}

Askama — compile-time templating

Askama takes the opposite tradeoff. Templates are parsed at compile time and turned into specialized Rust code; you bind a template to a #[derive(Template)] struct, and any field reference that doesn't exist or has the wrong type fails the build . The 0.14 line is current (released April 2025); the project re-unified with the rinja fork in 2024–2025 and is again the single canonical implementation .

There is one 2026 gotcha worth flagging: the dedicated askama_actix integration crate was deprecated in Askama 0.13 and removed before 0.14 — you no longer get an impl Responder for T: Template for free . The replacement is two lines: call .render() manually and return the string body. This is mildly annoying but irrelevant in steady state. 

// Askama — compile-time templates, type-checked against ServerListPage.
use askama::Template;
use actix_web::{web, HttpResponse, Result};

#[derive(Template)]
#[template(path = "servers/list.html")]
struct ServerListPage<'a> {
    servers: &'a [ServerSummary],
    selected: Option<&'a str>,
}

async fn server_list(state: web::Data<McpdState>) -> Result<HttpResponse> {
    let snapshot = state.servers.snapshot().await;
    let html = ServerListPage { servers: &snapshot, selected: None }
        .render()
        .map_err(actix_web::error::ErrorInternalServerError)?;
    Ok(HttpResponse::Ok().content_type("text/html").body(html))
}

The framing from a 2026 survey of Rust template engines: runtime engines (Tera) win developer iteration speed; compile-time engines (Askama, Maud) win type safety and runtime performance . For MCP Manager, where the domain types (Server, Tool, LogLine, Status) are stable and we want the compiler to scream when we rename a field, Askama wins on the axis that matters most — see the summary page for the full argument.

SSE in Actix

Real-time updates over Server-Sent Events are a hard requirement for MCP Manager (log tails, server status). Actix has had a community SSE pattern for years, and the maintainer-blessed implementation lives in actix-web-lab as the sse module: Sse::from_infallible_receiver, Sse::from_stream, plus helpers for keepalive and retry timing .

The canonical broadcast pattern: a tokio::sync::broadcast::Sender held in app state, an HTTP route that subscribes (receives a Receiver) and converts it to an SSE stream, a heartbeat task that pings every 10 seconds to evict stale clients . For MCP Manager this means a single broadcast channel per server (log lines) plus a status channel, both consumed by every connected browser tab. 

// Actix-Web + actix-web-lab SSE — broadcast log lines to all subscribers.
use actix_web::{get, web, HttpResponse, Responder};
use actix_web_lab::sse::{self, Sse};
use tokio::sync::broadcast;
use std::time::Duration;

#[get("/api/servers/{id}/logs")]
async fn tail_logs(
    path: web::Path<String>,
    state: web::Data<McpdState>,
) -> impl Responder {
    let id = path.into_inner();
    let rx: broadcast::Receiver<LogLine> = state.subscribe_logs(&id).await;

    let stream = tokio_stream::wrappers::BroadcastStream::new(rx)
        .filter_map(|res| async move {
            res.ok().map(|line| sse::Event::Data(
                sse::Data::new(serde_json::to_string(&line).unwrap())
                    .event("log")
            ))
        });

    Sse::from_stream(stream).with_keep_alive(Duration::from_secs(10))
}

HTMX, Alpine, and the "sprinkle of JS" question

Pure SSR works for static pages, but MCP Manager needs live log tails, server start/stop without a full page reload, and interactive forms. Two paths exist:

  1. HTMX (~12 KB gzipped) — turns HTML attributes into AJAX requests. hx-post="/api/servers/X/restart" swaps a fragment without writing JS. The sse extension turns any element into a live-updating widget: <div hx-ext="sse" sse-connect="/api/servers/X/logs" sse-swap="log">...</div> appends every log line into the DOM with zero glue code .
  2. Alpine.js (~15 KB gzipped) — client-side reactive state without a build step. Good for dropdowns, modals, toggles, command palette UI — anything that doesn't need a server round-trip .

The 2026 lightweight-frontend consensus is that you use both: HTMX for server-driven HTML swaps, Alpine for local reactive UI . This is the "HARM stack" pattern (HTMX + Axum/Actix + Rust + Maud-or-Askama), which is increasingly common in self-hosted tools . Total client-side JS for MCP Manager: ~27 KB, no build step, no Vite, no npm.

The honest alternative is no JS at all — full-page reloads on every action, classic Web 1.0. This is viable for the MCP Manager admin surface but feels jarring for log tails. We pick HTMX+Alpine deliberately as a "minimum viable interactivity" budget. 

<!-- Live log tail with htmx-sse. No JS code written. -->
<div hx-ext="sse" sse-connect="/api/servers/filesystem/logs">
  <div sse-swap="log" hx-swap="beforeend"></div>
</div>

<!-- Restart button — partial swap of the row. -->
<button hx-post="/api/servers/filesystem/restart"
        hx-target="#row-filesystem"
        hx-swap="outerHTML">
  Restart
</button>

Dev loop: cargo-watch, listenfd, template auto-reload

The dev-iteration story is the SSR stack's biggest deficit vs. Tauri+Vite (sub-100ms HMR) — and the place where the Tera-vs-Askama choice matters most.

  • Rust code edits: cargo watch -x run rebuilds + restarts on save. Cold incremental builds for a medium Actix app land in ~2–4 seconds . Add listenfd + systemfd per the official Actix auto-reload guide and the socket survives restarts so in-flight SSE connections aren't always nuked .
  • Template edits: this is where the engines diverge. With Tera + auto_reload, save the file, refresh the browser — sub-second. With Askama, every template edit triggers a Rust rebuild (~2–4s with cargo-watch). The compile-time type-checking is bought with this dev-loop cost.
  • CSS / static JS: served from a static-files mount; no rebuild needed. Sub-second.

Prior art: Jellyfin / Sonarr / Pi-hole style apps

The "localhost web server is the UI" pattern is the dominant architecture in the self-hosted homelab world. Jellyfin binds 8096 on the host and serves a full SPA — no native window at all . Sonarr and Radarr follow the same model on 8989/7878. Pi-hole v6 ships a localhost web UI with password auth set at install time — a direct prior-art reference for our auth UX .

None of these are written in Rust + Actix specifically, but the architectural lessons are stable: users learn the bookmark, expect a password/token at first launch, and accept that the "app" is a browser tab. The trade is that distribution is trivial (one binary, brew/apt/curl), the UI inherits all the browser's accessibility, and LAN/mobile access is essentially free.

The Rust-specific reference points are subtler. Zola (Tera-based, by Tera's author) demonstrates that Tera scales to real applications . MeiliSearch's dashboard is served by Actix. Sentry's edge services use Actix internally. There is no single famous "Jellyfin in Rust with Actix+Askama" app, but the building blocks are battle-tested individually .
