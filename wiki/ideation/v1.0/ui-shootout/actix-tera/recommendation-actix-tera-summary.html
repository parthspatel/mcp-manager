Recommendation — Actix-Web + Askama + HTMX (localhost SSR)

The opinionated bottom line: this is the lowest-risk, highest-leverage stack for MCP Manager v1.0. Pick this if shipping working software fast matters more than feeling-like-a-native-app, and if you trust that the homelab world (Jellyfin, Sonarr, Pi-hole) has already proven the architecture at scale. Don't pick this if the product story demands a native window with deep OS integration.

The verdict

Architecture: GUI lives inside mcpd as an Actix-Web server on 127.0.0.1. The "GUI" is a browser tab. No IPC, no serialization boundary between handlers and mcpd state. One Rust binary that owns daemon, CLI, and UI.

Template engine: Askama (compile-time, type-checked) over Tera. The mcpd domain types (Server, Tool, LogLine, Status) are stable; we want the compiler to scream when we rename a field. We pay for that with a ~2–4s rebuild on every template edit instead of Tera's sub-second auto-reload . Worth it. If hot-template-iteration starts hurting team velocity, switching to Tera is a mechanical port — both engines use Jinja-style syntax .

Interactivity: HTMX + Alpine.js. ~27 KB total client JS, no build step, no node_modules. HTMX for SSE log tails and partial swaps; Alpine for client-only UI state .

Pros

  • Accessibility for free. The browser is the most accessible runtime ever shipped. VoiceOver, NVDA, Orca, IME, zoom, high-contrast, reader mode — all work without us writing a line of AccessKit glue. This is the strongest single argument for the SSR stack: the 2025 boringcactus survey showed 94% of Rust GUI toolkits fail a basic screen-reader + IME test that the browser passes trivially .
  • SSE is the native idiom. Log tails, status updates, resource graphs all map directly to actix-web-lab::sse + tokio::sync::broadcast + a 10-second heartbeat. With hx-ext="sse" on the client, a live log view is one HTML attribute .
  • Zero IPC. GUI handlers call mcpd modules directly. No JSON-RPC, no Channel, no command derivation, no serialization round-trips. Function-call latency.
  • Type safety from DB to DOM. Askama templates fail to compile when the struct they bind to changes shape. Rename ServerSummary.name to ServerSummary.id and the build catches every template that referenced it .
  • Mobile path on day one. Opt-in --bind 0.0.0.0 (with bearer token) makes MCP Manager reachable from any phone on the LAN. No iOS app build, no Play Store. The Tauri stacks would need a full mobile target to match this.
  • Distribution is trivial. One binary, brew install mcpm or cargo install. No DMG, no AppImage, no signing/notarization, no auto-updater story — for v1.0 we just brew upgrade like every other CLI .
  • Boring, mature pieces. Actix is 9 years old, 68M+ downloads. Askama is the post-rinja unified line, stable on 0.14. HTMX/Alpine are widely deployed. No bleeding-edge surprises .
  • Hiring is easy. "Knows HTML + a little Rust" is a much larger pool than "writes reactive Rust with signals/RSX." Templates are HTML; anyone on the team can fix the dashboard.
  • Smaller idle footprint than a WebView app. No WebView2/WKWebView runtime — Actix at rest is ~50–80 MB, comparable to or smaller than the Tauri options once you account for the OS WebView's RSS share .
  • The license posture is clean. MIT-or-Apache-2.0 across the whole stack; no GPL contamination, no commercial-license surprises .

Cons

  • It's a browser tab. No native window, no dock icon out of the box, no Spotlight presence. PWA install (Chrome/Edge) recovers some of this but not on Safari .
  • Focus stealing is real. Opening the GUI yanks focus to the browser; the browser may decide to open a new window instead of focusing the existing tab.
  • Accidentally closeable. Cmd-w closes the tab mid-edit. beforeunload partially mitigates.
  • Template hot-reload is worse than Vite. Askama rebuilds on every template change (~2–4s with cargo-watch). Vite/Trunk HMR is sub-200ms. Tera mitigates by trading away the type safety .
  • No global hotkeys, no native notifications, no system file picker drag-drop. Browser sandboxes.
  • The askama_actix integration crate was deprecated. Not a real cost — calling .render() manually is two lines — but worth knowing during onboarding .
  • Discoverability problem for non-developer users. "How do I open MCP Manager?" requires a CLI, a tray icon, or a PWA install — all of which need explanation.

Gotchas

  • DNS rebinding is a real attack against localhost web servers. Defense in depth: bind 127.0.0.1, validate the Host header, require a bearer token. None of the three alone is sufficient .
  • SSE through corporate proxies / VPNs can stall or be buffered. We control the network in dev but if a user reaches the LAN-bound mcpd through their work VPN, SSE may need a polling fallback.
  • Browser tab limits: most browsers cap concurrent connections to the same host at ~6. A page with 6+ open SSE streams will starve. Multiplex log/status updates over a single SSE connection if you have many sources.
  • Tray icon main-thread requirement on macOS conflicts with mcpd's Tokio runtime. Either ship a separate mcpd-tray binary or thread carefully .
  • PWA install UX varies wildly across browsers. Chrome/Edge are great; Safari is iffy; Firefox doesn't support desktop PWA install at all. Document "use Chrome to install."
  • Browser-tab state loss on refresh. SSE connections drop and re-establish; in-flight log buffer may have gaps. Server-side persistence (write logs to a ring buffer mcpd holds) handles this.

When to pick this stack

  • The user model is "power user managing local infrastructure" — they're already comfortable with localhost admin UIs from Jellyfin, Sonarr, Portainer, Pi-hole.
  • Accessibility is a real requirement (a11y-conscious orgs, screen-reader users, CJK input).
  • You want a mobile/LAN management story without building a mobile app.
  • The team has more web-frontend muscle than reactive-Rust muscle.
  • Time-to-v1.0 matters more than feeling-like-a-Mac-app.

When NOT to pick this stack

  • The product positioning is "Docker Desktop quality native app" with deep OS integration (file pickers, drag-drop, dock badges, global hotkeys, native notifications without permission prompts).
  • App Store distribution is a hard requirement.
  • Users will object on principle to "it's just a browser tab" — for some audiences this signals 'unfinished' regardless of capability.
  • The team wants to do most of the UI work in reactive Rust (Leptos/Dioxus) for type-safety-everywhere reasons. The SSR stack has type-safe templates, but reactive state is on the client in JS.
  • Real-time updates need bi-directional streaming (SSE is one-way). Most MCP Manager needs are one-way; this is unlikely to bite, but if it does we'd need WebSockets.

Tera or Askama? — the call

Pick Askama. Here's the argument:

  1. The mcpd domain types are stable and we'll rename fields. Compile-time template checks turn "broken UI in production" into "broken build on the dev's machine" .
  2. The syntax is Jinja-compatible with Tera, so the team's mental model transfers. We can switch to Tera later with mechanical effort if hot-iteration becomes the bottleneck .
  3. Performance: Askama compiles templates to specialized Rust code; runtime cost is essentially zero. Tera parses and interprets at runtime — fine for our load, but Askama is strictly faster.
  4. The deprecation of askama_actix is not a real problem — calling .render() + HttpResponse::Ok().content_type("text/html").body(...) is two lines .
  5. The 2026 dev-loop gap shrinks: cargo-watch + listenfd gives ~2–4s reload; the browser's auto-refresh extensions close the gap further .

The only scenario where Tera wins is if a non-Rust designer is editing templates frequently and the rebuild cycle becomes a chronic interruption. That's not the v1.0 reality.

The architectural call: GUI inside mcpd

For v1.0, the Actix server lives inside the mcpd process. Reasons summarized:

  • The zero-IPC story is the SSR stack's unique strength vs. Tauri — splitting GUI into a separate process throws it away.
  • Single binary, single config file, single auth token, single log stream.
  • The "daemon not yet running" problem evaporates: launching the GUI is launching the daemon.
  • If/when blast-radius (UI bug crashes daemon) becomes painful, extracting to a separate mcpd-ui that talks to mcpd via the existing UDS JSON-RPC is a clean refactor — the HTTP API doesn't change.

The two-sentence summary

The SSR stack is what you build when you've internalized that the browser is the most-deployed, most-accessible UI runtime in human history, and you have a long-lived daemon already — so you might as well have it serve the UI. The trade is that the result is a browser tab, not a native window, and the design has to be at peace with that.
