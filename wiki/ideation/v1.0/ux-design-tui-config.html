TUI shape & pane layout

Single-screen, lazygit / k9s style. Left side stacks three concern-grouped panes (Servers / Toolchains / Secrets). Right side is contextual for the focused entity. Status bar top-right; context-aware hint bar bottom.

┌─ MCP Manager ────────────────────── github · 12:34:08 ┐
│ Servers ▸                       │ Logs · github         │
│ ──────                          │ [server][mcpd][audit] │
│ ▸ github     ●● running  14h    │ ──────                │
│   filesystem ●● running   3d    │ 12:34:01 connected    │
│   sqlite     ●○ stopped         │ 12:34:02 listed tools │
│   github-pr  ⚠  failed (5/5)    │ 12:34:05 tools/list   │
│                                 │ 12:34:08 ready        │
│ Toolchains ▾                    │                       │
│ ──────────                      │                       │
│   ✓ claude-code  sync           │                       │
│   ✓ cursor       sync           │                       │
│   ⚠ zed          drifted        │                       │
│                                 │                       │
│ Secrets ▾                       │                       │
│ ───────                         │                       │
│   GITHUB_TOKEN  set             │                       │
│   SQLITE_PATH   set             │                       │
├─────────────────────────────────┴───────────────────────┤
│ ? help · / search · enter view · l logs · s start · q quit │
└─────────────────────────────────────────────────────────┘

Design rationale: mcpm is an inventory + action tool. The user needs at-a-glance answers to "what's running? what's broken? what's drifting?". Single-screen with always-visible inventory delivers this; multi-screen designs (htop / tig style) require navigation to get the same information, which is the wrong tradeoff for a dashboard.

Pane focus + always-on hint bar

  • The focused pane gets a highlighted border. Single-character actions in the hint bar apply to the focused pane's selected entity.
  • The hint bar is context-aware: when a server is stopped, s appears; when it's running, d appears instead. This mirrors lazygit's pattern of hiding inapplicable affordances.
  • Switching pane focus: Tab within the left column (Servers → Toolchains → Secrets → Servers) when the right pane is on a log tab; outside of log tabs, Shift+Tab to switch pane focus and Tab for log-stream cycling. (See log multiplexing for the precise binding semantics.)

Keymap

Top-5 single-key actions (locked)

Standard reserved keys

Reserved for future

The following keys are intentionally unbound in v1.0 to leave room for v1.x features without breaking muscle memory:

  • x, D — destructive deletes (server config removal, secret purge). Will require typed confirmation when added.
  • v — visual-select multi-pick for batch actions (start/stop multiple).
  • T, S, L — could be context-shortcuts to jump to Toolchains / Secrets / Logs panes directly, but Shift+Tab covers the case.

Mouse support

ratatui + crossterm's EnableMouseCapture. About 5 lines of setup at TUI boot; degrades gracefully on terminals without mouse support.

  • Click to focus a pane — clicking inside the Servers pane focuses it (same as Shift+Tab to it).
  • Click to select an entity — clicking a server row selects it (same as arrow-down-to-it).
  • Mouse wheel — scrolls the focused pane (including log scrollback).
  • Double-click — same as Enter on the focused entity (drill into detail).
  • Option/Alt bypass — holding Option (macOS) / Alt (Linux) while click-dragging bypasses mouse capture, allowing native terminal text selection for copy/paste. This is the universal escape hatch; documented in the help modal.

Right-click is unbound in v1.0 (no context menus in the TUI yet).

Log multiplexing

Three log streams: the focused server's stdout+stderr, mcpd's own structured logs, and the audit log. When a server is focused in the left pane, the right pane shows logs for that server by default. Tab cycles through the streams.

Tab order:  [server]  →  [mcpd]  →  [audit]  →  [combined]  →  [server]  →  ...

[server]   stdout + stderr of the currently-focused server
[mcpd]     mcpd's own tracing logs (per-server filtered when a server is focused;
           shows all daemon-level events when "mcpd" itself is focused)
[audit]    audit-log events (per-server filtered when a server is focused;
           shows all events when "mcpd" is focused)
[combined] interleaved view of all three, source-tagged + severity-colored

State preservation

  • Each tab maintains its own scroll position.
  • Switching server in the left pane carries the tab selection forward (if you were on [audit] for github, switching to filesystem keeps you on [audit] but for filesystem now).
  • Follow mode (always-tailing) is on by default; pressing f toggles it. When paused, the user can scroll back without losing new entries — they're buffered and appear when follow re-engages.

Filtering inside a stream

  • / within a log pane greps the current buffer (incremental, case-insensitive by default).
  • n/N next/previous match.
  • Esc clears the filter.

Config-edit paradigm

e on the focused entity opens $EDITOR with that entity's TOML stanza extracted to a temp file. On save, mcpd reads the temp file, validates, applies atomically, and audit-logs the change. If validation fails, the error appears in a TUI modal with the offending line highlighted; the temp file is preserved for retry.

Why not in-TUI form editing? TUIs are bad text editors. The user already has $EDITOR tuned (vim modelines, neovim LSP, even VSCode-as-editor). We provide the dispatch + atomic reload, not a worse editor.

Implementation sketch:

  1. Extract the stanza for the focused entity (e.g., [server.github] and any sub-tables like [server.github.env]) into $TMPDIR/mcpm-edit-XXXXXX.toml.
  2. Suspend the TUI (release the alternate screen + show cursor).
  3. Spawn $EDITOR $TMPDIR/mcpm-edit-XXXXXX.toml as a foreground child.
  4. On editor exit (any non-error status), parse + validate the temp file.
  5. If valid: atomic write back into the canonical config (server scope or project scope, depending on where the original stanza lived); emit config.change audit event; SIGHUP mcpd or call the equivalent reload RPC; restore the TUI.
  6. If invalid: re-enter TUI, show validation-failure modal with line/column, keep temp file path so user can retry with e again.

Source URI shape

Servers are declared with an explicit TOML table. A source = "..." string is accepted as syntactic sugar for the common case; parsed into the table form at load time.

Explicit table form (canonical)

[server.github]
registry = "official"
package  = "github-mcp"
version  = "^0.4"

Sugar string form (accepted)

[server.github]
source = "official/github-mcp@^0.4"

Both forms are equivalent. mcpm always serializes back to whichever form the user wrote (round-trip preserving).

Why TOML table over a custom URI scheme

  • TOML is what we're already using — let TOML do what it's good at.
  • v1.x will add fields beyond registry/package/version (subpath, feature flags, signed-by overrides, etc.). Each is a clean key addition. A URI scheme would need its own grammar extension every time.
  • String form stays available for the common case where copying from docs is easier than writing a multi-line block.

Per-project ↔ per-user layering

The model: layered overlay with name-override (mise-style), with explicit modes for stricter isolation when needed.

Default: layered overlay (inherit = "all")

Project config OVERLAYS user config. Same-name entries: project wins. Disjoint names: both visible.

# ~/.config/mcp-manager/config.toml (user)
[server.github]
registry = "official"
package  = "github-mcp"
version  = "^0.4"
secrets  = ["GITHUB_TOKEN"]

[server.filesystem]
registry      = "official"
package       = "filesystem-mcp"
version       = "^1.0"
allowed_paths = ["~/code", "~/Documents"]

# /work/acme-project/.mcp-manager.toml (project)
[mcpm]
inherit = "all"   # default; can be omitted

[server.acme-db]                # adds to the effective set
registry = "official"
package  = "postgres-mcp"
version  = "^0.3"
secrets  = ["ACME_DB_URL"]

[server.github]                 # overrides the user-level github
allowed_paths = ["/work/acme-project"]
# Other keys (registry/package/version/secrets) inherited from user level

Effective state inside /work/acme-project/:

  • github (project-overridden, but inherits the user-level registry/package/version unless project explicitly sets them)
  • filesystem (user, unchanged)
  • acme-db (project-added)

Mode 2: allowlist inherit

[mcpm]
inherit = ["filesystem"]   # explicit list; "github" is NOT pulled in

[server.acme-db]
registry = "official"
package  = "postgres-mcp"
version  = "^0.3"

Effective state: filesystem (inherited by name) + acme-db (project-added). User's github invisible here.

Mode 3: full isolation

[mcpm]
inherit = "none"

[server.acme-db]
registry = "official"
package  = "postgres-mcp"
version  = "^0.3"

Effective state: acme-db only. Used for privacy-sensitive client work where personal tools should not be visible.

Opt-out of a single inherited server (within Mode 1)

# /work/private-client/.mcp-manager.toml
[mcpm]
inherit = "all"

[server.github]
disabled = true   # user's github is hidden here, but other user servers stay

Project detection & trust gate

Auto-walk

mcpm walks up from cwd looking for .mcp-manager.toml. Stops at the first match, or at $HOME / filesystem root if no match. Same pattern as .git, .envrc, Cargo.toml, package.json.

Caching: the walked path is cached for the lifetime of the mcpm invocation. The daemon caches it per-client-connection with a 60-second invalidation window (so cd-ing into a different project is reflected on the next mcpm call without restarting the daemon).

Trust gate (direnv-style)

When mcpm encounters a .mcp-manager.toml for the first time in a given project, it does NOT silently load it. It prompts:

$ cd /work/cloned-from-github
mcp-manager: detected new project config:  /work/cloned-from-github/.mcp-manager.toml
             servers declared:             1 added (acme-db), 1 override (github)
             inherit mode:                 "all"
             registry sources:             official (trusted)
             secrets referenced:           ACME_DB_URL (not in your keychain)

This is the first time mcpm has seen this project config. Trust it?
  y) yes, trust this exact config (sha256: 8a9f2d...)
  n) no, ignore the project config for this session
  e) edit it before deciding

[y/n/e]:

Trust is pinned to a sha256 of the project's .mcp-manager.toml contents. If the file changes (upstream push, local edit), trust is invalidated and the prompt re-appears. Trust grants are stored in ~/.config/mcp-manager/trust.toml:

[trust."9c4f8a..."]   # sha256 of the project path
path         = "/work/cloned-from-github"
config_hash  = "8a9f2d..."   # sha256 of the project's .mcp-manager.toml
granted_at   = "2026-05-24T15:22:01Z"
granted_by   = "interactive"

Why this matters: a cloned-from-elsewhere repo can declare arbitrary servers + reference arbitrary registries. Silently loading that on cd would let a malicious repo project-configure mcpm in ways the user didn't consent to. Explicit trust gate makes the consent moment visible. This is the model direnv pioneered.

Audit-logged as project.trust / project.untrust.

Lockfile content per scope

Each scope has its own lockfile, with content that mirrors the scope's own entries — not the effective merged state. This is important for the team-onboarding story.

~/.config/mcp-manager/projection.lock (per-user)

version  = 1
metadata = { generated = "2026-05-24T14:33:01Z", mcpm = "1.0.0" }

[[server]]
name             = "github"
registry         = "official"
package          = "github-mcp"
version          = "0.4.2"           # exact-pin, resolved from "^0.4"
checksum         = "sha256:9f4e2d..."
advertised_spec  = "2025-06-18"
resolved_at      = "2026-05-24T14:33:01Z"

[[server]]
name             = "filesystem"
registry         = "official"
package          = "filesystem-mcp"
version          = "1.0.3"
# ...

[[projection]]
tool        = "claude-code"
managed_at  = "2026-05-24T14:33:01Z"
fingerprint = "sha256:..."

/work/acme-project/.mcp-manager.lock (per-project, in repo)

version  = 1
metadata = { generated = "2026-05-24T14:33:01Z", mcpm = "1.0.0" }

[[server]]
name             = "acme-db"
registry         = "official"
package          = "postgres-mcp"
version          = "0.3.1"
checksum         = "sha256:7b2c1e..."
advertised_spec  = "2025-06-18"
resolved_at      = "2026-05-24T14:33:01Z"

# Note: NO entry for `github` even though the project overrides it,
# because the override only sets allowed_paths (a project-local concern).
# The version pin for github lives in the USER lockfile.

# Note: NO entry for `filesystem` because it's user-only.

What this means for team-onboarding: when a teammate clones the repo, mcpm resolves their effective state by walking up to the project's .mcp-manager.toml (after trust gate), then composing it with their user config. They get the project's acme-db pin exactly; their personal github MCP is whatever they have in their own user config.

GITHUB_OWNER  = "anthropic"

[registry.corp]

# MCP Manager · project-scope canonical config (checked into repo)

allowed_paths = ["/work/acme-project"]
# All other keys (registry/package/version/secrets) inherited from user config.

What we deliberately rejected

Recording rejections is as important as recording picks. When v1.x rolls around and someone asks "why not X?", the answer should be findable here.

  • Multi-screen TUI (htop / tig style) — rejected because mcpm is an inventory tool; cross-cutting visibility is the primary use case and multi-screen designs fight that.
  • Minimal TUI (server-list-only, CLI for everything else) — rejected because the "obsessed about UX" mandate calls for staying-in-context for the common workflows.
  • In-TUI form editing for config — rejected; TUIs are worse text editors than the user's $EDITOR. e dispatches.
  • Always-combined log view as the default — rejected because focused investigation is the more frequent case; combined is one Tab away.
  • Split-pane logs (3 mini-windows) — rejected because on narrow terminals (tmux splits, SSH on tablet) each window becomes too small.
  • Custom URI scheme (pkg+default://...) — rejected; TOML tables are what TOML is good at. URI is sugar, not canonical.
  • Project-isolated-by-default — rejected because most developers have a personal toolkit they want available everywhere; "all" inheritance is the better default. Isolation is one-line opt-in.
  • Silent auto-load of project configs — rejected because cloned-from-elsewhere repos could carry arbitrary server declarations + registry references. Explicit direnv-style trust gate is required.
  • Right-click context menus — deferred to v1.x. Adds complexity without solving a workflow that single-key shortcuts can't.
