Product overview

MCP Manager is Docker for Model Context Protocol servers. A small Rust daemon and a polished CLI/TUI replace the current "edit five different JSON files and paste your tokens into all of them" experience. One canonical configuration, one set of secrets in the OS keychain, one process supervisor — and your existing AI tools (Claude Code, Cursor, Zed, JetBrains IDEs, VS Code) keep working with no changes.

The problem

The Model Context Protocol (MCP) lets AI assistants call out to external tools: a GitHub MCP that reads PRs and creates issues, a filesystem MCP that browses local files, a SQL MCP that queries a developer's database, etc. Each MCP server is a separate process the assistant launches and talks to over stdio or HTTP. The Anthropic/OpenAI ecosystem has converged on this protocol and there are now dozens of MCP servers actively maintained.

What's missing is management. Today, if a developer wants the GitHub MCP available in both Cursor and Claude Code:

  • They install the server twice (or three times, or four — once per editor) and configure it separately in each.
  • They paste their GITHUB_TOKEN into multiple plaintext config files. CVE-2025-6514 (mcp-remote RCE, CVSS 9.6) demonstrated this exact pattern getting weaponized — secrets in plaintext editor configs are a real, exploited attack surface.
  • Each editor spawns its own copy of the server, so updating one doesn't update the others. Crashes are silent. Memory is double-counted. Restart-on-failure depends on the editor, not the user.
  • If they want to share an MCP setup with a teammate, there's no portable format. Each editor's config schema is different. Our survey found 6 top-level config keys, 10 file locations, and 4 different env-variable expansion syntaxes across the major editors.
  • When something breaks, the developer has no central log to investigate. Each editor logs differently, if at all.

The current state is genuinely broken UX. As MCP server count per developer grows from 2-3 (today) to 10+ (likely in 2026), the friction compounds.

Who it's for

Primary: the AI-assisted developer

A developer using one or more AI coding assistants (Claude Code, Cursor, Zed AI, JetBrains AI Assistant, VS Code Copilot/Continue, …) who has reached a handful of MCP servers and started feeling the management pain. They have a dev machine, run a few personal projects + maybe some work projects, and want the AI tooling to "just work."

Secondary: the platform / dev-experience engineer

Someone at a small-to-medium engineering org responsible for "make AI tools work consistently across our team." Wants to standardize the MCP server set, pin versions, audit secret access, and onboard new engineers without per-laptop ceremony. Per-project config + lockfile-in-repo is the surface they care most about.

Tertiary: the contributor / extender

A developer who wants to publish an MCP server or add support for a new editor. v1.0 ships TOML manifests for both: third parties can publish servers to a registry and ship a TOML toolchain manifest describing their editor's config shape. No PR to MCP Manager itself required.

What MCP Manager does

One central place to manage MCP servers — install, configure, secret-set, supervise — with everything else flowing automatically.

  1. Install servers from any registry. 3 default registries baked in (official LF-stewarded MCP Registry, GitHub MCP Registry, Docker MCP Catalog). Private/corporate registries via mcpm registry add. All signed (minisign on index, cosign-when-present on packages).
  2. Keep secrets in the OS keychain. mcpm secret set GITHUB_TOKEN prompts via TTY, writes to macOS Keychain (or Linux libsecret), never to a plaintext file. Existing environment variables work as an escape hatch.
  3. Run a real process supervisor. mcpd is the long-lived daemon. It spawns MCP servers under isolation, watches for crashes, restarts with exponential backoff + max-attempts (no thundering-herd, no infinite-loops), catches OOM kills, and writes an append-only audit log of every state change.
  4. Project the config into your editors. One canonical TOML config lives in ~/.config/mcp-manager/. mcpm rewrites your editor configs (Claude Code, Cursor, Zed, JetBrains, VS Code, Windsurf, Continue, Cline, Goose, …) to point at the manager, using Ansible-style managed-block sync so your hand-edits outside the managed region are preserved.
  5. Provide an interactive surface. mcpm tui opens a lazygit/k9s-style terminal UI: three panes (Servers / Toolchains / Secrets) on the left, contextual right pane (logs / details / edit). Mouse + keyboard. Log tails for the daemon, each server, and the audit log are all one Tab away.
  6. Per-project scoping. A project can override or extend a developer's user-level MCP set via a checked-into-repo .mcp-manager.toml. Direnv-style trust gate prevents cloned-from-elsewhere repos from silently configuring the manager.
  7. Run anywhere mcpd is running. Auto-spawns from mcpm exec (no daemon-not-running errors). Opt-in registration with the user's service manager (launchd on macOS, systemd-user on Linux) on first launch.

What using it feels like

A worked example. New developer on macOS, just installed MCP Manager:

# 1. Install MCP Manager (one of two paths)
$ curl -sSf https://mcp-manager.dev/install.sh | sh
   ✓ mcpd 1.0.0 installed to /usr/local/bin/mcpd
   ✓ mcpm 1.0.0 installed to /usr/local/bin/mcpm
   Run `mcpm init` to get started.

# 2. First-run setup (fully interactive; or `mcpm init --defaults -y` for non-interactive)
$ mcpm init
   What's your name? [Parth Patel]   ←
   Scope: user or project? [user]   ←
   Detected: Claude Code, Cursor, Zed. Project into all three? [Y/n]   ←
   Detected: Docker. Enable Docker MCP Catalog as a registry? [y/N]   ←
   Register mcpd with launchd as a background service? [y/N]   ←
   ✓ Configured at ~/.config/mcp-manager/config.toml

# 3. Add an MCP server
$ mcpm search github
   official/github-mcp        v0.4.2   GitHub PR + Issue MCP (Anthropic)
   github/octocode-mcp        v0.3.1   GitHub code-search MCP (community)
   ...
$ mcpm install github-mcp
   ✓ Installed github-mcp v0.4.2 from official, pinned to ^0.4
   ⚠ Server requires secret: GITHUB_TOKEN
     Run `mcpm secret set GITHUB_TOKEN` to provide it.

# 4. Add the secret
$ mcpm secret set GITHUB_TOKEN
   Enter value (input hidden): **********
   ✓ Stored in OS keychain.

# 5. Verify it works
$ mcpm test github-mcp
   ✓ initialize    (12ms)
   ✓ tools/list    (8 tools advertised)
   ✓ tools/call create_issue  (dry-run)
   Server is healthy.

# 6. Editor configs are already updated. Open Cursor / Claude Code /
#    Zed and the github-mcp is wired up automatically.

# 7. Browse with the TUI
$ mcpm tui
   (lazygit-style interface, server statuses, live log tails)

From here, normal day-to-day is invisible: the daemon runs in the background, restarts servers when they crash, and rewrites editor configs whenever the canonical state changes.

Differentiators

Things MCP Manager does that the alternatives (mostly: "edit your editor configs by hand") don't:

DifferentiatorWhy it matters
Secrets never on disk in plaintext OS keychain integration (macOS Keychain / Linux libsecret). CVE-2025-6514 is the canonical reason.
One server, many editors Per-editor configs are projected from a single canonical state. Cursor and Claude Code share the same mcpd-supervised process.
Real process supervision Restart-on-crash with jittered backoff + max-attempts; OOM detection; audit log. Editors do none of this consistently.
Per-project + per-user scope, layered Personal toolkit available everywhere; project-specific tools added in repo. Layered with name-override (mise-style); explicit isolation available for privacy-sensitive client work.
Zero telemetry, ever No phone-home. Not opt-in, not opt-out — never collected. Permanent project commitment.
JetBrains XML projection The hard one. JetBrains IDEs store MCP config in XML; we ship support out of the box in v1.0.
Data-driven manifests, not hardcoded support Each editor's projection is a TOML manifest. When an editor's schema changes, ship a manifest update — no mcpd binary release required. Users can author manifests for new editors locally.

Non-goals

What MCP Manager deliberately doesn't do:

  • Implement MCP itself. The official Rust SDK (rmcp) is our dependency. We're a manager of MCP servers, not an MCP implementation.
  • Compete with the AI assistants. We project configs into Cursor / Claude Code / Zed / JetBrains; we don't replace them.
  • Run MCP servers in the cloud. v1.0 is a local-only developer tool. Cloud hosting is out of scope.
  • Support Windows. Permanent project decision. macOS + Linux only.
  • Telemetry. No usage metrics, no anonymous crash reports, no opt-in pings. Permanent.
  • Scale to thousands of MCPs. Architecture optimizes for "a few dozen managed servers per user," not a package-index workload.
  • GUI in v1.0. Deferred (research preserved). v1.0 is CLI + TUI + config files.

What success looks like

We will know v1.0 succeeded if:

  1. An AI-assisted developer with 5 MCP servers reaches "everything just works" in under 10 minutes from curl … | sh to "Cursor sees my github MCP and the token came from the keychain."
  2. The same developer can move to a new machine and reach the same state in under 5 minutes — restore the canonical config from their dotfiles repo, re-set secrets, done.
  3. A small engineering team can check in a .mcp-manager.toml + .mcp-manager.lock and have new hires reach a working setup by running mcpm init in the repo.
  4. An MCP server crash never leaves the developer wondering what happened — the audit log and per-server log tail tell the story.
  5. Adding a new editor target takes a third party an afternoon, by writing a TOML manifest — no mcpd PR, no release cycle.

The deeper success criterion is qualitative: developers should enjoy using mcpm. lazygit/k9s set the bar — the TUI we ship has to feel like that, not like a half-finished admin panel. The "OBSESSED about UX" product-owner mandate drives the entire surface.
