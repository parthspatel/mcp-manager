GUI (deferred from v1.0)

What: A visual interface for MCP Manager — server list, log tails, secret editor, toolchain projection status. v1.0 ships with CLI + TUI + config files; the GUI was researched but deferred.

Why deferred from v1.0

  • Scope reduction. Cutting the GUI removes Actix-Web, Askama, HTMX/Alpine, the HTTP/SSE bridge, the DNS-rebinding mitigations, the tray-icon helper, and the entire "browser tab vs native window" UX-tax debate from v1.0. mcpd simplifies to a tokio daemon with JSON-RPC over UDS.
  • The TUI is sufficient for v1.0's target user. Power developers running a few dozen MCP servers don't need a dashboard; they need `mcpm` + a terminal log tail. The GUI was the surface most likely to delay shipping.
  • Pre-decided architecture preserved. The GUI shootout remains as research — whenever the GUI ships, Actix + Askama (served from inside mcpd) is the standing recommendation.

v1.x spec (pre-decided in 2026-05-24 shootout)

  1. Architecture: Actix-Web + Askama, served from inside mcpd on localhost:NNNN. Server-rendered HTML + SSE for live updates + HTMX for interactivity. Zero IPC, single auth surface.
  2. Tray-icon helper (tray-icon crate, ~2MB) — dock/menubar presence on macOS + Linux.
  3. PWA install manifest — users who want a dock icon can install the localhost app to their dock with one click.
  4. Auth on localhost: bearer token in URL on first launch (Pi-hole pattern). Host: header allowlist (refuse anything except localhost/127.0.0.1/[::1]) to neutralize DNS rebinding.
  5. Save-on-blur for all edit flows — Cmd-W can't lose work.
  6. Opt-in LAN/mobile access: mcpm gui --bind 0.0.0.0 unlocks management from a phone or tablet on the same network. --bind tailscale0 for Tailscale-gated remote access.

What v1.0 must do to not foreclose this

  • Keep the JSON-RPC RPC method names stable so the GUI can talk to mcpd over the same wire as the CLI/TUI.
  • Keep mcpd's canonical state in TOML + structured journal — the GUI is just another view onto the same state.
  • Don't bake CLI-only assumptions into mcp-core (e.g. terminal-only progress reporting). The TUI already enforces this separation.

Source of deferral: 2026-05-24 product lockdown. Research preserved at ui-shootout/ (3 stacks evaluated; Actix+Askama recommended).

Secrets: rotation, TTLs, vault providers

What: v1.0 ships mcpm secret set/list/unset backed by OS keychain + an env-var passthrough escape hatch. v1.1+ adds:

  • TTL / rotation: declare per-secret rotation policy; mcpd warns or refuses to spawn a server with an expired secret.
  • Vault providers: 1Password CLI (op), Bitwarden CLI (bw), HashiCorp Vault, Doppler, Infisical, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault. Each plugs in through the SecretStore trait designed in v1.0 (closing-gap agent C).
  • Per-secret access policies: "this secret can only be read by server github, not arbitrary servers."
  • Lease-based / on-demand fetch: never persist the secret value locally; fetch from vault at spawn time, cache in memory only for the lifetime of the server process.

Source: 2026-05-24 lockdown. The v1.0 trait sketch in closing-gaps/secrets-lifecycle/ is designed to support these without re-architecting.

Import-from existing editor configs

What: mcpm import-from cursor, mcpm import-from claude-code, etc. Read the user's current editor MCP configs (which were the input to Stream 1's survey) and seed mcpd's canonical state. Massive friction-removal for adoption: a user with 8 servers already configured in Cursor doesn't have to redo any of them.

Why deferred: v1.0 ships with hand-write or `mcpm install`. Import-from is a polish feature; it can wait until v1.1.

v1.x scope: S6's projector code is already symmetric — it CAN read the same configs it writes. Import is a thin CLI verb wrapping that capability + a "first-run: shall I import?" hook in the onboarding flow (agent B's `mcpm init` accepts a stub --import-from flag in v1.0).

Source: 2026-05-24 lockdown.

Observability: metrics, tracing, Prometheus

What: v1.0 ships logs (the 3-stream tail API) and audit log. v1.1+ adds:

  • Prometheus-style /metrics endpoint on the (then-existing) GUI HTTP server, or a separate mcpd --metrics-addr bind.
  • OpenTelemetry tracing spans across the wrapper-command → mcpd → MCP-server boundary. Per-request latency histograms.
  • Standard MCP metrics: requests/sec, error rate, tool invocation counts per server, p50/p95/p99 latencies.

Source: 2026-05-24 lockdown. Out of v1.0 scope because logs cover the user-facing case; metrics are ops-facing.

Backup / restore / state portability

What: mcpm export dumps the user's canonical state (servers, projections, lockfiles, audit log) to a tarball. mcpm import-state restores it on a new machine. Secrets are NOT in the tarball — those must be re-set on the target machine via mcpm secret set (or imported from a vault in v1.x when vault providers are supported).

Why deferred: v1.0 workaround is to manually back up ~/.config/mcp-manager/; secrets are already in OS keychain (with native backup tooling on macOS). v1.1 makes this first-class.

Source: 2026-05-24 lockdown.

Resource limits beyond memory (CPU, disk, network)

What: v1.0 supports per-server memory limits via cgroupv2 (Linux) / RLIMIT_AS (macOS). v1.1+ adds CPU quota (cgroupv2 cpu.max, RLIMIT_CPU), disk I/O quotas, and network egress filtering (Linux: nftables / cgroup-bound rules; macOS: pf rules).

Why deferred: OOM was the most-frequent failure mode; CPU/disk/network are nice-to-have. The supervisor architecture already abstracts "resource limits" — adding more dimensions is additive.

Source: 2026-05-24 lockdown.

Plugin / extensibility system

What: Beyond the TOML manifest escape hatch, a real plugin SDK that lets third parties add: custom isolation backends (e.g. firejail on Linux), custom audit sinks (Splunk, Datadog), custom transport adapters (e.g. gRPC instead of stdio), custom registry providers (private corporate registries).

Why deferred: The TOML manifests + the SecretStore trait designed in v1.0 cover most third-party extension needs. A full plugin SDK with versioning, ABI compatibility, and a marketplace is a v2+ concern, not v1.1.

Source: 2026-05-24 lockdown.

Curated community toolchain registry

What: A hosted, curated registry of community-contributed toolchain manifests — analogous to Homebrew taps, mise plugins, or asdf plugins. Users would run something like:

mcpm toolchain add @community/cline-fork
mcpm toolchain add github:user/my-custom-editor-manifest
mcpm toolchain list --remote

…and pull a vetted TOML manifest for an editor or AI client that MCP Manager doesn't ship native support for.

Why deferred from v1.0

  • Maintenance burden. A curated registry needs a moderation policy, a vetting process, abuse reporting, and someone responsible for it. v1.0 doesn't have the bandwidth.
  • Trust model is non-trivial. A manifest in the projector runs with the user's filesystem permissions — a malicious manifest could exfiltrate secrets or overwrite arbitrary files. Needs signing, provenance, possibly a sandboxed execution model.
  • v1.0's TOML escape hatch already covers the urgent need. Users CAN teach mcpm about new tools right now by dropping a TOML manifest in ~/.config/mcp-manager/manifests/. The registry just makes discovery easier.

v1.1 spec sketch

  1. Registry format: probably a Git repository (Homebrew-tap-style) — clone or shallow-fetch, no central HTTP API needed. Lower ops cost.
  2. Trust tiers:
    • core — manifests shipped with mcpm itself (e.g. @mcp-manager/core).
    • community — vetted, signed by a maintainer (@community/*).
    • unverified — arbitrary git URLs; user must accept a "trust this source" prompt the first time. Signature optional.
  3. Signing: minisign or ssh-signed-git-tags. Pick one; minisign is simpler.
  4. Capability declarations: each manifest declares what filesystem paths it writes and what env vars it reads. mcpm enforces the declaration at projection time (refuses to write outside the declared paths). This makes a malicious manifest much less dangerous — the worst it can do is corrupt the editor configs it explicitly says it manages.
  5. CLI: mcpm toolchain sub-commands — add / list / remove / update / verify.
  6. Curation policy: needs human governance. Probably one or two trusted maintainers initially; PR-based.

What can be done in v1.0 to NOT make this harder

The v1.0 TOML manifest format should be designed with future-registry use in mind:

  • Include a schema_version field so v1.0 manifests work on v1.1 mcpm.
  • Include optional capabilities declarations (paths-written, env-read) — v1.0 won't enforce them, but v1.1 will. Manifests authored now will already be enforceable later.
  • Include optional source + signature fields. Tolerate absence in v1.0; require for community-tier in v1.1.

Source of deferral: 2026-05-24 product lockdown. Originally flagged in clever-fox-bridge / S6.

Tauri shell over the future GUI

What: Once the GUI itself ships (see above), a follow-on improvement is a thin Tauri 2 binary whose WebView points at http://localhost:NNNN — i.e., the same Actix UI wrapped in a real native window with a dock icon, native menu bar, system notifications, and macOS code signing / notarization. Best of both: zero UI rewrite, but a "real app" feel.

Why this lands later than the GUI itself

  • The GUI deferral (the section above) is the primary v1.0 → v1.x scope reduction. The Tauri shell only makes sense once the GUI exists.
  • The "browser tab" UX taxes (no dock icon, Cmd-W kills the UI, no global hotkeys) can be measured empirically once the GUI ships — we'll know whether the tray-icon + PWA mitigations are enough.
  • Tauri adds packaging complexity (Apple notarization, code-signing certs, AppImage/.deb/.rpm builds) that's better learned after the UI itself is stable.

v1.1 spec sketch

  1. New crate mcpd-shell-tauri — Tauri 2 app, dependency on mcpd as a sidecar, points the WebView at localhost:NNNN.
  2. No UI rewrite — Actix server and Askama templates from v1.0 are reused verbatim. The shell is purely a wrapper.
  3. Distribution: Tauri shell becomes the recommended download for non-developer users; the headless mcpd + browser-tab mode remains supported (and still required for LAN/mobile use).
  4. Native integrations: dock badge with running-server count, macOS Touch Bar entries for quick start/stop, system notifications for server crashes, native open/save dialogs for config import/export.
  5. Auto-update: Tauri's first-party updater for the shell binary; the bundled mcpd updates independently via Homebrew/apt/cargo.

What can be done in v1.0 to NOT make this harder

  • Make sure the Actix server can be configured via env vars or flags (port, bind address, auth token) so the Tauri shell can launch it cleanly.
  • Keep all UI state in the URL (deep-linkable views) so the Tauri shell can restore the user's last view on launch.
  • Avoid any UI feature that fundamentally requires browser-only behavior (e.g. drag-and-drop FROM the OS into the UI) without an equivalent IPC fallback.

Source: ui-shootout open questions. Flagged by the actix-tera agent (open question #5) as a likely v1.1 ask.
