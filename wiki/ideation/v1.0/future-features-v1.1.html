Curated community toolchain registry

What: A hosted, curated registry of community-contributed toolchain manifests — analogous to Homebrew taps, mise plugins, or asdf plugins. Users would run something like:

mcpm toolchain add @community/cline-fork
mcpm toolchain add github:user/my-custom-editor-manifest
mcpm toolchain list --remote

…and pull a vetted TOML manifest for an editor or AI client that MCP Manager doesn't ship native support for.

Why deferred from v1.0

  • Maintenance burden. A curated registry needs a moderation policy, a vetting process, abuse reporting, and someone responsible for it. v1.0 doesn't have the bandwidth.
  • Trust model is non-trivial. A manifest in the projector runs with the user's filesystem permissions — a malicious manifest could exfiltrate secrets or overwrite arbitrary files. Needs signing, provenance, possibly a sandboxed execution model.
  • v1.0's TOML escape hatch already covers the urgent need. Users CAN teach mcpm about new tools right now by dropping a TOML manifest in ~/.config/mcp-manager/manifests/. The registry just makes discovery easier.

v1.1 spec sketch

  1. Registry format: probably a Git repository (Homebrew-tap-style) — clone or shallow-fetch, no central HTTP API needed. Lower ops cost.
  2. Trust tiers:
    • core — manifests shipped with mcpm itself (e.g. @mcp-manager/core).
    • community — vetted, signed by a maintainer (@community/*).
    • unverified — arbitrary git URLs; user must accept a "trust this source" prompt the first time. Signature optional.
  3. Signing: minisign or ssh-signed-git-tags. Pick one; minisign is simpler.
  4. Capability declarations: each manifest declares what filesystem paths it writes and what env vars it reads. mcpm enforces the declaration at projection time (refuses to write outside the declared paths). This makes a malicious manifest much less dangerous — the worst it can do is corrupt the editor configs it explicitly says it manages.
  5. CLI: mcpm toolchain sub-commands — add / list / remove / update / verify.
  6. Curation policy: needs human governance. Probably one or two trusted maintainers initially; PR-based.

What can be done in v1.0 to NOT make this harder

The v1.0 TOML manifest format should be designed with future-registry use in mind:

  • Include a schema_version field so v1.0 manifests work on v1.1 mcpm.
  • Include optional capabilities declarations (paths-written, env-read) — v1.0 won't enforce them, but v1.1 will. Manifests authored now will already be enforceable later.
  • Include optional source + signature fields. Tolerate absence in v1.0; require for community-tier in v1.1.

Tauri shell over the Actix UI

What: A thin Tauri 2 binary whose WebView points at http://localhost:NNNN — i.e., the same Actix UI v1.0 ships, but wrapped in a real native window with a dock icon, native menu bar, system notifications, and macOS code signing / notarization. The Actix server runs as a Tauri "sidecar" process (or the same mcpd binary, just launched by Tauri instead of by the user). Both targets ship from one codebase.

Why deferred from v1.0

  • v1.0 ships Actix + Askama served from inside mcpd (see ui-shootout). That gets users a working GUI sooner with the simplest architecture.
  • The "browser tab" UX taxes (no dock icon, Cmd-W kills the UI, no global hotkeys) are partially mitigated in v1.0 by a tray-icon helper + PWA manifest. Whether they're painful in practice is an empirical question — we'll know after v1.0 ships.
  • Tauri adds packaging complexity (Apple notarization, code-signing certs, AppImage/.deb/.rpm builds) that we want to learn after the UI itself is stable.

v1.1 spec sketch

  1. New crate mcpd-shell-tauri — Tauri 2 app, dependency on mcpd as a sidecar, points the WebView at localhost:NNNN.
  2. No UI rewrite — Actix server and Askama templates from v1.0 are reused verbatim. The shell is purely a wrapper.
  3. Distribution: Tauri shell becomes the recommended download for non-developer users; the headless mcpd + browser-tab mode remains supported (and still required for LAN/mobile use).
  4. Native integrations: dock badge with running-server count, macOS Touch Bar entries for quick start/stop, system notifications for server crashes, native open/save dialogs for config import/export.
  5. Auto-update: Tauri's first-party updater for the shell binary; the bundled mcpd updates independently via Homebrew/apt/cargo.

What can be done in v1.0 to NOT make this harder

  • Make sure the Actix server can be configured via env vars or flags (port, bind address, auth token) so the Tauri shell can launch it cleanly.
  • Keep all UI state in the URL (deep-linkable views) so the Tauri shell can restore the user's last view on launch.
  • Avoid any UI feature that fundamentally requires browser-only behavior (e.g. drag-and-drop FROM the OS into the UI) without an equivalent IPC fallback.

Source: ui-shootout open questions. Flagged by the actix-tera agent (open question #5) as a likely v1.1 ask.
