Argument parsing

clap is the dominant choice with 75M+ downloads and 22k+ GitHub stars by 2025, and is what Rain's well-known CLI recommendations recommends for nearly all projects . Within clap there is a choice of two APIs: derive (declarative, struct-driven) and builder (imperative). The maintainers themselves state that the derive API is "generally recommended over the builder API due to its readability, ease of modification, and better synchronization between argument declaration and reading," while the builder API offers "faster compile times (if not already using other procedural macros) and provides more flexibility, allowing access to argument values, their ordering, and their sources, which the Derive API does not support" . 

// clap derive — what the MCP Manager CLI would likely look like.
use clap::{Args, Parser, Subcommand};

#[derive(Parser)]
#[command(name = "mcpm", version, about = "MCP Manager")]
struct Cli {
    #[command(subcommand)]
    command: Commands,
}

#[derive(Subcommand)]
enum Commands {
    /// Start one or more MCP servers
    Up(UpArgs),
    /// Stop running servers
    Down { server: Option<String> },
    /// List servers
    Ps,
}

#[derive(Args)]
struct UpArgs {
    server: Vec<String>,
    #[arg(long)] detach: bool,
}

fn main() { let _ = Cli::parse(); }

Derive is the "git-like" pattern that clap itself documents in its cookbook . It composes well with #[command(flatten)] for shared arg sets and with externally defined argument structs (Args::augment_args) .

// clap builder — when you need runtime customization, e.g. plugins
// registering subcommands at startup, or inspecting which arg set a
// value came from.
use clap::{Arg, ArgAction, Command};

fn cli() -> Command {
    Command::new("mcpm")
        .subcommand(
            Command::new("up")
                .arg(Arg::new("server").num_args(0..))
                .arg(Arg::new("detach").long("detach").action(ArgAction::SetTrue)),
        )
}

fn main() { let _m = cli().get_matches(); }

Builder is what you reach for when subcommands are discovered at runtime (e.g. dynamic plugin registration), or when you need ArgMatches::index_of / value_source level introspection that the derive API doesn't expose .

// bpaf — applicative parser combinators.
use bpaf::*;

fn options() -> OptionParser<(bool, Vec<String>)> {
    let detach = long("detach").switch();
    let server = positional::<String>("SERVER").many();
    construct!(detach, server).to_options()
}

fn main() { let (_d, _s) = options().run(); }

bpaf supports both a combinatoric API (above) and a derive API. Its applicative semantics let it derive better completions and clearer error messages, at the cost of being unfamiliar to Rust developers used to clap .

// argh — Google's Fuchsia-flavored derive parser.
use argh::FromArgs;

#[derive(FromArgs)]
/// MCP Manager
struct Cli {
    #[argh(subcommand)]
    cmd: SubCommand,
}

#[derive(FromArgs)]
#[argh(subcommand)]
enum SubCommand { Up(Up), Down(Down) }

#[derive(FromArgs)]
#[argh(subcommand, name = "up")]
struct Up { #[argh(switch)] detach: bool }

#[derive(FromArgs)]
#[argh(subcommand, name = "down")]
struct Down {}

fn main() { let _: Cli = argh::from_env(); }

argh follows Fuchsia OS conventions, which differ from POSIX/GNU long-option idioms users expect on Unix; on the upside it has the lowest binary-size overhead in its derive class .

// pico-args — zero-dependency manual matching.
fn main() -> Result<(), pico_args::Error> {
    let mut args = pico_args::Arguments::from_env();
    let detach = args.contains("--detach");
    let _server: Vec<String> = args.finish().into_iter()
        .map(|s| s.into_string().unwrap()).collect();
    println!("detach: {detach}");
    Ok(())
}

pico-args is intentionally tiny — zero dependencies and the smallest binary footprint — but you write your own help text and there is no derive, no completion, and no subcommand routing .

Table / record formatting

The MCP Manager CLI will print server lists, mount tables, and config diffs. Three credible crates exist:

CrateStyleStatusNotes
tabled Derive-based: #[derive(Tabled)] on the row struct, then Table::new(rows) Active Best DX when rows correspond to a Rust type; flexible tabled::settings for borders/wrapping .
comfy-table Builder-based; rows are Vec<Cell> Active No unsafe, ANSI styling, dynamic column wrapping; minimal API surface .
prettytable-rs Builder-based; macro-friendly Unmaintained No commits in 3+ years and a rustsec/advisory-db entry was requested . Not viable for new work.

For machine-readable output (--output json, --output yaml) the CLI would lean on serde_json/serde_yaml directly, mirroring kubectl -o json and gh ... --json .

Colorization

The candidates form a clear "old / new / fork-of-old" pattern:

CrateApproachNotes
owo-colors Zero-allocation extension trait: "hi".red().bold() Zero deps by default, no_std-compatible, drop-in replacement for colored; supports ANSI, xterm-256, truecolor . Rain's recommendations endorse it as the modern default .
colored Older string-allocating API Still widely used; works fine but allocates and lacks no_std support .
nu-ansi-term Active fork of abandoned ansi_term Kept alive primarily for tracing-subscriber compatibility; not a typical pick for new code .

Whichever crate is chosen, the CLI must respect NO_COLOR and detect TTYs — per the Command Line Interface Guidelines .

Progress reporting

indicatif is the de facto choice with over 90 million downloads on crates.io . It provides bounded ProgressBars, unbounded spinners, and a MultiProgress coordinator for concurrent bars . Tracing-style observability can be piped through tracing-indicatif for free .

kdam is the only credible alternative — a tqdm-style port with gradient colors, nested bars, and Jupyter rendering — but its ecosystem reach is far smaller .

use indicatif::{ProgressBar, ProgressStyle, MultiProgress};

let mp = MultiProgress::new();
let pb = mp.add(ProgressBar::new(100));
pb.set_style(
    ProgressStyle::with_template("{spinner:.green} [{bar:40.cyan/blue}] {pos}/{len} {msg}")
        .unwrap()
        .progress_chars("=>-"),
);
for i in 0..100 { pb.set_position(i); }
pb.finish_with_message("done");

Shell completion

clap_complete generates static completion scripts for Bash, Zsh, Fish, Elvish, and PowerShell at build time or on demand at runtime via a hidden subcommand . clap_complete_nushell and clap_complete_fig add Nushell and Fig support. For dynamic per-invocation completions (e.g. completing live server names) the team would either use clap_complete's dynamic completion feature or fall through to bpaf, which has dynamic completion baked into the parser itself .

// Idiomatic clap pattern: hidden `completions <shell>` subcommand.
use clap::{CommandFactory, Parser, Subcommand};
use clap_complete::{generate, Shell};

#[derive(Parser)]
struct Cli { #[command(subcommand)] cmd: Commands }

#[derive(Subcommand)]
enum Commands {
    /// Print shell completion script
    Completions { shell: Shell },
    // ... real commands ...
}

fn main() {
    let cli = Cli::parse();
    if let Commands::Completions { shell } = cli.cmd {
        let mut cmd = Cli::command();
        generate(shell, &mut cmd, "mcpm", &mut std::io::stdout());
    }
}

CLI style precedents

The MCP Manager CLI is meant to feel familiar to operators already comfortable with container/orchestrator CLIs:

docker

Noun-verb grouping (docker container ls, docker image rm), implicit short-form aliases (docker ps), and --format for templated output .

kubectl

Verb-noun (kubectl get pods), -o {json,yaml,wide,...}, declarative -f file.yaml, and label selectors -l app=foo .

gh

Nested subcommands (gh pr view), --json field1,field2 for typed output, interactive prompts when args are missing in a TTY .

cargo / nix / bun

Cargo's --release / --features are the canonical Rust pattern; nix flake shows nested-subcommand depth; bun demonstrates colored, progress-driven first-time UX. All three obey the modern CLI Guidelines on color, exit codes, and help .

What this surface needs in practice:

  • Subcommands with at least one nesting level (mcpm server up, mcpm config set).
  • -o {table,json,yaml} for every list/show command, with table being the default in TTYs.
  • Colorized status pills (running, stopped, crashed) with TTY detection and NO_COLOR respect.
  • Streaming progress for long-running operations (up, rebuild, pull) via indicatif.
  • Shell completion for every subcommand and for live values (server names, profiles).
