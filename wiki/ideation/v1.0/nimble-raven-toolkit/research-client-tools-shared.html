Research — Cross-client shared layer (mcp-client)

The CLI, TUI, and GUI all need to do the same things: connect to the MCP Manager daemon, model errors, render server status, mask secrets, and report telemetry. Duplicating that logic three times is the failure mode. This page enumerates what should live in a shared mcp-client crate (consumed by all three surfaces) versus what is genuinely UI-specific.

Scope of mcp-client

The shared crate exists to absorb everything that is not rendering. It depends on the wire-protocol crate defined in Stream 4 but knows nothing about clap, ratatui, or any GUI framework. Each client crate (mcp-cli, mcp-tui, mcp-gui) depends on mcp-client and a single UI framework.

# Cargo workspace layout — illustrative.
[workspace]
members = [
  "crates/mcp-protocol",   # wire types, transport (from Stream 4)
  "crates/mcp-client",     # shared client logic — this page
  "crates/mcp-cli",        # clap-based binary
  "crates/mcp-tui",        # ratatui-based binary
  "crates/mcp-gui",        # tauri / egui / iced binary
]

Error model

A single error enum used by all three clients keeps user-facing messages consistent. The crate uses thiserror for library-style errors that downstream binaries can match on, and each binary uses anyhow or its own surface-specific wrapper for top-level reporting.

use thiserror::Error;

#[derive(Debug, Error)]
pub enum ClientError {
    #[error("daemon is not running at {socket}")]
    DaemonUnavailable { socket: String },

    #[error("server {0} not found")]
    UnknownServer(String),

    #[error("authentication required")]
    AuthRequired,

    #[error("protocol mismatch: client expects {expected}, daemon speaks {got}")]
    ProtocolMismatch { expected: String, got: String },

    #[error(transparent)]
    Io(#[from] std::io::Error),

    #[error(transparent)]
    Protocol(#[from] mcp_protocol::Error),
}

pub type Result<T> = std::result::Result<T, ClientError>;

The shared crate also defines exit-code mapping (impl From<ClientError> for i32) so the CLI uses identical codes across all subcommands, following the CLI Guidelines on exit codes .

Config loader

All three clients need to discover: where the daemon is listening, which profile the user is on, where credentials live, and which optional features are enabled. The shared loader is the source of truth.

Typical Rust stack for this:

  • directories for XDG-style paths (~/.config/mcpm/ on Linux, ~/Library/Application Support/mcpm on macOS, %APPDATA%\mcpm on Windows).
  • serde + toml (or serde_json) for the on-disk schema.
  • figment or hand-rolled layering for env-var overrides (e.g. MCPM_SOCKET, MCPM_PROFILE).
  • A Config::load_with_overrides() entry point that each client calls with surface-specific overrides (CLI flags vs. GUI Settings panel).
pub struct Config {
    pub socket: Option<PathBuf>,
    pub profile: String,
    pub colors: ColorPolicy,
    pub log_level: tracing::Level,
}

impl Config {
    pub fn load() -> Result<Self> { /* XDG + env + file */ }
    pub fn with_cli_overrides(self, cli: &CliFlags) -> Self { /* merge */ }
}

API client (consumer of the Stream-4 protocol)

The shared crate exposes one Client type that talks to the daemon over whatever transport Stream 4 picks (Unix domain socket, named pipe, TCP+token). The Stream-4 details are deliberately out of scope here; the shape of the consumer is not:

pub struct Client { inner: mcp_protocol::Connection }

impl Client {
    pub async fn connect(socket: &Path) -> Result<Self>;
    pub async fn list_servers(&self) -> Result<Vec<ServerSummary>>;
    pub async fn server_status(&self, name: &str) -> Result<ServerStatus>;
    pub async fn start_server(&self, name: &str) -> Result<()>;
    pub async fn stop_server(&self, name: &str) -> Result<()>;
    pub fn tail_logs(&self, name: &str) -> impl Stream<Item = Result<LogLine>>;
    pub fn watch_events(&self) -> impl Stream<Item = Event>;
}

All three clients depend on this surface. The CLI calls it synchronously (one request per command); the TUI subscribes to watch_events and refreshes panes; the GUI does the same and pushes events to the WebView/native UI thread via channels (for Tauri, via tauri::ipc::Channel which is purpose-built for streaming) .

Output formatters

The CLI needs --output {table,json,yaml,wide}. The TUI and GUI render the same data into widgets. The lowest-common-denominator that goes into the shared crate:

  • Data types only: ServerSummary, ServerStatus, ConfigDiff live in mcp-client with serde derives.
  • Plain-text/JSON/YAML serializers live in mcp-client::format::{json,yaml,plain} — used by the CLI for machine output and by the GUI for "Copy as JSON" actions.
  • Status pill semantics: a StatusKind enum + is_problem() / label() / color_hint() methods live in shared code. Each client maps the hint to its own concrete coloring (owo-colors on CLI, ratatui::style::Style on TUI, CSS class or egui::Color32 on GUI).
  • What does NOT belong: table renderers — that's UI-specific. The CLI uses tabled or comfy-table , the TUI uses ratatui::widgets::Table, the GUI uses its framework's grid.

Secret prompts

Adding a server often requires injecting an API key (Anthropic, OpenAI, GitHub token, etc.). The interaction differs per surface but the underlying behavior is shared.

SurfacePrompt mechanismStorage
CLI dialoguer or inquire for TTY prompts; refuses to prompt in non-TTY mode (uses env var or fails) OS keyring via keyring crate; falls back to encrypted file
TUI In-app modal with masked input Same keyring backend
GUI OS-native password field with platform autofill Same keyring backend

The shared crate exposes a SecretStore trait + a default KeyringStore impl. The clients only have to drive the prompt UX; storage is identical.

pub trait SecretStore {
    fn get(&self, key: &str) -> Result<Option<Secret<String>>>;
    fn set(&self, key: &str, val: Secret<String>) -> Result<()>;
    fn delete(&self, key: &str) -> Result<()>;
}

pub struct Secret<T>(T); // wraps zeroize::Zeroizing for memory safety

Telemetry & logging

All three clients use tracing for structured logging (the de facto Rust standard), with the formatter wired up per surface. The shared crate sets up the subscriber chain:

  • CLI: tracing_subscriber::fmt with EnvFilter::from_default_env(), color via nu-ansi-term (the version tracing-subscriber already pins) .
  • TUI: tracing-subscriber writing to a rolling file under ~/.cache/mcpm/logs/; optionally a tail-style pane via tui-logger.
  • GUI: tracing-subscriber + a file appender; the GUI itself surfaces logs via the Stream-4 event stream, not via the local tracing layer.

If indicatif progress bars are in play, tracing-indicatif bridges spans into bars cleanly so the CLI's progress output and its log output don't fight each other .

Where the boundary is

Decision rule: everything that depends on a user input device or a renderer stays out. Concretely:

ConcernBelongs in mcp-client?Reason
Wire types (ServerSummary, Event)YesPure data, used by all three
Config loading and mergingYesFile paths and env vars don't care which UI
Error enum + exit-code mappingYesShared message wording
Daemon transport / API methodsYesSingle source of truth for the wire protocol
JSON / YAML serializationYesSame machine output for all surfaces
SecretStore + Keyring backendYesStorage is identical
Status-kind enum and color hintsYesSemantic; concrete colors vary
Tracing setup (default subscriber)Yes (with feature flags)Each binary opts in
Argument parser (clap)NoCLI-only
Widgets (ratatui::widgets, egui::Window, ...)NoUI-specific
Concrete table renderer (tabled, comfy-table)NoCLI-only
Color crate (owo-colors)NoEach surface picks its own
Progress bars (indicatif)NoCLI-only; GUI/TUI use their native progress widgets
Prompts (dialoguer, inquire)NoTUI/GUI use modal UIs instead

A useful heuristic: the shared crate should compile to WASM with no changes. If a dependency makes that impossible, it probably belongs in a UI crate instead.
