Recommendation — version management for v1.0

Adopt the range-in-manifest, exact-in-lockfile model from Cargo and npm. For spec-version negotiation, advertise an allow-list of MCP spec dates and refuse incompatible servers at install time using the registry's advertised supportedSpecVersions. Classify update diffs with Renovate's vocabulary. Wire every version change to the existing audit.config.change event spine, and run the v1.0 health check (mcpm test) automatically after every bump with rollback on failure.

CLI surface

CommandBehaviour
mcpm install github-mcpNo version constraint. Resolves the latest registry version; writes github-mcp = "^X.Y" to manifest using the resolved version's leftmost non-zero digit as the floor (Cargo caret default); writes exact {version, checksum, source, advertised_spec} to lockfile.
mcpm install github-mcp@^0.4Explicit range. Manifest takes the literal string; lock records the resolved exact version.
mcpm install github-mcp@=0.4.2Exact pin. Manifest stores =0.4.2; lock is identical. Future mcpm update ignores this entry unless --include-pinned is passed.
mcpm updateFor every entry, re-resolve within the manifest constraint; classify changes (major/minor/patch/digest/spec-bump); render colored diff; ask for confirmation; on accept, write lock, emit audit event, run health check, roll back on failure.
mcpm update github-mcpSame as above, scoped to one server.
mcpm update --precise github-mcp@0.5.0Cargo-style precise update. Bumps lock to exactly 0.5.0 even if outside manifest constraint — in which case the manifest is widened (with explicit prompt).
mcpm outdatedRead-only preview. No lockfile writes. Lists every server with its current pinned version, the latest available, and the classification of the diff. Equivalent to npm outdated.
mcpm lock --strictMise-style strict mode. Refuse to fetch anything not pre-recorded in the lockfile. Default for CI environments.
mcpm lock --refreshRenovate's lockFileMaintenance: re-resolve without changing any version pins; useful after a registry migration.

Lockfile format (TOML)

Composes with the toolchain-projection lockfile decided by clever-fox-bridge: one file, two top-level tables. Per-user: ~/.config/mcp-manager/mcp-manager.lock. Per-project: ./mcp-manager.lock. Schema sketch: 

# mcp-manager.lock — sample (10 lines, server-version section)
version = 1
metadata = { generated = "2026-05-24T14:33:01Z", mcpm = "1.0.0", spec_versions = ["2025-11-25", "2025-06-18"] }

[[server]]
name = "io.github.modelcontextprotocol/github-mcp"
version = "0.4.2"
source = "registry+https://registry.modelcontextprotocol.io"
checksum = "sha256:9f4e2d1a8b3c7f6e5d4c3b2a1908f7e6d5c4b3a2"
advertised_spec = "2025-06-18"
resolved_at = "2026-05-24T14:33:01Z"

Notes on this schema, with prior-art links:

  • version at top — lockfile schema version, separate from any package version. Cargo and Nix both do this; uv does not and has paid for it. Pin to 1 for v1.0.
  • name is fully namespaced — reverse-DNS as the MCP Registry already mandates.
  • source — URL-with-prefix tag, mirroring Cargo. Acceptable prefixes: registry+<url>, git+<url>#<sha>, path+<abs-path> (local dev).
  • checksum — SHA-256 of the install artifact tarball. Skipped for path+ sources.
  • advertised_spec — the MCP spec date the server claims at registry-publish time, used for install-time refusal before runtime negotiation ever happens.
  • resolved_at — helps with debugging "why did this resolve to a different version than my teammate's same date?" — useful only when the manifest is loose; ignored for pure verification.
  • The projection section (from clever-fox-bridge) lives under [projection.<tool>] tables, not shown here. Same file, separate concern.

Spec-version negotiation algorithm

The algorithm runs in three phases. Phase 1 is install-time (read registry metadata), phase 2 is initialize-time (MCP lifecycle handshake), phase 3 is wire-time (every subsequent HTTP call must carry the negotiated MCP-Protocol-Version header to avoid the @ai-sdk/mcp regression):

  1. Phase 1 — install-time refusal. mcpd config holds spec_versions: an allow-list of MCP spec dates ordered newest-first. Default: ["2025-11-25", "2025-06-18"]. When mcpm install <server> reads the registry entry, it computes intersect(registry.supportedSpecVersions, daemon.spec_versions). Empty intersection ⇒ install refused with structured error SpecVersionUnsupported listing both sides. Non-empty ⇒ the lockfile records the newest common version in advertised_spec.
  2. Phase 2 — initialize-time negotiation. When mcpd spawns the server and sends initialize, it advertises its newest supported version (matching the MCP spec contract). The server responds with either (a) the same version — happy path, or (b) a different supported version. mcpd checks the response against its allow-list: if in-list, accept and proceed; if out-of-list, log audit.session.refused and disconnect per the spec's SHOULD.
  3. Phase 3 — wire-time consistency. The negotiated version is stored on the per-session connection object and re-emitted as the MCP-Protocol-Version request header on every Streamable HTTP call. Stdio sessions don't need this (the framing is in-band) but the same state machine guards against accidentally upgrading mid-session.

Worked example

Scenario: A user installs github-mcp (which advertises supportedSpecVersions: ["2025-06-18"]) on a daemon configured with spec_versions = ["2026-04-01", "2025-06-18"].

  1. Install (phase 1). Registry metadata for io.github.modelcontextprotocol/github-mcp@0.4.2 declares supportedSpecVersions: ["2025-06-18"]. Daemon allow-list is ["2026-04-01", "2025-06-18"]. Intersection is ["2025-06-18"]. Install proceeds. Lockfile records advertised_spec = "2025-06-18".
  2. Initialize (phase 2). mcpd opens the server process and sends initialize with protocolVersion: "2026-04-01" (newest supported). The server responds with protocolVersion: "2025-06-18". 2025-06-18 is in the allow-list. Accept.
  3. Wire (phase 3). If the server uses Streamable HTTP, the connection object stores negotiated_version = "2025-06-18"; every subsequent tool-call request emits MCP-Protocol-Version: 2025-06-18. Stdio servers skip this.
  4. Audit. Log audit.session.opened {server: "github-mcp", negotiated_spec: "2025-06-18", advertised: "2026-04-01"}. The fact that a downgrade happened is recorded so a team lead can ask "why are we still on the old spec for this server" without spelunking through process logs.
  5. Counter-scenario. If instead the server advertised only 2025-03-26 and the daemon allow-list was ["2026-04-01", "2025-06-18"], phase 1 would refuse the install with: 
    error[E.SpecVersionUnsupported]: github-mcp@0.4.2 advertises MCP spec [2025-03-26]
which is not in the daemon's allow-list [2026-04-01, 2025-06-18].
Hint: add "2025-03-26" to spec_versions in ~/.config/mcp-manager/config.toml,
or upgrade the server with `mcpm update github-mcp`.

mcpm update — classified diff UX

The terminal output uses Renovate's class names so users with prior dependency-management experience pattern-match instantly. Best-practice defaults follow Renovate's recommendation: auto-apply patch + digest-after-confirmation, prompt for minor, refuse major without an explicit flag. 

$ mcpm update
Resolving updates for 5 servers...

  [PATCH]  github-mcp           0.4.2 -> 0.4.3       (mcp-spec unchanged: 2025-06-18)
  [MINOR]  fetch-mcp            1.2.0 -> 1.3.0       (mcp-spec unchanged: 2025-11-25)
  [MAJOR]  postgres-mcp         0.9.4 -> 1.0.0       REFUSED - pass --accept-breaking
  [SPEC]   filesystem-mcp       0.6.1 (now advertises 2025-11-25, was 2025-06-18)
  [MAINT]  slack-mcp            checksum refresh, no version change

Apply 3 changes (1 patch, 1 minor, 1 spec-bump)? [y/N/d=diff]

  > y
Updating lockfile...
Running health checks (mcpm test) on changed servers...
  github-mcp       initialize OK, tools/list OK (12 tools)
  fetch-mcp        initialize OK, tools/list OK (4 tools)
  filesystem-mcp   initialize FAILED: server crashed during initialize.
                   Rolling back to 0.6.0 in lockfile.
Audit log entries written: audit.config.change x4, audit.session.refused x1.

The interactive prompt accepts d to drop into a detailed per-server diff view (changelog link if registry provides one, full version metadata, the previous and new checksums, a list of which tools the server now exposes vs before via cached tools/list output). All without leaving the terminal — works equally in mcpm (CLI) and the TUI surface.

Audit-log integration

Every write to the version section of the lockfile emits exactly one event with the existing audit.config.change schema: 

{
  "type": "audit.config.change",
  "ts": "2026-05-24T14:35:00Z",
  "actor": { "kind": "cli", "user": "parth" },
  "subject": { "kind": "lockfile.server_pin",
               "name": "io.github.modelcontextprotocol/github-mcp" },
  "before": { "version": "0.4.2", "checksum": "sha256:9f4e..." },
  "after":  { "version": "0.4.3", "checksum": "sha256:1a2b..." },
  "classification": "patch",
  "trigger": "mcpm update"
}

Spec-version refusals get their own event type (audit.session.refused) since they happen at runtime, not config-change time. Digest anomalies (same version, different checksum) emit both audit.config.change and audit.security.anomaly.

Health-check integration & rollback

  1. For each server whose lockfile entry changed, run mcpm test <server> — the v1.0 health check that runs initialize + tools/list and reports.
  2. If the test passes, the new lockfile entry is committed in place.
  3. If the test fails, the lockfile is restored to the previous entry (atomic file replace via tempfile + rename), an audit.config.change reversal event is emitted, and the user sees a "rolled back" line in the update output.
  4. This pattern means mcpm update is always safe to run blind — the worst case is "no changes applied because health check refused them."

Open questions for orchestrator synthesis

  • Default spec_versions allow-list. Recommend ["2025-11-25", "2025-06-18"] at v1.0 ship. When 2026-07-28 goes stable, do we (a) auto-roll the default in the next mcpm point release, (b) require the user to opt-in via mcpm config spec-versions add 2026-07-28, or (c) auto-add the newest but never auto-drop the oldest? Suggest (c) — never break running setups.
  • SDK version coupling. The Rust SDK we use advertises spec-version support at compile time. Should mcpd refuse to load if its SDK can't speak a version in the user's allow-list? Yes — refuse loudly at daemon start, not later.
  • Registry trust. The MCP Registry is metadata-only — the actual checksums live in npm / PyPI / Docker. Do we verify checksums against the registry's published value or refetch from upstream and trust whatever upstream says? Recommend: trust the registry's value as the canonical record and refuse if upstream returns something different. (This is also where the digest classification fires.)
  • Per-server spec override. Should we expose manifest.servers.github-mcp.spec = "2025-06-18" as a per-server allow-list override? Useful for shimming a server that lies in its registry metadata. Recommend: ship it, but document it as escape-hatch, not idiomatic.
  • Lockfile commit policy when per-project. Following Cargo: yes, commit the per-project lockfile. The per-user lockfile stays in ~/.config/ and is git-ignored.
