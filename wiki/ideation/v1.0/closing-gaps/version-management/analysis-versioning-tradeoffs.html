Analysis — versioning tradeoffs

We have to decide three things, and they couple loosely: (1) how do users express the version they want for a server, (2) where does the source of truth live — manifest or lockfile — and (3) how does mcpd handle the MCP-spec-version mismatch axis. This page lays out the options for each, scores them, and feeds the matrix in data/versioning-strategy-ranking.json.

Axis A — server-version pinning

Option A1 — Always-latest (no pinning, no lock)

The "npx -y latest" UX: every mcpm install resolves to whatever the registry says is newest, no record kept. Wins on freshness and lockfile simplicity (no lock at all). Fatal for v1.0: our scale target is "a teammate installs the same servers tomorrow and gets the same versions"; this option breaks that hard. It also defeats supply-chain integrity — if a malicious version 0.4.3 ships overnight, the user installs it without seeing what changed.

Option A2 — Exact pin only, no lock

Users write github-mcp = "=0.4.2" in the manifest; the manifest is the lock. Mirrors asdf's .tool-versions philosophy. Maximally reproducible, minimally maintainable: every patch bump is a hand-edit. Loses Cargo-style "let me get the latest 0.4.x without thinking" affordance.

Option A3 — Range in manifest, no lockfile

What you get if you write github-mcp = "^0.4" in package.json without --save-exact and delete the lock. Two machines installing on different days get different versions. The original ergonomic disaster that prompted lockfiles in the first place.

Option A4 — Range in manifest + lockfile (Cargo/npm pattern)

Manifest expresses intent (^0.4); lockfile records what was actually installed (0.4.2 + sha256). First install resolves and writes the lock; subsequent installs read the lock; mcpm update re-resolves within the manifest constraint and updates the lock with a visible diff. This is the model Cargo, npm, and mise have all converged on independently. Wins everywhere except raw lockfile-simplicity (vs A1/A2).

Option A5 — Lockfile only (no manifest)

The asdf model rebuilt around our schema. One file lists every server at an exact version; users edit it directly. Wins on simplicity, loses on the affordance gap (no way to express "any 0.4.x") and on team review (every patch bump looks the same as a major bump in the diff). Rejected for shipping — but kept as a runtime fallback when a manifest is absent.

Option A6 — Content-addressed (Nix flake style)

Record a hash that uniquely identifies the install artifact rather than a name+version pair. Maximally rigorous; defeats registry-rename attacks. Overkill for 10s of MCPs and one canonical registry — the registry's own checksum field plus version coordinate gets us the same property at much lower complexity. We adopt the checksum, not the addressing model.

Axis B — spec-version negotiation

The MCP wire protocol itself versions on a date string. Three independent layers can disagree:

  1. mcpd's own client-facing protocol (between mcpd and clients like Claude Code / Cursor / Zed). Currently 2025-11-25.
  2. The MCP server's protocol (between mcpd and the server it spawns). Whatever the server author chose to implement when they wrote it — 2025-03-26 through 2025-11-25 are all common.
  3. The MCP Manager codebase's own semver (mcpm 1.0.0). Independent of spec dates.

Option B1 — Strict equality (server-spec must match daemon-spec)

mcpd refuses to start any server that doesn't advertise the exact same date. Untenable: servers don't track spec releases instantly, and we'd lock out 80% of the ecosystem on every spec bump. Violates the MCP lifecycle contract itself, which explicitly allows the server to respond with a different version.

Option B2 — Always upgrade (always advertise newest)

Daemon always advertises its newest supported version in initialize and accepts whatever the server downgrades to. This is the spec's default contract. Problem in practice: a server speaking 2025-03-26 may not understand request shapes our client (Claude Code) generates because the client is on 2025-11-25. The "downgrade me to your version" outcome silently amputates features.

Option B3 — Advertise an allow-list, refuse outside it

Daemon configures a set of accepted spec dates (default: the current stable plus the previous one). At initialize, mcpd advertises the newest, lets the server pick, and refuses (with a structured error) if the server insists on something outside the allow-list. The client-facing daemon protocol announces "I will speak to servers in {2025-06-18, 2025-11-25}." This composes with the Cargo rust-version / Python requires-python idiom — refuse early, fail loudly, surface in the audit log.

Option B4 — Per-server explicit pin

Each server entry in the manifest declares the spec version it expects: github-mcp.spec = "2025-06-18". Mcpd uses that for negotiation. Highest control, highest cognitive load. Reject as default but keep as an override for servers that misbehave with newer specs.

Cargo's split — manifest declares intent, lockfile records reality — is the right one. We don't relitigate.

Classifying changes in mcpm update

We adopt Renovate's vocabulary verbatim so users don't have to learn a new mental model. The classifier runs against the registry's published version metadata for each server in the lock:

ClassRuleDefault actionColored CLI tag
patchz bumped in x.y.zApply on mcpm update, no prompt if --auto-patch is configuredgreen [PATCH]
minory bumped in x.y.zApply, show changelog link if registry provides oneyellow [MINOR]
majorx bumped (or 0.y → 0.(y+1) per Cargo caret rules)Refuse without --accept-breakingred [MAJOR]
digestSame version, different checksum (registry republished)Refuse — this is supply-chain anomaly. Emit audit.security.anomaly.red-flash [DIGEST]
pinUser pinned an exact version where there was a rangeApply, update manifestblue [PIN]
lockFileMaintenanceRe-resolve and re-record without changing any version (refresh checksums, metadata)Apply — this is the equivalent of cargo update with no args after a registry migrationdim [MAINT]
spec-bump (new, MCP-specific)Server advertises a newer MCP spec version that's still in our allow-listApply, log; if outside allow-list, refuse with a config-hint messagepurple [SPEC]

Why digest is a refusal, not a warning: if the registry republishes the same name+version with a different checksum, either a typo-squat is in progress or the publisher's account is compromised. Both are emergencies. The user must explicitly --accept-digest-change with a confirm prompt to proceed.

Open issues handed to the recommendation page

  • One file or two? Should mcp-manager.lock hold both projection-state (clever-fox-bridge) and server-version state, or should they be siblings? Recommendation page picks: one file, two top-level tables, since they are read together and a single audit-log event covers any write.
  • What happens to running servers when mcpm update bumps their version? Recommendation: bump is staged. The daemon keeps the old server running, spawns the new one, runs the health check, swaps atomically on success, rolls back on failure.
  • Spec-version refusal on install vs runtime. Recommendation: refuse at install time using the registry's advertised spec versions. Runtime negotiation should never reach the disconnect path if install-time refusal works correctly.
