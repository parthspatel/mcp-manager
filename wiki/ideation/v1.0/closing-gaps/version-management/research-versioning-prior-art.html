Prior art — package version pinning & protocol negotiation

Two adjacent ecosystems already solved each half of our problem. Package managers (Cargo, npm, pip-tools/uv, mise, asdf, Nix flakes, Renovate) ship dependency pinning that has been beaten into shape over a decade. Protocol designers (HTTP, gRPC, Postgres wire, MCP itself) ship version negotiation strategies that survive multi-decade ABI churn. This page enumerates the patterns; the analysis page picks between them; the recommendation page binds the winners to the mcpm CLI surface.

MCP spec versioning — current state (2026-05)

Versions in the wild and the negotiation contract
Version namingDate strings YYYY-MM-DD, not semver. A new spec date is published roughly twice a year.
Current stable2025-11-25 — the one-year anniversary release. Headline features: experimental Tasks primitive, Sampling-with-Tools, formal Extensions framework, OAuth 2.1 + OpenID Connect authorization, standardized tool-name format (SEP-986). Described as "backward compatible" by maintainers.
Still encountered2025-06-18 and 2025-03-26. Many servers haven't bumped.
Next2026-07-28 release candidate — described as "the largest revision since launch": stateless protocol core, Extensions formalised, Tasks promoted, MCP Apps, OAuth/OIDC tightening, a formal deprecation policy. Tier-1 SDKs have a ten-week window to ship support.
Negotiation rule (lifecycle)Client sends the latest protocolVersion it supports in initialize. Server responds with the same version, or its preferred alternative. If the client cannot speak the server's response it SHOULD disconnect.
Wire-level subtletyStreamable HTTP requires the negotiated version to be re-emitted in the MCP-Protocol-Version request header on every subsequent call. A known bug in @ai-sdk/mcp where the header did not downgrade after negotiation broke Figma Dev Mode MCP integration — a real-world reminder that negotiation is per-session state, not a global toggle.
SDK release cadenceEach SDK is independently versioned (semver) and advertises its supported spec dates. TypeScript SDK typically ships within days; Python SDK within ~1–2 weeks; the Rust SDK we depend on sits in the same band.
RegistryThe official MCP Registry launched 2025-09-08. Metadata only — points to npm / PyPI / Docker. Each publish is tied to one server-version, with reverse-DNS naming (io.github.user/server). Useful for us: the registry already publishes a "supported spec versions" field per server.

Cargo — range in manifest, exact in lockfile, checksums for integrity

The model we will most closely mirror
Manifest specifiersCaret (^1.2.3), tilde (~1.2.3), equals (=1.2.3), and the default ("1.2.3" is sugar for ^1.2.3). Caret allows any version compatible by the leftmost non-zero digit; tilde restricts to patch within the stated minor.
Lockfile schemaTOML. [[package]] array-of-tables with name, version, source = "registry+https://..." or git+https://...#<sha>, and checksum.
Commit policyCargo.lock is committed for end-products (binaries, applications), not for libraries. For us this maps cleanly: a per-user projection is the "application", a shared per-project file is also the "application" — both get the lock committed (or kept in ~/.config/).
Update UXcargo update bumps within the manifest constraint. cargo update --precise 1.4.6 regex pins exactly. cargo update --dry-run shows the proposed diff. RFC 3493 refined --precise for pre-release versions.
ResolutionSAT-style resolver picks the newest version satisfying every constraint. Overkill for 10s-of-MCPs scale, but the algorithmic pattern is well-understood.

npm — package-lock.json + shrinkwrap

Two lockfile flavours, and what we learn from each
package-lock.jsonAuto-generated, committed by convention. Records the full resolved tree with versions, resolved URLs, integrity hashes (SRI), and dev/prod scopes.
npm-shrinkwrap.jsonA package-lock published with the package itself — used by libraries that want to ship a frozen dependency tree to downstream consumers. Rare in practice.
Update UXnpm update [pkg] bumps within the semver range in package.json. npm outdated previews. The lockfile is updated in place.
Lesson for usIntegrity hashes (SRI) belong in the lockfile, not the manifest. The manifest stays human-edited; the lock is the machine's source of truth.

pip-tools / uv — the .in / .txt compile pattern

Loose constraints compile into pinned outputs
Patternrequirements.in (or pyproject.toml) carries ranges; pip-compile resolves them and emits requirements.txt with exact pins plus hashes.
uv as drop-inuv pip compile is a faster, equivalent re-implementation; supports platform-independent locks and reproducible resolution.
Reproducibilitypip-compile reads any existing output file and prefers the pinned versions there — so the lock is stable as long as constraints are satisfiable.
Lesson for us"Compile" is a useful verb. Our mcpm install is conceptually a compile step: read manifest, resolve, write lock. mcpm update is recompile-with-allow-bumps.

mise — opt-in lock with strict mode

Best-in-class for a tool that's a sibling problem to ours
Manifestmise.toml with loose specifiers like node = "22" or node = "latest". Idiomatic mise discourages over-pinning at the manifest level.
Lockfilemise.lock records exact version + per-platform download URL + checksum. Opt-in via mise lock; not generated automatically.
Strict modeWhen enabled, mise refuses to call upstream APIs — if a URL/checksum for the current platform is missing from the lock, install fails. Maximally reproducible.
Update UXmise upgrade [tool] bumps within the manifest specifier; supports --dry-run.
Lesson for usThe opt-in posture is wrong for us — we want a lock by default since the user has to trust unknown servers. But the strict-mode escape hatch is gold for security-conscious teams.

asdf — manifest-as-lock

One-file model: minimal but limited
File.tool-versions — one tool per line, exact version required (no caret, no "latest"). The manifest is the lock.
PluginsNot versioned. asdf trusts the plugin author at install time.
Lesson for usThe simplicity is alluring at this scale (10s of MCPs). But it forfeits the "loose in manifest, exact in lock" affordance — the developer who wrote github-mcp 0.4.2 in week 1 cannot later say "give me the latest 0.4.x" without manually editing the version. Reject.

Nix flakes — content-addressed lock

The most rigorous reproducibility model in the wild
flake.lockJSON; one node per input; each node carries a narHash (content hash of the Nix store path) plus locked input parameters (rev, ref, lastModified).
narHashContent-addressed: the lockfile is invariant under URL changes, mirror redirects, or registry restructuring — if the bytes are the same, the hash matches.
Update UXnix flake update bumps all inputs; nix flake lock --update-input nixpkgs targets one.
Lesson for usContent-addressing is overkill for a single registry where every artifact is already addressed by name@version + checksum. But the principle — the lockfile records enough to fetch the byte-identical thing — carries.

Renovate — the update classification vocabulary

The taxonomy we will adopt verbatim for mcpm update output
matchUpdateTypes enummajor, minor, patch, pin, pinDigest, digest, lockFileMaintenance, rollback, bump, replacement.
Best practiceAuto-merge patch + digest; manual review for major. Group everything-non-major into one PR by default.
packageRulesMatch on update type + dependency name + group; act with automerge / labels / schedule. The example library has hundreds of patterns we can crib.
Lesson for usDon't invent vocabulary. Renovate's enum is what users already know — we expose it in mcpm update output so the user can pattern-match against their existing intuition.

Protocol negotiation — HTTP, gRPC, Postgres

Three distinct philosophies; we pick the one that matches MCP's reality
HTTP Upgrade (RFC 9110 §7.8)Client lists acceptable protocols in Upgrade: header; server selects one and returns 101 Switching Protocols, or proceeds in the original. Multi-version advertise, server picks.
gRPC versioningNo runtime negotiation. Backward and forward compatibility are achieved through Protobuf field-number stability; breaking changes require a new service path. The contract is compatibility.
Postgres FE/BE protocolClient sends a major.minor request; server responds with the highest version it supports up to that. NegotiateProtocolVersion message lists supported optional params explicitly — structured rather than free-form.
MCP's choiceMCP follows the HTTP Upgrade philosophy: client advertises its preferred, server may downgrade. No SAT solving, no min/max range — just "do we share a supported version?" If not, disconnect.
Toolchain version advertisementAdjacent prior art for advertising tooling-level version compatibility: Cargo's rust-version field, Python's requires-python. Both let a package say "I won't run unless you're ≥ X" without negotiation — just a refusal. We mirror this: an MCP server's registry entry declares the spec versions it speaks, and mcpd refuses to install one we cannot speak.
Deprecation advertisementRFC 8594 standardises a Deprecation: response header with a sunset date. Useful when our daemon supports an old MCP version but wants to nudge users off it before the next stable release rolls compatibility forward.
Field reportsIBM's mcp-context-forge filed a feature request for "Protocol Version Negotiation & Backward Compatibility" — confirming a production gateway still treats this as an open problem; we have an opportunity to be opinionated about it.

What carries forward to the analysis & recommendation

  • Cargo's "range in manifest, exact in lock with checksums" is the strongest match for our scale and audience.
  • uv's "compile" metaphor lines up with how we should describe mcpm install internally.
  • mise's strict-mode flag is the right escape hatch for teams who want maximal supply-chain rigor.
  • Renovate's classification enum is what users will see in mcpm update output. We don't invent new words.
  • HTTP Upgrade-style "advertise + downgrade" matches the MCP spec's own contract; we honor it and add a registry-level "advertised spec versions" field for server install-time refusal.
