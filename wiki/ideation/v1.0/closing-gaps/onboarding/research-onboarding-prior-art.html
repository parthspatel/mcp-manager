Prior art for terminal-first onboarding flows

A working tour of thirteen comparable bootstrap commands — what each transcript looks like in 2026, what worked, what hurt, and the concrete pattern mcpm should borrow. Every tool here ships a real "first-run, do this one thing" command; the design space for mcpm init is the union of their good ideas minus their well-documented mistakes.

Surveyed tools

  • gh auth login (GitHub CLI)
  • aws configure (AWS CLI)
  • mise activate & mise use
  • direnv hook + direnv allow
  • terraform init

gh auth login — GitHub CLI

The reference design for an interactive auth bootstrap that also exposes every choice as a flag. The interactive sequence is short, conversational, and never asks a question whose answer is obvious from context.

$ gh auth login
? What account do you want to log into?  [Use arrows to move, type to filter]
> GitHub.com
  GitHub Enterprise Server

? What is your preferred protocol for Git operations on this host?
> HTTPS
  SSH

? Authenticate Git with your GitHub credentials? (Y/n) Y
? How would you like to authenticate GitHub CLI?
> Login with a web browser
  Paste an authentication token

! First copy your one-time code: ABCD-1234
Press Enter to open https://github.com/login/device in your browser...

✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
✓ Logged in as octocat
What worksEvery prompt has a default highlighted by >. Y/n capitalisation signals which is the default. The summary at the end enumerates exactly what was written. Non-interactive variant gh auth login --with-token < tok.txt takes no other prompts.
What hurtsThe browser-flow is the default and there's no way to ask for a paired device-code flow without first declining "Login with a web browser." If you're on a headless box you have to know that "Paste an authentication token" is the right branch.
For mcpmAdopt the visible-default-with-> pattern. Adopt the closing summary line ("wrote X, configured Y"). Reject the browser-flow default — mcpm has no authentication target, only local-machine state, so the equivalent is "what scope?" and the default is user.

aws configure — AWS CLI

The most copied design in CLI history. Bracketed defaults, ENTER preserves existing values, four prompts max, idempotent re-run.

$ aws configure
AWS Access Key ID [None]: AKIAIOSFODNN7EXAMPLE
AWS Secret Access Key [None]: wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
Default region name [None]: us-east-2
Default output format [None]: json
$

# Re-running shows current values in brackets; ENTER keeps them.
$ aws configure
AWS Access Key ID [****WXYZ]:
AWS Secret Access Key [****EFGH]:
Default region name [us-east-2]: us-west-2
Default output format [json]:
$
What worksBracketed [None] / [****WXYZ] / [us-east-2] defaults make the second run trivially fast. The two files written (~/.aws/config, ~/.aws/credentials) are documented and inspectable.
What hurtsNo --yes / non-interactive mode; you have to drop down to aws configure set profile.default.region us-east-2 for scripting. No "what just happened?" output line — the command exits silently.
For mcpmAdopt the bracketed-defaults pattern verbatim. Fix the silence by always printing a summary block. Add the -y flag that AWS lacks.

mise activate / mise use — mise-en-place

Separates "hook into my shell" (one-time, edits rc-file) from "set a tool version" (per-project, edits mise.toml). The split is the design lesson; mcpm uses the same two-phase model.

# Phase 1: shell activation (one-time, idempotent, modifies ~/.zshrc).
$ mise activate zsh
# bash output: an eval script. The recommended install line is shown
# in the docs but mise itself does not write to the rc file.
$ echo 'eval "$(~/.local/bin/mise activate zsh)"' >> ~/.zshrc

# Phase 2: per-project pinning.
$ cd ~/projects/myapp
$ mise use node@22
mise WARN  No untrusted config files found.
mise ~/projects/myapp/mise.toml tools: node@22.4.0
What worksExplicit, copy-pasteable install line; mise itself never silently edits your shell config. mise use writes only mise.toml in the cwd — nothing else.
What hurtsSome users miss the difference between "activate" (hook) and "use" (pin) and run them in the wrong order. The shim-vs-activate decision is a footgun for new users.
For mcpmSplit shell-init from config-init. mcpm init never edits a shell rc file; that's a separate mcpm shell-init that prints the line and (optionally, with confirmation) appends it.

direnv hook + direnv allow

Two-step trust model: the shell hook is installed once, but every directory needs an explicit direnv allow before its .envrc runs. The consent gate is the lesson.

$ cd ~/projects/myapp
direnv: error /Users/me/projects/myapp/.envrc is blocked. Run `direnv allow` to approve its content
$ direnv allow
direnv: loading ~/projects/myapp/.envrc
direnv: export +DATABASE_URL +OPENAI_API_KEY
What worksYou cannot accidentally load an attacker's .envrc by cloning their repo. The blocked-by-default behaviour is a security property, not a friction tax.
What hurtsThe error message names the right command but doesn't explain the security rationale; new users assume direnv is broken.
For mcpmFor mcpm project init, adopt direnv's consent model: a project-scope config in someone else's repo is not trusted until the user runs mcpm project allow (or passes --allow at init). Loud, explanatory error message: "This project declares MCP servers from a registry you don't trust. Run mcpm project allow after reviewing .mcp-manager/project.toml."

terraform init

The gold standard for project-scoped init with staged, visible side effects. mcpm's project-scope init matches this UX almost line for line.

$ terraform init

Initializing the backend...

Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.41.0...
- Installed hashicorp/aws v5.41.0 (signed by HashiCorp)

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control repository
so that Terraform can guarantee to make the same selections by default when
you run "terraform init" in the future.

Terraform has been successfully initialized!

You may now begin working with Terraform. Try running "terraform plan" to see
any changes that are required for your infrastructure. All commands are now
safe to run because the working directory is initialized.
What worksEach phase has a heading ("Initializing the backend..."). Side effects (created lock file, downloaded providers) are spelled out. The closing paragraph tells the user the next concrete command to run.
What hurtsThe lock-file message is dense; users skim it and miss the "commit this file" guidance.
For mcpmSteal the staged headings ("Detecting toolchains..." / "Writing config..." / "Registering audit log..."). Steal the closing "next command to run" line. Avoid the wall-of-text lock-file paragraph — mcpm shows that hint only on first run, not on every subsequent init --force.

cargo new / cargo init

Project scaffolding done right. cargo new foo creates a directory; cargo init populates the current directory. Both are non-interactive and idempotent-by-refusal (won't clobber).

$ cargo new --bin --vcs git mcpm-test
     Created binary (application) `mcpm-test` package

$ cd mcpm-test && ls -a
.  ..  .git  .gitignore  Cargo.toml  src

$ cargo init --bin .
warning: file `Cargo.toml` already exists in this directory: file exists
error: `cargo init` cannot be run on existing Cargo packages
What worksThe "refuse to clobber" default is correct. The --vcs git|none|hg flag is a single decision-point with a sane default, not a prompt. --quiet exists for scripts.
What hurtsThe error message names the conflict but not the fix — a new user might not know to delete Cargo.toml or pass --force (which Cargo doesn't offer for init — you have to start over).
For mcpmAdopt refuse-to-clobber. Add a --force flag (with audit-log backup of the previous state) that Cargo lacks; users who deliberately want to re-init shouldn't be stuck.

pipx ensurepath

The cleanest example of a CLI that does one rc-file mutation and tells you about it.

$ pipx ensurepath
Success! Added /Users/me/.local/bin to the PATH environment variable.

Consider adding shell completions for pipx. Run 'pipx completions' for instructions.

You will need to open a new terminal or re-login for the PATH changes to take effect.

Otherwise pipx is ready to go! ✨
What worksOne-line summary of what was added and where. Explicit "open a new terminal" instruction. Idempotent: running twice is a no-op.
What hurtsDoesn't show which file was edited — the user has to grep their rc files to find the diff.
For mcpmAlways print the path of every file we wrote. Always print the "what to do next" line. The emoji is optional; we'll keep our output plain by default.

op account add & op signin — 1Password CLI

A useful counter-example: 1Password's CLI does the interactive thing well but the non-interactive path is awkward (env-var-fed prompts plus a piped password).

$ op account add
Enter your sign-in address (example.1password.com): myteam.1password.com
Enter the email address for your account on myteam.1password.com: me@example.com
Enter the Secret Key for me@example.com on myteam.1password.com: A3-XXXXXX-XXXXXX-XXXXX-XXXXX-XXXXX-XXXXX
Enter the password for me@example.com at myteam.1password.com: ***************
Now run 'eval $(op signin)' to sign in.

# Multi-account flow uses an arrow-key selector at signin time:
$ eval $(op signin)
? Pick an account to sign in to:
> my-team
  personal
What worksThe arrow-key account picker at signin is a clean UX for the multi-default case. Prompts include context (the host being added) so the user knows which field they're filling.
What hurtsThe non-interactive bootstrap requires exporting four env vars then piping the password into op signin — awkward enough that a community write-up was needed to document it. There's no --password-stdin equivalent on op account add.
For mcpmEvery interactive prompt must have a corresponding long-form flag. Never require env-var setup as the non-interactive path; that's deferred to power-users.

npm init / pnpm init

The canonical source of the -y / --yes flag. npm init -y is the most-typed three-character command in modern Node.js setup.

$ npm init
This utility will walk you through creating a package.json file.
It only covers the most common items, and tries to guess sensible defaults.

package name: (myapp)
version: (1.0.0)
description:
entry point: (index.js)
test command:
git repository:
keywords:
author:
license: (ISC)
About to write to /Users/me/myapp/package.json:
{ ... }
Is this OK? (yes)

# Skip every prompt:
$ npm init -y
Wrote to /Users/me/myapp/package.json:
{ "name": "myapp", "version": "1.0.0", ... }

# pnpm flips the default: never interactive, just writes the file.
$ pnpm init
{ "name": "myapp", ... }
What worksThe -y flag is universally understood. npm's interactive walk shows guessed defaults in parentheses. pnpm argues the opposite extreme: don't even ask — defaults are always fine for the metadata you can edit later.
What hurtsnpm's confirmation prompt at the end ("Is this OK? (yes)") is redundant in the -y path and a UX speedbump in the interactive path. pnpm's silent write surprises users who expected a wizard.
For mcpmAdopt -y verbatim. Use guessed-defaults-in-parens for hostnames / paths. Drop the final "Is this OK?" — show the summary, write the files, return.

kubectl config set-context

The "no interactive command at all" extreme. kubectl ships no kubectl init; you compose your kubeconfig by hand or accept whatever the cluster install dumped at ~/.kube/config.

$ kubectl config set-context prod --cluster=prod-cluster --user=me --namespace=default
Context "prod" created.

$ kubectl config use-context prod
Switched to context "prod".

$ kubectl config current-context
prod
What worksComposable from the get-go: every flag is its own setter; the file is fully under user control; scripts can stamp out clusters trivially.
What hurtsThe new-user experience is bad: you can spend an afternoon trying to figure out how kubeconfig got into the state it's in. There's no "show me what you'd do if I ran the wizard" preview because there's no wizard.
For mcpmProvide the interactive wizard and the flag-driven composition. kubectl's strength (every choice is a flag) is achievable without kubectl's weakness (no init at all).

poetry init

A mid-2020s gold standard: every prompt has a bracketed default, every default is a smart guess based on cwd, and the user can ENTER through the whole thing in three seconds.

$ poetry init

This command will guide you through creating your pyproject.toml config.

Package name [myapp]:
Version [0.1.0]:
Description []:
Author [Me <me@example.com>, n to skip]:
License []:  MIT
Compatible Python versions [^3.11]:

Would you like to define your main dependencies interactively? (yes/no) [yes] no
Would you like to define your development dependencies interactively? (yes/no) [yes] no

Generated file:

[tool.poetry]
name = "myapp"
...

Do you confirm generation? (yes/no) [yes]
What worksBracketed defaults; smart guesses (package name from cwd, author from git config); branch-flattening prompts ("interactively? no" elides whole sub-questionnaires); generated-file preview before write.
What hurtsThe final "Do you confirm generation?" is an "are you sure you're sure" prompt — the user has already pressed ENTER ten times.
For mcpmAdopt smart-default guessing (machine name, OS-detected service manager, detected editors). Reject the final confirm-confirmation prompt; preview-then-write is enough.

stripe login

Worth surveying for one specific reason: it does both a device-pairing-code flow and a --interactive flag for no-browser environments. mcpm rejects the device flow but the --interactive escape hatch is instructive.

$ stripe login
Your pairing code is: lovely-cuddly-puppy-12
This pairing code verifies your authentication with Stripe.
Press Enter to open the browser (^C to quit) ...

# CI-friendly path: paste an API key, no browser.
$ stripe login --interactive
Enter your API key: sk_test_***
How would you like to identify this device in the Stripe Dashboard? [my-laptop]: ci-runner-prod
You're configured and all set to use the Stripe CLI.
What worksThe --interactive flag (despite the slightly misleading name — it actually avoids the browser) is a real escape hatch. The human-readable pairing code reduces phishing risk in the browser path.
What hurtsThe flag's name is wrong (--interactive opens fewer interactive prompts than the default!). The browser flow assumes a graphical session is reachable.
For mcpmmcpm has no remote service to authenticate against, so the entire device-flow concern is moot. The takeaway is that flag names matter: ours are --defaults (accept defaults) and -y / --yes (skip confirms), not --interactive which is overloaded and confusing.

create-next-app — the "use defaults?" shortcut

A modern scaffolder that fronts every per-question prompt with one umbrella default-accept.

$ npx create-next-app@latest myapp
✓ Would you like to use the recommended Next.js defaults? … Yes
Using defaults: TypeScript, ESLint, Tailwind, App Router, src/ dir, import alias @/*
Creating a new Next.js app in /Users/me/myapp.
...

# Or, decline the shortcut and answer each:
✓ Would you like to use TypeScript? … No / Yes
✓ Would you like to use ESLint? … No / Yes
✓ Would you like to use Tailwind CSS? … No / Yes
...
What worksThe "accept all defaults?" front-door collapses ten prompts into one for the lucky-day case. Users who care can decline and answer per-item.
What hurtsThe defaults change between releases (the React team's deprecation of create-react-app illustrates the broader fragility of scaffolders that bake too much policy). What was the right default last quarter may not be this quarter.
For mcpmAdopt the umbrella-default-accept prompt. Document the current defaults in a stable file (mcpm init --show-defaults) so users in scripts can detect drift.

Cross-cutting patterns

Patterns that work (steal these)

  • Bracketed defaults (aws, poetry): every prompt shows the value ENTER will accept.
  • The -y / --yes contract (npm, apt, dnf): a single flag that skips every confirmation is universally understood.
  • Idempotent re-run (terraform init, pipx ensurepath, aws configure): running the bootstrap a second time prints a diff or no-ops; never errors, never duplicates state.
  • Per-prompt corresponding flag (gh, kubectl): every interactive answer is also a long-form flag, so scripts and humans share one command surface.
  • Staged, labelled output (terraform): each phase has a heading; the user knows what's happening, in order, in real time.
  • Closing summary + next-command hint (terraform, gh): the last lines tell the user what was written and what to try next.
  • Consent-gated trust (direnv): a config file in someone else's repo doesn't auto-execute; it requires explicit user approval first.
  • Smart defaults from context (poetry, cargo): infer the package name from the directory; infer the author from git config; offer them as bracketed defaults.
  • XDG-compliant write locations (mise, direnv, modern Rust CLIs): $XDG_CONFIG_HOME / $XDG_STATE_HOME on Linux; ~/Library/Application Support or ~/.config on macOS by convention.
  • Conservative ANSI (clack): use escape sequences that work in macOS Terminal, iTerm2, and tmux/screen out of the box; never rely on truecolor or 24-bit colour for legibility.

Patterns that fail (avoid these)

  • Forced interactivity: a tool with no non-interactive path is unscriptable. (1Password's account-add is the most prominent recent offender.)
  • Implicit state writes: aws configure's silent exit is a small example; the worst offender is any installer that edits your shell rc without saying so.
  • Doctor commands: flutter doctor, rustup show, etc. — these compress nine unrelated checks into one wall of output that conceals which step actually failed. mcpm's strategy is the opposite: each setup step has its own command and its own clear pass/fail.
  • Browser flows on headless boxes: gh auth login defaults to opening a browser; on a remote ssh session the user has to know to pick the "Paste a token" branch. Always offer the no-browser path as a flag, not a hidden branch.
  • Confirmation theatre: poetry's "Do you confirm generation? (yes/no) [yes]" after the user has already pressed ENTER nine times.
  • Wrong-named flags: stripe's --interactive meaning "no browser, more keystrokes" is the canonical example. Pick verbs that match what the user is asking for.
  • Defaults that drift silently between releases: create-next-app's umbrella "use defaults" hides this. mcpm pins defaults in a documented file and bumps it as a SemVer-relevant change.
  • Refusing to clobber without offering --force: cargo init errors but provides no fix; you have to delete files by hand. We provide --force with a backup.

What this means for mcpm

The convergent design across thirteen comparable tools is consistent enough to lift wholesale: bracketed defaults, -y as the universal skip, staged labelled output, closing summary, per-prompt flags, XDG-compliant write paths, ratatui for the interactive layer with a line-prompt fallback for non-TTY shells.
