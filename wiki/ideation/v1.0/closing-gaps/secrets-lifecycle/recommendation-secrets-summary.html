Recommendation: secrets lifecycle & the SecretStore trait

Headline. Ship a single SecretStore trait in v1.0 with two implementations: OsKeyringStore (macOS Keychain + Linux libsecret via the keyring-rs crate) and EnvVarPassthroughStore (read-only escape hatch). Compose them into a LayeredSecretStore that mcpd consults at server-spawn time. Every read/write emits a structured audit event with no values. v1.1+ plugs in 1Password, Vault, Doppler, Infisical, AWS/GCP/Azure secret managers behind the same trait — zero v1.0 re-architecture.

The SecretStore trait

Single trait, three operations, one associated reference type. Async-trait so v1.1's HTTP-backed stores fit naturally; v1.0's keyring impl wraps blocking calls in spawn_blocking.

use secrecy::SecretString;
use async_trait::async_trait;

/// A v1.0 secret reference. v1.1+ stores extend this enum (non-exhaustive
/// is locked in now so adding variants is non-breaking).
#[non_exhaustive]
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum SecretRef {
    /// Canonical mcpd-scoped name, e.g. ("github", "GITHUB_TOKEN").
    Named { server: String, name: String },
}

#[async_trait]
pub trait SecretStore: Send + Sync + 'static {
    /// Stable identifier ("os-keyring", "env-passthrough", "1password", ...).
    fn id(&self) -> &'static str;

    /// Read a secret. Returns None if this store has no entry for `r`
    /// (callers fall through to the next store in the chain).
    async fn get(&self, r: &SecretRef) -> Result<Option<SecretString>, SecretError>;

    /// Write or overwrite. Returns SecretError::ReadOnly for stores that
    /// don't support writes (env-passthrough, every cloud vault).
    async fn set(&self, r: &SecretRef, value: SecretString) -> Result<(), SecretError>;

    /// Remove. Returns Ok(false) if no such entry existed.
    async fn unset(&self, r: &SecretRef) -> Result<bool, SecretError>;

    /// Names only — never values.
    async fn list(&self) -> Result<Vec<SecretRef>, SecretError>;
}

#[derive(Debug, thiserror::Error)]
pub enum SecretError {
    #[error("backend unavailable: {0}")]
    BackendUnavailable(String),
    #[error("read-only store")]
    ReadOnly,
    #[error("backend error: {0}")]
    Backend(#[source] Box<dyn std::error::Error + Send + Sync>),
}

Notes on shape:

  • #[non_exhaustive] on SecretRef — lets v1.1 add e.g. OnePassword(String) or VaultPath { mount, path, field } variants without breaking external callers.
  • get returns Option, not Result<_, NotFound> — "missing" is a normal control-flow signal for the layered chain, not an error.
  • list returns SecretRefs, not String — preserves structure for the TUI.
  • Send + Sync + 'static — required because mcpd holds a Arc<dyn SecretStore> shared across tokio tasks.
  • No rotate, lease, or ttl methods — these are v1.1+ concerns. They will arrive as additional traits (RotatableSecretStore: SecretStore, LeasedSecretStore: SecretStore) that specific backends opt into, not as required methods on every backend.

v1.0 implementations

OsKeyringStore — the default backend

Wraps the keyring crate. Service string is fixed at "dev.mcpmanager"; the keychain account is the rendered form {server}/{name}.

pub struct OsKeyringStore;

#[async_trait]
impl SecretStore for OsKeyringStore {
    fn id(&self) -> &'static str { "os-keyring" }

    async fn get(&self, r: &SecretRef) -> Result<Option<SecretString>, SecretError> {
        let acct = render_account(r);
        tokio::task::spawn_blocking(move || {
            let entry = keyring::Entry::new("dev.mcpmanager", &acct)?;
            match entry.get_password() {
                Ok(s)  => Ok(Some(SecretString::new(s.into()))),
                Err(keyring::Error::NoEntry) => Ok(None),
                Err(e) => Err(SecretError::Backend(Box::new(e))),
            }
        }).await.map_err(|e| SecretError::Backend(Box::new(e)))?
    }
    // set / unset / list elided — same shape, all via spawn_blocking.
}

Per-platform behavior is delegated to keyring's apple-native (Keychain Services) and linux-native-sync-persistent (libsecret over D-Bus) features. The accessibility attribute on macOS is kSecAttrAccessibleWhenUnlocked, the default.

EnvVarPassthroughStore — the escape hatch

Read-only, ignores everything except the secret name, and only when looked up at spawn time. This is what makes export GITHUB_TOKEN=ghp_xxx in the user's ~/.zshrc "just work" without ever writing to the keychain.

pub struct EnvVarPassthroughStore;

#[async_trait]
impl SecretStore for EnvVarPassthroughStore {
    fn id(&self) -> &'static str { "env-passthrough" }

    async fn get(&self, r: &SecretRef) -> Result<Option<SecretString>, SecretError> {
        let SecretRef::Named { name, .. } = r;
        Ok(std::env::var(name).ok().map(|s| SecretString::new(s.into())))
    }

    async fn set(&self, _: &SecretRef, _: SecretString) -> Result<(), SecretError> {
        Err(SecretError::ReadOnly)
    }
    async fn unset(&self, _: &SecretRef) -> Result<bool, SecretError> {
        Err(SecretError::ReadOnly)
    }
    async fn list(&self) -> Result<Vec<SecretRef>, SecretError> { Ok(vec![]) }
}

This store is the only one allowed in the v1.0 chain whose list() returns empty — we cannot enumerate which env vars "might be secrets," so we don't try.

LayeredSecretStore — the composition

mcpd holds exactly one Arc<dyn SecretStore>, which in v1.0 is always:

// Read order: env-passthrough first (user override), then OS keychain.
// Write order: keychain only (env-passthrough refuses writes).
let store: Arc<dyn SecretStore> = Arc::new(
    LayeredSecretStore::new()
        .with(EnvVarPassthroughStore)
        .with(OsKeyringStore)
);

The "env wins" order is intentional: a user who exports a token in their shell has intentionally overridden the keychain. We honor that without surprise.

#[async_trait]

    async fn rotate(&self, r: &SecretRef) -> Result<(), SecretError>;
}

#[async_trait]
pub trait LeasedSecretStore: SecretStore {
    async fn get_leased(&self, r: &SecretRef)
        -> Result<(SecretString, LeaseHandle), SecretError>;
}

The cloud-vault stores translate SecretRef::Named { server, name } into {prefix}/{server}/{name}-style provider keys (configurable). The shell-out stores (op, bw, doppler, infisical, AWS/GCP/Azure CLIs) all follow the same template: spawn child, write nothing to stdin, capture stdout into SecretString, log secret.read. Their CLI surfaces are all (a) reference-in, plaintext-on-stdout, (b) authenticated via the user's existing CLI session, so we never have to store provider credentials ourselves.

Daemon-side injection flow at server spawn

This is the moment of truth: mcpd has decided to spawn the github MCP server. The server's manifest declares it needs GITHUB_TOKEN. What happens?

  1. Resolve required-secret list. mcpd reads the server manifest's requires_secrets: ["GITHUB_TOKEN"] declaration.
  2. For each required secret, call store.get(&SecretRef::Named { server: "github", name: "GITHUB_TOKEN" }) through the LayeredSecretStore:
    1. EnvVarPassthroughStore::get — if GITHUB_TOKEN exists in mcpd's process env, return it. Audit event: {event: "secret.read", store: "env-passthrough", server: "github", name: "GITHUB_TOKEN", actor: "<requesting-client>", outcome: "ok"}.
    2. Otherwise fall through to OsKeyringStore::get — query keyring::Entry::new("dev.mcpmanager", "github/GITHUB_TOKEN"). On hit: audit event with store: "os-keyring".
    3. On miss in both: refuse to spawn the server. Audit event: {event: "secret.read", outcome: "miss", ...}. Return a structured error to the requesting client.
  3. Build the child's environment. Inherit mcpd's env, then overlay the resolved secrets via std::process::Command::env(name, value.expose_secret()). The SecretString is dropped (zeroized) immediately after the spawn() call returns.
  4. Spawn the child. Standard tokio::process::Command. The child sees only GITHUB_TOKEN=ghp_... in its environment; the MCP server code consumes that env var exactly as it would if the user had inlined it in editor config.
  5. Audit on child exit records the child's exit code but never the secret. (The audit log is owned by mcp-core; see the schema below.)

Crucially, the mcpm exec wrapper (the user-facing CLI for one-off server invocation) never touches secrets — it talks to mcpd over the IPC socket, mcpd does the resolve-and-inject, and the wrapper's argv has no token in it. This is the architectural property that prevents the OWASP MCP01:2025 failure mode.

Audit event schema

Owned by mcp-core; secrets stream emits, audit subsystem records. Schema (JSON):

{
  "ts":      "2026-05-24T19:15:02.413Z",     // RFC 3339 UTC
  "event":   "secret.read" | "secret.write" | "secret.unset" | "secret.list",
  "store":   "os-keyring" | "env-passthrough" | "1password" | ...,
  "ref":     {
    "kind":   "named",
    "server": "github",                        // SecretRef::Named.server
    "name":   "GITHUB_TOKEN"                   // SecretRef::Named.name
  },
  "actor":   {
    "kind":  "client" | "cli" | "internal",
    "id":    "zed-1.234.5",                    // e.g. UA from IPC handshake
    "pid":   84219
  },
  "outcome": "ok" | "miss" | "denied" | "backend-error",
  "error":   null | "human-readable string",   // never includes value bytes
  "v":       1                                 // schema version
}

Invariants the test suite enforces:

  • No event JSON, anywhere, contains the secret value — we have a fuzz test that writes random bytes as secrets and greps every emitted log line.
  • Every secret.read with outcome: "ok" has a matching child-spawn event within 100ms (or the read was unused, which is also a flag).
  • Audit events are append-only; the audit channel is a separate mcp-core sink so a buggy or compromised SecretStore impl cannot suppress events.

Compare to Kubernetes' Secret audit-policy events, which our schema deliberately mirrors at a much narrower scale — same actor/verb/resource/outcome shape, no value bytes.

Failure modes & error UX

Situationv1.0 behaviorError message
macOS Keychain locked (system-keychain item, ACL prompt declined) Surface upstream error; do not retry silently your keychain refused access (cancel/deny) — re-run after unlocking
Linux: no D-Bus user bus / no Secret Service running Fail loudly on first write attempt; CLI shows install hint no freedesktop Secret Service is reachable. Install gnome-keyring (or KWallet, or KeePassXC with Secret Service plugin) and ensure it's running in your session. Alternatively, export the secret as an env var: export GITHUB_TOKEN=<value>
Secret name collides with another server Scoped by (server, name); no collision possible n/a — github/GITHUB_TOKEN and linear/GITHUB_TOKEN are independent items
User pastes a secret with a trailing newline (from --from-file) Trim ONE trailing newline; preserve all other whitespace Silent success. Most APIs reject tokens with whitespace; we save the user from themselves once.
Required secret not present at spawn time Refuse to spawn; structured error to client cannot start server 'github': required secret 'GITHUB_TOKEN' is not set. Run: mcpm secret set GITHUB_TOKEN --for github
mcpm secret set invoked over an SSH session without a TTY Detect !isatty(stdin) and refuse the interactive prompt no controlling terminal — use --from-file, --from-env, or pipe the value: cat token | mcpm secret set NAME --stdin
User passes --value Refuse before reading the rest of argv --value is not supported (argv leaks into shell history and process listings). Use the interactive prompt, --from-file, --from-env, or --stdin.

Open questions for the orchestrator

  1. Service string namespacing. We've proposed "dev.mcpmanager" as the macOS Keychain service string and the freedesktop xdg:schema. Confirm this matches the org's reverse-DNS convention (or change it once across both backends before v1.0 ships — renaming after release means user keychains lose access to existing items).
  2. Per-secret access policies. Should v1.0 already support "this secret is only readable by these specific MCP servers" as an attribute on the stored item, even though we don't enforce it until v1.1? Adding it later is non-breaking (extra attribute on a new schema version); leaving it out is simpler.
  3. Code-signing. macOS Keychain works fine for unsigned binaries today, but TouchID-gated reads and Secure Enclave entitlements require signed code. Does v1.0 commit to a signed Apple Developer ID release, or do we explicitly defer signing to v1.1? This blocks any biometric-gated v1.x feature.
  4. Audit log shape. The schema above lives here, but mcp-core owns the actual sink. Confirm mcp-core's audit channel will accept the JSON shape we've proposed, or harmonize with their existing schema before ship.
  5. Mass-rotation tooling. If a user wants to bulk-rotate every GITHUB_TOKEN across N MCP server slots, v1.0 has no mcpm secret rotate. Acceptable for v1.0? (We think yes — defer to v1.1's RotatableSecretStore.)
  6. One-time secrets. Some servers require write-once-then-discard tokens (e.g. OAuth refresh tokens that are rotated on every read). v1.0 has no concept of "read-once"; v1.1's LeasedSecretStore covers it. Confirm OK to defer.
