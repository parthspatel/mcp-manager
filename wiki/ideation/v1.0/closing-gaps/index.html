Closing v1.0 gaps

The 2026-05-24 gap review identified five Tier-1 blocking gaps. Distribution was resolved directly (curl + Nix flake), and the GUI was deferred. The remaining four gaps — server discovery+install, onboarding flow, secrets lifecycle, version management — were each given to a focused-design agent. All four reported back; this hub summarises and links to their work.

Cross-agent convergence

Four independent agents (each unaware of the others) all converged on the same architectural principles. That's a robust signal.

Trait-based extension points

Each agent designed a v1.0 surface that v1.1 can extend without re-architecting:

  • Secrets: SecretStore trait, #[non_exhaustive] ref enum
  • Registry: RegistrySource trait (named + signed + cached) — multi-source federation built in
  • Versioning: per-server spec override, opt-in --accept-breaking, lockfile schema versioned
  • Onboarding: --import-from stubbed but already accepted as a flag

Argv hygiene

Three agents independently rejected putting sensitive data on argv (secrets via --value, install via --token, etc.). Universal pattern: TTY prompt (rpassword) or env-var passthrough. The fourth agent (versioning) doesn't surface sensitive values, but applied the same hygiene to its lockfile (no plaintext checksums or hashes leaking past safe boundaries).

Audit-log integration

Every agent emits audit events: secret.read/write/unset (C), config.change on lockfile updates (D), registry.refresh + registry.verify (A), project.trust + project.register (B). The common audit-log shape decided by directive #3 lands as the single sink. Schemas are non-conflicting; the orchestrator confirms the unified schema below.

Default trust = baked into binary

The "default registries" (A's 3 sources) and the "default mcpd spec allow-list" (D's 2 dates) both ship inside the mcpd binary. Updating either is a hotfix release, not a runtime manifest. Same model as OS-package-manager trusted-keys. Pubkey rotation cadence is the open question both agents flagged.

Idempotency by construction

Onboarding (mcpm init re-runs as no-op), registry refresh (re-syncs in place), version pinning (lockfile written atomically + rolled back on health-check failure), secret set (overwrites existing keychain entry with no error). v1.0's CLI surface is replay-safe end-to-end.

Cross-stream coupling on per-project scope

All four agents respected the v1.0 lockdown decision: canonical scope is user-configurable per registered project, lockfile location follows. Verified:

  • A: mcpm install --scope user|project consistent
  • B: mcpm project init distinct from mcpm init
  • C: per-project secret stores called out as a cross-stream open question for v1.1
  • D: lockfile placed alongside projection lockfile per scope

Aggregated open questions for the orchestrator

Most agent-flagged questions either resolve trivially or wait for v1.1. The ones that need explicit product-owner attention:

Pubkey rotation policy (A + D)

Both server-registry and version-management bake trust roots into the binary (default registry minisign keys for A; default MCP spec allow-list for D). Rotation today requires a hotfix mcpd release. Question: ship a "trust manifest" file in v1.0 that lets users (or us) rotate without rebuilding? Or accept hotfix-release cadence as the rotation mechanism for v1.0 and revisit in v1.1?

Docker source auto-enable threshold (A)

If Docker is detected on the user's machine at mcpm init time, should the docker registry be auto-enabled, or ask once? Agent A leans "ask once" to be explicit; agent B's onboarding flow has a slot for this question.

Service-string namespace (C)

The OS keychain entry's "service" attribute is "dev.mcpmanager" in the recommendation. Renaming after v1.0 ships orphans users' existing keychain entries. Confirm this is the canonical reverse-DNS we want forever.

Code-signing commitment for macOS (C)

TouchID-gated keychain reads and Secure Enclave entitlements require signed macOS binaries. v1.0 ships code-signed, or defer signing (blocks any biometric feature for v1.1)?

Per-server spec override (D)

Ship [server.<name>].spec = "..." as a v1.0 escape hatch for servers that lie about their advertised MCP version? Agent D leans yes, documented as an escape hatch. Confirm.

Health-check gating on minor bumps (D ↔ health check)

Agent D's recommendation auto-runs mcpm test after every classified change. Confirm this composes cleanly with the health-check's UX (probably a --no-test flag on mcpm update for users who'd rather skip).

Service-manager unregister on uninstall (B)

If the user accepted the launchd/systemd registration during onboarding and later runs mcpm uninstall, does mcpm unregister itself first? Agent B left this unaddressed.
