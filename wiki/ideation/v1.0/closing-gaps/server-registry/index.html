Server discovery + install (closing gap)

How does a user go from "I want a Linear MCP server" to a running, sandboxed, secrets-aware server entry in their mcpd state — in one command, from a CLI, with no telemetry, on macOS or Linux? This sub-stream answers that. The five other tier-1 streams handle isolation, secrets, config projection, and onboarding; we sit between "user has mcpd installed" and "user has a sandbox spec to feed to stoic-badger-sandbox".

The gap in one paragraph

v1.0 has five tier-1 streams that all assume the user already has a server entry in their canonical TOML state. None of them answer the question "how does an entry get there in the first place?" Asking the user to hand-author a TOML stanza with a binary path, an args array, a sandbox spec, and a transport discriminator is a non-starter for the brand promise (Just Works on Day 1). This gap closes that.

What we are not solving here

  • How the server runs after install. That is stoic-badger-sandbox. We emit a sandbox-spec reference; they execute it.
  • How secrets get supplied. That is secrets-lifecycle. We emit secret-reference placeholders in the TOML entry; they resolve them.
  • How clients see the server. That is clever-fox-bridge. We update canonical state; they project into client config files.
  • Discovery of what already exists locally. mcpd already enumerates installed servers via mcpm list — this stream is strictly about new servers from upstream sources.

v1.0 constraints we respect

ConstraintHow this stream respects it
macOS + Linux onlyNo Windows-specific paths in any registry adapter; we only ship code we test on both platforms.
No telemetry, everSearch hits the registry's read endpoints; nothing is sent about the user, the query is the entire payload, and we do not log it remotely. Registries that require telemetry tokens for read access are disqualified or behind explicit per-source opt-in.
Apache 2.0 licenseRegistry source code adapters we write are Apache 2.0. Registries we read from are flagged in the source manifest with their own license so a corporate user can audit downstream.
10s of MCPs / user, not 1000sSearch returns top-50 by default; results cached locally (TTL minutes); install is rare and OK to be slow.
No GUI in v1.0Every surface is mcpm CLI + TUI. TUI install picker reuses the same search backend.
Distribution via curl + Nix flakeRegistry adapter code ships in the same mcpd binary; no extra install step.
Isolation via devenv + sandbox-exec / bwrapOur install emits a sandbox-spec reference, never a bare command. The package's declared runtime (npx, uvx, docker) chooses the wrapper.
Canonical state is TOMLInstall writes a single [servers.<name>] block to ~/.config/mcpd/servers.toml; nothing else.

Headline recommendation

Multi-source federation with the official registry seeded, signed manifests at the registry layer, and trust-anchored "tap" semantics for private sources.

Default sources are registry.modelcontextprotocol.io (official, signed) and GitHub MCP Registry (curated, GitHub-auth backed). A user can mcpm registry add <name> <url> to add Smithery, Docker, a private corp registry, or a local file path. All search queries fan out in parallel, results are union-merged with source-of-truth attribution, and ranking is local (BM25 over name+description+capabilities) so we never ship a query to a third party. See the recommendation page for the full CLI surface and worked examples.
