Recommendation — mcpm search / install / registry

Concrete CLI surface, default sources, trust posture, and the four worked transcripts that prove the design fits a real user's day. Everything below assumes mcpd is already installed (curl-installer or Nix flake) and the user has run mcpm init once.

One-line summary

Multi-source federation seeded with official MCP Registry[1] + GitHub MCP Registry[2]; optional Docker MCP Catalog if Docker is detected on the system[3]. Per-source minisign pubkeys for index attestation[4]; Sigstore / cosign verification of underlying packages where attestations exist[5]. Search is local BM25 over a refreshed cache; queries never leave the machine.

Default sources seeded in v1.0

NameURLTrust anchorNotes
official https://registry.modelcontextprotocol.io minisign pubkey baked into mcpd binary Default source. Vendor-neutral Linux Foundation governance[6]. Uses official OpenAPI spec.[7]
github https://github.com/mcp (JSON feed) HTTPS + repo GPG verification Curated, GitHub-identity-backed. Heavy overlap with official source — merge dedupes by canonical server.json#name.
docker (opt-in default) https://github.com/docker/mcp-registry cosign on the OCI images Auto-enabled if Docker is detected at mcpm init time; user can disable.

Not bundled by default but documented in a one-liner: Smithery[8], Glama[9], PulseMCP[10]. Each has a copy-pasteable mcpm registry add line in our docs.

CLI surface in full

mcpm search

mcpm search <query> [--source <name>] [--language py|ts|go|...] [--transport stdio|http]
                    [--limit N=20] [--json] [--no-cache]
                    [--include-experimental] [--has-secret] [--license <spdx>]
  • Default behaviour: queries the local cache of every enabled source, scored locally with BM25 over name + description + tags + capabilities, results union-merged across sources, dedupe key is server.json#name.
  • Query is never sent to a third party. The only network traffic search generates is the periodic index refresh, which fetches the source's published manifest in full and is the same request every user makes regardless of query.
  • Output: one row per server: name, source(s), one-line description, latest version, language, transport, license, trust pills (signed / provenance / curated).
  • Cache freshness: indexes refresh on-demand if older than 6h; --no-cache forces refresh. Air-gap users pin to --cache=full at registry-add time and refresh manually.

mcpm install

mcpm install <server>[@version] [--source <name>]
                     [--runtime devenv|docker|podman|uvx|npx]
                     [--scope user|project] [--name <alias>]
                     [--dry-run] [--accept-unsigned] [--review]
  • Resolves server against the local cache. If ambiguous across sources, prompts (or fails with --source required in non-interactive mode).
  • Verifies the source's index signature, then verifies the package's own attestation if present (npm Sigstore[5], cosign for OCI[11]). If neither exists, the user must pass --accept-unsigned.
  • Picks an isolation runtime per the rules in stoic-badger-sandbox: devenv + sandbox-exec/bwrap by default; Docker if the user passed --runtime docker or the package's packages[].registryType == "oci"; uvx/npx pinned-version escape hatch only with --accept-unsigned or explicit --runtime.
  • Renders a sandbox spec for stoic-badger-sandbox, writes the canonical [servers.<name>] block to ~/.config/mcpd/servers.toml, and emits the secret-reference placeholders for any declared env var that has secret: true in the manifest. (Resolution is secrets-lifecycle's job.)
  • Does NOT push to client config files — that's clever-fox-bridge's projection step, which runs on the next reconciliation.
  • --review opens the resolved server.json in $EDITOR before writing — the security-conscious user's "I want to read what I'm about to run" affordance.[12]

mcpm registry

mcpm registry add <name> <url> [--signed-by <pubkey-file|fingerprint>]
                              [--auth-header <header>] [--api-key-env <VAR>]
                              [--cache full|index] [--priority N]
                              [--license-flag] [--telemetry-acknowledge]

mcpm registry list [--json]
mcpm registry remove <name>
mcpm registry refresh [<name>]      # force re-fetch index now
mcpm registry verify [<name>]       # validate signatures + schema
  • --signed-by mirrors apt's signed-by[13]. Without it, the user is opting into maintainer-trust-only and we emit a warning at add time, every install from that source, and on every list.
  • --telemetry-acknowledge is required to add any source that ships telemetry (we detect this via a flag in the source's OpenAPI metadata, where present, and otherwise via our maintained "known-telemetry sources" list). Per our no-telemetry constraint, the default is always-refuse; --telemetry-acknowledge is the explicit per-source opt-in.
  • --cache=full downloads the entire source index for air-gap; index downloads just the manifest with names+versions.
  • --priority breaks ties in result merging (lower number = higher priority); default 100.

Trust & provenance posture

Three independently-verifiable layers, with v1.0 only enforcing layer A:

LayerWhat's signedToolv1.0 enforcement
A. Registry indexWhole source manifest (the JSON we cache)minisign (Ed25519)[4]Required for default sources. User-added sources warn loudly if absent.
B. Package provenanceThe npm/PyPI/OCI package the server runs fromSigstore + Fulcio + Rekor[11][14]Verified when present, never required. Absence shown as a pill.
C. Container imageOCI artifactcosign[11]Verified for docker source; absence aborts install on the docker source.

We do not stand up a Sigstore-like service ourselves. We do not maintain a key escrow. The official registry's minisign pubkey ships baked into the mcpd binary — same model as how OS package managers ship trusted-keys.gpg. Rotation requires a mcpd release. This is acceptable at v1.0 cadence.

TUI integration

The TUI's "Add server" pane reuses the same registry adapters and the same local index. From the TUI:

  • / opens an incremental search bar — same BM25 backend, same dedupe, same trust pills.
  • Selecting a result reveals an expanded server.json preview pane (the --review equivalent).
  • Enter triggers the same install flow.
  • Telemetry sources are shown with a glowing pill; first install from one re-prompts.

On-disk config shape

Registry config lives in ~/.config/mcpd/registries.toml (separate file from servers.toml to keep schemas independent and make secrets-lifecycle's job easier):

schema = "mcpd.registries.v1"

[registries.official]
url       = "https://registry.modelcontextprotocol.io"
signed_by = "builtin:official-v1"      # baked into mcpd binary
priority  = 100
cache     = "index"

[registries.github]
url       = "https://github.com/mcp"
signed_by = "builtin:github-mcp-v1"
priority  = 100
cache     = "index"

[registries.docker]
url       = "https://github.com/docker/mcp-registry"
signed_by = "builtin:docker-mcp-v1"
priority  = 100
cache     = "index"
enabled   = true                       # auto-set true if `docker` in PATH at init

[registries.bigcorp]
url            = "https://mcp-registry.bigcorp.internal/v0.1"
signed_by      = "file:/etc/bigcorp/mcp-registry.pub"
priority       = 50
cache          = "full"
auth_header    = "X-BigCorp-Cert: ${file:/etc/bigcorp/cert.pem}"
telemetry_ack  = false
license_flag   = "Apache-2.0"

Open questions for the orchestrator

  1. Pubkey rotation cadence. If the official registry rotates its minisign key, do we ship a hotfix mcpd release or fetch a key-rotation manifest at runtime? The latter is more flexible but adds a bootstrap-trust question. Recommend: hotfix release for v1.0.
  2. What is the threshold for auto-enabling the docker source? "Docker in PATH" is the obvious heuristic, but a user might have Docker installed for unrelated reasons and not want a third source by default. Recommend: ask once during mcpm init rather than auto-enable.
  3. How does mcpm install interact with the onboarding stream's first-run wizard? First-run probably wants to show the top-10 most-likely-useful servers from the seeded sources; that needs a "featured" tag in the manifest that the official registry doesn't yet expose. Coordinate with onboarding-flow.
  4. Should we expose a mcpm registry trust <name> verb to upgrade a maintainer-trust-only source to signed-by after the fact? Useful when the user knows the registry just hasn't shipped signing yet. Recommend: yes, but v1.1.
  5. Search-query privacy when using semantic-search sources. Even with explicit --telemetry-acknowledge, do we want a "private mode" envelope (Tor / proxy) for high-paranoia users? Probably no for v1.0 — this is what "don't add the source" is for.
  6. Dedupe key for cross-source results. The official spec's name field (e.g. io.github.linear/mcp-server) is the natural key, but Smithery/Glama use their own slugs. Do we re-key on first observation or maintain per-source name? Recommend: maintain per-source name but offer canonical alias via the source adapter.
  7. Per-project vs user scope for installed servers. --scope project writes to ./.mcpd/servers.toml alongside the repo. This conflicts with the secrets-lifecycle stream's choices about per-project secret stores — need alignment.
