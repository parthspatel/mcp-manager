Recommendation — primary path + escape hatch

This is the only page in the stream where opinions appear. Everything below is derived from the cited research pages and the ranking matrix.

Two-tier model

Primary path: a per-MCP-server devenv.nix profile, supervised by the MCP Manager daemon, with the running process wrapped in the best-available OS sandbox (bubblewrap on Linux, sandbox-exec on macOS, AppContainer on Windows). Secrets are declared in a secretspec.toml next to the profile and pulled at launch time from the OS keychain via libsecret / Keychain / DPAPI.

Escape hatch: when Nix is not installed and the user does not want to install it, the manager falls back, in order, to (1) Docker MCP Toolkit catalog images, (2) Podman rootless containers, (3) version-pinned uvx / npx wrapped in the OS sandbox layer. Raw npx without a pin is supported but flagged as insecure in the UI.

Ranked strategies

  1. devenv + OS sandbox — best reproducibility and strong run-time isolation. Recommended primary path. Cost: requires Nix.
  2. Docker MCP Toolkit — best cross-platform, signed-catalog story. Recommended fallback when the user has Docker.
  3. Podman rootless — strongest container-side isolation (rootless by default), Linux-first.
  4. Bubblewrap / sandbox-exec / AppContainer + pinned uvx/npx — lightweight middle ground; reproducibility limited to lockfiles.
  5. devenv naked — strong build reproducibility, weak run-time scoping. Acceptable on trusted dev machines but not a default.
  6. Raw npx / uvx with version pins + lockfile — “works today” tier; what most MCP host apps default to.
  7. Raw npx latest / OS native install — never the default. Available for one-off experimentation only, behind a confirmation prompt.

Why this shape, in one paragraph

The MCP specification explicitly declines to enforce isolation at the protocol level: that responsibility belongs to the host. Documented real-world attacks (npm supply chain, CVE-2025-6514) show that the “just run npx” status quo is unsafe by default. A reproducible build (devenv) closes the supply-chain surface; an OS sandbox closes the run-time surface; together they form the strongest defence available without forcing every user into containers. Containers remain the obvious fallback because they map most uniformly across Linux, macOS, and Windows.

What the manager must ship

  • A Rust sandbox orchestration crate with platform back-ends: bubblewrap on Linux, sandbox-exec on macOS, AppContainer + Job Objects on Windows. The policy is the same declarative schema across all three; back-ends translate to each native language.
  • A devenv adapter that builds a profile, exposes its activation environment to the spawn call, and tracks generations for atomic rollback.
  • A container adapter that consumes the Docker MCP Catalog format and runs against Docker or Podman with comparable constraints.
  • A SecretSpec wrapper for secret declaration + delivery, defaulting to the OS keyring via the Rust keyring crate.
  • A clear UI affordance that surfaces the active isolation tier per server (“Nix + bubblewrap”, “Docker”, “uvx pinned”, “raw — insecure”).

What the manager should not ship

  • A custom secrets vault. Delegate to OS keychain or external store via SecretSpec / Vault Agent.
  • A custom container runtime. Reuse Docker / Podman.
  • Its own SBPL profile authoring tool. Ship a small curated profile library and let advanced users edit raw .sb files.

Honest acknowledgements

Nix has a real learning curve

The decision to make Nix the primary path means the manager has to absorb the “flatten the learning curve” cost itself: ship pre-authored devenv profiles for the popular MCP servers, document failure modes in plain language, and never make a Nix expression the first thing the user has to read. devenv mitigates this meaningfully but does not eliminate it.

macOS sandbox-exec is deprecated

It works on every shipping macOS and is still used by Apple internally, but Apple has not committed to a long-term replacement for headless / CLI sandboxing. The manager needs a contingency: if a future macOS release removes sandbox-exec, fall back to container-based isolation via Docker / Podman as the macOS path.

Windows is the weakest tier

Nix on Windows means WSL; AppContainer authoring is non-trivial; Docker Desktop carries a licence. The honest answer for Windows is “Docker MCP Toolkit by default,” with AppContainer-direct as an advanced path that not all servers will work under. WSL-with-devenv is a power-user option but not the on-ramp.

Cold-start cost is real

If host apps frequently spawn short-lived MCP server instances, the per-spawn container cost (~1s) is meaningful. devenv-plus-sandbox keeps native exec latency. The manager should prefer long-lived supervised processes over per-call spawning where possible.

Boundaries with other streams

  • steady-bear-foundation owns the daemon & supervision model; this stream specifies what spawn / lifecycle calls have to support (devenv eval, bwrap fork, container start).
  • precise-crane-conduit owns the wire protocol; secret-handling envelopes (do not log values, redact in transit) belong there.
  • curious-otter-survey owns the host-app config schemas this manager will need to translate to / from.

One sentence

Ship devenv as the reproducibility layer, ship the best-available OS sandbox as the run-time layer, ship Docker / Podman as the escape hatch, delegate secrets to the OS keyring, and never let raw npx latest be the default path.
