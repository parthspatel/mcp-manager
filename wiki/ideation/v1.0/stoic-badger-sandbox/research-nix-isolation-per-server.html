Per-MCP-server devenv profiles

A neutral inventory of what "one declarative environment per server" looks like in practice using devenv.sh. Examples cover Python servers via uv, Node servers via npm/bun, Rust/native binaries, and atomic upgrade and rollback.

Mental model

Every MCP server gets its own directory containing a devenv.nix, a devenv.yaml, and a devenv.lock. The MCP Manager treats that directory as the unit of installation: launching the server is a matter of evaluating the devenv expression and exec-ing the resulting entry point inside the resulting Nix closure. The closure pin in devenv.lock guarantees that two machines installing the same server get bit-identical toolchains.

Concrete examples

Python MCP server pinned with uv

# devenv.nix
{ pkgs, ... }:
{
  languages.python.enable  = true;
  languages.python.version = "3.11.6";

  # uv is shipped as a first-class Nixpkgs binary;
  # combined with uv.lock this pins every transitive Python dep.
  packages = [ pkgs.uv ];

  env.UV_PYTHON_DOWNLOADS = "never";   # force Nix-provided Python
  env.UV_LINK_MODE        = "copy";    # avoid hardlinks into /nix/store

  enterShell = ''
    uv sync --frozen
  '';

  processes.mcp-server.exec =
    "uv run python -m mcp_server_filesystem --root \"$MCP_ROOT\"";
}

The uv runner itself is fast (Rust-based) and exposes ephemeral isolated venvs via uvx, but combined with a Nix-pinned interpreter it gives a fully reproducible Python closure.

Node MCP server pinned with npm

# devenv.nix
{ pkgs, ... }:
{
  languages.javascript.enable      = true;
  languages.javascript.package     = pkgs.nodejs_20;
  languages.javascript.npm.enable  = true;
  languages.javascript.npm.install.enable = true;   # run npm ci in enterShell

  processes.mcp-server.exec =
    "node ./node_modules/.bin/mcp-server-everything";
}

This pins Node 20 from Nixpkgs and re-runs npm ci when package-lock.json changes. The MCP server is started by path, never by npx — avoiding the “curl | bash”-class supply-chain pattern that npx resolution introduces.

Bun MCP server

# devenv.nix
{ pkgs, ... }:
{
  languages.javascript.enable     = true;
  languages.javascript.bun.enable = true;

  enterShell = ''
    bun install --frozen-lockfile
  '';

  processes.mcp-server.exec = "bun run src/index.ts";
}

devenv ships a bun.enable toggle that pulls Bun from Nixpkgs and respects bun.lockb.

Rust / Go / native binary

# devenv.nix
{ pkgs, ... }:
{
  languages.rust.enable  = true;
  languages.rust.channel = "stable";

  packages = [ pkgs.openssl pkgs.pkg-config ];

  processes.mcp-server.exec = "cargo run --release -- --transport stdio";
}

For pre-built binaries you can substitute packages = [ self.packages.${system}.my-mcp-server ]; referencing a flake output, getting a fully built artifact pinned by hash.

Atomic upgrade and rollback

Because each devenv evaluation produces a new Nix profile generation, "upgrade" is replacing a symlink and "rollback" is replacing it back. The MCP Manager can record the previous generation's store path before activating a new one and expose a one-shot rollback API. No partial-update window, no half-installed servers. 

# conceptual pseudocode
prev = current_generation(server_id);
new  = devenv_build(server_dir);     # produces new /nix/store/... path
swap_symlink(server_id, new);        # atomic rename
on_failure_within(5s, () => swap_symlink(server_id, prev));

What “reproducible” concretely means here

DimensionPinned by
Interpreter / runtime version (Python, Node, Bun)devenv.nix + devenv.lock
Transitive language depsuv.lock / package-lock.json / bun.lockb / Cargo.lock
System libraries (OpenSSL, libffi, libxml2…)nixpkgs revision in devenv.lock
Build sandbox / chrootNix builder, automatic
Environment variables visible at buildEmpty by default in Nix builds

Where this approach doesn't isolate

A devenv profile is a build-time isolation construct. At runtime, a process launched from a devenv shell still inherits the host filesystem, network, and process tree unless an OS sandbox is layered on top. The next page, runtime sandboxing, covers that second layer.

Practical footnotes

  • devenv supports composition: a "base" profile common to all MCP servers can be imported, and each server overrides what it needs.
  • Nix's binary cache (cachix) lets a team pre-build profiles once, then pull binaries on every other machine — important for cold-start UX.
  • devenv.yaml can pin the devenv version itself, so the manager can guarantee “this server was authored against devenv X.Y” even years later.
