Nix & devenv — what they actually are

This page is just-enough background to make the rest of the stream readable. It explains the Nix store, derivations, flakes, and where devenv.sh fits on top. It does not make recommendations.

Nix in one paragraph

Nix is a purely functional package manager. Every package is built from a Nix expression (a "derivation") whose hash captures every input — source, build script, dependencies, even build-time environment variables. The result is dropped into an immutable, content-addressed location under /nix/store/<hash>-<name>. Two systems that evaluate the same expression with the same inputs produce the same store path; the same store path can never be silently replaced. This is the core of Nix's reproducibility model.

The Nix store, mental model

  • Hash-addressed: /nix/store/abc123…-python-3.11.6/bin/python3. Different versions live side by side, never overwriting each other.
  • Closure: a built artifact references every store path it needs at runtime. Garbage collection happens against these references — nothing reachable is removed.
  • Atomic upgrades / rollbacks: a "profile" is a symlink to a generation. Pointing it at the previous generation is a constant-time operation; no partial-update window exists.

Derivations

A derivation is a JSON-like description of a build: inputs, builder script, environment, output names. Evaluating Nix code produces derivations; building a derivation produces store paths. The promise is that building the same derivation twice yields the same result. 

# minimal derivation example
{ stdenv, fetchurl }:
stdenv.mkDerivation {
  pname   = "hello";
  version = "2.12.1";
  src     = fetchurl {
    url    = "mirror://gnu/hello/hello-2.12.1.tar.gz";
    sha256 = "086…";
  };
}

Flakes

Flakes are an experimental layer that gives a project a canonical entry point — a flake.nix file with inputs (pinned dependencies) and outputs (packages, dev shells, apps, NixOS configurations). A companion flake.lock records the exact commit and content hash of every input, the same way package-lock.json or Cargo.lock pins JavaScript or Rust deps. Two checkouts of a repo with the same lock file build identical artifacts. 

# flake.nix skeleton
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-24.05";

  outputs = { self, nixpkgs }: {
    devShells.x86_64-linux.default =
      nixpkgs.legacyPackages.x86_64-linux.mkShell {
        packages = [ /* …pinned tools… */ ];
      };
  };
}

Flakes remain officially "experimental" and the model has known coupling and composability rough edges, but they are how virtually every new Nix project pins its inputs.

FHS sandboxing and the build sandbox

Nix builds run in a sandbox: a stripped /nix/store-only filesystem view, no network (except for fixed-output fetches with a known hash), no access to /etc, /home, or other host state. This is what makes "build it twice, get the same output" plausible. The same sandboxing primitive — namespaces on Linux, chroot-style on macOS — is later reusable for runtime isolation of the resulting binary.

What devenv adds

devenv.sh is a higher-level wrapper around Nix aimed squarely at developer environments. Instead of writing raw Nix derivations, you toggle pre-baked modules: 

# devenv.nix — turn-on-by-toggle
{ pkgs, ... }:
{
  languages.python.enable  = true;
  languages.python.version = "3.11.3";
  languages.javascript.enable = true;
  languages.javascript.package = pkgs.nodejs_20;

  packages = [ pkgs.ripgrep pkgs.uv ];

  enterShell = ''
    echo "MCP server env ready"
  '';

  processes.echo.exec = "while true; do date; sleep 5; done";
}

devenv claims activation in roughly 100 ms once warm, layers process supervision and service definitions on top, and has built-in integrations for git hooks, task runners, and (importantly for this stream) secret management.

Closure determinism — why it matters here

Because every byte that a server depends on is hash-addressed and pinned by flake.lock, the identity of the binary stack is auditable. For an MCP Manager that wants to say "this is server x.y.z with these dependencies, signed and reproducible," Nix's closure semantics give a stronger foundation than "I ran npx and hope it pulled the same tree as last week."

Caveats up front

Learning curve is real

Community surveys and long-form retrospectives consistently call out three independent burdens: the Nix language itself, the conventions of nixpkgs, and reasoning about whatever upstream tool is now living inside Nix. Pierre Zemb, Richard Goulter, and the NixOS documentation team all flag this as a primary adoption blocker.

Windows is second-class

Nix runs on Linux and macOS; Windows requires WSL. Any tool that ships Nix as its primary isolation strategy needs a documented Windows escape hatch from day one. (See escape hatch.)

Flakes are still experimental

The flag --extra-experimental-features 'nix-command flakes' is still required on default Nix installs. The semantics are stable in practice but the bar for "officially supported" hasn't been crossed.
