Escape hatch for non-Nix users

Not every user wants Nix on their machine. This page surveys what the MCP Manager can offer instead: containers (Docker, Podman), language-native isolated runners (uvx, pipx, npx), and OS package managers — and what each option costs in reproducibility, install friction, and isolation strength.

Container runtimes

Docker MCP Toolkit

Docker ships a first-party MCP integration: a managed toolkit + a catalog of 300+ vetted MCP servers as signed container images. Each tool runs in its own container with a default 1-CPU and 2 GB-of-RAM cap, no host filesystem unless the user explicitly mounts a path, and an interception layer that blocks tool I/O containing secrets. 

# conceptual: run an MCP server image with the manager
mcp-manager add docker://mcp/server-filesystem@sha256:abc...
mcp-manager run server-filesystem --mount /home/me/projects/foo:/work:ro

Strengths: zero authoring for end users — the image already exists. Provenance is built into the catalog with image signing. Weaknesses: requires Docker Desktop (licensing constraint for some orgs), and cold-start cost is >1 s per container — non-trivial when many short-lived MCP servers are spawned.

Podman (rootless)

Podman is daemonless and rootless by default. Each container is a child of the user session, not a privileged daemon, and Linux user namespaces map the in-container root UID to an unprivileged host UID. Containers receive 11 capabilities by default (vs Docker's 14) and store images under $HOME rather than /var/lib/docker.

For an MCP server lifecycle that mostly stays inside one user account, Podman's no-daemon model is a closer fit than Docker. Trade-off: per-container start-up is comparable to Docker (slow relative to native exec), and rootless restrictions on privileged ports rarely matter for MCP because servers communicate over stdio or localhost.

Language-native isolated runners

uvx (Python)

uvx is uv's ephemeral runner: it materialises a fresh, isolated venv, installs the requested package, and execs it. The venv is cached, so cold runs take ~1 s and warm runs tens of milliseconds. It supports --python 3.11 and downloads the interpreter automatically if not present. 

# versioned, isolated execution
uvx --python 3.11 mcp-server-fetch@1.2.3 --help

uvx isolates by venv, not by OS sandbox — the running process still has full filesystem and network access.

pipx (Python)

pipx pioneered the isolated-venv-per-CLI-tool pattern. It is pure Python (slower than uv), has unique features uv lacks (pipx inject, manual pages, --global), and is widely pre-installed by distros.

npx / bunx (Node ecosystem)

npx pkg@ver fetches and executes a package. Unlike uvx, npx by default fetches latest if no version is pinned. Most JS MCP servers are launched this way today — and the security community has documented this as a "curl | bash"-class supply-chain vector. Pinning versions is mandatory: npx -y @modelcontextprotocol/server-filesystem@2025.11.18, not npx -y @modelcontextprotocol/server-filesystem. CVE-2025-6514 (CVSS 9.6) is the canonical recent example of full RCE against an MCP client via a hijacked Node MCP server.

Native installs (brew / apt / choco)

OS package managers give the lowest install friction once a user already has the relevant tooling. Reproducibility is OS-dependent (Homebrew bottles vs apt pinning vs Chocolatey), and isolation is effectively zero — the binary runs with the user's full permissions. This is the “just got something working” tier of the escape hatch and the manager should treat it as opt-in.

Pairing escape-hatch runners with an OS sandbox

A manager that wants “decent isolation without requiring Nix” can compose:

  • Linux: bwrap … -- uvx pkg@ver
  • macOS: sandbox-exec -f profile.sb uvx pkg@ver
  • Windows: launch the runner inside an AppContainer with internetClient and minimal capabilities

This recovers some of the runtime-isolation story devenv-plus-sandbox provides, at the cost of giving up build-time reproducibility (the venv contents still depend on what PyPI / npm serve at fetch time).

Summary of the escape-hatch ladder

  1. Best fallback: Docker MCP Toolkit catalog images (when the user has Docker).
  2. Linux-native fallback: Podman rootless containers.
  3. Lightweight fallback: uvx/npx with explicit version pins and lockfiles.
  4. Last resort: OS package manager. Track installed version for upgrade nags; no isolation.
