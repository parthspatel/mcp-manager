Projection mechanics

A "projection" is the act of taking a canonical record of one MCP server in mcpd's state store and writing the on-disk representation that a specific tool expects. This page enumerates the mechanical transforms involved — schema mapping, env-syntax translation, secret-reference rewriting, transport coercion, capability mapping, MCP-spec-version negotiation — and the idempotency invariants the writer must preserve.

The canonical record

The projector is downstream of Stream 3's state store and Stream 4's wire protocol; it does not invent any new abstraction over McpServer. The canonical record for one server is approximately: 

// pseudo-rust; the real type lives in mcpd
struct McpServer {
    id: ServerId,                  // stable UUID
    name: String,                  // user-visible
    transport: Transport,          // Stdio { command, args } | Http { url } | Sse { url }
    env: BTreeMap<String, EnvValue>,
    headers: BTreeMap<String, HeaderValue>,
    secret_refs: Vec<SecretRef>,   // references resolved at projection time
    spec_version: McpSpecVersion,  // minimum MCP version the server requires
    capabilities: ServerCapabilities,
    enabled: bool,
    projection_targets: Vec<ToolchainTarget>, // which tools this entry should be projected into
}

The projector reads this, queries the toolchain manifest for the target (one of Tier-1/Tier-2 catalog entries plus any user-defined toolchains), and emits a target-specific file or fragment.

Env-syntax translation

Every host invents its own env-expansion syntax (Stream 1's schema page documents this). Projection must rewrite from the canonical form to the target's expected form:

TargetEnv syntaxResolution time
Claude Code${VAR} / ${VAR:-default}server-start
VS Code${env:VAR} + ${input:id}config-load + prompt
Cursor${env:VAR} + envFileserver-start
Continue${{ secrets.X }} onlyconfig-load
Codexnone (literal strings)n/a
GooseOS keyring refs in env mapserver-start

For targets without env-expansion, the projector inlines the resolved value at write time, with the caveat that it must NEVER inline a secret. For targets with expansion, the projector emits a reference in the target's native syntax that resolves at the target's resolution time.

Secret-reference rewriting

The strongest projection-time invariant is: no secret material ever crosses the projector into a plaintext file. Stream 3 owns secret storage in the OS keyring; the projector's job is to rewrite secret_refs into target-specific reference syntax:

TargetBest available referenceFallback
VS Code${input:id} with the input declared in the inputs array; VS Code stores it in its own secret storen/a
Claude CodeheadersHelper command that shells out to mcpm secret print KEY${VAR} with a stub in the user's profile
GooseRefer to OS keyring entry by namen/a
CursorenvFile pointing at ~/.config/mcp-manager/secrets/<target>.env that mcpd materializes with restrictive permissions at projection timedirect env
Codex / Continue / Cline / WindsurfNone native; the projector emits a wrapper command (mcpm exec --secrets-from KEY -- <real command>) that injects env at process-startnone
JetBrainsIDE keychain reference via project-level XML; UI-drivennone

The wrapper-command fallback is the universal escape hatch. It works for every stdio transport because we can always interpose ourselves; we lose the ability for stdio targets to launch the server without mcpd running, but this is an acceptable trade in v1.0. The pattern matches podman's reference-based secret model.

Transport coercion

The MCP spec defines two transports — stdio and Streamable HTTP — with HTTP+SSE deprecated as of 2025-06-18. Targets have different transport support:

  • Stdio is universal.
  • Streamable HTTP is supported by Claude Code, VS Code, Continue, Cursor (recent versions), Cline, LibreChat.
  • SSE is still accepted by some hosts as a legacy alias.
  • Codex CLI supports stdio only.

For a target without HTTP support but a canonical record that uses HTTP transport, the projector has two choices: (a) emit a stdio wrapper (mcpm proxy --remote <url> that bridges stdio to HTTP); (b) skip the projection and surface a warning in the GUI/CLI. v1.0 picks (b) as default with (a) opt-in to avoid silent semantic drift.

These map cleanly to optional fields on McpServer and are emitted only into targets that understand them.

MCP-spec-version negotiation

The canonical record carries a spec_version (the minimum spec version the server requires — informed by the MCP lifecycle handshake). Targets fall into three buckets:

  • Always-current — Claude Code, VS Code; the projector assumes the latest spec without coercion.
  • Pinned — Goose, Continue (per release); the projector consults a table in the toolchain manifest declaring the supported spec range.
  • Unknown — LibreChat, Windsurf; the projector emits both modern and legacy fields when format allows, otherwise emits modern and surfaces a warning.

Idempotency invariants

Three rules the writer must obey, derived from prior art in chezmoi and home-manager:

  1. Re-projection without canonical change yields a bit-identical file. No timestamps, no nondeterministic key ordering, no random UUIDs in output.
  2. Re-projection after canonical change touches only the managed region. Hand-edited surrounding content survives byte-for-byte. This is the managed-block requirement.
  3. Removal of all managed servers from canonical state collapses the managed region cleanly. The fence markers vanish; surrounding content snaps closed without leftover whitespace. (Matches FreeBSD etcupdate's "delete-aware merge" mode.)

The writer implementation uses content-addressed projection: serialize the canonical record set to a stable bytestring, hash it, and on every projection compare the hash to a sidecar .mcp-manager.lock beside the projected file. If the hash matches, no write. If it differs, parse the existing target file, splice the new managed block, write atomically via rename. See research-toolchain-sync-modes for the full strategy comparison.
