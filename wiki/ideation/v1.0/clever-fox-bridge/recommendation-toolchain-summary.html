Recommendation — Toolchain projection design

This is the only page in the stream where opinions live. The argument: MCP Manager treats every supported tool as a data-driven toolchain manifest, not a hardcoded code path; the default sync mode is managed-block with sentinel-key fencing for pure-JSON tools and sibling-file projection where the tool natively supports it; conflict resolution defaults to preserve & report; the user-extensibility format is TOML.

TL;DR

  • Tier-1 (auto-detected, projected by default with first-time consent): Claude Code CLI, Codex CLI, VS Code, Cursor, Zed, JetBrains family (IntelliJ / PyCharm / RustRover / WebStorm / CLion / GoLand — treated as one logical target with per-product instances). 6 tools / families
  • Tier-2 (supported, opt-in): Windsurf, Continue, Cline, Goose, LibreChat, Claude Desktop. 6 tools
  • Default sync mode: managed-block (or sentinel-key fence on pure JSON, or sibling-file where supported). Near-default
  • Conflict policy: preserve & report; mcpm sync --force degrades to backup & overwrite.
  • Escape hatch: TOML toolchain.toml files loaded from $XDG_CONFIG_HOME/mcp-manager/toolchains/. Could-flip-on-evidence — YAML if community feedback is overwhelmingly negative on TOML.

Where it doesn't, we either project to a sibling file the tool natively reads, or take the file whole (only where the file's sole purpose is MCP).

Custom toolchain escape hatch — toolchain.toml

Any user can teach MCP Manager about a new tool without modifying the binary by dropping a TOML file into $XDG_CONFIG_HOME/mcp-manager/toolchains/. The format follows the Renovate-customManagers / Homebrew-taps pattern of declaring projection as data: a target path template, a format, a mapping expression, env / secret rewriting rules, and optional pre/post hooks.

Why TOML and not YAML or JSON? TOML is what Rust ecosystem tooling already uses (Cargo.toml, mise, proto) and what mcpd itself uses for its own config. Choosing TOML keeps our format surface area small (one parser) and signals to power users that the format is meant to be hand-edited. YAML's indentation pitfalls and JSON's lack of comments both disqualify them at this layer. (If the community pushes back strongly, this is one of the recommendation's flip triggers; see below.)

Worked example: projecting into a hypothetical "Nemo" editor

Imagine Nemo is a new AI editor that just shipped MCP support. Its config lives at ~/.config/nemo/mcp.yaml, uses YAML with a top-level nemo_mcp_servers map, requires explicit transport: stdio | http, and accepts {{ env.VAR }} Jinja-style env expansion. The user adds Nemo to MCP Manager by writing: 

# ~/.config/mcp-manager/toolchains/nemo.toml

[toolchain]
id = "nemo"
display_name = "Nemo Editor"
tier = 2                          # opt-in by default; user enables via `mcpm toolchain enable nemo`
homepage = "https://nemo.example/"

[discovery]
# How to detect Nemo is installed. First match wins.
strategy = [
  { kind = "path-exists",  path = "~/.config/nemo" },
  { kind = "exec-on-path", binary = "nemo" },
  { kind = "macos-bundle", id = "io.nemo.editor" },
]

[target]
# Where the projected file lives. Templating uses {{ home }}, {{ xdg_config }}, {{ project }}, {{ os }}.
path = "{{ xdg_config }}/nemo/mcp.yaml"
format = "yaml"                   # json | jsonc | yaml | toml | xml
sync_mode = "managed-block"       # overwrite | managed-block | sentinel-key | sibling-file
fence_begin = "# BEGIN MCP-MANAGER MANAGED BLOCK"
fence_end   = "# END MCP-MANAGER MANAGED BLOCK"

[schema]
# How canonical state maps onto the target's expected shape.
# Right-hand side is a small jq-flavoured expression evaluated against the canonical server record.
container_key      = "nemo_mcp_servers"
container_kind     = "map"          # map | array
entry_key          = ".name"        # how to derive the map key (or sort index for arrays) from the canonical record
field_map = {
  command   = ".transport.command",
  args      = ".transport.args",
  url       = ".transport.url",
  env       = ".env",
  transport = '''if .transport.kind == "stdio" then "stdio" else "http" end''',
}

[env_syntax]
# How to rewrite ${VAR} references for this target's expansion language.
template = "{{ '{{' }} env.{name} {{ '}}' }}"
# escape `{{` / `}}` so the projector emits literal Jinja markers

[secrets]
# What syntax to use when a canonical secret_ref lands in this target.
strategy = "wrapper-command"
wrapper  = "mcpm exec --secrets-from {ref} -- {command} {args}"

[hooks]
# Optional; run after projection completes. Stdout captured into mcpd logs.
post_write = ["nemo --reload-config"]

[capability_map]
# Which optional fields the target understands.
supports = ["timeout", "disabled"]
ignore   = ["alwaysLoad", "autoApprove"]

That file is the entire contract. MCP Manager loads it at daemon start (and on filesystem-watcher reload), discovery probes match, projection executes through the same engine that handles Tier-1 tools. If Nemo's schema changes, the user edits one file — no MCP Manager release required.

The same engine projects Tier-1 tools too — their manifests just ship inside the binary's assets/toolchains/ directory and are loaded first. A user manifest with the same id overrides the bundled one, providing a clean override surface.

Default sync mode — managed-block

The matrix on matrix-toolchain-sync-strategy.html ranks managed-block first under the default weighting and second under every weighting we tested that didn't zero out hand-edit preservation. Its dominant strengths:

  • Preserves hand-edits outside the fence by construction (the Ansible blockinfile pattern with 10+ years of production hardening).
  • Self-documenting — the fence markers tell future humans (and future-us) what's going on.
  • Works on every format that supports line-oriented comments (TOML, YAML, JSONC, XML, INI). For pure JSON, we degrade to sentinel-key fencing or sibling-file as specified per-tool.

Push (overwrite) was rejected for the reason in the analysis page — users routinely hand-edit their MCP configs; an overwrite-by-default tool gets uninstalled within a week. Watch + reconcile was rejected because the blast radius is unacceptable when a single bad canonical record propagates to every editor on every machine in seconds. Three-way merge would be a viable v2 escalation if conflict honesty becomes a more pressing concern than implementation simplicity.

Conflict-resolution UX — preserve & report

When the projector detects the existing target file differs from the last-projected baseline (sidecar .mcp-manager.lock hash mismatch), the default behaviour is:

  1. Do not write the target file.
  2. Mark this target as "in conflict" in the daemon's state.
  3. Surface a notification in CLI (mcpm status), TUI (top status bar), and GUI (per-target badge).
  4. Provide three resolution affordances: mcpm sync --keep-local (pull user edits back into canonical), mcpm sync --force (backup-and-overwrite), and mcpm sync --merge (interactive diff3 in $EDITOR).

The default is non-destructive. --force always creates a file.bak.<ISO-timestamp> beside the target before writing, with a 30-day TTL retention policy enforced by the daemon. This matches the chezmoi precedent.

Open questions Orchestrator decides

  1. Per-project vs per-user scope as default. Stream 1 documented that hosts disagree about whether MCP config is user-scoped or project-scoped. The recommendation is silent on which scope MCP Manager itself privileges. If the daemon's canonical state is project-aware, we need to decide whether projecting into a per-user file is the "sum of all my projects" or "a default plus per-project overrides".
  2. How aggressively to detect Flatpak/Snap installs of editors. Linux discovery is correctness-vs-noise: enumerating all Flatpak/Snap sandbox roots adds latency and surfaces a lot of paths; missing them surprises Linux users when projection silently doesn't take effect.
  3. Whether the wrapper-command secrets fallback (mcpm exec --secrets-from) is acceptable in tools the user might run without mcpd running. A user who launches Cursor on a machine where mcpd isn't started will find their stdio servers fail to launch. We could ship a static binary helper that reads the OS keyring directly without needing the daemon, at the cost of a second trusted path into the keyring.
  4. Whether to ship a community toolchain registry. Should we curate https://toolchains.mcp-manager.dev/ with vetted manifests for editors as they ship MCP support, mirrored from a GitHub repo a la Homebrew taps? Or rely entirely on user-authored manifests?
  5. Lockfile location. Sidecar .mcp-manager.lock beside each projected file vs centralized ~/.local/state/mcp-manager/projection.lock? Sidecar is more debuggable; central is more atomic.
  6. Whether the JetBrains XML projector is worth shipping in v1.0 or should be deferred. XML is a different code path; if the engineering cost outweighs the user benefit relative to telling JetBrains users to use the IDE UI, we should know.

Could-flip-on-evidence triggers

  • If three or more Tier-1 tools change their schema in a way that managed-block can't accommodate (e.g. forbid unknown top-level keys), reconsider overlay/kustomize-style as default.
  • If a security incident demonstrates that watch+reconcile is required to mitigate (e.g. server compromise via edited target file), promote watch to a configurable opt-in.
  • If community feedback on TOML manifests is strongly negative, switch to YAML — the engine treats the manifest format as a parser concern, not a semantic one.
  • If MCP itself standardizes a host-config schema (long shot but discussed in spec issues), defer all projection to the standard and shrink this stream's scope to env-syntax translation and secret rewriting.
  • If JetBrains 2026.x exposes .idea/mcp.xml as stable per-project config, drop the per-IDE projection in favour of per-project alone.
